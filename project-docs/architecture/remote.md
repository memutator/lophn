# remote

폰 앱이다. pairing한 폰이 컴퓨터의 core에 붙어 lophn agent의 session 목록을 보고, 대화를 읽고 보내고 멈추고, 승인과 질문에 답하고, job을 켜고 끄고, project의 file을 읽는다. 컴퓨터의 desktop 앱에서 도는 coding agent(Claude Code, Codex, OpenCode, omp)의 대화도 같은 화면으로 보고 답하고 새로 열고, 그 터미널 화면을 보고 허락받은 기기는 친다. 폰 화면은 폰 앱(`mobile`)의 native React Native 화면이고 폰 UI kit(`@lophn/ui-native`, `ui-kit.md`)으로 짓는다. lophn 자신의 화면은 컴퓨터가 내려주지 않는다. 컴퓨터에서 도는 사용자 앱의 폰 화면(앱의 agent가 kit으로 쓴 React Native)만 컴퓨터가 bundle로 내려주고 폰 앱 안의 격리된 runtime(guest)에서 돈다(`phone-screen.md`). 컴퓨터가 폰에 묻는 길(`request`·`response` frame, 앱 backend가 폰의 위치를 읽는 첫 기능)과 폰의 홈 화면(위젯, 아이콘, open target. `phone-home-screen.md`)도 여기서 이어진다. 연결(listener, Noise, pairing)은 `platform.md`의 "폰이 붙는 listener", 기기 자격과 route 목록은 `approval.md`의 "폰(기기) 자격", 기기에 가는 event는 `event.md`가 맡는다.

## 문제

- 폰에서 일을 이어 가려면 desktop과 같은 대화·승인·Inbox 해석(ACP reducer, 승인·질문 card, 대기열, rewind)이 있어야 한다. 폰용으로 다시 짜면 같은 해석이 두 벌이 되어 고칠 때마다 맞춰야 한다.
- 폰 화면은 scroll, keyboard, gesture가 폰다워야 한다. desktop의 web 화면을 폰 WebView에 넣어 보았더니(계획 `phone-remote-web`) 폰답지 않았다. 컴퓨터가 화면을 내려주는 길(web bundle, hash 확인 cache, WebView, bridge)은 폰 껍데기를 무겁게 하고 폰에 없는 통로를 부르는 화면까지 끌고 왔다.
- 화면을 폰마다 맞춰 짜면 안 된다. 폭 320~430의 어느 폰에서나 맞아야 하고, 폭이 넓은 기기(접은 폰, tablet)에서도 깨지지 않아야 한다.
- 폰의 기기 key는 폰 안에만 있어야 하고, 화면 code가 그 key나 연결을 직접 만지지 않아야 한다.

## 목표와 비목표

- 목표: 사람이 승인한 wireframe대로 native 화면을 짓는다. 화면 아래의 로직(event client, Inbox store, 대화 source, 순수 reducer와 규칙)은 desktop과 같은 TypeScript를 쓰고 해석을 한 벌로 둔다. 화면 문구는 desktop과 같은 catalog를 쓴다. 컴퓨터 없이도 화면 모양을 볼 수 있다(sample 컴퓨터).
- 비목표: iOS build(push도 Android만이다, 사용자 앱의 폰 화면도 Android만이다), 폰의 알림 목록 화면, iOS의 위젯과 아이콘, 폰의 위치 말고 다른 기능(camera, background 위치와 위치 연속 받기, agent가 폰 기능을 부르는 길. 쓰는 예가 생길 때 하나씩 연다). coding session에서 폰이 터미널 크기를 바꾸는 것, WebView terminal, 모든 터미널 탭의 목록(보는 것은 coding session의 터미널뿐), 폰에서 이미지 붙이기와 rewind 미리보기, headless harness agent(`coding_*`)의 승인 card. 폰에서 secret 넣기(보호 입력 창은 desktop의 것), 만들기·고치기·지우기(agent, job, 앱, project, workflow 정의), provider와 model 관리, skip 켜기, session 지우기. 폰의 권한은 보기, 말하기, 답하기(승인·질문·앱 update), 켜고 끄기, 지금 돌리기, 새 session이다.

## 모델

```
폰 앱 ──(Noise 연결, call/watch frame, direct나 relay)──▶ core remote listener
  │ 컴퓨터마다 연결 하나. 모양은 desktop의 CoreSource(subscribe, current, call, watch, onEvent)
  ▼
data 층: 컴퓨터 store → event client, Inbox store, 대화 source (desktop과 같은 로직)
  ▼
화면: 뼈대(sidebar + place의 stack) 안의 native 화면. 폰 UI kit 위에 선다
```

- **뼈대.** root는 컴퓨터가 하나도 없으면 연결 흐름(pairing)에서 시작하고, 있으면 frame이다. frame은 왼쪽 sidebar(drawer)와 그 옆 place의 stack이다. 아래 tab bar는 없다. 폭 600 이상이고 높이 480 이상이면 sidebar가 늘 열려 있고 stack은 그 옆 card에 든다. 가로로 든 폰은 폭이 넘어도 낮아서 drawer로 둔다. 화면 이동은 React Navigation(native stack과 drawer)이다.
- **갈 곳.** 앱 안의 모든 곳(Home, Search, Inbox, 앱 새 판 살펴보기, Jobs, Agents, workspace, workflow 실행, file, 대화, diff, 새 session, Settings)은 하나의 union(`Place`)으로 이름 짓는다. 화면은 곳을 직접 만들지 않고 그 곳을 열어 달라고 한다. place마다 화면이 하나 등록되어 있고 그 화면은 place를 인자로 받는다. sidebar는 컴퓨터(고르기), Search, Inbox(배지), Jobs, Agents, workspace(project와 앱)와 그 session, Settings를 보인다.
- **화면.** Home(session 목록, 컴퓨터가 offline일 때의 안내), Search(session, workflow, file, job, agent 한 칸), Inbox(Now: 답할 것, 앱 새 판 살펴보기. History는 notice 목록이다), 대화(보내기, 멈추기, 승인과 질문 card, 여러 답 질문, model·mode·이름 같은 sheet, 첨부, 파일 diff), 새 session(workspace와 agent 고르기), project workspace(session, workflow, file 목록과 글 file 읽기), 앱 workspace(실행 기록과 판), Jobs(목록, 켜고 끄기, 놓친 차례 Start now), Agents(목록과 상세), Settings(Computers, Appearance, About).
- **컴퓨터의 coding agent.** 폰은 desktop의 harness GUI 대화(Claude Code, Codex, OpenCode, omp)를 lophn agent session과 같은 대화 화면과 승인·질문 card로 보고 답한다. core가 shell main이 올린 ACP 상태를 사본으로 중계하므로 대화는 기존 `acp/snapshot`·`acp/send`·`AcpUpdated`이고 목록과 view 바꾸기·열기·깨우기는 `coding_sessions/*`다(`harness-gui.md`, `acp.md`). data 층은 desktop의 harness GUI source에 폰이 읽은 `AcpState` feed를 끼운 것이다(재접속과 core의 사본 교체 때 snapshot을 다시 읽고 그동안 온 갱신은 snapshot 뒤에 접는다). source가 답하지 못하는 지난 session 목록, rewind 미리보기, 이미지는 capability로 칸이 숨는다.
  - 화면. project workspace의 Sessions 위에 그 project의 coding 목록(chat은 상태 점, 터미널에서 도는 것은 작은 Terminal 표지). 대화(`session`에 `coding`을 단 place). 터미널에서 도는 session은 대화 대신 `View terminal`과 `Switch to chat`이 서고(composer가 없다) 바꾸기 전에 sheet가 무엇이 멈추는지(도는 turn, background task, 줄 선 메시지)를 말하고 `Switch`를 눌러야 바꾼다. 못 바꾸면 이유가 한 줄이다(extension이 꺼짐, 아직 session을 모름, 도는 agent가 없음, Windows). 새 session의 agent sheet에 컴퓨터의 coding agent 넷이 한 묶음으로 서고 고르면 컴퓨터에 새 터미널 탭이 열려 그 대화로 간다(첫 메시지를 먼저 받지 않는다. 이슈 `phone-new-coding-session-opens-on-pick`). 끝난 coding session은 읽기만 되고 `Continue as chat`이 컴퓨터에서 같은 CLI session을 되살려 이어 간다(그 project의 지난 harness agent session). 컴퓨터가 그 project를 보이는 창이 없으면 열기가 컴퓨터의 문장을 그대로 보인다.
  - 앱이 꺼져 있을 때. 목록이 `shell: absent`면 그 자리에 "lophn is not running on <computer>"와 `Start lophn on the computer` 단추가 선다. 깨우기는 이 단추로만 하고 화면을 보는 것만으로는 부르지 않는다(컴퓨터에 창이 열린다). 깨운 뒤에는 터미널이 앱과 함께 죽어 있으므로 목록이 비어 있고 "No coding sessions are open"과 새 session, Continue as chat이 선다.
- **사용자 앱의 폰 화면.** 사람의 앱 가운데 폰 화면(`phone` 자리)이 있는 앱은 sidebar와 Home의 앱 줄을 누르면 앱 workspace 대신 그 앱의 폰 화면이 열린다(`phone-screen.md`). 앱 workspace(session, 실행 기록)는 화면의 ⋯ menu로 간다. 컴퓨터에서 그 앱의 preview가 돌면 ⋯ menu에 "Preview from lophn"이 서고, live 폰 화면이 아직 없는 앱은 preview가 도는 동안 앱 줄에 "Preview" 표시가 붙어 바로 preview 화면을 연다(`phone-screen.md`). 폰은 컴퓨터의 `apps/phone_screens`로 화면 목록과 manifest를 읽어 폰이 돌릴 수 있는 화면인지 보고(`phone_too_old`면 "Update the lophn app to open this screen", `screen_too_old`면 "Ask lophn on your computer to update this app"), 돌릴 수 있으면 `phone.js`를 `apps/screen_file`로 받아 bundle hash로 cache하고, view를 `app_views/open`으로 열어 guest에서 돌린다. 화면의 operation 호출과 앱 event는 host bridge로 core의 view 표를 지나고 폰이 직접 앱을 부르지 않는다. 컴퓨터가 offline이거나 앱이 안 돌면 그 사실을 말하는 화면이 서고 돌아오면 저절로 열린다. 새 release가 live가 되면 화면을 새 bundle로 다시 띄우고 "Updated to Release N" 줄을 잠시 보인다. 화면 ⋯ menu가 앱의 session, 실행 기록, 변경 청하기, 앱의 다른 폰 화면을 연다.
- **폰에서 도는 앱.** 선언의 `runs_on`에 `phone`이 든 앱(sync 앱, standalone 앱)은 폰이 backend와 data를 가져 컴퓨터가 꺼져도 열리고 쓴다(`app-sync.md`). 폰은 `apps/phone_screens`의 항목(`runs_on`, backend manifest)을 보고 `apps/phone_file`로 backend와 migration file을, sync 앱은 `app_sync/snapshot`·`snapshot_file`로 컴퓨터 DB의 사본을 받아 폰 앱 폴더(`files/apps/<컴퓨터 key>/<앱>/`)에 둔다. 컴퓨터에 닿고 앱이 앞에 있는 동안 `app_sync/push`·`pull`로 맞추고 `AppSyncChanged`를 계기로 삼는다. 이 일은 sidebar가 쥐고 있어 앱을 열지 않아도 돈다(앱 목록은 폰이 가진 사본에서도 읽어 컴퓨터가 없어도 폰에서 도는 앱은 목록에 있고 열린다). Home의 앱 tile은 컴퓨터가 offline이어도 폰에서 도는 앱은 흐리지 않고 offline 안내가 그 앱이 계속 돈다고 말한다. 컴퓨터를 지우면 그 컴퓨터의 sync 앱 폴더는 컴퓨터에 안 간 변경이 없을 때만 지우고 standalone 앱의 data는 지우지 않는다.
- **터미널 보기.** `View terminal`이 coding session의 터미널을 컴퓨터에 보이는 글과 색 그대로 보인다(`terminal_view/*`, `terminal-agent.md`). 화면을 styled text row로 그리고 각 칸은 고정폭 글꼴의 한 칸이라 열이 맞는다. `Fit width`(줄 전체를 폭에 맞춰 글자를 줄인다)와 `100%`(글자 크기를 두고 가로로 민다)가 있고 폰은 PTY 크기를 바꾸지 않는다. 앞에 있는 동안 10초마다 lease를 갱신해 컴퓨터가 화면을 밀게 하고 뒤로 가면 멈춘다. `View only`가 기본이고 컴퓨터의 Settings › Remote에서 이 기기의 "Allow typing in terminals"가 켜져 있으면 글 칸(보내기는 글만 치고 Enter를 치지 않는다)과 key 줄(Esc, Tab, Ctrl-C, 화살표, Enter)이 선다. 꺼져 있으면 그 한 줄이 선다. 터미널이 컴퓨터에서 닫히면(`not_found`) 마지막 화면을 둔 채 닫혔다고 하고, 컴퓨터가 답하지 않으면 화면이 낡았을 수 있다고 한다.
- **data 층.** 컴퓨터마다 연결 하나(`CoreSource`와 같은 모양이라 desktop 코드가 그대로 돈다) 위에 desktop과 같은 event client, Inbox store, 대화 source를 얹는다. 화면은 그 읽기 hook만 쓰고 연결을 만지지 않는다. 폰이 desktop에서 가져오는 것은 DOM과 Electron에 닿지 않는 순수 logic뿐이다. desktop file이 DOM kit이나 desktop 탭 type을 import해서 못 가져오는 순수 규칙(workflow 규칙, line diff)은 import가 깨끗한 file로 옮겨 둘이 같이 쓴다. 옮기지 못한 몇 곳은 폰이 베껴 쓴다(이슈 `phone-copies-desktop-pure-helpers`).
- **sample 컴퓨터.** dev build에서 환경 변수로 켜면 지어낸 data를 내는 컴퓨터가 목록에 든다. desktop gallery의 fake core를 같은 event client, store, hook으로 돌려 화면이 진짜 컴퓨터와 같은 모양을 받는다. 저장하지 않고 하는 일은 메모리만 바꾼다. 화면 모양은 sample로, 동작은 개발 core로 본다.
- **문구.** desktop과 같은 `@lophn/i18n` catalog다. desktop에 있는 문장은 그 key를 그대로 쓰고, 폰에만 있는 문장만 `mobile.`로 시작하는 key로 더한다. Hermes에는 `Intl.Segmenter`, `Intl.PluralRules`, `Intl.RelativeTimeFormat`이 없어 앱 시작 때 한 곳에서 영어 대체를 깐다(제목 한도의 글자 수를 code point로 세어 이모지 조합은 조금 길게 센다).
- **모양.** Appearance는 theme(시스템, light, dark)와 글 크기(small, default, large)를 이 폰의 보안 저장소에 둔다. 글 크기는 kit의 text scale 한 값으로 넘기고 화면마다 따로 고치지 않는다.
- **pairing.** 처음 열면 Welcome이다. Scan the code는 camera로 QR을 읽고, "Enter a pairing code instead"는 desktop Settings › Remote의 "Show as text"가 보이는 글(QR에 든 JSON)을 붙여 넣는다(camera가 없거나 허락하지 않은 폰, emulator). Pairing 화면이 `pair` frame으로 code와 폰 이름, OS, 화면 크기, DPR을 보내고 첫 연결이 열리기를 기다린다. Paired에서 사람이 이 폰에서 그 컴퓨터를 부를 이름("Shown as")을 확인한다. core는 자기 이름을 보내지 않아 이름을 안 정하면 주소로 부른다. 지났거나 이미 쓴 code는 Code expired, 닿지 않으면 Cannot reach 화면이다. 기기 key 쌍과 컴퓨터 목록(주소 후보, port, core key, relay 주소, 기기 id, 끊김 표시, 이름)은 보안 저장소(이 기기에서만, 잠금이 풀렸을 때만)에 둔다. 무작위는 `expo-crypto`다(Hermes에는 전역 crypto가 없다).
- **컴퓨터를 지우고 다시 pairing.** Settings에서 컴퓨터를 지울 때 그 컴퓨터에 붙어 있으면 `devices/unpair`로 컴퓨터의 자기 등록을 지우고 폰의 기록을 지운다. 닿지 않으면 폰만 잊는다. 컴퓨터는 그 폰의 key를 계속 알고 있지만 같은 key가 유효한 code로 `pair`하면 옛 등록을 새 등록으로 바꾸므로(`approval.md`) 같은 컴퓨터와 다시 pairing이 된다. 마지막 컴퓨터를 지우면 Welcome으로 돌아간다. 컴퓨터에서 기기를 끊어 `closed(credential_revoked)`를 받으면 그 컴퓨터를 "다시 pairing"으로 표시하고 다시 붙기를 멈춘다.
- **연결.** QR의 direct 주소 후보와 relay(QR에 있으면)를 같이 걸어 먼저 handshake가 된 것을 쓴다. relay 길은 바이트만 넘기므로 handshake와 그 뒤는 direct와 같다. relay를 더하기 전에 pairing한 폰은 한 번 다시 pairing해야 relay 주소를 안다. 붙을 때마다 마지막 `watch`(없으면 `[]`)를 보내고 core의 `ready`로 `ready`가 된다. 끊기면 1초에서 30초 backoff로 다시 붙는다. core가 protocol 오류로 연결을 닫은 뒤에도 다시 붙는다. 앱이 뒤로 가면 다시 붙기를 멈추고, 앞으로 오면 열린 연결에 `watch`를 다시 보내 3초 안에 `ready`가 없으면 버리고 바로 다시 붙는다. 틀린 조건(session id가 아닌 문자열 등)은 `watch`에 싣지 않는다. core가 그 조건을 이해하지 못하면 연결을 닫고, 새 연결이 마지막 `watch`를 다시 보내므로 폰이 영영 offline에 머문다. 컴퓨터 목록은 컴퓨터마다 상태(connecting, connected, offline, revoked)와 길(direct, relay), 그 컴퓨터 Inbox의 대기 수를 보인다.
- **폰 route 목록.** 기기가 부를 수 있는 route는 `approval.md`가 정한다. 폰 화면을 지으며 session·대화 쪽에 Agents, Jobs와 그 실행 기록, workflow, 앱 실행 기록과 release, project의 file 목록과 글 file 읽기(`project_files/list`, `project_files/read`)가 더해졌고, 기기가 부르는 `jobs/update`는 `{job, enabled}`만 받는다. coding agent를 위해 `coding_sessions/list|switch_plan|switch|open|wake`와 `terminal_view/snapshot|watch|input`이 더해졌다(`terminal_view/input`은 목록에 있어도 사람이 컴퓨터에서 이 기기의 입력을 켰을 때만 core가 받는다. 그 스위치 `devices/set_terminal_input`은 목록에 없다). 기기 route는 폰이 자기 등록을 지우는 `devices/unpair`와 자기 push 설정을 두는 `devices/set_push` 둘이고, 알림을 위해 `presence/report`(지금 앞에 보이는지와 열린 session)도 목록에 있다. 사용자 앱의 폰 화면을 위해 `apps/phone_screens`, `apps/screen_file`, `app_views/open|call|close`가 있고 폰에서 도는 앱을 위해 `apps/phone_file`과 `app_sync/push|pull|snapshot|snapshot_file`이 있다(앱을 직접 부르는 `apps/call_tool`, grant, 화면 오류를 쓰는 `apps/log_view_error`는 없다). 홈 화면 위젯을 위해 `app_widgets/list`가 있다(`phone-home-screen.md`). 앱이 폰에 묻는 `app_phone.request`는 폰 gate에 없다. `devices/clear_push`와 `devices/push_targets`는 core 안 machine 자격만 부르고 폰은 부를 수 없다. 화면은 목록 밖 route를 부르는 단추를 보이지 않는다(Inbox에 job 거절이 없고 job 이름·때 고치기가 없다).
- **컴퓨터가 폰에 묻는 길.** core가 폰에 일을 시키는 길은 하나다. remote channel에 frame 둘이 있다: core→폰 `request {id, kind, input, deadline_ms}`(deadline은 1~60초)와 폰→core `response {id, ok, value | error}`(`result`와 같이 ok로 가른다). `kind`는 폰이 하는 일의 이름이고 폰은 답할 kind를 handshake 뒤 `hello`의 `capabilities`에 적는다. core는 거기 없는 kind를 묻지 않으므로 옛 폰은 `request`를 받지 않고 `REMOTE_PROTOCOL_VERSION`은 그대로다. kind는 표 하나(`PHONE_KINDS`)에 입력 schema, 출력 schema, deadline과 같이 한 항목이고, 새 일은 그 항목 하나와 폰의 handler 하나로 더한다. frame은 바뀌지 않는다. 답의 bytes는 `value` 안의 `*_base64` 문자열에 base64로 싣고 원래 8 MiB 안에서 frame 상한(16 MiB)에 든다.
  - core의 `PhoneLink.call({device, kind, input, deadline_ms})`가 묻는다. 그 기기의 열린 연결에 `request`를 보내고(같은 기기의 연결이 여럿이면 마지막 것) 같은 연결에서 온 같은 `id`의 `response`, deadline, 연결 닫힘 가운데 먼저 온 것으로 끝낸다. 연결이 없거나 닫히면 `unavailable`(`phone_unreachable`), 폰이 그 kind를 `capabilities`에 적지 않았으면 `unavailable`(`unsupported`), deadline까지 답이 없으면 `unavailable`(`timeout`)이다. 모르는 `id`의 답, deadline 뒤의 답, 다른 연결(다른 기기)의 답은 버린다. 폰을 push로 깨우지 않는다. 입력과 출력이 kind에 맞는지는 묻는 쪽이 본다.
  - 폰의 handler는 앱이 앞에 있을 때만 답한다(아니면 `unavailable`, `phone_in_background`). 입력은 kind의 schema로 본다(틀리면 `invalid_input`). 답이 deadline 뒤에 올 일이면 보내지 않는다. kind는 handler가 있는 것만 `hello`에 적는다.
  - 첫 kind는 `location.get`이다. 입력 `{accuracy?: low|balanced|high, max_age_ms?: 0~300000}`(기본 balanced와 0, 기본은 폰이 적용한다), 출력 `{lat, lon, accuracy_m, at}`, deadline 20초다. 폰은 OS의 앞에 있을 때 위치 권한만 쓰고(background 권한은 manifest에 없다) 처음 쓸 때 한 번 OS에 묻고 거절하면 다시 묻지 않는다(`forbidden`과 `details.reason: "os_permission_denied"`. 사람이 시스템 설정에서 바꾼다). OS의 위치 서비스가 꺼져 있으면 `unavailable`(`location_off`)이고, `max_age_ms`가 있으면 그 안의 마지막 위치를 먼저 쓴다.
  - 앱의 길은 이 길 위의 하나다. 앱 backend가 SDK part `@lophn/cap-phone`의 `getLocation`을 부르면 앱 supervisor의 broker(`/_lophn/broker/phone/request`)가 live 자식인지, 지금 release의 선언 ∩ grant에 `phone.use {capability}`가 있는지를 요청마다 보고(없으면 `forbidden`이고 폰에는 묻지 않는다) core의 memory route `app_phone.request`(actor app)를 그 자식의 credential로 부른다. core는 앱이 active인지, 입력이 kind에 맞는지 본 뒤 사람의 기준 폰(`devices.is_primary`)에 묻고 폰의 답이 kind의 출력에 맞는지 보고 앱에 준다(안 맞으면 `unavailable`). 기준 폰이 없으면 `unavailable`(`no_phone`)이다. `app_phone.request`는 폰이 부르는 route가 아니다(폰 gate에 없다). 위치를 읽는 일은 lophn의 banner를 띄우지 않고 기록을 쓰지 않는다. 동의는 앱의 activation 동의 카드(`activation.md`)이고 읽는 것을 사람에게 보이는 것은 Android 자신의 위치 표시다.
  - drive(`drive.snapshot|act|screenshot|wait`, 단계 10). 컴퓨터의 agent가 연 phone 탭(`browser-tab.md`)의 `lophn browser` 호출을 core가 `drive.*`로 바꿔 그 앱의 preview view를 연 기기에 묻는다. preview만이다: core는 기기 owner의 preview view만 고르고, 폰은 자기가 연 preview view(그 컴퓨터를 위해 연 것)가 아닌 view에는 native module을 부르지 않고 `no_preview`로 답한다. 폰은 preview 화면이 열린 동안 화면을 켜 두지만 컴퓨터가 폰을 깨우거나 lophn 앱을 앞으로 부르지 못한다. 화면이 꺼졌으면 `screen_off`, 무언가가 preview를 덮었으면 `covered`, 사람이 take control했으면 act만 `conflict`다. 폰 앱의 화면과 native module은 `phone-screen.md`의 "drive".
- **알림.** 폰은 push token과 알림 설정을 pairing한 모든 컴퓨터에 `devices/set_push`로 알린다(붙을 때마다, 바뀔 때마다). 컴퓨터는 이 값을 그 기기의 행에 둔다(token과 설정 칸 일곱, `devices/list`는 내지 않는다). 입력에 기기 id가 없어 부른 기기 자기 행만 고친다. `token: null`은 push를 끈 것이라 token만 지우고 설정은 둔다. 앱이 앞에 있는지와 열린 session은 `presence/report`로 알린다(앞뒤가 바뀔 때, session 화면이 열고 닫힐 때, 앞에 있는 동안 30초마다). 누구에게 언제 무엇을 보낼지는 core의 주의가 정한다(`attention.md`).
  - core 쪽. 기기의 마지막 연결이 닫히거나 기기가 끊기면 core가 그 기기의 presence를 잊는다. 죽은 token은 core가 `devices/clear_push`로 거둔다. push는 컴퓨터의 key를 remote가 처음 켜질 때 푸는 것에 기대므로 remote를 켠 적이 없는 core는 push를 보내지 않는다(켰다가 끈 뒤는 이슈 `push-continues-after-remote-off`). `remote.push`가 비어 있어도 나가지 않는다.
  - 폰 앱 쪽. Paired가 알림을 한 번만 묻는다(`Turn on notifications`와 `Not now`. 다른 컴퓨터를 pairing해도 다시 묻지 않는다). Settings › Notifications에서 나중에 켜고 스위치를 고른다: 일곱(`An agent needs me`, `Long work finishes`, `An app update waits`, `A job was missed`, `My apps notify me`, `Stay quiet while I am at the computer`, `Show session names`). 허락을 거절했으면 그 화면에 시스템 설정을 여는 단추가 선다. 알림 channel은 `needs-you`(high), `finished`, `apps` 셋이고 앱이 시작할 때 만든다(Android 13은 허락과 token을 부르기 전에 있어야 한다). 앱이 앞에 있으면 알림 배너를 그리지 않는다(core도 앞에 있는 폰에는 보내지 않는다).
  - 알림을 누르면. 알림의 `data`는 위젯과 홈 화면 아이콘이 쓰는 open target 해석 하나를 지난다(`phone-home-screen.md`). `data.host`가 가리키는 컴퓨터를 고르고 `session`(그 대화), `app`(그 앱의 폰 화면), `inbox`(Inbox)를 연다. 터미널 TUI session(`term:<탭>`)은 대화가 없어 Inbox로 간다(GUI 탭의 승인 대기는 알림이 아직 없다, 이슈 `push-misses-gui-tab-approvals`). 목록에 없는 session은 8초 기다린 뒤 Inbox를 연다. 이 폰에 pairing하지 않은 컴퓨터나 모양이 틀린 `data`는 아무것도 열지 않는다. 앱이 죽어 있다가 알림으로 열려도 같은 곳이 열린다.
  - 개발. EAS project id가 없는 build는 push token을 받을 수 없어 알림이 "쓸 수 없다"로 선다. dev build만 처음 쓸 때 만든 가짜 token을 `devices/set_push`로 보내고 개발 core의 fake push server가 그것으로 온 글을 받는다. 폰에 알림을 그리는 것은 Expo의 일이라 fake가 못 하고, Settings › Notifications 맨 아래(dev build만)의 `Send a test notification`이 같은 `data`의 local 알림을 띄워 누르기를 본다.
- **첨부.** 대화의 Add sheet는 Photos(Android 시스템 사진 선택기라 권한이 없다)와 Camera(권한을 묻고, 거절하면 이유와 설정으로 가는 길을 보인다)를 준다. 사진은 JPEG로 다시 인코딩해 보낸다. PNG, JPEG, GIF, WebP만이고 한 장 5 MiB까지다. 올릴 때는 desktop composer가 붙여 넣은 그림을 올리는 길 그대로 `message-images/upload`(바이트는 `call` 안 base64)를 부르고 받은 blob을 message의 image block에 싣는다. 사진만 있는 message도 보낼 수 있다. 컴퓨터가 offline이면 첨부를 잠근다. desktop은 컴퓨터의 path로 아무 file이나 붙이지만 폰의 file에는 컴퓨터의 path가 없어 그림만이다.
- **bytes.** frame은 JSON뿐이다. upload route는 `{input, base64}`로 보내고 file route의 답은 `{content_type, base64}`로 받는다. 한 file 8 MiB, frame 16 MiB 안이다.
- **폰 앱 package.** `mobile`은 root npm workspace 밖의 Expo project(SDK 58, dev build)다. Metro가 protocol, design(kit, i18n), desktop의 순수 logic file을 source로 읽고, 그 안의 bare import(zod, `@noble/*`)는 폰 앱의 `node_modules`에서 푼다. 연결(handshake, frame)은 좁은 입구 `@lophn/protocol/remote/client`로 쓴다. 명령과 개발 build는 그 package의 README에 있다.
- **개발.** `npm run dev:remote`는 개발 core(`.dev-data`)의 remote를 켜고(port 47432, 사람의 lophn과 겹치지 않게, relay는 비운다) pairing text(QR에 싣는 JSON)를 찍는다. 폰이나 emulator의 "Enter a pairing code instead" 칸에 붙여 넣는다. code는 5분, 한 번이다.

## 지키는 것

1. 폰이 부르는 route는 모두 기기 route 목록 안이다. 화면이 목록 밖 route를 부르는 단추를 보이지 않는다(skip 바꾸기, session 지우기, 설정·secret 화면, job 만들기·고치기·거절).
2. desktop 화면의 동작과 모양은 폰 때문에 바뀌지 않는다. desktop 화면에 폰을 위한 분기(prop, host member)가 없고, 폰은 desktop의 DOM·Electron 화면 file을 import하지 않는다. 폰이 가져오는 것은 순수 logic뿐이다.
3. 화면은 연결과 key를 직접 만지지 않는다. data 층의 읽기 hook만 쓴다.
4. 기기 key는 폰의 보안 저장소에만 있다.
5. 틀린 `watch` 조건은 보내지 않는다. 연결이 닫힌 뒤에는(사람이 끊은 것이 아니면) 다시 붙는다.
6. 폰이 컴퓨터를 지우면 그 폰의 기록이 지워지고 컴퓨터에 닿으면 컴퓨터의 등록도 지워진다. 닿지 않아도 같은 컴퓨터와 다시 pairing할 수 있다.
7. 폰 화면의 문구는 `@lophn/i18n`의 key다. 폰에만 있는 문장만 `mobile.`로 시작하는 새 key다.
8. relay는 증명하지 못한 control socket에 폰 연결을 잇지 않고, 폰 연결 둘의 message는 서로의 data socket으로 가지 않는다. relay는 내용을 보지 못한다(Noise는 폰과 core 사이에서 끝난다).
9. 폰은 자기 push token과 설정을 자기 기기 행에만 둔다. 다른 기기의 것을 고치는 입력이 없고, token과 설정은 `devices/list`로 나가지 않으며 `devices/clear_push`·`devices/push_targets`는 폰이 부를 수 없다.
10. 폰이 부르는 `coding_sessions/switch`는 `confirmed: true` 없이는 거절되고(화면이 sheet로 확인을 받은 뒤에만 보낸다) `terminal_view/input`은 core가 그 기기의 허락을 입력마다 본다. 폰 화면이 입력 칸을 그리는지는 안내일 뿐이다.
11. 폰은 컴퓨터의 앱이 꺼져 있을 때 목록만 보고 앱을 띄우지 않는다. 깨우기는 사람이 누른 단추 하나다.
12. 알림을 눌러 무엇을 여는지는 폰이 `data`를 모양대로 읽을 때만이다. 모양이 틀리거나 모르는 컴퓨터면 아무것도 열지 않는다. 알림 글은 대화 내용을 싣지 않는다(`attention.md`).
13. 사용자 앱의 폰 화면은 guest 안에서만 돈다. guest는 폰 앱의 JS 전역, 보안 저장소, file system, network에 닿지 않고 그 오류가 폰 앱을 죽이지 않는다. 폰은 자기가 못 돌리는 화면(자기보다 새 kit·base, 옛 major, 모르는 module)을 열지 않고 받은 `phone.js`가 manifest의 크기와 sha256과 다르면 쓰지 않는다(`phone-screen.md`).
14. 폰이 연 view는 그 기기의 연결에 묶인다. 연결이 닫히면 core가 그 기기의 view를 지우고 폰이 다시 붙으면 같은 인자로 다시 연다. 폰은 view id로만 operation을 부르고 부를 수 있는 operation은 core가 view의 release 선언으로 정한다.
15. core의 `request`는 지정한 기기의 연결로만 가고, 그 기기가 `hello`의 `capabilities`에 적은 kind만 보낸다. 모르는 `id`, 다른 연결, deadline 뒤의 `response`는 버리고 기다리는 사이 연결이 닫히면 `unavailable`로 끝난다. 한 기기의 답이 다른 기기에 묻은 요청을 채우지 못한다.
16. 폰의 위치는 `phone.use {location.get}` grant가 있는 앱이 live일 때만 나가고 grant가 없으면 폰에 묻지도 않는다. 폰은 앱이 앞에 있고 OS 권한이 있을 때만 읽는다. background 위치를 읽지 않는다. 폰을 깨우지 않는다.
17. 폰에서 도는 앱의 data는 컴퓨터에 안 간 변경이 있는 동안 지우지 않는다(컴퓨터를 지워도 앱이 컴퓨터의 목록에서 빠져도 같다). standalone 앱의 data는 자동으로 지우지 않는다. 폰의 sync는 앱이 앞에 있고 컴퓨터에 닿은 동안만 돈다. `app_sync/push`와 `snapshot`은 짝지은 기기 자격만 받는다(`app-sync.md`).
18. 폰은 앱이 앞에 있을 때만 답하고 입력을 kind의 schema로 검사한다. `drive.*`는 그 폰이 연 preview view에만 닿고 live 화면, lophn 자신의 화면, 다른 앱에는 닿지 않는다.

## 경계와 계약

- boundary `remote-protocol`: frame, 기기 route 목록(`devices/unpair`, `devices/set_push`, `presence/report`, `project_files/list|read` 포함), base64 bytes. 폰은 연결에 좁은 입구 `@lophn/protocol/remote/client`(연결, frame type, key, `REMOTE_PATH`, QR 해석 schema)를 쓰고, route 정의와 schema는 protocol source를 그대로 읽는다.
- 폰의 coding agent와 터미널: route `coding_sessions/*`, `terminal_view/*`, 기존 `acp/*`, event `AcpUpdated`·`StateChanged{coding_sessions}`·`TerminalScreenChanged`. 기기 허락 `terminal_input`은 ledger의 `devices` 칸이다.
- core가 폰에 묻는 길: frame `request`·`response`(protocol의 `phone` 폴더가 모양, kind 표, `unavailable` 이유를 정한다), `hello.capabilities`, core의 `PhoneLink`. 앱의 길은 memory route `app_phone.request`(actor app), broker `/_lophn/broker/phone/request`, SDK part `@lophn/cap-phone` 1.0.0, grant `phone.use {capability}`다. 이유 `details.reason`: `no_phone`, `phone_unreachable`, `unsupported`, `phone_in_background`, `location_off`, `timeout`(모두 `unavailable`)과 폰의 `forbidden`·`os_permission_denied`. drive(단계 10)는 `unavailable` 이유 `no_preview`, `screen_off`, `covered`, `conflict` 이유 `taken_over`, `stale_ref`, `off_screen`, agent에게 가는 문장 `PHONE_TAB_TEXT`를 더한다.
- 폰의 홈 화면: route `app_widgets/list`(폰 gate에 있다), `app_widget.set`(앱 자격), URL scheme `lophn`. 설계는 `phone-home-screen.md`다.
- boundary `mobile`: 폰 앱. boundary `design-native`: 폰 UI kit.
- 폰에서 도는 앱: route `apps/phone_file`, `app_sync/push|pull|snapshot|snapshot_file`, event `AppSyncChanged`. 계약은 `app-sync.md`다.
- 사용자 앱의 폰 화면: route `apps/phone_screens`, `apps/screen_file`, `app_views/open|call|close`, event `AppViewEvent`. 계약(manifest, host module 목록, host-guest 메시지)은 `phone-screen.md`다.
- 앱 안의 길: place union 하나. 화면은 `open(place)`, `back()`, sidebar 열기, 컴퓨터 고르기만 부른다.

## 결정

- 폰 화면은 컴퓨터가 내려주는 web 화면이 아니라 폰 UI kit으로 쓴 React Native 화면이다. 이유: scroll, keyboard, gesture가 폰답고, 화면 내려주기(bundle, hash 확인 cache, WebView, bridge)가 없어 폰 앱이 단순하다. 비교한 폰 앱 다섯 가운데 셋이 RN native였다. 버린 안: 얇은 껍데기와 core가 내려주는 web 화면(계획 `phone-remote-web`과 `phone-shell`이 만들었고 이번에 지웠다). (사람, 2026-11-15)
- wireframe이 화면의 기준이다. 뼈대는 sidebar이고 아래 tab bar를 두지 않는다. 폭 600 이상에서는 sidebar가 늘 열려 있다. (사람, 2026-11-15)
- 화면 이동은 React Navigation(native stack과 drawer)이다. 이유: 넓은 화면의 고정 sidebar가 들어 있고 비교한 폰 앱이 쓰는 표준이다. (agent, 2026-11-15)
- 폰의 권한은 보기, 말하기, 답하기, 켜고 끄기, 지금 돌리기, 새 session이다. 만들기·고치기·지우기와 secret, provider, model 관리는 컴퓨터에서 한다. 폰에서 mode(skip)를 바꾸지 않는다: skip은 agent가 사람에게 묻지 않고 돌게 하는 권한 설정이라 desktop에서 정한다(`approval.md`). (사람, agent)
- 화면 문구는 desktop과 같은 `@lophn/i18n` catalog에서 온다. 이유: 같은 문장이 두 벌이 되지 않는다. (사람, 2026-11-15)
- 화면 아래의 로직은 desktop과 같은 TypeScript(event client, Inbox store, 대화 source)를 그대로 쓴다. 이유: 대화 해석이 한 벌이어야 한다. 대가: DOM에 묶인 desktop file의 순수 부분을 DOM 없는 file로 옮겨야 한다. 옮기지 못한 것은 폰이 베낀다. (agent)
- 폰의 대화 화면은 desktop 대화 화면(`AgentView`)을 폰 host로 쓰지 않고 폰 kit으로 새로 그린다. 이유: desktop 화면은 DOM이고 desktop만의 통로(터미널, file 열기, 끌어 놓기, preload)를 끌고 온다. 대화 해석(source)만 공유한다. (agent)
- 화면을 core 없이 보도록 dev build에 sample 컴퓨터를 둔다. 이유: 화면 worker와 사람이 컴퓨터 없이 모양을 본다. (agent)
- 폰이 컴퓨터를 지울 때 `devices/unpair`로 자기 등록을 지우고, 컴퓨터가 이미 아는 key의 유효한 `pair`는 옛 등록을 바꾼다. 이유: 닿지 않을 때 폰만 잊으면 컴퓨터가 그 key를 계속 알아 같은 컴퓨터와 다시 pairing이 "Cannot reach"가 되었다. 버린 안: 폰이 지우기 전에 컴퓨터에서 먼저 끊게 하기(꺼져 있는 컴퓨터는 못 끊는다). (agent)
- 첨부는 사진(Photos, Camera)만이고 5 MiB, 그림 네 종류다. 이유: desktop과 같은 route와 message 모양을 쓰고, 폰의 file에는 컴퓨터의 path가 없다. 버린 안: 아무 file 첨부(file 고르기 module이 하나 더 들고 route가 없다). (agent)
- byte는 frame 종류를 늘리지 않고 `call` 안에 base64로 싣는다. 이유: 대화 이미지와 file은 작고, frame 종류를 늘리면 연결 계약이 커진다. (agent, 2026-11-15)
- 앞으로 온 앱은 열린 연결에 `watch`를 다시 보내 3초 안의 `ready`로 살아 있는지 본다. 이유: background에서 소리 없이 죽은 socket은 close event가 오지 않는다. 멀쩡한 연결은 `stale`로 깜빡이지 않는다. (agent, 2026-11-15)
- 폰 앱은 root workspace 밖의 `mobile`에 자기 `package.json`과 lock을 가진 Expo project로 둔다. 이유: React Native 의존 tree가 Electron 설치와 `npm run check`에 섞이지 않는다. protocol과 kit은 Metro가 source로 읽어 한 벌이다. 대가: 폰 앱의 type 검사와 test는 따로 돌린다(폰 앱 폴더의 `npm run typecheck && npm test`). (agent, 2026-11-15)
- 폰은 coding agent를 core가 중계한 대화로 다루고 터미널은 화면 보기가 기본이다. 이유와 버린 안은 `harness-gui.md`(사본 중계, 바꾸기 확인, 열기·되살리기 범위)와 `terminal-agent.md`(터미널 보기). 폰 쪽의 정한 것: 터미널 화면은 먼저 React Native의 styled text row로 그린다(WebView terminal은 그 길이 못 쓸 때만. native module이 없이 되고 새 dev build가 필요 없다). 대화는 새로 그리지 않고 desktop의 harness GUI source에 폰의 feed를 끼운다. (agent)
- 터미널의 보이는 화면은 가리지 않고 폰에 보낸다. 입력은 사람이 컴퓨터의 Settings › Remote에서 기기마다 켜야 통한다(기본 꺼짐). 이유와 대가는 `terminal-agent.md`의 결정. 폰의 입력 허락을 폰이 아니라 core가 입력마다 본다. (agent)
- push는 Expo Push를 core가 직접 부르고 폰 쪽은 `expo-notifications`다. 알림 설정은 폰에 한 벌이고 pairing한 모든 컴퓨터에 사본으로 둔다. 이유와 버린 안은 `attention.md`. 폰 쪽의 정한 것: Paired에서 한 번만 묻고 거절하거나 미루면 Settings에서 켠다. 이유: 처음 pairing하는 순간이 "알림이 왜 필요한지"를 가장 잘 말하고, 다른 컴퓨터를 더할 때마다 다시 묻는 것은 귀찮다. token을 받을 수 없는 build(EAS project id가 없는 build)는 가짜 token을 만들지 않고 "쓸 수 없다"로 둔다. 개발 build만 가짜 token을 쓴다. (agent)
- 사용자 앱의 폰 화면은 폰 앱 안의 guest runtime에서 돌고 react-native-web WebView로 그리지 않는다. desktop preview만 react-native-web이다. 이유와 버린 안은 `phone-screen.md`. (agent)
- core가 폰에 일을 시키는 길은 remote channel의 `request`·`response` frame 하나이고 `PhoneLink`가 묻는다. 칸 이름은 `capability`가 아니라 `kind`다. 이유: 폰이 하는 일은 한 갈래이고 위치 말고 폰 화면을 모는 일(단계 10)이 같은 길에 얹힌다. 그래서 frame은 그대로 두고 kind만 더한다. 앱 쪽 이름 `capability`(grant 범위, SDK)는 앱에 열어 준 kind만 가리킨다. 버린 안: desktop의 `/host-link`를 폰에 넓히기(loopback만이고 연결 하나이고 인증이 desktop의 Bearer다), 폰이 server가 되기(NAT 뒤), 기능마다 socket, event와 답 route로 주고받기(답을 이으려고 전달 보장을 다시 만든다). (agent)
- 폰은 답할 kind를 `hello.capabilities`에 적고 core는 적힌 kind만 묻는다. 이유: 옛 폰이 모르는 frame을 받아 연결이 끊기지 않고 판을 올리지 않는다. (agent)
- 폰을 push로 깨우지 않고 앞에 있을 때만 답한다. 이유: Android는 앞에 있는 앱의 foreground 위치만 허락하고 background 위치는 권한과 Google의 심사가 따로 든다. 위치를 읽으려고 사람의 폰을 push로 불러내는 것은 사람이 모르는 때에 읽는 길이다. 대가: 앱은 `unavailable`이 평소 일이다. (agent)
- 앱의 길만 열었다. agent가 폰 기능을 부르는 route와 CLI, 기기마다의 스위치는 쓰는 예가 생길 때 연다. 이유: 부르는 쪽이 없는 기능을 먼저 만들지 않는다. (agent)
- 위치 읽기에 lophn의 banner와 기록을 두지 않는다. 이유: 동의 카드가 앱마다 한 번의 동의이고 Android가 자기 위치 표시를 띄운다. (agent) 사람이 읽기를 보고 싶어 하면 그때 기록을 더한다.
- 앱의 `phone.use`는 기능마다 따로 묻고 거둔다(scope `{capability}`). 이유: 위치를 허락한 앱이 camera까지 얻지 않는다. `secret.use {name}`과 같은 모양이라 permission kind 하나로 기능을 늘린다. 버린 안: 기능마다 permission kind(더할 때마다 파일이 열 개 남짓 는다), 호출마다 묻기(위치는 조용하고 잦다). 사람은 두 번 묻는다: lophn의 동의 카드(이 앱이 폰의 위치를 써도 되나. 한 번)와 OS의 위치 권한(lophn이 위치를 읽어도 되나. 처음 쓸 때 한 번). (agent)
- 폰에서 도는 앱의 backend와 data는 폰이 가지고 컴퓨터가 hub다. 폰 gate에는 그 앱이 설치되고 맞추는 데 필요한 route(`apps/phone_file`, `app_sync/*`)와 event(`AppSyncChanged`)만 열고 앱을 직접 부르는 길은 계속 닫는다. 이유와 버린 안(relay가 변경을 맡기, 폰 둘을 직접 맞추기)은 `app-sync.md`. (planner)
- core가 폰에 묻는 길은 하나다(planner, 2026-11-15). remote channel에 `request`·`response` frame을 더하고 core에 `PhoneLink`를 둔다. 폰 기능(단계 8)과 폰 화면 다루기(단계 10)가 같이 쓴다. desktop의 `/host-link`와 같은 모양이고 폰은 두 번째 host다. 그래서 drive를 위한 `AppViewEvent` 갈래나 폰이 부르는 답 route(`app_views/drive_answer` 같은 것)는 없다. 버린 안: event로 요청을 보내고 route로 답 받기(두 길이 따로 기한과 짝을 맞춰야 한다).
- 폰을 깨우지 않는다(planner). 앱이 앞에 없으면 `unavailable`이고 문장이 agent에게 사람에게 부탁하라고 말한다. 이유: 폰 화면을 다루는 것은 사람이 폰을 들고 있을 때의 확인이고, 컴퓨터가 폰을 깨우거나 앞으로 부르면 사람이 모르는 사이에 폰이 움직인다.

## 열린 것

폰의 preview 화면 다루기(drive)는 emulator의 release build와 개발 core(fake model)로만 보았다. 실제 폰, 실제 model의 agent turn, iOS는 보지 못했다(change-log `mobile-browser-use`).

사용자 앱의 폰 화면(`phone-screen.md`)은 emulator에서 개발 core에 손으로 지은 앱을 붙여 보았고 실제 agent가 만든 앱이나 실제 폰으로 보지 못했다. iOS는 짓지 않았다. 폰에서 도는 앱(`app-sync.md`)도 같다: emulator와 개발 core의 손으로 지은 앱 둘로만 보았고 실제 폰, 실제 agent가 만든 앱, 한 앱을 두 폰이 맞추는 것은 보지 못했다. 폰 화면의 알려진 빈틈은 `phone-screen.md`의 열린 것과 이슈 `phone-guest-*`, `phone-screen-*`, `phone-apps-menu-lacks-wireframe-rows`, `phone-open-url-blank-workspace`.

폰의 홈 화면(위젯, 아이콘)과 폰의 위치 읽기는 emulator에서 개발 core에 손으로 지은 앱을 붙여 보았다. 실제 폰, Electron desktop 앱의 동의 카드 줄과 앱 상세의 `phone.use` 줄, 실제 agent가 만든 앱, iOS는 보지 못했고 위치 정확도 `balanced`·`low`는 emulator에서 시간 초과였다(`high`만 됐다. emulator에는 network 위치가 없다). 설계와 알려진 빈틈은 `phone-home-screen.md`와 change-log `mobile-widgets`.

폰의 coding agent와 터미널은 실제 desktop 앱(Electron)에 붙여 보지 못했다. 폰 화면은 emulator에서 개발용 가짜 coding host(change-log `mobile-coding-agents`)를 붙인 개발 core로만 보았다: 컴퓨터를 깨우는 데 성공하는 경우, 지난 session을 실제로 되살리는 경우, 열기의 `conflict`·`unavailable` 거절, 실제 coding agent의 대화는 보지 못했고 실제 폰도 쓰지 않았다(change-log `mobile-coding-agents`). sample 컴퓨터에는 터미널 화면의 답이 없어 View terminal이 "Waiting for the terminal’s screen…"에 머문다(이슈 `phone-sample-terminal-screen-missing`). 폭 2칸 글자(CJK, emoji)의 간격은 시스템 fallback 글꼴이 1em이라는 가정이다(이슈 `phone-terminal-wide-glyph-spacing`).

폰의 알림은 실제 FCM 배달을 확인하지 못했다. 사람의 Expo·Firebase 계정이 있어야 하고 지금까지는 fake push server로만 보았다(change-log `mobile-push`, `attention.md`). 폰에 아직 없는 것과 알려진 빈틈은 이슈와 change-log `mobile-app`에 있다: 대화의 수식과 mermaid는 code box로 보인다, Deny에 이유를 쓰지 못한다, fork·rewind·subagent 열기가 없다, Inbox의 History는 notice 목록이다, agent 줄의 model은 raw 이름이다, folder가 여럿인 project는 첫 folder만 보인다.
