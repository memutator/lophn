# 0.11.0

## 앱 화면과 artifact 화면을 `<webview>` guest로 옮기고, desk를 오가도 page를 지킨다

```yaml
modules: [packages/shell/main, packages/shell/renderer, packages/shell/ipc]
checked: [architecture-workspace-layout, architecture-browser-tab, architecture-annotation, architecture-appearance, architecture-keybindings, architecture-artifact]
```

- 전:
  - 앱 화면(app panel 탭, 앱 place 본문, 앱 card, 앱 전용 창)과 artifact 탭은 native `WebContentsView`였다. native view는 shell DOM 위에 그려져 floated 패널·menu·toast가 page 밑에 깔렸고, 피하려고 view 층(`appViewOrder`), cover로 view 줄이기(`useViewCover`, `createViewCovers`), bounds relay(`placement.ts`, `visibility.ts`, `frame-router.ts`, `renderer/app-frame/bounds.ts`), 앱 place menu가 열린 동안 화면 숨기기라는 장치가 쌓였다.
  - 앱 전용 창은 문서가 없는 빈 `BrowserWindow`에 native view 하나였다. `webviewTag`와 shell preload가 없어 단축키가 닿지 않았다.
  - desk를 떠났다 돌아오면 일반 browser 탭의 `<webview>`를 놓아 page를 url로 다시 load했다(`issues/workspace-layout.md`).
- 후:
  - 앱 화면과 artifact 화면이 browser 탭과 같은 창의 `<webview>` 그릇에 산다(`packages/shell/renderer/app-frame/webview-host.tsx`, kind 중립). project 창은 floats 층, detached 창·앱 전용 창은 본문, 앱 place는 `.content`다. 앱·artifact element는 `src`만 적고 첫 load 전까지 숨긴다. z-index 규칙은 그대로다(pane 화면 1, floated 화면 `--z-sticky + 2L+1`, 패널은 그 위).
  - main registry가 state에 `src`를 싣는다. 앱은 `lophn-app://<label>/<screen>/index.html?view_session=..&mount=<generation>`, artifact는 `lophn-artifact://<host>/<entry>?mount=<n>`이다. `acceptGuest(window, src)`가 그 창의 view이고 아직 안 쓴 src일 때만 1회 받고, `did-attach-webview`에서 guest를 그 view에 묶는다. 붙이기 판정은 `wiring/browser.ts`의 `will-attach-webview` 하나이고 `webview-guest.ts`의 `hardenWebviewAttach`가 kind별로 partition·preload·webPreferences를 강제한다. browser guest는 `lophn-*` src를 거절한다. 신원은 `byContents` 그대로라 app-ipc·annotate·app-call은 바뀌지 않는다. annotation screenshot은 guest `capturePage`다.
  - 앱 전용 창은 shell 문서 `#app-window=<app>/<release>/<screen>`(`packages/shell/renderer/app-frame/app-window.tsx`)이고 `webviewTag`·shell preload를 쓴다. 앱 하나에 창 하나이고 전역 palette·tray는 detached 창처럼 건너뛴다.
  - `<webview>`는 탭 key가 어느 desk의 layout에든 있는 동안 그대로 두고, 모든 desk에서 사라지거나 그 탭이 detached가 될 때만 지운다. desk를 오가도 page를 다시 load하지 않는다.
  - secret 입력 창의 입력 차단이 `hostWebContents`로 guest까지 본다.
- 계약:
  - 바뀐 것: `AppFrameViewState`·`ArtifactViewState`에 `src`가 생겼다. 앱 panel·artifact 탭의 Detach transfer가 `{ value: null, views: [] }`이고 받는 창이 다시 연다. `AppViews.moveViews`는 browser의 크기 준 popup과 DevTools만 옮긴다.
  - 생긴 것: kind 중립으로 옮긴 `<webview>` 그릇(`packages/shell/renderer/app-frame/webview-host.tsx`), `acceptGuest`·`bindGuest`·`dropGuest`, 앱 전용 창 route `#app-window=`, `renderer/app-frame/app-window.tsx`.
  - 지운 것: `app-frame/placement.ts`, `app-frame/visibility.ts`, `browser/frame-router.ts`, `renderer/app-frame/bounds.ts`, `useViewCover`·`createViewCovers`·`ViewCoversProvider`, cover 빼기, 앱 view 층. `app-frame/view-order.ts`는 overlay 층만 남는다. native relay는 `renderer/browser/native-bounds.ts`, `main/browser/native-bounds.ts`, `native-view.ts`, `view-order.ts`에만 있다.

왜: native view가 shell DOM 위에 그려져 menu·popover·floated 패널·toast가 앱 page 밑에 깔렸고, 그 우회 장치가 층·cover·bounds relay로 쌓였다. browser 탭은 같은 이유로 이미 `<webview>`를 쓰고 그 뒤로 겹침 문제가 없다. 앱 화면과 artifact 화면도 같은 그릇으로 모으면 장치가 하나로 줄고, 같은 변경에서 desk를 오갔다 돌아오면 browser 탭 page가 다시 load되던 결함이 닫힌다.

결정:
- 화면 그릇은 `<webview>`다. iframe은 preload의 isolated world, 앱별 partition, `sender.id` 신원을 잃고, remote UI는 앱이 자기 DOM·CSS component를 못 쓰게 한다. Electron은 `<webview>`를 권하지 않지만 browser 탭이 이미 그 위험을 지고 있어 새 위험이 아니다. (사람)
- Detach하면 앱 화면이 다시 load된다. browser 탭과 같다. 앱이 화면 상태를 URL이나 storage에 두면 잃는 것이 줄어든다. (사람)
- artifact 탭도 같이 옮긴다. 같은 겹침 문제를 갖고 있고, 남기면 앱 쪽 장치를 지우지 못한다. (agent)
- 붙이기 ticket은 `src` 하나이고 한 번만 쓴다. renderer가 적은 partition·preload·webPreferences는 버리고 registry가 정한 값만 쓴다. (agent)
- 앱 저장소 partition 이름(`persist:app-<app>:live`, `persist:app-<app>:preview-<bundle hash>`)을 바꾸지 않는다. 사람의 `~/.lophn` cookie·localStorage·IndexedDB가 이어져 migration이 없다. (agent)
- 앱 template `AGENTS.md`(lophn-managed 절)에 "다시 load되어도 잃으면 곤란한 화면 상태는 `localStorage`에 둔다"를 더했다. 새로 만드는 앱에만 들어간다(agent). URL query는 Detach 때 main이 새 `src`를 내므로 남지 않는다.

## `skill.read`가 `PATH: "SKILL.md"`로도 본문을 주고, 실패 문장에 원인을 싣는다

```yaml
modules: [packages/core/lophn-agent]
checked: []
```

- 전:
  - `skill.read`는 `path`가 없을 때만 본문을 줬고, `path: "SKILL.md"`는 어떤 skill에서도 `not_found`였다(딸린 file 목록에 SKILL.md를 담지 않았다). 본문을 `path` 없이 읽으라는 말은 tool 설명 어디에도 없었다.
  - 없는 file의 문장은 `skill X has no file Y`였지만 실행기가 모든 `not_found`를 `tool target is not available`로 바꿔, "없는 file", "꺼진 skill", "없는 이름"이 model에게 같은 문장으로 갔다.
- 후:
  - `path`가 `SKILL.md`, `./SKILL.md`, `.`, `/`이면 본문을 준다. `path`는 SKILL.md 옆에 딸린 `.md` file 하나다. 모르는 `path`의 `not_found` 문장에 그 skill의 딸린 file 이름을 싣고(`skill X has no file Y (files: a.md, b.md)`), 없으면 `(no bundled files)`다. tool 설명은 "Omit path to get the skill body. path reads a bundled .md file that ships beside SKILL.md."로 바뀌었다.
  - `executeToolCall`은 실패한 대상이 model이 보낸 입력뿐인 tool(`INPUT_SCOPED_FAILURES`, 지금 `skill.read`)의 handler 문장을 `tool target is not available: <handler 문장>` 꼴로 싣는다. 그 밖의 tool은 지금처럼 공통 문장만 쓴다.

왜: 실제 session에서 `skill.read`가 `path`(`SKILL.md`, `/`, `.`, `design-app.md`)를 채워 9번 불렸고 9번 모두 `not_found`여서 skill 본문이 한 번도 agent에게 닿지 않았다. 실패 문장에서 원인이 지워지면 model은 같은 입력으로 되풀이해 turn과 비용만 쓴다. `skill.read`의 이름은 prompt의 skill 목록에 이미 실려 있어 문장에서 가려 얻는 것이 없다.

결정:
- `ErrorCode`(`code`·`message`) 꼴은 넓히지 않고 딸린 file 이름을 `message`에 실었다. (agent)
- `SKILL.md`를 `files`에 담지 않고 reader가 그 이름을 본문으로 돌려준다. 실패 문장의 목록이 model이 실제로 고를 수 있는 이름과 같아진다. (agent)
- 허용은 tool 이름의 명시 집합 하나다. `forbidden`·`not_found` 문장을 나누는 것만으로는 "이 skill에 그 file이 없다"를 알 수 없다. (agent)

후속: 없음.

## 내장 skill 설명은 절차를 요약하지 않고 무엇을 하는 skill인지만 말한다

```yaml
modules: [packages/core/agent-places, packages/shell/renderer]
checked: []
```

- 전: `design-app`의 description이 본문이 정한 `DESIGN.md`의 절 일곱(`Purpose, Reuse, Model, Journeys, Screens, Tools, Failure branches`)과 화면·재사용 규칙을 그대로 들어, model이 본문을 읽지 않고도 뼈대를 채울 수 있었다. `new-app`, `repair-app`, `check-domains`는 할 단계를, `write-workflow`는 folder 모양(`workflow.yaml`, `workflow.md`, artifacts)을 들었다.
- 후: 그 다섯 description은 무엇을 하는 skill인지만 말하고 절·단계·파일 모양은 본문에만 있다. `design-app`은 "Design an app or a change before you build it. Read this skill and write DESIGN.md as it says."다. `make-domain`, `write-kinds`, `write-artifact`의 description은 본문이 다루는 주제만 이름으로 들어 규칙이나 산출물의 뼈대를 주지 않으므로 그대로 두었다. skill 목록과 `/` 메뉴에 실리는 글만 바뀌고, skill 본문과 발견·읽기 규칙은 그대로다.

왜: description만으로 산출물의 뼈대를 채우면 "skill을 읽었다"와 "절 이름만 안다"가 결과에서 구별되지 않는다. 실제 session이 본문을 한 번도 못 읽은 채 `DESIGN.md`의 일곱 절을 다 채웠고, 본문이 금지한 것(앱 이름을 화면 머리에 다시 쓰기, 화면을 설명하는 문단, 자산 안내 문단)을 넣었다.

결정:
- description은 "읽을지"를 고르는 재료로만 둔다. 버린 길: skill 목록 글에 "본문을 읽지 않았으면 그 skill의 절차를 지킨 것으로 보지 않는다" 한 줄을 더하기. 같은 자리에 다시 요약이 생기면 문장으로는 못 막는다. (agent)

후속: 없음.

## `package.read @lophn/ui`가 guide를 창으로 나눠 주고, kit guide의 props는 분류별 예산 안에서만 붙는다

```yaml
modules: [packages/core/apps]
checked: [architecture-ui-kit, architecture-agent-definition]
```

- 전:
  - `@lophn/ui` guide는 42,356 byte(1.1.0)였다. `package.read`의 내장 SDK 갈래가 본문을 `TEXT_MAX_BYTES`(24 KiB)에서 자른 뒤 `fitted`를 배열 키 없이 불러, 잘린 본문도 버리고 `content`를 `null`로 만들었다. agent는 `status: success`, `complete: false`, `content: null`만 받아 kit guide를 한 번도 받지 못했다.
  - guide 생성(`apps/packages/builtin.ts`)은 분류마다 props 정의를 조건 없이 붙였다. 컴포넌트가 늘면 앞 알파벳 분류(`data`, `feedback`, `input`, `layout`)가 예산을 다 쓰고 `navigation`·`overlay`·`primitives`·`reading`이 먼저 사라졌고, 잘렸다는 사실은 `guide_truncated: true` 하나로만 보였다.
- 후:
  - `package.read`는 안내 본문을 자르지 않고 창으로 나눈다. 결과 JSON 전체(다른 칸까지 포함)가 `TEXT_MAX_BYTES` 안에 오도록 창 크기를 잰 뒤, 남았으면 `guide_truncated: true`, `content.guide_offset_bytes`, `content.guide_size_bytes`와 `continuation.read_next`(`offset_bytes=<다음 창의 시작>`)를 싣는다. 다시 부를 때 `offset_bytes`를 넣으면 그 위치부터 이어진다. 내장 SDK와 사용자 package가 같은 창 나누기를 쓴다. `cutBytes`는 지웠다.
  - guide 생성은 예산(`GUIDE_BUDGET_BYTES`, 20 KiB)을 두고 props 정의를 분류마다 하나씩 돌아가며 붙인다. 컴포넌트가 늘어도 특정 분류가 props를 독점하지 않는다. 예산 밖으로 밀린 props가 있는 분류에는 뺐다는 한 줄이 남고, `## 분류`·설명·`import from` 줄과 `- 이름: 언제 쓰나` 줄은 분류마다 늘 있다. 생성은 결정적이다.
  - `@lophn/ui` 1.1.0 guide는 20,449 byte이고 여덟 분류가 모두 있으며, `package.read @lophn/ui` 한 번에 다 온다(`complete: true`, `content` 있음).
- 계약:
  - 바뀐 것: tool `package.read` 입력에 `offset_bytes`(정수, 0 이상, 선택)가 생겼다. `name` 없이 주면 `invalid_input`이다. 결과 `content`에 `guide_offset_bytes`·`guide_size_bytes`가 생겼다. 결과 상한을 넘으면 `content` 대신 창과 `continuation`을 준다.
  - 생긴 것: `GUIDE_BUDGET_BYTES`, `packages/core/lophn-agent/tools/result.ts`의 `jsonBytes` export.
  - 지운 것: `packages/core/apps/agent-tools/package.ts`의 `cutBytes`.

왜: kit의 가장 큰 guide가 결과 상한에 걸려 통째로 버려졌고, 살아남은 guide도 알파벳 순서로 뒤쪽 분류를 잃었다. tool 결과 상한을 이미 다루는 길(`file.read`의 `continuation`)을 그대로 써서, agent가 한 번 더 부르면 잃는 것 없이 끝까지 받는다.

결정:
- paging 방식은 `file.read`·`pdf.read`와 같은 `continuation`이다. guide를 "색인"과 "props" 두 요청으로 나누는 안은 agent가 구조를 알아야 하고 route도 늘어난다. (agent)
- 창 크기는 `TEXT_MAX_BYTES`에서 JSON overhead를 뺀 값으로 잰다. 넘치면 넘친 만큼 줄여 다시 재므로 escape가 늘어나는 본문도 상한을 넘지 않는다. (agent)
- guide 예산은 tool 한 창보다 작은 20 KiB다. 색인과 예산 안의 props가 `package.read` 한 번에 오고, 넘는 부분은 앱 폴더의 SDK 사본에서 읽는다. (agent)

후속: 없음.

## `app.status` 요약이 상태 이름과 이유를 보인다

```yaml
modules: [packages/core/apps]
checked: [architecture-agent-definition]
```

- 전: `packages/core/apps/agent-tools/runtime.ts`의 handler가 `fitted(\`app <id> is ${body.state}\`)`를 불렀고 `body.state`는 `{ state, termination_pending, reason? }` 객체라, 요약이 `app app_01m661c1… is [object Object]`였다. 실제 session 네 turn 모두 그 문장이었다.
- 후: 요약이 상태 이름을 쓰고, `reason`이 있으면 ` (<code>: <summary>)`를 덧붙인다. 예: `app app_x is unavailable (crash_loop: unexpected exits exceeded five within ten minutes)`. 상태 값(`content.state`)은 그대로다.

왜: `app.status`는 앱이 뜨지 않을 때 agent가 가장 먼저 부르는 tool이고, 요약 줄은 tool 결과 목록과 turn 기록에 그대로 남는다. 요약이 `[object Object]`면 기록만 보고 진단할 때 상태가 보이지 않는다.

결정:
- 요약에 `termination_pending`은 넣지 않는다. 사람이 읽는 상태 전이의 이름(`running`, `stopped`, `preparing`, `unavailable`)이 먼저이고, 그 값은 `content`에 있다. (agent)

후속: 없음.
