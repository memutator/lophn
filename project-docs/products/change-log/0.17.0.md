# 0.17.0

## browser 탭의 Google 로그인

```yaml
modules: [packages/shell/main]
checked: []
```

- 전: browser 탭에서 Google 계정 로그인이 "This browser or app may not be secure"로 막혔다. UA에서 `Electron/x`와 앱 이름 token을 모두 빼고 `sec-ch-ua`에 `Google Chrome` brand를 지어 넣어 Chrome인 척했다.
- 후: UA에서 `Electron/x`만 빼고 `lophn/x` token을 남긴다. client hints와 page JS의 `navigator.userAgentData`는 Chromium 값 그대로다.

왜: 사람이 browser 탭에서 Google 로그인이 안 된다고 했다(사람 2026-11-03). 실험에서 UA가 순수 Chrome일 때만 Google이 막았고, Electron이나 앱 이름 token이 남으면 통과했다.

결정:
- Chrome인 척하지 않고 자기 이름을 단 Chromium 브라우저로 보인다. (agent)
- `Electron/x`는 계속 뺀다. Electron을 보고 막는 사이트가 있다. (agent)

## sidebar와 탭의 agent session 모양 하나로, 새 session +와 group 탭 정리

```yaml
modules: [packages/shell/renderer]
checked: []
```

- 전: lophn session과 터미널 coding agent session은 상태 점 규칙(`sessionDot`, `terminalAgentDot`)과 agent 아이콘을 sidebar, Agent 탭, 터미널 탭, 새 session 목록이 따로 그렸다. place 줄의 +(28px)는 session 줄의 점·x(20px 칸)와 세로로 4px 어긋났고, lophn agent·coding agent는 + 오른쪽 클릭 menu로 골랐다. 연필(Rename)·x(Stop)는 이 창이 보이는 place의 줄에만 있었다. 고르지 않은 group 탭과 칸에 숨은 탭도 안 보이는 닫기 자리를 차지해 이름 사이에 빈 칸이 생겼다. 사람 차례인 workflow 줄은 "Your turn" 글자를 달았다.
- 후: `renderer/parts/agent-session`이 공통 모양(`AgentFaceIcon`, `activityDot`)을 두고 `lophn.ts`·`coding.ts`가 각 종류를 그 값으로 옮긴다. sidebar·탭·+ 목록이 이것만 그린다. +는 점·x와 같은 칸이고, hover하면 Terminal hover와 같은 목록(lophn agents / Coding agents, 사이 divider)이 뜬다. lophn session 줄은 어느 place든 연필·x가 있고, 다른 place의 session을 멈추면 그 place의 저장된 layout에서 탭을 지운다. 고르지 않은 group과 칸에 숨은 탭에는 ×가 없고(●나 상태 점만 남고 누르면 그 탭을 고른다), 같은 칸의 탭 사이에는 세로 선이 있다. workflow 줄은 점만 보인다.

왜: 사람이 + 정렬과 lophn session에 연필·x가 안 뜨는 것을 짚었고, 한 곳을 고치면 다른 곳을 따로 고쳐야 하는 구조를 공통 agent session 구조로 바꾸라고 했다(사람 2026-11-04). group 탭의 빈 칸과 칸 사이 가름도 사람이 짚었다.

결정:
- 공통 모양은 parts에 두고 lophn/coding 차이는 adapter 둘이 맡는다. 탭 줄의 닫기 칸(`CloseSlot`)은 모든 kind의 탭이 쓰므로 묶지 않았다. (agent)
- 고르지 않은 group의 ×는 겹쳐 띄우기(A)나 아이콘 바꾸기(B)가 아니라 없앤다(C). 닫기는 가운데 클릭, tab 메뉴, group을 고른 뒤의 ×다. (사람)
- 다른 place의 터미널 줄에는 연필·x를 두지 않는다. 그 PTY와 닫기 확인은 그 place 창의 몫이다. (agent)

후속: 없음.

## Inbox Finished 줄은 늘 탭 이름을 쓴다

```yaml
modules: [packages/shell/ipc, packages/shell/main, packages/shell/renderer]
checked: []
```

- 전: Finished의 터미널 줄은 이 창이 보이는 place의 탭에서만 이름을 찾았다. 다른 place나 다른 창의 터미널은 시작 폴더 이름이 나왔다. 이름을 알면 탭 이름 / Claude Code, 모르면 Claude Code / 폴더 이름으로 순서가 뒤집혔고, lophn 줄은 agent 이름 / session 이름이었다.
- 후: `TerminalRuntime`에 `tab_name`이 생겼다. 창이 `shell:terminal-tab-name`으로 알린 이름을 main의 tracker `decorate`가 runtime에 실어 모든 창에 보내고, 이름이 바뀌면 runtime을 다시 보낸다. Finished 줄은 굵은 윗줄이 탭·session 이름, 작고 흐린 아랫줄이 coding agent 제품 이름·lophn agent 이름이다. 폴더 이름은 창이 이름을 알리기 전의 잠깐만 쓴다. `InboxNames.terminals`는 없어졌다.

왜: 사람이 coding agent 줄을 탭 이름과 agent로 보이게 하고 탭 이름을 모르는 경우가 없게 하라고 했다(사람 2026-11-04).

결정:
- 한 줄(`Claude Code / 탭 이름`)이 아니라 두 줄이고 탭 이름이 굵은 윗줄이다. lophn 줄도 같은 순서로 바꿨다. (사람)
- 탭 이름의 정본은 이미 OS 알림 제목에 쓰던 main의 메모리다. renderer끼리 이름을 나누는 새 길을 만들지 않았다. (agent)

후속: 없음.

## domain과 kind를 지우고 경계를 그릇으로 접었다

```yaml
modules: [packages/cli, packages/core/agent-places, packages/core/apps, packages/core/lophn-agent, packages/core/main, packages/core/projects, packages/design, packages/protocol, packages/sdk, packages/shell/ipc, packages/shell/main, packages/shell/renderer]
checked: [architecture-testing, architecture-eval, architecture-agent-chat, architecture-ui-kit, skill-ui-design, tool-check]
```

- 전: 그릇(project, app) 안에 domain(`dom_`)이 있었다. 앱을 만들면 앱 slug 이름의 domain이 같이 생겼다. domain마다 `<data>/domains/<dom>/`에 `DOMAIN.md`(지침 층), `kinds.yaml`(kind 검사, 위반 toast, `kind.list`·`kind.check`), `skills/`(domain skill 층), `artifacts/`가 있었다. 앱 command는 `lophn <domain> <command>`였고 비공개 command는 같은 domain을 맡은 agent만 봤다. 정의의 `domains`가 맡을 domain을 골랐다. place 정보에 Domains 절과 domain 지도가, 오른쪽 sidebar에 Domain panel이 있었다.
- 후:
  - kind 기능(`kinds.yaml`, kinds worker, `kind.*` 명령, 위반 toast, `kinds_changed` notice)은 대체 없이 없다.
  - 앱 command는 `lophn <app slug> <command>`, wire 이름 `<slug>_<command>`, deny 규칙 `lophn(<slug> <낱말>)`이다. domain이 하나인 앱은 글자가 그대로다. 비공개 command는 그 앱 place의 session만 본다. 내장 명령 묶음 이름은 앱 slug로 쓰지 못한다(`app.create`가 `invalid_input`).
  - 선언의 command에 `domain` 칸이 없다. `@lophn/declaration` 3.0.0, `@lophn/app-ui` 2.2.0.
  - `app.usage`는 invocation 기록만 세고 쓰는 쪽은 부른 session의 place(다른 앱, project)다. `release.prepare`의 `removed_public_tools`는 `[{tool}]`, `removed_public_skills`는 `[{skill}]`이다.
  - artifact는 `<그릇 자리>/artifacts/<name>/`이고 신원은 `{project, name}`이나 `{app, name}`이다. 그릇 자리는 `<data>/projects/<prj>/`, `<data>/apps/<app>/`다. 탭 key는 `artifact:<project|app>:<id>:<name>`, place layout은 판 9다.
  - 지침 층은 전역, project `LOPHN.md`, agent 본문이다. skill 층 `domain`은 `place-data`(그릇 자리의 `skills/`)다. 내장 skill `make-domain`, `check-domains`, `write-kinds`는 없다.
  - 정의에 `domains` 칸이 없다. 칸이 차 있던 agent는 그릇 전체로 넓어진다.
  - place 정보의 Domains 절 대신 home 지도에 앱마다 public command와 그것을 쓰는 앱·project("Used by")가 실린다. project·app place 정보에 `Skills folder:` 줄이 있다.
  - Domain panel(project sidebar의 Domain 탭, app panel의 Domain 탭), `lophn domain`, agent tool `domain.read`·`domain.create`가 없다.

옮기기(사람의 data root가 새 판으로 이어진다):
- ledger step `apps.releases.declaration-no-domain`: 저장된 release 선언에서 `commands[].domain`을 지운다. `declaration_hash`는 그대로다.
- ledger step `apps.annotations.artifact-container`: artifact annotation 묶음의 domain을 그 domain의 그릇(`project`나 `app`)으로 바꾼다.
- data step `approvals.deny-rule-slug`: 정의 파일의 `lophn(<domain> …)`을 그 domain을 가진 앱의 slug로 바꾼다. 못 찾은 규칙(project domain 등)은 그대로다.
- data step `artifacts.container`: `domains/<dom>/artifacts/*`를 그릇의 `artifacts/`로 옮기고, 그 artifact의 rewind 기록과 place layout(판 8 → 9)의 artifact 탭을 새 자리로 다시 쓴다.
- data step `domains.place-data`: `domains/<dom>/skills/*`를 그릇의 `skills/`로 옮기고 그 skill의 rewind 기록도 새 자리로 다시 쓴다. `DOMAIN.md`·`kinds.yaml`은 지우고 그 file의 rewind 기록도 지운다(되돌려도 되살아나지 않는다).
- data step `agents.drop-domains`: 정의 파일의 `domains` 칸을 지운다.
- data step `domains.retire`(맨 끝): `domains` 표와 `<data>/derived/kinds.sqlite`를 지우고, `<data>/domains/`에 남은 file이 없으면 폴더를 지운다.
- 이름이 겹치면(한 그릇의 domain 둘에 같은 이름의 artifact나 skill) domain 이름이 앞서는 쪽이 이름을 갖고 다른 쪽은 `<name>-<domain 이름>`이 된다. skill은 SKILL.md의 `name`도 고친다. 그 이름도 차 있으면 옮기지 않고 `domains/<dom>/`에 남는다(덮어쓰지 않는다).
- 옛 ledger step `domains.tables`는 inert로 목록에 남는다(지우면 기동이 `newer_schema`로 거절한다).

왜: domain은 직관적이지 않고 쓰임이 없었다. 대부분 그릇과 1:1이었고 뒤 단계(runtime 칸, 명함, 앱 안 agent, harness)가 고칠 자리(정의 칸, prompt 층, skill 층, command 이름)를 줄이려고 먼저 덜어냈다(사람 2026-11-03, `project-docs/products/roadmap/agent-platform.md` 단계 1).

결정:
- 앱 command 이름의 첫 낱말은 앱 slug다. 같은 앱의 domain 둘이 같은 이름의 command를 냈으면 저장된 선언은 그대로 두고 다음 release 기록이 겹침으로 거절한다. (agent)
- 선언의 `domain` 칸을 지우고 SDK를 3.0.0으로 올린다. 봉인한 옛 bundle은 새 판에서 뜨지 않고 다시 release해야 한다(0.14.0 선례). (agent, 사람이 답하지 않아 추천대로)
- `DOMAIN.md`와 `kinds.yaml`은 옮겨 두지 않고 지운다. 레거시를 남기지 않는다. 읽는 쪽이 없고 보관 폴더도 만들지 않는다. (사람 2026-11-04, "레거시 남기지 말고 정리")
- 정의의 `domains`는 지우고 칸이 차 있던 agent는 그릇 전체로 넓어진다. 좁히는 길은 `skills_off`와 할당이다. (agent)
- `app.usage`는 invocation만 센다. 할당받은 agent의 열린 session place를 세던 안은 session을 열고 닫을 때마다 결과가 바뀌어 버렸다. (agent)
- 이름이 겹친 skill의 SKILL.md `name`을 고치므로, 옛 checkpoint가 그 SKILL.md를 되돌리려 하면 밖에서 고친 file로 보고 건너뛴다. 같은 skill의 다른 file은 되돌려진다. (agent)
- 저장된 `DomainCreated`·`DomainArchived`·`DomainUnarchived` event의 정의를 지웠다. 저장된 event를 type으로 parse해 거절하는 곳이 없다. (agent)

후속:
- 봉인한 release가 있는 앱은 다시 release해야 뜬다. 다시 release할 때 command 이름이 겹치면 고친다.
- 개발 data(`.dev-data/`)는 data step이 옮기므로 지우지 않아도 된다.
- `RESERVED_APP_SLUGS`에 지운 명령 묶음 이름 `domain`, `kind`가 남아 있다. tool 이름까지 막는 넓은 목록이라 그대로 둔다.

## float 패널은 창 몸통 어디든 가고, 고정(always on top)이 생겼다

```yaml
modules: [packages/shell/renderer, packages/shell/main, packages/design]
checked: []
```

- 전: float 층은 card가 서는 stage만 덮어서 패널이 sidebar 위로 가지 못했다. 패널은 사람이 접거나 닫을 때까지 늘 떠 있었고, bar를 두 번 눌러도 아무 일이 없었다. 창 닫기 단추는 다른 창 단추와 같은 회색 hover였다.
- 후: float 층이 title bar 아래 창 몸통 전체(양쪽 sidebar 포함)를 덮고 rect도 그 기준이다. 패널 bar에 고정 단추가 있다. 고정한 패널은 늘 고정 안 한 패널 위이고, 고정 안 한 펴진 패널은 그 패널 밖을 누르면 접힌다(`<webview>` 안 click 포함, 패널의 menu·dialog와 접힌 패널 아이콘 칸은 제외). layout 파일의 float 항목에 선택 필드 `pinned: true`가 생겼다(판 9 그대로). bar를 두 번 누르면 dock이다(`FloatPanel`의 `onBarDoubleClick`). 창 닫기 단추는 hover 때 danger 빨강이다.

왜: 사람이 float이 main 영역을 못 벗어나는 것, 다른 곳을 누르면 저절로 내려가는 모드와 늘 위에 두는 고정 모드, bar 더블클릭 dock, 창 닫기 hover 색을 요청했다(사람 2026-11-04).

결정:
- 고정 안 한 패널이 "내려가는" 것은 접기(minimize)다. 닫거나 뒤로 보내지 않는다. 새 float은 고정 안 함으로 연다. (agent)
- 저장된 rect는 옮기지 않았다. 옛 rect는 왼쪽 sidebar 폭만큼 왼쪽에 그려진다(폭이 창마다 달라 옮길 값이 없다). (agent)
- 코드가 옮긴 focus로는 접지 않는다. 사람이 누른 pointerdown과 webview 안 click(webview 그릇이 쏘는 focusin)만 본다. (agent)

후속: 없음.

## call 본문과 답, 사람 메시지가 content block으로 오가고 이미지는 model에 바로 간다

```yaml
modules: [packages/protocol, packages/cli, packages/core/lophn-agent, packages/core/router, packages/core/main, packages/shell/renderer]
checked: [architecture-event, architecture-run, architecture-workflow, architecture-agent-chat, architecture-eval, architecture-testing, architecture-approval, architecture-artifact, architecture-coding-agent, architecture-terminal-agent]
```

- 전: call 본문·답(`body`)과 사람 메시지 content는 글뿐이었다. 사람이 붙인 이미지는 `<data>/message-images/<session>/<id>`에 올라가고 글 끝에 `Attached image: open with image.read path "attachment:<id>".` 줄이, 붙인 파일은 `Attached file: <path>` 줄이 붙었다. agent는 `image.read`로 이미지를 열었다. agent는 call에 이미지를 실을 수 없었다.
- 후:
  - `SendMessage.content`, `EditQueued.content`, `SendCall.body`, `ReplyCall.body`, 받은 봉투의 `body`가 content block 배열이다(`packages/protocol/lophn-agent/content-block.ts`). block은 MCP ContentBlock 꼴인 `text`, `image {mimeType, blob}`, `resource_link`, `resource`다. 저장 part kind에 `image`, `resource_link`, `resource`가 더해졌다(`schema_version` 1 그대로).
  - 이미지는 blob이다. 사람은 `UploadMessageImage`(입력 `{content_type, bytes}`, 출력 `{blob}`), agent는 새 memory route `PrepareMessageImage`(base64, 180 KB 이하)로 올린다. 메시지가 blob 참조(field `image`)를 갖고, 그 참조가 있는 session에서만 읽힌다(`ResolveMessageImage`, `ReadMessageImage`는 `att_` id와 blob hash를 다 받는다).
  - 받은 turn과 뒤 이력이 같은 함수(`inputParts`)로 tag 글, image part, 닫는 글을 만든다. 이미지는 `image.read` 없이 넷 packer가 각자의 image 꼴로 싣고, 이미지를 못 받는 model에는 `IMAGE_OMITTED`가 간다. 입력 예산은 이미지를 4096 token으로 센다. 자동 제목, 검색, Compact 재료에는 `[image]`가 간다.
  - model 요청의 이미지는 최신 것부터 base64 합 12 MiB까지만 싣는다(`omitOldImages`, tool 결과 이미지와 같이 센다). 예전에는 tool 이미지 최신 둘이었다.
  - `lophn call send|reply`에 `--image <path>`(되풀이 가능)가 생겼다. lophn tool로 부르면 그 session이 읽을 수 있는 file만(file tool과 같은 검사) 싣는다.
  - composer는 이미지를 image block으로, 파일을 `file://<path>` `resource_link` block으로 보낸다. 메시지 목록은 사람 메시지와 받은 call·답의 이미지, 링크, resource를 그린다. 대기 메시지를 고쳐도 이미지가 남는다.
  - `packages/protocol/lophn-agent/message-attachments.ts`(첨부 줄 만들기·떼기)를 지웠다.

옮기기: 없음. 새 column과 ledger step이 없다. 옛 메시지는 첨부 줄을 글 그대로 가진다(가져간 본문은 trigger가 고정한다). `image.read`와 화면은 옛 `attachment:<id>`를 계속 읽는다. 화면은 옛 줄을 이미지로 그리지 않고 글로 보인다.

왜: bare agent에는 `image.read`가 없어 첨부 줄로는 이미지를 못 본다. 뒤 단계(runtime 칸, 명함, 앱 안 agent, harness)가 모두 이 단위로 주고받는다(`project-docs/products/roadmap/agent-platform.md` 단계 2).

결정:
- block은 MCP ContentBlock 꼴을 빌리고 이미지는 bytes 대신 blob hash를 갖는다. content 상한(240 KiB)에 이미지가 안 들어가서다. (agent)
- 넘길 것은 값으로 싣는다. 받는 쪽에 file 읽기 허락(grant)을 주지 않는다. (agent)
- 받은 이미지는 뒤 turn에도 그대로 싣는다. 넘치면 자동 Compact가 맡는다. 다만 base64 합이 12 MiB를 넘으면 오래된 이미지는 `[image]`(tool 이미지는 `[image omitted]`)가 된다. 요청 body 전체를 저장하는 blob 상한이 16 MiB라 사람의 5 MiB 이미지 셋이면 session이 막혔다. 개수 규칙(최신 둘)은 한 메시지의 작은 screenshot 여럿을 빼서 크기 규칙으로 바꿨다. (agent)
- redaction은 글(text, link, resource text)에만 한다. 이미지는 tool 결과 이미지처럼 거치지 않는다. (agent)
- 옛 메시지의 첨부 줄은 block으로 옮기지 않는다. (agent)
- runtime이 이미지 bytes를 읽는 길은 새 machine read가 아니라 agent 자격의 `ResolveMessageImage`다. credential session과 입력 session이 같아야 하고 그 session의 메시지가 blob을 참조해야 한다. Compact는 bytes를 읽지 않는다. (agent)
- 읽지 못한 이미지는 받은 turn과 이력 모두 `[image unavailable]` 글이 된다. 깨진 이미지 하나가 session을 막지 않게 했다. (agent)
- 파일만 보낸 메시지의 자동 제목은 예전처럼 파일 이름이다(`blocksSummary`가 링크 이름을 낸다). (agent)

후속:
- 일하는 중 보낸 이미지만 든 메시지가 live 대기 줄에서 빈 줄로 보인다(`project-docs/issues/shell.md`).
- 보내지 못한 메시지를 10분 넘어 다시 보내면 올린 이미지 준비가 만료되어 실패한다. 사람이 다시 붙인다.
- session을 지워도 이미지 blob과 옛 이미지 파일은 지우지 않는다(지금도 그렇다).

## bare runtime: 정의가 고른 것만 싣는 agent

```yaml
modules: [packages/protocol, packages/cli, packages/core/agent-places, packages/core/lophn-agent, packages/core/main, packages/core/router, packages/shell/renderer, packages/design]
checked: [architecture-approval, architecture-place-session, architecture-workflow, architecture-event]
```

- 전: 같은 place 종류의 session은 agent가 누구든 같은 tool 목록, 제품 고정 규칙과 place 종류 지침, 지침 층, 내장 skill, place 정보를 받았다. result call은 받은 agent가 `lophn call reply`로 답해야만 done이었다. 정의에 한 줄 목적 칸이 없었다.
- 후:
  - 정의에 `runtime`(`lophn | bare`, 없으면 lophn), `description`(한 줄, 200자 이하), `tools`(bare일 때만, 고른 이름)가 생겼다. 내장 lophn은 `bare`를 거절하고, lophn에서 `tools`를 쓰면 `invalid_input`이다. agent도 `agent.create`·`agent.update`로 세 칸을 쓴다. 옛 정의 파일은 옮기지 않는다(없으면 lophn).
  - bare session의 system은 정의 본문 하나다(web tool을 골랐으면 `<lophn-untrusted>` 한 줄을 붙인다). 제품 고정 규칙, place 종류 지침, 전역·project 지침, skill 목록, place 정보 글은 없다. tools는 고른 내장 tool ∩ place 종류 목록, 고른 명령·할당 앱 command만 실은 `lophn` tool, 고른 MCP tool이다. 실행 목록도 같게 좁고, 목록 밖을 고르면 보이지도 돌지도 않는다. credential 상한(`placeOperations`)과 file 범위는 place 종류 그대로다. notice는 tool이 바뀐 것만 간다.
  - bare가 받은 result call 글은 "마지막 응답이 답"이라고 알린다(받은 turn과 이력 재생이 같은 bytes). 그 turn이 `answer_completed`로 끝나고 마지막 응답 글이 있으면 core wiring(`wiring/bare-reply.ts`)이 `TurnEnded`를 보고 새 machine 명령 `AutoReplyCall`로 답한다. 멈춤, 실패, 빈 글이면 답하지 않아 call은 accepted로 남는다. lophn runtime은 지금처럼 reply 명령이다.
  - place 종류 tool 이름 목록(`placeToolNames`)이 `packages/protocol/lophn-agent/tool-lists.ts`로 옮겼다. 순서(`TOOL_ORDER`)는 core에 남았다. Agents 편집 화면에 Description, Runtime, bare의 Tools 고르기(모든 place 종류의 내장 tool 체크와 이름 적기)가 생겼고, bare면 Skills 칸을 숨긴다. 카드에 description이 보인다.
  - 마지막 응답 읽기는 run의 답과 bare 자동 답이 같은 함수(`wiring/turn-answer.ts`의 `turnAnswer`)다.

첫 요청 bytes (fake 조립, provider 호출 없음. place 정보는 앱 하나·project 하나·다른 agent 하나, 지침은 전역 "Be brief."와 project "Use pnpm.", skill은 그 place의 내장 skill. 대화는 "hello" 하나. bare는 `file.read, file.glob, file.grep, file.write, shell.run, web.fetch, call.reply`를 고르고 본문 95 bytes):

| place | lophn system | lophn tools | lophn 합 | bare system | bare tools | bare 합 |
|---|---|---|---|---|---|---|
| home | 8,869 | 7,120 | 16,443 | 223 | 2,524 | 2,972 |
| project | 8,829 | 8,885 | 18,175 | 223 | 3,974 | 4,422 |
| app | 12,430 | 9,465 | 22,405 | 223 | 3,974 | 4,422 |

home에서는 `file.write`, `shell.run`이 place 종류 목록 밖이라 빠진다. 이 변경 앞뒤로 lophn session의 요청 전체 sha256이 세 place 모두 같았다.

왜: 앱 안 코치나 짧은 일 agent는 lophn 제품 규칙과 내장 tool 전부가 필요 없고 그 bytes가 매 turn 든다. reply 명령을 모르는 runtime이 result call에 답하지 않아 부른 쪽이 멈추는 일을 막는다(`project-docs/products/roadmap/agent-platform.md` 단계 3).

결정:
- 고르는 칸은 `tools: string[]` 하나이고 bare에서만 쓴다. lophn runtime에는 항목별 끄기를 두지 않는다. (agent)
- 고른 것은 place 종류 목록, 할당, 설정한 MCP 안에서만 보이고 돈다. credential 상한은 고른 것과 상관없이 place 종류로 정한다. (agent)
- bare의 system cache 표시는 본문 block 하나에 단다(tools까지 덮는다). (agent)
- 정의에서 뺀 이름은 바로 못 부르고, 더한 이름은 새 session부터다. tool 목록을 session 시작에 고정하는 규칙과 같은 때다. (agent)
- 자동 답은 runtime 쪽이나 tx 안이 아니라 core wiring이 `TurnEnded`를 보고 한다. 멈춘 turn에 답이 나가지 않고, 본문 blob은 tx 밖에서 만든다. 답하지 못한 call에 새 실패 길을 더하지 않았다. (agent)
- bare가 받은 call의 경계는 tag 이름과 메시지마다 붙는 고정 글이 알린다. 인터넷에서 온 것만 `<lophn-untrusted>` 한 줄로 알린다. (agent)
- 편집 화면의 내장 tool 목록은 core와 같은 protocol 목록을 쓰고, 정의가 전역이라 모든 place 종류의 tool을 보인다. (agent)

후속:
- bare agent가 `workflow.report`를 고르지 않으면 workflow step을 끝내지 못한다(`project-docs/issues/workflow.md`).
- 고른 이름이 틀리거나 상한 밖이면 말없이 빠진다(`project-docs/issues/agent-definition.md`).
- Compact 요약 재료는 bare의 result call도 lophn 글("`lophn call reply`로 답하라")로 싼다(`packages/core/session/compactor.ts`가 runtime을 넘기지 않는다).
- 자동 답은 글만 싣는다. 실제 core에서 bare session을 끝까지 돌리는 test는 아직 없다(module test만 있다).

## extension: 본체와 따로 켜는 기능 묶음

```yaml
modules: [packages/protocol, packages/shell/main, packages/shell/ipc, packages/shell/preload, packages/shell/renderer, packages/core/config, packages/design, tools]
checked: [tool-check, architecture-layers, tool-dev, tool-worktree-prep, architecture-workspace-layout, architecture-ui-kit, architecture-appearance, skill-ui-design, tool-wireframes]
```

- 전: 대다수에게 필요 없는 기능(third-party CLI GUI, harness host)을 따로 두고 켜는 구조가 없었다.
- 후: extension 하나는 폴더와 `manifest.json`(`id`, `name`, `description`, `version`, `entry`, `provides`)이다. shell main의 registry가 manifest만 읽고, 설정 `extensions.<id>.enabled`가 켜졌고 판이 제품 판과 같은 것만 `entry`를 load해 `activate(ctx)`한다. 끄면 `deactivate()`한다. extension code는 `ctx`(`core`, `settings`, `spawn`, `clock`, `ids`, `files`)로만 lophn에 닿고 shell main 내부를 import하면 `tools/check-deps.ts`가 막는다. Settings › System › Extensions에서 사람이 설치(표시 file)·켜기·끄기·지우기를 한다. 지우기는 extension이 `ctx.files`로 쓴 file만 지운다. 설정 `extensions.harness.enabled`(기본 false)를 선언했다. 본체 안 extension은 아직 없다(`project-docs/architecture/extension.md`).

왜: 사람이 "별도로 설치하게끔, 근데 지금 그런 구조가 없거든", "구조도 만들어놓자"라고 했다(`project-docs/products/roadmap/agent-platform.md` 단계 6).

결정:
- 받는 길은 먼저 본체 .deb 안에 넣어 두고 설정에서 켠다. 뒤에 따로 받는 package로 옮긴다. 그 전환이 구조를 고치지 않게 따로 빌드한 file을 경로로 load하고, registry는 폴더 목록만 읽고, `ctx`로만 닿는다. (사람, 2026-11-04)
- 설정 선언은 id마다 `packages/core/config/shell-settings.ts`에 정적으로 한 줄이다. 선언이 없는 id는 켜지 않는다. Settings › General은 `extensions.*`를 보이지 않는다. (agent)
- `ctx`에 `files.write`를 더했다. 무엇을 썼는지 registry가 알아야 그것만 지운다. (agent)
- 판은 글자가 같아야 켠다. (agent)
- 새 pane id는 `extension-packages`다. Settings › Agents의 `tools` pane(lophn agent의 skill·MCP, 문구 "Extensions")과 다르다. (agent)

후속:
- 설치본에 본체 안 extension 넣기와 계획 harness-agent의 켜기를 `extensions.harness.enabled`로 바꾸기는 계획 harness-agent가 했다(아래 항목).

## A2A의 명함과 시야: agent가 서로를 고르고, place 정책이 누가 누구를 부를지 정한다

```yaml
modules: [packages/protocol, packages/cli, packages/core/agent-places, packages/core/lophn-agent, packages/core/main, packages/core/router, packages/core/config, packages/core/apps, packages/shell/renderer, packages/design, tests]
checked: [architecture-layers, architecture-run, architecture-workflow, architecture-eval, architecture-testing, architecture-app-call, architecture-activation, architecture-artifact, tool-eval, tests-support, tool-test-live, tool-models-snapshot]
```

- 전: 부르는 agent는 "Agents you can call"의 이름만 보고 골랐다. 받는 agent가 이미지를 받는지, result로 답할 수 있는지 알 길이 없었고 Router는 무엇이든 보냈다. 어느 place의 agent든 어느 place로든 call을 보낼 수 있었고, 불려서 home에 열린 session은 등록된 모든 project 폴더를 읽었다. bare는 skill을 받지 못했다.
- 후:
  - 정의에 `modality: {input?, output?}`(`text`, `image`, `file`, 없으면 셋 다)가 생겼다. 명함은 program이 정의와 할당에서 계산하고 저장하지 않는다: name, description, runtime, modality, 답 방식, 기본 lophn agent와의 차이(plus, minus), notes. 읽기 route `agents/card`, 명령 `lophn agent card <name>`이고 모든 place 종류에서 부른다. agent session이 읽으면 `callable`(자기 place에서 부를 수 있나)이 붙는다.
  - place 정보의 "Agents you can call"이 `- <name>: <description>`이다. notice 기준에도 같은 줄이 들어가 description이 바뀌면 `agents_changed`가 간다. 차이와 modality는 system에 싣지 않는다.
  - Router는 agent가 보낸 call만 거른다. call 정책 밖이면 `forbidden`이고, 받는 agent의 입력 modality에 없는 block(image → image, `resource_link`·`resource` → file)이나 받는 agent가 못 하는 답 방식이면 `invalid_input`이다. 둘 다 tx가 되돌아가 call 행도 새 session도 남지 않는다. 사람 메시지, program 알림, workflow step, 답은 보지 않는다.
  - call 정책의 기본은 모두 허용이다. 설정 `lophn-agent.call_policy`의 `places`가 place 쌍을, `agents`가 agent 쌍을 거절하거나 허용한다(agent 쌍 → place 쌍 → 기본 허용). Settings › Agents에 "Calls between places" 절이 생겼고, 규칙이 없으면 모두 허용이다.
  - 다른 place의 session이 부른 call로 열린 home session은 project 폴더를 읽지 않는다. 열 때 부른 place를 `sessions.called_from_kind`·`called_from_id`(새 schema step `lophn-agent.sessions.called-from`, 옛 행은 비어 있어 그대로다)에 남긴다.
  - bare 정의에 `skills`(고른 skill 이름, bare만)가 생겼다. 고른 skill이 있으면 bare system에 그 목록만 싣고 `skill.read`를 더한다. 명함 plus에 `skill: <name>`으로 보인다.
  - Agents 화면의 카드와 편집기가 같은 명함을 보인다. 편집기에서 modality와 bare의 skill을 고른다.

왜: 사람이 agent가 서로를 고를 명함과, place마다 agent가 열이면 agent 쌍을 하나하나 고르기엔 경우가 너무 많으니 place 정책으로 크게 정하자고 했다(`project-docs/products/roadmap/agent-platform.md` 단계 9). bare는 다 덜어진 상태에서 사람이 skill도 더한다(단계 3의 남은 것).

결정:
- model에 가는 자리는 place 목록의 한 줄 목적과 `lophn agent card`다. 차이는 system prompt에 싣지 않는다(cache). (agent)
- 차이는 place와 상관없이 할당한 앱의 public command·public skill, 정의 층 MCP server, `skills_off`, runtime으로 계산한다. prompt 원문은 보이지 않는다. (agent)
- 답 방식은 칸 없이 program이 정한다. lophn은 none, result, conversation이고 bare는 none, result에 `call.reply`를 골랐을 때 conversation. (agent)
- model이 이미지를 못 받으면 거절하지 않고 명함 notes가 알린다. (agent)
- 시야는 기본 허용이고, 사람이 place 정책으로 크게 거절하고 agent 정책이 예외로 덧쓴다. 거절은 `forbidden`이다. 먼저 있던 기본 거절 표는 agent의 추천이었고 lophn의 container 넘는 위임을 막아 되돌렸다. (사람, 2026-11-04)
- 불려서 home에 열린 session은 실어 보낸 것만 본다. 이미 열린 home session에 닿은 call과 사람이 연 home session은 좁히지 않는다. (사람, 2026-11-04 추천대로)
- bare가 skill을 고르면 `skill.read`를 program이 더한다. 고른 skill을 읽을 tool이 없으면 목록이 소용없다. (agent)

후속:
- 정책이 막는 agent도 "Agents you can call"과 call 목록에 보인다. 부르면 tool 결과가 바로 `forbidden`이다.
- 불려서 home에 열린 session의 place 정보에는 project 이름과 목적이 그대로 보인다(폴더는 못 읽는다).
- 넘기기 효과를 재는 eval은 실제 model 호출이라 사람이 정할 때 돌린다.

## harness agent: Claude Code, Codex, OpenCode를 agent runtime으로

```yaml
modules: [packages/protocol, packages/core/lophn-agent, packages/core/router, packages/core/main, packages/core/config, packages/core/agent-places, packages/core/workflows, packages/cli, packages/coding-agent, packages/shell/main, packages/shell/renderer, packages/design, tools]
checked: [architecture-run, architecture-testing, architecture-eval, architecture-activation, architecture-app-call, architecture-artifact, tool-check, tool-dev, tool-eval, tests-support, tool-test-live, tool-models-snapshot, tool-worktree-prep, architecture-workspace-layout, architecture-ui-kit, architecture-appearance, skill-ui-design]
```

- 전: lophn은 coding agent에게 일을 맡기지 않았다. 정의의 `runtime`은 `lophn | bare`였고 workflow의 harness 참가자는 `not_handed`였다.
- 후: `runtime`에 `claude-code`, `codex`, `opencode`가 있다. 그런 agent의 session은 core의 harness 입력함이 받고, extension `harness`(Settings › System › Extensions, 설정 `extensions.harness.enabled`)가 입력마다 그 harness의 headless 명령(`claude -p`, `codex exec`, `opencode run`)을 place 폴더에서 돌려 출력을 메시지와 `harness_tool` part로 기록한다. harness의 session id를 session에 두어(ledger step `lophn-agent.sessions.harness`) 다음 입력과 각 CLI의 resume이 같은 대화를 잇는다. turn마다 그 session·turn에만 쓰이는 agent 자격을 env `LOPHN_AGENT_CREDENTIAL`로 넘겨 harness가 자기 shell에서 `lophn call reply|send`, `session list`, `agent card`를 부르고, 내장 skill `lophn-agent`가 그 쓰는 법을 harness skill 폴더에 둔다. result call은 답하지 않으면 마지막 메시지가 답이다. workflow step은 `{agent}` 참가자로 harness agent에 간다. 편집기는 켜졌을 때 harness runtime을 고르게 한다. 본체 안 extension의 entry를 따로 build해 .deb의 설치 root `extensions/`에 넣고, manifest 판이 제품 판과 다르면 build가 멈춘다. extension process는 stdout·stderr를 따로 받고 stdin을 닫을 수 있고 `LOPHN_HOME`을 늘 받는다. ACP의 `message_recorded`는 `model_call: null`을 받는다(`project-docs/architecture/coding-agent.md`의 "harness agent").

왜: 사람이 "third party agent harness도 우리 agent로 등록해서 프로그램틱 호출, tui 열기가 가능하게 할거야 워크플로우에서 쓰기 위해서", "그 실행은 cli command가 맡는거고"라고 했다(`project-docs/products/roadmap/agent-platform.md` 단계 7).

결정:
- harness는 programmatic 실행을 공식으로 지원하므로 사람 없이(workflow, job) 돌려도 된다. (사람, 2026-11-04)
- host는 shell main의 extension `harness`이고 켜기는 extension 설정 하나다. 계획 extension이 먼저 land했다. (agent)
- harness가 쓴 tool은 lophn이 실행한 것이 아니라 gate·rewind chain에 넣지 않고 `harness_tool {name, summary, status}` part로만 남긴다. (agent)
- 전부 허락 flag(`bypassPermissions`, `danger-full-access`)는 쓰지 않는다. Claude Code는 `acceptEdits`와 `Bash(lophn *)` allow(그 밖의 쓰기 Bash 거절, 읽기 명령은 Claude Code 자체 규칙으로 통과), 정의의 deny는 disallow다. Codex는 `workspace-write`이고 deny를 옮길 수 없어 deny가 있는 정의는 띄우지 않는다. (agent)
- Codex의 sandbox가 loopback까지 막아 CLI가 core에 닿도록 `network_access=true`를 넣는다. Codex가 돌리는 명령이 인터넷에도 닿는다. (사람, 2026-11-04. harness-lab의 emdash·orca는 sandbox를 끄고 happy는 host tool을 MCP로 넘긴다는 조사를 보고)
- harness는 MCP bridge가 아니라 `lophn` CLI를 쓰고, 쓰는 법은 skill로 harness skill 폴더에 배포한다. (사람, 2026-11-04)
- opencode에는 권한 flag가 없어 사람의 opencode 설정대로 돈다. (사람, 2026-11-04)
- 자격은 기존 `CredentialRegistry`로 내고 범위는 그 place 종류의 `lophn` 명령 route다(file·rewind·gate·ask 없음). user token은 넘기지 않는다. (agent)
- 실제 harness 실행(Claude Code 2.1.318, codex-cli 0.166.0, opencode 2.1.4)으로 parser fixture를 녹화하고, argv와 resume, Claude→Codex call send와 `lophn call reply`, opencode의 `lophn` 호출, Claude의 쓰기 Bash 거절을 확인했다. (사람이 허락)

후속:
- harness session의 steer와 fork가 harness에 닿지 않는다, home에서 돌지 않고 opencode는 git root에 쓴다, opencode 권한을 좁히기(`project-docs/issues/coding-agent.md`).
- 이름 없는 `{kind: harness}` workflow 참가자 지우기(`project-docs/issues/workflow.md`).
- TUI 열기 화면은 없다. 같은 session id로 각 CLI가 resume한다(단계 8과 같이).
