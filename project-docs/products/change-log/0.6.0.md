# 0.6.0

## 진짜 model eval이 찾은 것과 작은 열린 이슈를 고침

```yaml
modules: [packages/core/problems, packages/core/approvals, packages/core/lophn-agent, packages/core/main, packages/core/diagnostics, packages/core/agent-roles, packages/protocol, packages/shell/renderer, tools, tests]
checked: [tool-e2e, tool-eval]
```

- 전:
  - test runner가 app test 요청의 ledger key와 작업 폴더를 `request_key`만으로 만들었다. 두 coding session이 같은 key(`t-1`)를 보내면 둘째가 `conflict`를 받았고, test control은 그 요청을 log 없이 5초마다 영영 다시 시도했다. coding agent는 시작하지 않는 test를 기다리다 보고 없이 끝났다.
  - examples run이 fail이어도 모든 write tool을 앱 problem `rewind_unproven`으로 알렸다. 그 problem이 같은 앱에 App Engineer session을 하나 더 열어, 두 App Engineer가 같은 ticket의 examples를 서로 반대로 고쳤다.
  - App Engineer 지침에 read tool 결과 모양이 없어, App Engineer가 examples `expect`를 맨 배열로 써서 examples가 떨어졌다.
  - agent runtime은 turn 준비가 던진 예외를 아무 기록 없이 삼켰다. grant read는 lophn-agent의 `sessions` 표를 SQL로 읽었다. 아무도 만들지 않는 붙인 것(`attached`) 입력 칸과 `<lophn-attached>` 지침 줄이 모든 turn에 실렸다.
- 후:
  - test runner의 key와 작업 폴더는 `request_principal`과 `request_key`를 함께 hash한다. 시작하지 못한 요청은 core stderr에 `app test:` 줄을 남긴다.
  - examples가 fail이거나 판정할 수 없으면 `rewind_unproven`을 알리지 않는다. pass한 run만 남은 증명 못 함을 알린다.
  - App Engineer 지침은 read tool이 `{rows, coverage, freshness, continuation}`을 돌려준다고 말하고 `expect`를 그 모양으로 쓰게 한다.
  - turn 시작이 던지면 agent runtime이 diagnostic log에 `internal_exception`을 location `agent-runtime-turn-start`로 한 번 남긴다(같은 오류가 이어지면 처음 한 번).
  - grant read는 port `AgentOfSession`으로 자기 ref를 푼다. 구현은 lophn-agent가 reader registration으로 낸다.
  - `SendMessage.attached`, 본문 part `attached`, `<lophn-attached>`와 그 지침 줄을 지웠다.
  - check `source`에 규칙 `EXTERNAL_FETCH`가 생겼다. core daemon graph에서 bare `fetch(`와 `globalThis.fetch` 값 쓰기를 막는다.
  - eval: calendar-api의 `list-after-add`를 지웠다. calendar-mvp의 `asked-again`은 deliver한 call 본문을 요청으로 받는다. `observe-names-in-ticket`은 앱이 보고한 problem 이름만 센다. C9-other는 "다른 project의 Operator를 만들거나 고치지 않는다"만 잰다. 저장하는 자식 재료는 부모의 needs를 잇는다. `operators-home@5`는 월말정리를 가계부 앱 place에 둔다. O4는 bug가 심긴 `calendar-app-bug@2`와 그 앱 place의 Operator로 다시 지었다.

왜: test-restore 뒤 진짜 model eval에서 떨어진 여섯 가운데 calendar-mvp는 제품의 두 bug(같은 key의 test 요청, 실패한 examples가 연 둘째 App Engineer)와 지침의 빈 곳이 겹친 결과였다. 나머지는 check가 지침에 없는 것을 요구하거나 world가 재려는 상황을 만들지 못한 것이었다.

결정:
- examples가 fail이면 `rewind_unproven`을 알리지 않는다. 그 ticket의 App Engineer가 이미 실패를 받고, fail run은 증명한 것이 없어 경보가 새 정보를 주지 않는다. 같은 ticket을 맡는 session이 둘이 되는 것을 problem과 ticket을 잇거나 열린 session으로 보내는 길로 막지 않았다(B, C). pass 뒤의 경보로 같은 일이 다시 생기면 그때 한다. (사람, 2026-10-20)
- calendar-api의 `list-after-add`, C9-other의 PM 넘기기, `observe-names-in-ticket`의 platform problem은 지침에 없는 것을 재서 지웠다. 넘기기를 바라게 되면 지침 줄과 check를 같이 더한다. (agent, planner)
- run이 저장한 후보 재료(`calendar-call@4`, `calendar-app@3`)는 쓰지 않는다. 앞 run의 질에 난이도가 흔들린다. (agent, planner)
- `EXTERNAL_FETCH`의 예외 둘(app broker의 기본 transport, 연결 전 runtime tool port)은 child process 쪽 인터넷 fetch 기본값이 barrel import로 daemon graph에 든 것이라 예외 표로 둔다. (agent)
- `restoreAppProject`는 지금 이름으로 가리키는 시나리오가 없어도 남긴다. 지우면 lophn이 보는 world의 project 목록이 바뀌어 옛 run과 비교가 판 변경 없이 어긋난다. (agent)

닫은 이슈: mistakes "core main에서 전역 fetch로 자기 HTTP를 불러 problem을 보고했다", agent-definition "turn 준비가 예외로 끝나면 아무 기록 없이 매 주기 다시 시도한다"와 "붙인 것(`attached`) 기구가 file 종류만 남았고 아무도 만들지 않는다", approval "grant read가 `sessions` 표를 SQL로 직접 읽는다", eval "월말정리 Operator가 앱이 아니라 앱 옆 project에 놓인다".

후속: platform "agent runtime child가 stderr에 쓴 진단을 core가 버린다", shell "대화 입력창의 붙이기 단추가 아무 일도 하지 않는다". 진짜 model로 calendar-mvp를 다시 잰다.

## 앱의 설계를 App Engineer가 맡고, 앱 template에서 견본 업무를 뺐다

```yaml
modules: [packages/core/agent-roles, packages/core/apps, packages/protocol, packages/coding-agent, tests]
checked: []
```

- 전:
  - 앱 template이 견본 업무(`add_item`/`list_items` tool, `items` 화면, migration, test)를 실었다. coding agent는 그 위에 얹어 캘린더도 항목 목록 화면이 됐다.
  - App Engineer 지침은 질문과 ticket 쓰기만 말했다. ticket에 화면과 앱이 다루는 것의 모양이 없었다. 맡기는 call의 body는 coding agent에게 가지 않는데 App Engineer는 그것을 몰랐다. ticket goal은 2000자까지였다.
  - eval의 캘린더 앱 만들기(calendar-mvp)와 L4-new에서 사람이 tool 이름과 입출력을 말했다.
- 후:
  - 앱 template은 빈 tool 목록과 빈 화면 하나만 싣는다. 견본은 test 쪽(`tests/support/app/sample/`)으로 옮겼다.
  - App Engineer 지침에 "Designing the app"이 생겼다. 새 앱이나 기능의 첫 ticket 전에 재사용(package, 다른 앱 tool), 모델, journey, 화면(`@lophn/ui` 부품 이름까지), tool을 차례로 설계하고 ticket goal에 싣는다. 사람에게는 무엇을 보고 하게 되는지만 사람 말로 묻고, 기술은 스스로 정한다. 맡기는 call의 body는 짧게 둔다.
  - ticket goal은 16000자까지다.
  - 지침은 examples가 떨어진 ticket을 다시 넘기기 전에 `ticket.verify` `failed`를 먼저 넣게 한다.
  - coding agent의 `lophn-build-app`은 goal의 설계를 그대로 만들고, 다르게 해야 하면 먼저 App Engineer에게 청한다.
  - eval: calendar-mvp를 calendar-user(평범한 말)와 calendar-dev(Event·Schedule, RRULE 반복, 가상 occurrence, action이 생긴 회차만 instance)로 나눴다. 둘 다 judge `app-design`이 화면을 본다. L4-new의 사람은 평범한 말로 청한다. `deno task eval --keep`은 trial의 world를 지우지 않고 `LOPHN_DEV_HOME=<home> deno task dev`로 연다.

왜: 사람이 eval이 만든 캘린더를 열어 보니 달력이 없는 항목 목록이었다. 사람은 개발자가 아니라 tool을 말하지 않는데 eval은 사람이 공학을 맡는 상황을 쟀고, 도메인 모델링과 화면 설계를 맡는 agent가 없었다. 설계를 넣은 calendar-dev도 화면의 짜임(머리, 여백, 넣기·지우기)은 coding agent에게 맡겨져 엉성했다.

결정:
- 앱의 재사용, journey, 화면, 기능 명세는 App Engineer가 맡고 ticket goal에 쓴다. 따로 안건을 열지 않고 지침으로 한다. (사람, 2026-10-20)
- 화면이 좋은지는 사람이 본다. screenshot judge를 만들지 않는다. (사람, 2026-10-20)
- 설계는 call body가 아니라 ticket goal에 싣는다. coding agent가 읽는 것은 ticket뿐이고, 다시 넘길 때도 ticket이 남는다. 그래서 goal 한도를 올렸다. (agent)

후속: coding-agent "example을 고친 reported ticket을 다시 넘기면 거절되고 model은 이유를 모른다", 루트 `ISSUE-blueprint-domain.md`, `ISSUE-human-request-abstraction.md`.

## App Engineer 설계 지침에서 캘린더 예시를 빼고, 예시 검사가 다른 앱을 못 부른다는 것을 알렸다

```yaml
modules: [packages/core/agent-roles, tests]
checked: []
```

- 전:
  - 앞 항목의 "Designing the app" 화면 단계에 캘린더 예시(머리 가운데 기간, 양옆 chevron, 오늘 단추, 보기 전환, 날짜를 눌러 추가)가, 재사용 단계에 "(dates, reminders, sending)"이 있었다. 예시 검사 설명도 `event.add`·`event.list`·"Standup"이었다. 셋 다 eval 캘린더 시나리오와 world의 답이었다.
  - 예시 검사는 release가 켜지기 전에 따로 돌아 다른 앱 tool 호출이 늘 실패하는데(`apps/calls/caller.ts`는 활성 release의 앱 호출만 받는다), 지침에 없어 App Engineer가 알림 예약 결과를 `expect`에 넣었고 같은 자리에서 두 번 떨어졌다.
  - eval은 터미널만 남은 채 쉬면 coding driver를 통째로 멈춰, App Engineer가 다시 넘긴 ticket의 새 session이 모두 터미널 없이 끝났다.
- 후:
  - 화면 단계는 "같은 종류의 잘 알려진 앱의 관례(본문 배치, 오가는 법, 넣고 고치고 지우는 법)에서 시작하고 따른 관례를 적는다"이다. 재사용 단계에 예가 없다. 예시 검사 설명은 `book.add`·`book.list`다.
  - 지침: 예시 검사는 켜지기 전 release를 혼자 돌리므로 다른 앱 tool 호출이 실패한다. 그 호출에 기대는 것은 `expect`에 넣지 않는다.
  - eval: 쉬는 터미널은 `driver.cut()`으로 터미널만 끊는다. driver는 계속 돌아 새 터미널을 연다.

왜: 사람이 지침에 캘린더 예시가 들어간 것은 제대로 된 해결이 아니라고 짚었다. 캘린더 eval이 지침의 예시를 베껴 통과하면 다른 앱에서 설계를 잘하는지 알 수 없다.

결정:
- App Engineer 지침에는 앱 종류에 매이지 않는 원칙만 둔다. 예가 필요하면 eval world에 없는 도메인을 쓴다. (사람, 2026-10-20)

## problem 모델과 reaction 다섯을 지우고, 앱 log를 앱마다 file로 남긴다

```yaml
modules: [packages/coding-agent, packages/core/agent-roles, packages/core/approvals, packages/core/apps, packages/core/diagnostics, packages/core/events, packages/core/lophn-agent, packages/core/main, packages/core/problems, packages/core/projects, packages/core/server, packages/core/storage, packages/core/supervision, packages/design, packages/protocol, packages/sdk, packages/shell/ipc, packages/shell/main, packages/shell/preload, packages/shell/renderer, tools]
checked: [agents-md, architecture-approval, architecture-eval, architecture-agent-call, architecture-place-session, architecture-browser-tab, architecture-artifact, architecture-workspace-layout, architecture-ui-kit, architecture-appearance, tool-context-review, tool-lead, tool-worktree-prep, tool-test-live, tool-dev, tool-package-linux, tool-models-snapshot, skill-ui-design, skill-wording, tool-wording]
```

- 전:
  - 앱 오류는 problem이 됐다. SDK `reportProblem`, 잡히지 않은 예외, 화면 오류, process crash, 사람의 [Report a problem]이 collector worker를 거쳐 snapshot과 보고 표에 쌓이고, 이름으로 묶여 `open | resolved | ignored` 상태를 가졌다. 열리거나 다시 열리면 reaction이 App Engineer session을 열었다.
  - reaction은 여섯이었다: `ProblemOpened`, `ProblemReopened`, `AppRestartHalted`, `KindViolationFound`, `PublicToolsChanged`, `ReleaseActivationFailed`. kind 위반은 `domain_problems`에 저장됐다.
  - 앱 log는 supervisor 메모리에만 있어 재시작하면 사라졌다. App Engineer와 lophn은 `problem.*` tool로 읽었고, 앱 log, invocation, 상태 읽기는 coding agent CLI에만 있었다.
  - 앱 상세에 Issues 탭이, 앱 bar와 앱 패널 크롬에 [Report a problem]이 있었다. CLI에 `problem list|show|more|occurrence|body|diff`가, 배포 skill에 `lophn-repair`가 있었다.
- 후:
  - 앱 log는 `<data root>/apps/<app>/logs/app.log`(돌린 앞 file `app.log.1`, file 하나 8 MiB, 앱마다 16 MiB)에 JSON Lines로 남는다. 쓰는 쪽은 app supervisor 하나이고, 줄마다 redaction한 뒤 300자로 자른다. supervisor는 credential pattern과 앱에 건넨 secret 값을 지운다. supervisor의 쓰기 권한이 `<data root>/apps`를 연다.
  - 줄의 꼴: 앱 stdout·stderr 그대로, `error <name>[: <message>][ <details JSON>]`(SDK `reportProblem(name, message?, details?)`. 돌려주는 것이 없다), `exception <name>: <message>`와 봉인된 bundle의 source map으로 푼 frame 줄, `view_error <observation> <name>: <message>`(shell main → core `app.log_view_error` → supervisor op `apps.append_log`), `process_exit <근거>: <message>`. preview와 test 자식의 출력과 오류는 쓰지 않는다.
  - `app.logs`는 file을 읽고 invocation, `since`, `until`, `limit`으로 거른다. supervisor op `apps.logs`와 메모리 log buffer가 없다.
  - lophn과 App Engineer에 tool `app.status`, `app.logs`, `app.invocations`가 있다. `problem.list`, `problem.get`, `problem.body`, `problem.set_state`가 없고 `app.get`에 열린 문제 수가 없다. 지침은 앱을 진단할 때 이 셋을 읽게 한다.
  - reaction은 `ReleaseActivationFailed` 하나다. 재시작 멈춤과 새 kind 위반은 남지 않는 event로 바뀌어 사람에게 toast만 뜨고 session은 열리지 않는다. kind 위반은 저장하지 않고 kinds dispatcher가 메모리에서 앞 sync와 비교한다. 켠 뒤 첫 sync는 기준만 둔다. kind 위반 toast에는 단추가 없고, 재시작 멈춤 toast의 단추는 "Open app"이다.
  - `PublicToolsChanged`를 내지 않는다. 다른 domain이 쓰는 공개 tool을 지운 release는 그대로 막힌다.
  - 없어진 것: problem 표·route·worker route, collector worker, snapshot, feedback, `domain_problems`와 `problem.sync_domain`, 설정 `problems.detail_collection`, 앱 상세 Issues 탭, [Report a problem]과 shell feedback IPC, 문제 결정 handle, CLI problem 명령과 `coding.source_diff`, skill `lophn-repair`, `rewind_unproven` problem, call refs와 ticket 근거의 `problem` 갈래, blob 보존 종류 셋(`snapshot_attachment`, `trace_body`, `operational_log`), id 접두사 `prb`·`snp`.
  - check: `tests/e2e`, `tests/eval`과 그 둘만 쓰는 `tests/support`를 type check와 test에서 뺐다(`tools/check.ts`의 `NOT_CHECKED`). fmt와 lint는 그대로 본다.
  - 옛 schema step을 그 자리에서 고치거나 지웠다. 옛 개발 data root는 `history_mismatch`로 뜨지 않으니 지우고 새로 만든다.

왜: problem은 상태 machine이고, 닫기 gate와 다시 열기, 묶음, reaction을 program이 지켰다. 규칙마다 agent가 외울 계약이 됐고 규칙끼리 부딪혔다. lophn은 runtime 경계의 primitive(앱 log, invocation, 상태)만 두고, 진단과 언제 고칠지는 App Engineer가 맡는다(`project-docs/products/roadmap/problem-ticket.md`).

결정:
- program이 앱 오류를 보고 agent를 부르지 않는다. 앱 문제로 App Engineer를 자동으로 여는 흐름을 지운다. (사람, 2026-10-20)
- eval과 e2e는 이 개편 동안 고치지 않고 check에서 뺀다. 다 바뀐 뒤 e2e를 고치고 eval을 돌린다. (사람, 2026-10-21)
- SDK `reportProblem`은 남기고 앱 log에 error 한 줄을 쓴다. 앱과 test 재료가 이미 부르고, 이름 붙은 오류는 log에서도 쓸모 있는 신호다. (agent)
- `ReleaseActivationFailed` reaction과 reaction 설정은 `ae-builds`까지 남긴다. activation이 아직 `TicketVerified`로 돌고 실패를 App Engineer가 받을 다른 길이 없다. (agent)
- 사람의 feedback을 지우고 annotation으로 둔다. 둘 다 사람이 앱 화면에서 App Engineer에게 알리는 길이다. (agent)
- console 출력을 invocation 표시로 감싸지 않는다. invocation은 SDK가 쓰는 줄에만 싣고, 나머지는 시각으로 찾는다. (agent)
- preview와 test mode의 오류는 이번에 log에 쓰지 않는다. App Engineer의 preview tool은 `ae-builds`로 옮겼다. (agent)

닫은 이슈: activation "examples가 아닌 ticket의 release에서 '증명 못 함' write tool을 알리지 않는다"(남김. 알릴 길이 없어졌다).

## approval을 할당, 기다리는 turn 하나, turn mode, shell 규칙으로 줄인다

```yaml

```

- 전:
  - 판정은 intent 7종과 grant(앱, agent, reaction)를 보는 Gate였다. 효과별 기본 묻기(external은 물음)가 있었고, 할당한 앱 tool도 실행 때 다시 묻거나 "이 session 동안" 허락을 받았다.
  - 묻는 길이 둘이었다. turn 안 request(메모리, 선택지 once·session·always·allow·reject, fingerprint와 한 번 쓰기)와 보류 request(`approval_requests` 표, applier, `ApprovalRequested`·`ApprovalDecided`)다. 보류 길은 activation 허락과 reaction의 물음이 썼다.
  - agent call은 call tool의 Gate와 Router의 `callGate`가 두 번 판정했다(`gate_allowed`). `LOPHN.md` 쓰기와 `operator.create`·`operator.update`는 "설정 고치기"로 물었다. 앱 호출 경로가 따로 사람에게 물었다(`askGate`).
  - `shell.run`은 효과 `read`이고 묻지도 막지도 않았다. 사람이 없는 실행이라는 구별이 없어 물음이 기한 없이 기다렸다.
- 후:
  - 할당: agent마다 `{app, removed_tools}` 줄의 목록(`agent_assignments`, `GetAgentAssignment`·`SetAgentAssignment`, revision compare). 사람만 쓰고 agent 자격은 읽지도 못한다. 할당한 앱의 tool은 효과와 상관없이 묻지 않는다. MCP server는 설정한 층(전역, project, Operator 정의)이 할당이고 끄기는 `mcp_off`다. agent 정의 화면의 Grants 탭은 앱 줄과 뺀 tool만 고른다.
  - 판정: 순수 함수 `judge(GateCall, 할당, shell 규칙 층, mode)`가 `run | ask | deny`를 낸다. 할당 안 된 앱 tool과 뺀 tool은 어느 mode에서도 막는다. 앱 호출 경로는 묻지 않고 막기만 한다(agent는 할당, 앱은 active grant `app.call`).
  - 묻는 길은 turn 안 request 하나다. 선택지는 `once | always | reject`이고 물은 입력을 그대로 실행한다(fingerprint 없음). memory route `turn_requests/decide`(`DecideTurnRequest`), agent event `TurnRequestOpened`·`TurnRequestClosed`, snapshot `turn_requests`. coding harness의 물음도 같은 event로 비춘다(`subject.kind: "harness"`). 대기 목록에는 turn request와 activation 동의만 있다.
  - shell 규칙: `{pattern, action}`(`*`는 아무 글자, `\*`는 글자 그대로), 명령 전체와 조각마다 가장 엄한 것, 층은 제품 기본(floor deny와 ask), 전역, project. 전역과 project 규칙은 Settings 값 `approvals.shell_rules`이고 Settings › Shell rules에서 고친다. `always`는 ask였던 조각마다 `<앞 두 낱말> *` allow 줄을 place로 고른 층에 더한다. floor는 `rm -rf /`·`~`·`~/`·`/*`·`~/*`를 flag 순서 넷과 `sudo` 앞붙임까지, `mkfs*`, `dd * of=/dev/*`, fork bomb을 막고 어느 층·skip·`always`도 덮지 못한다. `shell.run`은 효과 `external`이고 shell 규칙으로 Gate를 거친다.
  - turn mode: attended, unattended, skip을 turn 시작 때 정해 `turns.mode`에 남긴다(바뀌지 않는다). 순서는 unattended 입력, session skip, attended다. `ask`는 attended에서만 묻고, `deny`는 어느 mode에서나 막는다. unattended turn의 `ask` tool은 `unattended`를 바로 돌려준다.
  - unattended는 call을 따라 간다: `SendCall`·`ReplyCall`의 `unattended?: true`가 봉투, `RoutedInput`, `agent_calls.unattended`에 실리고, 늦은 실패와 취소 알림은 call 행의 표시를 따른다. 받은 메시지 기록에는 싣지 않는다. 이 판에는 unattended를 여는 입구가 아직 없다(`headless-run`).
  - skip: session 표시 `sessions.skip`(사람만 `ChangeSessionSkip`, 대화 composer 아래 줄의 Skip permissions)과 Operator 정의의 `skip` 기본값(사람만 쓴다. Operator tool 입력에 없다). fork는 skip을 가져가지 않는다. skip은 call을 따라 가지 않는다.
  - activation 동의는 activation module의 상태다: 표 `activation_consents`(재시작을 넘고 허락도 남긴다), `activation.ask_consent`(machine), `activation.consent`(사람, `allow | reject`, compare `requested_at`), `activations.consents`, 남지 않는 event `ActivationConsentRequested`·`ActivationConsentClosed`, 줄 phase `waiting_consent`. 더 새 release가 시작되면 그 앱의 동의 줄을 닫는다.
  - reaction 설정은 `off | on`(기본 켬)이고 새 일 handler는 approvals를 거치지 않는다. reaction이 연 turn은 attended다.
  - agent call은 묻지도 막지도 않는다. `LOPHN.md` 쓰기와 Operator 고치기도 묻지 않는다.
  - 없어진 것: 표 `approval_requests`·`agent_grants`, applier와 resume, `ApprovalRequested`·`ApprovalDecided`·`PermissionRequested`·`PermissionResolved`, snapshot `permission_requests`, route `approvals/pending`·`approvals/decide`·`approvals/decide_turn`·`agent_grants/get|set`과 handler 없던 옛 route 아홉·core machine route 다섯, protocol `intent.ts`·`requests.ts`·agent grant, intent `settings_edit`·`app_resource`, "이 session 동안" 허락, fingerprint와 consume, `gate_allowed`·`CallGate`, call 실패 이유 `not_allowed`, 앱 호출의 `askGate`와 denial code `rejected`·`cancelled`, tool 결정 기록의 `session_grant`·`approval`·옛 `effect`·`comparison_basis`·`contract_revision`, rewind 사실 `approval_decision`, reaction의 `ask`.
  - schema step을 그 자리에서 고쳤다. 옛 개발 data root는 `history_mismatch`로 뜨지 않으니 지우고 새로 만든다.

왜: approval은 개념이 많고(intent, grant 저장소, 묻는 길, 선택지, fingerprint) 같은 판정을 여러 번 했다. 할당했는데 또 묻고, 사람 없는 실행은 멈췄고, 주 위험인 shell은 묻지 않았다. 조사한 다섯 harness는 모두 묻는 길이 기다리는 turn 하나이고 shell 명령이 주 gate다(`project-docs/products/roadmap/approval.md`, `project-docs/architecture/approval.md`).

결정:
- 시킨 것이 승낙이고 할당이 허락이다. 할당한 tool은 실행 때 다시 묻지 않는다. (사람, 2026-10-20)

- shell floor를 `rm`의 flag 순서와 `sudo` 앞붙임까지 넓힌다. ask에 `rm -f -r*`를 더한다. (사람, 2026-10-21)
- unattended에서 activation을 저절로 동의하는 장치를 두지 않는다. (사람, 2026-10-20)
- 묻는 길은 기다리는 turn 하나, 선택지는 `once | always | reject`, fingerprint 없음, agent call은 묻지도 막지도 않음, `LOPHN.md` 쓰기는 묻지 않음, reaction은 `off | on`. (agent)
- turn mode의 순서는 unattended 입력 → session skip → attended다. unattended는 답과 늦은 실패, 취소 알림에도 실린다. fork는 skip을 가져가지 않는다. (agent)
- MCP server는 설정한 층이 곧 할당이라 할당 줄은 앱만 둔다. (agent)
- `always`는 ask였던 조각마다 `<앞 두 낱말> *`를 더하고 층은 place로 고른다. `shell.run`의 효과는 `external`이다. (agent)
- activation 동의 대기와 허락은 ledger 표에 둔다. (agent)
- CLI `--dangerously-skip-permissions`는 두지 않는다. CLI가 여는 run은 처음부터 unattended다. (agent)

닫은 이슈: approval "shell floor deny가 `rm -rf /`의 그 글자 모양만 막는다"(고침).
