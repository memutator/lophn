# architecture

여러 module에 걸친 메커니즘의 설계다. 무엇을 풀려고 어떤 모양을 골랐고 무엇을 지키는지를 적는다. 어느 file과 함수가 그 일을 하는지는 적지 않는다. 그것은 code와 flow catalog(`project-docs/flows/`, flow의 `code`·`steps`)가 맡는다.

문서마다 이 꼴이다.

```markdown
# <topic>

<이 메커니즘이 무엇인지 한 문단. 사람이나 agent가 겪는 말로.>

## 문제
<무엇을 풀려는가. 이 메커니즘이 없으면 누가 무엇을 잃나.>

## 목표와 비목표
- 목표: ...
- 비목표: ... (일부러 하지 않는 것과 그 이유)

## 모델
<개념, 상태, 관계. 그림 하나를 써도 된다. 이름은 계약에 나오는 이름이다.>

## 지키는 것
1. <깨지면 안 되는 성질 하나. 검증할 수 있게.>

## 경계와 계약
<누가 무엇을 주고받나. boundary-catalog ID, route·event·tool·설정 key 같은 공개 계약 이름, 저장 모양의 의미.>

## 결정
- <정한 것>. 이유: ... 버린 안: ... (사람 | agent, 정한 날을 알면)

## 열린 것
- <아직 정하지 않았거나 알려진 한계. 이슈가 있으면 이슈 id.>
```

- 쓰지 않는 것: `packages/…` path, `.ts` file 이름, 함수·class·변수 이름, 줄 번호, test file 이름, 실행 명령. 계약 이름(route, event, tool, 설정 key, 저장 file의 자리와 모양)은 쓴다.
- 지금 code의 설계만 적는다. 앞으로의 모양은 roadmap이나 계획에 둔다.
- 동작을 바꿔 설계와 달라지면 같은 변경에서 고친다.
- `node tools/records.ts check`가 path·file 이름이 섞였는지와 필수 절(문제, 지키는 것, 결정)을 본다.
