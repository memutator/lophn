# 0.2.0

## project-docs를 catalog, architecture, skill, check로 줄임

```yaml
modules: [tools]
checked: []
```

- 전: requirements, specs, dev 문서, task 기록이 약 4만 줄. 요구 ID 천 몇백 개를 사람이 검수하기 어렵고 코드와 30곳 넘게 어긋남.
- 후: `PRODUCT.md`, `boundary-catalog.yaml`, `module-catalog.yaml`, `architecture/<topic>.md`, `plan/`(skeleton, `weight.md`, `gaps.md`), `.claude/skills/` 넷. 약 2.2천 줄. architecture 문서는 지금 코드를 보고 다시 씀. `tools/check-source.ts`가 주석과 test 이름의 요구 ID, task 번호, 옛 말을 잡음.

왜: MVP 때 쌓인 명세가 코드보다 늦고 원자적이라 유지보수가 안 됨. 코드가 먼저이고 문서는 코드로 알 수 없는 것만 둔다.

결정:
- requirements, dev, tmp, 끝난 plan 내용을 지운다. 옛 내용은 tag `docs-before-trim`에 남긴다.
- requirements를 추상화한 `features.yaml`은 두지 않는다. 버린 이유: 또 하나의 동기화 비용.
- 무게 추적은 `plan/weight.md` 하나만. futures, metric, yaml 체계는 너무 무거워 버린다.
- 수평 관심사는 skill 넷(wording, write-test, orchestrate, ui-design)으로. module마다 AGENTS.md를 두지 않고 필요한 곳만.
- architecture 문서는 pull로 둔다. 사람이 필요할 때 넣어 준다.
- 전역 AGENTS.md에는 실천적이고 검증할 수 있는 지침만 둔다. 철학은 넣지 않는다. "스타트업처럼", "가장 단순한 구현", "방어 코드를 미리 만들지 않는다"는 효과가 있어 남긴다.

## core layer 규칙을 check로 강제

```yaml
modules: [tools]
checked: []
```

- 전: core module 사이의 import 방향을 보는 check가 없음. 바닥이 domain을, module이 `core/main`을 import하는 곳이 있음.
- 후: `tools/check-deps.ts`가 막음: module → `core/main`, 바닥 → lophn-agent·domain, lophn-agent → domain, domain끼리는 problems → apps만. 어긴 import는 type이나 함수를 쓰는 쪽으로 옮겨 고침. 동작은 같음.

왜: Deno는 실행 때 tree shaking을 하지 않아 import가 process와 Worker에 무엇이 실리는지를 정한다. 거꾸로 가는 import는 권한을 좁힌 process를 시작부터 죽이거나 순환 import를 만든다. 자세한 것은 `architecture/layers.md`.

결정:
- "domain끼리 import 금지"를 방향 규칙으로 완화한다. problems → apps는 자연스러운 한 방향 의존이다.
- 못 끊은 두 곳(projects → apps, lophn-agent → projects)은 check-deps에 이름으로 예외를 둔다. 버린 길: 다른 module의 표를 SQL로 직접 읽기. 의존이 check가 못 보는 곳으로 숨는다.
- "다른 module은 mod.ts로만 import"는 두지 않는다. barrel이 module 전체를 실어 오고, 막아 주는 깨짐은 type check가 잡는다.
- lophn-agent를 harness와 lophn domain으로 나누는 리팩터링을 다음 계획으로 한다. 예외 둘은 그때 다시 본다.

후속: 없음

## changelog와 버전, context-component-registry를 둠

```yaml
modules: [tools]
checked: []
```

- 전: 바뀐 것과 결정을 남기는 곳이 없음. 어떤 context 조각이 어떤 코드에 기대는지 적힌 곳이 없음.
- 후: `products/change-log/<version>.md`, `context-component-registry.yaml`. `boundary-catalog.yaml` 머리말을 다시 쓰고, `tools/check-modules.ts`에서 쓰지 않는 kind(guidance, bundle)와 참조 칸을 지움.

왜: plan → 구현 → changelog → context 유지보수의 흐름을 만들기 위해. catalog ID가 그 메타데이터 축이다.

결정:
- 버전은 lophn 하나에 `0.MINOR.PATCH`. 배포 단위로 나누는 것은 오픈 소스로 배포할 때 정한다.
- changelog는 tag 하나에 md 파일 하나, 폴더 하나에 평평하게. 열린 판에 덧붙이기만 하고 닫힌 판은 고치지 않는다. 버린 길: 변경마다 파일 하나, MINOR마다 폴더.
- 항목은 boundary ID가 아니라 module path를 적는다. 바뀐 module은 diff로 기계적으로 나오고 boundary는 module-catalog로 따라간다.
- plan을 가리키지 않는다. plan은 닫히면 사라진다.
- 고친 context 조각은 diff로 알 수 있어 적지 않고, 봤지만 고칠 것이 없던 조각만 `checked`에 적는다.

## 열린 이슈를 issues/에 이슈 하나에 파일 하나로 둠

```yaml
modules: [packages/core/config]
checked: []
```

- 전: `plan/weight.md`(무겁게 짠 것)와 `plan/gaps.md`(알려진 미완)가 긴 목록 둘. worker의 실수를 남기는 곳은 없음.
- 후: `project-docs/issues/<kind>-<slug>.md`. kind는 bug, defect, mistake. weight와 gaps 항목을 bug 23개, defect 64개로 옮김. 이 대화에서 나온 worker 실수 둘을 mistake로 씀. settings 파일을 덮는 규칙은 이슈 대신 `config/store.ts` 주석으로 옮김.

왜: 개발 중 생긴 문제, 버그, 코드 결함을 한 곳에서 찾고, 열린 것만 보이게 하려고.

결정:
- 이름은 `problems`가 아니라 `issues`. core의 `problems` domain(앱 문제)과 섞이지 않게.
- weight와 gaps를 합쳐 kind로 나눈다. 무엇을 어디 적을지 고르는 비용을 없앤다.
- mistake는 코드가 아니라 context나 check를 고친다. 막기는 문장보다 check가 먼저다.
- 고치면 파일을 지우고 changelog에 남긴다. 남기기로 하면 이유를 코드 주석으로 옮기고 지운다. 찾은 날은 git log로 본다.

## issues를 주제별 파일과 archived로 바꿈

```yaml
modules: []
checked: []
```

- 전: 이슈 하나에 파일 하나(89개). weight·gaps 글을 그대로 옮겨 짧고, 하나씩 열어야 해서 검수가 어려움.
- 후: `issues/<topic>.md`에 이슈 하나가 `##` 절 하나. 주제 이름은 architecture 문서와 같고 그 밖은 contexts, shell, platform, code-health, mistakes. 닫은 이슈는 `issues/archived/<topic>.md`에 closed(fixed | kept)와 guard를 붙여 덧붙임. 이슈마다 코드와 대조해 지금 / 영향 / 고치려면 / 정할 것을 다시 씀. 열림 84, 이미 고쳐져 archived로 간 것 5.
- `architecture/agent-call.md`: 앱 줄은 메모리가 아니라 `coding_lines` 표이고 켤 때 비운다고 바로잡음.

왜: 주제 단위로 읽고 검수하고, architecture 문서와 같은 이름이라 한 쌍으로 넣어 주려고. 앞 항목의 "이슈 하나에 파일 하나"를 바로잡는다.

결정:
- 남기기로 한 이슈는 코드 주석으로 옮기고 지우지 않고 archived에 kept로 둔다.
- 회귀는 문서로 잡지 못한다. archived에서 되돌려 "다시 생김"을 적고, bug는 두 번째 고칠 때 test, mistake는 check로 막는다. guard가 없음인 닫힌 이슈가 회귀 후보다.
- annotation은 기능이지만 여러 module을 건너는 흐름이라 architecture 문서로 둔다. architecture의 기준은 "코드 한 곳만 봐서는 모르는 흐름"이다. (agent)

## 이슈의 큰 결정을 인터뷰로 정함

```yaml
modules: []
checked: []
```

- 전: 열린 이슈 84개 중 56개에 "정할 것"이 있음.
- 후: 원칙과 제품 결정으로 정리. 열림 76, archived 12. 정할 것이 남은 것 11. 이슈마다 "정한 것"을 적고, 남기기로 한 경계 장치 7개는 archived에 kept로 닫음. AGENTS.md "속도"에 위협 원칙 한 줄을 더함.

왜: 이슈 하나씩이 아니라 원칙을 먼저 정해 나머지가 따라오게 하려고.

결정:
- 사용자 앱과 사람이 쓴 글은 공격자로 보지 않는다. 막는 것은 AI가 만든 코드와 agent의 실수, 인터넷에서 온 것이다. 그래서 CLI data fence, domain event의 "data, not instructions" 문구, 앱 화면 오류 보고 서명을 지운다. 실수와 인터넷을 막는 장치(file tool realpath, rewind pre-image, migration 검사, 허락 뒤 다시 확인, 끊긴 activation 이어받기, web.fetch 내부 주소 검사)는 남긴다.
- 반쯤 만들고 안 쓰는 길은 지운다(unarchive route, md 아닌 목차와 저장 목차, 제보 창 기존 문제 고르기, deferred tool, App Engineer active context 읽기, ledger `domainOnly`, direct-socket 흔적).
- 경계도 아니고 동작도 맞는 무거운 내부 구현은 다이어트 계획 하나로 모아 정한다.
- activation이 겹치거나 `unavailable`이면 거절하고 사람이 다시 누른다. 줄과 30초 재시도를 없앤다.
- annotation은 source 위치(jsx 바꿔치기, source map)를 지운다. 화면 요소가 겹쳐 있어 줄 번호가 사람의 의도를 가리키지 않는다. 대신 찍은 곳의 component 겹(`List > Card > Button`)을 보낸다. ChatGPT 데스크톱 앱의 browser comment도 source 위치를 쓰지 않는다. 계산된 style과 text 선택은 넣지 않는다.
- App Engineer는 screenshot을 공통 이미지 읽기 tool로 본다.
- harness는 7종을 유지한다. 설치는 열 때마다 앱 폴더에 하지 않고 orca처럼 사용자 전역 설정에 한 번 하고 lophn 환경 변수로 켠다. 처음 한 번 사람에게 묻는다. 설치 hash와 설치 명령의 권한 계산을 지운다. "hook은 앱 source 폴더 안에만" 원칙을 버린다.
- coding agent 완료 보고 뒤 터미널을 따로 끄지 않는다.
- 앱 place의 Operator에게 앱 source 폴더 읽기를 준다.
- 400줄 넘는 파일을 check로 막지 않는다.
