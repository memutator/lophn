# 0.5.0

## 앱 app-api를 MCP tool 모양으로 바꾸고 coding agent에 MCP를 연다

```yaml
modules: [packages/protocol, packages/core/apps, packages/core/server, packages/core/lophn-agent, packages/core/problems, packages/core/main, packages/sdk, packages/coding-agent, packages/shell/main, packages/shell/renderer, packages/shell/preload, packages/shell/ipc, packages/design]
checked: [architecture-annotation, architecture-activation, architecture-approval, architecture-testing]
```

- 전:
  - 앱은 blueprint `app_api[]`(`key`, `label`, `input`, `effect`, `project_scope`)로 선언하고, 호출 route는 `app.call_api`(입력 `api`, `project`)였다. project 범위 app-api는 부른 쪽이 project를 정하고 앱은 `@lophn/cap-project`로 읽었다. 앱 view에는 project picker가 있었다.
  - preview 호출은 활성 release의 선언으로 판정해 release에 아직 없는 tool은 `not_declared`였고, 활성 release가 있으면 `mode: "preview"` invocation을 남겼다.
  - coding agent가 lophn에 닿는 길은 CLI 하나였다.
- 후:
  - 선언은 blueprint `tools[]` = `{name, title, description, inputSchema | null, outputSchema?, effect, public}`이다. 이름은 1~64자 `[A-Za-z0-9_.-]`, schema root는 `object`다. MCP annotation은 effect에서 만든다(`toMcpTool`). `public`은 칸만 있고 읽는 쪽은 계획 `domain-place`다.
  - 호출 route는 `app.call_tool`(입력 `{target, tool, input?, caller}`)이고 invocation operation은 `{kind: "tool", tool}`이다. `app.app_api`의 출력과 `app.app_api_index`의 항목은 `tools`다. index는 입력에 `app`이 있을 때만 `inputSchema`·`outputSchema`를 싣는다.
  - project 범위가 없어졌다: 선언의 `project_scope`, 호출의 `project`, 거절 code `project_required`·`project_mismatch`·`project_not_found`, route `app.projects`, broker `projects/list`, `@lophn/cap-project`, invocation의 `project` 칸과 필터, 앱 view의 project picker와 project 묶음.
  - SDK는 `tool(name, handle)`, `registeredTools`, `ToolRejection`, `connectTools`(client `callTool`), `@lophn/app-ui`의 `useTool`, `ToolButton`이다. 화면 bridge는 `window.lophnApp.callTool(tool, input)`, IPC `app:call-tool`이다.
  - agent tool은 이름(`app__<앱>__<tool>`)과 결과 mapping이 그대로이고 입력의 project 칸이 없다. ticket `examples` step은 `{tool, input?, expect}`다.
  - preview 호출은 그 preview bundle의 선언으로 판정하고 invocation을 남기지 않는다. 호출 길에 `previewOnly` 자격이 생겼다.
  - core가 coding agent용 MCP endpoint(`POST /mcp`, `2025-06-18`, POST만, session 없음)를 연다. coding token의 operation `coding.mcp`로 열고 그 앱의 tool만 보이며, MCP tools/call은 그 앱의 지금 도는 preview로만 간다(없으면 `unavailable`). Claude Code(`--mcp-config`), Codex(`-c mcp_servers.lophn.*`), OpenCode(`OPENCODE_CONFIG_CONTENT`)는 session 실행 계획에 이 endpoint를 싣는다. token은 env `LOPHN_CODING_TOKEN`에만 있다.
  - 화면 셋(앱 공간 첫 화면, 앱 화면 목록, agent grant의 앱 목록)이 지워진 route `apps/blueprint`를 읽어 비어 있던 것을 `apps/app_api`로 고쳤다.

왜: 앱이 내놓는 기능을 MCP tool 모양 하나로 맞춰 화면, SDK, agent, ticket, coding agent가 같은 선언을 쓰게 한다(roadmap `domain.md` "core가 아는 한 가지 모양"). 앱 code의 project별 data 나누기는 core가 지키지 못해 project 범위를 지웠다. coding agent가 자기 코드를 harness의 tool 호출로 확인하되 사용자 data에는 닿지 않게 preview로만 보낸다.

결정:
- 이름 바꾸기(app → domain tool, `app__` 접두, `app_api` grant 칸·approval kind·SDK package 이름)는 계획 `domain-rename`이 한다. 이 판은 그 이름들을 둔다.
- preview 호출은 기록을 남기지 않는다. ledger의 `release`를 비울 수 없어 release 없는 bundle의 호출은 기록할 자리가 없고, preview는 일회용 DB라 rewind 대상이 아니다. (agent)
- coding agent의 MCP 호출은 새 caller 종류 없이 `person` caller와 `previewOnly` 자격으로 들어간다. 새 종류는 ledger의 caller CHECK, caller 판정, rewind를 바꿔야 하는데 preview 호출은 기록이 없다. (agent)
- MCP tools/list는 preview가 돌면 그 bundle의, 아니면 활성 release의 선언이다. `listChanged`는 SSE가 필요해 내지 않는다. (agent)
- `app.app_api_index`는 앱 하나를 볼 때 호출 모양을 싣는다. agent tool `app.app_api`가 index만 읽어서다. (agent)
- Gemini CLI, pi, Hermes, OpenClaw는 MCP를 잇지 않는다. Gemini는 session마다 MCP를 넣을 길이 없고 pi는 MCP가 없다. (agent)

후속:
- 저장 모양이 바뀌었다(invocation 표의 `project` 칸과 색인). 개발 data(`.dev-data/`)는 지우고 새로 만든다. 이미 만든 앱은 옛 선언·SDK 이름을 써서 새로 만든다.
- e2e(`tests/e2e`)는 type check만 맞췄고 돌리지 않았다. `domain-rename` 뒤 다시 쓴다.
- eval materials는 `domain-rename` 뒤 새 판으로 다시 만든다(`project-docs/issues/eval.md`).

## coding agent가 preview를 띄우고 MCP로 인자 없는 tool을 부를 수 있다

```yaml
modules: [packages/core/apps, packages/coding-agent]
checked: [architecture-app-call, architecture-coding-agent]
```

- 전:
  - CLI `lophn app preview start`가 늘 `invalid_input`이었다. route 입력의 칸 `input`을 CLI가 자기 공통 key로 보고 지웠다.
  - 실제 bundle의 preview는 supervisor가 늘 거절했다. preview flags 검사가 쓰기 path를 일회용 폴더와 "같다"로 보았는데 앱 flags는 그 안의 DB file과 socket을 쓴다. 거절 이유는 core 오류에서 "app supervisor rejected the request"로 지워졌다.
  - coding agent MCP는 `inputSchema: null`인 tool을 늘 `invalid_input`으로 불렀다.
- 후:
  - CLI는 자기 flag가 만든 칸(`json`, `idempotency_key`)만 빼고 route 입력은 그대로 보낸다.
  - preview flags는 일회용 폴더 안의 쓰기만 받는다(`..`로 나가는 path는 거절). 읽기와 net 검사는 그대로다. supervisor의 거절 message가 core 오류에 실린다.
  - MCP는 인자 없는 tool을 `input` 없이 부르고, 그런 tool에 인자를 주면 앱에 보내지 않고 `isError`로 돌려준다.

왜: 계획 `domain-tools`의 손 확인에서 coding agent가 preview를 띄워 MCP로 앱 tool을 부르는 길이 이 셋에서 막혔다. 앞의 둘은 그 전부터 있었다(skill의 preview 확인 단계도 돌지 않았다).

결정: 없음.

후속: 없음.

## project의 context를 kind 파일과 내장 tool로 바꿈

```yaml
modules: [packages/protocol, packages/core/projects, packages/core/problems, packages/core/events, packages/core/agent-roles, packages/core/lophn-agent, packages/core/main, packages/shell/renderer, packages/shell/main, packages/shell/ipc, packages/design, tools, tests]
checked: [architecture-event, architecture-approval, architecture-workspace-layout]
```

- 전: project의 문서 모양은 context(계약 bundle, draft·test·submit 판, 선언한 search, glossary, saved view)가 정했다. PM은 `context.*` tool로 판을 내고, Operator는 정의의 `contexts` 칸으로 붙은 context만 받았다. 위반은 `ContextViolationFound`와 context·위반 chip으로 PM에게 갔다. shell에는 Contexts·Context 탭, 선언 search, 문서 info의 Contexts 탭이 있었다.
- 후:
  - project마다 kind 파일 `<data>/projects/<prj>/kinds.yaml` 하나가 문서 모양을 정한다. 판이 없다. 파일이 바뀌면 검사해 맞으면 바로 쓰고, 틀리면 앞의 맞던 kind를 계속 쓰고 problem을 연다.
  - kinds worker(`documents/kinds`, `derived/kinds.sqlite`)가 문서를 읽어 item을 뽑고 칸을 검사하고 index에 둔다. core가 project 폴더와 kind 파일을 감시한다.
  - agent tool `kind.list`(조건, 정렬, 집계, `skipped`), `kind.check`, 모든 role의 `file.outline`이 생겼다. project place에서만 그 project를 읽는다.
  - 문서 위반은 project problem(`project_problems`)이다. 새로 열리거나 다시 열린 위반이 있으면 `KindViolationFound`가 PM session을 연다. PM은 `problem.list`에 `project`를 주어 읽는다.
  - prompt에 PM·Operator의 `<lophn-kinds>` 글이 실리고, kind 파일이 바뀌면 `kinds_changed` notice가 붙는다. PM의 place 정보에 `Kinds file:` 줄이 있다.
  - PM의 file 범위에 `kinds.yaml` 하나가 file 항목으로 더해졌다. agent runtime의 쓰기 권한은 `<data>/projects` 전체에서 project마다의 `kinds.yaml`로 좁아졌다. `file.write`는 부모 폴더가 없을 때만 만든다.
  - 내장 skill은 `context-init`·`context-update` 대신 `kinds-yaml` 하나다.
  - context의 표·route·worker·tool·화면·wording·eval 재료(`tax-receipts` → `tax-kinds`)와 Operator 정의의 `contexts`·`app_reads`, project record의 `tracking`, context·위반 chip을 지웠다. toast와 설정의 reaction 줄은 Kind violation이다.
- 계약:
  - 새 route: `kind.get`·`kind.list`·`kind.check`(core memory route), `problem.sync_project`(machine), `problem.list_project`. 새 event `KindViolationFound {project, count}`와 reaction grant 칸 `KindViolationFound`.
  - 지운 것: `context.*`·`glossary.*`·draft·bundle route와 표, `ContextViolationFound`, id 접두 `ctx`·`cbn`·`chk`·`trm`·`ser`·`viw`, tab kind `contexts`·`context`와 선언 search 탭, `attached`의 `context`·`violation` 종류, notice `contexts_changed`, 정의 issue code `missing_reference`·`archived_reference`.
  - 개발 data는 지우고 새로 만든다(옛 표와 옛 Operator 정의의 `contexts:`는 읽히지 않는다).

왜: roadmap `project-docs/products/roadmap/domain.md`의 1단계다. 판과 선언 search가 하던 일을 바뀔 때의 검사, rewind, 부를 때 짜는 조회로 줄였다(`project-docs/architecture/kinds.md`).

결정:
- tool 이름은 `kind.list`·`kind.check`, event는 `KindViolationFound`, 내장 skill은 `kinds-yaml`이다. (agent)
- `kind.list`의 조건은 세 층(묶음, 묶음, leaf)까지다. 깊이를 묶음 셋으로 읽으면 tool 하나의 JSON schema가 18KB였다. 모든 role의 모든 요청에 실리므로 약 6KB로 줄였다. (agent)
- project problem은 앱 problem과 표·route가 따로다. 한 목록으로 합칠지는 `domain-rename` 뒤에 본다. (agent)
- kinds worker는 `sync`에서만 훑는다. 읽기가 훑으면 그 결과가 위반 비교를 거치지 않는다. (agent)
- 위반의 정체성은 JSON 배열 글로 저장한다. NUL로 이은 글은 node:sqlite가 잘라 읽어, 둘째 sync부터 `problem.sync_project`가 늘 `internal`로 실패했다(실제 core probe에서 찾음). (agent)
- 경로에서 뽑는 칸(`from: path`)은 `list`일 수 없다. kind 파일 schema가 거절한다. (agent)
- operators-home 재료의 판은 나중에 land하는 쪽(이 계획 또는 domain-place)이 두 변경을 합쳐 `@3`으로 만든다. (agent, planner)

닫은 이슈: "md가 아닌 문서는 context로 쓸 수 없다"(`project-docs/issues/archived/contexts.md`). kind는 어느 형식의 파일도 item으로 받는다.

후속: 열린 이슈 `project-docs/issues/agent-definition.md`("붙인 것(`attached`) 기구가 file 종류만 남았고 아무도 만들지 않는다").

## 앱을 project 하나에 묶고, 앱 place와 App Engineer를 없애 Project Manager가 맡고, 공개 tool을 project 사이에서 다룸

```yaml
modules: [packages/protocol, packages/core/projects, packages/core/apps, packages/core/problems, packages/core/events, packages/core/approvals, packages/core/agent-roles, packages/core/lophn-agent, packages/core/main, packages/shell/renderer, packages/design, tests]
checked: [architecture-layers, architecture-approval, architecture-workspace-layout, architecture-browser-tab, architecture-appearance]
```

- 전:
  - 앱 record에 project가 없었고 앱 저장 자리는 `<data>/apps/<app>/`였다. place는 project 하나나 앱 하나였고 role은 lophn, Project Manager, App Engineer, Operator 넷이었다. App Engineer가 앱마다 하나 있어 ticket, blueprint, release, problem 상태를 맡았다.
  - project는 사람의 폴더가 하나 이상 있어야 등록되었다.
  - Operator 정의는 `skills_off`로 skill을 끄고, project 층 skill 폴더는 file tool이 닿지 않았다.
  - lophn에는 project들의 앱과 공개 tool을 한눈에 보는 길이 없었고, 다른 project 앱의 비공개 tool도 agent에게 보였다. 공개 tool을 지우거나 바꾸는 release를 막거나 쓰는 쪽에 알리는 길이 없었다. package에는 주인이 없었다.
- 후:
  - 앱은 project 하나에 묶인다(`App.project`, 필수, project 하나에 앱 하나, 보관한 앱도 project를 점유한다). `app.create`가 project를 받는다. project는 사람만 등록하고, 맞는 project가 없으면 lophn이 사람에게 묻는다.
  - project를 사람의 폴더 없이 등록할 수 있다. 그 project의 `LOPHN.md`는 `<data>/projects/<prj>/LOPHN.md`이고 PM의 file 범위 밖이다.
  - 앱 저장 자리는 `<data>/projects/<prj>/app/`(`data/`, `bundles/<hash>/`, `staging/`, `preview/<nonce>/`, 기본 source `source/`)다. 자리 계산은 `packages/protocol/apps/app-storage.ts` 하나다. 사람이 이은 source 폴더는 그대로다.
  - place는 project 하나이고 role은 lophn, Project Manager, Operator 셋이다(coding agent는 밖). 앱 place와 App Engineer(정의, 지침, tool 목록, 화면)는 없다. coding session의 place는 앱의 project다.
  - PM이 App Engineer의 일을 맡는다: ticket, blueprint, release, problem 상태, package publish, source 연결, 앱 Operator. 자격에 `conditions.app`(그 project의 앱)이 실려 "자기 앱" 검사가 모두 그것을 본다. 문제 열림·다시 열림, 재시작 멈춤, activation 실패, kind 위반, 공개 tool 바뀜 reaction, coding 완료·claim 만료·session 끝, coding agent의 메시지, 앱 화면 annotation이 그 앱 project의 PM에게 간다.
  - PM의 file 범위는 project 폴더, artifacts 폴더, kind 파일, 그 앱의 source 폴더, project skill 폴더(`<data>/projects/<prj>/skills`, PM 정의를 만들 때 함께 만든다)다. 앱의 `app/` data와 release 사본은 범위 밖이다. 범위에 상대 경로의 기준 `base`가 실린다(사람의 첫 폴더, 없으면 `<data>/projects/<prj>`). `base`는 허락을 넓히지 않는다. agent runtime의 Deno 권한은 project 폴더, artifacts·skill 폴더, 앱 source, kind 파일(쓰기)의 합이다. 이제 `<data>/projects` 전체를 열지 않고 `placeScope`를 거치지 않는다.
  - 정의의 `skills_off`가 `skills`(받을 skill 이름, 비면 전부, 끌 수 없는 내장 skill은 늘 받는다)로 바뀌었다. 전역과 project 층의 `skills_off`는 그대로다.
  - lophn의 place 정보에 project 지도(이름, 목적, 앱, 공개 tool, 설치한 package, 그 공개 tool을 쓰는 다른 project)가 program의 조립으로 실린다. 사용 관계는 새 읽기 `app.usage`(grant와 invocation 기록)이고 lophn만 읽는다.
  - 다른 project 앱의 비공개 tool은 agent의 tool 목록과 `app.app_api` 결과에 없다. 같은 project의 agent는 모두 본다.
  - package는 처음 publish한 앱의 project가 주인이다(`owner_project`). 다른 project는 새 version을 낼 수 없고, package 읽기가 주인을 싣는다.
  - 새 reaction event `PublicToolsChanged`(project마다 하나, 끌 수 있음)가 PM을 연다. 다른 project가 쓰는 공개 tool을 지운 release는 machine command `activation.block`으로 막히고, 공개 tool이 바뀌거나 지워진 release는 그 앱 project의 PM과 쓰는 project의 PM에게 이 event를 낸다. agent grant 화면은 다른 project 앱의 공개 tool만 보인다.
  - eval: `scenarios/app-engineer/`가 Project Manager 시나리오(`CA1-ask`, `CA12`)가 되었고 `A14-other`는 지웠다. 재료 `operators-home@3`을 쓴다.
- 계약:
  - 새 읽기와 command: `app.usage`, `activation.block`(machine). 바뀐 입력과 칸: `app.create`의 `project`, `App.project`, `Package.owner_project`, 정의의 `skills`, 범위의 `base`. 새 event `PublicToolsChanged`와 reaction grant 칸.
  - 지운 것: role `app_engineer`와 앱 place, 정의의 `skills_off`, `<data>/apps/<app>/`.
  - 개발 data는 지우고 새로 만든다(앱 저장 자리, `apps`·`packages` 표 칸, 옛 Operator 정의의 `skills_off`).

왜: 앱 data의 경계를 core가 지키려면 앱이 어느 project 것인지가 data에 있어야 한다. 앱이 project 하나에 묶이면 앱 place를 따로 둘 이유가 없고, 한 project에 agent가 둘이면 지침과 file 범위와 reaction이 갈린다. 공개 tool은 다른 project가 기대는 약속이라 지도로 보이고, 지우면 막고, 바꾸면 쓰는 쪽을 깨운다(`project-docs/products/roadmap/domain.md`).

결정:
- 사람이 project를 폴더 없이 등록하는 것을 허용했다(2026-10-19).
- 계획은 wave 2 중간에 land하지 않았다. union 정리(`dp-place-protocol`: `Role`·`Place`에서 `app_engineer`와 앱 place 지우기)를 맨 끝으로 옮겼다. 앞 task를 막지 않고, 앞 task가 남긴 `app_engineer` stub도 한 번에 지운다. (agent, planner)
- 앱 저장 자리는 migration 없이 옮겼다. 개발 data는 지우고 새로 만든다. (agent)
- 막기는 오류를 내는 command가 아니라 새 machine command `activation.block`이다. 오류를 내는 command는 event를 되돌리기 때문이다. (agent)
- `skills`가 비면 전부 받으므로 Operator가 skill을 하나도 받지 않게 할 수는 없다. 마지막 하나를 빼면 다시 전부다. (agent)
- 다른 project에서 난 package 문제를 주인 project의 PM에게 넘기는 것은 지침이 한다. program은 하지 않는다. (agent)

닫은 이슈: agent-call "App Engineer의 부를 수 있는 목록에 다른 앱의 App Engineer가 없다"(App Engineer가 없어지고 PM 후보는 project 목록에서 온다).

후속: 개발 data(`.dev-data/`)를 지우고 새로 만든다. eval 재료 `notify-app`, `calendar-app`, `calendar-app-bug`의 `AGENTS.md.tmpl`에 "App Engineer"가 남았다(새 판을 올려야 한다). `Role`·`Place` union 정리(`dp-place-protocol`)가 끝나면 protocol에서 `app_engineer`와 앱 place가 없어진다. 이름 바꾸기(project → domain)는 `domain-rename`이 한다.

## write tool의 되돌리기를 실제로 성공한 호출로 증명함

```yaml
modules: [packages/core/problems]
checked: [architecture-kinds]
```

- 전: release 준비의 app test가 모든 앱에서 `rewind`·`examples` 검사로 떨어졌다. harness가 process wire에서 지운 `context.project`를 실어 앱이 모든 호출을 `invalid_input`으로 거절했다. 고쳐도 `rewind`는 만든 입력의 호출이 실패하면(앞선 상태가 있어야 하는 tool) fail이었다. 검사 결과는 user token이 읽지 못했다(`forbidden`).
- 후:
  - harness가 지금 process wire로 앱을 부른다.
  - app test `rewind`는 호출이 성공한 write만 되돌려 본다. 호출이 실패한 tool은 "증명 못 함"이라 떨어뜨리지 않고 증거 `unproven`과 pass 이유 한 줄에 남는다.
  - ticket `examples`는 예시가 모두 맞으면 예시 write의 changeset을 뒤집어 첫 호출 전 상태로 돌아오는지 본다. 돌아오지 않으면 fail이다. 되돌아온 tool이 증거 `proven`이다.
  - examples run이 끝나면 같은 (app, bundle_hash)로 통과한 app test의 증명 못 함에서 그 examples가 증명한 tool을 뺀 것을 앱 problem `rewind_unproven`으로 알린다. examples가 fail이면 빼지 않고, 판정할 수 없었으면 알리지 않는다. activation은 막지 않는다.
  - user token이 앱의 verification을 읽는다.
- 계약: 새 problem 이름 `rewind_unproven`(같은 앱은 한 problem으로 묶인다). runner 요청 본문에 examples 요청일 때만 `app_test_unproven`과 `unproven_credential`(live app credential)이 실린다. route·event·schema는 그대로다.

왜: 만든 입력으로는 앞선 상태가 있어야 하는 write tool의 되돌리기를 증명할 수 없다. 사람이 쓴 ticket 예시의 실제로 성공한 write가 증명 재료다(`project-docs/architecture/coding-agent.md`).

결정:
- tool 선언에 test용 fixture 입력 칸을 두지 않는다. 운영과 무관한 data가 선언에 들어가고 앞 호출이 만든 id를 고정 값으로 맞출 수 없다. (사람)
- 증명 못 함은 examples ticket일 때만 problem으로 알린다. examples가 아닌 ticket은 app test 증거와 pass 이유 한 줄로만 남는다. (planner)
- examples run과 app test run의 판정을 합치지 않는다. examples의 되돌리기는 examples 검사 안에서 판정한다. (planner)
- 판정할 수 없었던(inconclusive) examples run은 알리지 않는다. (agent)
- 보고는 core main이 아니라 runner child가 주입받은 fetch로 한다. core는 app test pass 이유에서 증명 못 함을 읽어 live app credential과 함께 넘긴다. 검사별 증거는 observations blob에 hash만 있어 core가 읽지 못한다. (agent)

닫은 이슈: "write app-api의 rewind 검사가 fail로 나온다"(`project-docs/issues/archived/activation.md`).

후속: 열린 이슈 `project-docs/issues/activation.md`("examples가 아닌 ticket의 release에서 \"증명 못 함\" write tool을 알리지 않는다", "app test 검사별 detail을 아무도 읽지 못한다"), `project-docs/issues/mistakes.md`("core main에서 전역 fetch로 자기 HTTP를 불러 problem을 보고했다").

## agent가 쓴 HTML을 artifact 탭으로 본다

```yaml
modules: [packages/protocol, packages/core/agent-roles, packages/core/apps, packages/core/lophn-agent, packages/core/main, packages/shell/main, packages/shell/ipc, packages/shell/preload, packages/shell/renderer, packages/design, tools]
checked: [architecture-browser-tab, architecture-workspace-layout]
```

- 전: agent 결과가 사람에게 가는 길은 대화 글, 파일, 앱 card뿐이었다. `.html`은 document editor가 text로 열었다. annotation은 앱 화면에만 달 수 있었고 그 앱의 App Engineer만 받았다.
- 후:
  - project마다 lophn data 자리 `<data>/projects/<prj>/artifacts/<name>/`에 `index.html`이 있으면 artifact다. 그 project의 PM과 project place의 Operator가 file tool로 쓰고 rewind된다. runtime이 turn 시작 때 폴더를 만들고, runtime 쓰기 권한에 project마다의 artifacts 폴더를 더했다.
  - PM·Operator의 place 정보에 `Artifacts` 섹션(`Folder:` 절대 path와 이름·제목·설명 목록, 50개까지)이 실린다. 내장 guide `artifact`가 자리, 폴더 모양, `data/`와 `_entries.json`, 제목과 설명, network 없음, appearance token을 적고, 두 role 지침이 이 guide를 가리킨다.
  - 새 탭 kind `artifact`가 봉한 view(`persist:lophn-artifact`, scheme `lophn-artifact://`)로 그린다. root 안의 일반 file만(4 MiB까지) 주고, CSP는 `connect-src 'self'`, 밖은 죽은 proxy가 막는다(loopback 포함). 봉할 때 잠깐 띄운 loopback server에 닿으면 봉하지 못한 것으로 본다. 파일이 바뀌면 다시 load한다. 탭에는 [Edit source]와 [Annotate]가 있고, 폴더가 없으면 안내와 [Try again]이다. page의 http·https link는 입력 직후에만 browser 탭으로 연다.
  - 사람의 폴더에 있는 `.html`을 열면 artifact 탭이다(root는 그 file이 든 폴더). source는 [Edit source]로 text 편집기에서 연다.
  - project sidebar에 Artifacts 탭이 생겼다. 대화 글의 artifact path(상대·절대)는 link이고 누르면 artifact 탭이 열린다.
  - artifact 탭에서 annotation을 달아 보내면 그 폴더에 마지막으로 쓴 열린 PM·Operator session이 받고, 없으면 그 project의 PM이 받는다. PM·Operator는 `image.read "annotation:<id>"`로 자기 project의 artifact annotation screenshot을 읽는다.
- 계약:
  - `annotations.send` 입력이 `{app, …}`에서 `{target, session, annotations}`로 바뀌었다. `target`은 `{kind: "app", app}` 또는 `{kind: "artifact", project, name | null}`이고, artifact이면 annotation의 `release`와 `view.screen`이 null이다. 읽기 값의 `app` 칸도 `target`이다. `annotation_batches`에 `target_kind`·`project`·`artifact` 칸이 생기고 `annotations.app`이 없어졌다(schema step을 제자리에서 고쳤다).
  - credential 조건 `project`가 생겼다(project place의 PM·Operator). `annotations.get`을 PM·Operator에게도 주고, 앱에도 project에도 묶이지 않은 agent는 forbidden이다.
  - `annotation` tag 속성에 `kind`·`project`·`artifact`가 더해졌다.
  - shell IPC `shell:artifact-open`·`-reload`·`-list`와 push `shell:artifact-state`·`-event`, preload `window.lophnArtifact`, artifact page preload `preload-artifact`(annotate layer만). `AnnotateViewPort`는 `app`·`release`·`screen` 대신 `target`이다.
  - protocol `projects/artifact.ts`(상수, `parseArtifactMeta`, `artifactMentions`, import 없음), `projects/values.ts`의 `artifactNameSchema`.
  - 개발 data는 지우고 새로 만든다(annotation 표 모양).

왜: roadmap `artifact.md`. agent 결과를 채팅 밖 화면으로 받는다(PRODUCT 축 2). browser-tab roadmap의 "로컬 HTML 미리 보기"도 이것으로 했다.

결정:
- artifact 전용 tool은 두지 않는다. 만들기는 `file.write`, 찾기는 관례 자리, 알리기는 말과 link다. (사람, roadmap)
- 화면에서 artifact를 지우는 단추는 이번에 두지 않는다. 지운 폴더는 rewind로 되살릴 수 없어 확인과 test가 필요하다. roadmap `artifact.md`에 남겼다. (사람)
- sidebar 탭은 Explorer, Agent, Artifacts다. Context 탭은 domain-kinds가 지웠다. (사람)
- agent는 artifact를 절대 path로 쓴다. 상대 path의 기준이 사람의 project 폴더라서 상대 `artifacts/…`는 사람의 폴더에 써진다. (agent)
- protocol의 `artifact.ts`에 import를 두지 않는다. shell main이 zod·base를 싣는 protocol file을 import하지 못한다. (agent)
- `tests/e2e/annotation_test.ts`는 돌리지 않고 type check가 통과하게 입력 모양만 맞췄다. (planner)

후속: 개발 data(`.dev-data/`)를 지우고 새로 만든다.
