# 0.8.0

## PM이 쓴 code가 이끄는 flow workflow

```yaml
modules: [packages/protocol, packages/core/workflows, packages/core/runs, packages/core/apps, packages/core/main, packages/core/agent-roles, packages/core/jobs, packages/sdk, packages/coding-agent, packages/design, packages/shell/renderer, tools]
checked: [tool-check, architecture-testing, architecture-eval, architecture-activation, architecture-agent-call, architecture-place-session, architecture-coding-agent, architecture-annotation, architecture-browser-tab, architecture-artifact, architecture-workspace-layout, architecture-ui-kit, architecture-appearance, architecture-kinds, tool-context-review, tool-worktree-prep, tool-e2e, tool-test-live, tool-check-deps, tool-dev, tests-support, tool-package-linux, tool-models-snapshot, skill-ui-design, skill-wording, tool-wording]
```

- 전:
  - `kind: flow` 선언은 읽혔지만 시작하지 못했다(`problem` `not_agent`, sidebar "Flow · can't be started here").
  - 앱 tool을 부르는 쪽은 사람, agent, 앱, program(job) 넷이었다. run의 출처는 job 하나였다.
- 후:
  - 사람(화면, CLI)과 job이 `kind: flow` workflow를 시작한다. code는 workflow 폴더의 `flow.ts`이고 PM이 쓴다. 선언에서 lophn이 읽는 것은 `kind`와 `steps`의 key뿐이다. `flow.ts`가 없으면 `problem` `no_flow_file`로 시작하지 못한다. 동작은 `project-docs/architecture/workflow.md` "flow"다.
    - instance마다 `deno run` process 하나를 sandbox 안에 띄운다. 읽기는 그 workflow 폴더와 `<data>/sdk`뿐이고 쓰기, 네트워크, 다른 program 실행, 환경 변수가 없다. 끝나면 다시 띄우지 않는다.
    - process와 core는 stdin·stdout JSON 줄로 말한다(`packages/protocol/workflows/flow-wire.ts`). 새 SDK `@lophn/flow`(`packages/sdk/flow`)가 `input`, `instance`, `agent(...)`, `tool(...)`, `report(...)`를 내고 실패도 값으로 준다. `console.log`는 stderr로 간다.
    - stderr는 redaction을 거쳐 `<data>/flows/<instance>.log`에 남는다. process가 끝나면 새 줄 `program_exited`(끝 code, stderr 끝 10줄)를 남기고 `running`이면 `ended`로 닫는다. lophn은 성공을 판정하지 않는다.
    - flow의 report는 줄의 `by`가 `program`이고 넘기지 않는다. 멈추기는 process를 죽이고 그 instance가 연 run을 취소한다. 켤 때 `running`인 flow instance는 `lophn_restarted` 줄(step·receiver null)과 함께 `ended`가 된다.
  - 앱 호출의 부르는 쪽에 `flow`(`{kind: "flow", instance}`)가 생겼다. 판정은 그 project PM의 지금 할당(unattended)과 PM이 맡은 domain이다. 앱 process의 caller parser, `@lophn/cap-tool`의 `AppToolCaller`, invocation `caller_kind`도 받는다. `caller_kind` CHECK는 protocol schema에서 만든다.
  - run의 origin이 job과 workflow instance 둘이 됐다. run 기록에 `instance` 칸이 생겼다. `RunService.cancelOfInstance`가 그 instance가 연 run을 취소한다.
  - protocol: `WORKFLOW_LINE_KINDS`에 `program_exited`, `LineBy`에 `program`, `started` 줄 step nullable, `CreateWorkflowInstance.handoff`와 `StartWorkflow.handed` nullable, change `program_exited`·`flow_restarted`, route `CheckWorkflow`.
  - PM tool `workflow.check`: `flow.ts`를 실행하지 않고 설치된 SDK에 대고 type check만 한다. PM의 내장 skill `guide-workflows`에 "Flow workflows" 절이 생겼다. job tool 설명의 `workflow_start`가 flow를 말한다.
  - 화면: workflow 탭이 flow도 시작한다(첫 step을 고르지 않는다). flow report는 "Program", `program_exited` 줄은 끝 code와 stderr 끝 줄을 보인다. sidebar는 `problem`이 있으면 "Has errors"다. 앱 활동과 session rewind 목록은 flow 호출을 "Workflow"로 보인다. gallery에 flow page 넷(`workflow-tab-flow-exited`, `workflow-tab-flow-restarted`, `workflow-tab-flow-missing`, `workflow-start-dialog-flow`)이 생겼다.

왜: 결정적 처리와 검증이 필요한 workflow는 agent에게 step을 넘기는 것만으로 짜기 어렵다. program이 앱 tool과 agent 호출을 섞어 부르고 agent처럼 report를 내게 한다(`project-docs/products/roadmap/workflow.md` 원칙, `headless-schedule.md`).

결정:
- flow의 code는 workflow 폴더에 `workflow.yaml` 옆 file로 둔다. 앱으로 두지 않고 사람의 저장소에도 두지 않는다. (사람, 2026-10-23)
- code 이름은 `flow.ts` 하나로 고정하고 선언에 적지 않는다. lophn이 flow 선언에서 읽는 것은 `kind`와 `steps`의 key뿐이다. (agent, planner)
- instance 하나에 process 하나, 다시 띄우지 않는다. 켤 때 도는 flow는 닫는다. 바깥 효과가 두 번 나지 않게 한다. (agent, planner)
- sandbox는 앱 process와 같은 꼴이다. AI가 짠 code라 바깥 효과를 앱 tool과 agent로만 내게 해 invocation 기록과 rewind를 세운다. (agent, planner)
- flow의 앱 tool 호출은 PM의 지금 할당과 맡은 domain 안에서만 된다. code를 쓴 것이 PM이라 code로 할당을 넓히지 못한다. flow가 부르는 agent는 누구든 되고 자기 할당으로만 일한다. (agent, planner)
- flow process에는 credential을 주지 않는다. origin과 flow 자격은 route 입력이 아니고 core가 그 instance의 이름으로 한다. (agent, planner)
- 통로가 깨진 줄(JSON 아님, id 없음, 1 MiB 넘음)은 process를 끝내고, 읽히지만 칸이 틀린 요청은 `invalid_input` 값으로 답한다. 오타 하나로 flow 전체가 죽지 않게 한다. (agent, planner)
- 시간 한도를 두지 않는다. 오래 도는 flow가 정상이고 멈추는 길은 `StopWorkflow`다. (agent, planner)
- 진짜 flow process를 띄우는 test는 두지 않았다. lead가 throwaway core에서 손으로 확인했다: agent 답과 report, 틀린 step 이름의 `invalid_input` 값, `console.log`의 stderr 행, throw의 끝 code 1과 stack, sandbox 밖 읽기·쓰기·네트워크 거절, 멈추기의 `program_exited`(code null). (agent)

후속:
- 개발 data를 지우고 새로 만든다. `workflow_lines`의 CHECK, `runs` 표의 `instance` 열, `invocations.caller_kind` CHECK를 제자리에서 바꿨고 migration이 없다.
- `project-docs/issues/workflow.md`의 열린 이슈: workflow 폴더 안 symlink를 따라 밖을 읽음, CPU·memory·시간 한도 없음, `Deno.stdout`에 바로 쓰면 process가 죽음.

## flow process sandbox의 틈 셋을 막았다

```yaml
modules: [packages/core/main, packages/sdk, packages/core/agent-roles]
checked: [agent-role, architecture-layers, architecture-app-call, tool-check-deps, context-component-registry, architecture-approval, architecture-testing, architecture-eval, architecture-activation, architecture-agent-call, architecture-place-session, architecture-run, architecture-agent-definition, architecture-annotation, architecture-artifact, architecture-ui-kit, architecture-kinds, architecture-domain, tool-e2e, tool-test-live, tool-dev, tests-support, tool-package-linux, tool-models-snapshot]
```

- 전:
  - flow process는 workflow 폴더 안 symlink를 따라 폴더 밖을 읽을 수 있었다.
  - memory 한도가 없었다.
  - `flow.ts`가 `Deno.stdout.write`로 쓰면 core와의 통로가 깨져 host가 process를 끝냈다.
- 후:
  - launch 때 host가 workflow 폴더 전체를 훑어(앱과 같은 `realPathResolver`의 `linksIn`) 실제 경로가 폴더 밖이거나 풀리지 않는 symlink마다 `--deny-read=<lexical 경로>`를 더한다(`packages/core/main/flow-host/flags.ts`의 `flowFlags`).
  - `--v8-flags=--max-old-space-size=512`를 늘 더한다. 넘으면 process가 죽고 `program_exited` 줄에 끝 code와 stderr 끝이 남는다.
  - `packages/sdk/flow/wire.ts`가 원래 `Deno.stdout.write`를 잡아 두고 통로는 그것만 쓴다. `entry.ts`는 `flow.ts`를 import하기 전에 `Deno.stdout.write`·`writeSync`를 stderr로 돌린다.
  - SDK `guide.md`와 PM skill `guide-workflows`가 memory 한도, 폴더 밖 symlink, stdout 돌리기를 말한다.

왜: flow는 AI가 짠 code라 앱과 같은 sandbox 경계를 지켜야 한다. 계획 `flow`가 알고 넘긴 틈 셋이다.

결정:
- 훑기와 launch 사이에 새로 생긴 link는 막지 못한다. 앱의 `permissions.limit.symlink-changes`와 같은 한계다. (agent, planner)
- memory는 512 MiB다. flow는 agent와 앱 tool을 부르는 순서를 짜는 code라 넉넉하다. (agent, planner)
- CPU 한도는 OS 한도(`prlimit`)가 필요해 두지 않았다. 앱의 한도를 정할 때 같이 정한다. 시간 한도는 계획 `flow`대로 두지 않는다. (agent, planner)
- `Deno.stdout.writable` stream은 돌리지 않는다. 실수로 부를 만한 길은 `write`와 `writeSync`다. (agent, planner)
- 진짜 flow process를 띄우는 test는 두지 않았다. worker가 SDK entry를 따로 돌려 `Deno.stdout.write`·`writeSync`·`console.log`가 stderr로 가고 stdout에는 통로 줄만 남는 것을, lead가 `flowFlags`의 flag 그대로 `deno run`을 돌려 폴더 안 link는 읽히고 폴더 밖 link는 `NotCapable`이며 heap 한도가 512 MiB 근처로 줄어든 것을 손으로 확인했다. (agent)

후속:
- `project-docs/issues/workflow.md`의 열린 이슈: flow process에 CPU 한도가 없다.

## domain artifact에서도 kit으로 node를 그린다

```yaml
modules: [packages/core/agent-roles]
checked: [agent-role, context-component-registry, architecture-layers, architecture-approval, architecture-eval, architecture-place-session, architecture-workflow, architecture-agent-definition, architecture-artifact, architecture-domain, tool-check-deps]
```

- 전:
  - kit(`_lophn/kit.js`의 `LophnKit.renderGraph`)은 모든 artifact view에 있었지만 쓰는 법은 PM skill `guide-workflows`에만 있었다. domain artifact를 쓰는 App Engineer와 Operator는 kit을 몰랐다.
- 후:
  - 내장 skill `guide-artifact`(PM, App Engineer, Operator)에 "Drawing nodes with the kit"과 "Drawing a domain" 절이 생겼다. kit을 부르는 법, node·edge 모양, tone 값이 이 한 곳에 있다. kit이 그림 전체를 오류로 그리는 경우(빈 id나 겹친 id, 없는 node를 가리키는 edge, 자기 자신으로 가는 edge, 다섯 값 밖의 tone)도 처음 적었다. 순환은 된다.
  - domain에서 그리는 것은 둘이다. kind 지도는 kind가 node, `ref` 칸이 edge(label은 칸 이름)이고 item 수를 `kind.list`의 `aggregate` count로 세어 note에 둔다. 상태 흐름은 상태를 뜻하는 `enum` 칸의 값이 node이고 값마다 item 수(`group_by`)를 note에 둔다. 값 사이 edge는 `DOMAIN.md`나 사람의 말에서 오고 모르면 edge 없이 그린다. 그리기 전에 `ask`로 묻는다.
  - artifact는 `kinds.yaml`을 읽지 못하므로 agent가 그림 data를 `data/*.json`에 쓴다. `kinds-yaml` skill: kind 지도 artifact가 있으면 kind 파일을 바꿀 때 그 data도 고친다.
  - `guide-workflows`의 "Drawing nodes with the kit"은 `guide-artifact`를 가리키고 workflow에만 걸린 것(static·instance artifact, `data/_instance.json`, 예 HTML)만 남겼다. instance 예는 자기 자신을 `next`에 둔 step의 edge를 뺀다.

왜: 사람이 workflow의 node 그림 방식을 domain에도 쓰기로 했다(2026-10-22, `project-docs/products/roadmap/workflow.md` "정한 것 (사람)"). kit은 이미 모든 view에 있어서 남은 것은 domain artifact를 쓰는 agent가 쓰는 법과 무엇을 그릴지를 아는 것이었다.

결정:
- kit 쓰는 법은 `guide-artifact` 한 곳에 둔다. domain artifact를 쓰는 세 role이 모두 받고, 같은 API 설명이 두 곳에 있으면 갈라진다. (agent, planner)
- domain에서 그리는 것은 kind 지도와 상태 흐름 둘이다. 그림은 domain 주인 agent가 artifact로 그리고 program이 저절로 그리지 않는다. 상태 값 사이 순서는 domain의 뜻이라 agent가 정한다. (agent, planner)
- 그리기 전에 묻는다. workflow artifact에 사람이 정한 것("모든 workflow에 필요한 것은 아니다. PM이 물어보면 된다")을 domain에 그대로 썼다. (agent, planner)
- kind 지도의 data는 kind 파일을 바꾼 agent가 같이 고친다. (agent, planner)
- 자기 kind를 가리키는 `ref`는 kind 지도에 edge로 그리지 않고, 필요하면 node의 note에 쓴다. kit은 self-edge 하나로 그림 전체를 오류로 그린다. (agent)

후속: 없음.

## 앱 secret에 OAuth를 열고 사람이 앱 secret을 넣는 화면을 두었다

```yaml
modules: [packages/protocol, packages/core/apps, packages/core/lophn-agent, packages/core/secrets, packages/core/main, packages/sdk, packages/design, packages/shell/renderer, packages/shell/main, tools]
checked: [tool-check, boundary-catalog, context-component-registry, architecture-layers, architecture-approval, architecture-testing, architecture-eval, architecture-agent-call, architecture-place-session, architecture-run, architecture-annotation, architecture-browser-tab, architecture-artifact, architecture-workspace-layout, architecture-ui-kit, architecture-appearance, architecture-kinds, architecture-domain, tool-worktree-prep, tool-e2e, tool-test-live, tool-check-deps, tool-dev, tests-support, tool-package-linux, tool-models-snapshot, skill-ui-design, skill-wording, tool-wording]
```

- 전:
  - 앱 secret은 Bearer 값 하나였고 사람이 값을 넣는 화면이 없었다. 보호 입력 창의 `purpose: "app"`을 부르는 곳이 없었다.
  - OAuth refresh는 MCP에만 있었다.
  - 앱의 `netFetch`는 본문과 header를 보내지 못했다.
  - `provider-oauth.` 이름은 앞머리가 없는 것으로 보여 앱 secret으로 분류됐다. 앱 호출이 allowance만 맞으면 보낼 수 있었다.
- 후:
  - 선언: `secret.use` scope에 선택 칸 `oauth: {authorization_endpoint, token_endpoint, scopes, params?}`가 생겼다(`packages/protocol/apps/blueprint`).
    - 끝점은 https이거나 loopback http다.
    - 정규화: `scopes`는 정렬하고 중복을 지우며, 빈 `params`는 칸을 뺀다.
    - OAuth 표준 key(`OAUTH_RESERVED_PARAMS`)는 `params`에 쓸 수 없다.
    - 같은 이름의 `secret.use`가 둘이면 거절한다.
    - `@lophn/blueprint`가 `OAuthDeclaration` type을 낸다.
  - activation: OAuth 칸이 바뀌면 넓어진 선언이다. 동의 화면 label은 `secret.use:<이름> oauth:<authorize host> → <token host> scopes:<scope들>`이다.
  - route: 사람이 부르는 `apps.oauth_client_set`, `apps.oauth_begin`, `apps.oauth_cancel`, `apps.oauth_state`가 생겼다. `apps.secret_value`의 오류에 `conflict`(`oauth sign-in required`)가 생겼다.
  - core(`packages/core/apps/oauth`): MCP OAuth code(PKCE, loopback, 교환, refresh, vault)를 인자로 열어 쓴다.
    - access token은 선언한 이름에 둔다.
    - refresh token, meta, client id, client secret은 `app-oauth.<이름>.refresh|.meta|.client_id|.client`에 둔다.
    - `apps.secret_value`가 값을 보내기 직전에, 남은 시간이 5분 이하면 refresh한다.
    - 400·401·`invalid_grant`로 거절되면 token을 지우고 `failed`/`refresh_rejected`로 둔다.
    - 닿지 못하거나 5xx면 만료 전 token을 그대로 보낸다.
    - MCP 동작은 그대로다: https만, 400 이상 거절, 60초 skew, client secret 없음.
  - `file-attach`: `app-oauth.`·`provider-oauth.` 이름은 누가 불러도 보내지 않는다.
  - `netFetch`:
    - 본문(글 또는 bytes, 10 MiB까지)과 header(32개까지)를 싣는다.
    - `Authorization`·`Cookie`·`Host`·`Content-Length`·`Proxy-Authorization` header와 `GET`·`HEAD` 본문은 거절한다.
    - redirect:
      - 301·302·303은 `GET`으로 바꾸고 본문을 버린다. 307·308은 method와 본문을 그대로 다시 보낸다.
      - 앱 header는 처음 origin의 hop에만 싣는다.
    - broker의 `net/fetch` JSON 상한을 그 크기에 맞게 올렸다.
    - 앱 runtime이 broker 요청을 끝까지 쓴다. 전에는 큰 본문이 socket에서 잘릴 수 있었다.
  - 화면: 앱 Access 탭의 secret 줄
    - OAuth가 없는 secret: [Set value]/[Change value](보호 입력 창)
    - OAuth secret: client id 입력, [Set client secret], [Sign in](core가 loopback을 열고 shell이 OS browser로 연다), 상태와 실패 이유, [Cancel]
    - 기다리는 동안 2초마다 다시 읽는다. renderer allowlist에 route 넷이 생겼다.
    - 탭 안내 key가 `app-detail.note.access-intro-secrets`로 바뀌었다.
    - gallery Screens에 `new-app-access-secrets`, `new-app-access-oauth-setup|ready|waiting|signed-in|failed`가 생겼다.

왜: 앱이 Google Drive 같은 OAuth 서비스를 쓰게 한다. 10일마다 gdrive 폴더의 파일을 옮기는 job의 앞 단계다(`project-docs/products/roadmap/headless-schedule.md`). 앱 secret을 사람이 넣는 길도 없었다.

결정:
- OAuth는 `secret.use`의 칸이고, secret 이름 하나에 인증 방식 하나다. (agent, planner)
- client id와 client secret은 사람이 그 서비스에 만든 것을 넣는다. lophn이 자기 client를 들고 다니려면 서비스마다 심사를 받아야 한다. (agent, planner)
- access token은 선언한 이름에 둔다. broker, 전달, Bearer 붙이기를 바꾸지 않으려는 것이다. (agent, planner)
- refresh는 값을 보내기 직전에 한다(5분 skew). 400·401·`invalid_grant`만 거절로 보고, 일시 오류로는 sign-in을 잃지 않는다(provider refresh와 같다). (agent, planner)
- `netFetch`가 막는 header에 `Proxy-Authorization`을 더했다. (agent, lead)
- redirect에서 앱 header는 처음 origin에만 보낸다. API key 같은 header가 다른 host로 새지 않게 하려는 것이다. (agent, worker)
- Access 탭 wireframe을 lead 추천안대로 승인했다. client id 칸도 설정 선 안에 두고, 시간 초과 문구는 "Sign-in timed out. Try again."이다. client id는 줄 안에서 넣고 OAuth 줄과 plain 줄은 한 목록에 둔다. (사람, 2026-10-23)
- 진짜 Google로 sign-in, refresh, Drive 호출을 해 보는 것은 미룬다. App Engineer가 gdrive 앱을 지을 때의 첫 sign-in이 그 확인이다. Google "Testing" 상태 앱의 refresh token 7일 만료는 Google 문서에서 확인해 `packages/sdk/cap-secret/guide.md`에 적었다. (사람, 2026-10-23)

후속:
- 개발 data를 지우고 새로 만든다. SDK(`@lophn/cap-net`, `@lophn/blueprint`, `@lophn/cap-secret` guide)의 byte가 같은 version에서 바뀌어, 이미 만든 data root는 기동 때 conflict가 난다.
- 손으로 해 볼 것: 진짜 Google로 sign-in, refresh, Drive 호출. gdrive 앱과 함께 한다.
- 열린 이슈:

## "blueprint"를 걷어내고 앱의 선언(declaration)으로 부른다

```yaml
modules: [packages/protocol, packages/core/apps, packages/core/agent-roles, packages/core/lophn-agent, packages/core/main, packages/core/server, packages/sdk, packages/coding-agent, packages/shell/main, packages/shell/renderer, tools, tests]
checked: []
```

- 전:
  - 앱이 lophn에 내놓는 선언(이름, 설명, 화면, tool, 권한, 다른 앱 tool 쓰기, SDK 판)을 "blueprint"라는 따로 된 개념으로 불렀다. 앱 source의 `blueprint.ts`, SDK `@lophn/blueprint`(`defineBlueprint`), agent tool `blueprint.check`, CLI `lophn app blueprint`, release의 `blueprint_hash`, bundle의 `blueprint.json`, 실패 code `blueprint_missing` 등이 agent에게 그대로 보였다. 사람 화면과 문서는 대부분 "선언"이라 불렀다.
  - protocol에 선언 검증기의 flat 사본(`packages/protocol/apps/blueprint{,-types,-json,-schema,-scope}.ts`)과 폴더판이 같이 있었다.
  - coding agent 첫 prompt는 "blueprint 변경이 필요하면 알린다"고 하고, 앱 template의 `AGENTS.md`는 coding agent가 선언을 직접 먼저 고치라고 했다.
- 후: 선언은 그대로 앱 code 안에 있고 release와 같이 봉인된다. 이름만 바뀌었다.
  - 앱 source의 선언 file은 `lophn.ts`, 선언 test는 `tests/declaration_test.ts`다.
  - SDK `@lophn/declaration` 1.0.0(`packages/sdk/declaration/`)이 `defineApp`, `validateDeclaration`, type `AppDeclaration`을 낸다. 선언의 부분 이름(`ToolDeclaration`, `ScreenDeclaration`, `AppToolUseDeclaration`)은 그대로다.
  - agent tool `declaration.check`, route `declarations/check`(`declarationCheck`), CLI `lophn app declaration`.
  - release: wire `declaration_hash`, release 표의 열 `declaration`(정규 선언 JSON)과 `facts`(선언에서 뽑은 권한 요구, 다른 앱 tool 쓰기, tool 이름. 전의 `declarations` 열), bundle의 `declaration.json`. 파생 사실은 `AppFacts`, `factsOfDeclaration`, port `apps.permissions.CurrentFacts`이고 `apps/tools` 읽기와 activation 기록의 칸도 `facts`·`declaration`이다.
  - 실패 code: `declaration_missing`, `declaration_eval_failed`, `not_a_declaration`.
  - 폴더: `packages/protocol/apps/declaration/`, `packages/core/apps/declaration/`, `packages/core/apps/permissions/facts.ts`, `tools/deps-declaration.ts`(rule `declaration-pure`). flat 사본은 지웠다.
  - coding agent 첫 prompt(`firstPromptOf`)와 `project-docs/products/AGENT-ROLE.md` K4가 template을 따른다: 맡은 일에 필요하면 coding agent가 `lophn.ts`를 코드보다 먼저 직접 고치고 `deno.json` import map을 같은 정확한 version으로 함께 고친다. 막혔을 때만 `lophn message send`로 알린다.
  - eval: 재료 `notify-app`, `calendar-app`, `calendar-app-bug`, `date-range`, `calendar-data`의 @4(`lophn.ts`와 새 SDK 이름. `date-range@4`·`calendar-data@4`는 needs만 바뀌었다), criterion `card-covered@5`(judge 입력 이름표 `[BLUEPRINT]` → `[DECLARATION]`), check id `blueprint-kept` → `declaration-kept`. 시나리오 8개(calendar-user, calendar-dev, calendar-api, calendar-maintain, calendar-diagnose, L4-new, L7, O4)의 world와 criterion 핀을 새 판으로 올리고 n을 하나씩 올렸다.

왜: "blueprint"는 앱의 선언과 따로 된 개념처럼 보였다. 개념은 하나(앱의 선언)이고 사람 화면도 이미 "declarations"라 부른다. text만 바꾸면 file 이름, tool, SDK, 실패 code, `release.get` 칸이 agent에게 계속 보여 개념이 남는다(root `ISSUE-blueprint-domain.md`).

결정:
- 선언은 지금처럼 앱 code 안에 두고 release와 같이 봉인한다. 따로 된 개념 "blueprint"와 그 이름만 모두 걷어낸다. (사람, 2026-10-23)
- 앱 source의 선언 file은 `lophn.ts`다. 그 file을 읽는 쪽 이름을 쓰는 관례(`Dockerfile`, `wrangler.toml`)다. "manifest"는 bundle의 `manifest.json`과 겹치고 `@lophn/app`은 template import map의 별칭이라 쓰지 않는다. (agent, planner)
- 전의 `declarations`(파생 사실)는 `facts`로 바꿔 선언 전체와 겹치지 않게 했다. 사람 화면의 wording "declarations"는 그대로다. (agent, planner)
- 옛 이름을 읽는 호환 장치 없이 모두 바꿨다. migration은 없다. (agent, planner)

후속:
- 개발 data를 지우고 새로 만든다. release 표의 열 이름과 schema step(`apps.releases.tables`)이 바뀌었고, bundle file 이름이 바뀌어 모든 bundle hash가 바뀌었다.
- eval: check id가 `declaration-kept`로 바뀌고 criterion `card-covered`가 @5, 재료가 @4가 되어 지난 run과의 비교가 끊긴다. 옛 재료 판(@1~@3)과 registry 옛 항목은 기록이라 그대로 두었고, `blueprint.ts`를 담은 옛 판은 이제 release 준비를 지나지 못한다. component·core·checks 판은 이 변경에서 새로 재지 않았고 다음 진짜 run이 잰다.
- 열린 이슈: `project-docs/issues/mistakes.md`: 이름 바꾸기가 type 없이 오가는 wire 칸을 놓쳤다
