# 0.20.0

## 앱 화면이 연 session: 허용 입력, 제목·다시 붙기·새로 시작, 알림

```yaml
modules: [packages/protocol, packages/sdk, packages/core/apps, packages/shell/main, packages/shell/ipc, packages/shell/preload, packages/shell/renderer]
checked: []
```

- 전: 앱 bridge `agent.send`는 `run_shell`만 막고 나머지 ACP 입력을 사람 자격으로 core에 넘겼다. 앱 code가 자기 agent의 승인(`decide`)이나 `rewind`·`fork`도 보낼 수 있었다. `useAgentSession`은 화면이 load될 때마다 첫 `send`에서 새 session을 열어 제목이 첫 prompt 글이 됐고, workspace를 떠났다 오면 새 session이라 도는 turn의 답을 잃었다. 설치된 SDK 사본은 type shim이 `reduce.ts`가 import하는 type을 다 내지 않아 `@lophn/agent`를 쓰는 앱마다 `tsc`가 19건 오류였다. 앱이 연 session도 turn이 끝날 때마다 Finished 알림과 점이 떴다(오목은 수마다).
- 후:
  - bridge `agent.send`는 `send`, `stop`, `answer`, `rename`만 받고 나머지는 core에 닿기 전에 `forbidden`이다. 승인은 채팅 탭에서만 한다.
  - `open({agent, title?})`가 연 직후 제목을 붙인다. `@lophn/agent` 1.3.0: `useAgentSession({agent, title?, session?})`, `rename(title)`, `reset()`. `session`은 그 앱 workspace의 기존 session에 다시 붙어 바로 snapshot을 읽고 거기로 보낸다. `reset()`은 다음 `send`가 새 session을 열게 한다.
  - 설치 사본의 ACP shim은 `export type *`로 `acp-types.ts`를 통째로 다시 낸다.
  - 앱 화면이 연(또는 다시 붙은) session은 turn 끝(완료·실패)을 알리지 않고 Finished 점도 찍지 않는다. 승인·질문은 그 session을 쥔 앱 화면이 focus 창에 보이지 않을 때만 알린다. 앱 view는 `EmbeddedView`가 보임을 `{view_session, visible}`로 main에 알린다.

옮기기: 없음. 앱 template의 `@lophn/agent`가 1.3.0이다. 기존 앱은 `package.json`과 `lophn.ts`의 판을 올려야 새 API를 쓴다.

왜: 오목 앱 점검에서 앱 code가 승인을 풀 수 있는 길, 화면 load마다 쌓이는 session, 수마다 뜨는 알림, 설치 사본의 type 오류가 드러났다(사람, 2026-11-07).

결정:
- 허용 목록으로 막는다. 새 ACP 입력이 늘어도 앱은 닿지 못한다. (사람)
- 제목은 `rename` 입력으로 붙이고, 못 붙여도 열기는 성공한다. (agent)
- 앱 session 표시는 view가 사라져도 shell main 수명 동안 남긴다. 떠난 사이 끝난 turn도 알리지 않는다. 재시작하면 다시 붙을 때 되살아난다. (agent)
- `@lophn/agent` 1.2.0은 0.19.0이 낸 판이라 다시 쓰지 않고 1.3.0으로 올렸다. (agent)

후속: 없음.

## agent 주소는 handle, agent의 workspace 범위, call용 session 목록

```yaml
modules: [packages/protocol, packages/core/lophn-agent, packages/core/router, packages/core/apps, packages/core/agent-workspaces, packages/core/main, packages/cli, packages/shell/main, packages/shell/renderer, packages/design, tests]
checked: []
```

- 전: agent의 주소가 name이라 이름이 겹치지 못했고, 앱이 SDK로 agent를 열 때는 내부 id(`lophn`, `agt_…`)를 넘겨야 했는데 agent가 그 id를 볼 길이 없었다. lophn의 이름은 바꿀 수 없었다. agent 정의는 모두 전역이라 앱 하나를 위한 agent도 모든 workspace의 "Agents you can call"에 실렸다. call용 session 목록은 agent·이름·상태만 줬고 사람의 승인을 기다리는 session도 `running`이었다. `lophn agent card`는 어떤 agent든 `not_found`였다.
- 후:
  - agent 주소는 `handle`이다. 만들 때 정하고 바뀌지 않으며 전역에 하나(대소문자 무시)이고 `lophn`은 예약이다. `name`은 보이는 이름이고 바꿀 수 있고 겹쳐도 된다. lophn은 handle `lophn` 고정, name은 사람이 바꾼다(profile은 그대로 고정).
  - call `to.agent`, `agent run --agent`, `agent card|update <handle>`, `agent create <handle>`, `app share --agent`, `workflow.yaml`의 `agent`, 앱 SDK `useAgentSession({agent})`, "Agents you can call"이 모두 handle이다. 내부 id는 저장, 설정(call 정책), session 행에만 있다.
  - agent 정의에 선택 칸 `workspace`(project나 app)가 있다. 범위 agent는 그 workspace에서만 목록·명함·session 열기에 보이고, 밖에서는 `{agent, workspace}` call로만 닿는다(call 정책과 private은 그대로). agent가 `agent create`를 부르면 그 session의 workspace가 범위다(home이면 전역). Settings에서 사람이 만들면 전역이다.
  - 앱 범위 agent는 자기 앱의 command(비공개 포함)를 사람의 할당 없이 부른다. bare는 `tools`에서 골라야 보인다. 다른 앱의 command는 지금처럼 할당이다.
  - `lophn session list`(`ListSendableSessions`)가 handle·이름·session 제목·마지막 활동 시각을 싣고, 승인이나 질문을 기다리는 session은 `waiting`이다.
  - `agent card` read가 reader pool에 등록됐다.

옮기기: data step `agents.handle`이 기존 정의 파일(`agents/agt_*.md`)에 `handle` = 지금 name을 채운다. 기존 call과 `workflow.yaml` 참조가 그대로 닿는다. lophn.md와 틀린 파일은 건드리지 않는다.

왜: builder가 앱 안 agent를 만들고 SDK로 부르려면 주소가 눈에 보이는 하나여야 하고, 사람은 lophn의 이름도 바꾸고 싶어 했다. workspace마다 agent를 두어야 private/public 구분이 agent에도 의미를 갖는다(사람, 2026-11-07).

결정:
- 주소(handle)와 보이는 이름(name)을 가른다. 앱의 slug·name과 같은 꼴이다. (사람)
- agent 정의에 workspace 범위를 둔다. 범위는 보이는 곳과 수명만 정하고 handle 이름 공간은 전역에 하나다. (사람, 이름 공간은 agent)
- 새 handle은 소문자·숫자·`-`·`_` 40자까지다. 옮긴 handle은 옛 name 그대로 받는다. (agent)
- handle과 workspace는 만든 뒤 바꾸지 못한다. agent가 만든 agent의 범위는 부른 session의 workspace로 고정한다. (agent)
- `waiting`은 도는 turn에 결정 없는 confirm tool call이나 시작한 `ask`가 있을 때다. (agent)

후속:
- 범위 agent를 전역으로 올리기, 편집 화면의 범위 고르기, 앱·project를 지울 때 범위 agent 정리는 없다.
- Settings에서 이름이 ASCII 글자 없이만 된 agent를 만들면 handle을 직접 적어야 한다.

## 떠난 workspace의 page를 필요할 때만 살린다

```yaml
modules: [packages/protocol, packages/sdk, packages/core/apps, packages/design, packages/shell/ipc, packages/shell/main, packages/shell/preload, packages/shell/renderer, tools]
checked: []
```

- 전: workspace를 바꾸면 그 workspace의 `<webview>` page(browser 탭, 앱 화면, artifact)가 모두 놓이고 돌아오면 다시 load됐다. `<webview>` 그릇이 `WorkspaceWindow` 안에 있었기 때문이다.
- 후:
  - 그릇이 창 단위(`app-frame/workspace-views.tsx`)로 올라갔고 `WorkspaceWindow` 본문은 그 그릇과 같은 stacking context에 portal로 그린다.
  - 떠날 때 기본은 지금처럼 놓는다. page가 "살려 둬" 신호를 켠 동안은 숨겨 두고 돌아오면 다시 load하지 않는다(그 탭이 layout에 있을 때).
  - 앱 화면: `@lophn/app-ui` 2.5.0 `useKeepAlive(active)`, bridge `lophnApp.setKeepAlive(active, key?)`. key마다 켜고 끄며 하나라도 켜져 있으면 산다. `@lophn/agent`는 보내는 중이거나 turn이 도는 동안(승인·질문 대기 포함) 스스로 켠다.
  - browser 탭: 소리가 나는 중, 다운로드 중, 사람이 탭 ⋯ menu의 Keep alive를 켰을 때 살린다(layout의 선택 칸 `keep_alive`).
  - artifact 탭은 page와 host 사이 통로가 없어 기본대로 놓는다.
  - 살려 두는 page는 창마다 6개까지이고 넘치면 가장 오래 안 본 것부터 놓는다. 전역 float는 그대로다.

옮기기: 없음. browser 탭 layout의 `keep_alive`는 선택 칸이다.

왜: 오목 앱 화면이 agent 답을 기다리는 중에 다른 project에 다녀오면 답을 잃고 새 session이 열렸다. 모두 살리면 자원을 쓰고 program은 page 안의 뜻을 모르므로, page를 짓는 builder가 신호로 정한다(사람, 2026-11-07).

결정:
- 기본은 놓고 신호를 켠 page만 살린다. 고정 설정이 아니라 page가 필요할 때 켜는 신호다. (사람이 추천을 받음)
- browser 탭은 builder가 없어 program이 알 수 있는 신호(소리, 다운로드)와 사람의 탭별 toggle로 정한다. (사람이 추천을 받음)
- 상한은 창마다 6개, 오래 안 본 것부터 놓는다. (사람이 추천을 받음)
- 살려 둘지는 떠날 때 한 번 정한다. (agent)

후속:
- 실제 Electron에서 portal 뒤 z-order와 workspace 오가기를 눌러 보지 못했다(dev 앱을 sandbox 없이 띄우는 것을 사람이 확인해야 한다).
- 소리가 멈춘 뒤에도 page는 상한에 밀리거나 돌아올 때까지 남는다.

## 큰 tool 결과 때문에 started로 남던 tool call 기록

```yaml
modules: [packages/core/lophn-agent, packages/core/main, packages/core/storage]
checked: []
```

- 전: tool 결과가 core JSON 본문 한도(256 KiB, 깊이 16, 항목 4,096)나 summary 400자를 넘으면 기록 finish가 `invalid_input`으로 거절됐다. 큰 이미지의 `image.read`, 큰 JSON의 `web.fetch`, 깊이 25인 `lophn settings get`이 그랬다. 결과는 `uncertain`이 되어 한 번 다시 시도했고 같은 이유로 실패해, `tool_calls` 행 둘(attempt 0, 1)이 `started`로 남았다. turn은 정상으로 끝났고 ACP 화면에는 그 tool이 영원히 실행 중으로 보였다.
- 후: finish가 거절되면 줄인 기록(summary를 자르고 내용을 빼고 이미지는 개수만)으로 한 번 더 내 행이 제 outcome으로 끝난다. 전체 결과는 output blob에 있고 model에는 전체가 간다. 진입한 뒤 결과 저장·redaction·finish·진입 기록이 실패하거나 handler가 던져도 행을 `uncertain`으로 닫는다.

옮기기: ledger step `lophn-agent.harness-tools.close-stuck`이 끝난 turn 안에서 `requested`·`started`로 남은 tool call을 `uncertain`으로 닫는다(`finished_at`은 turn이 끝난 시각).

왜: 사람의 ledger에서 끝난 turn 안의 `started` 행 12개(재시도 쌍 6개)가 나왔다.

결정:
- 줄인 기록은 거절된 뒤에 낸다. core의 한도를 복제하지 않는다. `result` 열을 읽는 곳은 context 추정뿐이라 이미지 개수만 남긴다. (agent)
- 원인이라고 처음 짚은 blob 동시 준비 한도는 ledger와 맞지 않아(call 하나짜리 응답에서도 생겼다) 그 장치를 넣지 않았다. (agent)
- 이미 끝난 turn의 열린 행은 결과를 모르므로 `uncertain`으로 닫는다. (agent)

후속:
- 멈춤 요청에 답하지 않아 loop가 포기한 call은 늦은 결과가 와야 닫힌다.
- 수 MB 이미지 결과의 redaction이 시간 안에 끝나는지는 확인하지 못했다.

## 앱 공유 요청을 activation 동의와 한 번에 승인

```yaml
modules: [packages/protocol, packages/core/approvals, packages/core/apps, packages/core/main, packages/core/agent-workspaces, packages/cli, packages/shell/renderer, packages/design]
checked: []
```

- 전: builder가 `lophn app share`로 공유를 청하면 사람이 activation 동의와 공유 요청을 대기 목록에서 따로 두 번 승인했다.
- 후: 그 앱의 activation 동의가 대기 중이면 동의 카드가 공유 요청(받을 agent, coding agent, 이유, 받는 공개 skill·command 수)을 같이 보이고, 동의를 허락하면 같은 tx에서 공유 요청도 승인한다. 공유 요청은 따로 줄을 서지 않는다. 동의 대기가 없으면 지금처럼 제 줄로 선다. `activation.consent` 입력에 선택 칸 `share_requested_at`이 있다.

옮기기: 없음.

왜: 사람이 command를 만들고 grant하는 것까지 agent가 알아서 하기를 바랐다. 사람의 승인은 남기되 한 번으로 줄였다(사람, 2026-11-07).

결정:
- 동의 카드가 본 공유 요청의 `requested_at`을 싣고, 그 사이 요청이 바뀌었으면 동의째 `conflict`다. 보지 않은 요청을 승인하지 않는다. (agent)
- 공유를 먼저 적용하고 실패하면 tx가 되돌아가 동의는 대기로 남는다. (agent)
- 동의를 거절하면 공유 요청은 남아 제 줄로 다시 보인다. (agent)

후속: 카드가 열린 동안 새로 열린 공유 요청은 그 동의에 묶이지 않고 따로 선다.

## 앱 안 agent: builder 안내

```yaml
modules: [packages/core/agent-workspaces, packages/core/apps, packages/sdk]
checked: []
```

- 전: builder가 앱 안 상대·코치를 만들 때 기본 lophn agent를 그대로 썼다(turn마다 제품 규칙과 file·shell tool이 실렸다). SDK의 `agent` 값을 알아내려고 SDK와 설치된 Electron bundle을 뜯어 봤다. 판마다 session을 나누지 않았다. template이 "앱 CSS는 token만"이라 판과 돌도 회색 token으로 그렸다.
- 후: `design-app` skill에 "An agent inside the app" 절이 있다. 이 앱 workspace에서 bare agent를 먼저 만든다(`lophn agent create <handle>`, `tools: []`, 지침에 역할·context block·답 꼴). 화면은 `useAgentSession({agent: <handle>, title})`를 쓰고, 일 단위(판, review)마다 session 하나를 쓰며 그 id를 앱 data에 두고 `session`으로 다시 붙는다. 다음 단위는 `reset()`과 새 `title`이다. 앱이 context를 조립하고 agent는 JSON으로 답하며 앱 code가 검사한다. app workspace 지침, template `AGENTS.md`, `@lophn/agent` guide가 같은 것을 말하고, `new-app` handoff는 앱 안 agent를 정했는지 적는다. 앱 틀은 token만 쓰고 판·말·지도·차트 같은 domain 그림은 고정 색과 gradient를 써도 된다.

옮기기: 없음.

왜: 사람은 lophn 구현을 모른다. SDK 쓰는 법, agent 만들기, bare 지침 쓰기까지 lophn agent가 해야 한다(사람, 2026-11-07).

결정:
- 앱 안 agent는 bare로 만들고 앱이 context를 조립해 JSON으로 답하게 하는 것이 기본이다. command는 앱 data를 건드려야 할 때만 준다. (사람)
- `model`은 builder가 알 때만 정한다. provider 목록을 읽을 명령이 없다. (agent)

후속: builder는 preview에서 화면을 보지 못한다. 안내는 agent와 주고받는 논리를 순수 함수로 두고 test하는 데 기댄다.

## Inbox에 영구 기록이 남는다: 알림 표 하나, program 기록, Now·History

```yaml
modules: [packages/protocol, packages/sdk, packages/core/apps, packages/core/main, packages/core/storage, packages/core/agent-workspaces, packages/design, packages/shell/main, packages/shell/renderer, tools]
checked: []
```

- 전: 사람에게 오는 알림은 앱 알림(`app_notices`)뿐이었고 모두 휘발이었다. 지우면 행이 지워졌고 종류·출처·읽음이 없었다. core는 사람에게 알릴 길이 없어 release 결과, 앱 멈춤, data migration, lophn 업데이트가 Inbox에 남지 않았다. 지난 release를 Inbox에서 찾을 수 없었다.
- 후:
  - ledger 표 `notices` 하나가 앱 알림과 program 기록을 담는다. 줄마다 출처(`app`·`program`), 종류, 앱, project, 영구 여부, `action`, 읽은 시각이 있다. 휘발 줄은 지우면 사라지고 영구 줄은 읽음으로만 바뀌어 남는다. program 줄은 늘 영구이고 지우지 못한다(DB trigger). 앱의 영구 줄은 앱마다 최근 200개, 휘발 줄은 50개다.
  - route는 `notices.post`(앱만, 자기 앱), `notices.record`·`notices.observe_version`(core만), `notices.dismiss`·`notices.mark_read`(사람), `notices.list`·`notices.open`이다. event는 `NoticePosted`·`NoticeClosed`·`NoticeRead`다. program 글은 고정 template과 매개변수로만 만든다.
  - `@lophn/cap-notify` 1.2.0: `notify({ ..., persistent? })`. 기본은 지금과 같은 휘발이다.
  - program 기록: release 켜짐(`release_activated`)·실패(`release_failed`, 이전 release로 돌아갔으면 그 말을 싣는다)·사람이 이전 release로 돌아감(`release_rolled_back`), 앱 멈춤(`app_unavailable`, 앱마다 한 줄), 앱 data migration 적용·복원, lophn 업데이트(`lophn_updated`). 상태를 바꾸는 command와 같은 tx에서 쓴다. toast·OS 알림은 실패·되돌림·멈춤·복원·SDK 업데이트 필요만 띄운다.
  - ledger 표 `core_meta`가 data root가 마지막으로 돈 제품 판을 적는다. 판이 바뀐 기동에서 `lophn_updated`를 한 번 남기고 `productStartListeners`를 부른다. 새 data root는 판만 적는다.
  - Inbox가 두 탭이다. Now는 답할 것(승인·질문·동의·공유·job)과 그 아래 Notifications(끝난 탭, 휘발 알림)다. History는 영구 기록을 최근 것부터 보이고 앱·project·종류로 거르고 글로 찾는다. sidebar 배지는 Now만 세고 안 읽은 기록 수는 History 탭 머리에만 보인다.
  - 기록에 `action`(`open_home_skill`)이 있으면 Ask lophn 단추가 선다. 누르면 home lophn 새 대화가 열리고 `/<skill> <args>`가 사람의 첫 말로 간다.
  - 앱 상세 Activity 탭 위쪽에 그 앱의 영구 기록이 보인다.

옮기기:
- ledger step `apps.notices.unified`: `app_notices` 줄을 앱이 쓴 휘발·안 읽은 줄로 `notices`에 옮기고 옛 표를 지운다.
- ledger step `apps.notices.product-version`: 표 `core_meta`. 판을 적지 않던 data root는 처음 켜질 때 `from`을 모르는 `lophn_updated` 한 줄을 남긴다.

왜: 사람이 지난 release 같은 일을 찾을 수 있어야 하고, 영구와 휘발을 가르고 싶어 했다. 앱 알림도 영구/휘발을 고르게 했다(사람, 2026-11-07, `project-docs/products/roadmap/inbox-history-sdk-migration.md`).

결정:
- Inbox는 답할 것·알림(휘발)·기록(영구) 셋이다. (사람)
- 앱 알림도 영구/휘발을 고른다. 기본은 휘발이다. (사람)
- program 기록은 지우지 않고 앱 영구 알림은 앱마다 200개다. (사람이 추천을 받음)
- 기록은 표 하나다. 같은 key는 영구 줄이어도 덮어쓰고 안 읽음으로 되돌리므로, key는 앱 멈춤처럼 상태를 나타내는 기록에만 쓴다. (agent)
- program 기록은 상태를 바꾸는 command의 tx 안에서 쓴다. 재전송과 끊김에서 빠지거나 늘지 않는다. (agent)
- 안 읽은 기록은 배지에 세지 않는다. 기록은 나중에 찾는 것이고 급한 것은 toast가 맡는다. (agent)

후속:
- 실패 이유에는 앱의 migration script가 낸 글이 실릴 수 있다(앞 200자).
- 복원된 실패는 toast가 둘(실패, data 복원) 뜰 수 있다.
- program 기록에 project가 비어 있다.

## SDK 판별 migration 메모와 지원 하한

```yaml
modules: [packages/core/agent-workspaces, packages/protocol, packages/sdk, packages/design, tools]
checked: []
```

- 전: 판마다 무엇이 바뀌었고 앱 code를 어떻게 고치나 하는 메모가 제품 changelog에만 있어 agent가 못 읽었다. lophn이 아직 돌리는 가장 옛 SDK 판이 어디에도 적혀 있지 않았다.
- 후:
  - 내장 skill `migrate-sdk`(home·app, `/` 메뉴 아님)가 절차 하나를 갖고, SDK 판 하나가 메모 file 하나(`<sdk 이름에서 @lophn/를 뺀 것>-<판>.md`)로 SKILL.md 옆에 쌓인다. 메모는 바뀐 것, `Breaking:`, 앞 판에서 옮기는 code, `Previous:`를 적는다. 앱 lophn은 고정 판 뒤부터 지금 판까지의 메모만 읽는다.
  - 지금 판 전부와 0.13.0 뒤 앱이 옮겨야 했던 판의 메모 31개가 있다.
  - SDK와 지원 소스의 `package.json`에 `lophn.supported_from`(지원 하한)이 있다: `@lophn/declaration` 4.0.0, `@lophn/cap-tool` 2.0.0, `@lophn/app-ui` 2.3.0, `@lophn/agent` 1.1.0, `@lophn/ui` 1.1.0, 나머지 1.0.0. 설치 사본에도 남는다.
  - `npm run check`의 `sdk notes` 단계가 지금 판과 하한의 메모, 메모 이름, `Previous:` 사슬을 본다. AGENTS.md "코드"에 같은 규칙이 있다.

옮기기: 없음.

왜: SDK 판이 바뀐 앱을 옮기는 일은 결정적으로 할 수 없어 agent가 한다. agent가 읽을 판별 메모가 필요했다. skill은 하나로 두고 내용만 md file로 더한다(사람, 2026-11-07).

결정:
- migration skill은 하나이고 판별 메모를 file로 더한다. 메모는 지우지 않는다. agent는 범위만 읽어 context는 그 앱이 뒤처진 만큼만 커진다. (사람)
- `@lophn/agent` 하한은 1.1.0이다. `agt_` id를 넘긴 1.2.0 앱만 깨지는데 판으로 알 수 없어 1.3.0 메모에 적었다. (agent)
- data root에 옛 SDK 사본을 따로 싣지 않는다. 하한 아래 앱은 처음 다시 release할 때 옮긴다. (agent)

후속: 오래된 major 구간이 길어지면 제품을 낼 때 메모를 합친다.

## SDK 업데이트 감지와 lophn에게 맡기기

```yaml
modules: [packages/protocol, packages/core/apps, packages/core/main, packages/core/router, packages/core/agent-workspaces, packages/cli, packages/design, packages/shell/renderer]
checked: []
```

- 전: 앱이 고정한 SDK 판과 깔린 판을 견주는 곳이 없었다. 계약이 바뀐 major로 앱이 뜨지 않아도 일반 `start_failed`로만 보였다. home lophn은 앱의 고정 판을 볼 수 없었다. private workspace는 home의 call도 막아 home에서 앱으로 일을 넘길 수 없었다.
- 후:
  - 읽기 `app.sdk_status`(`lophn app sdk-status [<앱>]`, home·app)가 archived가 아닌 앱의 켜진 release마다 SDK별 고정 판, 지금 판, 지원 하한, 단계(`required`·`available`·`current`), 읽을 메모 file을 준다.
  - lophn이 새 판으로 켜지면 `required` SDK가 있는 앱마다 "SDK 업데이트 필요" 기록(앱마다 한 줄)을 Ask lophn 단추(`/update-apps <앱>`)와 함께 남긴다. `available`만 있는 앱은 lophn 업데이트 기록에 "N apps have optional SDK updates." 한 줄로만 보인다. 앱 상세 Version 탭에 SDK마다 필수/가능/최신이 보인다.
  - 내장 home skill `update-apps`(`/` 메뉴): SDK 상태와 메모를 읽어 앱마다 무엇이 바뀌는지 사람 말로 설명하고, 사람이 고른 앱의 lophn에게 `reply: none`으로 넘긴다. 앱 lophn은 `migrate-sdk`대로 옮긴다.
  - call 정책: home의 기본 lophn이 private workspace의 lophn에게 `reply: none`으로 보내는 call은 private 판정을 건너뛴다. 답·결과를 받는 reply, 다른 home agent, private에서 나가는 call은 그대로 막히고 agent·workspace 쌍 규칙이 먼저다.

옮기기: 없음.

왜: SDK가 바뀌면 사람에게 알리고, 사람이 맡기면 home lophn이 바꿀 곳을 찾아 앱 lophn에게 넘겨 옮기게 한다(사람, 2026-11-07).

결정:
- 맡기기는 늘 home을 거친다. (사람)
- Inbox에는 필수만 올리고 가능은 lophn 업데이트 기록과 앱 상세에만 보인다. (사람: 알아서)
- private 예외는 home의 기본 lophn, private 쪽 lophn, `reply: none` 셋이 다 맞을 때뿐이다. home을 통째로 예외로 두지 않는다. (사람이 추천을 받음)
- 사람이 앱을 옮긴 뒤에도 "SDK 업데이트 필요" 줄은 그때의 기록으로 남는다. 지금 상태는 SDK 상태 read와 Version 탭이 말한다. (agent)

후속:
- 감지는 제품 판이 바뀔 때만 돈다.
- `update-apps`가 실제 model에서 그대로 따르는지는 eval이 없다.

## 정정: SDK 업데이트 줄은 하나, home이 숲을 보고 정한다, 배지는 History도 센다, History 기간 거르기

```yaml
modules: [packages/protocol, packages/core/apps, packages/core/main, packages/core/agent-workspaces, packages/shell/main, packages/shell/renderer, packages/shell/preload, tools/wireframes]
checked: []
```

- 전: 0.20.0을 설치하면 History에 `lophn_updated` 한 줄과 앱마다 "The app needs an SDK update"(mahas, masup, calendar) 줄이 있고 줄마다 [Ask lophn]이 `/update-apps <앱>`을 열었다. 가능(`available`) 갱신은 `lophn_updated` 본문에 "N apps have optional SDK updates."로만 있었다. `update-apps`는 SDK 상태를 사람 말로 옮겨 설명하고 고른 앱을 넘기는 일만 했다. 안 읽은 History 줄은 sidebar 배지에 세지 않아 사람이 아무것도 보지 못했다. History에 기간 거르기가 없었다.
- 후:
  - 제품 판이 바뀐 기동에서 필수나 가능 SDK가 있는 앱이 하나라도 있으면 앱 없는 `sdk_update_needed` 줄 하나를 쓴다. params `{required, available}`, 글 "SDK updates for your apps" / "3 apps must update, 2 can use new SDK features.", key `sdk_update_needed`(다음 기동이 개수를 새로 쓰고 안 읽음으로 되돌린다), action `/update-apps`(전체). `lophn_updated`의 `optional_sdk_apps`와 `notices.observe_version`의 같은 입력을 지웠고 `ctx.sdkStatus` 제공도 지웠다. 이 줄은 앱이 없어도 toast·OS 알림으로 뜨고(`NoticeTarget` `inbox`) 누르면 Inbox를 연다.
  - `update-apps`는 숲을 보는 skill이다. 앱마다 SDK 상태(필수와 가능), 목적·공개 command, 지나는 판의 메모를 읽고 (a) 필수 migration, (b) 새 SDK 기능 중 이 앱에 쓸 만한 것(예: 한도가 지나면 휘발 알림), (c) 그대로 두기를 정해 추천한다. 사람에게 내부 용어 없이 앱별 짧은 계획을 보이고 `ask`로 고르게 한 뒤, 고른 앱의 lophn에게 필수 migration, 고른 기능(앱 대화에서 사람과 확인하고 `design-app`으로 설계할 제안), 목표 판, 메모 file을 `reply: none`으로 넘긴다. home은 앱 source를 못 읽어 목적·command·메모로 판단하고 자세한 것은 앱 lophn에게 맡긴다. `migrate-sdk`는 migration을 release한 뒤 고른 기능을 넣는 단계(11)를 더했다.
  - sidebar Inbox 배지가 안 읽은 영구 기록(History)도 센다. History 탭 머리의 숫자는 그대로다.
  - `notices.list`에 `since`·`until`(`created_at`, since 포함·until 미포함)을 더했다. History 필터 바의 `DateRangeFilter`(kit)가 고른 달력 날짜를 지역 자정으로 풀어 보낸다. [Reset filters]로 돌아가고 [Load more]·[Mark all read]는 거른 줄에 쓴다. 안 고른 상태는 필터 버튼에 "Custom range"로 보인다.

옮기기: 없음. 이미 낸 앱마다의 옛 `sdk_update_needed` 줄은 program 줄이라 지울 수 없어 남고 단추도 동작한다. 새 줄은 같은 kind를 앱 없이 쓴다(표 모양은 그대로).

왜: 줄마다 [Ask lophn]이 있으면 home을 거칠 이유가 없다. home은 각 앱을 두고 갈지 올릴지 숲을 먼저 보고 자세한 migration을 넘기는 곳이다. 사람은 SDK 변화가 무엇을 깨고 무엇을 가능하게 했는지 판단하지 못하니 lophn이 판단해야 한다. 알림 목적은 사람이 알게 하는 것이라 History도 배지에 센다. (사람, 2026-11-07)

결정:
- kind는 `sdk_update_needed`를 앱 없이 다시 쓴다(새 kind를 만들지 않았다). 필수와 가능을 한 줄에 센다. (agent)
- 앱 없는 program 줄 중 이 줄만 toast로 띄운다. (agent)
- 가능만 있어도 줄을 쓴다(앱 상세 Version 탭과 별개로, 새 기능을 채택할지 판단하게 하려는 것). (사람)

후속:
- 기동 중에 쓴 줄은 toast가 뜨지 않는다. `afterReady`가 core의 hello 전에 돌아 shell main이 `NoticePosted`를 받지 못한다. 배지와 History로만 보인다(`project-docs/issues/shell.md`).
- 기간을 안 고른 상태가 "Custom range"로 보인다(kit의 `DateRangeFilter`가 "전체" 상태를 모른다).
- 앱에 맞는 새 기능을 model이 실제로 잘 제안하는지는 eval이 없다.
