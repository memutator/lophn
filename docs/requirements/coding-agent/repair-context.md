# coding-agent/repair-context

coding agent가 작은 요약부터 필요한 근거를 읽고 과거 증상과 현재 상태를 구별하도록 문제·snapshot·ticket·release·지난 고친 기록에서 요청 때 조립하는 수리 자료의 내용·순서·선정·크기·추가 읽기를 맡는다; snapshot 자체는 problems/snapshots, 전송 표현은 coding-agent/mcp-server와 coding-agent/cli를 가리킨다.

## 요구

### 조립과 순서

**[R1]** 수리 자료는 매 요청 현재 허용 범위의 정본을 읽어 조립하고 조립 시각·증상 관찰 시각·발생 release·source 위치의 기준 commit을 함께 보여 주며 완성 묶음을 별도 정본으로 저장하지 않는다.
- 이유: 현재 조회와 고정 당시 증거를 혼동하지 않게 한다.
- 확인: 두 조회 사이 발생과 release를 바꾸면 새 상태와 조립 시각이 반영되고 옛 source 줄 번호는 발생 release의 commit 기준으로 표시된다.
- 의도: coding-agent#I7

**[R2]** 수리 자료는 ticket에 연결된 여러 문제를 문제별로 구별하고 ticket 준비 전 조사도 같은 내용 계약으로 문제 하나를 읽게 하되 code 작업은 ticket 생성·MCP claim 뒤에만 시작한다.
- 이유: ticket 준비 조사와 여러 문제의 작업 근거를 한 통로에서 제공하되 섞지 않는다.
- 확인: 여러 문제 ticket에서 각 근거가 어느 문제인지 확인되고 ticket 준비 조사 묶음 읽기만으로 ticket·claim이 생기지 않고 code 작업 시작 안내는 담당 agent의 ticket 준비로 연결된다.
- 의도: coding-agent#I7, coding-agent#I4

**[R3]** 절은 대상과 증상·사람 말·볼 곳·acceptance check·지킬 것·발생 근거와 실패 invocation·대표 발생·직전 변화·log·지난 고친 기록·관련 문제·첨부·재현·더 읽기·반환 방법 순서로 제공하고 내용과 누락 사실이 모두 없는 빈 절만 뺀다.
- 이유: 무엇을 고치고 보존할지 먼저 읽고 사실과 검증을 뒤따라 보게 한다.
- 확인: 같은 입력에서 절 순서가 같고 누락 이유가 있는 절은 사라지지 않으며 반환 안내를 끝에서 찾는다.
- 의도: coding-agent#I7

### 기본 묶음의 크기

**[R4]** 머리 정보는 앱·문제·상태·현재 ticket claim의 연결·횟수·처음과 마지막 시각·발생 release를 6줄 이하로 제공한다.
- 이유: 문제의 현재 상태와 발생 기준을 적은 문맥으로 식별한다.
- 확인: 긴 이름과 여러 발생에서도 6줄 안에 해당 항목이 있고 없는 claim을 꾸며 넣지 않는다.
- 의도: coding-agent#I7

**[R5]** 사람에게 보이는 증상 문구는 문제당 1줄·전체 2줄, 사람 원문 excerpt는 5줄 및 문제당 300자, 볼 source와 고정 근거는 10줄 및 최대 5개로 제한해 나머지는 실제 근거 읽기로 잇는다.
- 이유: 사람 말과 구현 근거를 잃지 않고 기본 묶음을 작게 유지한다.
- 확인: 긴 원문과 많은 source를 넣어 각 상한이 지켜지고 원문·고정 근거로 추가 조회가 가능하다.
- 의도: coding-agent#I7

**[R6]** acceptance check와 지킬 것은 각각 8줄 및 200자 요약으로 제공하되 전체 조건과 유지 제약의 읽을 곳을 반드시 연결한다.
- 이유: 요약을 전체 검사 조건이나 권한으로 착각하면 안 된다.
- 확인: 12개 조건과 20개 유지 제약에서 요약 상한이 지켜지고 ticket 전체 조건을 빠짐없이 읽을 수 있으며 문제 닫힘 조건은 problems/closing을 가리킨다.
- 의도: coding-agent#I7, coding-agent#I4

**[R7]** 대표 발생은 최대 3개·전체 30줄·각 excerpt 400자, 실패 invocation은 15줄 이하로 당시 실패 연산과 근거를 보여 준다.
- 이유: 반복 전체 대신 차이와 실패 지점을 전달한다.
- 확인: 긴 스택과 수백 발생에서도 상한을 지키고 대표 Report·snapshot과 apps/invocations의 당시 기록을 이어 읽는다.
- 의도: coding-agent#I7

**[R8]** 직전 변화는 최대 12개·14줄·각 100자, 기본 log는 45줄, 지난 고친 기록은 10줄 및 최신 5개로 제한한다.
- 이유: 전체 수리 자료에 log나 변화 목록이 대부분을 차지하지 않게 한다.
- 확인: 큰 변화·log·수리 이력에서 해당 상한을 지키고 실제 release·고친 기록·test result로 이어 읽힌다.
- 의도: coding-agent#I7

**[R9]** 관련 문제는 관계 묶음마다 5줄 및 전체 최대 10개, 첨부 절은 40줄 및 이미지 metadata 최대 20개로 제한하고 읽기 명령 결과는 명령마다 3행만 보여 준다.
- 이유: 관련 문제를 재귀 조립하거나 화면 결과를 통째로 붙이지 않는다.
- 확인: 많은 문제와 화면 결과에서 상한을 지키고 나머지 행·첨부를 추가 조회할 수 있으며 binary는 기본 텍스트에 들어가지 않는다.
- 의도: coding-agent#I7

**[R10]** 재현 안내는 6줄 및 500자, 더 읽기 안내는 5줄, 반환 안내는 4줄로 제한해 전체 근거 읽기·현재 ticket의 완료 보고와 실제 테스트 요청으로 잇고 ticket 없는 조회는 담당 agent의 ticket 준비로 잇는다.
- 이유: 고쳤다는 주장과 machine 확인을 구별하면서 다음 행동을 찾게 한다.
- 확인: 안내가 상한을 지키고 연결된 요청이 실제 동작하며 coding agent가 문제를 대신 닫도록 안내하지 않는다.
- 의도: coding-agent#I7, coding-agent#I5

**[R11]** 문제 summary는 문제당 2줄·전체 10줄·1,200자 이하로 제공하고 전체 묶음과 추가 텍스트 페이지는 UTF-8 24 KiB(24,576 bytes)와 300줄을 모두 지킨다.
- 이유: 요약·전체·추가 읽기의 비용을 통로에 관계없이 제한한다.
- 확인: 다국어와 한 줄짜리 큰 자료에서도 요약과 두 전체 상한을 지키며 ticket의 모든 문제를 합산하고 누락 표시·이어 읽기 안내도 예산에 포함한다.
- 의도: coding-agent#I7

**[R12]** 전체 상한을 넘으면 log·대표 발생 excerpt·첨부 metadata 순으로 줄이고 각 생략 지점에 잘림·원래 범위·실제 추가 읽기를 남기며 그래도 넘치면 필수 참조와 상태를 보존한 채 나머지를 이어 읽기로 바꾼다.
- 이유: 작게 반환하면서 조용한 근거 손실을 막는다.
- 확인: 큰 log와 여러 문제·첨부를 넣으면 축소 순서와 각 누락 위치가 확인되고 나머지를 읽을 수 있으며 Unicode와 JSON 구조가 깨지지 않는다.
- 의도: coding-agent#I7

### 대표 근거 선정

**[R13]** 대표 발생은 첫·마지막·고정 근거가 가장 다른 발생을 중복 없이 최대 3개 고르고 동일 후보에서는 먼저 접수된 발생을 우선해 같은 자료에서 같은 결과를 낸다.
- 이유: 반복 전체 대신 처음과 최근 및 근거 차이를 볼 수 있어야 한다.
- 확인: 같은 발생 자료를 반복 조립해 대표 순서가 같고 첫 발생과 마지막 발생이 같으면 중복이 없다.
- 의도: coding-agent#I7

**[R14]** 직전 변화는 첫 발생 시각 7일 전부터 조회 현재까지 중 첫 발생 시각에 가까운 순서로 최대 12개를 선택하고 같은 거리에서는 먼저 기록된 변화를 우선하되 원인으로 단정하지 않는다.
- 이유: 원인 판단용 변화와 실제 인과 판정을 구별한다.
- 확인: 기간 경계와 같은 거리 변화를 넣어 결정적 순서를 확인하고 자료에 원인이라는 확정 표현이 생기지 않는다.
- 의도: coding-agent#I7

### 추가 근거

**[R15]** 추가 근거는 종류를 지정한 요청에서만 log 200줄·발생 목록 20개·source diff 300줄·화면 텍스트 24 KiB까지 페이지로 제공하며 초과 목록과 텍스트는 조건을 유지하는 cursor로 이어 읽게 한다.
- 이유: 기본 묶음을 작게 유지하면서 필요한 자료 전체에 닿게 한다.
- 확인: 각 상한 초과 자료에서 페이지 제한과 추가 cursor가 있고 같은 조건으로 이어 읽으면 누락·중복 없이 실제 보존 근거를 읽는다.
- 의도: coding-agent#I7

**[R16]** source diff는 첫 발생 전 고정 release와 현재 고정 release의 변경 통계 및 관련 source 차이를 제공하고 보존 근거가 없으면 없는 이유를 표시하며 현재 임의 파일을 당시 증거로 보충하지 않는다.
- 이유: 현재 변화와 당시 source의 차이를 과거 사실로 오인하지 않게 한다.
- 확인: 두 release의 통계·diff가 300줄 안에 나오고 source 보존이 없는 사례에서는 없는 이유와 읽을 근거만 나온다.
- 의도: coding-agent#I7

**[R17]** 이미지는 redaction 뒤 하나당 2 MiB(2,097,152 bytes)까지 제공하고 이미지 미지원 통로에는 허용된 로컬 첨부 열기 참조·종류·크기를 알려 coding-agent/cli로 확인하게 한다.
- 이유: 이미지 지원 여부로 수리 근거가 사라지거나 운영 경로가 새면 안 된다.
- 확인: 이미지 지원 MCP와 텍스트 전용 세션에서 같은 허용 첨부를 찾고 큰 이미지는 크기·미제공 이유가 나오며 base64로 텍스트 상한을 우회하지 않는다.
- 의도: coding-agent#I7

### 정합성과 안전

**[R18]** summary·전체 묶음·추가 근거는 같은 문제·Report·snapshot·release와 사실을 가리키고 없음·부분 수집·미검증·redaction·범위 거절·잘림을 요약에서도 숨기지 않는다.
- 이유: 자료가 없다는 것과 당시 이상이 없었다는 것은 다르다.
- 확인: 누락과 미검증 근거가 있는 문제를 summary만 읽어도 그 한계가 보이고 추가 조회가 다른 사실로 바뀌지 않는다.
- 의도: coding-agent#I7, coding-agent#I5

**[R19]** 묶음과 추가 페이지·첨부마다 coding-agent/connection 범위를 검사하고 platform/redaction 및 platform/security를 적용해 사람 말·앱 문자열·log 원문은 명시 data fence 안에 두고 agent 해석과 구별한다.
- 이유: 자료에 담긴 지시나 근거 주소가 권한과 판단을 바꾸면 안 된다.
- 확인: 범위 밖 고정 주소와 비밀·악성 지시를 넣어도 밖의 내용과 비밀이 텍스트·JSON·이미지에 없고 인용 자료와 해석이 구별된다.
- 의도: coding-agent#I7, coding-agent#I2

**[R20]** 수리 자료 읽기는 claim·문제·ticket 상태를 바꾸지 않고 전체 raw log 전송을 기본값으로 삼지 않는다.
- 이유: 읽기와 착수·갱신을 구별하고 불필요한 자료 노출을 줄인다.
- 확인: 반복 읽기 전후 claim 기한과 상태가 같고 기본 응답에는 bounded log excerpt만 있다.
- 의도: coding-agent#I7, coding-agent#I8
