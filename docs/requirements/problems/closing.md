# problems/closing

현재 사용 중인 앱에서 문제를 닫을 근거와 사람 확인을 정하고, 테스트 확인·사람 확인·현상이 안 보임·더 다루지 않음을 구별하며 닫힌 뒤 현재 release의 재발을 같은 문제로 다시 연다.

## 요구

### 닫힘 권한과 근거

**[R1]** 문제 닫힘은 machine의 실제 reproduction 판정 또는 shell/confirmation-window의 사람 결정으로만 하며 coding agent·lophn agent·앱의 닫기·무시·사람 대신 확인은 거절한다.
- 이유: 고친 쪽의 주장과 자기 평가가 최종 확인을 대신해서는 안 된다.
- 확인: 각 agent와 앱·일반 CLI의 사람 주장으로 닫기를 시도하면 거절되고 실제 machine 판정 또는 보호된 결정만 적용된다.
- 의도: problems#I3

**[R2]** release 준비·activation·앱 시작·일반 command 성공·app test·test command 통과·ticket 완료·고친 기록·앱의 해소 주장만으로는 문제를 닫지 않는다.
- 이유: 배포·실행 성공·증상 회복·수리 검증은 서로 다른 사실이다.
- 확인: 각 신호만 차례로 만들어도 열린 문제가 테스트로 확인됨으로 닫히지 않는다.
- 의도: problems#I3

### 테스트로 확인됨

**[R3]** 테스트로 확인됨으로 닫는 판정은 problems/tests의 reproduction 통과 결과만 사용하고 app test·test command 결과나 agent의 통과 주장으로 대신하지 않는다.
- 이유: 처음부터 성공한 테스트나 실패를 숨긴 변경은 수리 증거가 아니다.
- 확인: problems/tests의 reproduction 통과 조건을 충족하지 못한 결과는 자동 닫힘으로 쓰지 않는다.
- 의도: problems#I3

**[R4]** 자동 닫힘에는 reproduction을 통과한 고친 release가 현재 활성화되어 있고 테스트 요청 때 읽은 문제 기준 뒤 같은 문제의 새 운영 보고가 0개여야 한다.
- 이유: 낡은 결과로 현재 재발을 숨기지 않는다.
- 확인: 고친 release가 아닌 앱을 사용하거나 요청 뒤 새 보고가 1개라도 있으면 자동 닫힘을 거절하고 이전 release의 늦은 새 보고도 재평가한다.
- 의도: problems#I3

**[R5]** 자동 닫힘의 최소 quiet 대기 기간은 0ms이고 결과의 날짜 기반 유효기간은 두지 않되 현재 문제 기준과 활성 release가 바뀌면 다시 판정한다.
- 이유: 근거가 충분할 때 불필요한 대기를 만들지 않지만 오래된 기준은 사용하지 않는다.
- 확인: 모든 재현·activation·무새보고 조건이 맞으면 추가24시간 대기 없이 닫히고 낡은 상태로 보낸 판정은 충돌한다.
- 의도: problems#I3

### 사람의 확인

**[R6]** 사람의 고쳐짐 확인은 지금 쓰는 release와 보인 문제 기준에 묶인 일회 결정으로 닫고 실제 reproduction 통과를 만들거나 대신 기록하지 않는다.
- 이유: 사람이 확인한 수리와 machine 확인의 근거를 구별한다.
- 확인: 사람이 고쳐졌다고 확인하면 내가 확인함으로 보이며 test result가 새로 생기지 않고 결정 재사용·release 변경 뒤 적용은 거절된다.
- 의도: problems#I3

**[R7]** 현상이 안 보임으로 닫는 것은 사람이 현재 release와 마지막 보고를 보고 보호 화면에서 확인한 경우뿐이며 특정 코드 변경이 고쳤다고 표시하지 않는다.
- 이유: quiet나 회복 신호만으로 recovered를 자동 만들지 않는다.
- 확인: 새 보고 없이72시간이 지나도 열림이고 사람이 현상이 안 보임을 선택해야 그 근거로 닫힌다.
- 의도: problems#I3

**[R8]** 더 다루지 않음과 오탐 판단은 사람이 보호 화면에서 공백 아닌 한 줄 이유를 남겨 닫으며 수리 성공으로 표시하거나 별도 자동 오탐 문제를 만들지 않는다.
- 이유: 무시한 이유와 검증된 수리를 섞지 않는다.
- 확인: 빈 이유는 거절되고 오탐의 기대 기준·판단 이유를 남길 수 있으며 로그 부재만으로 고쳐졌다고 하지 않는다.
- 의도: problems#I3

**[R9]** reproduction을 만들 수 없는 코드 수리도 ticket과 claim을 거쳐야 하며 그 닫힘은 보호 화면에서 사람이 “내가 확인함”으로 남긴 확인을 acceptance check로 쓰되 테스트 통과와 구별하고 다른 테스트 통과나 ticket·session 완료를 자동 수리 확인으로 바꾸지 않는다.
- 이유: 재현 테스트를 만들 수 없는 수리도 사람의 확인으로 닫을 수 있어야 하지만 그 확인을 machine 통과로 꾸미지 않는다.
- 확인: 보호된 사람 확인과 문제 닫힘 근거를 별도로 보존하고 이 닫힘은 내가 확인함으로 보이며 테스트로 확인됨으로 표시되지 않는다.
- 의도: problems#I3

**[R10]** 사람이 “아직입니다”라고 하면 열린 문제는 닫지 않고 닫힌 문제는 다시 열며 같은 release에 같은 확인을 반복 요청하지 않는다.
- 이유: 부정 확인을 실패나 무응답으로 처리하고 다시 압박하지 않는다.
- 확인: 아직입니다 뒤 열림이 보이고 새로운 고친 release나 새 근거가 있을 때만 다시 고쳐짐 확인을 요청한다.
- 의도: problems#I3

### 닫힌 뒤 재발

**[R11]** 닫힌 문제의 같은 분류로 현재 활성 release에서 운영 보고가 접수되면 경과 기간과 닫힘 이유에 관계없이 같은 문제를 다시 연다.
- 이유: 이전 수리와 닫힘의 근거를 재발에서도 잃지 않는다.
- 확인: 15일이 지난 재발과 더 다루지 않음 뒤 재발도 같은 문제로 열리고 이전 닫힘 근거·고친 기록이 남는다.
- 의도: problems#I3

**[R12]** 이전 release의 늦은 운영 보고는 기존 문제에 남기되 현재 release의 재발로 다시 열지 않는다.
- 이유: 과거 자료 도착을 현재 앱 실패로 오해하지 않는다.
- 확인: 현재 release에서 닫힌 뒤 이전 release 보고를 접수하면 보고는 읽히지만 현재 문제 상태는 닫힘이다.
- 의도: problems#I3

### 정직한 화면과 판정

**[R13]** 닫힌 문제는 테스트로 확인됨·내가 확인함·현상이 안 보임·더 다루지 않음을 구별하고 기본으로 닫힌 이유와 지금 필요한 주의만 보여 주며 실제 확인 범위·미확인 부분·release·근거는 펼친 상세에서 읽을 수 있고 release는 화면에서 사람이 아는 영어로 설명한다.
- 이유: 원인이나 모든 입력의 정상화까지 증명된 것처럼 보이면 안 된다.
- 확인: 4종 닫힘이 각각 다르게 보이고 미실행 테스트·외부 효과 미확인·발생 기회 없음은 성공으로 채워지지 않는다.
- 의도: problems#I3, shell#I1

**[R14]** 문제 확인의 적용은 최신 문제 기준과 활성 release를 다시 비교하고 그 뒤 바뀐 보고·ticket·release를 오래된 판정으로 덮어쓰지 않는다.
- 이유: 동시 보고와 확인에서 실제 재발이 닫힘 뒤에 숨지 않아야 한다.
- 확인: reproduction 결과·activation·새 보고를 동시 처리해도 낡은 닫기 요청은 충돌하고 확인 근거가 없는 전이는 거절된다.
- 의도: problems#I3
