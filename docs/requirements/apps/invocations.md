# apps/invocations

앱 명령과 automation 한 번의 invocation에서 당시 release와 실제 결과를 되짚게 하고, 일반 호출의 응답 뒤 비동기 기록과 유실 표시, 사람 확인이 필요한 명령의 선행 접수와 approval 한 번 사용을 맡는다.

## 요구

### 직접 호출과 후행 기록

**[R1]** 일반 앱 호출은 apps/runtime의 직접 호출 통로에서 응답하고 invocation 기록은 응답 뒤 비동기로 남긴다.
- 이유: ledger 지연이 앱 업무 응답까지 붙잡지 않게 한다.
- 확인: 기록 저장을 지연시켜도 화면·CLI·agent의 일반 호출 응답이 먼저 돌아오고 그 뒤 기록이 반영된다.
- 의도: apps#I5, platform#I3

**[R2]** 확인이 필요한 명령, 업무 변경·외부 효과 명령, automation의 읽기 포함 모든 호출, 실패·거절된 읽기 명령, 앱 시작과 데이터 변경은 invocation을 남기되 화면 byte 조회와 성공한 일반 읽기는 매번 남기지 않는다.
- 이유: 수리에 필요한 변경과 실패는 남기면서 성공 조회의 과다 기록을 피한다.
- 확인: 각 종류를 호출한 뒤 기록 대상을 찾을 수 있고 성공한 일반 읽기 100회가 같은 수의 invocation을 만들지는 않는다.
- 의도: apps#I5

**[R3]** invocation에서는 당시 앱·release·호출 대상·직접 호출이나 automation 등 계기·운영이나 preview·인증된 원래 호출자·실제 시작과 종료 결과를 찾을 수 있다.
- 이유: 현재 코드와 당시 코드, 사람이 요청한 일과 machine의 회차를 구분한다.
- 확인: release를 교체한 뒤 과거 invocation을 열어도 당시 대상과 계기 및 실제 호출자가 유지되고 앱이 입력으로 내세운 사람 이름으로 바뀌지 않는다.
- 의도: apps#I5

**[R4]** 명령 경계 한 번에는 invocation 하나를 연결하고 진행·취소 요청도 같은 호출에 연결하되 내부 helper와 trace를 별도 invocation으로 만들지 않는다.
- 이유: 업무 한 번과 내부 계측 조각을 혼동하지 않는다.
- 확인: 내부 helper 10개를 부르는 명령에서 invocation은 하나이며 그 명령의 진행과 취소를 같은 호출로 따라갈 수 있다.
- 의도: apps#I5

**[R5]** 이미 끝난 업무의 성공·실패는 후행 진단이나 invocation 전달 실패 때문에 바꾸지 않고 기록 메시지만 제한된 메모리에서 backoff 재전송한다.
- 이유: 관측 실패가 업무 실패나 업무 retry로 바뀌어서는 안 된다.
- 확인: 업무가 성공한 뒤 기록 전달을 끊으면 응답은 성공으로 유지되고 명령은 반복되지 않으며 기록 메시지만 다시 보내고 한도 초과 손실은 platform/diagnostics로 드러난다.
- 의도: apps#I5

**[R6]** 같은 invocation의 같은 사실을 재전송하면 같은 기록을 반환하고 확정한 종료 결과와 충돌하는 늦은 사실은 거절한다.
- 이유: 중복 전달이나 역순 전달이 이력을 늘리거나 과거 결과를 바꾸지 않게 한다.
- 확인: 종료 통보를 반복 보내도 결과가 하나이며 종료 뒤 시작 통보나 다른 종료 결과를 보내도 진행 중이나 새 성공으로 바뀌지 않는다.
- 의도: apps#I5

### confirm 명령

**[R7]** 사람 확인이 필요한 명령은 호출자 종류와 관계없이 사람이 확인한 정확한 release·명령·기본값을 적용한 입력에 묶인 approval을 실행 직전의 접수와 함께 한 번만 사용한다.
- 이유: apps/invocations에 따라 승인하지 않은 판이나 입력과 중복 호출에 사람 결정을 쓰지 않는다.
- 확인: 승인과 접수 저장이 함께 확정되기 전 handler는 호출되지 않고 저장 실패에서는 실행되지 않으며 같은 접수 재전송은 기존 접수만 반환한다.
- 의도: platform#I7

**[R8]** 접수 뒤 같은 confirm 호출을 재전송하거나 프로세스를 다시 시작해도 handler를 중복 실행하지 않고 release·명령·입력이나 프로세스가 달라지면 원래 확인으로 실행하지 않는다.
- 이유: 응답 유실과 프로세스 교체가 한 번 승인한 효과를 다시 만들지 않게 한다.
- 확인: 같은 접수를 동시에 보내면 handler가 1회만 돌며 옛 프로세스의 실행 증명을 새 프로세스에 보내거나 입력을 바꾸면 거절된다.
- 의도: platform#I7

**[R9]** confirm 접수는 실제 시작과 구분해 보여 주고 시작과 결과는 실제 관측 뒤 후행 기록으로 남긴다.
- 이유: 먼저 저장한 접수를 이미 실행했다는 증거로 꾸미지 않는다.
- 확인: 접수만 확정하고 handler 시작을 지연시키면 접수됨만 보이며 실제 시작 시각은 접수 시각으로 채워지지 않는다.
- 의도: apps#I5

### 결과의 한계와 유실

**[R10]** 시작이나 결과를 확인할 수 없는 알려진 invocation은 미확인으로 표시하고 기록 자체가 없거나 연결할 호출을 모르면 그 부재를 표시한다.
- 이유: 기록 없음은 미실행·성공·0회가 아니다.
- 확인: 결과 전달 전 프로세스를 종료하면 미확인이나 기록 없음이 드러나고 모르는 호출의 가짜 invocation을 생성하지 않는다.
- 의도: apps#I5

**[R11]** 실패·timeout·중단·취소 요청 접수는 부분 DB 저장이나 외부 효과가 없다는 뜻으로 표시하지 않는다.
- 이유: 이미 저장하거나 전송한 일이 오류 응답 뒤에도 남을 수 있다.
- 확인: 로컬 저장 뒤 외부 전송이 실패한 명령에서 저장 완료와 전송 실패를 따로 찾고 취소 요청만 받은 상태를 외부 효과 취소 완료라고 보이지 않는다.
- 의도: apps#I5

**[R12]** 결과 미확인과 invocation 기록 누락을 이유로 업무를 자동 재실행하지 않으며 기록만으로 외부 효과의 exactly-once를 주장하지 않는다.
- 이유: 응답 유실을 중복 전송으로 해결해서는 안 된다.
- 확인: 외부 전송 뒤 응답을 끊으면 같은 전송이 자동 반복되지 않고 존재하는 외부 확인 근거와 모르는 단계가 구별된다.
- 의도: apps#I5

**[R13]** invocation 성공은 handler 반환과 경계 계약 만족만 뜻하며 업무 집계 정확성이나 problem 닫힘을 대신하지 않는다.
- 이유: 틀린 합계를 정상 응답한 앱을 올바르다고 판정하지 않는다.
- 확인: 형식은 맞지만 집계 값이 틀린 응답을 성공 invocation으로 남겨도 업무 정확성 확인과 problems/closing의 판정은 별도로 남는다.
- 의도: apps#I5

**[R14]** 읽기 명령 결과는 정상 0행과 원천 미수집·부분 범위·신선도 부족을 구분하고 페이지 이어 읽기는 처음 조건·정렬·데이터 기준이 바뀌면 거절한다.
- 이유: 빈 결과를 완전한 수집 성공으로 읽거나 서로 다른 목록을 한 결과로 섞지 않는다.
- 확인: 미수집과 실제 0행의 응답이 다르고 기간이나 정렬을 바꾼 뒤 원래 이어 읽기를 재사용하면 거절된다.
- 의도: apps#I5

**[R15]** invocation 상세와 요약은 platform/redaction을 따르며 문서 저장을 포함한 명령의 저장 성공은 documents/versions를 따른다.
- 이유: 후행 관측이 비밀을 노출하거나 invocation 기록만으로 문서 저장 성공을 대신하지 않는다.
- 확인: 실패 상세에서 secret 원값을 찾을 수 없으며 문서 확정이 실패하면 invocation 전달 여부와 무관하게 문서 저장 성공이라고 응답하지 않는다.
- 의도: platform#I2, documents#I2

### 다른 앱과 agent 출처

**[R16]** 다른 앱 또는 agent가 부른 invocation은 인증된 부른 앱과 당시 release 또는 agent run과 tool call을 남기며 알려진 부모 invocation은 연결하고 모르는 출처를 만들어 채우지 않는다.
- 이유: 대상 앱의 결과에서 누가 어떤 업무로 호출했는지 되짚는다.
- 확인: A→B와 agent→B 기록을 구별하고 A release 교체 뒤에도 당시 출처가 유지되며 부모 기록이 없으면 없음으로 보인다.
- 의도: apps#I11, apps#I5

**[R17]** 앱 쌍 허락과 agent 허락은 invocation의 원래 caller를 사람으로 바꾸지 않고 confirm approval의 사람 결정과 실제 요청자를 따로 남긴다.
- 이유: 사람이 허락했다는 사실과 사람이 직접 호출했다는 사실을 섞지 않는다.
- 확인: agent나 A가 요청한 confirm 호출을 사람이 승인해도 요청자는 agent나 A이고 approval은 별도 참조다.
- 의도: apps#I11, apps#I5

**[R18]** 다른 앱과 agent가 부른 일반 command도 R1·R2의 후행 기록과 기록 대상 규칙을 따르며 confirm은 호출자 종류와 관계없이 정확한 대상·입력의 approval을 선행 접수에 한 번 사용한다.
- 이유: 새로운 caller가 응답 지연·유실·중복 실행 규칙을 바꾸지 않는다.
- 확인: A→B와 agent→B의 일반 성공 read에는 매번 기록이 생기지 않고 write 기록은 응답 뒤 남으며 confirm 접수 저장 실패에는 handler가 실행되지 않는다.
- 의도: apps#I11, platform#I7

**[R19]** confirm 실행 marker는 프로세스당 4096개, 후행 기록 전달 목록은 전체 4096 메시지 또는 8MiB 중 먼저 닿는 한도, redaction한 summary는 UTF-8 최대 16KiB로 제한하고 전달의 unavailable만 1초·2초·4초부터 최대 30초 backoff로 재전송한다.
- 이유: R5·R8의 유한 메모리와 중복 실행 방지를 실제 한도로 검사한다.
- 확인: marker가 가득 차면 유효한 기존 marker를 버리지 않고 새 접수를 거절하며 전달 한도 초과는 안전한 손실 진단을 남기고 unauthorized·conflict·invalid_input은 반복하지 않는다.
- 의도: apps#I5, platform#I3

## 열린 질문

- apps/invocations#Q1 일반 후행 기록을 현재 제한된 메모리 재전송보다 더 오래 보장할 durable 전달 보관이 필요한가?
- apps/invocations#Q2 전체 운영 통계를 위한 호출·실행 기회·실패 분모와 계측 공백의 별도 집계를 제공할까?
- apps/invocations#Q3 confirm 실행 증명의 기한을 platform/identity와 얼마로 정하고 R19의 marker·전달 용량·summary·backoff 기본값을 실측 뒤 조정할 필요가 있을까?

## 버린 것

- 모든 호출에 다단계 실행 허가와 다중 credential·세대·기한 envelope를 강제하는 장치: 현재 직접 호출과 필요한 invocation·release·actor로 줄인다.
- 일반 호출 전 idempotency ticket 발급·client 보관·만료 영수증과 모든 write·external의 영구 접수·영구 결과 뒤 응답: apps/invocations의 confirm 접수 외에는 선행 기록 없이 응답한다.
- 앱별 독립 journal, 선행 Binding 접수와 span·외부 receipt 필수 entity, 24시간·16MiB/app 상세 journal: 단일 ledger를 앱별 host 저장소로 나누지 않는다.
- 공통 요구의 일반 비동기 기록·confirm 선행 접수 별도 항목: 없앤 동작이 아니라 R1·R7로 합쳐 한 concern이 소유한다.
