### 아직 정하지 않은 것

- Router가 core process에 사는지 agent-runtime에 사는지. 03이 같은 물음을 올렸다. Router 입력(사람 메시지, call, reaction)이 core에서 생기고 run-loop 입력함은 agent-runtime에 있다.
- agent-runtime의 run-loop가 내는 agent event를 core의 Bus로 넘기는 길(감독 pipe, loopback API, 공유 메모리 없음). Bus는 core 메모리, run-loop는 다른 process다.
- Gate를 어느 process에서 부르는지와 grant 읽기(ledger)를 어디서 하는지. Gate는 IO 없는 함수라 계산은 어디서든 되지만, 입력인 grant를 어디서 읽는지가 비어 있다.
- 입력함이 durable인지(03). lophn이 꺼졌다 켜진 뒤 대기 입력이 남는지는 coding agent만 "버려진다"가 명시됐다.
- agent-runtime의 Deno 권한 목록. S4의 file(read·write·edit·glob·grep)·shell·web tool은 place 폴더 쓰기, 프로세스 실행, 임의 host network를 요구하는데 지금 목록은 data root 읽기와 등록 host·MCP stdio만 허락한다. 도구를 같은 process에서 돌릴지, 권한이 넓은 별도 process를 둘지 정해지지 않았다. 환경 변수는 필요한 것만 넘기고 token과 secret은 넣지 않는다(S4)는 규칙은 shell tool을 띄우는 쪽에서 지켜야 한다.
- Harness adapter가 도는 process와 Router→PTY 입력 경로(core에서 shell main으로, 다시 terminal-host로). hook은 CLI→core loopback이다(S6 4장).
- secret 파일을 읽고 쓰는 process(I/O worker에 남기는지, core가 직접 하는지). 값은 이미 core 보호 메모리에 올라 있다(`openSecretStore`의 held).
- 설정 파일의 형식, 위치, 변경을 쓰는 요소에 알리는 방법. ledger를 거치지 않으니 `SettingsChanged` 같은 깨움이 없다.
- 설정 항목의 화면 이름과 설명을 어디서 얻는지.
- 단일 instance lock과 data root 권한 검사(0700)를 install-and-update 보류에 넣는지. 추천은 둘 다 core 시작에 필요하므로 남긴다.
- `ledger-id` 파일을 복원이 없어진 뒤에도 두는지(derived 무효화와 구독 저장소가 쓴다).
- 이 process 구성이 "lophn이 꺼지면 coding agent PTY process도 끝난다"(S1 10장)와 어떻게 맞는지는 shell main이 부모라 맞는 것으로 보이나 core 쪽 회수 순서는 확인 못함.
