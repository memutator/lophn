# lophn-agent/evaluation

실제 model로 역할의 판단 품질을 재는 개발 도구의 fixture·eval suite·채점·비교를 맡는다; 제품 화면이나 제품 ledger의 domain entity가 아니며 모델 없는 결정적 회귀는 각 concern의 테스트가 맡는다.

## 요구

### fixture와 격리

**[R1]** 평가 사례 하나는 한 종류의 일을 다루며, 시작할 문서·앱·세션과 그 버전, 입력할 의도, 평가할 역할 정의, 줄 도구와 권한, 사람이 답할 내용, 반드시 생길 결과, 생기면 안 되는 변경, 실행 방식, 제한 시간, 판정 기준을 실행 전에 정한다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 문서를 바꾸는 사례에서 시작 버전과 기대한 변경 및 금지한 변경을 결과를 보기 전에 읽을 수 있고, 사람 답이 없는 질문을 임의로 승인하지 않는다.

**[R2]** eval suite을 시작하기 전에 machine은 사례 이름의 중복, 빠진 시작 자료, 빠진 판정 기준, 0 이하의 반복 횟수와 제한 시간을 검사하고, 하나라도 있으면 모델을 부르지 않고 평가 준비 오류로 끝낸다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 같은 이름의 사례 둘과 시작 자료가 없는 사례를 각각 넣으면 모델 호출이 0회이고 어떤 준비가 잘못됐는지 나온다.

**[R3]** fixture와 판정 기준은 버전이 있는 개발 자료로 관리하고 새 버전 채택·사례 제외·suite 이동은 사람이 정하며 평가 대상 agent는 이를 바꾸지 못하고 제품 ledger의 entity로 저장하도록 강제하지 않는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 실패 직후 agent가 기대를 자기 결과에 맞춰 바꾸려 하면 막히고, 사람이 기대를 바꿔도 이전 판정은 이전 사례 버전을 계속 가리킨다.

**[R4]** eval suite은 이미 검증된 일을 지키는 regression suite과 아직 해내지 못한 일을 재는 capability suite로 나누고, 능력 사례가 최근 3번의 실제 모델 평가에서 매번 5회 모두 통과한 경우에만 사람에게 regression suite 이동 후보로 제시한다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 15회 중 1회라도 실패하거나 판정하지 못하면 이동 후보가 되지 않고, 15회 모두 통과해도 사람이 채택하기 전에는 capability suite에 남는다.

**[R5]** 공통 평가에는 이름이 같은 문서 2개, 이미 반영된 변경, 바꿀 후보 2개, 대소문자만 다른 검색어, 접힌 섹션의 자료, 잘린 도구 결과, 문서 2개에 걸친 일, 권한 밖 변경, 한 번에 읽을 수 없는 큰 문서의 9가지 함정을 넣고, 각 함정에서 필요한 결과와 금지할 변경을 따로 판정한다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 이름이나 변경 후보가 모호한 사례는 지정된 사람 답으로 대상을 확정하며, 잘린 결과와 큰 문서는 빠진 근거를 찾았는지로 판정하고 특정 읽기 순서로 채점하지 않는다.

**[R6]** 권한 거절·approval 대기 중 취소·model 응답 중 취소·run 중 새 입력·외부 MCP 결과의 지시 인젝션을 각각 별도 공통 regression 사례로 둔다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 각 사례에서 lophn-agent/harness/tool-judgment·lophn-agent/harness/safety·lophn-agent/harness/run-loop의 경계를 어기는 부작용이 없음을 검사한다.

**[R7]** 매 시행은 격리된 fixture 폴더·DB에 시작 자료를 새로 복사하여 시작하고 운영 데이터·자격 증명·MCP 연결을 읽지 않으며 앞 시행의 세션·문서 변경·문맥·승인을 다음 시행에 넘기지 않는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 첫 시행이 자료를 바꾸고 승인해도 두 번째 시행에서는 원래 자료와 미승인 조건으로 시작하며, 운영 중인 문서와 자격 증명은 변하지 않는다.

**[R8]** 바깥 MCP 동작은 평가 전용 가짜 서버로 대신하되 도구 분류와 호출별 권한 판정은 lophn-agent/extensions와 lophn-agent/harness/tool-judgment을 그대로 따르고, 승인·거절은 사례에 적힌 사람 답만 제공한다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 같은 쓰기 호출에 승인과 거절을 주는 두 사례에서 가짜 MCP의 부작용이 각각 1회와 0회이며, 사람이 연결하지 않은 서버를 agent가 평가 중 연결하면 실패한다.

### 판정과 비교

**[R9]** machine은 먼저 최종 문서·앱 동작·상태 변경과 금지한 부작용을 검사하고, 성공했다고 한 응답 문장이나 세션 전문의 문자열 일치 및 도구 호출의 정확한 순서는 통과 기준으로 쓰지 않는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 성공이라고 답해도 기대 문서가 없으면 실패하고, 다른 도구 순서로 같은 유효 결과를 내고 금지한 변경이 없으면 같은 판정을 받는다.

**[R10]** 판정은 준비 자료의 검사, 실제 출력의 형식 검사, 결과와 금지 변경 검사, 필요한 내용 판단의 순서로 진행하고, agent가 만든 잘못된 인자·결과·문서 형식은 품질 실패로 세며 평가 자료나 판정기의 결함은 평가 오류로 분리한다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 시작 자료가 깨진 시행은 평가 오류이고, 유효 자료를 받은 agent가 형식에 안 맞는 문서를 남긴 시행은 실패이며, 두 경우 모두 내용 판정 모델을 부르지 않는다.

**[R11]** 시행 결과는 기대 충족, 기대 불충족, 평가 오류, 판정 근거 부족을 구분하고, 예상 밖 provider 장애·평가 프로세스 중단·재생 오류를 통과로 처리하거나 성공할 때까지 다시 돌려 최초 결과를 지우지 않는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 예상 밖 장애가 난 시행은 기대 불충족과 다른 이유로 남고, 사람이 다시 돌려 성공해도 앞선 오류 결과는 남으며, 오류 복구를 일부러 테스트하는 사례는 정한 복구 결과로 판정한다.

**[R12]** 실제 모델의 회귀 사례는 3회, 실제 모델의 능력 사례는 5회 같은 시작 조건에서 시행하며, regression suite은 모든 사례의 모든 시행이 통과해야 통과한다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 실제 회귀 사례가 3회 중 2회 통과하면 실패하고, 능력 사례의 5회 결과는 전부 표시되며 성공한 시행 하나만 고를 수 없다.

**[R13]** eval suite은 예정 시행 수·통과 수·실패 수·평가 오류 수·판정 근거 부족 수를 따로 내고, 평가 오류나 판정 근거 부족 또는 빠진 시행이 하나라도 있으면 전체 통과율과 변경 전후 차이를 숫자로 내지 않는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 예정 10회 중 9회 통과하고 1회 중단되면 100%라고 하지 않으며, 9회의 결과와 1회의 중단 이유는 각각 남는다.

**[R14]** 내용 판정 모델은 machine이 판정하지 못한 이해하기 쉬움과 제공된 근거에 충실함의 2가지 축만 각각 판단하고, 축마다 질문·충족과 불충족의 경계를 미리 정해 결과 문서와 그 근거 문서만 준다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 도구 오류나 문서 형식은 내용 판정 모델이 덮어쓰지 못하고, 근거에 없는 주장 하나를 넣으면 근거 충실함 축으로만 판정한다.

**[R15]** 내용 판정 모델의 답은 충족·불충족·판단 불가의 3가지 중 하나만 받아들이고, 다른 답은 1회만 다시 물으며, 두 번째도 잘못됐거나 필요한 근거가 없으면 해당 축을 판정 근거 부족으로 남긴다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: '충족 같지만 확신이 없다'는 답을 충족으로 읽지 않고, 근거가 빠진 입력에서 판단 불가를 실패 또는 통과로 바꾸지 않는다.

**[R16]** 내용 판정 모델은 평가 대상과 다른 모델을 명시적으로 배정하고, 모델이나 판정 기준을 처음 쓰거나 바꾸면 축마다 사람이 확정한 30개 결과에서 24개 이상 일치하기 전에는 그 모델의 판정을 통과 근거로 쓰지 않는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 모델 배정이 없거나 30개 중 23개만 일치하면 해당 축은 통과 근거가 되지 않으며, 사람 둘의 답이 다른 항목은 질문을 다듬기 전까지 30개에서 제외한다.

**[R17]** 보정한 내용 판정 모델은 실제 모델 eval suite 10회마다 축별로 최근 판정 5개를 사람에게 다시 확인받고, 2개 이상 다르면 그 축을 통과 근거에서 빼고 30개 보정을 다시 한다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 점검에서 5개 중 2개가 다르면 다음 eval suite에서 해당 축만 판정 근거 부족으로 남고, machine 판정은 계속 유효하다.

**[R18]** 각 eval suite은 사례와 시작 자료의 버전, 실행 방식, 제품 버전, 역할 정의·프롬프트·skill·도구·권한의 버전, provider와 모델, 샘플링 조건, 판정 모델과 기준, 반복 수를 시작 때 고정하고 종료 뒤 결과와 함께 되짚을 수 있게 남긴다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: skill이나 판정 기준이 바뀐 두 결과를 같은 조건의 결과라고 합치지 않고, 종료 후 사례를 고쳐도 당시 조건을 찾을 수 있다.

**[R19]** 변경 전후 비교는 한 번에 조건 1개만 바꾸고 같은 사례·시작 자료·반복 수·판정 기준으로 별도 fixture 작업 공간에서 실제 모델을 돌리며, 홀수 반복은 변경 전을 먼저, 짝수 반복은 변경 후를 먼저 시행한다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 모델과 프롬프트를 동시에 바꾼 비교는 시작 전에 거절되고, 3회 비교의 실행 순서는 전·후, 후·전, 전·후이며, 어느 쪽도 상대가 남긴 결과를 읽지 않는다.

**[R20]** 평가 결과는 시행별 기대와 실제 결과, 실패하거나 판단하지 못한 이유, 관측의 근거 연결을 제공하고, 모델 호출 수·도구 호출 수·도구 오류 수·같은 인자의 재호출 수·잘린 도구 결과 수를 비교용으로만 센다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 호출 수가 줄어도 기대한 일을 못 하면 실패이고, 실패한 시행 하나에서 기대 문서·실제 문서·판정 이유·해당 실행 근거를 찾을 수 있다.

**[R21]** 평가는 정해진 주기로 자동 실행하지 않고, 모델 없는 결정적 회귀는 평가가 아니라 관심사마다 명세에 딸린 테스트이 맡는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: eval suite은 사람의 명시적 요청 없이 시작되지 않고, 가짜 provider로 도는 회귀는 평가 결과에 섞이지 않는다.

**[R22]** 실제 모델 회귀·능력 평가·변경 전후 비교는 사람이 실행을 지시할 때만 돌리고, 프롬프트·모델·역할 정의·skill·도구 제공·권한 적용·문맥 조립 중 하나가 바뀌면 적용 전에 영향을 받는 실제 회귀 사례를 다시 확인하며, 결과가 없거나 실패하거나 불완전하면 품질이 유지됐다고 인정하지 않는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 자정 평가에서 실제 provider 호출은 0회이며, 변경 전에 오프라인 테스트만 통과한 결과는 실행 제어 확인으로만 인정하고 실제 판단 품질 확인은 미실행으로 남는다.

**[R23]** 실제 업무에서 나온 실패나 사람의 거절은 원래 입력과 기대한 결과를 비밀 없는 최소 사례로 사람이 채택한 뒤 capability suite에 추가하고, 회귀 실패를 고칠 때는 같은 결함을 재현하는 사례를 함께 남기며 실패한 기대를 현재 결과에 맞춰 낮추지 않는다.
- 이유: 판정 조건을 결과보다 먼저 고정하여 실제 판단 품질의 반복 신뢰성과 비교 가능성을 지킨다.
- 확인: 실제 실패에서 만든 사례는 사용자 데이터 없이 결함을 재현하고, 수정 전 실패·수정 후 통과를 확인하며, 원래 기대를 바꾸려면 사람의 새 버전 채택과 변경 이유가 필요하다.

### 초기 선택

**[R24]** 실제 model 시행의 초기 제한 시간은 600초로 사례마다 시작 전에 고정하고 제품의 시간 초과와 eval 실행기 장애를 서로 다른 결과로 남긴다.
- 이유: 끝없는 유료 호출과 실행기 장애를 품질 성공으로 감추지 않는다.
- 확인: 600초를 넘긴 제품 시행과 실행기 자체 중단을 구별한다.
