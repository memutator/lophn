# platform/blob-store

정확한 바이트의 sha256 주소로 불변 blob을 중복 없이 저장하고 원자적 설치·영구 참조 등록·안전한 읽기·GC를 맡는다; 어떤 내용을 blob으로 보관하고 얼마나 남길지는 그 내용 소유 concern, 변경 확정은 platform/ledger, 출력 보호는 platform/redaction을 따른다.

## 요구

### 불변 내용과 설치

**[R1]** blob은 기존 바이트 hash 체계를 보존하는 정확한 바이트의 sha256 content address로 구별하고 같은 내용은 한 번만 보관하며 확정 뒤 덮어쓰거나 바꾸지 않는다.
- 이유: 예전에 읽은 근거가 같은 주소 아래 다른 바이트가 되지 않아야 한다.
- 확인: 기존 blob fixture의 주소가 같은 바이트에 그대로 대응하고 같은 바이트를 여러 번 준비해 저장량이 늘지 않으며 1바이트 변경은 다른 내용으로 구별되고 이전 blob이 그대로인지 확인한다.
- 의도: platform#I2

**[R2]** blob 준비는 같은 파일 시스템의 임시 파일에 streaming으로 저장·sha256 계산·크기 검증을 마치고 파일 sync·원자적 설치·지원 OS의 directory sync 뒤에만 성공한다.
- 이유: 반쪽 파일과 내구성 없는 파일을 확정 근거로 연결하지 않는다.
- 확인: stream 중단·예상 hash 불일치·sync 실패·동시 같은 내용 설치를 재현해 반쪽 blob을 읽지 못하고 완성된 하나만 남는지 확인한다.
- 의도: platform#I5

**[R3]** 완성 blob은 POSIX 파일 권한 0400 또는 동등한 소유자 읽기 전용 ACL로 두며 API에서 저장소 내부 경로나 임의 파일 경로를 받지 않는다.
- 이유: 불변 내용과 내부 파일의 우회 접근을 막는다.
- 확인: 완성 파일의 권한과 Windows의 동등 ACL을 검사하고 일반 caller가 덮어쓰기·내부 경로 읽기를 요청하면 거절되는지 확인한다.
- 의도: platform#I4

### 참조와 읽기

**[R4]** blob 참조는 검증된 준비 결과의 주체·목적을 확인한 뒤 소유 기록의 변경과 같은 ledger transaction에서 등록하고 document·고정 판·release·SDK·event·message·model 호출·test 근거의 모든 참조를 포함한다.
- 이유: 같은 blob을 공유해도 한쪽 연결이 사라졌다는 이유로 살아 있는 근거를 지우면 안 된다.
- 확인: 여러 종류 기록에서 같은 blob을 참조한 뒤 한 연결을 없애도 나머지 근거가 남고 commit 실패에는 영구 참조가 생기지 않는지 확인한다.
- 의도: platform#I2

**[R5]** blob hash나 공유 여부는 읽기 권한이 아니며 각 읽기는 현재 허용된 소유 기록·고정 판의 참조에서 시작하여 platform/identity의 scope를 검사한다.
- 이유: 내용 중복 제거가 권한을 합쳐서는 안 된다.
- 확인: 같은 blob을 허용·금지 대상에서 공유해 금지 대상의 hash를 알아도 읽지 못하는지 확인한다.
- 의도: platform#I4

**[R6]** 확정 참조의 blob이 없거나 hash가 맞지 않으면 저장소 손상·사용 불가로 표시하고 빈 내용·성공으로 채우지 않는다.
- 이유: 없어진 근거를 내용 없는 정상 자료로 믿게 하지 않는다.
- 확인: 확정 blob을 제거하거나 손상시켜 읽으면 명시적인 부재·손상 오류가 나오고 0바이트 정상 blob과 구별되는지 확인한다.
- 의도: platform#I5

**[R7]** 부분 blob 읽기는 전체 크기·실제 바이트 범위·잘림 여부를 함께 반환하며 일부만 반환한 결과를 전체 내용이라고 표시하지 않는다.
- 이유: 잘린 근거를 전체로 해석하지 않아야 한다.
- 확인: 구간 한도를 넘는 내용을 요청해 실제 범위와 잘림이 확인되고 전체·부분·정상 0바이트가 구별되는지 확인한다.
- 의도: platform#I2

### GC와 용량

**[R8]** GC는 새 준비·command를 막고 진행 준비를 끝내거나 중단한 정지 유지보수에서만 실행하며 고정 ledger의 모든 참조를 대조해 보관된 대상·옛 판·감사 근거를 포함한 참조 blob을 남긴다.
- 이유: 실행 중 준비와 참조 등록 사이 경쟁으로 근거를 지우지 않아야 한다.
- 확인: 준비·commit·GC를 경합시키고 archive·옛 판·감사 참조를 검사해 참조된 blob이 삭제되지 않는지 확인한다.
- 의도: platform#I5

**[R9]** 미참조 설치 blob은 미참조를 확인한 때부터 7일 유예 뒤에만 삭제하고 비정상 종료의 임시 준비 파일은 재시작 시 진행 중 아님을 확인한 뒤 정리한다.
- 이유: blob 설치와 ledger commit은 공동 원자 작업이 아니므로 고아와 손상을 구별한다.
- 확인: 설치 직후 commit 전 종료해 완성 고아가 즉시 사라지지 않고 7일 전후로 삭제 자격이 달라지며 살아 있는 준비 파일은 삭제하지 않는지 확인한다.
- 의도: platform#I5

**[R10]** 기동 시와 매일 미참조 blob의 GC 필요 여부를 점검하되 실제 삭제는 정지 유지보수에서 수행하고 정상 동작 중 나이만 보고 삭제하지 않는다.
- 이유: 기존 주기 점검은 유지하면서 현재 모델의 GC 경쟁 방지를 지킨다.
- 확인: 장시간 동작 중 매일 점검을 확인하고 삭제가 필요하면 유지보수로 전환하며 일반 app 호출과 command 중에는 삭제가 없는지 확인한다.
- 의도: platform#I5

**[R11]** 링크나 참조 하나를 제거한 결과를 모든 공유 blob·derived 사본·backup의 물리 삭제라고 표시하지 않으며 참조 차단·반환 차단·OS 파일 삭제·다른 사본의 잔존을 구별하고 첫 판은 자동 전면 삭제를 약속하지 않는다.
- 이유: 삭제 범위를 실제보다 넓게 설명하지 않는다.
- 확인: 공유 blob에서 한 참조만 제거해 남은 참조와 사본을 확인하고 삭제 완료 범위가 정확한지 확인한다.
- 의도: platform#I2

**[R12]** ledger·WAL·blob·임시 준비·안전 여유를 포함한 실제 디스크 공간이 부족하면 새 수집·변경을 제한하여 이미 확정된 자료를 보호하고 임의로 참조 blob을 지워 성공을 만들지 않는다.
- 이유: 변경 기록·결정·확정 결과는 영구 보존이고 유한 디스크와 동시에 무제한으로 약속할 수 없다.
- 확인: 디스크를 채워 신규 준비·변경이 사용 불가가 되어도 저장된 blob·근거가 유지되는지 확인한다.
- 의도: platform#I5

**[R13]** model 호출 본문·snapshot 첨부·trace 본문·운영 log 같은 큰 자료의 blob은 측정해 고정한 종류별 용량 상한을 넘으면 오래된 것부터 정리하되 변경 기록·결정·확정 결과의 blob과 그 참조는 기간이나 용량으로 삭제하지 않고 상한 초과 준비는 명시적으로 거절하거나 부분만 반환한다.
- 이유: 큰 자료는 유한한 디스크에 맞춰 정리하고 무엇이 왜 바뀌었는지는 언제든 볼 수 있어야 한다.
- 확인: 상한을 넘겨 가장 오래된 큰 자료만 정리되고 변경 기록·결정·확정 결과의 blob은 남으며 정리한 blob의 참조는 부재로 표시되는지 확인한다.
- 의도: platform#I2, platform#I5
