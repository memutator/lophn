# agent-definition

lophn agent의 session 하나는 agent 정의(전역), session의 place, 설정 층으로 정의되고, turn마다 model 요청 하나로 조립된다. 이 조립에는 `agents`, `agent-places`(place 종류 층), `agent-tools`, `run-loop`, 지침 파일, skill, `projects`·`apps`·`domains`가 주는 place 정보가 모두 들어간다. 어려운 점은 두 가지다. 사람이 고친 지침이 며칠씩 열린 session에 닿아야 하고, 그러면서 prompt cache가 깨지지 않아야 한다. 그리고 prompt에 들어오는 글(다른 agent, web, 문서)이 사람의 지시로 읽히면 안 된다.

## Profile

기본 profile은 `{ kind: "character", shape, color }`다. shape 6종과 color 8종은 protocol이 고정하고, shell의 `parts/avatar/character.tsx`가 한 body path와 점 눈 두 개로 SVG를 그린다. 표정은 고정이고 형태·색으로 agent를 구별한다. sidebar, 대화, Agents 카드, 알림은 같은 Avatar를 쓴다.

lophn은 고정 character를 쓰고 바꾸지 못한다. 사람이 만든 agent는 편집 화면에서 형태·색을 고르거나 이미지를 올린다. 정의 파일에는 shape·color 또는 `{ kind: "image", image: "avatar.<ext>" }`만 저장한다. 올린 이미지는 png·jpg·webp만 받으며 SVG는 제품이 그리는 기본 character에만 쓴다. main 알림과 대화 머리에서 올린 이미지 주소를 풀 수 없으면 이름 첫 글자를 쓴다.

`dev:mock`도 편집 화면과 대화가 같은 AgentsSource를 쓴다. 대화 기록만 장면별 fake이고 이름·profile은 요청한 agent의 정의에서 읽는다. 정의나 grant를 저장하면 열린 대화의 `changed` 구독에도 알려 다시 읽는다.

## 흐름

```
 run-loop: turn 시작 때 한 번 읽어 그 turn의 판을 고정한다
   agents ─────── agent 정의 + session place + 설정 층 ─▶ resolved agent
   agent-places ── 제품 고정 규칙 + place 종류 지침(home·project·app), place 종류별 tool 이름 목록, place 글과 kind 글,
                  설정 층의 project 자리와 domain 자리, 내장 skill(place 종류로 준다)
   agent-tools ── 조립이 넘긴 tool 정의(범용·domain·place 층) 중 그 session의 place 종류 목록에 든 것 + 할당한 앱의 tool과 설정한 층의 외부 MCP tool
   지침 파일 ──── 전역 · project LOPHN.md · 맡은 domain의 DOMAIN.md · agent 지침
   skill ──────── 내장 · 전역 · domain
   place 정보 ─── 같은 place의 agent, 맡은 domain 목록과 artifact 목록과 kind 글, lophn은 project·앱 목록과 domain 지도 (잘 안 바뀌는 것만)
        │
        ▼  assemble (순수 함수. I/O 없음)
   system  1 제품 고정 규칙 + place 종류 지침   ← cache 경계
           2 지침 층 (전역, LOPHN.md, DOMAIN.md, agent)
           3 skill 목록 (이름과 설명)
           4 place 정보                    ← cache 경계
   tools[] 정렬된 정의 (place 정책이 숨긴 tool은 tool.load 설명에 이름과 한 줄 안내만. native는 defer_loading으로 싣고, 그 밖은 빼고 tool_call로 부른다)
   대화    Router 입력(tag로 출처 표시) ... 끝에 notice   ← 마지막 block과 그 앞 user message에 cache 경계
        ▲
        └─ 지난 turn이 본 판(seen)과 비교해 바뀐 층·목록만 notice로 끝에 덧붙인다.
           첫 turn과 compact 직후는 seen이 없어 notice가 없다(최신 판으로 prefix를 새로 만든다).
```

## 지키는 것

- **도는 turn은 시작 때 읽은 판을 끝까지 쓴다.** 지침, skill, place 정보가 도중에 바뀌면 다음 turn 시작에 system을 그 turn이 읽은 지금 판으로 다시 만들고, 바뀐 층·목록은 notice로도 대화 끝에 알린다(그 turn 요청에만 붙고 이력에 저장하지 않는다). 바뀐 turn에는 cache miss가 한 번 난다. tool 목록은 아래처럼 session을 시작할 때 고정이라 system에 안 닿고 notice로만 알린다.
- **같은 재료는 같은 bytes다.** 정렬하고, 시각·무작위에 기대지 않는다. tag 목록도 코드에서 끼우지 않고 고정 문장으로 둔다. 뭔가 하나라도 흔들리면 cache 경계가 매번 달라진다.
- **cache 표시는 system 층 둘(place 종류, place 정보)과 대화 쪽 둘이다.** Anthropic 요청은 표시를 넷까지 받아 그 안에 든다. 대화 쪽 표시는 마지막 message와 그 앞 user message의 마지막 content block에 단다(`packages/core/lophn-agent/providers/adapters/messages.ts`의 `buildRequest`, system·tools가 쓴 표시를 뺀 남은 자리만 쓴다). 끝 block은 turn마다 새로 생긴 tool 결과나 사람 글이라 다음 call은 앞 call이 쓴 prefix를 읽는다. Anthropic은 표시마다 앞쪽 20 block까지만 찾으므로, 한 call에 block이 많이 늘어도 그 앞 user message 표시가 앞 call의 entry를 찾는다. 지침 층은 사람이 지침을 고칠 때만 바뀌어 따로 표시하지 않는다(바뀌면 place 정보 경계까지 다시 쓴다). 앱 하나를 짓는 turn은 model call이 백 번 가까이 되어 대화를 cache하지 않으면 매 call 대화 전체를 새 입력으로 낸다. tools는 system 앞이라 첫 system 층(제품 규칙과 place 종류 지침) 표시가 함께 덮는다.
- **사람이 쓴 지침은 조용히 빼지 않는다.** 한 층이라도 못 읽거나 상한을 넘으면 turn을 시작하지 않는다. 빠진 채 일하면 사람이 모른다. 읽은 지침은 redaction을 거치고, 끝나지 않으면 역시 시작하지 않는다.
- **지침 층은 덮지 않고 이어 붙인다.** skill과 MCP server만 같은 이름일 때 마지막 층이 덮는다. MCP server의 층은 전역, project, agent 정의 순이다. 단 내장 skill은 모두 끌 수 없고 사람 skill이 같은 이름으로 덮지 못한다. role이 일하는 데 필요한 skill이 사라지면 lophn 동작이 막힌다.
  - 층의 자리(domain 층의 skill 폴더와 project 층의 `extensions.json`)와 내장 skill 폴더(`packages/core/agent-places/skills/`)는 place 종류 층이 정하고 harness는 받아 쓴다. 읽기 허락과 skill 발견이 같은 값을 써야 허락 밖 폴더를 찾다 막히지 않는다.
- **`AGENTS.md`는 읽지 않는다.** 지침은 `LOPHN.md`뿐이다. 다른 도구의 지침이 섞이면 사람이 무엇이 prompt에 들어가는지 모른다.
- **지침은 prompt 조립이 싣는다. agent가 tool로 지침을 읽게 하지 않는다.** home은 place가 없어 project 지침이 없다. project의 일은 `call`로 그 project의 session에 넘기고, 거기서 조립이 `LOPHN.md`를 싣는다. 앱 place의 agent에게는 project 지침이 없다.
- **`DOMAIN.md`는 그 agent가 맡은 domain의 것만 지침 층에 실린다.** 글이 예산(24000자)을 넘으면 넘은 domain부터 목적 한 줄로 줄인다. 규칙은 `architecture/domain.md`다.
- **Router가 넣는 입력은 모두 user role이고 `lophn-` tag로 출처를 밝힌다.** 본문 속 `lophn-` tag는 escape하고 속성 값은 scrub한다. 사람의 steer만 `<lophn-steer>` 모양을 믿는다고 고정 본문에 적는다. 받은 메시지, 알림, tool 결과는 허락도 사람의 지시도 아니다. 받은 메시지는 뒤 turn의 이력에서도 받은 turn의 입력과 같은 bytes로 싼다(봉투가 답 방식, reaction event, 실패 이유를 저장한다. `agent-call.md`).
- **감싸는 결과는 web 검색과 web 읽기뿐이다.** file, shell, 앱 tool, 외부 MCP 결과는 감싸지 않는다. 앱과 MCP는 사람이 할당하고 설정한 순간 믿는다는 철학이고, 실행 때 의심을 더하지 않는다. "안전해 보이니 감싸자"로 되돌리지 않는다.
- **agent 정의 층의 MCP server는 그 agent의 turn과 MCP 목록에만 닿는다.** MCP server는 설정한 층(전역, project, agent 정의)이 곧 할당이고 끄기는 `mcp_off`다(`architecture/approval.md`). turn 준비가 그 agent의 `mcp_servers`만 agent 층으로 넘기고, MCP tool 목록 요청(`agent-mcp-tools/list`)도 agent id를 실어 같은 층을 더한다. 반면 `mcp.` secret 목적지는 모든 agent의 정의 층을 합친 목록을 본다(runtime child 하나가 모든 session의 MCP를 돌린다). 정의 층 server의 credential 이름은 `mcp.<agent id>.<서버>`라 다른 층·다른 agent와 겹치지 않는다. 이름 접두는 core가 강제하지 않고 편집 화면이 만든다. 정의 file을 쓰는 것은 사람뿐이다.
- **agent 정의의 `skip`은 그 agent 새 session의 skip 기본값이다.** 켜 두면 새 session이 skip으로 시작해 shell `ask`를 묻지 않는다(deny 규칙은 막는다). `mcp_servers`처럼 사람만 쓴다: `agent.create`·`agent.update` 입력에 없다. session의 skip은 사람이 대화 화면에서 켜고 끄고(`ChangeSessionSkip`), fork한 session은 skip을 가져가지 않고 정의의 기본값으로 시작한다(`architecture/place-session.md`).
- **tool 목록은 session을 시작할 때 고정한다.** session 도중 activation이나 할당으로 앱 tool, MCP tool이 더해지거나 빠져도 `tools[]`는 그대로 두고 대화 끝에 notice로 알린다. 빠진 tool은 목록에 남아도 부를 때 막힌다. 앱 tool은 Gate가 지금 할당을 읽고, MCP tool은 연결 쪽 `call`이 지금 server 설정을 다시 읽는다(`architecture/approval.md`). notice는 program이 쓴 고정 문장만 쓰고 앱이 쓴 글(tool 설명)은 넣지 않는다. notice도 다음 turn부터는 이력의 앞부분(prefix)이라, 앱 글이 들어가면 그 글이 바뀔 때마다 같은 재료가 같은 bytes가 아니게 되어 cache가 깨진다.
- **tool 목록은 session의 place 종류(home, project, app)로 코드가 고정하고, 목록 밖 tool은 정의에도 실행에도 없다.** 같은 place 종류의 session은 agent가 누구든 같은 목록을 받는다. 사람은 목록을 넓히거나 좁히지 않는다. 넓히는 길은 할당 하나다. 공통 읽기와 job tool 넷, `agent.create`·`agent.update`는 셋 모두에 준다. `kind.list`·`kind.check`는 작업 domain이 있는 project·app만 받는다. home은 작업 domain이 없어 이 호출이 항상 실패하기 때문이다. 그 밖의 읽기·쓰기 tool도 실행할 수 있는 place 종류로 나눈다. 목록은 `agent-places/tool-lists.ts`에 있고, 목록의 이름마다 정의가 있고 정의마다 어느 목록에 든다(`main/agent-tools_test.ts`). 어긋나면 agent가 그 tool을 말없이 못 본다.
- **model에 보이는 schema와 실행 검증은 구분한다.** 기본은 `input`에서 JSON Schema를 만들고 tool API에서 쓰지 않는 생성기의 `$schema` 표시는 뺀다. 명시한 `inputSchema`는 그대로 보낸다. `kind.list`는 조건 tree 한 층과 중첩 모양의 설명만 보내 schema 반복을 줄이지만, 실행기는 기존 `input`으로 전체 깊이·형식·추가 key를 검사한 뒤 Gate와 handler를 부른다. description은 tool 선택과 호출에 필요한 의미·예외를 남기고 schema와 중복되는 문구를 줄인다.
- **tool 정의는 늦게 싣는다: 숨긴 tool은 이름과 한 줄 안내만 알리고 `tool.load`로 펼친다.** provider와 무관한 공통 경로가 기준이고 native loading은 packer가 고른다. 숨김은 보이는 방식만 바꾸고 place 종류 구분이 아니다(그 구분은 위 목록과 할당이 한다).
  - 숨는 것: place 종류마다 첫 요청에 싣는 내장 tool(`agent-places/tool-lists.ts`의 `exposedToolNames`) 밖의 그 session 고정 목록 전부, 앱 tool 전부, 외부 MCP tool 전부. 첫 요청에 싣는 것은 처음부터 쓰는 파일 탐색·이미지·web, 질문·협업·완료 보고(`ask`, `call`, `reply`, `cancel`, `workflow.report`), `skill.read`, `tool.load`, `tool.call`, home은 앱 탐색(`app.read`, `app.tools`), project·app은 작업 tool과 `kind.list`다. 정책은 이 한 곳이고 tool 정의에 따로 표시하지 않는다. 노출 목록의 이름은 place 목록에 있어야 한다(`tool-lists_test.ts`).
  - 숨김은 session의 tool 목록을 고정할 때(첫 turn) 정하고 session 동안 같다. provider·model을 가리지 않는다.
  - `tool.load` description 끝에 숨긴 tool의 wire 이름과 설명 첫 문장(100자까지, 줄바꿈 없음)을 이름 순으로 한 줄씩 싣는다. 목록 밖 tool은 이 안내에도 없다.
  - `tool.load`의 항목은 wire 이름이거나 묶음 이름이다. 항목 `g`는 wire 이름이 `g`와 같거나 `g_`로 시작하는 숨긴 tool에 맞는다(`job`, `release`, 앱 domain `calendar`, `mcp__<server>`). 숨긴 tool만 펼친다. session 목록 밖이면 `not_found`, 숨기지 않은 tool이면 `invalid_input`이고 하나라도 틀리면 전체가 실패한다(`packages/core/lophn-agent/tools/bundles/tool_test.ts`). 목록 밖 tool을 펼치면 place 종류 목록과 할당이라는 권한 경계를 넘는다. model은 code만 본다(`executeToolCall`이 실패 문장을 code별 고정 문장으로 바꾼다).
  - 공통 경로(Responses, Chat Completions, Cloud Code Assist, native를 못 받는 Anthropic Messages): packer가 `inlineToolLoading`(`prompt-assembly/loading.ts`)으로 숨긴 정의를 `tools[]`에서 빼고, `tool.load` 결과 글 뒤에 불러온 정의(이름, 설명, 입력 schema)를 JSON으로 잇는다. model은 그 tool을 `tool_call {name, input}`으로 부른다. `tools[]`는 session 동안 같고 정의는 이력 끝에 붙어 prefix가 그대로다.
  - native 경로: built-in `anthropic` provider 정의(key `anthropic`)의 Claude 4.5 이상·5 세대·Fable·Mythos model(`providers/definitions.ts`의 `supportsDeferredTools`)이면 Anthropic packer가 숨긴 정의를 매 요청 `tools[]`에 `defer_loading: true`로 싣고 `tool.load` 결과를 `tool_reference` 조각으로 그린다. API가 그 자리에서 정의를 펼치고 model은 tool을 제 이름으로 부른다. 받는 model의 요청에는 beta header `advanced-tool-use-2025-11-20`를 늘 붙인다. 고르는 것은 turn의 binding이라 같은 session도 provider를 바꾸면 경로가 바뀐다(숨김은 그대로다).
  - `tool_call`은 loop의 tool 묶음(`packages/core/lophn-agent/run-loop/tool-batch.ts`)이 기록·effect 판단·Gate·retry 전에 대상 tool의 호출로 푼다(`packages/core/lophn-agent/tools/dispatch.ts`의 `dispatchTarget`). 그래서 tool 호출 기록, 승인, 병렬·재시도 판단, rewind는 대상 tool의 이름과 effect를 쓴다. wrapper(read)로 판단하면 쓰기가 병렬로 돌거나 다시 실행된다. 이력의 tool_use는 model이 보낸 `tool_call` 그대로다. 대상은 session 고정 목록에서 찾고 실행기가 대상의 `input`으로 검사한다. 대상이 다시 `tool_call`이면 거절한다. 불러오지 않은 숨긴 tool도 부를 수 있다: 불러오기는 정의를 보이는 일이지 권한이 아니다.
  - 불러온 tool은 session 동안 남는다. 다음 turn부터 이력에 앞 turn의 성공한 `tool.load` 호출과 결과를 그 turn의 요청 뒤, 답 앞에 다시 싣는다(`packages/core/lophn-agent/session/history.ts`의 `readLoads`). 저장된 tool 호출 기록과 결과 본문을 읽고, compaction·숨김·접힘이 그 요청과 같이 덜어 낸다. 다시 그릴 때 지금 숨긴 정의에 없는 이름(runtime이 다시 떠 목록을 새로 만든 session)은 빼고, 남는 것이 없으면 고정 문장 하나로 알린다. native 요청에서 없는 이름을 참조하면 API가 요청을 거절한다.
  - 실행 쪽(`executeToolCall`, Gate)은 이번 요청의 `tools[]`가 아니라 session 고정 목록을 본다. 숨김은 model이 보는 것만 바꾼다.
- **목록과 하나는 `<자원>.read` 하나로 읽는다(`app.read {app?}`, `domain.read {domain?}`, `package.read {name?, version?}`).** 대상을 생략하면 목록, 주면 그 하나의 상세다. agent 자격의 기존 core route(`app.list`·`app.get`, `domain.list`·`domain.get`, package route들)를 그대로 부르므로 읽기 범위(app place session은 그 앱 하나, domain은 그 그릇)와 오류는 route의 것이다. 지정한 대상이 없거나 범위 밖이면 그 오류이고 목록으로 바꾸지 않는다. 결과는 원래 목록·상세의 꼴 그대로다. `package.read`의 `version`과 `offset_bytes`는 `name`과 함께만 쓰고, `name` 없이 주면 `invalid_input`이다. `action` enum이나 중첩 union은 두지 않는다.
- **틀린 입력에는 어디가 왜 틀렸는지 알린다.** 실행기의 입력 검사가 거절하면 첫 문제의 자리와 이유를 싣는다(`at count: Too big: expected number to be <=5`, 모르는 key는 `unknown key extra`). handler가 `invalid_input`을 돌려주면 그 문장을 붙인다(`tool input is not valid: version needs name`). `not_found`·`forbidden` 등 다른 code는 code별 고정 문장이다: handler 문장은 범위 밖 대상의 이름·존재를 담을 수 있다(`packages/core/lophn-agent/tools/work.ts`, `registry_test.ts`). 그래서 handler의 `invalid_input` 문장에는 범위 밖 대상의 정보를 넣지 않는다. 실패한 대상이 model이 보낸 입력뿐인 tool은 그 handler 문장을 그대로 싣는다(`work.ts`의 `INPUT_SCOPED_FAILURES`, 지금 `skill.read` 하나): 그 이름은 prompt의 skill 목록에 이미 실려 가릴 것이 없고, 가리면 원인을 못 가려 같은 입력으로 되풀이한다.
- **모든 앱의 tool 목록을 읽는 tool(`app.tools`)은 home과 app 목록에만 있다.** 새 앱을 청받았을 때 이미 있는 기능을 찾고, app place의 agent가 선언의 `app_connections`에 정확한 tool key를 적으려는 것이다. 읽기 전용 route `app.tool_index`가 active 앱의 이름·설명과 tool(name, title, description, effect, public, domain)만 주고, 앱 하나를 지정하면 `inputSchema`와 선언된 `outputSchema`도 준다. 이 route는 앱 범위 판정을 하지 않는다. app place session의 자격이 그 앱 하나(`conditions.app`)로 묶여 있어 기존 `app.list`·`app.get` route의 검사는 그대로 두고, 돌려주는 칸을 이것으로 한정해 다른 앱의 source, ticket은 열리지 않게 했다.
- **다른 domain의 비공개 tool은 agent의 tool 목록에도 `app.tools` 결과에도 없다.** agent는 맡은 domain의 tool을 모두 보고, 다른 domain(같은 앱의 다른 domain 포함)은 `public`인 tool만 본다(domain이 없는 lophn은 `public`만 본다). tool의 domain이나 부른 agent의 domain을 읽지 못하면 뺀다(막는 쪽으로 실패한다). 걸러내기는 할당한 앱의 tool을 모으는 자리(`packages/core/lophn-agent/tools/app-public.ts`)와 `app.tools`의 결과 두 곳에서 같은 규칙으로 한다. 규칙은 `architecture/domain.md`다.
- **내장 SDK(`@lophn/*`)는 package tool이 설치 사본에서 읽는다.** `package.read`의 목록은 catalog의 앱 package 뒤에 `builtin` 칸을 싣고, `@lophn/` 이름을 주면 `packages.builtin`으로 설치 사본(`<data root>/sdk`)의 판과 `guide.md`를 읽는다. 내장 SDK는 catalog에 등록하지 않고 설치 사본이 정본이다. 어느 role도 그 폴더를 file tool로 읽지 못하므로 tool이 대신 읽어 준다. guide가 tool 결과 상한(`TEXT_MAX_BYTES`)보다 길면 `package.read`가 상한 안의 창을 돌려주고 `continuation.read_next`에 다음 창의 `offset_bytes`를 싣는다(잘라 버리지 않는다).
- **앱을 진단하는 읽기 tool(`app.status`, `app.logs`, `app.invocations`)은 home과 app 목록에만 있다.** 앱이 돌고 있는지, 앱 log에 무엇이 쌓였는지, 어느 호출이 어떻게 끝났는지를 읽는다. problem 같은 가공된 보고 대신 원래 기록을 직접 읽고 판단하는 쪽이 agent의 몫이다. 정의는 `packages/core/apps/agent-tools/runtime.ts`다. app place session의 자격은 그 앱 하나(`conditions.app`)로 묶여 있다. log의 줄 꼴과 redaction은 `architecture/app-call.md`다.
- **agent credential의 operation 상한은 tool이 core에 부르는 route 이름이다.** core는 route 이름으로 대조하므로 tool 이름(`preview.start`)을 넣으면(route는 `previews.start`) command가 `forbidden`이다. tool 정의는 helper가 부르는 것까지 `routes`에 적고, 상한은 그 place 종류 목록 tool의 route 합집합에 place 읽기, rewind, Gate 대기 같은 보조 operation을 더한 것이다. place 읽기(`agent-places/credentials.ts`의 `PLACE_READS`)에는 prompt의 "Agents you can call"을 채우는 agent 목록도 들어 있다. 조건은 session place에서 나온다: app place면 `conditions.app`, project place면 `conditions.project`, home은 없다. 할당 읽기(`GetAgentAssignment`)는 agent 자격에 없다(사람과 machine만 읽는다).
- **"tool 정의가 바뀌었나"는 정의에서 계산한다.** 이름, 설명, 입력 JSON schema, effect의 hash다. 따로 들고 다니는 판 번호를 두지 않는다. 손으로 올리는 번호는 잊히고, 정의가 같으면 release가 바뀌어도 알림이 나가지 않는 것이 맞다.
- **효과(read, write, external)는 model에 보이는 정의에 넣지 않는다.** registry만 안다. 효과는 기록과 재시도에 쓰이고, 판정은 할당과 shell 규칙이 한다.
- **file tool은 place 폴더 안에 가둔다.** realpath로 판정하고, 새 파일이면 가장 가까운 상위 폴더의 realpath에 이름을 붙여 판정한다. 끊어진 symlink는 따라 쓰면 밖에 쓰게 되므로 거절한다. 읽기와 쓰기는 Gate를 거치지 않고 쓰기는 rewind로 되돌린다. `LOPHN.md` 쓰기도 묻지 않는다. shell은 shell 규칙으로 Gate를 거친다(`architecture/approval.md`).
- **agent 정의는 lophn data에 있어 file tool이 닿지 않는다.** agent가 자기 정의를 file tool로 고쳐 할당을 우회하지 못한다. 지침 파일(`LOPHN.md`)과 domain 폴더의 `DOMAIN.md`·`kinds.yaml`·`skills/`는 그 범위의 agent가 묻지 않고 쓴다(rewind로 되돌린다).
- **shell은 환경 변수 허용 목록만 넘긴다.** lophn token과 secret은 이름으로 막는 것이 아니라 목록에 없어서 나갈 수 없다. 앱 data는 앱 tool로만 다루고 앱 DB는 직접 열지 않는다(고정 본문).
- **agent 정의를 만들고 고치는 tool(`agent.create`, `agent.update`)은 할당을 주지 못한다.** 할당, 정의 층 MCP server, skip 기본값은 사람이 정한다. agent가 자기 권한을 넓히거나 묻기를 끄는 길이 없어야 한다.
- **agent 정의는 전역이고 꼴이 하나다.** 자리는 `<data>/agents/<id>.md`(올린 avatar는 그 옆)이고 칸은 name, profile, model, skills, domains, mcp_off, mcp_servers, skip, 본문이다(`agentDefinitionSchema`, `packages/protocol/lophn-agent/agent-values.ts`). route는 `agents/*`다. lophn은 고정 id `lophn`의 내장 정의라 지우지 못하고 이름과 profile을 바꾸지 못한다(`forbidden`). agent 이름은 전역에 하나이고 `lophn`은 예약이다. 주소가 이름이라 겹치면 받는 agent가 하나로 정해지지 않는다. 등록(project, 앱)은 agent를 만들지 않는다.
- **할당은 agent id마다 한 줄이다**(`agent_assignments.agent`, route `assignments/*`). 정의가 전역이라 할당도 place를 갖지 않는다.
- **tool 결과는 model에 약 24 KiB까지만 싣는다.** shell도 stream마다 앞 12 KiB와 뒤 12 KiB만 남기고 가운데는 생략 표시로 바꾼다. 오류는 끝에 나오므로 뒤를 버리지 않는다. 출력 많은 명령 한 번이 context를 채우지 않게 한다.
- **model 요청에 싣는 이미지는 그 turn의 최신 둘뿐이다.** 오래된 이미지 조각은 빼고 짝 tool 결과 글 끝에 `[image omitted]`를 붙인다. 요청 body 전체를 blob으로 저장하고 그 상한이 16 MiB라, 이미지가 쌓이면 model call을 보내지 못한다. 입력 예산은 이미지를 base64 byte가 아니라 이미지당 고정 token(4096)으로 센다. base64를 byte로 세면 screenshot 하나로 `context_limit`이 난다.
- **입력 예산은 같은 turn 앞 call의 실제 prompt token에 늘어난 byte를 더해 잰다(`packages/core/lophn-agent/prompt-assembly/budget.ts`의 `measureSize`).** 앞 call의 token은 provider가 보고한 `input + cache_read + cache_write`다. 늘어난 byte는 그대로 token으로 세고 줄어든 byte는 3 byte를 한 token으로 뺀다. 앞 call이 없거나(turn의 첫 call) token을 모르면 이미지를 뺀 byte를 3으로 나눠 센다. 영어·code는 약 3.5~4, 한국어는 약 3~4.5 byte가 token 하나라 대개 실제보다 크다. 예전처럼 byte를 그대로 token으로 세면 200k 창 model이 실제 약 5만 token에서 막혔다. compact 요약의 chunk와 본문 상한도 같은 세기다. 낮게 센 경우는 provider가 거절하고 아래처럼 줄인다.
- **turn 안 이력은 context에 맞게 줄인다(`packages/core/lophn-agent/run-loop/turn.ts`, `run-loop/history.ts`의 `omitOldToolResults`).** 조립한 요청이 예산의 85%를 넘거나 넘쳐 막히면, 그 turn 안 가장 오래된 tool 결과부터 본문을 고정 문장 하나로 바꿔 60% 아래로 내린 뒤 다시 조립한다. 가장 최근 tool 결과 묶음 둘과 `skill.read` 결과는 바꾸지 않고, 50 token보다 적게 줄어드는 결과도 그대로 둔다. tool_use와 결과의 짝, 이미지·참조 조각은 남는다. 한 번 바꾼 결과는 그 turn이 끝날 때까지 바뀐 채라 그 뒤 prefix는 다시 같다(줄일 때마다 cache miss는 한 번). 원문은 tool 호출 기록에 그대로 있고, model은 필요하면 tool을 다시 부른다. provider가 입력이 크다고 거절하면(`context_exceeded`) 보낸 크기의 60% 아래로 줄여 다시 보낸다(turn마다 두 번까지). 줄일 것이 없으면 turn은 `context_limit`으로 끝난다.
- **provider credential(API key, 구독 OAuth access token)은 `secrets.json`의 이름 `provider.<id>`로만 가리킨다.** ConnectProvider는 그 provider 몫의 이름만 받는다. 값은 core가 전송 직전에 그 이름을 가진 회수되지 않은 provider의 endpoint origin과 요청 목적지가 같을 때만 읽어 agent runtime의 전송 callback 하나에 준다. 값은 ledger, event, log, 오류, model 입력에 없다. 다른 이름을 가리킬 수 있으면 앱·MCP secret이 provider endpoint로 나간다.
- **secret 저장소는 `secrets.json` 하나이고 이름의 앞머리가 이름 공간이다.** `provider.`는 provider credential(구독 OAuth는 옆에 `provider.<id>.refresh`·`.meta`를 둔다. 둘은 어떤 provider의 secret_name과도 같지 않아 core 밖으로 안 나간다), `mcp.`(`mcp.<global 또는 agent의 agt id>.<서버>`)는 사람이 넣은 MCP credential, `mcp-oauth.<scope>.<서버>.access`·`.refresh`·`.meta`는 MCP OAuth token이다. `app-oauth.<이름>.refresh`·`.meta`·`.client_id`·`.client`는 앱 OAuth의 갱신 token, meta, 사람이 넣은 client이고 access token은 앱이 선언한 이름 그대로 둔다(`app-call.md`). `provider-oauth.`는 provider 로그인이 쓰는 core 안의 이름이다(`HOST_ID_NAME`). 전송 부착(`core/secrets/file-attach.ts`)은 앞머리로 용도를 정한다. `app-oauth.`와 `provider-oauth.`는 누가 불러도 보내지 않는다. 앞머리가 없는 이름은 앱 secret이고, 앱을 대신하는 호출(`conditions.app`)만 보낸다(앱 호출이 앞의 셋을 가리키거나 그 밖의 호출이 앱 secret을 가리키면 거절한다). 앱 secret의 목적지는 이름 공간이 아니라 현재 선언 ∩ active grant가 정한다(`app-call.md`). provider와 MCP 이름의 목적지는 이름 공간마다 따로 찾는다(`lophn-agent/secret-destinations.ts`): `mcp.` 값은 그 이름을 header나 bearer·api_key로 보내는 켜진 http 서버(전역, project 층, 모든 agent의 정의 층)의 URL origin으로만, `mcp-oauth.` 접근 token은 그 meta가 묶인 서버 URL origin으로만 간다. 갱신 token과 meta는 core 밖으로 나가지 않는다. MCP 설정 schema는 `mcp.` 이름만 받으므로 설정(사람 실수나 agent가 고친 project 설정)이 provider key나 다른 서버의 token을 가리켜 MCP URL로 보내지 못한다.
- **MCP OAuth의 접근 token과 갱신 token은 각자 이름이다.** 알려진 값 registry가 값 전체로 맞추므로 JSON 하나로 합치면 token 하나를 redaction할 수 없다. 만료가 가까우면 core가 보내기 전에 갱신하고 secret store의 put이 새 값을 먼저 알려진 값으로 올린다. 발급자가 갱신을 400·401·`invalid_grant`로 거절하면 세 이름을 지우고 사람이 다시 로그인한다. 그 밖의 실패(5xx, 닿지 못함)에는 만료 전 token을 그대로 쓴다.
- **MCP OAuth sign-in은 server의 소유자로 연다.** 소유자는 전역(place·agent 둘 다 null), project 층(place), agent 정의 층(agent id) 중 하나이고 `agent-mcp-auth/*`가 `place`와 `agent`를 받는다(둘 다 있으면 `invalid_input`). token 이름도 소유자로 정한다: `mcp-oauth.<global, project id, 또는 agent id>.<server>.*`. 같은 이름의 server가 층마다 있어도 token이 섞이지 않는다. 사람이 server form에서 OAuth 2.1(issuer, client ID, scopes)을 고르고, client secret은 더한 뒤 보호 입력으로 `mcp.<scope>.<server>.client`에 넣는다(넣지 않으면 public client). `oauthServerOf`(`extensions/mcp-auth-control.ts`)가 그 값을 secret store에서 읽어 token 교환과 refresh 본문에만 싣는다. `begin`(`extensions/mcp-oauth.ts`)은 `${issuer}/.well-known/oauth-authorization-server`를 발급자 대기열로 먼저 읽어 https 끝점을 쓰고, 없거나 맞지 않으면 `${issuer}/authorize|token`이다. dynamic client registration은 없다. agent 정의 층 server는 저장된 정의 파일에서 찾으므로 저장하기 전에는 sign-in하지 못한다.
- **구독 provider 로그인(ChatGPT, SuperGrok, Claude, Google Antigravity)은 token을 core만 만진다.** `providers/login.ts`가 writer queue 앞에서 `BeginProviderLogin`·`CompleteProviderLogin`·`CancelProviderLogin`을 받는다. SuperGrok은 device code다. ChatGPT(`openai` 정의의 product `chatgpt`, `providers/oauth-chatgpt.ts`), Claude(`anthropic` 정의의 product `claude`, `providers/oauth-claude.ts`), Antigravity(`google-antigravity` 정의, `providers/oauth-antigravity.ts`)는 PKCE와 정의의 `redirect_uri`에 고정된 callback이다(ChatGPT `localhost:1455/auth/callback`, Claude `localhost:54545/callback`, Antigravity `127.0.0.1:51121/oauth-callback`). ChatGPT는 Codex CLI의 공개 client(`app_EMoamEEZ73f0CkXaXp7hrann`)로 로그인하고 교환은 form이다. 계정 id(`chatgpt_account_id`)와 email·plan은 token claim에서 읽고, 계정 id가 없으면 연결하지 않는다. OpenAI 공식 Sign in with ChatGPT가 아니다(그 token은 `api.openai.com/v1`만 받고 `prompt_cache_key` routing을 줄 수 없어 cache가 거의 맞지 않았다). browser를 열기 전에 그 port로 듣고(`localhost`면 127.0.0.1과 ::1을 함께 쥔다), 다른 프로그램이 쓰고 있으면 `conflict`다. listener는 path와 이 시도의 state가 맞는 callback 하나만 받고 다른 요청은 400으로 돌려보낸 채 기다림을 잇는다. Claude 교환은 JSON이고 token 응답에 계정·조직이 빠지면 bootstrap으로 빈 칸만 채운다. Antigravity 교환은 form에 installed-app client pair를 싣고, refresh token이 없으면 연결하지 않는다. 그 뒤 userinfo로 email을, `loadCodeAssist`(tier가 없으면 free-tier `onboardUser`와 30초 안의 operation poll)로 Cloud Code project를 정한다. 마지막 `loadCodeAssist`가 준 project만 저장하고 없으면 연결하지 않는다. 로그인이 확정한 계정(id, email, 조직, project)은 비밀이 아니라서 credential의 `account` 칸에 둔다. Complete는 기다리지 않고 한 번 보고 pending이나 연결된 provider를 낸다. 끝나면 core가 token 셋을 저장하고 사람의 context로 ConnectProvider를 부른다. token은 renderer와 ledger·event·log를 지나지 않는다. 발급자 주소와 client 값은 provider 정의 data라서 fake 발급자는 정의만 바꿔 돈다. Anthropic은 제3자 앱의 Claude.ai 로그인과 구독 credential 사용을 허락하지 않고, ChatGPT가 쓰는 Codex backend와 Antigravity가 쓰는 Cloud Code `v1internal`도 공개 API가 아니다. 사람이 그 위험을 알고 고른 연결이다.
- **구독 OAuth access token은 runtime에 건네기 직전에 갱신한다.** agent runtime이 `provider.<id>`를 달라고 하면 core(`providers/oauth-refresh.ts`, `runtime-secret.ts`의 hook)가 만료까지 5분 미만일 때 provider마다 한 번에 하나만 refresh grant를 보낸다. token을 바꾸는 곳은 이 하나다(model 호출과 model 목록이 따로 갱신하지 않는다). grant 꼴은 product가 정한다: ChatGPT·SuperGrok·Antigravity는 form(Antigravity는 client pair를 싣는다), Claude는 JSON에 OAuth beta와 SDK User-Agent를 붙인다. Antigravity는 저장된 project가 없으면 보내지 않고 project를 다시 찾지도 않는다. 발급자의 답을 받으면 provider를 다시 읽고, 그사이 Disconnect했거나 다시 로그인했으면(`logged_in_at`이 다르면) 늦은 token을 저장하지 않는다. refresh token은 회전할 수 있으므로 새 refresh를 먼저 저장하고(오지 않으면 지금 것을 그대로 쓴다) access를 저장한 뒤 `RefreshProviderCredential`로 만료를 올린다. 저장이 실패하면 받은 같은 값으로 다시 쓰고, 이미 쓴 옛 refresh token을 다시 보내지 않는다. 발급자가 grant를 거절하면 credential이 `revoked`가 되고 token을 건네지 않는다. 그 밖의 실패는 지금 token이 살아 있으면 그대로 건넨다. 같은 refresh token을 두 곳에서 쓰면 발급자가 둘 다 폐기할 수 있다. ChatGPT와 Antigravity provider는 연결 직후와 갱신 직후, 그리고 목록이 아직 없을 때 token을 건넨 뒤에 같은 Bearer로 계정 model 목록(ChatGPT Codex backend `GET /models?client_version=…`의 `models[].slug`, Antigravity 그 project의 `fetchAvailableModels`에서 내부용·꺼진 줄을 뺀 key)을 읽어 `credential.reported_models`에 둔다(`RecordProviderModels`, `providers/reported-models.ts`의 `readAccountModels`). 읽는 일은 token을 기다리게 하지 않고, 실패하면 앞서 저장한 목록을 남긴다. 구독 OAuth provider의 이 목록만 계정의 허락 목록이다: model을 고르는 화면과 turn의 resolver는 목록 밖 이름을 쓰지 않는다(`null`이면 거르지 않는다, `entitlementAllows`).
- **ChatGPT 구독 호출은 Codex backend로 보낸다(`providers/adapters/codex.ts`).** ChatGPT 로그인 연결의 provider endpoint는 정의의 `oauth.inference_endpoint`(`https://chatgpt.com/backend-api/codex`)다. packer가 만든 Responses body를 보내기 직전에 `/responses`로 바꿔 보낸다: `max_output_tokens`를 빼고(backend가 거절한다), `include`에 `reasoning.encrypted_content`를 늘 넣고, session에서 만든 같은 값을 본문 `prompt_cache_key`와 `session_id`·`conversation_id`·`session-id` header에 싣는다. backend는 이 값으로 cache를 가진 machine을 고르므로, 빠지면 앞부분이 같은 요청도 cache를 거의 못 읽는다. `chatgpt-account-id`·`originator`·`version`(Codex client 판, model 목록도 이 판으로 거른다) header를 붙인다. 값은 Codex client profile이고 OpenAI가 제3자에게 공개 보장한 계약이 아니다. plan 한도 code `usage_limit_reached`는 `credential_unavailable`·`quota`로, `usage_not_included`는 `plan_access`로 읽는다.
- **Claude 구독 호출은 Claude Code client profile로 보낸다(`providers/adapters/claude-code.ts`).** packer가 만든 Messages body를 보내기 직전에 다시 만든다: `/v1/messages?beta=true`, Claude Code header 묶음(`anthropic-beta`에 option·defer의 beta를 합친다), system 앞의 billing block과 identity block, custom tool 이름 앞 `_`(응답의 tool 이름은 그 요청의 표로 원래 이름으로 되돌린다), `metadata.user_id`(provider와 계정에서 만든 device id, session에서 만든 session id), 마지막 byte의 cch(placeholder를 넣어 직렬화한 byte의 XXH64를 host가 만든 billing slot 다섯 byte에만 쓴다). 모든 cache 표시의 수명은 1시간(`ttl: "1h"`)이다. Claude Code도 plan 안의 대화에 1시간을 쓰고, 5분이면 tool 실행이나 사람을 기다리는 사이에 cache가 사라진다. 표시를 모두 같은 수명으로 두어 "긴 수명이 짧은 것보다 앞" 규칙에 걸리지 않는다. header와 이 값들은 2026-10 조사 snapshot이고 Anthropic이 보장한 계약이 아니다. 같은 `anthropic` 정의의 API key 호출은 이 profile을 쓰지 않는다.
- **Antigravity 호출은 protocol `cloud-code-assist`다(`providers/adapters/cloud-code.ts`).** Claude model도 Anthropic wire가 아니라 Google contents/parts로 간다. packer가 이력을 contents로 옮기고(tool 결과는 call ID로 잇고 그 assistant turn의 call 순서대로 user turn 하나에 모은다, tool schema는 Cloud Code가 받는 부분집합으로 줄인다), 보내기 직전에 `{project, requestId, request, model, userAgent}` envelope로 감싼다. conversation 값(cascade·trajectory·`sessionId`)은 session에서 만들어 요청마다 같다. 응답은 `{"response": …}` frame이고 root error, prompt 차단, finishReason 없는 끝은 성공이 아니다. Gemini가 functionCall에 붙인 thought signature는 tool call에 실려 그 turn의 이력(`tool_use.signature`)을 따라가고, 같은 turn의 다음 요청에 그대로 돌려보낸다(서명 없이 먼저 온 조각의 서명은 다음 functionCall에 붙인다). 저장한 이력에는 남지 않아 앞 turn의 functionCall에는 서명 검사를 건너뛰는 표시를 싣는다. output 상한은 보내지 않는다. 계정 project가 없는 credential로는 turn을 시작하지 않는다.
- **OAuth 발급자 호출(MCP, provider, 앱 OAuth)은 대기열 하나로 runtime이 대신 보낸다.** core module graph에는 외부 fetch가 없다. core가 요청(https이거나 loopback http, GET·POST)을 `lophn-agent/issuer-requests.ts`에 놓고 agent runtime의 `issuer-pump.ts`가 machine 입구(`TakeIssuerRequest`·`FinishIssuerRequest`)로 가져가 보낸 뒤 답한다. 요청과 응답 본문은 작업 메모리에만 있다. 계정 model 목록 GET(Bearer)도 이 대기열이 나른다.
- **custom provider가 알려 주는 model 목록은 찾기 위한 것이다.** custom provider는 연결 form에서 API(Chat Completions, Responses, Anthropic Messages)를 고르고, 그 값이 정의의 `protocols`와 provider의 `protocol`이 된다. 요청 경로와 인증 header는 내장 provider와 같다(Anthropic Messages는 `x-api-key`). 내장 정의가 아니고 OAuth도 아닌 provider는 연결 직후와 사람의 `RefreshProviderModels` 때 core(`lophn-agent/providers/model-list.ts`)가 `GET {endpoint}/models`(OpenAI 호환 `data[].id`)를 같은 발급자 대기열로 읽어 `credential.reported_models`에 둔다. 정의의 `models_endpoint`는 https만 담으므로 주소는 provider의 endpoint에서 만든다(local http 주소도 같다). `api_key`면 `provider.<id>` 값을 endpoint와 같은 origin에만 Bearer로 붙인다. 실패하면 저장하지 않아 앞 목록이 남고 명령은 `unavailable`이다. 내장 provider와 OAuth provider에는 `invalid_input`이다: 내장 provider의 `/models`에는 embedding 같은 model이 섞여 고를 목록을 망친다. 이 목록은 고를 것을 보여 줄 뿐 목록 밖 이름을 막지 않는다. 연결 직후 화면(`desktop/settings/providers/connect-host.tsx`)이 목록을 한 번 다시 읽어, 찾았으면 도착한 창에 찾은 수를 한 줄로 보이고, 없으면(실패나 빈 목록) Manage models의 그 provider 묶음과 model 정보 form을 바로 연다. 기본 model 고르기는 그 뒤다. 이 읽기는 Bearer만 붙이므로 Anthropic Messages 주소에서는 대개 실패해 form으로 간다.
- **stdio MCP 서버의 env는 값만 받는다.** 실행 파일은 대조할 목적지가 아니라서 secret을 넘기지 않는다. 설정 schema가 `{secret}`을 거절한다.
- **model catalog는 동봉 snapshot 위에 models.dev 갱신을 덮고, 사람이 적은 custom model 정보가 맨 위 user 층이다.** snapshot은 판을 낼 때 `tools/models-snapshot.ts`가 만들고, 실행 때 갱신(24시간에 한 번 공개 GET, 설정 `lophn-agent.model.catalog_auto_update`로 끈다)이 같은 변환을 쓴다. catalog는 고를 수 있는지를 정하지 않고 정보(한도, option 축, 입력·출력 형식, 가격)만 준다. 고를 목록은 provider가 알려 준 목록이 있으면 그것, 없으면 그 정의의 catalog 항목이고, 어느 쪽이든 사람이 정보를 적은 그 정의의 model을 더한다(`selectableModels`). 다른 정의의 catalog 항목은 이름이 같아도 빌리지 않는다(같은 이름도 provider마다 한도가 다르다). 사람이 적은 정보(`SaveUserModelInfo`·`RemoveUserModelInfo`·`ReadUserModelInfo`, compare `seq`)는 custom 정의에만 받고(내장·OAuth 정의 key는 `invalid_input`) ledger에 둔다. derived `catalog.json`은 깨지면 snapshot으로 다시 만들어 사람이 적은 것을 잃기 때문이다. catalog를 읽는 세 곳(`ReadModelCatalog`, turn resolver, 저장 검사 `checkChoice`·session model)이 모두 그 정보를 `source: "user"` 항목(`models/user-entry.ts`)으로 만들어 같은 열쇠의 catalog 항목 위에 둔다. 사람이 안 적은 한도는 turn이 칸마다 아래 기본 한계로 채운다. core는 어느 provider에서나 목록 밖 model 이름을 받는다(화면에서 이름을 적는 길은 Manage models의 custom provider [Add model]뿐이다). catalog에 없는 이름은 option 축 없이 기본 한계(context 131072, output 4096, tool 지원)로 돌고, 호출 기록의 basis에 `model_listed: unknown`으로 남는다. 이름이 틀리면 provider 호출이 거절해 기존 실패 길(`model_unavailable`)로 드러난다. 거절하는 것은 구독 OAuth 계정의 허락 목록 밖 이름뿐이고, 저장 검사(`checkChoice`, session model)는 목록을 보지 않는다.
- **한 호출의 output은 `min(32000, output_limit, context_limit / 4)`이다(`models/binding.ts`의 `cappedOutput`).** OpenAI 계열이 보내는 `max_tokens`와 입력 예산이 남기는 output 몫(`run-loop/prepare.ts`, `session/compactor.ts`)이 같은 값이다. vLLM 계열은 입력과 `max_tokens`의 합이 context를 넘으면 거절한다. context의 4분의 1로도 묶어 작은 context model이 창 대부분을 입력에 쓴다. Anthropic은 `min(output_limit, 32000 + thinking 예산)`이다. Cloud Code Assist는 상한을 요청에 싣지 않고(계정 model의 상한을 모른다) 입력 예산만 같은 몫을 남긴다. Chat Completions의 effort `maximum`은 `"max"`로 보내고, Responses에는 그 값이 없다.
- **call의 추정 비용은 겹치지 않는 token 구간 × 그 call의 `price_basis` 요율이다(`usage/cost.ts`의 `estimatedCost`).** 새 입력, cache read, cache write, output을 각자 요율로 곱한다. cache 요율이 없으면 input 요율로 센다. 저장된 `input`은 adapter가 이미 cache를 뺀 새 입력이라 다시 빼지 않는다(`cache_in_input`은 provider가 원래 어떻게 세는지를 적은 표시다). provider는 금액을 주지 않아(OpenAI·Anthropic·b.ai 응답의 `usage`는 token 수뿐) 금액은 늘 `estimated`이고, 가격이 없으면 `unknown`이다. 계산한 비용을 보이는 화면은 없다(`ReadAgentUsage`로 읽는다).
- **model을 고르는 세 자리(대화의 picker, Settings → Agents의 Default model, agent·project 정의의 Model 칸)는 같은 picker이고 고르기만 한다(`conversation/model-picker/model-picker.tsx`).** 붙인 provider의 model 가운데 켠 것만 provider별로 보이고, 지금 고른 model은 꺼져 있어도 보인다(`orderPicker`는 켠 목록 또는 지금 model에 있는 것만 낸다). 지금 model이 어느 층(이 대화 > agent 정의 > project > 전역 기본값)에서 왔는지 한 줄로 보인다. 정의 읽기의 `effective.model.source`는 project place에서 agent가 고르지 않았고 project에 model이 있으면 `project`다. 맨 아래 "Manage models" 줄이 Manage models 창(`model-picker/manage-models.tsx`, host는 `desktop/settings/providers/manage-models-host.tsx`)을 연다. 그 창에서 provider마다, model마다 켜고 끄고, "+ Connect provider"로 연결 창(`connect-host.tsx`)을 연다. 붙이면 그 provider 묶음이 맨 위에 온다. model 행에는 입력 형식 icon과 context가 보인다. custom provider 묶음에는 목록 다시 읽기와 [Add model]이 있고 model 행마다 [Edit]이 있다. 둘 다 model 정보 form(`model-picker/model-info-form.tsx`)을 연다. 저장한 정보는 user 층이라 다시 읽기가 목록을 provider 것으로 바꿔도 그 model이 남는다. 켠 model은 전역 목록 하나(`ReadShownModels`·`ChangeShownModels`, 칸 `provider`·`model_name`)에 적는다. 기본이 끔이라 새 provider와 새 model은 꺼져 나오고 사람이 Manage models에서 켠다. 사람이 model을 고르면(전역 기본, project, session 저장) core가 같은 transaction에서 그 model을 켠 목록에 더한다. 고른 model이 picker에 보여야 하기 때문이다. 전역 기본 model이 없을 때 session이나 project의 model을 처음 고르면 그 선택이 전역 기본으로도 저장된다. 다음 대화가 model 없이 실패하지 않게 하려는 것이다. 전역 기본 model이 없을 때 provider를 붙이면 기본 model 고르기 창이 뜬다. 켠 model이 아직 없으므로 그 창의 picker는 켠 목록과 상관없이 고를 수 있는 model 전부를 보이고(`showAll`), Manage models 줄이 없다.
- **compact는 사람이 부르거나, 이전 대화가 커지면 다음 turn을 시작하기 전에 runtime이 한다.** 같은 model이 요약하고, 요약 대상 원문은 data 경계로 감싸 지시로 읽히지 않게 한다. turn의 첫 call이 예산의 절반보다 크고 그 가운데 이전 대화가 예산의 5분의 1 이상이면, 또는 turn이 `context_limit`으로 끝나면, 그 session의 다음 turn을 시작하기 전에 runtime(machine 자격)이 Compact 요청을 열고 바로 요약한다(`packages/core/lophn-agent/run-loop/driver.ts`, `session/compactor.ts`의 `compactNow`). 이전 대화는 turn 안에서 줄일 수 없어서 turn 사이에 줄이고, 남는 절반이 turn 안 tool loop의 자리다. 요청과 event(`CompactStarted`, `CompactEnded`)는 사람의 Compact와 같다. 요약할 것이 없으면 요청을 열지 않는다. 실패해도 turn은 그대로 시작한다. 이 판단은 runtime 메모리에 있어 runtime이 다시 뜨면 잊고, 그 뒤 넘치는 turn이 다시 정한다. agent는 Compact를 열지 못한다(`session/guards.ts`의 `requireUserOrMachine`). 요약은 앞 요약이 있으면 그것을 갱신하고, 끝에 답을 기다리는 질문이나 요청이 있으면 그대로 남긴다.
- **skill은 목록(이름과 설명)만 prompt에 넣고 본문은 tool로 읽는다.** 꺼진 skill은 목록에서 빼고 읽기도 막는다. 도는 turn은 시작 때 읽은 판을 쓴다. `skill.read`는 `path`를 빼면 본문이고, `path: "SKILL.md"`(과 `./SKILL.md`)도 같은 본문이다. `path`는 SKILL.md 옆에 딸린 `.md` file 하나이고, 없으면 `not_found` 문장에 그 skill의 딸린 file 이름을 싣는다(없으면 `no bundled files`). model이 본문을 읽으려고 `path`를 채워 보내는 것이 실제 호출의 다수여서, `SKILL.md`를 실패시키면 읽을 길이 없다.
- **모든 place 종류에 같은 말은 제품 고정 규칙(`PRODUCT_INSTRUCTIONS`, `agent-places/prompts/prompts.ts`) 한 곳에 둔다.** place 종류 지침(`prompts/{home,project,app}.md`)에는 그 종류에만 맞는 말만 두고 agent 이름을 말하지 않는다. 같은 종류의 session은 agent가 누구든 같은 지침을 받고, 이름은 place 정보와 정의 본문이 준다. tool이나 skill이 일부 종류에만 있는 말은 고정 규칙에 "If you have …" 꼴로 둔다(`write-artifact`). `agent.create`는 세 종류 모두에 있어 그냥 쓴다. 넘기는 곳은 agent 이름과 place로 적는다(`to: {agent: "lophn", place: {app: "<name>"}}`). app 지침의 짓기 절차는 role이 있던 때 앱 담당 지침 그대로다. domain 폴더 설명은 내장 skill `make-domain`, kind 위반 다루기는 `write-kinds`이 맡는다.
- **일의 절차와 쓰는 법은 내장 skill이다.** 사람이 부르는 `new-app`·`repair-app`(home), `check-domains`·`write-workflow`(project), `write-kinds`·`write-artifact`(project, app), 설계 절차 `design-app`(app), 세 종류 모두에 가는 `make-domain`이 `agent-places/skills/`에 있다. app 지침은 짓기 전에 `design-app`을 읽으라고만 하고, `DESIGN.md`의 절, kit 찾기, 화면 원칙은 그 skill이 갖는다. lophn 사용법을 설명하는 skill은 없다. 선언(`BUILTIN_SKILLS`, `protocol/lophn-agent/skill-settings.ts`)은 이름, place 종류(`places`), `can_disable: false`, `menu`이고, 설명은 SKILL.md frontmatter 하나에 있다. 설명은 "읽을지"를 고르는 재료라 무엇을 하는 skill인지만 말하고, 절과 규칙은 본문에만 있다. 필요할 때 읽는 길은 `skill.read` 하나다. 설정의 뜻은 `settings.get`이 읽는다.
- **`/` 명령은 session 조작 built-in 여덟(new, rename, archive, compact, fork, mcp, skills, permissions)과 skill뿐이다.** 메뉴 항목은 `{name, title, description, source: builtin | skill}`이고 묶음은 Commands와 Skills 둘이다. `/이름 글`은 `Use the "<skill>" skill for this request.` 뒤에 빈 줄과 사람이 친 글을 이어 그 session의 다음 turn 사람 메시지로 접수한다(renderer가 잇는다, `conversation/agent-tab-core-source-commands.ts`). 내장 skill은 `menu: true`인 것만 메뉴에 뜨고 사람이 쓴 skill(전역, domain)은 늘 뜬다. built-in 이름과 같은 skill은 메뉴에서 빠진다(읽기는 된다). model 없이 tool을 바로 부르는 명령은 없다.
- **agent 정의의 `domains`와 `skills`는 일할 domain과 받을 skill을 고른다.** `domains`가 비어 있으면 그릇의 active domain 전부를, 있으면 그 가운데 고른 것을 맡는다(`ResolvedAgent.domains`). 받을 skill은 환경이 준 skill(내장, 전역, domain 층) 가운데 전역·내장 skill과 맡은 domain의 skill이 후보이고, `skills`가 비어 있으면 후보 전부를, 이름이 있으면 그 이름만 받는다. 끌 수 없는 내장 skill은 고르지 않아도 늘 받는다. prompt의 skill 목록, `skill.read`, `/` 메뉴가 같은 규칙(`skillReceived`)을 쓴다. 내장 skill은 선언한 role의 agent만 발견한다. prompt 목록, `skill.read`, `/` 메뉴, Agents 탭의 skill 수가 같은 발견(`extensions/skills.ts`의 `discoverSkills`)을 쓰고, 사람 화면(`ReadSkills`)만 place 종류 없이 모두 본다. 모든 agent 정의(lophn 포함)가 이 칸을 쓰고, 전역과 project 층의 끄기 설정(`skills_off`)은 그대로 층마다 있다.
- **place 정보에는 잘 안 바뀌는 목록만 넣는다.** 열린 session 목록과 앱 화면 상태는 넣지 않는다. 화면에서 본 것은 annotation이나 메시지로만 들어온다.
- **project place의 session에는 `Workflows folder:` 줄이 실린다.** 그 project의 `workflows/` 절대 경로다(`<data>/projects/<prj>/workflows`, turn 시작에 만든다). workflow 목록과 instance 상태는 싣지 않는다. 정의와 오류는 `workflow.list`, instance는 `workflow.get`으로 읽는다. flow의 `flow.ts`는 실행하지 않고 `workflow.check`(project place만)로 type check한다. 받은 step 메시지 하나가 그 agent가 workflow에 대해 받는 전부다(`architecture/workflow.md`).
- **lophn의 place 정보에는 domain 지도가 실린다.** domain마다 이름, 주인(project나 앱), 목적, 주인 앱의 활성 release가 내놓은 그 domain의 공개 tool(키, effect, 설명), 그 공개 tool을 쓰는 다른 domain을 이름 순으로 program이 결정적으로 조립한다. 설치한 package(`이름@version`)는 domain이 아니라 주인 앱의 줄에 붙는다. 쓰는 관계는 `app.usage`가 할당과 invocation 기록(부른 session이 맡은 domain)에서 읽고, 다른 domain의 관계를 보는 lophn session만 읽는다. 예산을 넘으면 tool 설명을 빼고(short), 그래도 넘으면 domain 이름과 주인만 싣는다(bare). 같은 package나 공개 tool을 여러 domain이 쓰는지는 지도에 있고, 그 뜻을 읽어 기획에 쓰는 것은 lophn이다.
- **kind 글은 program이 쓰고 있는 domain의 kind 파일에서 결정적으로 조립한다.** domain마다 한 덩이로, kind 이름, 한 줄, glob, key, 칸 이름과 type만 싣는다. 같은 kind 파일이면 같은 글이고, 바뀜은 그 파일의 hash로 본다(`project-docs/architecture/kinds.md`).
- **사람에게 묻는 중 사람이 그 session에 메시지를 보내면 기다림을 끝내고 그 메시지를 tool 결과로 넘긴다.** 그것이 답인지는 LLM이 읽는다. harness가 뜻을 가리지 않는다.

## 왜 이 모양인가

- **지침 반영: 대화 끝에 덧붙이기.** 조사한 harness는 세 갈래다. session 시작에 고정(Claude Code, Hermes)은 며칠 열린 lophn session에서 `LOPHN.md` 수정이 안 닿는다. 매 call 다시 조립(Goose)은 call마다 prefix가 흔들린다. 바뀐 것을 대화 끝에 notice로 알리는 Codex와 OpenCode를 따르되, system은 turn 시작마다 지금 지침으로 만든다. 지침은 거의 안 바뀌어 편집 뒤 첫 turn의 cache miss 한 번이 싸고, notice를 session 기록에 저장해 prefix를 고정하는 쪽은 비용이 크다. 옛 설계(매 model call 직전에 다시 읽기)는 Goose 쪽이었고 버렸다.
- **sandbox를 따로 두지 않는다.** 조사한 harness 여덟 가운데 경계를 기본으로 켜는 것은 Codex 하나다. lophn agent는 coding agent보다 직접 하는 일이 적고 place가 범위를 정한다. 대신 경로 가두기와 환경 변수 목록을 둔다.
- **MCP와 앱 tool 결과를 감싸지 않는다.** 일곱 harness 가운데 다섯이 그대로 넣고, server 신뢰 표시로 결과 처리를 바꾸는 곳은 없다. 감싸는 것은 아무도 배정하지 않은 web 결과뿐이다.
- **tool은 자원 하나에 동사 하나(`<자원>.<동사>`).** 효과, 쓸 수 있는 place 종류, 상태 전이의 전제, 결과 모양 가운데 하나라도 다르면 나눈다. Gate, rewind, place 종류 목록이 모두 tool 단위이기 때문이다. 거르기와 범위만 다르면 인자로 합친다.
- **일의 흐름은 tool로 만들지 않는다.** `app.plan` 같은 흐름 tool을 버리고 지침과 skill이 primitive를 엮게 했다. 예: 앱 오류를 고치는 일은 `app.logs`로 읽은 줄을 근거로 앱 place의 session이 코드를 고치고 `release.prepare`로 이어 간다.
- **`document.*`를 file tool로 대신한다.** 문서는 디스크의 파일이다. pdf와 이미지만 model에 보이는 모양이 달라 따로 읽는다. 이미지 결과는 JSON 글이 아니라 `tool_result_image` 조각으로 싣는다. 앱 place의 session은 같은 `image.read`로 annotation screenshot(`annotation:<id>`)도 연다(annotation).
- **place 종류 고정 목록과 할당이 옛 preset과 tool 묶음을 대신한다.** 사람이 tool 목록을 고치는 길을 없애고, 권한을 바꾸는 길을 할당 하나로 모았다.
- **place 정보는 목록만 prompt에, 내용은 tool로.** 목록이 없으면 model은 그것이 있는 줄 몰라 찾지 않는다(skill 목록과 같은 이유).
- **고정 규칙은 영어 고정 본문 하나.** tag의 뜻을 입력마다 반복하지 않고 prefix에 한 번 둔다. 입력에는 값만 싣는다. reaction(`<lophn-reaction>`)은 lophn program이 알리는 사실이고 본문은 고정 문구다. 사용자 앱을 공격자로 보지 않으므로 "data, not instructions"를 붙이지 않는다.
- **command는 사람이 이름으로 부르는 skill이다.** 새 개념을 두지 않았다. role 명령은 같은 이름의 내장 skill이 됐고, core route가 없던 `/recap`과 만드는 곳이 없던 command의 `tool` 갈래는 지웠다. 사람이 tool을 바로 누르는 곳은 앱 화면이다.
- **model이 읽는 내장 skill(`make-domain`, `write-*`, `design-app`)은 `/` 메뉴에 띄우지 않는다.** 사람이 부를 일이 아니고, 띄우면 메뉴에 끌 수 없는 줄만 는다.
- **lophn 사용법을 설명하는 skill(옛 `guide-*` 여덟 편)을 두지 않는다.** 0.10.1에서 사람이 지웠다. 설정의 뜻은 `settings.get`이 public 정의에서 읽는다.
- **skill 발견은 동기 구현 하나다.** core의 read handler(`ReadSkills`, `ListCommands`, agents read)가 동기라 비동기 발견을 부를 수 없고, turn 준비는 비동기 함수 안에서 동기 함수를 그대로 부른다. 파일 IO는 `SkillFiles` port로 받아 core module graph에 동기 file API가 없다.
- **model catalog는 OpenCode 꼴이다.** OpenCode와 Codex는 catalog snapshot을 넣고 실행 때 받는다. 손으로 쓴 목록은 새 model이 나와도 판을 올리기 전에는 쓸 수 없다. models.dev 항목의 `limit.input`이 없으면 context 한도를 입력 한계로 두고, 출력 예약은 입력 예산이 따로 뺀다.
- **오래된 이미지만 빼고 기록은 그대로 둔다.** tool 호출 기록과 그 출력 blob에는 이미지 base64가 남는다. 기록에서 빼는 길은 model call이 막히지 않으니 실제로 막힐 때 한다.
- **tool 정의를 늦게 싣는 꼴은 Claude Code의 ToolSearch와 Hermes의 bridge를 합쳤다.** tool 정의가 role prompt, skill 목록, tool을 합친 고정 부분의 약 80%였고(role마다 34~52개), Anthropic 문서는 30~50개를 넘으면 고르는 정확도가 떨어진다고 한다. 처음에는 Anthropic만 `defer_loading`으로 숨기고 다른 provider는 모두 실었다. 공통 경로는 Hermes처럼 늘 있는 진입점(`tool_call`)으로 부르게 하고, loop가 기록 전에 대상으로 풀어 권한·실행 경로를 하나로 둔다. 옛 `tool.search`는 정의를 결과 글로 주고 model이 선언되지 않은 이름을 부르게 해 provider가 받는다는 보장이 없었다. 지금은 선언된 `tool_call`을 부른다. 숨김을 tool 정의마다 표시하던 `defer: true`는 place별 노출 정책 하나로 바꿨다: 무엇을 처음부터 쓰는지는 place 종류마다 다르고, 표시와 정책을 둘 다 두면 어긋난다(roadmap `tool-lazy-loading.md`, 2026-10-29).
- **keyword 검색 대신 묶음 이름으로 불러온다.** 내장 `<자원>_<동사>`, 앱 `<domain>_<tool>`, MCP `mcp__<server>__<tool>`이 모두 이름 앞부분이 묶음이라 접두사 하나로 된다. 한 작업에 필요한 묶음은 한 번에 부른다(예: 앱 배포 `release`·`preview`). native 경로는 매 요청 숨긴 정의를 모두 실어 불러온 이름을 `tools[]`를 위해 따로 추적하지 않는다. custom provider는 `anthropic-messages`여도 proxy나 호환 API가 `defer_loading`을 모를 수 있어 공통 경로다. OpenAI responses의 `tool_search`는 아직 연결하지 않았다(`plan/context-cache`의 `defer-responses`).
- **kind 글은 받은 domain의 것만 받는다.** 정의의 `domains`가 비면 그릇의 domain 전부, 있으면 그 가운데 그릇에 있는 것이다. 일을 좁히는 것은 `domains`와 skill이다. kind 글, `DOMAIN.md`, 앱 tool이 모두 같은 domain 단위로 좁혀지므로 따로 고르는 칸을 두지 않는다.
