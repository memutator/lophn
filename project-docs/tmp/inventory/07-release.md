## 문서끼리 어긋난 것

1. **req-0825 확인 줄이 옛 방식이다.** 3번째 줄 "migration을 DB 사본에 돌려 표나 열이 지워지거나 row 수가 줄면 그 내용을 보이고…"는 S7 6장·11장 2, req-1520("DB 사본에서 migration을 돌려 손실을 재지 않는다")과 정면으로 어긋난다. 같은 줄의 "external app-api를 선언한 release는 사람이 허락하기 전에는 activate되지 않는다"도 S7 6장("app-api가 더해지는 것은 activation에서 묻지 않는다. agent grant가 효과별 기본값으로 받는다")과 `specs/approval.md` 55·57행에 어긋난다. 어느 쪽을 따를지 사람이 확정해야 한다(이 목록은 spec을 따랐다).
2. **`changes.md` 4장 app-releases 줄**("migration을 DB 사본에서 잰다")과 `docs-review.md` 955행("data 손실 가능 migration은 묻는다(사본에서 잼)")이 낡았다. S7 11장 2가 이긴다.
3. **`changes.md` 2장 activation 줄**에 "migration이 없는 release는 선언 비교만 한다"만 있고 TicketVerified는 3장 뒤에 따로 적혔다. S7 5장이 정본이다.
4. **필수 검사 "22개"**: docs-review와 `changes.md` 3장은 `definitions.ts`가 22개라고 적었으나 지금 정의는 runner 3 + harness 18 = 21개에 실패 경로가 선언 code마다 하나씩 더해진다. 같은 파일을 가리켜도 숫자가 다르다. 남길 넷(선언·구현 일치, 의존, migration, 되돌림)과 지금 이름의 대응(`blueprint_handler_match`, `fixed_sdk`, `migration_empty`+`migration_upgrade`, `revert_restore`)은 req-0818 문장에서 이 목록이 짚은 것이고 문서가 이름까지 정하지는 않았다.
5. **req-0818은 "넷"인데 acceptance와 req-0820·0821이 그 안을 풀어 쓴다.** `migration_empty`·`migration_upgrade`를 합쳐 하나로 셀지 둘로 셀지 문서에 없다.
6. **req-1361 "지난 고친 기록"**: 고친 기록(`ProblemFixRecorded`)이 problems에서 사라졌는데 coding agent가 CLI로 읽는 종류에 남아 있다. ticket 완료 보고(req-0744)에서 읽는다는 뜻으로 보이나 문서가 잇지 않았다(06과 같이 확인).
7. **AGENT-ROLE H2("앱을 처음 activation하거나 새 release가 선언을 넓히면")**와 S7 6장 비교 정의: 이전 활성 release가 없을 때 무엇과 비교하는지 S7이 말하지 않는다. 첫 activation은 사람이 허락한다는 H2를 따라 "선언 전부가 늘어난 것"으로 가정했다.
8. **S7 11장 4(activation 줄)와 req-0829 rejected**: rejected의 이유가 "당연한 구현 품질"이라 줄에 세우는 동작을 요구가 직접 받지 않는다. S7이 정했으므로 spec만 따랐다.
9. **req-0054(storage 기동 실패)**와 요구는 이 영역이 아니다. req-0057의 gap은 위 "고칠 것"에 올렸다.
10. **S7 3장 표의 "Invocations: 이전 release의 changeset을 지운다"**와 S5 6장의 "지금 활성 release 것만 둔다"는 같은 말이다. 어긋나지 않는다.
