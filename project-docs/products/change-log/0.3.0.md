# 0.3.0

## model이 받는 글을 코드에 맞춤

```yaml
modules: [packages/core/agent-roles, packages/coding-agent, packages/sdk, packages/core/apps, packages/protocol, packages/core/problems, packages/core/lophn-agent]
checked: [architecture-annotation, architecture-place-session]
```

- 전: role 지침, coding agent skill, 앱 template, 받은 turn의 입력이 지금 코드에 없는 skill·tool·test 종류·reaction을 말했다. 받은 turn의 입력과 뒤 turn의 history가 bytes로 달랐다.
- 후:
  - lophn 소개 줄은 "registers apps"만 말한다. App Engineer 지침은 "the acceptance check"와 "the app stopped restarting after repeated crashes"를 쓴다.
  - App Engineer는 앱을 만들거나 기능을 더하는 ticket에 보고할 실패 분기와 이름을 적고, 고친 release가 active가 된 뒤에만 problem을 resolved로 바꾼다(고친 release 없이 닫아야 하면 `ask`). program이 resolved를 막는 것은 아직 아니다(AGENT-ROLE A15).
  - Project Manager는 경계와 계약 위반 때 계약과 문서 중 무엇을 고칠지 스스로 정하고 이유를 대답에 남긴다. 사람에게는 용어의 뜻만 묻는다(AGENT-ROLE C6).
  - `lophn-build-app` skill은 ticket의 실패 분기마다 `reportProblem`을 두게 하고, cap-problem guide는 이름으로 묶는 규칙을 쓴다. `lophn-repair` skill은 ticket의 check 하나를 따르고, `app test`가 `unavailable`이면 돌리지 못한 확인과 이유를 보고에 적는다.
  - 앱 template `AGENTS.md`의 managed 절은 skill 둘, `lophn ticket show`, 설치 사본의 `guide.md`, 의존 변경은 App Engineer에게 청하기만 가리킨다. `withStore`는 저장소를 여는 일만 `store_unavailable`로 바꾸고 업무 일의 예외는 그대로 던진다.
  - `reproduction` test 종류와 그 연결 칸(`problem`, `basis_seq`, `reports`, `before`, `after`), 동결 test의 `symptom`, `app test` 입력의 `ticket_source`, `ListVerifications`의 `problem` filter를 지웠다.
  - 받은 메시지의 봉투와 `messages` 표에 `reply`(call의 답 방식), `event`(reaction의 event type), `fail_reason`(실패한 답의 이유)이 생겼고, history가 그것으로 받은 turn의 입력과 같은 글을 만든다. `callInput`·`reactionInput`은 지웠다.

왜: eval이 재기 전에 틀린 줄로 알고 있는 것을 없앤다. reproduction은 runner를 줄일 때 지운 길이라 되살리지 않는다.

결정:
- 저장 모양이 바뀌었다(`messages`의 칸 셋). schema step을 그 자리에서 고쳤고 migration은 없다. 개발 data(`.dev-data/`)는 지우고 새로 만든다. (agent)
- PM 판단은 PM이 정한다(사람). 답 방식(`reply` 속성과 "answer with the reply tool" 줄)은 받은 agent가 결과를 답하게 하는 줄이라 지우지 않는다.

후속: `test_command` check를 runner가 돌리지 않는 것은 `issues/coding-agent.md`에 남는다. 고친 release 없는 resolved를 program이 막는 것은 `issues/problems.md`에 남는다.

## 설정 화면의 command 봉투를 하나로 모으고, Operator의 MCP server를 runtime이 쓰고, 보낸 chip을 대화에 남긴다

```yaml
modules: [packages/shell/renderer, packages/core/lophn-agent, packages/core/main, packages/protocol]
checked: []
```

- 전: 설정 화면이 command 봉투에서 `compare`를 빼서 provider 연결과 기본 model 바꾸기가 core에 닿기 전에 `invalid_input`으로 거절됐다. Operator 편집 화면이 저장한 `mcp_servers`는 runtime이 읽지 않아 조용히 안 쓰였다. 보낸 context·위반 chip이 대화 본문에 없었고, 실패한 turn을 다시 보내면 chip이 빠졌다.
- 후:
  - 봉투: renderer 전체가 `command-call.ts`의 helper 하나로 봉투를 만든다. 설정에서 provider 연결과 기본 model 바꾸기가 다시 된다.
  - 설정의 일반 통로(`SettingsSource`)에서 화면이 부르지 않던 MCP·skill 폴더 함수를 지웠다.
  - Operator MCP: turn 준비, runtime child의 `--allow-run`·`--allow-net`, `mcp.` secret 목적지, Grants 목록(`agent-mcp-tools/list`가 Operator id를 받음)이 Operator 정의 층의 server를 안다. 정의가 바뀌면 child가 다시 뜬다.
  - 정의 층 server의 credential 이름은 `mcp.<agt id>.<server>`다. 새 Operator는 저장 전에 id를 받고, 저장 뒤 보호 입력 창이 값을 받는다. 내장 role 편집 화면에서 Add server 단추를 뺐다.
  - chip: 본문에 chip마다 `attached` part가 남고(`context` id 포함) 다시 보내기가 그 part로 `SendMessage.attached`를 되살린다.
- 계약: `agent-mcp-tools/list` 입력과 `request-take` 출력에 `agent`(Operator id 또는 null)가 생겼다. 본문 `attached` part에 optional `context`가 생겼다. 옛 모양은 남기지 않았다.

왜: 사람이 설정에서 provider를 하나도 붙이지 못했고, 화면이 보이는 Operator MCP는 실제로는 안 쓰였고, 같은 project의 server와 secret 이름이 겹치면 한 server의 secret이 다른 server의 origin으로 갈 수 있었다. 봉투는 화면마다 손으로 짜서 한 곳의 실수가 연결 기능 전체를 막았다.

결정:
- 봉투 helper는 `compare`를 기본값으로 채우지 않는다. 필요한 route에서 빠뜨리면 type이 잡는다.
- Operator에게도 자기 MCP server가 필요하다(사람). 권한과 승인은 project 층 server와 같은 규칙을 쓰고 새 규칙은 만들지 않았다. server를 넣는 길은 사람의 Operator 편집 화면뿐이고 agent tool은 `mcp_servers`를 받지 않는다.
- Operator의 `mcp_off`는 Grants 목록에 적용하지 않는다. 끈 server의 tool도 사람이 미리 assign할 수 있다.
- 이름 접두(`mcp.<agt id>.`)는 core가 강제하지 않고 편집 화면이 만든다. 정의를 쓰는 것은 사람뿐이고 project 층도 같은 신뢰다.
- 정의 층 server의 OAuth 로그인은 만들지 않았다(편집 화면은 none·bearer·api_key만 받는다).
- 개발 data: 정의 file에 `mcp.<project id>.<server>` 이름을 쓴 server는 그대로 동작한다(이름을 다시 쓰지 않는다).

후속: 없음

## ChatGPT 계정이 쓸 수 있는 model만 고르게 하고, 구독 OAuth를 진짜로 확인하는 live 길을 둠

```yaml
modules: [packages/core/lophn-agent, packages/core/main, packages/protocol, packages/shell/renderer, tests]
checked: [agents-md, tool-dev]
```

- 전: ChatGPT로 연결한 provider에서 catalog의 `openai` model이 모두 보였다. 계정이 못 쓰는 model을 고르면 turn이 provider 거절로 실패했다. 구독 OAuth는 fake 발급자로만 확인했다.
- 후:
  - core가 연결 직후와 token을 건넨 뒤(갱신 직후, 목록이 아직 없을 때)에 같은 Bearer로 `GET /v1/models`를 읽어 `credential.account_models`에 둔다. 읽기는 token 넘기기를 기다리게 하지 않고, 실패하면 앞서 저장한 목록을 남긴다.
  - resolver는 목록 밖 model을 `not_found`로 거절하고, 대화의 model picker와 agent 편집의 Model 칸은 같은 거름(`accountAllows`)을 쓴다. 목록이 `null`이면(API key provider, 못 읽음) 전과 같이 모두 보인다.
  - `deno task test:live:login`: live 전용 root(`.dev-data/live/home`)에 사람이 진짜 ChatGPT 로그인을 한 번 저장하고 계정 model 목록 응답 모양을 찍는다. `deno task test:live`는 그 root가 있으면 구독 token으로 turn을 돌려 계정 목록·`subscription` 과금 경로·(만료 5분 전이면) refresh token 회전을 단정한다.
- 계약: `ProviderCredential.account_models: string[] | null`, command `RecordProviderAccountModels`가 생겼다. 발급자 요청 header 값 상한이 512에서 4096으로 올랐다(Bearer + JWT). `provider_credentials` 표 step에 열이 늘어 옛 개발 data는 새로 만든다.

왜: 계정마다 쓸 수 있는 model이 다른데 화면이 몰라서 사람은 고른 뒤 실패해서야 알았다.

결정:
- 목록을 읽지 못하거나 모양이 틀리면 `null`(거르지 않음)로 둔다. 잘못 읽어서 model을 전부 숨기는 쪽이 못 읽는 쪽보다 나쁘다. (agent)
- live root에 쓸 수 없는 credential이 있으면 `test:live`는 이유를 찍고 실패한다. 조용히 넘기면 만료를 숨긴다. (agent)
- 이미 목록 밖 model이 기본값으로 저장돼 있으면 picker는 그 이름을 보이되 고를 목록에는 없고, turn은 `not_found`로 실패한다. 저장 검사(`checkChoice`)는 목록을 보지 않는다.

후속: 첫 진짜 로그인에서 `data[].id`·`visibility` 칸 이름이 맞는지 확인한다(틀리면 `providers/account-models.ts`의 상수 한 곳).

## 재사용할 것과 진단 근거를 agent가 읽고, ticket을 App Engineer가 쓴 app-api 예시로 확인하고, 앱이 cap 셋을 쓴다

```yaml
modules: [packages/core/apps, packages/core/agent-roles, packages/core/problems, packages/core/main, packages/core/secrets, packages/core/supervision, packages/protocol, packages/coding-agent, packages/sdk, tests]
checked: [architecture-layers, architecture-approval, architecture-activation, tool-package-linux, tool-worktree-prep, tool-check-deps]
```

- 전: lophn과 App Engineer가 내장 SDK와 다른 앱의 app-api를 볼 길이 없었다. `cap-fs`, `cap-net`, `cap-secret`은 `deno.json`이 없어 깔리지 않았고, 깔려도 앱 supervisor가 기계 밖으로 나가지 못했고 secret 전달이 늘 `unavailable`이었다. App Engineer와 coding agent는 보고의 message, details, log 본문을 읽지 못했다. agent가 고친 release 없이 problem을 resolved로 바꾸면 같은 release의 새 발생이 묻혔다. ticket의 `test_command` check는 돌릴 길이 없어 program이 확인할 수 있는 업무 check가 없었다.
- 후:
  - 내장 SDK: `package.list`가 `builtin` 칸에 설치 사본의 `@lophn/*` 이름과 판을 싣고, `package.get`이 `@lophn/` 이름이면 설치 사본의 판과 `guide.md`를 읽는다(route `packages.builtin`). `@lophn/ui`의 guide는 분류별 export index다.
  - 다른 앱의 app-api: tool `app.app_api`가 모든 active 앱의 이름·설명과 app-api 목록을 주고, 앱을 주면 입력 모양도 싣는다(route `app.app_api_index`). lophn과 App Engineer의 목록에만 있고, 두 지침이 읽으라고 한다.
  - cap 셋: 세 SDK가 설치된다. 앱 supervisor가 host 없는 net으로 뜨고 broker가 요청마다 선언 ∩ grant로 목적지를 검사한다. loopback 목적지는 http, 나머지는 https이고 lophn 자기 port는 막는다. 앱이 `useSecret`을 부르면 supervisor가 core route `apps.secret_value`로 값을 한 번 받아, 같은 invocation의 같은 목적지 요청에 `Authorization: Bearer`로 붙인다(60초 만료). 앱은 값을 보지 못한다. `lophn-build-app` skill이 세 SDK를 말한다.
  - 보고 본문: App Engineer tool `problem.body`와 coding agent 명령 `problem body`, `problem occurrence`가 message, `report_details`, log 본문을 읽는다. `problem.get` tool은 latest에 message 앞 2,000자와 details hash를 싣는다. tool 설명이 실제로 주는 것과 맞다.
  - resolved: agent 자격의 `problem.set_state`는 마지막 발생의 release보다 뒤에 activate된 active release가 있을 때만 resolved로 받고, 아니면 `conflict`다. 사람은 전과 같다.
  - ticket 확인: check가 `app_test`, `examples`, `text`다. `examples`는 App Engineer가 쓴 app-api 예시(api, input, expect) 1~20개다. 완료 보고가 나면 program이 보고된 release의 격리 사본에서 예시를 불러 비교하고, 결과를 ticket에 남긴다. `ticket.verify`는 `examples` ticket을 pass가 기록된 뒤에만 verified로 받는다. coding agent는 예시를 고치지 못한다. `lophn-repair`·`lophn-build-app` skill, App Engineer 지침, 앱 template `AGENTS.md`가 이를 말한다.
  - Reactor가 `VerificationRecorded`(program 일)를 받는다.
  - memory route: core가 기동 때 팀이 등록한 memory route와 wiring이 붙인 handler를 대조해 한쪽만 있으면 뜨지 않는다. handler만 있고 등록이 빠져 늘 `not_found`이던 여섯 route(`apps.secret_value`, `blueprints.check`, `packages.builtin`, `packages.publish`, `session_inputs.steer_now`, `session_inputs.remove`)를 등록했다. 그래서 앱 secret, App Engineer의 `blueprint.check`·`package.publish`·내장 SDK 읽기, 대화에서 대기 중인 메시지를 지금 turn에 넣기(steer)와 지우기가 실제 core에서 처음 돈다.
- 계약:
  - 생긴 것: route `packages.builtin`, `app.app_api_index`, `apps.secret_value`(supervisor의 machine 자격만), `problems.report_body`의 field `report_details`, test kind `examples`, 도메인 event `VerificationRecorded`, tool `app.app_api`·`problem.body`, CLI `problem occurrence`·`problem body`.
  - 바뀐 것: ticket check와 `RequestTest`·verification의 kind가 `test_command` 대신 `examples`다. broker `secrets/use`의 destination scheme이 `http`도 받는다(loopback만). `launch-spec`은 `net_any`를 agent runtime과 apps supervisor에 허락한다. 앱 secret은 `secretAttach`가 이름 앞머리가 없는 이름으로 알아보고 앱을 대신하는 호출(`conditions.app`)에만 보낸다.
  - 지운 것: `test_command` check와 `PreparedAdmission.unavailable`, 옛 `createSecretAllowance`(`secretAllowanceOver`가 대신한다), broker의 닫힌 secret 전달 기본값.
  - 저장 모양이 바뀌었다(`verifications.kind`의 check). schema step을 그 자리에서 고쳤고 migration은 없다. 개발 data(`.dev-data/`)는 지우고 새로 만든다.

왜: lophn이 있는 것으로 될 일을 새 앱으로 기획하고, 앱이 외부 API와 secret을 쓸 길이 없고, 원인 설명을 못 읽은 채 problem 이름 하나로 수리하고, 고치지 않은 problem이 닫혀 앱이 계속 실패하는데 아무도 몰랐다. ticket은 coding agent가 쓴 test로 채점하면 자기 채점이 되므로 사람의 요구에서 뽑은 예시를 program이 돌려야 했다.

결정:
- cap 셋을 모두 살린다(사람). 앱은 사람이 켠 바깥 서비스(같은 컴퓨터의 서비스 포함)로만 나가고, 비밀값은 lophn이 붙이며 앱은 값을 보지 못한다. 구현은 supervisor에 host 없는 net, 목적지 검사는 broker, loopback만 http, secret 전달 adapter다. (agent)
- 다른 앱의 app-api 목록은 lophn과 App Engineer만 본다(사람). App Engineer의 자격은 자기 앱 하나로 묶여 있어, 기존 `app.list`·`app.get`·`app.app_api`의 검사는 넓히지 않고 앱 이름·설명과 app-api 목록만 주는 새 read `app.app_api_index`로 연다. 다른 앱의 source, problem, ticket은 열지 않는다. (agent)
- agent의 resolved는 program이 막는다(사람). 고친 release 없이 닫을 일은 agent가 사람에게 묻는다.
- ticket은 App Engineer가 쓴 예시를 program이 돌려 확인한다. `test_command`는 지운다(사람). 새 runner를 만들지 않고 app test runner가 앱을 격리 사본에서 부르는 길을 다시 쓴다.
- 예시 비교 규칙: 객체는 `expect`의 key가 다 있고 값이 맞아야 하고(실제에 key가 더 있어도 된다), 배열은 길이가 같고 원소가 차례로 맞아야 하고, 나머지는 `===`다. 오류로 끝난 호출은 불일치다. (agent)
- `ticket.verify`의 관문은 check가 `examples`인 ticket에만 건다. `app_test`와 `text`는 전과 같다. (agent)
- 내장 SDK는 catalog에 등록하지 않고 설치 사본이 정본으로 둔다. 비밀값은 지금 `Authorization: Bearer`로만 붙이고 다른 방식은 쓰는 앱이 생길 때 더한다. 보고 본문은 이슈가 추천한 넷(message 앞부분, log 본문, details, tool 설명)을 모두 한다. (agent)
- 고친 길의 자동 확인은 기존 E2E table에 행으로 더했다(예시 확인, agent 자격의 `problem.body` 읽기, loopback `cap-net`·`cap-secret` 호출). 새 E2E file은 만들지 않았다. (agent)

후속: `package.publish`와 앱끼리 call(`app_connections`)은 아직 E2E로 확인한 적이 없다. turn 준비가 예외로 끝나도 기록이 남지 않는 것은 `issues/agent-definition.md`에 올라 있다.

## provider를 붙이고 model을 고르는 흐름을 하나로: provider가 알려 주는 목록, 이름 직접 적기, 같은 picker

```yaml
modules: [packages/core/lophn-agent, packages/core/main, packages/protocol, packages/shell/renderer, packages/design, tools]
checked: [architecture-appearance, skill-wording, tool-wording, tool-models-snapshot]
```

- 전: provider는 Settings → Providers에서만 붙였고, model은 세 자리(대화 picker, Settings → Agents의 Default model, Operator 편집의 Model)가 서로 다른 칸으로 골랐다. custom provider는 model 목록을 읽지 않아 사람이 이름을 알아야 했고, 목록이 있는 provider는 catalog 밖 이름을 거절했다. 지금 model이 어디서 왔는지 보이지 않았다.
- 후:
  - custom provider를 붙인 직후와 사람이 "Refresh models"를 누를 때 core가 `GET {endpoint}/models`를 읽어 `credential.reported_models`에 둔다. 실패하면 앞 목록이 남고 화면이 한 줄로 알린다. ChatGPT 계정 목록과 같은 칸과 같은 대기열이다.
  - model 이름은 어느 provider에서나 직접 적어 고른다. catalog에 없는 이름은 기본 한계로 돌고 호출 기록에 `model_listed: unknown`으로 남는다. 구독 OAuth 계정의 허락 목록 밖 이름만 거절한다.
  - 세 자리가 같은 picker를 쓴다. 붙인 provider만 보이고, 맨 아래 "Connect provider" 줄이 연결 창을 열고 연결 뒤 그 provider 묶음으로 돌아온다. 지금 model이 온 층(이 대화, 이 agent, project default, Workspace default)이 한 줄로 보인다.
  - 전역 기본 model 없이 provider를 처음 붙이면 기본 model 고르기 창이 뜬다([Skip] 있음).
  - gallery에 picker의 빈 상태, 따르는 상태, custom provider, 다시 읽기 실패, Operator picker, 기본 model 창 page가 생겼다.
- 계약:
  - 이름이 바뀐 것: credential 칸 `account_models` → `reported_models`, 명령 `RecordProviderAccountModels` → `RecordProviderModels`.
  - 생긴 것: 명령 `RefreshProviderModels`(사람, compare 없음, 내장·OAuth provider에는 `invalid_input`, 읽기 실패는 `unavailable`), protocol 함수 `selectableModels`·`entitlementAllows`·`typedNameAllowed`.
  - 바뀐 것: 정의 읽기의 `effective.model.source`와 목록 줄의 `model.source`에 `project`가 나온다.
  - 지운 것: `snapshotModelListed`, `ModelCommandDeps.modelListed`, renderer의 `customProvidersOf`와 `custom` 칸.
  - 저장 모양이 바뀌었다(credential 칸 이름). 개발 data(`.dev-data/`)는 지우고 새로 만든다.

왜: 사람이 custom provider를 붙이고도 model을 고르지 못했고, provider 설정과 model 설정이 너무 떨어져 있었다. opencode와 hermes처럼 고르는 자리에서 붙이고 바로 고르게 했다.

결정:
- 저장은 provider와 model을 따로 두고, 흐름은 하나로 잇는다(사람: "opencode, hermes 식으로").
- 이름은 직접 적을 수 있다. 구독 OAuth provider의 목록만 허락 목록으로 보고, custom provider의 목록은 찾기 위한 것이라 목록 밖 이름도 받는다. catalog는 정보만 준다. (agent)
- custom provider의 model은 다른 provider 정의의 catalog 항목과 이름이 같아도 정보를 빌리지 않는다. 같은 이름도 provider마다 한도가 달라, 빌리면 예산이 틀린다. 그래서 custom model은 option 축 없이 기본 한계로 돈다. (agent)
- 내장 API key provider의 `/models`는 읽지 않는다(embedding 같은 model이 섞인다). (agent)
- 연결 직후 목록 읽기는 다시 시도하지 않는다. agent runtime이 host 없는 net이라 새 주소도 runtime 재시작을 기다리지 않는다(손으로 확인). (agent)
- reasoning effort는 picker 안의 option 축으로 둔다. (agent)
- 앞 항목의 "목록이 있는 provider가 모르는 model 이름은 계속 거절한다"를 이 항목이 바꾼다.

후속: 화면 모양은 사람이 gallery에서 보고 고른다. 연결 직후 목록 읽기가 실패하면 사람이 다시 읽기를 눌러야 한다.

## model picker는 고르기만 하고, 보일 model과 provider 연결은 Manage models 창에서 한다. Settings에서 돌아가는 단추


- 후:

  - 즐겨찾기가 없어지고 끈 model 목록이 생겼다. 새 provider와 새 model은 켜져 나온다.
  - Settings 머리에 "Back"이 있다. Settings를 열기 전 화면(같은 project, 앱, session)으로 돌아가고, 없으면 launcher다.

왜: 고르는 곳과 등록하는 곳이 섞여 picker가 무엇을 하는 곳인지 흐려졌다. opencode처럼 picker는 고르고, 무엇을 보일지와 provider 연결은 한 창에서 한다.

결정:
- picker는 고르기만 한다. 즐겨찾기를 없애고 켜기·끄기 하나로 둔다. 새로 붙인 provider는 모두 켠다. Settings에 앞 화면으로 돌아가는 단추를 둔다(사람).
- 끈 것만 적는다(기본이 켬). provider toggle은 그 provider의 지금 model을 하나씩 적는다. 지금 고른 model은 꺼져 있어도 picker에 보인다. "Change defaults…"를 빼고 기본 model은 Settings → Agents에서 정한다. 이름 더하기는 custom provider 묶음에 늘 두고 `reported_models`에 붙인다(새 칸 없음). (agent)
- 내장 provider의 catalog 밖 새 model은 화면에서 고를 길이 없다. catalog 갱신(24시간)을 기다린다. (agent)

후속: Back은 Settings를 열 때의 route로 돌아간다. workspace 안에서 session을 옮긴 뒤면 화면의 session이 아니라 route의 session으로 돌아갈 수 있다(workspace와 앱 공간이 보이는 session을 위로 알리지 않는다).

## 탭을 workspace 위에 띄우고 상단 bar로 접음

## custom provider model 정보를 catalog 모양으로 적고, output 상한을 32000으로 올린다

```yaml
modules: [packages/core/lophn-agent, packages/protocol, packages/shell/renderer, packages/design, tools, tests]
checked: [agent-role, architecture-layers, architecture-approval, architecture-testing, architecture-eval, architecture-agent-call, architecture-place-session, architecture-agent-definition, architecture-appearance, architecture-workspace-layout, architecture-ui-kit, context-component-registry, tests-support, tool-e2e, tool-test-live, tool-eval, tool-check-deps, tool-models-snapshot, tool-check, tool-wireframes, tool-worktree-prep, tool-wording, tool-package-linux, tool-dev, skill-ui-design, skill-wording]
```

- 전: custom provider model은 이름뿐이라 effort를 고를 수 없었다. context는 131072, 입력은 text, 가격은 모름으로 돌았다. OpenAI 계열 호출은 catalog model도 output 4096에 묶였다.
- 후:
  - Manage models의 custom provider 묶음에 [Add model], 행마다 [Edit]이 있다. 둘 다 model 정보 form을 연다. form 칸은 한도 셋, tool 지원, 입력·출력 형식(text, image, audio, video, pdf), reasoning effort 단계와 기본값, 가격 넷(input, output, cache read, cache write, USD per 1M)이다.
  - 적은 정보는 catalog의 user 층이 된다. picker의 effort 줄, turn의 한도와 image 허용, 호출 기록의 추정 비용이 그 정보를 쓴다. Refresh가 목록을 바꿔도 남는다.
  - Manage models의 모든 model 행에 입력 형식 icon과 context가 보인다.
  - 한 호출의 output은 min(32000, output 한도, context의 4분의 1)이다. Chat Completions effort의 최고 단계는 `max`로 보낸다.
  - custom provider 연결 form에서 API(Chat Completions, Responses, Anthropic Messages)를 고른다. 연결 직후 목록을 한 번 읽어, 찾았으면 찾은 수를 보이고, 없으면 Manage models의 그 provider와 model 정보 form을 바로 연다. Settings → Providers에서 연결하면 그 provider 줄 아래에도 결과 한 줄과 [Manage models] 또는 [Add model]이 화면을 떠날 때까지 남는다(이미 기본 model이 있으면 뜨는 창이 없어 결과가 안 보였다). key 안내는 header를 말하지 않고 제목에서 "optional"을 뺐다(https 주소는 key가 있어야 한다).
- 계약:
  - 생긴 것: custom provider 입력의 `protocol`(`CUSTOM_PROTOCOLS`), Manage models 열기의 `first`·`notice`·`addModel`·`onClosed`, 명령 `SaveUserModelInfo`·`RemoveUserModelInfo`(사람, compare `seq`, 내장·OAuth 정의 key는 `invalid_input`), 읽기 `ReadUserModelInfo`(resource `user-model-info`), `MODEL_MEDIA`의 `pdf`, `OUTPUT_CAP`·`cappedOutput`, workspace agents source의 `userModels`·`saveModelInfo`·`removeModelInfo`.
  - 바뀐 것: `selectableModels`가 그 정의의 user 항목을 더한다. 저장 검사(`checkChoice`, session model)가 user 항목을 본다.
  - 지운 것: workspace agents source의 `addModelName`, `ProviderChoice.revision`, Manage models의 `canAddName`, `catalog.json`에서 user 항목을 읽던 길, prepare의 `reservedOutput` dep, compactor의 `RESERVED_OUTPUT`.
  - 저장 모양이 바뀌었다(표 `model_user_info`, `model_user_info_seq`). schema step을 그 자리에서 고쳤고 migration은 없다. 개발 data(`.dev-data/`)는 지우고 새로 만든다.

왜: 사람이 hive와 b.ai 같은 custom provider를 붙여도 effort를 고를 수 없었고, 한도와 가격을 넣을 길이 없었다. opencode와 omp는 이 정보를 설정 파일로만 받고, hermes는 가격을 받지 않는다. 화면에서 받는 곳은 없었다.

결정:
- 사람이 적는 칸은 catalog 항목 모양이고, 적은 effort는 고를 수 있다. modality는 icon으로 보이고 고칠 수 있다. runtime이 아직 못 쓰는 형식도 자리를 만든다. 가격을 받아 비용 추적에 쓴다. output 상한은 32000이다(사람).
- 저장은 ledger에 한다. derived `catalog.json`은 깨지면 다시 만들어 사람이 적은 것을 잃는다. custom 정의에만 받는다. 이름 더하기는 user 정보를 만들고 `reported_models`에 붙이지 않는다. Chat Completions effort의 `maximum`은 `"max"`로 보낸다. `pdf`를 더한다. 가격 빈칸은 모름, 0은 무료다. 안 적은 한도는 null로 두고 칸마다 기본값으로 돈다. output 상한은 context의 4분의 1로도 묶는다. 32000만 걸면 context 32768인 catalog model의 입력 예산이 768이 된다. (agent)
- custom provider 연결은 쓸 수 있는 model로 끝난다. 연결 form에 API 고르기를 둔다(사람). custom header와 key를 env var·command로 받기는 하지 않는다(hive와 b.ai 모두 쓰지 않는다). provider의 API가 못 보내는 effort 값(Responses의 Max 등)은 form에서 막지 않고 turn이 `invalid_input`으로 실패한다. (agent)
- 앞 항목들의 "custom model은 option 축 없이 기본 한계로 돈다"와 "이름 더하기는 `reported_models`에 붙인다"를 이 항목이 바꾼다.

후속: 비용 계산의 cache 요율과 대화 화면의 비용 합은 다음 계획 `model-cost`다(roadmap `model-cost.md`). model 정보 읽기는 page를 따라가지 않는다(model 몇 개를 기준으로 했다).

  - 탭과 bookmark 목록에 page favicon이 보인다.
  - Settings에 Browser pane이 생겼다: bookmark 목록(고치기, 지우기)과 Clear browsing data(확인 뒤 cookie·storage·cache를 지우고 열린 page를 다시 load한다).
  - floated 패널 위쪽 가장자리의 회색 선을 지워 강조선만 보인다.
- 계약:
  - 생긴 것: shell IPC `ipc/browser.ts`(navigate, command, adopt, clear-data, devtools open·close·window, bookmarks list·add·update·remove, push state·event·bookmarks-changed)와 preload `window.lophnBrowser`. 탭 kind `browser`(layout `{key, url}`), renderer 전용 transient kind `browser_devtools`. overlay choice의 `image`(data URL). design `Palette` item의 `image`. `TabHost.openFloat(tab, size?)`, `TabHost.viewKeeps`, `openTabIn`의 `after`. project 창의 `webviewTag`.

왜: terminal에서 dev server를 띄우거나 로그인할 때 lophn 창과 OS browser를 오가야 했다.

결정:
- browser는 새 탭 kind이고 terminal·editor와 같은 pane에 들어간다. 크기 준 popup은 floated 탭으로 연다. bookmark를 둔다(사람).
- 보통 탭은 `<webview>`, 크기 준 popup과 DevTools만 native view다(사람, 2026-10-19). native view는 DOM 위에 그려져 menu·패널이 page 밑에 깔렸다. 표준 Electron에는 popup contents를 `<webview>`에 넣는 길이 없다(ChatGPT desktop은 고친 Electron으로 한다). dock한 popup은 같은 주소의 `<webview>`로 다시 연다(사람).
- DevTools는 Chrome처럼 탭 안에 붙고 floating·분리를 고른다(사람). `<webview>`는 DevTools를 담지 못해 native view에 붙이고, 자리를 바꿀 때 view를 옮긴다(실험).
- favicon을 보인다(사람). roadmap의 "favicon 하지 않는다"를 뒤집었다. main이 page session으로 받아 data URL로 싣는다(agent).
- toolbar menu는 overlay로 띄운다. 별 popover는 `<webview>` 탭에서 이름 칸을 둔다(사람).
- 규칙은 rea `desktop-embeded-browser`를 TS로 옮겨 짰고 dependency로 넣지 않았다. partition은 persistent 하나다. localhost·사설 IP를 막지 않는다. tab cap, site list, capability 승인, storage mode는 두지 않는다(agent).

후속: terminal이 여는 URL과 Ctrl-click link를 browser 탭으로 보내는 `$BROWSER` bridge와 link를 열 곳 설정은 계획 `browser-bridge`다. 열린 이슈: `project-docs/issues/shell.md`(page에 focus가 있으면 Ctrl+W·Ctrl+Tab이 듣지 않는다), `project-docs/issues/browser-tab.md`.

## coding agent에 맡긴 일이 조용히 멈추지 않게

```yaml
modules: [packages/core/lophn-agent, packages/core/agent-roles, packages/coding-agent, packages/protocol, packages/shell/renderer, packages/design]
checked: [architecture-eval, agent-role, architecture-place-session, architecture-approval, architecture-agent-definition, architecture-workspace-layout, skill-wording]
```

- 전:
  - coding agent가 `lophn message send`로 물으면 App Engineer가 받는 봉투에 답하는 길이 없었다. 글로만 답하면 터미널에 가지 않아 coding agent가 멈췄다. `lophn message send --help`는 `refs (선택, array)`로만 적었다.
  - Claude Code가 새 앱 source 폴더마다 folder trust를 묻는 동안 hook이 돌지 않는데, lophn 화면에는 아무것도 보이지 않았다.
- 후:
  - coding agent가 보낸 call의 봉투에 `Plain text does not reach its terminal. To answer, use call with to:{session:"<id>"} and reply:"conversation".` 한 줄이 붙는다. App Engineer 지침에 같은 길과 "`to:{role:"coding_agent", place}`는 새 ticket 맡기기 전용"을 적었다.
  - CLI help가 입력 칸의 schema description을 보인다. `refs`는 "ticket IDs, e.g. ["tkt_…"]"다.
  - 터미널을 열고 5초 안에 첫 hook 신호가 없는 coding session(첫 신호가 `SessionStarted`인 harness)이 대기 목록에 "Check the terminal"로 보인다. 누르면 그 탭으로 focus가 가고, 첫 신호·session 끝·터미널 exit에 사라진다.

왜: eval의 첫 진짜 run에서 두 길 모두 사람 모르게 맡기기가 멈췄다.

결정:
- 답하는 길은 봉투와 지침으로 알린다(사람). 답할지, 무엇을 답할지는 App Engineer가 정하고 core는 글을 터미널로 보내지 않는다. 그 줄은 `from.kind === "coding_agent"`로 정한다. 받은 turn과 뒤 이력이 같은 함수로 같은 bytes를 만들어 cache가 깨지지 않는다(agent).
- `lophn message send --help`가 `refs`는 ticket id 문자열의 배열이라고 적는다(agent).
- trust는 대기 목록으로 알린다(사람). 화면 글은 긁지 않고 `~/.claude.json`은 쓰지 않는다. 조건은 core가 아니라 shell renderer가 센다(agent). 5초는 정상 SessionStart가 오는 시간의 기록이 없어 정한 값이다(agent).

후속: App Engineer 지침과 `packages/core/lophn-agent`, CLI·protocol이 바뀌어 eval의 `instruction:app-engineer`, `runtime`, `core`가 올랐다. 그래서 commit된 eval run은 낡음으로 보인다. 그대로 두고 계획 `eval-experiment`의 baseline이 새로 잰다. 열린 이슈: `project-docs/issues/coding-agent.md`(`session.list`에 열린 coding session이 없음, 뒤에 연 창에는 첫 신호 대기 항목이 없음).

## 열린 coding session이 목록과 모든 창에 보임

```yaml
modules: [packages/core/router, packages/core/main, packages/core/agent-roles, packages/protocol, packages/shell/renderer]
checked: [agent-role, architecture-place-session, architecture-eval, architecture-approval, architecture-agent-definition, boundary-catalog]
```

- 전:
  - App Engineer의 `session.list`에 열린 coding session이 없었다. 봉투가 없는 turn(같은 앱의 새 App Engineer session, 사람이 "그 coding agent에게 전해"라고 할 때)에서는 도는 coding agent에게 말을 걸 id를 몰랐다.
  - "Check the terminal"(`coding_start`)은 터미널이 열릴 때 runtime을 받은 창에만 떴다. 뒤에 연 창에는 없었고, event stream이 다시 붙은 뒤에는 이미 시작한 session에 잠깐 잘못 뜰 수 있었다.
- 후:
  - `session.list`가 끝나지 않은 coding session을 `role: "coding_agent"`, `place: {kind:"app", id}`, 이름은 harness label로 싣는다. `find`와 같은 `transport: "harness"` 대상이라 그 id로 `to:{session}`을 보내면 PTY에 닿는다. 목록 상태에 `waiting`이 생겼고 coding session만 낸다. grant가 deny인 상대와 자기 자신은 지금처럼 뺀다. `queued_coding`은 그대로다.
  - App Engineer 지침에 한 줄: 도는 coding agent는 `session.list`에도 보이고, 봉투가 없으면 그 id로 `call`을 `to:{session}`, `reply:"conversation"`으로 보낸다. 목록에 없으면 새 ticket으로 맡긴다.
  - session snapshot이 coding session의 `harness`를 싣는다(선택 칸, lophn session은 싣지 않는다).
  - 대기 목록이 snapshot에서 `unknown`이고 첫 신호가 `SessionStarted`인 harness의 coding session도 runtime 길과 같은 5초로 센다. snapshot에서 첫 신호를 들은 session은 다시 세지 않는다.

왜: 계획 `coding-handoff`가 남긴 두 빈틈이다. 도는 coding agent를 App Engineer와 사람이 놓치지 않게 한다.

결정:
- `session.list`가 열린 coding session을 싣는다. Router `describe`가 coding session의 place와 state를 내고, `waiting`은 coding session만 낸다. 고르는 규칙과 `queued_coding`은 그대로다. (agent)
- App Engineer 지침에 한 줄을 더한다. 줄이 없으면 봉투 밖에서 이 길을 쓸 근거가 없다. (agent)
- coding session snapshot이 harness를 싣는다. 뒤에 연 창은 터미널 runtime을 받지 않아 SessionStart hook이 있는 harness인지 달리 알 길이 없다. (agent)
- 대기 항목은 snapshot으로도 센다. 첫 신호를 들은 session은 `done`에 넣어 다시 붙은 뒤 온 runtime event가 항목을 띄우지 않는다. snapshot 길은 창을 연 때부터 5초를 센다. (agent)

후속: `packages/core`, `packages/protocol`, App Engineer 지침이 바뀌어 eval의 `core`와 `instruction:app-engineer`가 올랐다. commit된 eval run은 낡음으로 보인다. 그대로 두고 계획 `eval-experiment`의 baseline이 새로 잰다. `project-docs/issues/coding-agent.md`의 두 이슈를 닫았다.

## terminal이 연 URL과 Ctrl/Cmd-click한 link가 browser 탭에 열림

```yaml
modules: [packages/core/config, packages/design, packages/shell/ipc, packages/shell/main, packages/shell/preload, packages/shell/renderer, packages/shell/terminal-host, tools]
checked: [architecture-workspace-layout, architecture-ui-kit, architecture-appearance, tool-check, tool-worktree-prep, tool-dev, tool-package-linux, skill-ui-design, skill-wording, tool-wording]
```

- 전: terminal의 프로그램이 연 URL(`gh auth login --web`, `python3 -m webbrowser`)은 OS browser로 갔다. terminal에 보이는 URL은 눌러도 아무 일이 없었다.
- 후:
  - project 창의 shell 탭(Linux·macOS)은 env에 `BROWSER`(앱이 켤 때마다 per-run 폴더에 쓰는 shim)와 `LPN_BROWSER_BRIDGE`를 받는다. 프로그램이 `$BROWSER <url>`을 부르면 browser 탭이 열려 선택된다. pane이 둘이면 terminal 반대쪽 pane, 하나면 terminal 바로 뒤, terminal이 floated이면 focus pane이다.
  - terminal에 보이는 http/https 주소를 Ctrl/Cmd-click하면 같은 규칙으로 browser 탭에 연다. 그냥 click은 text 선택이다.
  - Settings › Browser에 Links 구역: Web links와 Local links(localhost, `.local`, 사설 IP)를 각각 Browser tab 또는 System browser로 연다. 기본은 둘 다 Browser tab이다.
  - 탭을 열 수 없을 때(Settings·app space 화면, detached 창 안 terminal, coding 탭, 설정이 System browser, `http`·`https`가 아니거나 userinfo가 든 URL)는 OS browser로 간다. 사용자가 앱 env에 `BROWSER`를 두었으면 shell 탭은 그것을 그대로 쓴다. socket 경로가 너무 길거나 Windows이면 bridge가 꺼지고 지금처럼 OS browser다.
  - gallery: `browser-bridge-pane`, `browser-bridge-one-pane`, `settings-browser-links`, `settings-browser-links-system`.
- 계약:
  - 생긴 것: shell IPC `shell:terminal-link`, `shell:terminal-bridge-ack`(invoke), `shell:terminal-bridge-open`(push)과 `TerminalApi.openLink`·`ackBridgeOpen`·`onBridgeOpen`. terminal host `open` 요청의 `env`(restart도 같은 env). core 선언 설정 `shell.browser.web_links`·`shell.browser.local_links`(`browser_tab` | `system_browser`). socket protocol `{v:1,key,url}` 한 줄 → `{"result":"pane"|"declined"}` 한 줄. renderer 의존성 `@xterm/addon-web-links@0.12.0`.

왜: `vite`와 `gh auth login`을 하며 lophn 창과 OS browser를 오가지 않게.

결정:
- 범위는 shell 탭이다. coding 탭은 app space 패널에 붙어 browser 탭을 열 pane이 없다(agent).
- renderer가 탭을 연 뒤 ack해야 `pane`이고, 1500ms 안에 없으면 `declined`로 shim이 OS browser로 연다. URL이 조용히 사라지지 않게(agent).
- key는 terminal 탭마다 main이 발급해 host `open`이 성공하면 묶고 탭을 닫으면 버린다. 비교는 `Map` 조회다(socket이 0700 폴더 안 0600 file이다)(agent).
- per-run 폴더는 data root 아래가 아니라 core socket 폴더 규칙(`XDG_RUNTIME_DIR`)을 따른다. unix socket 경로 104 byte 한도 때문이다(agent).
- link 설정은 renderer가 밀지 않고 main이 요청마다 core에서 읽는다(agent).
- bridge는 `desktop/main.ts`가 아니라 `wiring/coding.ts`가 만든다(agent).

후속: coding 탭의 bridge, detached 창 안 terminal의 bridge, host가 죽은 뒤 다시 시작한 shell의 bridge는 `project-docs/products/roadmap/browser-tab.md`의 "남은 bridge 일"이다.

- detached 창은 탭 하나만, ×는 dock, 앱을 끄는 중에는 dock하지 않는다(다음 실행에 돌아온다). (agent)
- project 창 renderer가 detached까지 layout 전체를 갖는다. detached 창은 main을 거쳐 탭 하나를 받는다. (agent)
- detached 창 안 popup은 features 크기를 따르지 않고 기본 창 크기다. 그 창에서는 DevTools를 floated 패널로 둘 수 없다. (agent)

## 접어 둔 app panel, 뜨자마자 옮긴 popup, docked page 옆 경계의 버그 셋을 고침

```yaml
modules: [packages/shell/renderer]
checked: [architecture-workspace-layout, architecture-browser-tab]
```

- 전: 접어 둔 app panel을 다시 펴면 접을 때의 view state가 보였다. 크기 준 popup이 뜬 직후 Dock·Float하면 그 탭이 오류 화면이 됐다. browser page 옆 pane 경계의 잡는 띠가 page 쪽 절반이 page 밑에 깔렸다.
- 후:
  - 보관 중인 app view도 main이 미는 state(unresponsive, crashed, 연결 끊김)를 받아, 다시 펴거나 Detach할 때 최신 state를 보인다.
  - popup의 adopt 답 전에 다시 mount한 탭은 같은 adopt를 기다려, 거절 없이 popup을 이어 쓴다.
  - 경계 잡는 띠가 docked browser page 위에 그려지고 floated 패널은 여전히 그 위에 그려진다. floats 층은 stacking context가 아니다.

## detached 창의 알려진 틈 넷을 고침

```yaml
modules: [packages/shell/renderer, packages/shell/main, packages/shell/ipc]
checked: [architecture-browser-tab]
```

- 전: detached 창에서 같은 agent의 새 대화가 이미 있는 대화를 앞으로 가져왔고, DevTools를 floated로 옮기면 DevTools가 사라졌고, 크기 준 popup이 960×600으로 떴고, project를 떠났다 돌아오면 detached terminal이 PTY에 붙지 못했다.
- 후:
  - agent 새 탭의 key는 floated·detached 탭까지 보고 고른다. detached 창이 연 새 탭이 project 창의 다른 session 탭과 key가 겹치면 project 창이 새 번호로 연다.
  - detached 창의 browser 탭은 DevTools 자리 menu에 floated가 없다.
  - detached 창 안의 popup은 opener 창 가운데에 features 크기로 뜬다(화면 작업 영역 안으로 당긴다). detached 창만 최소 크기가 320×240이다.
  - 같은 실행 안에서 project를 떠났다 돌아오면 detached terminal이 같은 PTY에 다시 붙는다. 앱을 다시 띄우면 붙지 않는다.
- 계약: IPC `detached-changed`에 선택 칸 `resume`이 생겼다. `TabKindDef.resume`(terminal만 선언). `Workspace`와 `DetachedTab`의 TabHost slice는 `useTabHostSlices` 하나로 만든다(동작 같음, detached 창의 `openPath`는 이제 열린 파일을 먼저 본다).

왜: `project-docs/issues/workspace-layout.md`에 올려 둔 detached 틈이다.

결정:
- terminal의 PTY 참조는 detached 창이 알려 main이 든다. 떠날 때 창을 dock시키는 안은 창이 돌아오지 않아 고르지 않았다. 디스크에는 쓰지 않는다. (agent)

## 앱 app-api를 MCP tool 모양으로 바꾸고 coding agent에 MCP를 연다

```yaml
modules: [packages/protocol, packages/core/apps, packages/core/server, packages/core/lophn-agent, packages/core/problems, packages/core/main, packages/sdk, packages/coding-agent, packages/shell/main, packages/shell/renderer, packages/shell/preload, packages/shell/ipc, packages/design]
checked: [architecture-annotation, architecture-activation, architecture-approval, architecture-testing]
```

- 전:
  - 앱은 blueprint `app_api[]`(`key`, `label`, `input`, `effect`, `project_scope`)로 선언하고, 호출 route는 `app.call_api`(입력 `api`, `project`)였다. project 범위 app-api는 부른 쪽이 project를 정하고 앱은 `@lophn/cap-project`로 읽었다. 앱 view에는 project picker가 있었다.
  - preview 호출은 활성 release의 선언으로 판정해 release에 아직 없는 tool은 `not_declared`였고, 활성 release가 있으면 `mode: "preview"` invocation을 남겼다.
  - coding agent가 lophn에 닿는 길은 CLI 하나였다.
- 후:
  - 선언은 blueprint `tools[]` = `{name, title, description, inputSchema | null, outputSchema?, effect, public}`이다. 이름은 1~64자 `[A-Za-z0-9_.-]`, schema root는 `object`다. MCP annotation은 effect에서 만든다(`toMcpTool`). `public`은 칸만 있고 읽는 쪽은 계획 `domain-place`다.
  - 호출 route는 `app.call_tool`(입력 `{target, tool, input?, caller}`)이고 invocation operation은 `{kind: "tool", tool}`이다. `app.app_api`의 출력과 `app.app_api_index`의 항목은 `tools`다. index는 입력에 `app`이 있을 때만 `inputSchema`·`outputSchema`를 싣는다.
  - project 범위가 없어졌다: 선언의 `project_scope`, 호출의 `project`, 거절 code `project_required`·`project_mismatch`·`project_not_found`, route `app.projects`, broker `projects/list`, `@lophn/cap-project`, invocation의 `project` 칸과 필터, 앱 view의 project picker와 project 묶음.
  - SDK는 `tool(name, handle)`, `registeredTools`, `ToolRejection`, `connectTools`(client `callTool`), `@lophn/app-ui`의 `useTool`, `ToolButton`이다. 화면 bridge는 `window.lophnApp.callTool(tool, input)`, IPC `app:call-tool`이다.
  - agent tool은 이름(`app__<앱>__<tool>`)과 결과 mapping이 그대로이고 입력의 project 칸이 없다. ticket `examples` step은 `{tool, input?, expect}`다.
  - preview 호출은 그 preview bundle의 선언으로 판정하고 invocation을 남기지 않는다. 호출 길에 `previewOnly` 자격이 생겼다.
  - core가 coding agent용 MCP endpoint(`POST /mcp`, `2025-06-18`, POST만, session 없음)를 연다. coding token의 operation `coding.mcp`로 열고 그 앱의 tool만 보이며, MCP tools/call은 그 앱의 지금 도는 preview로만 간다(없으면 `unavailable`). Claude Code(`--mcp-config`), Codex(`-c mcp_servers.lophn.*`), OpenCode(`OPENCODE_CONFIG_CONTENT`)는 session 실행 계획에 이 endpoint를 싣는다. token은 env `LOPHN_CODING_TOKEN`에만 있다.
  - 화면 셋(앱 공간 첫 화면, 앱 화면 목록, agent grant의 앱 목록)이 지워진 route `apps/blueprint`를 읽어 비어 있던 것을 `apps/app_api`로 고쳤다.

왜: 앱이 내놓는 기능을 MCP tool 모양 하나로 맞춰 화면, SDK, agent, ticket, coding agent가 같은 선언을 쓰게 한다(roadmap `domain.md` "core가 아는 한 가지 모양"). 앱 code의 project별 data 나누기는 core가 지키지 못해 project 범위를 지웠다. coding agent가 자기 코드를 harness의 tool 호출로 확인하되 사용자 data에는 닿지 않게 preview로만 보낸다.

결정:
- 이름 바꾸기(app → domain tool, `app__` 접두, `app_api` grant 칸·approval kind·SDK package 이름)는 계획 `domain-rename`이 한다. 이 판은 그 이름들을 둔다.
- preview 호출은 기록을 남기지 않는다. ledger의 `release`를 비울 수 없어 release 없는 bundle의 호출은 기록할 자리가 없고, preview는 일회용 DB라 rewind 대상이 아니다. (agent)
- coding agent의 MCP 호출은 새 caller 종류 없이 `person` caller와 `previewOnly` 자격으로 들어간다. 새 종류는 ledger의 caller CHECK, caller 판정, rewind를 바꿔야 하는데 preview 호출은 기록이 없다. (agent)
- MCP tools/list는 preview가 돌면 그 bundle의, 아니면 활성 release의 선언이다. `listChanged`는 SSE가 필요해 내지 않는다. (agent)
- `app.app_api_index`는 앱 하나를 볼 때 호출 모양을 싣는다. agent tool `app.app_api`가 index만 읽어서다. (agent)
- Gemini CLI, pi, Hermes, OpenClaw는 MCP를 잇지 않는다. Gemini는 session마다 MCP를 넣을 길이 없고 pi는 MCP가 없다. (agent)

후속:
- 저장 모양이 바뀌었다(invocation 표의 `project` 칸과 색인). 개발 data(`.dev-data/`)는 지우고 새로 만든다. 이미 만든 앱은 옛 선언·SDK 이름을 써서 새로 만든다.
- e2e(`tests/e2e`)는 type check만 맞췄고 돌리지 않았다. `domain-rename` 뒤 다시 쓴다.
- eval materials는 `domain-rename` 뒤 새 판으로 다시 만든다(`project-docs/issues/eval.md`).

## coding agent가 preview를 띄우고 MCP로 인자 없는 tool을 부를 수 있다

```yaml
modules: [packages/core/apps, packages/coding-agent]
checked: [architecture-app-call, architecture-coding-agent]
```

- 전:
  - CLI `lophn app preview start`가 늘 `invalid_input`이었다. route 입력의 칸 `input`을 CLI가 자기 공통 key로 보고 지웠다.
  - 실제 bundle의 preview는 supervisor가 늘 거절했다. preview flags 검사가 쓰기 path를 일회용 폴더와 "같다"로 보았는데 앱 flags는 그 안의 DB file과 socket을 쓴다. 거절 이유는 core 오류에서 "app supervisor rejected the request"로 지워졌다.
  - coding agent MCP는 `inputSchema: null`인 tool을 늘 `invalid_input`으로 불렀다.
- 후:
  - CLI는 자기 flag가 만든 칸(`json`, `idempotency_key`)만 빼고 route 입력은 그대로 보낸다.
  - preview flags는 일회용 폴더 안의 쓰기만 받는다(`..`로 나가는 path는 거절). 읽기와 net 검사는 그대로다. supervisor의 거절 message가 core 오류에 실린다.
  - MCP는 인자 없는 tool을 `input` 없이 부르고, 그런 tool에 인자를 주면 앱에 보내지 않고 `isError`로 돌려준다.

왜: 계획 `domain-tools`의 손 확인에서 coding agent가 preview를 띄워 MCP로 앱 tool을 부르는 길이 이 셋에서 막혔다. 앞의 둘은 그 전부터 있었다(skill의 preview 확인 단계도 돌지 않았다).

## project의 context를 kind 파일과 내장 tool로 바꿈

```yaml
modules: [packages/protocol, packages/core/projects, packages/core/problems, packages/core/events, packages/core/agent-roles, packages/core/lophn-agent, packages/core/main, packages/shell/renderer, packages/shell/main, packages/shell/ipc, packages/design, tools, tests]
checked: [architecture-event, architecture-approval, architecture-workspace-layout]
```

- 전: project의 문서 모양은 context(계약 bundle, draft·test·submit 판, 선언한 search, glossary, saved view)가 정했다. PM은 `context.*` tool로 판을 내고, Operator는 정의의 `contexts` 칸으로 붙은 context만 받았다. 위반은 `ContextViolationFound`와 context·위반 chip으로 PM에게 갔다. shell에는 Contexts·Context 탭, 선언 search, 문서 info의 Contexts 탭이 있었다.
- 후:
  - project마다 kind 파일 `<data>/projects/<prj>/kinds.yaml` 하나가 문서 모양을 정한다. 판이 없다. 파일이 바뀌면 검사해 맞으면 바로 쓰고, 틀리면 앞의 맞던 kind를 계속 쓰고 problem을 연다.
  - kinds worker(`documents/kinds`, `derived/kinds.sqlite`)가 문서를 읽어 item을 뽑고 칸을 검사하고 index에 둔다. core가 project 폴더와 kind 파일을 감시한다.
  - agent tool `kind.list`(조건, 정렬, 집계, `skipped`), `kind.check`, 모든 role의 `file.outline`이 생겼다. project place에서만 그 project를 읽는다.
  - 문서 위반은 project problem(`project_problems`)이다. 새로 열리거나 다시 열린 위반이 있으면 `KindViolationFound`가 PM session을 연다. PM은 `problem.list`에 `project`를 주어 읽는다.
  - prompt에 PM·Operator의 `<lophn-kinds>` 글이 실리고, kind 파일이 바뀌면 `kinds_changed` notice가 붙는다. PM의 place 정보에 `Kinds file:` 줄이 있다.
  - PM의 file 범위에 `kinds.yaml` 하나가 file 항목으로 더해졌다. agent runtime의 쓰기 권한은 `<data>/projects` 전체에서 project마다의 `kinds.yaml`로 좁아졌다. `file.write`는 부모 폴더가 없을 때만 만든다.
  - 내장 skill은 `context-init`·`context-update` 대신 `kinds-yaml` 하나다.
  - context의 표·route·worker·tool·화면·wording·eval 재료(`tax-receipts` → `tax-kinds`)와 Operator 정의의 `contexts`·`app_reads`, project record의 `tracking`, context·위반 chip을 지웠다. toast와 설정의 reaction 줄은 Kind violation이다.
- 계약:
  - 새 route: `kind.get`·`kind.list`·`kind.check`(core memory route), `problem.sync_project`(machine), `problem.list_project`. 새 event `KindViolationFound {project, count}`와 reaction grant 칸 `KindViolationFound`.
  - 지운 것: `context.*`·`glossary.*`·draft·bundle route와 표, `ContextViolationFound`, id 접두 `ctx`·`cbn`·`chk`·`trm`·`ser`·`viw`, tab kind `contexts`·`context`와 선언 search 탭, `attached`의 `context`·`violation` 종류, notice `contexts_changed`, 정의 issue code `missing_reference`·`archived_reference`.
  - 개발 data는 지우고 새로 만든다(옛 표와 옛 Operator 정의의 `contexts:`는 읽히지 않는다).

왜: roadmap `project-docs/products/roadmap/domain.md`의 1단계다. 판과 선언 search가 하던 일을 바뀔 때의 검사, rewind, 부를 때 짜는 조회로 줄였다(`project-docs/architecture/kinds.md`).

결정:
- tool 이름은 `kind.list`·`kind.check`, event는 `KindViolationFound`, 내장 skill은 `kinds-yaml`이다. (agent)
- `kind.list`의 조건은 세 층(묶음, 묶음, leaf)까지다. 깊이를 묶음 셋으로 읽으면 tool 하나의 JSON schema가 18KB였다. 모든 role의 모든 요청에 실리므로 약 6KB로 줄였다. (agent)
- project problem은 앱 problem과 표·route가 따로다. 한 목록으로 합칠지는 `domain-rename` 뒤에 본다. (agent)
- kinds worker는 `sync`에서만 훑는다. 읽기가 훑으면 그 결과가 위반 비교를 거치지 않는다. (agent)
- 위반의 정체성은 JSON 배열 글로 저장한다. NUL로 이은 글은 node:sqlite가 잘라 읽어, 둘째 sync부터 `problem.sync_project`가 늘 `internal`로 실패했다(실제 core probe에서 찾음). (agent)
- 경로에서 뽑는 칸(`from: path`)은 `list`일 수 없다. kind 파일 schema가 거절한다. (agent)
- operators-home 재료의 판은 나중에 land하는 쪽(이 계획 또는 domain-place)이 두 변경을 합쳐 `@3`으로 만든다. (agent, planner)

닫은 이슈: "md가 아닌 문서는 context로 쓸 수 없다"(`project-docs/issues/archived/contexts.md`). kind는 어느 형식의 파일도 item으로 받는다.

후속: 열린 이슈 `project-docs/issues/agent-definition.md`("붙인 것(`attached`) 기구가 file 종류만 남았고 아무도 만들지 않는다").
