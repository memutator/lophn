# Observations and diagnosis in lophn: facts for the eval design

Read-only investigation of /home/pyosechang/projects/lophn (HEAD e4f69ac0f). All paths are repo-relative. Counts and limits are quoted from code. Items marked INFERENCE are my reading, not a stated rule.

## 0. Ten facts that matter most

1. Two kinds of observation reach `problems`: (a) the app's own `reportProblem(name, message, details?)` ("named" report, source `app`) and (b) platform-observed exceptions (source `exception`): uncaught error / unhandledrejection in the app process, an Error thrown out of an app-api handler, process exit/crash, and view errors. Only (a) needs the app author to place anything. (b) is automatic.
2. The App Engineer (AE) prompt, both coding-agent skills and the blueprint say NOTHING about where to place `reportProblem`. The only instruction is two lines in the scaffolded app's `AGENTS.md.tmpl` plus one example call site in the scaffold's `app-api.ts.tmpl`. See section 4.
3. `createExceptionObserver` is not an app-level call. The runtime entrypoint installs it before app code loads (`packages/core/apps/runtime/entrypoint/main.ts:67-74`). `createProblemReporter` is also installed by the entrypoint (`main.ts:75-96`). App code only calls `reportProblem`. So "does the app call createExceptionObserver" is the wrong grader check; it is always installed.
4. `problem.get` (the AE's only problem-reading tool besides `problem.list`) does NOT return the message or details of a `reportProblem` report. For a named report the latest snapshot has `error: null` (`packages/core/problems/reporting/worker/collector.ts:553-559`), so AE sees only: problem name, state, counts, releases, 20 occurrence stubs, invocation id and a log-evidence stub (hash, line count). `report_details` has no read route at all. See section 3.
5. For exceptions, `problem.get` does return `error.name`, `error.message`, up to 32 source frames (`path`, `function`, `line`, `column`) resolved against the sealed bundle copy, and a stack hash (not the stack text).
6. Problem states are `open | resolved | ignored` only (`packages/protocol/problems/problem-record.ts:14`). Nothing resolves a problem automatically. A problem leaves `open` only via `problem.set_state` (AE for its own app, or a user). A resolved problem is reopened by a live occurrence only if the occurrence's release was activated after the resolve time (`packages/core/problems/reporting/model.ts:107-115`).
7. The "problem tests" subsystem (`packages/core/problems/tests/*`) is a platform verification runner, not a place where AE or the coding agent author reproduction tests. `app_test` = fixed platform checks (5 checks, none checks business logic). `test_command` = a `deno test` run requested for a ticket check, with test files written by the coding agent. `reproduction` is in the schema but `RequestTest` rejects it (`packages/core/problems/tests/commands.ts:48-50`).
8. Ticket evidence kinds: `problem`, `ticket`, `release`, `file` (path only, no line), `annotation` (`packages/protocol/coding-agent/ticket/values.ts:91-97`). One acceptance check per ticket (`app_test`, `test_command`, `text` up to 500 code points). There is no ticket "kind" field (repair vs implementation).
9. Reaction input to AE is tiny: `<lophn-reaction event="ProblemOpened" seq="N">A new problem was opened for this app.</lophn-reaction>` plus a ref line to the problem id (`packages/core/events/reactor/session-opening.ts:54-60`, `packages/core/lophn-agent/run-loop/input-text.ts:119-126`). Each new problem opens a NEW AE session (`new_session`), so there is no memory across problems.
10. A deterministic bug plant that needs no model is feasible and already patterned: `tests/support/app/patch-*.ts` + `createAppSource({patch})` + `core.call(appCallApi, ...)` produce reports without a model. `tests/e2e/reaction_test.ts` does exactly this for crash (see section 6).

Details: JSON (`SafeReportDetails`), structuredClone'd; failure to clone -> failed value, never throws (`reporter.ts:82-104`).

- SDK queue: 32 pending and 4,194,304 bytes; over -> completion `failed/unavailable` (`reporter.ts:105-116`). Reporter not installed (unit test) -> returns `failed/unavailable "problem reporting is not installed"` (`report-port.ts:405-422`).
- Core intake rate: 20 NEW reports per 60 s per app; over -> `unavailable` (`new_reports_per_window`, `window_ms`; `packages/core/problems/reporting/model.ts:142-166`, `commands.ts:71-80`).

- Logs in a snapshot come from the supervisor's in-memory buffer: per invocation last 200 lines, 500 invocations, 500 unattached lines, 300 chars per line (`packages/core/apps/runtime/observations/log-buffer.ts:1-5`). Collection can be turned off by the "detail collection" setting (`snapshots/logs.ts:35-38`).
- Redaction (fail-closed) is applied to name, message, details, error name/message/stack, log lines before anything is stored.

## 2. How observations become problems; reactions

Grouping (`packages/protocol/problems/problem-record.ts:18-33`, key unique per `(app, group_key)` regardless of state: `reporting/model.ts:50-62`):
- named (source 1): key = the name only. Same app + same name = one problem forever. Different causes sharing a name merge.
- exception (sources 2-5): discriminator = sha256(error name + `path:line` of the top resolved app frame) (`snapshots/work.ts:455-475`). Frames resolve through the screen source map (`/screens/<key>/main.js`) or a stack file inside the sealed bundle copy (`apps/<app>/bundles/<hash>`), `snapshots/work.ts:89-175,225-275`.
- exception with no resolvable frame (process_exit, view errors, unmapped stack): since commit dfea0fd78 (`snapshots/work.ts:455-475`, changed from report id) discriminator = sha256(observation kind + error name + message + bundle hash). So the same crash reason in the same bundle is ONE problem; a new bundle (new release) with the same crash makes a NEW problem. A message that varies per occurrence (ids, timestamps) defeats the grouping and floods up to the 20/min limit.
- feedback: each feedback = its own problem.

Problem record (`problem-record.ts:42-54`): `id`, `app`, `group_key`, `name` (first occurrence's name), `state`, `state_changed_at`, `seq` (starts 1, +1 per state change), `recurred {resolved_at, release} | null`.

States and transitions:
- `open`: created by first live report (`ProblemOpened` event, payload `{app, report}`; `commands.ts:167-186`). Further occurrences while open only accumulate; no event.
- `resolved` / `ignored`: set only by `problem.set_state` (command `problems/set_state`; AE of that app or any user; no gate, no pending request, no event; `packages/core/problems/grouping/commands.ts:19-67`). Setting state clears `recurred`.
- reopen: a live occurrence on a `resolved` problem reopens it (state back to `open`, `recurred = {resolved_at, release}`, `seq+1`, `ProblemReopened` event) only if the occurrence's release has `activated_at > state_changed_at` (`reporting/model.ts:107-115`, `commands.ts:139-165`). An occurrence from an older release, or with unknown release, just accumulates. `ignored` never reopens.
- There is no "reopened" state, no repeat/loop counter on problems, and no auto-resolve when a fixed release is activated. Protocol routes `problems/apply-decision`, `problems/link-interpretation`, the report-code routes `problems/report`, `problems/record-report` (old code-based) exist in `packages/protocol/problems/registry.ts:21-60` / `closing.ts` / `reports.ts` but I found no core handler for `ApplyProblemDecision`/`LinkProblemInterpretation`/`ReportProblem`/`RecordReport` (grep over packages/core). Treat as dead protocol residue (AGENTS.md says no leftover compat code).
- `problemDetailSchema` in `packages/protocol/problems/problem-detail.ts` (progress/owner/closed/decision) has no producer in core/shell main (grep). Residue as well. So "closed by verified / user_confirmed / recovered" in `closing.ts` is not implemented.
- "Repeat/loop detection": only the process-level crash loop (`AppRestartHalted`). AE prompt line 11-13 says reactions include "a repeating problem closed"; no such event exists. The real new-work events are `ProblemOpened`, `ProblemReopened`, `AppRestartHalted`, `ReleaseActivationFailed`, `ContextViolationFound` (`packages/protocol/events/domain.ts:153-157`, `session-opening.ts:174-188`).

What opens a reaction (`session-opening.ts`; AGENT-ROLE E1/E2/E3/E4 `project-docs/products/AGENT-ROLE.md:191-198`):
- Handler per event consults the reaction grant (`off`/`ask`/`open`, setting key `reactions.problem_opened`, `tests/e2e/reaction_test.ts:51`). Default is open without asking (AGENT-ROLE:191). `ask` creates a pending approval; the e2e shows allow/off/restart behaviour.
- Call: `from: program event_seq`, `reply: none`, `to: new_session app_engineer app`. Idempotent by (handler name, cause seq).
- Bodies: ProblemOpened "A new problem was opened for this app." refs `[problem]`; ProblemReopened "A solved problem happened again on the active release." refs `[problem]`; AppRestartHalted "The app crashed N times in a short time, so its automatic restart stopped. Release: rel_..." refs `[]`; ReleaseActivationFailed "Release rel_ failed to activate (code)." refs `[ticket]`.
- Model-visible text: `<lophn-reaction event="..." seq="...">body</lophn-reaction>` + ref lines (`input-text.ts:119-126`). The reaction does not contain name, message, release, count, or a pointer to source.
- Every new problem opens its own AE session. A reopened problem opens another new session; the session that closed it is not resumed.

## 3. What the AE (and coding agent) can read to diagnose

AE tool set (`packages/core/agent-roles/tool-lists.ts:5-82`): `file.read/glob/grep`, `file.write/edit`, `shell.run`, `pdf.read`, `image.read`, `web.*`, `call`, `reply`, `ask`, `skill.read`, plus `ticket.list/get/create/update/verify/cancel`, `problem.list/get/set_state`, `app.list/get`, `blueprint.check`, `package.*`, `release.list/get`, `guide.read`, `settings.get`, etc. The AE folder scope is read+write on the app's connected source folder (`packages/core/agent-roles/place/place-folders.ts:37-39`), so the AE CAN read/grep source (and technically edit it; the prompt forbids it, `app-engineer/prompt.md:50`). AE has NO tool for: app logs, invocations, `problem.more`, `problem.get_occurrence`, `problems.report_body`, source diff between releases, calling app-apis, or reading verification records. (grep: `get_occurrence`/`report_body` are mapped to no agent tool.)

`problem.get` output (`packages/core/problems/agent-tools.ts:49-78`, route `problems/get_problem`, `packages/protocol/problems/problem-views.ts:55-74,102-111`, built `packages/core/problems/grouping/reads.ts:182-241`):
- `problem` record, `occurrence_count`, `first_observed_at`, `last_observed_at`, `first_release`/`last_release` `{id, number, code_commit}`, `occurrences` (<= 20: `report`, `observed_at`, `source`, `release`), `latest {occurrence, snapshot}`.
- `snapshot`: `invocation {id, record_missing_reason}`, `error` (exceptions only: `name`, `message`, `frames[]`, `stack` = sha256 hash, `truncation_notes`; null for named reports), `logs` evidence (`blob` hash, `line_count`, `truncated`, `scope`, times; NOT the lines), screen (feedback only).
- If the result is too large the tool drops `latest.snapshot.logs` and sets `omitted.logs` (`agent-tools.ts:67-76`).
- Therefore for a `reportProblem` report the AE cannot see the message, the details, the log lines, or the stack text. Message text is stored (`report_text` blob) and exposed by routes `problems/get_occurrence` (preview <= 2,000 chars, `problem-views.ts:13,99-121`) and `problems.report_body` (fields `report_text`, `snapshot_logs`, `feedback_state` only; `packages/protocol/problems/report-body.ts:11-14`), actors include `agent` and `coding_agent`, but neither is mapped to an AE tool or a coding-agent CLI command. `report_details` has no read route at all (grep of `report_details` shows only write paths). So `details` passed to `reportProblem` is effectively write-only.

`problem.list`: items `{id, app, state, name, occurrence_count, last_observed_at, seq}`, filter by app/state/since/until, limit <= 100 (`problem-views.ts:76-91`).

Coding agent (CLI `lophn`, `packages/protocol/coding-agent/cli-commands.ts:154-231`): `problem list`, `problem show` (= `problem.get`, same output as AE), `problem more` with kinds `occurrences`, `failed_invocations` (report + invocation id pairs), `logs` (evidence stubs per report, again hashes), `release_changes` (added/removed resources between releases), `related_problems` (`problem-views.ts:123-176`, handler `packages/core/problems/repairs/more.ts`), `problem diff` (source diff between two releases, `packages/protocol/coding-agent/source-diff.ts`), `app logs` (live in-memory buffer, optionally by invocation), `app status`, `app invocations`, `app blueprint`. The coding agent has the source tree as its working directory. `lophn-repair/references/investigation.md:1-31` gives a fact/hypothesis procedure (8 steps) but no tool-specific hints.

Snapshots/logs retention: `problems/snapshots/logs-read.ts` shows the log blob can be pruned (`pruned|missing|corrupt`); `snapshot_logs` is readable by user/agent actors via `problems/get_snapshot_logs` route but not mapped to an AE tool either.

"Problem tests" subsystem (`packages/core/problems/tests/*`, 3,279 lines in `.ts` at the top level; protocol `packages/protocol/problems/tests.ts`):
- What it is: a platform runner for verifications, one `Verification` record per run, three kinds: `app_test`, `reproduction`, `test_command` (`tests.ts:11`).
- `app_test`: requested by the coding agent via `lophn app test` against a prepared bundle (`bundle_hash`, `test` hash from `release prepare`). The FrozenTest is derived from the sealed bundle (`tests/app-test/frozen.ts`), not authored by anyone. Required checks (`tests/harness/definitions.ts:13-24`): `blueprint_handler_match` (declared app-api set equals registered handlers and a deliberately invalid input is rejected for each app-api), `dependencies` (imports match declared exact versions), `migration_empty`, `migration_upgrade`, `rewind` (write app-api call + changeset reversal restores state). Runs the sealed bundle as a child with `mode=test`, a test DB, no network (`work/app-driver.ts:1-8`). None of these checks business behaviour, so `app_test` passing says nothing about whether a planted bug is fixed. One precise exception: it calls each app-api with an invalid input and a minimal valid input only for rewind; a handler bug on other inputs is invisible.
- `test_command`: ticket check kind `test_command {executable, argv, cwd, timeout_ms, expected_exit_code}`; argv must start with `test` and may not widen Deno permissions (`tests.ts:57-81`). The coding agent requests it with `lophn app test`; the `deno test` files themselves are written by the coding agent in the app source (the repair skill asks for an "original symptom reproduction test", `lophn-repair/SKILL.md:41,60,170-172`). Results are recorded as `Verification` with `result` pass/fail/inconclusive, linked to ticket + completion_seq; the ticket checker maps them to `check_result` (`packages/core/apps/tickets/checks.ts:64-96`, `checker/result.ts:39-60`). `text` checks are not run by the program; AE judges them (`checker/result.ts:39`).
- `reproduction`: schema requires `problem`, `basis_seq`, `reports`, `before`, `after` releases, but `handleRequestTest` returns `invalid_input "받지 않는 test 종류다"` for it (`tests/commands.ts:48-50`). So the platform does not run a before/after reproduction. The repair skill text mentions "reproduction test", which in practice can only be a `test_command`.
- Could they serve as a reproduction check for a diagnosis? Only `test_command`, and only because the coding agent writes a `deno test` in the app. A grader can read the resulting `Verification` (`problems/list-verifications` by `ticket`, `problems/get-verification`, event `VerificationRecorded`, `tests.ts:432-446`). Nothing guarantees the test fails before the fix; the platform runs it only on the fixed bundle (side `single`; `judge.ts:46-47` rejects any other side).
- Runner limits: concurrency 2, timeout <= 300,000 ms (suggested 60,000), output 1 MiB per side, process memory 512 MiB, Deno heap 256 MiB (`tests.ts:17-25`). App tests run under `systemd-run --user --scope` (`project-docs/architecture/testing.md` "앱 길").

  - AE prompt says verify "against the ticket's acceptance checks" but the check is one of app_test (platform, business-blind), test_command, or `text` (AE judgement).
  - AE has no tool to read report message/details/logs, so "read it with `problem.get`" yields little for named reports.

Ticket schema (`packages/protocol/coding-agent/ticket/values.ts`, `routes.ts:35-53`):
- `ticket.create` input: `app`, `goal` (<= 2,000 code points), `check`, `evidence?`.
- `check`: `test_command | app_test | text(<=500 code points)` (:66-87). One check only, although the AE prompt says "checks" (also noted in `project-docs/products/roadmap/eval.md`).
- `evidence`: <= 20, unique, kinds `problem {id}`, `ticket {id}`, `release {id}`, `file {path}` (source-relative path, no line/column field), `annotation {id}` (:91-100).
- No ticket kind or `problem` top-level link. A repair ticket is a ticket whose evidence has a `problem` entry; INFERENCE: the coding agent chooses build-app vs repair by itself from the goal and evidence.
- `ticket.show` / `tickets/show` returns `goal`, `check`, `evidence`, `claim`, `completion` (release, summary hash, verifications), `check_result`, `verdict` (`routes.ts:100-110`). `tickets/list` returns id/app/title/state only.

## 5. Program-checkable signals for a grader

### (A) After an app is built

Static (read the app source folder, `core.run.work/<slug>` in e2e, via `createAppSource`'s `dir`, or the registered `source_path`):
- Count and locate `reportProblem(` call sites in `src/**/*.ts` (not `tests/`, not `.lophn/`), and the string literal names. Check that call sites sit in: (1) `catch` blocks around store/IO/external calls, (2) app-api handlers on branches that return/throw after a validation failure not already handled by the blueprint input schema, (3) a failure branch after a `cap-net` request (external dependency), (4) store errors. Match with a simple AST pass. Name hygiene: each distinct failure kind has a distinct name (grouping is by name only), names are static strings, messages carry no ids (the collector groups named reports by name only, so message variation does not matter for grouping but matters for readability). Compare `reportProblem` vs thrown `Error` vs `AppApiRejection` at each failure site. `createExceptionObserver` / `installProblemReporter` appearing in app source would be a defect, not a pass (the entrypoint owns them).
- Whether the app's `catch` swallows an exception without any report AND without rethrow (silent failure). Whether `catch` blocks rethrow `AppApiRejection` after reporting (as the template does, which suppresses the automatic exception report; see section 4).
- `sdk_dependencies` in `blueprint.ts` contains `@lophn/cap-problem` exact version (the template has it).

Dynamic (needs a running app; planted failures through product routes):
- Trigger an app-api via core route `appCallApi` (`packages/protocol/apps/mod.ts`; used by `tests/e2e/reaction_test.ts:291-295` with `target {mode:"live", app, release:null}`, `api`, `caller {kind:"person", view_session}`) with: invalid input (rejected before the handler by the declared input schema, so no report is expected), valid-but-failing input (empty/oversized/unique-violating titles), input that makes the store throw. The response `outcome.status` is `succeeded|unknown|...` plus error codes `invalid_input`, `internal`, `unavailable`.
- External dependency down: `cap-net` is a permission-gated package; in `preview`/`test` mode network is virtualized (`app-driver.ts:1-8`); in live e2e "network is loopback only" (`testing.md`). A scenario can point the app at a closed loopback port (INFERENCE; not exercised in existing patches).
- Store error: the template's `withStore` hides it as `store_unavailable`. A way to cause it deterministically is a patch that drops/renames a column so a SQL statement throws (this also exercises the masking caveat).
- View error: core route `problems/observe-view-error` called by the test (user token), exactly what `tests/e2e/reaction_test.ts:55-83` does. No app process needed.
- Process crash: the `crashPatch` app-api (reply then throw in `setTimeout`).
- Then read: `problem.list` route `problems/list_problems` with `{app}` (name, state, occurrence_count, last_observed_at) and `problems/get_problem` (frames for exceptions). For named reports verify `name` equals the expected one and `source = "app"` in `occurrences[].source`. For message/details content use `problems/get_occurrence` (message preview + `details_hash`) and `problems.report_body` with `field: report_text` (user token; the AE cannot use these). Expect exactly 1 problem per distinct name regardless of the number of calls (use `occurrence_count`).
- Rate caution: > 20 new reports per 60 s per app are refused with `unavailable` (scenario loops must stay below that).
- Events: gateway `connectGateway(core, {conditions:[{types:["ProblemOpened","ProblemReopened","AppRestartHalted"]}]})` (as in `reaction_test.ts` and `activate.ts`).

### (B) After a planted bug is reported

AE side (read the AE session record via `tool-calls/list` and `turns/body-view` per `project-docs/products/roadmap/eval.md` "결과를 읽는 길"):
- Reaction received: `agentSessionList {agent:{role:"app_engineer", app}}` + `receivedMessageList {session}`; first message `from.kind === "program"` and `refs` containing `{kind:"problem", problem}` (helper `reactionSessions`, `reaction_test.ts:86-103`).
- Diagnosis steps: tool calls `problem.get` with that problem id; any `file.read`/`file.grep` of the file named in `latest.snapshot.error.frames[0].path` (the planted file); AE did not call `file.write`/`file.edit` on app source (prompt :50) and did not edit `blueprint.ts` (prompt :56; compare git tree / blueprint hash before-after).
- Ticket: `tickets/list {app}` then `tickets/show`. Check `evidence` contains `{kind:"problem", id: <the problem>}`; optionally `{kind:"file", path: <planted file>}`; check `goal` text names the planted file / app-api key / error name (substring match on `frames[0].path`, the app-api key, the error name); `check.kind` is `test_command` or `app_test`/`text` (judge by policy: `app_test` cannot detect the bug).
- Handoff: `call` tool with `to {role:"coding_agent"}` and `refs [{kind:"ticket", ticket}]` (`scriptAe` in `tests/support/app/activate.ts:171-190`).
- Fix: ticket `completion.release` -> `releasesListRecords {app}` (new release, `activated_at`, status) and `source-diff`/git diff of the source folder between the planted commit and the head. Check the diff touches the planted file/line and does not only delete the `reportProblem` call, loosen `catch` to swallow, change `blueprint.ts`, or edit tests/fixtures. Verification: `problems/list-verifications {app, ticket}`, `ticket.check_result`, `verdict`.
- Resolution: after the fix release is active, replay the exact failing `appCallApi` (same api + input). Expected: no new report (`occurrence_count` unchanged, `last_observed_at` unchanged, no `ProblemReopened`), and the call outcome now succeeded. If `problem.set_state resolved` was issued, compare its timestamp (`problem.state_changed_at` in `problems/get_problem`) with the fix release `activated_at`: resolved BEFORE the fix release was activated is a premature resolve (a later replay on the old release only accumulates and will not reopen). If the fix is wrong: replaying on the new release (activated after `state_changed_at`) produces `ProblemReopened` and `problem.recurred` non-null.
- `problem.set_state`: AE `tool-calls/list` entries named `problem_set_state` and the final `state` from `problems/list_problems`. Policy check: no `resolved`/`ignored` call without a verified ticket whose release is already activated; never `ignored` for a reproducible bug.
- Blueprint not used to hide: diff `blueprint.ts`/`blueprint.json` before/after; flag removal of the app-api that produced the problem, or loosening of its input schema to avoid the failing input.
- Activation: a pure code-fix release activates automatically after `ticket.verify` verified unless the declaration widened or data loss is possible (AGENT-ROLE E6 :198, `ReleaseActivationFailed` otherwise); first-ever activation always asks the person (`activate.ts:475-490`).

Routes and events that expose each:
- `problems/list_problems`, `problems/get_problem`, `problems/get_occurrence`, `problems/more_problem`, `problems.report_body` (reads); `problems/set_state` (write); `ProblemOpened`, `ProblemReopened`, `AppRestartHalted`, `ReleaseActivationFailed`, `VerificationRecorded`, `TicketVerified` (events); `tickets/list`, `tickets/show`; `tool-calls/list` + `turns/body-view`; `calls/read`; `releasesListRecords`; `appRuntime`.

Model-visible limit on what to grade as "AE found the real cause": AE sees only error name, message, top frames and counts (exceptions) or only the name (named reports). A good AE must open the source file at the frame path to diagnose. For a named report with no stack, a correct diagnosis depends on the name being informative and on grep in the source for that name string. A grader can check "AE grepped the report name in source" via `file.grep` inputs.

## 6. Planting a deterministic bug without a model

Existing pattern (`tests/support/app/*`, documented in `project-docs/architecture/testing.md`, "앱 길"):
- `createAppSource(core, {slug, title, patch})` (`tests/support/app/source.ts:40-60`) copies the core-installed template (`<home>/templates/app`), runs `scaffoldApp`, applies `patch(dir)` and does `git init` + commit; `amendAppSource(dir, patch)` makes a second commit for a later release.
- A patch edits `blueprint.ts` (adds the app-api declaration) and `src/app-api.ts` (adds the handler) via `replaceOnce(path, from, to)`; blueprint and handler must match to pass the platform `app_test` (`blueprint_handler_match`). Examples: `patch-reaction.ts:17-47` (`crash` read app-api: replies then throws in `setTimeout`), `patch-call.ts:66-147` (`big_write`, `put_text`, `external_ping`), `patch-rewind.ts`, `patch-sandbox.ts`, `patch-restart.ts` (slow handler), `patch-migration.ts` (failing migration), `patches.ts` (project-scope read).
- Activation without a model: `activateTestApp` -> `startTestApp` + `deliverRelease` + `approveActivation` + `waitRunning` (`activate.ts:518-529`) with scripted AE and CLI-driven coding agent. In a real-model eval the AE and coding agent are real, so the planted source must be committed in the app source BEFORE the coding agent's first release, or in a second `amendAppSource` commit which the real coding agent then turns into a release (INFERENCE: easier is to have the scenario's first ticket produce the app and then amend the source folder with a bug before the next release; the AE reads the same working tree).

Plant candidates and the report each yields (all trigger via `appCallApi`, no model):
1. Handler throw: add app-api `rename_item {id, title}` whose handler does `(input as any).meta.name.trim()` -> `TypeError` outside `withStore`. Runtime `reportCaught` reports it as exception `TypeError` with `invocation` id and frames `src/app-api.ts:<line>:<fn>` (needs bundle copy under `apps/<app>/bundles/<hash>` and stack lines inside it, `snapshots/work.ts:225-275`). Group key = sha(`TypeError` + `src/app-api.ts:<line>`).
2. Thrown inside `withStore.work`: any exception becomes `store_unavailable` named report (see caveat) and the rejection `AppApiRejection unavailable`. Good test of whether the coding agent / AE notice the mislabel. No frames. AE sees only the name `store_unavailable`.
3. Explicit named report: patch handler to `reportProblem("quota_exceeded", "...")` on a condition from the input (e.g. `title.length > 20` while the blueprint allows 200). Deterministic via `appCallApi` with a 25-char title.
4. Crash: `crashPatch` as is. 6 crashes within 600 s -> `AppRestartHalted` (`reaction_test.ts:370-410`, `CRASH_LIMIT_EXIT = 6`). Note the `unexpected_exit` problem is shared across crashes in one bundle (since dfea0fd78), `reaction_test.ts:285-287,403`.
5. View error: `observeViewError` route with `render_error` (no stack).
6. Silent failure planted for (A): handler catches an error and returns `[]` with `coverage: "complete"`; a good scenario expects the agent to add a report there. Detect via no problem after the failing call (`problems/list_problems` empty) while the call's output is wrong.

To keep determinism: use the fixed commit hash from `createAppSource`, the same `appCallApi` input, and read `problems/list_problems` until `occurrence_count` reaches the expected number (poll with `until`, `tests/support/core/human.ts:28`). Cap loops at < 20 calls per 60 s.

Real-model concerns (INFERENCE): the coding agent sandbox reads `AGENTS.md`; planting must not alter the managed block lines (`AGENTS.md.tmpl` has `lophn-managed` markers) or the coding agent may behave differently. Starting from the scaffold with the seeded `withStore` report means case (A) "does the new app place observations" must be graded on call sites ADDED beyond the template's one, otherwise a do-nothing app already has a `reportProblem`.

## 7. Gaps (instruction gaps and missing reads)

Instruction gaps, (A) placing observations:
- G1. No instruction to AE or coding agent says where to call `reportProblem` (failure branches of app-api handlers, catch blocks, external call failures, silent-fallback branches). Only 1 sentence in the scaffold `AGENTS.md.tmpl:45-46` and 1 example in `app-api.ts.tmpl:30-35`.
- G2. `lophn-build-app/SKILL.md` has no step or checklist item for observations; AE `prompt.md` ticket guidance has no "ask for reporting on failure paths" and `blueprint` has no observation declaration, so nothing is checkable before release.
- G3. The `cap-problem` guide gives the API but no placement, naming or granularity guidance (one example `sync_failed`); no statement that grouping is by name only, so distinct causes should get distinct names, and that `details` are currently unreadable.
- G4. The scaffold's `withStore` converts any in-work exception to `store_unavailable` + `AppApiRejection`, hiding stack/frames and teaching a misleading name. This is both an instruction gap (the pattern is copied) and a diagnosis hazard for (B).
- G5. The scaffold's tests do not check `reportProblem`, and platform `app_test` is business-blind, so no automatic check protects observation placement.

Instruction gaps, (B) diagnosis:
- G6. AE prompt `:38-41` is a single sentence for problem handling; no procedure for causes (read source at the frame path, compare releases, decide whether the evidence suffices), no instruction to cite the file/api in the ticket goal, no instruction to include a verification plan that would fail without the fix.
- G7. AE prompt `:11-13` lists "a repeating problem closed" which does not exist as an event; the reaction for `AppRestartHalted` has no problem ref, so AE has to find the cause via `problem.list`/`app.get`.
- G8. Repair skill requires a "fail-before/pass-after" reproduction test but the platform neither runs `reproduction` (`commands.ts:48-50`) nor records a before side; `app_test` cannot confirm a bug fix; `text` check is unverifiable by the program. The AE has no way to ask for the right check kind, and the prompt does not say which check kind fits a repair.
- G9. "problems decides closing" (repair skill :203) vs reality (AE `problem.set_state resolved` has no gate and no check that a fixed release is active). Nothing tells the AE when it is allowed to set `resolved`.
- G10. Ticket evidence `file` carries only a path (no line); no field for the frame, error name or report id. The grader can only match the goal text for line-level precision.
- G11. No ticket kind distinguishing repair from implementation; the coding agent picks a skill on its own.

Missing reads:
- R1. AE (and coding agent) cannot read the message and details of a `reportProblem` report. `problems/get_occurrence`/`problems.report_body` exist but map to no AE tool or CLI command; `report_details` has no read route at all. A named report therefore gives the AE only its name.
- R2. AE cannot read logs (`snapshot_logs` hash only in `problem.get`; no `app.logs` tool) and cannot read the stack text (hash). Coding agent has `app logs` (live buffer only, may be pruned) but not the snapshot's log blob.
- R3. AE has no tool to call the failing app-api to reproduce, no `problem.more`, no source diff between releases (`problem diff` is coding-agent only), and no read of verification results other than `ticket.show.check_result`.
- R4. Reaction body gives no name, count or release; the AE needs one `problem.get` call to learn anything. There is no "same cause as problem X" link; related problems are readable only by the coding agent (`problem more related_problems`).
- R5. No program-readable link from ticket/fix to the problem after the fact except `evidence` on the ticket; no event "fix release activated for problem X" and no automatic resolve or "still failing after fix" signal other than reopen via a new occurrence. A grader must create that signal itself by replaying the failing call.
- R6. Residue that may confuse a grader reading protocol: old code-based report routes (`reports.ts:142-253`), `apply-decision` (`closing.ts`), `problem-detail.ts` have no core handler found; I did not find a UI producer either. Not verified for the shell renderer; treat as unconfirmed.
