# documents/projects

프로젝트의 이름·목적과 폴더를 사람이 등록하고, 어떤 파일을 추적할지 정한다; 이름 변경과 보관도 맡으며 옛 address 안내는 documents/addressing을 따른다.

## 요구

### 등록

**[R1]** 프로젝트의 이름·제목·목적과 폴더·폴더 설명을 등록하거나 바꾸는 일은 사람만 하며 폴더는 OS 폴더 선택기로 고른다.
- 이유: 추적할 자료의 경계는 컴퓨터의 주인이 정해야 한다.
- 확인: 사람은 폴더를 추가하고 설명을 고치지만 agent와 앱의 같은 변경 요청은 거절된다.

**[R2]** 프로젝트에는 폴더를 여러 개 연결하거나 하나도 연결하지 않을 수 있고 lophn은 기본 프로젝트를 자동으로 만들지 않는다.
- 이유: 문서의 자리와 현재 디스크 폴더 연결은 같지 않다.
- 확인: 폴더 없는 프로젝트와 두 폴더가 연결된 프로젝트를 등록해 각각 조회한다.

### 추적 규칙

**[R3]** 프로젝트를 등록한 직후 추적은 꺼져 있고 처음 켤 때의 기본 제안은 포함 패턴 **/*.md와 .gitignore 적용이다.
- 이유: 폴더 등록만으로 원치 않는 자료가 문서가 되어서는 안 된다.
- 확인: 새 프로젝트에 Markdown 파일을 두어도 켜기 전에는 추적하지 않고 기본 제안을 적용한 뒤에만 추적한다.

**[R4]** 추적 규칙은 각 등록 폴더를 기준으로 한 상대 경로의 포함·제외 glob을 순서대로 적용하여 마지막 일치를 따르고 일치하지 않는 파일은 제외한다.
- 이유: 여러 폴더에서도 사람이 한 규칙의 의미를 예측할 수 있어야 한다.
- 확인: 포함·제외·재포함 패턴을 겹쳐 적용하고 같은 상대 경로가 두 폴더에서 같은 판정을 받는지 확인한다.

**[R5]** .gitignore 적용을 켜면 ignore 대상은 제외하고 .git 내부·lophn 데이터 폴더·등록 폴더 밖으로 나가는 symlink는 포함 패턴으로도 추적할 수 없다.
- 이유: 자료 수집이 다른 저장소나 플랫폼 내부로 번지지 않게 한다.
- 확인: 각 제외 대상에 일치하는 포함 패턴을 추가해도 미리보기와 추적에서 제외된다.

**[R6]** 추적을 켜거나 폴더·규칙을 바꾸기 전에 포함·제외 파일과 이유를 미리 보여 주며 적용은 미리 본 바로 그 폴더·규칙을 사용한다.
- 이유: 기본 Markdown 패턴에 맞는 개인정보 파일도 포함될 수 있으므로 적용 전에 범위를 확인해야 한다.
- 확인: 미리보기 후 규칙은 그대로 적용되고 중간에 프로젝트 구성이 바뀌면 충돌하며 디스크에 새로 생긴 파일은 적용한 규칙으로 판정한다.

**[R7]** 활성 프로젝트의 켜진 추적 폴더는 같은 실제 폴더나 조상·자손 폴더를 다른 켜진 추적 폴더와 겹쳐 등록할 수 없다.
- 이유: 같은 파일의 문서를 두 프로젝트가 경쟁해서 만들지 않게 한다.
- 확인: 같은 폴더와 그 하위 폴더를 두 프로젝트에서 켜려 하면 두 번째 요청이 충돌한다.

### 조회와 정리

**[R8]** 사람의 프로젝트 조회는 이름·목적·폴더 설명·문서 수와 현재 추적 패턴·.gitignore 적용 여부를 보여 준다.
- 이유: 프로젝트가 무엇을 모으는지 등록 후에도 확인할 수 있어야 한다.
- 확인: 여러 폴더의 설명과 추적 규칙을 조회하여 실제 적용한 값과 대조한다.

**[R9]** agent의 프로젝트 조회는 등록 목록·현재 작업과 연결된 프로젝트·읽을 수 있는 자료 참조를 제공하되 원본 파일 목록과 실제 절대 경로를 제공하지 않는다.
- 이유: 프로젝트 탐색과 디스크 접근을 분리한다.
- 확인: 현재 프로젝트에서 저장 문서로 이동할 수 있으나 파일 트리나 실제 경로를 얻을 수 없다; 읽기 권한은 platform/identity를 따른다.

**[R10]** 폴더 연결을 해석할 때 가장 깊은 등록 폴더를 고르며 파일 내용의 유사함으로 폴더 이동이나 재연결을 추측하지 않는다.
- 이유: 폴더 선택과 경로 재연결이 사람의 의도와 같아야 한다.
- 확인: 꺼진 추적의 중첩 폴더를 조회하면 가장 깊은 등록 폴더로 해석하고 폴더를 옮기면 명시적 재연결 전에는 연결을 바꾸지 않는다.

**[R11]** 사람은 프로젝트의 이름·목적·보관 여부를 바꿀 수 있고 보관해도 소속 문서와 저장된 version을 삭제하거나 일괄 보관하지 않는다.
- 이유: 프로젝트를 쉬게 하는 일과 자료를 없애는 일을 구분한다.
- 확인: 보관 후 이전 문서는 남고 자동 추적 중단·재개는 documents/file-tracking, 옛 이름 안내는 documents/addressing으로 확인한다.

**[R12]** 자리 없는 문서를 프로젝트 파일로 두려는 요청은 추적이 켜진 프로젝트만 허용하고 패턴 밖 경로라면 그 파일 하나의 포함 규칙을 사람의 적용으로 추가한다.
- 이유: 사람이 둔 문서가 다음 편집부터 추적되어야 한다.
- 확인: 켜진 프로젝트의 패턴 밖 파일에는 정확한 포함 규칙이 추가되고 꺼진 프로젝트에 두는 요청은 충돌한다; 파일 쓰기는 documents/file-tracking을 따른다.

## 열린 질문

- documents/projects#Q1 여러 프로젝트의 추적 폴더 겹침 금지를 유지할까.
- documents/projects#Q2 폴더의 label·기본 여부와 기본 추적 행의 존재 의미를 새 모델에도 유지할까.
- documents/projects#Q3 프로젝트의 폴더·원본 경로 정보를 별도 export로 제공할까.
- documents/projects#Q4 미리보기와 적용 후 파일 목록의 일치를 고정 디스크 snapshot으로 보장할까.

## 버린 것

- 기본 notes 프로젝트와 원본 없는 문서를 새 문서로 복사해 연결하는 방식은 버렸다; 원본 없는 문서의 편집은 documents/file-tracking의 문서별 작업 사본으로 한다.
- Home·기본 수신 자리·플랫폼 전용 자리와 그 이관 기능은 버렸다; 프로젝트나 앱 자체가 문서의 자리이고 처음부터 재구축한다.
