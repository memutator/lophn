**What identifies a computer to a phone:** the core public key from the pairing text (`proto/remote/frames.ts` `remotePairingSchema` = `{addresses[<=16], port, key, code, relay?}`). Phone stores `Computer = {addresses, port, key, relay?, device, revoked, name?}` in SecureStore (`mobile/src/pairing/store.ts`). Noise IK (`proto/remote/channel.ts` `connectRemote`, prologue `lophn-remote/1`) means the phone already refuses to complete a handshake with a responder that does not hold that key, so "same address, different machine" is already stopped; what it does not stop is two machines holding the **same** key.

**What the phone shows as the computer's name:** `mobile/src/data/computers.ts` `defaultName()` = `addresses[0] ?? relay ?? key.slice(0,8)`; comment: "The core does not send its own name". `Computer.name` is set only when the person renames ("Shown as"); `rename()` keeps the old name on re-pair. The core never sends a name: `hello` has only `{type, version, capabilities[<=64 strings of <=64 chars]}` and the core sends `capabilities: []` (`core/remote/host.ts` accept).

**What identifies a phone to the computer:** the phone's X25519 public key (handshake static key, SecureStore `device-key` on the phone), mapped to a `devices` row. Table (`core/remote/devices.ts`, steps `remote.devices`, `remote.devices.push`, `remote.devices.terminal_input`):

`devices(id text pk, name text not null, os text not null check in ('ios','android'), width int, height int, dpr real, public_key text unique, created_at, last_connected_at, is_primary int check 0/1, push_token text, push_prefs text default '{}', terminal_input int default 0 check 0/1)` STRICT.

- Name source: the phone sends it in the `pair` frame (`mobile/src/pairing/pair.ts` `thisDevice`: `Platform.constants.Model` sliced to 40, os, `Dimensions.get("screen")`, `PixelRatio`). `remoteDeviceSchema` = `{name 1..40, os enum ios|android, width 200..2000, height 200..3000, dpr 1..4}`.
- `register` (command, actor machine only): same public key replaces the old row; **the new device always becomes `is_primary=1`** (others cleared). Also writes `shell.devices` setting (`screensPaired`, `uniqueName` adds " 2"…), which feeds the preview device frames (`lophn tab open --preview --device <name>`).
- Gates and who may do what: `devices/set_terminal_input` (user only, not in the remote allowlist; core keeps an in-memory `createTerminalInputGrants` set loaded at boot and updated through `DevicesChange` after commit); `devices/set_push` and `devices/unpair` (device principal only, input has no id); `devices/clear_push`, `devices/push_targets`, `devices/register`, `devices/connected` (machine only: principal `machine:remote`, `REMOTE_CONTEXT` in `core/main/daemon/wiring/remote.ts`); `devices/rename|revoke|set_primary` (user, not in allowlist). Views "gate" is in `app_views` (owner `device:<id>`, 64 per owner, `core/apps/views`). Primary is consumed by `core/apps/phone/target.ts` (`apps/phone_target`, agents read it to draw phone screens), `core/apps/phone/changed.ts` (notice `phone_changed`), `core/apps/phone-request/handler.ts` (`app_phone.request` asks the primary device), `core/main/daemon/wiring/host-queue.ts` (primary device name in agent text).

**A copied data root shares with its source (code facts):** `host-key.json` (same core key: phones cannot tell the two cores apart; the relay closes the older control socket when the same key proves again, so two copies on relay flap), `ledger-id`, the whole `devices` table (all phone registrations, so every paired phone can connect to either copy), `settings.json` incl. `remote.relay/port`, `secrets.json`, app data DBs (including the sync node id inside each app DB, see D), `apps/*` ids (`app_…`, `prj_…`). **Where a computer-name setting would live:** `core/config/shell-settings.ts` (`declareSetting`, list `shellSettings` lines ~525-560; remote ones are `remote.enabled|port|relay|push`, all `locked: true` = only the person). Settings are stored in `<root>/settings.json`; the renderer reads/writes through `memory:settings/list|update` (allowlist `shell/main/desktop/core/allowlist.ts`), agents through `lophn settings get|set|unset` (`packages/cli/commands/settings.ts`). ## B. The remote connection as reusable client code

**`proto/remote` client side needs:** a `RemoteTransport` (`send(bytes), close(), onMessage(h), onClose(h)`), a `RandomSource` (`packages/base`), a `KeyPair` (`generateKeyPair`, `remoteKeyBytes/Text` in `noise.ts`, deps `@noble/ciphers|curves|hashes`), `zod` (frames). `connectRemote({transport, staticKey, remoteStatic, capabilities, random, maxFrameBytes?})`. No node: imports, no crypto global, no storage. Nothing RN specific; it is already run under Node by `tools/remote-client.ts` (pair/call/file/watch, global `WebSocket`). Narrow import for the phone: `proto/remote/client.ts` (re-exported as `mobile/src/remote.ts`). Limits: frame 16 MiB (`REMOTE_FRAME_MAX_BYTES`), Noise record chunks, unattached connections 4 KiB frames, handshake+hello in 10 s, 60 s to pair, 8 unattached sockets (`core/remote/host.ts`). Protocol version: `REMOTE_PROTOCOL_VERSION = 1`, `MIN = 1`; a peer below MIN is closed with `conflict`; there is no max negotiation. Relay URLs: `relayPhoneUrl(relay, key)` -> `/v1/phone?key=`.

**What the phone app adds** (all in `packages/mobile/src`, outside the root workspace, so `packages/shell` cannot import it): `connection/socket.ts` `dialSocket` (RN WebSocket), `connection/connection.ts` (`openFirst`: dials every address and the relay in parallel, first completed handshake wins; `createConnection`: `CoreSource`-shaped, backoff 1 s..30 s, `pause/resume` with a 3 s `watch` probe, drops conditions that fail `eventConditionSchema`, answers core `request` frames through `link/answer.ts` `phoneCapabilities()`), `data/computers.ts` (`createComputers`: one link per saved computer, status connecting/connected/offline/revoked, path direct/relay, `waiting` count, add/remove/rename/select, `unpair` on remove), `pairing/pair.ts` (`parseQr` = JSON parse + `remotePairingSchema`; "Enter a pairing code instead" is this paste path; `pair()` sends `{type:"pair", id:"pair", code, ...thisDevice()}`), `pairing/store.ts` (SecureStore, `random` from expo-crypto), `data/crypto.ts` (installs `crypto.getRandomValues/randomUUID`). `connection.ts` mixes generic code with phone-only `answerRequest`/`phoneCtx`, so moving it to a shared place needs that split.

**Desktop renderer -> core today:** `shell/renderer/desktop/connection/connection.ts` defines `CoreSource {subscribe, current?, call(CoreCall), watch?, onEvent?}`; `windowCoreSource()` wraps preload global `lophnCore` (`shell/ipc/core-api.ts` `CoreApi`, channels `shell:core-call|core-state|core-event|core-watch`). Constructed once in `renderer/desktop/entry.tsx` line ~104 (`const core = mock?.core ?? windowCoreSource()`), then ~20 sources are built from that one `core` (projects, apps, settings, jobs, agent tab, editor deps, remote settings, coding connection...), plus one `createEventClient(core)` per window. Also built in `workspace/app-preview-tab.tsx` and `settings/browser/window-source.ts`. The renderer holds no token or port: shell main (`shell/main/desktop/core/connection.ts`, `client.ts`, `events.ts`, `allowlist.ts`) holds the human token and shell capability, talks loopback HTTP + Gateway WebSocket (`lophn.gateway.1`), and filters renderer calls with its own allowlist (`SHELL_ROUTES` + `RENDERER_MEMORY_ROUTES`; call kinds read|command|memory|upload|file). The phone `Connection` copies the same `CoreSource` shape and `CoreCall.kind` is ignored by the remote `call` frame (`{resource, method, body}`; the core finds the kind from the route registry). Commands need the envelope that `renderer/command-call.ts` builds (phone reuses it).

**What assumes one local core + local shell host** (desktop code, facts): the module-level `core` in `entry.tsx`; non-core preload bridges that all talk to the local main/core: `lophnCoding` (coding agent detection), terminal bridge (`windowTerminalDeps`, xterm + PTY in `shell/terminal-host`), files/editor (`windowEditorDeps`, local FS paths), folder picker, browser tabs/`browser-bridge`, app views (`shell/main/app-frame/*`: view binding `app_views/open` owner `user`, custom `lophn-app://` protocol with an injected `Upstream` that fetches `screen_file` from the local core), protected secret window (`shell/main/secret-input`, uses shell capability + control socket pipe), `/host-link` (`shell/main/desktop/core/host-link.ts`: one `hello`/`request`/`response` link from shell main to its core; carries tab/terminal/browser requests of agent tools), layouts/desks (`<root>/shell/workspaces/<workspace>.json`, keyed by local ids, no machine axis), settings and secrets (routes not in the device allowlist), project folders (`project_folders.path` absolute on the core's machine). ## C. Presence and several viewers

- `core/attention/presence.ts`: in-memory table keyed by reporter principal; `isPhone(reporter) = reporter.startsWith("device:")`; phones count as present when `focused` (idle ignored), desktops (any non-`device:` reporter) need `idle_ms < 120 s`; TTL 90 s; `anyLooking(session)` over all reporters. `decide.ts`: for each `devices` row with a `push_token`, skip if that device is present, skip if `quiet_when_present` and `anyDesktopPresent`. Only phones have push tokens, so a viewer without a token never receives push; a desktop viewer connecting as a `device:` principal would be treated as a "phone" in presence (focus only, no idle) and could not make the local desktop quiet-rule fire (that rule reads non-device reporters).
- Everything keyed by `device:` is phone-semantic: `core/apps/sync/service.ts` `deviceOf` (push/pull/snapshot only for `device:`), `core/apps/views/mod.ts` (preview view picked from `device:` owners for phone tabs), `phone_target`/`app_phone.request`/`phone_changed` use `is_primary`, `core/remote/devices.ts` register makes the newest device primary, `shell.devices` gets an entry per paired device, `devices.os` is `ios|android` with a CHECK and `remoteDeviceSchema.os` is `z.enum(["ios","android"])`, width/height/dpr are required with ranges.
- **No field distinguishes a phone from another device kind** in the handshake, `hello` (`{version, capabilities[]}`), `pair` frame, `devices` table, or allowlist. The closest extension points: `hello.capabilities` (strings, <=64, core sends `[]`), a new column in `devices`, a new `os` value (needs a schema step: CHECK cannot be altered, table rebuild). `PhoneLink` (core -> phone `request` frames) only asks kinds listed in the peer's `capabilities`, so a desktop that lists none gets no requests.
- Per-device gates in code: allowlist scope (one list for all devices), `terminal_input` per device, `jobs/update` toggle-only, `acp/send` runs inner routes with the device credential, admission limits per principal (`createAdmission`). Doc says write conflicts between two viewers are "reject if unseen messages" (survey rule); not implemented (`acp/send` has no such check found).
- When the viewer is a desktop: its own local core also sees the same person on this machine through shell main presence (user principal); the remote core would see the viewer only if the viewer sends `presence/report` over the device channel (allowed). Unseen/finished dots are shell-main state (`unseen/*` not in allowlist).

## D. Sync engine reach

**Recorded change shape.** One change = one SQLite session changeset (binary, `readChangeset` in `packages/base/changeset-invert.ts`) for one write call (all tables except `sqlite_*`/`lophn_*`), plus one HLC for the whole changeset. HLC (`proto/apps/sync/clock.ts`) = 63-bit integer `[ms 42][counter 5][node 16]`, node part = FNV-1a of the node string, JSON as decimal string `^(0|[1-9][0-9]{0,18})$`. Wire form (`proto/apps/app-sync.ts`): `{id: ULID 26, operation, started_at, hlc, changeset base64}`; limits: change <= 8 MiB (`APP_SYNC_CHANGE_MAX_BYTES`), push <= 256 changes / 10 MiB, pull default 8 MiB max 10 MiB, 200 log rows per page (`PAGE_ROWS`), snapshot file chunk 8 MiB, snapshot TTL 10 min. Core-side `CHANGESET_MAX_BYTES` = 8 MiB (bigger -> "snapshot" row) and `RELEASE_CHANGESET_MAX_BYTES` = 128 MiB (sum per release, rewind).

**Hidden tables in every sync app DB** (`proto/apps/sync/tables.ts`, column names also used by the phone C++ module `mobile/modules/lophn-app-db`): `lophn_sync_row(tbl, pk blob, hlc, deleted)` (last insert/delete clock = tombstone included), `lophn_sync_col(tbl, pk, col index, hlc)` (only columns changed after insert, always > row clock), `lophn_sync_state(key,value)` keys `node, hlc, cursor, release`, `lophn_sync_outbox(id, operation, started_at, changeset, hlc)` (phone only), computer-only `lophn_sync_columns(tbl, columns)`. Clocks are cleared: insert/delete stamp `dropColumnClocks`; `forgetMovedColumns` (entrypoint/sync.ts, at app start) deletes column clocks of tables whose column list changed (col clocks are by index). **Not found:** tombstone garbage collection (no code deletes `lophn_sync_row` rows), a cap on future-stamped HLCs (`applyRemote` calls `clock.observe(hlc)` for any value; `next` throws only when ms >= 2^42), monotonic-per-machine counters beyond the HLC.

**Computer's sync log** (ledger table `app_sync_log`, step `apps.sync-log`, `core/apps/sync/schema.ts`): `seq integer pk autoincrement` (global across apps), `app, release, kind in (change|skipped|snapshot), origin in (computer|device|rewind), device, change_id, hlc text, changeset_hash, changeset_size, invocation, created_at`; CHECKs tie `origin='device'` to non-null `device`, `device` to `change_id`, `kind='change'` to a changeset blob; unique index `(device, change_id)`; changeset bytes live in the blob store (owner_kind `app_sync_log`, key = seq). **A row from another computer does not fit these CHECKs** (no origin, no machine column): changing them needs a table rebuild step (new id appended to `WIRINGS` last wiring `schemaStepsAfterTeams` = remote wiring, plus `{id,sha256}` appended to `core/storage/migration/schema-steps.lock.json`, now 77 entries ending `apps.sync-log`, `apps.permissions.phone_kind`), preserving `seq` because blob refs use it.

**"Take a new snapshot" rows (`kind='snapshot'`)** are written by `core/apps/sync/log.ts`: (1) `append` falls back to it when the changeset is empty/over 8 MiB/blob prepare or ref fails; (2) `unknown()` for a sync-app write whose result is unknown; (3) `prune()` after activation (old release rows deleted, one marker kept); (4) `backfill()` at core start for the crash gap between app commit and log row. `pull` returns `snapshot_needed` when a marker is after the cursor or the release differs.

**Cursors:** the core keeps no per-device state. The phone keeps `cursor` (last seq) in its own app DB (`lophn_sync_state`), one DB per computer per app (`files/apps/<computer key>/<app>/app.sqlite`, `mobile/src/apps/local/folder.ts`); phone `node` = the `dev_…` id the computer assigned (`mobile/src/data/local-stores.ts`). `duplicate(device, id)` dedupes by (device, change_id). Snapshots are core-side temp files in memory-tracked `Held` (device, path, size, expiry) (`core/apps/sync/snapshots.ts`, `take` requires a device principal).

**Node id on the computer:** `ids.newId("nod")` at every app process start (`core/apps/runtime/entrypoint/main.ts` ~l.138) but `ensureSyncTables` inserts it `on conflict do nothing`, so it is fixed at the first start of that app DB. `VACUUM INTO` snapshots copy the state table including this node; the phone's `adoptSnapshot` overwrites node/cursor/release and empties the outbox. A computer that received a copied DB must do the same or two replicas share a node (16-bit node part collision chance 1/65536 is accepted in the clock comment).

**Does the computer forward a phone's original changeset and clock unchanged? Yes (code).** `SyncRecorder.phone` stores `change.changeset` and `change.hlc` as received (origin `device`); `appSync.pull` returns `kind='change'` rows whose `device != puller` with `origin, hlc, changeset`. The effective changeset (what actually changed after LWW) is only stored on the invocation. The core never compares HLCs; order is by `seq`.

**What a computer-to-computer file exchange could reuse:**
- Export (i): `SyncLog.head/page/readChangeset` have no device assumption and give `(seq, release, origin, hlc, changeset bytes)`; rows of kind `snapshot` cannot be exported as files (they mean "re-baseline": would need a snapshot file via `writeSnapshot`/`VACUUM INTO`, `core/apps/runtime/entrypoint/sync.ts`); rows are pruned on release change, so a file stream is per release; each file must carry release id, data_schema, declaration hash.
- Import (ii): `applyRemote(db, changes, clock)` (pure, `proto/apps/sync/apply.ts`) and `applyPhoneChange` (app process, one change per transaction, constraint failure -> `skipped`, table/column mismatch -> `conflict`, bad bytes -> `invalid_input`) are usable as-is on any replica. The core wrapper `applyPhone` (`core/apps/calls/service.ts` ~l.498) makes one invocation per change with caller `{kind:"person", view_session: change.id, device}` and writes the log row with origin `device`; `createAppSync.push` and `snapshots.take` require a `device:` principal and `input.release === active`. These assume "other side = a device with a credential, a cursor on the other side, a `dev_` id". Needed new: a machine origin/caller (caller is JSON in `invocations.caller`; per `app-sync.md` decision `device` was added without a schema step, `machine?` could be too), a machine-keyed dedupe, a per-source "applied through" record on the receiving machine, an all-or-nothing validate-then-apply over a batch, relog of imported changes so this machine's phones pull them (existing `pull` already forwards `origin` rows), and loop prevention (do not re-export what came from a machine file).
- Rewind: `rewound` writes a `rewind` row with effective changeset and a new clock; imported changes appear in Activity/rewind scope like phone ones (doc: phone invocations are in rewind range).

**Release changes and migrations vs pending phone changes (code in `mobile/src/apps/local/release.ts`, `reexpress.ts`):** guest down -> backup `app.sqlite` -> all work in `work/` copies. Outbox empty: new snapshot becomes `app.sqlite`. Outbox pending: migrate a copy with the new release's migrations, adopt the new snapshot, `reexpress` pending changes by table/column name onto it (changes on dropped tables/columns are dropped; the migration's `-- loss:` lines were shown at activation), then push; backup kept until the first push on the new release empties the outbox. Computer: `core/apps/sync/service.ts` rejects push for a non-active release (`conflict` + `active_release`), `pull` answers `snapshot_needed`; `prune` after activation. **Same-release-only sync is invariant `app-sync.md` 6**; `applyRemote` returns `conflict` when table/PK shape differs. Two computers on different releases of one app: no code path; they would need per-release file streams and a re-baseline rule.

- Release: `lophn release prepare <app>` (HEAD only; worker `core/apps/releases/prepare/from-source.ts`): extract commit tree (`git-extract.ts`, 40-hex commit, no uncommitted files), copy pinned SDK files into staging `.lophn/sdk`, **run `npm` to download dependencies (network)**, evaluate declaration, build screens, phone bundle, seal. `releases(id, app, number unique per app, code_commit 40, bundle_hash 64, declaration_hash, data_schema, data_changes json, status, activation, declaration, facts...)`, immutable by trigger. Bundle copy `<root>/apps/<app>/bundles/<hash>/` sealed (0444, `.sealed` marker) with hardlinks to `<root>/bundle-files/<sha256>`; limits source 64 MiB, bundle 256 MiB, 10,000 files, 300 s. Because dependencies come from npm at prepare time, the same commit prepared on two machines may produce different `bundle_hash`; not checked anywhere. Release numbers are per-ledger.
- Moving an app to a second machine needs: new `apps` row (ids are ledger-local ULIDs; no cross-machine app id; slug unique per machine), source repo (git bundle plan, doc only), release prepared again locally or bundle copied (bundle contains `node_modules`; hash differs), activation with `activation_consents` (person approves again; widening and first activation ask), `grants` (per app+kind+scope, revoked-not-deleted, must be asked again), secrets (`secrets.json`, never copied), OAuth state, app data DB under `<root>/apps/<app>/data` (via the sync stream, not by copy), invocation history and rewind data stay local, notices, phone-screen bundles rebuilt by prepare. Declaration `runs_on` today has no machine dimension; a sync policy field would sit next to it.

## F. Projects

- Table `projects(id prj_…, name slug UNIQUE, title, purpose, revision, status active|archived)` + `project_folders(project, position, path absolute, description, PK(project,position), UNIQUE(project,path))` + `project_icons`. Created by route `projects/create` (`project.create`, user only): the **client supplies `id`**, `name` (slug) and `title`, `folders`; renderer register dialog derives the slug from the folder name with numbered retries (`desktop/workspaces/projects/core-source.ts`, issue `project-create-slug-retry`). `project.resolve(path)` maps a path to a project; `project.relink_folder` repairs a moved path; `found` flag per folder. **Git is not consulted for identity**: only `.git` is hidden in file listing/search and `.gitignore` is read for search; `core/projects` has no git call. No `.lophn` folder convention in project folders (`.lophn/skills` exists only in app bundles; `privateRoot` in `skill-folders.ts` guards `~/.lophn`). Project-layer human instructions are read from the project's **first registered folder** (`LOPHN.md`, else `CLAUDE.md`; falls back to `<root>/projects/<prj>/` when no folder) in `core/lophn-agent/instructions/files.ts`, so these already travel with git.
- Keyed by project id: `sessions(project, workspace_kind, workspace_id)`, `workflow_instances.project`, `jobs.creator_workspace` (`prj_…`/`app_…`), notices and annotations (`project` columns), `model_choices` scope, data folder `<root>/projects/<prj>/` (memory.md, skills/, extensions.json) and `<root>/home` for Home, shell layouts `<root>/shell/workspaces/<id>.json`, agent definitions are global `<root>/agents/*.md`. Coding sessions are not in the ledger (`core/coding-relay/relay.ts` keeps an in-memory copy of shell state keyed by project).
- Display name: `title` (renderer `ProjectItem.title`, phone shows title); `name` is the call key (`workspace: {project: name}`).
- Where the cross-machine id would be read: a file in the repository root of the first folder (read by core next to `LOPHN.md` handling; there is a precedent for reading repo files per project, not for writing them; no `.lophn/` precedent at project level). The `projects` table has no spare column: a second id means a new schema step (add column or table `project_identity`) plus a "not on this machine" state (the existing `found` per folder is the nearest thing).

## G. Agent-readable environment and guidance

- How an agent learns about the installation: system prompt is cache-sensitive (`prompt-assembly/layers.ts`, `date-notice.ts` puts the date in history, not in system), built from `PRODUCT_INSTRUCTIONS` + workspace-kind text (`core/agent-workspaces/prompts/{home,project,app}.md`) + agent definition + human instructions (`LOPHN.md`) + workspace `memory.md` (with names resolved by `memory-names.ts`) + skill list (names only; body via `skill.read`, 24 KiB limit per file = `SKILL_BODY_MAX_BYTES`, checked by check's skill size step). Facts come through the `lophn` tool (`lophn help|<group> --help`), e.g. `lophn app phone-target`, `lophn settings get`, `lophn session list`. No machine, folder or device list exists for agents; only `app.phone_target` (primary phone name/os/size) and `settings get`.
- Pattern for a read-only command: route in `proto/...` (`defineRead`/`defineMemory`, actors including `agent`), handler in the owning core module, then `defineCommand({name, summary, description, input, effect:"read", routes:[route], workspaces:[...], run})` in `packages/cli/commands/<x>.ts` and add to `COMMANDS` in `packages/cli/commands/mod.ts` (binary and the agent `lophn` tool share the table). Example: `app.phone_target` (`commands/app.ts` l.224, `core/apps/phone/target.ts` reads `devices` with a narrow select so agents never see keys). Adding a command/route requires `project-docs/flows/` updates (flows skill; check's flows step) and may need an agent-visible `workspaces` choice (`home|project|app`).
- Skills: built-in app-agent skills in `packages/core/agent-workspaces/skills/{design-app,migrate-sdk,new-app,publish-package,repair-app,update-apps,write-artifact,write-workflow}`; `design-app/SKILL.md` is **24,413 bytes of the 24,576 limit** (163 bytes free) with companion files `phone-apps.md` 5,909, `phone-check.md` 3,302, `phone-features.md` 4,501 (the split pattern: add bundled `.md` files, link from SKILL.md). Skill for harness agents (Claude Code, Codex...): `packages/coding-agent/skills/lophn-agent.ts` (13,870 bytes, name `lophn-agent`, synced into harness skill folders by `lophn harness sync-skills`; teaches `lophn call/session/agent/team/tab/browser`). Changing instructions the app agent reads triggers the sdk-note process.
- Jobs: tables `jobs(id, title, creator_agent, creator_workspace, every, at, action json, missed_policy run|hold, enabled, next_due_at, approved_at, ...)` and `job_runs(id, job, due_at, missed_count, state queued|running|done|failed|cancelled|held|skipped|interrupted, run, instance, session, ...)` (`core/jobs/schema.ts`, steps `jobs.tables|approval|workspace`). Agent creates with `lophn job create` (`commands/job.ts`: `every`/`at`/`trigger` + action `agent_run|tool_run|workflow_start`); a new job does nothing until the person approves it (`approved_at`). **No machine/owner column.** Scheduler `core/jobs/scheduler.ts` runs inside the core process, not in the desktop app: quitting the app leaves the core alive while any job is enabled or `remote.enabled` is on (idle-exit rule); when the core stops (`Stop lophn`, reboot, no autostart) nothing runs and `missed_policy` decides later (`run` or `hold`).

## H. Always-on today

- Start/stop (platform.md "core 수명", code in `core/main/daemon/`, `shell/main/desktop/core/supervise.ts`, `packages/cli`): core is not a child of the shell; `ensureCore` (control socket `identify`, detached spawn, stdout first-line `ready|start_failed`) used by shell and by CLI human commands (CLI starts a core if none; `lophn core stop` = `core.stop` in `packages/cli/commands/core.ts`, does not start one; **no `lophn core start`** command). Packaged core is the Electron executable run as Node (`ELECTRON_RUN_AS_NODE`) with `--home <root>`; there is no separate Node server artifact. Idle-exit: after 10 min with no jobs/runs/workflows/agent turns and no clients; `remote.enabled` counts as permanent work. Quit of the app does not stop the core. Crash: no core-side restart; next ensure restarts (shell: 60 s window, 5 crashes).
- Autostart: `shell/main/desktop/autostart.ts` (Linux XDG `lophn.desktop` autostart entry, macOS/Windows Electron login item; launch intent `--core`, `launch-mode.ts`; packaged builds only; state read/written from OS registration via `wiring/desktop.ts`, exposed from the tray, no setting). It starts only the core and ends.
- Packaging (`tools/package/{linux,mac,win}.ts`, `packages/base/install/*-install.ts`): Linux `.deb` -> `/opt/lophn`, `/usr/bin/{lophn-desktop,lophn}`, `/usr/share/applications/lophn.desktop`, DEBIAN `control` (Depends from `LINUX_DEPENDS`, Electron libs), `postinst` (chmod 4755 chrome-sandbox), md5sums; macOS dmg (`lophn-desktop.app`, CLI `<root>/bin/lophn`); Windows NSIS (`lophn.cmd`). **No systemd unit, launchd agent, Windows service or scheduled task anywhere in the repo**; invariant 14 of platform.md says this is deliberate. A core can be started headless only through the CLI or autostart, and it still needs the Electron/Chromium dependencies of the deb.
