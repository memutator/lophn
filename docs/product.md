# lophn

## 문제

- agent로 앱을 만드는 비용은 크게 낮아졌다. 하지만 만든 뒤 유지하는 비용은 낮아지지 않았다.
- 사람에게 필요한 것은 채팅 화면보다 소프트웨어와 GUI다.
- 앱마다 엉성하고 서로 다른 화면을 새로 만든다. 앱끼리 재료를 나누지 못해 두 번째 앱도 처음처럼 비싸다.
- 외부 형식이나 의존성이 바뀌면 앱이 조용히 깨지고, 왜 깨졌는지 알 수 없다.
- 반복되는 결정적인 일을 agent가 매번 token으로 처리해 비용과 변동이 늘고 검증할 수 없다.

## lophn은 무엇인가

lophn은 **코드를 읽지 않는 사람이 coding agent에게 시켜 만든 개인 앱과 문서를, 자기 컴퓨터에서 오래 쓰게 해 주는 로컬 데스크톱 플랫폼**이다.

- 사람은 의도를 말하고, 결정하고, 취향을 고른다. 저장, 버전, 색인, 권한 같은 안쪽 일은 보이지 않게 저절로 된다.
- 코드는 사람이 원래 쓰던 coding agent(Claude Code, Codex 등)가 짠다. lophn은 어느 coding agent든 붙을 수 있는 통로(MCP, CLI, skill)를 연다.
- lophn에는 자기 agent(lophn agent)가 있다. lophn agent는 **코드를 짜지 않는다.** 무엇을 왜 만들고 고칠지 정하고, 돌아가는 것을 지켜보고, 돌본다.
- 핵심 가치는 "만드는 순간보다 그다음"이다. 앱이 깨지면 사람보다 먼저 알고, 무엇이 왜 바뀌었는지 되짚을 수 있고, 고치는 동안 사람이 덜 끼어들고, 두 번째 앱이 첫 번째보다 싸게 만들어진다.
- 사람과 agent가 함께 보는 것은 대화가 아니라 **문서와 앱**이다. 대화로 합의한 것은 문서나 앱으로 남는다.
- 하지 않는 것: coding agent 자체를 만들지 않는다. 채팅 중심 비서가 아니다. 여러 사람이 나눠 쓰는 서비스가 아니다. 앱 마켓이 아니다.

### 문서와 앱

| | 문서 | 앱 |
|---|---|---|
| 가치 | 내용 | 동작 |
| 보는 사람이 없을 때 | 아무것도 안 한다 | 스스로 돈다 |
| 시간이 지나면 | 버전이 쌓인다 | release로 바뀐다 |

보는 사람이 없어도 돌아야 하거나 코드로 돌봐야 하면 앱, 아니면 문서다. 앱은 문서를 만들어 낼 수 있고, 자주 쓰는 문서는 새 앱의 씨앗이 될 수 있다.

## 누구를 위한가

- 최우선 사용자는 **코드를 읽지 않지만 coding agent에게 앱을 만들게 하는 사람**이다.
- 사람은 의도·결정·취향만 고르고, 저장·version·색인·권한은 안쪽에서 저절로 처리된다.
- 개발자도 쓸 수 있지만, 개발자 편의 때문에 코드를 읽지 않는 사람을 희생하지 않는다.

## 일은 맞는 주체에게

| 주체 | 맡는 것 |
|---|---|
| 사람 | 의도, 결정, 취향, 최종 권한 |
| agent | 설계, 판단, 모호함 해석, 유지보수 |
| machine | 반복, 수집, 집계, 스케줄, 렌더링 |

- 반복되는 결정적인 일은 소프트웨어로 굳히고, agent의 token은 새로운 판단에만 쓴다.
- 판단이 필요 없는 일을 agent에게 맡기지 않는다. 판단이 필요한 일을 규칙으로 흉내 내지 않는다.

## 하지 않는 것

- coding agent가 할 일을 하지 않는다.
- 채팅 중심 개인 비서가 아니다. 메신저 채널을 늘려 가지 않는다.
- 여러 사람이 나눠 쓰는 호스팅 서비스가 아니다. 기성 앱을 파는 마켓이 아니다.
- cloud 분산 시스템, 임의 workflow 언어, 범용 ORM으로 범위를 넓히지 않는다.

## 잘되고 있다는 신호

- 두 번째 앱이 첫 번째보다 싸게 만들어진다.
- 앱이 깨진 것을 사람보다 먼저 안다.
- 수리하는 동안 사람이 덜 끼어든다.
- agent가 필요한 정보에 더 적은 token으로 닿는다.
- 새 앱의 많은 부분을 쌓인 재료에서 다시 쓴다.

## 설계 원칙

모든 영역이 지킨다. 이전 lophn은 설계가 과했고(쓰이지 않는 표, 처리 주체 없는 큐, 상태 축 여러 개, 나중을 위한 자리), agent를 나중에 붙일 것으로 미뤘다. 아래 원칙은 그 반성이다.

- **P1 일에서 출발한다.** 모든 엔티티, 필드, 상태는 어느 [flow](flows/)의 어느 단계에서 쓰이는지 댈 수 있어야 한다. 대지 못하면 뺀다.
- **P2 지금 필요한 것만 넣는다.** 나중 확장을 위한 자리, 예약 필드, 아직 없는 경우를 위한 종류나 상태를 만들지 않는다. 실제로 필요해지면 그때 붙인다.
- **P3 상태는 적게.** 사람이 구분해서 봐야 하거나 machine이 판정에 쓰는 상태만 둔다. 같은 사실을 두 상태 축으로 나누지 않는다. 모든 상태 기계에는 전이표(어디서 어디로, 누가, 언제)를 둔다.
- **P4 ledger는 하나, 쓰는 주체도 하나.** lophn이 기억하는 사실은 `lophn.db` 한 곳에 있고, 쓰는 것은 코어의 명령 처리 하나뿐이다. 명령은 짧다. DB를 읽고 쓰는 것 말고는 하지 않는다. 파일 순회, 큰 파일 해시, 네트워크, 모델 호출, 앱 실행은 명령 처리 안에서 하지 않는다. 그런 일은 다른 프로세스가 하고, 결과만 명령으로 낸다(→ platform/ledger, platform/responsiveness). 결과가 낡았을 수 있으면 비교 기준(이전 버전, 이전 해시)을 같이 내고, 맞지 않으면 명령은 거절된다.
- **P5 ledger를 쓰지 않는 일은 ledger를 기다리지 않는다.** 읽기는 쓰기 줄을 거치지 않는다. 앱 화면과 앱 명령 호출은 ledger를 거치지 않고 앱으로 간다. 실행 기록은 뒤따라 적히고, 응답을 막지 않는다. lophn agent의 읽기 도구도 범위만 확인하고 바로 읽으며, 도구 호출 기록은 뒤따른다(→ lophn-agent/harness/tools). 예외는 하나다. 사람이 확인해야 하는 앱 명령은 실행 직전에 접수를 남기고 승인을 한 번 쓴다(→ apps/invocations).
- **P6 앱의 업무 데이터는 앱의 것.** 앱 DB는 그 앱만 쓴다. ledger에 넣지 않는다.
- **P7 파생물은 ledger가 아니다.** 목차, 검색 색인, 요약 캐시처럼 다시 만들 수 있는 것은 ledger 밖에 두거나 그때 계산한다. 파생물을 문서로 저장하지 않는다.
- **P8 모든 변경에 누가와 기록.** 상태 변경에는 actor가 붙고, 같은 트랜잭션에 이벤트가 남는다.
- **P9 agent는 결정하지 않는다.** 되돌릴 수 없는 일은 사람의 승인이 있어야 한다. agent는 문제를 닫지 못한다. "고쳤다"는 machine이 확인한 신호나 사람의 확인으로만 성립한다.
- **P10 "완료"는 쪼갠다.** 서로 다른 완료(파일 저장 / 버전 확정 / 색인 반영, 접수 / 실제 시작 / 결과)는 서로 다른 사실로 적고 화면에도 따로 보인다. 회수 요청과 실제 회수, 증상이 안 보임과 수리 확인도 다른 사실이다.
- **P11 없는 것은 없다고 적는다.** 모으지 못한 증거, 돌리지 않은 테스트, 모르는 사용량을 성공이나 0으로 채우지 않고 없음이나 모름으로 보인다.
- **P12 개념 하나에 이름 하나.** 문서와 코드 이름은 [말](README.md#말), 화면 말은 [ui-ux/README.md](ui-ux/README.md) 한 곳에서 정한다. 옛 이름을 별칭으로 남기지 않는다. 이름과 경로에 버전, 마일스톤, 작업 번호를 넣지 않는다(`v2`, `m1`, `w07` 같은 것 금지).
- **P13 한 개념은 한 영역만 정의한다.** 다른 영역은 이름으로 가리키기만 한다([concerns.yaml](concerns.yaml)).
- **P14 agent와 같이 설계한다.** agent가 읽고 판단하고 쓰는 것을 "나중에 붙일 것"으로 미루지 않는다. 처리 주체가 없는 흐름(아무도 처리하지 않는 큐)을 만들지 않는다.
- **P15 사람의 것은 사람의 컴퓨터에.** 사람의 문서, 앱 데이터, secret은 이 컴퓨터에 있다. 외부 연결이 끊겨도 로컬 문서와 기록을 읽는 일, 외부 연결이 필요 없는 앱 동작은 계속된다.
- **P16 일에는 주인이 있다.** 자동으로 처리한다고 접수한 일에는 실제로 처리할 주체가 정해져 있다. 사람이 해야 하는 일을 "자동 처리 대기"로 숨기지 않는다.
- **P17 화면은 덜어 낸다.** 화면을 보는 사람은 개발자가 아니라 바이브코딩 사용자다. 화면에는 지금 판단하거나 행동하는 데 꼭 필요한 것만 보인다. ledger, release, invocation 같은 안쪽 개념과 복잡한 과정은 lophn이 프로그램과 harness로 알아서 처리하고 숨기며, 원하면 펼쳐 본다. intent가 requirements를 덮듯 화면이 안쪽을 덮는다.
