# remote

폰 앱이다. 명단에 든 폰이 컴퓨터의 core에 붙어 lophn agent의 session 목록을 보고, 대화를 읽고 보내고 멈추고, 승인과 질문에 답하고, job을 켜고 끄고, project의 file을 읽는다. 컴퓨터의 core가 띄운 coding agent(Claude Code, Codex, OpenCode, omp, Antigravity)의 대화도 같은 화면으로 보고 답하고 새로 열고, 그 터미널 화면을 보고 허락받은 기기는 친다(터미널로 도는 session은 그 터미널 화면으로 열린다). 폰 화면은 폰 앱(`mobile`)의 native React Native 화면이고 폰 UI kit(`@lophn/ui-native`, `ui-kit.md`)으로 짓는다. lophn 자신의 화면은 컴퓨터가 내려주지 않는다. 컴퓨터에서 도는 사용자 앱의 폰 화면(앱의 agent가 kit으로 쓴 React Native)만 컴퓨터가 bundle로 내려주고 폰 앱 안의 격리된 runtime(guest)에서 돈다(`phone-screen.md`). 컴퓨터가 폰에 묻는 길(`request`·`response` frame, 앱 backend가 폰의 위치를 읽는 첫 기능)과 폰의 홈 화면(위젯, 아이콘, open target. `phone-home-screen.md`)도 여기서 이어진다. 연결(listener, Noise)은 `platform.md`의 "폰이 붙는 listener", 기기 자격과 route 목록은 `approval.md`의 "폰(기기) 자격", 기기에 가는 event는 `event.md`가 맡는다. 컴퓨터의 기계 id와 이름, 복제 판정은 `machine.md`다. 한 사람의 폰과 컴퓨터는 서명한 명단 하나를 같이 들어 한 번 들인 기기가 모든 컴퓨터와 이어지고, 컴퓨터의 core는 명단의 다른 컴퓨터마다 연결 하나를 든다(아래 "내 기기 명단"). desktop은 그 연결로 다른 기계의 lophn을 그 기계의 창에서 본다(아래 "desktop에서 다른 기계 보기").

## 문제

- 폰에서 일을 이어 가려면 desktop과 같은 대화·승인·Inbox 해석(ACP reducer, 승인·질문 card, 대기열, rewind)이 있어야 한다. 폰용으로 다시 짜면 같은 해석이 두 벌이 되어 고칠 때마다 맞춰야 한다.
- 폰 화면은 scroll, keyboard, gesture가 폰다워야 한다. desktop의 web 화면을 폰 WebView에 넣어 보았더니(계획 `phone-remote-web`) 폰답지 않았다. 컴퓨터가 화면을 내려주는 길(web bundle, hash 확인 cache, WebView, bridge)은 폰 껍데기를 무겁게 하고 폰에 없는 통로를 부르는 화면까지 끌고 왔다.
- 화면을 폰마다 맞춰 짜면 안 된다. 폭 320~430의 어느 폰에서나 맞아야 하고, 폭이 넓은 기기(접은 폰, tablet)에서도 깨지지 않아야 한다.
- 폰의 기기 key는 폰 안에만 있어야 하고, 화면 code가 그 key나 연결을 직접 만지지 않아야 한다.

## 목표와 비목표

- 목표: 사람이 승인한 wireframe대로 native 화면을 짓는다. 화면 아래의 로직(event client, Inbox store, 대화 source, 순수 reducer와 규칙)은 desktop과 같은 TypeScript를 쓰고 해석을 한 벌로 둔다. 화면 문구는 desktop과 같은 catalog를 쓴다. 컴퓨터 없이도 화면 모양을 볼 수 있다(sample 컴퓨터).
- 비목표: iOS build(push도 Android만이다, 사용자 앱의 폰 화면도 Android만이다), 폰의 알림 목록 화면, iOS의 위젯과 아이콘, 폰의 위치 말고 다른 기능(camera, background 위치와 위치 연속 받기, agent가 폰 기능을 부르는 길. 쓰는 예가 생길 때 하나씩 연다). WebView terminal, 모든 터미널 탭의 목록(보는 것은 coding session의 터미널과 폰이 연 터미널뿐), coding session의 rewind 미리보기, headless harness agent(`coding_*`)의 승인 card. 폰에서 secret 넣기(보호 입력 창은 desktop의 것), 만들기·고치기·지우기(agent, job, 앱, project, workflow 정의), provider와 model 관리, skip 켜기, session 지우기. 폰의 권한은 보기, 말하기, 답하기(승인·질문·앱 update), 켜고 끄기, 지금 돌리기, 새 session이다.

## 모델

```
폰 앱 ──(Noise 연결, call/watch frame, direct나 relay)──▶ core remote listener
  │ 컴퓨터마다 연결 하나. 모양은 desktop의 CoreSource(subscribe, current, call, watch, onEvent)
  ▼
data 층: 컴퓨터 store → event client, Inbox store, 대화 source (desktop과 같은 로직)
  ▼
화면: 뼈대(sidebar + place의 stack) 안의 native 화면. 폰 UI kit 위에 선다
```

- **뼈대.** root는 컴퓨터가 하나도 없으면 연결 흐름(pairing)에서 시작하고, 있으면 frame이다. frame은 왼쪽 sidebar(drawer)와 그 옆 place의 stack이다. 아래 tab bar는 없다. 폭 600 이상이고 높이 480 이상이면 sidebar가 늘 열려 있고 stack은 그 옆 card에 든다. 가로로 든 폰은 폭이 넘어도 낮아서 drawer로 둔다. 화면 이동은 React Navigation(native stack과 drawer)이다.
- **갈 곳.** 앱 안의 모든 곳(Home, Search, Inbox, 앱 새 판 살펴보기, Jobs, Agents, workspace, workflow 실행, file, 대화, diff, 새 session, Settings)은 하나의 union(`Place`)으로 이름 짓는다. 화면은 곳을 직접 만들지 않고 그 곳을 열어 달라고 한다. place마다 화면이 하나 등록되어 있고 그 화면은 place를 인자로 받는다. sidebar는 컴퓨터(고르기), Search, Inbox(배지), Jobs, Agents, workspace(project와 앱)와 그 session, Settings를 보인다.
- **화면.** Home(session 목록, 컴퓨터가 offline일 때의 안내), Search(session, workflow, file, job, agent 한 칸), Inbox(Now: 답할 것, 앱 새 판 살펴보기. History는 notice 목록이다), 대화(머리 줄은 session 이름이 큰 글이고 agent와 workspace가 아래 줄, 보내기, 멈추기, 승인과 질문 card, 여러 답 질문, 이유 한 줄을 받는 Deny sheet(대화 card, Inbox Now, Home 모두), model·mode·이름 같은 sheet, 입력칸에서 `/`를 치면 뜨는 command 목록(desktop과 같은 규칙. 화면 동작이 딸린 command는 그 sheet를 열거나 바로 하고, 모르는 이름과 컴퓨터에서만 되는 command는 보내지 않고 알린다), subagent 줄을 누르면 그 대화를 읽기 전용 sheet로, 첨부, 파일 diff), 새 session(workspace와 agent 고르기), project workspace(session, workflow, file 목록과 글 file 읽기), 앱 workspace(실행 기록과 판), Jobs(목록, 켜고 끄기, 놓친 차례 Start now), Agents(목록과 상세), Settings(Computers, Appearance, About).
- **컴퓨터의 coding agent.** 폰은 desktop의 harness GUI 대화(Claude Code, Codex, OpenCode, omp, Antigravity)를 lophn agent session과 같은 대화 화면과 승인·질문 card로 보고 답한다. core가 GUI handle을 갖고 그 ACP 상태를 내므로 대화는 기존 `acp/snapshot`·`acp/send`·`AcpUpdated`이고 목록과 view 바꾸기·열기는 `coding_sessions/*`다(`harness-gui.md`, `acp.md`). data 층은 desktop의 harness GUI source에 폰이 읽은 `AcpState` feed를 끼운 것이다(재접속과 handle이 바뀔 때 snapshot을 다시 읽고 그동안 온 갱신은 snapshot 뒤에 접는다). source가 답하지 못하는 지난 session 목록과 rewind 미리보기는 capability로 칸이 숨는다. 대화 상태에는 tool 본문이 없어(`harness-gui.md`) 폰은 tool 줄을 펼칠 때 `acp/tool_body`로 그 본문 한 쪽을 읽는다. core가 handle에서 읽어 대화와 같은 redactor를 지나 낸다. 사진은 `acp/image_upload`로 컴퓨터가 그 터미널 탭의 임시 폴더에 쓰고 message는 그 file의 `file://` link를 싣는다(desktop GUI의 붙이기와 같다). 대화 안의 그림 link(폰이 붙인 것, desktop에서 붙인 것, 다시 연 대화의 그림)는 `acp/image_read`로 읽어 작은 그림으로 보이고, 읽지 못하면 file chip이다.
  - 화면. project workspace의 Sessions 위에 그 project의 coding 목록(chat은 상태 점, 터미널에서 도는 것은 작은 Terminal 표지). 대화(`session`에 `coding`을 단 place). 터미널에서 도는 session을 열면 대화 대신 그 터미널 화면이 바로 선다(아래 "터미널 보기"). `Switch to chat`은 그 화면 머리 줄의 ⋯ menu에 있고, 바꾸기 전에 sheet가 무엇이 멈추는지(도는 turn, background task, 줄 선 메시지)를 말하고 `Switch`를 눌러야 바꾼다. 못 바꾸면 sheet에 이유가 한 줄이다(extension이 꺼짐, 아직 session을 모름, 도는 agent가 없음, Windows). 바뀌면 같은 자리에 대화가 선다. 새 session 화면의 고르기는 workspace와 agent 단추 둘이고, agent sheet 안에 lophn agent 묶음과 컴퓨터의 coding agent 다섯의 묶음이 같이 선다. coding agent 묶음의 끝 줄 Terminal은 그 project의 폴더에서 shell이 도는 새 터미널을 컴퓨터에 열고(`terminals/open`) 그 터미널 화면으로 간다. coding agent를 고르면 아무것도 열지 않고 입력 칸 위에 컴퓨터의 새 터미널에서 시작한다는 안내가 선다. 첫 메시지를 보낼 때 컴퓨터에 새 터미널이 열리고 그 대화가 설 때까지(1분까지) 기다려 그 메시지를 보낸 뒤 그 대화로 간다. 열렸는데 보내기가 실패하면 다시 보낼 때 같은 session에 보낸다. 새 session의 첫 메시지에는 coding agent에게 사진을 붙이지 않는다(열린 대화에서는 붙인다). 끝난 coding session은 읽기만 되고 `Continue as chat`이 컴퓨터에서 같은 CLI session을 되살려 이어 간다(그 project의 지난 harness agent session). 터미널은 컴퓨터의 core가 열어 창이 없어도 되고, 그 project를 보이는 창이 있으면 탭으로도 보인다. 열지 못하면 열기가 컴퓨터의 문장을 그대로 보인다.
  - 컴퓨터의 앱이 꺼져 있어도 core가 돌면 목록, 열기, 대화, 터미널이 그대로다(터미널과 coding agent는 core의 것이다). 앱을 깨우는 단추는 없다.
- **사용자 앱의 폰 화면.** 사람의 앱 가운데 폰 화면(`phone` 자리)이 있는 앱은 sidebar와 Home의 앱 줄을 누르면 앱 workspace 대신 그 앱의 폰 화면이 열린다(`phone-screen.md`). 앱 workspace(session, 실행 기록)는 화면의 ⋯ menu로 간다. 컴퓨터에서 그 앱의 preview가 돌면 ⋯ menu에 "Preview from lophn"이 서고, live 폰 화면이 아직 없는 앱은 preview가 도는 동안 앱 줄에 "Preview" 표시가 붙어 바로 preview 화면을 연다(`phone-screen.md`). 폰은 컴퓨터의 `apps/phone_screens`로 화면 목록과 manifest를 읽어 폰이 돌릴 수 있는 화면인지 보고(`phone_too_old`면 "Update the lophn app to open this screen", `screen_too_old`면 "Ask lophn on your computer to update this app"), 돌릴 수 있으면 `phone.js`를 `apps/screen_file`로 받아 bundle hash로 cache하고, view를 `app_views/open`으로 열어 guest에서 돌린다. 화면의 operation 호출과 앱 event는 host bridge로 core의 view 표를 지나고 폰이 직접 앱을 부르지 않는다. 컴퓨터가 offline이거나 앱이 안 돌면 그 사실을 말하는 화면이 서고 돌아오면 저절로 열린다. 새 release가 live가 되면 화면을 새 bundle로 다시 띄우고 "Updated to Release N" 줄을 잠시 보인다. 화면 ⋯ menu가 앱의 session, 실행 기록, 변경 청하기, 앱의 다른 폰 화면을 연다.
- **폰에서 도는 앱.** 선언의 `runs_on`에 `phone`이 든 앱(sync 앱, standalone 앱)은 폰이 backend와 data를 가져 컴퓨터가 꺼져도 열리고 쓴다(`app-sync.md`). 폰은 `apps/phone_screens`의 항목(`runs_on`, backend manifest)을 보고 `apps/phone_file`로 backend와 migration file을, sync 앱은 `app_sync/snapshot`·`snapshot_file`로 컴퓨터 DB의 사본을 받아 폰 앱 폴더(`files/apps/<컴퓨터 key>/<앱>/`)에 둔다. 컴퓨터에 닿고 앱이 앞에 있는 동안 `app_sync/push`·`pull`로 맞추고 `AppSyncChanged`를 계기로 삼는다. 이 일은 sidebar가 쥐고 있어 앱을 열지 않아도 돈다(앱 목록은 폰이 가진 사본에서도 읽어 컴퓨터가 없어도 폰에서 도는 앱은 목록에 있고 열린다). Home의 앱 tile은 컴퓨터가 offline이어도 폰에서 도는 앱은 흐리지 않고 offline 안내가 그 앱이 계속 돈다고 말한다. 컴퓨터가 목록에서 빠지면 그 컴퓨터의 sync 앱 폴더는 컴퓨터에 안 간 변경이 없을 때만 지우고 standalone 앱의 data는 지우지 않는다.
- **터미널 보기.** 터미널로 도는 coding session과 폰이 연 터미널을 컴퓨터에 보이는 글과 색 그대로 보인다(`terminal_view/*`, `terminal-agent.md`). 머리 줄은 session 이름이 큰 글이고 session의 상태(도는 중, 기다림 등)와 project가 아래 작은 줄이다. 폰이 연 터미널은 "Terminal"과 project다. 화면을 styled text row로 그리고 각 칸은 고정폭 글꼴의 한 칸이라 열이 맞는다. 폭 2칸 글자(한글, emoji)는 폰에서 그 글자의 폭을 한 번씩 재서 두 칸에 맞춘다. 크기는 Paseo와 같은 규칙이다: 폰이 화면을 열 때, 화면을 누를 때 자기 화면의 열과 줄 수로 PTY 크기를 잡고(`terminal_view/resize`), 크기를 쥔 동안(받는 화면이 자기 크기인 동안) keyboard와 회전으로 바뀐 크기를 따라간다. 컴퓨터의 탭은 그동안 "Sized for a phone · Click to fit"을 보이고, 사람이 그 탭을 고르거나 누르거나 치면 칸 크기로 다시 잡는다(마지막에 잡은 쪽이 이긴다). 폰이 떠나 lease가 모두 끝나면 탭이 자기 크기로 돌아간다. 확대와 가로 scroll은 없다. 앞에 있는 동안 10초마다 lease를 갱신해 컴퓨터가 화면을 밀게 하고 뒤로 가면 멈춘다. 이 기기의 터미널 입력 허락(초대장을 낼 때 정하고 기본 켬, 명단 항목이라 어느 컴퓨터의 My devices에서나 기기마다 바꾼다)이 켜져 있으면 글 칸(보내기는 글만 치고 Enter를 치지 않는다)과 두 줄 key 줄(Esc, Tab, 화살표, Enter, Paste, 한 번만 걸리는 Ctrl·Alt·Shift)이 서고 화면을 누르면 keyboard가 뜬다. 꺼져 있으면 머리 줄에 `View only`가 서고 아래에 그 한 줄이 선다. 터미널이 컴퓨터에서 닫히면(`not_found`) 마지막 화면을 둔 채 닫혔다고 하고, 컴퓨터가 답하지 않으면 화면이 낡았을 수 있다고 한다.
- **page 보기.** sidebar의 Pages는 그 컴퓨터의 core가 아는 browser 탭(agent가 연 탭, 사람이 멀리서 연 탭)의 목록이고, 줄을 누르면 그 page의 그림을 본다(`page_view/*`, `browser-tab.md` "멀리서 보기"). 터미널 보기와 같은 꼴이다: 앞에 있는 동안 lease를 10초마다 갱신하고, 컴퓨터가 그림이 바뀌었다고(`PageViewChanged`) 알리면 snapshot을 다시 읽는다. 머리 줄은 주소 칸과 뒤로·다시 읽기이고, agent가 다루는 중이면 "<agent> is using this page"와 [Take control], 가져왔으면 [Hand back]이 선다. 그림을 손가락으로 누르고 끌고 두 손가락으로 굴리며, 아래 글 칸과 key 줄(Enter, Backspace, Tab, 화살표)로 친다. 목록 위의 열기 칸이 그 컴퓨터에 새 page를 연다(화면 없는 기계의 로그인). 이 기기의 터미널 입력 허락이 꺼져 있으면 열기 칸, 주소 칸과 단추, 잡기, 입력이 없고 볼 수만 있다는 것과 허락을 켜는 곳(Settings › Remote › My devices)을 한 줄로 보인다. 화면 있는 컴퓨터의 창이 최소화되거나 숨겨져 page를 그리지 않으면 그렇다고, page가 닫히면 닫혔다고, 컴퓨터가 답하지 않으면 그림이 낡았을 수 있다고 한다.
- **data 층.** 컴퓨터마다 연결 하나(`CoreSource`와 같은 모양이라 desktop 코드가 그대로 돈다) 위에 desktop과 같은 event client, Inbox store, 대화 source를 얹는다. 화면은 그 읽기 hook만 쓰고 연결을 만지지 않는다. 폰이 desktop에서 가져오는 것은 DOM과 Electron에 닿지 않는 순수 logic뿐이다. desktop file이 DOM kit이나 desktop 탭 type을 import해서 못 가져오는 순수 규칙(workflow 규칙, line diff)은 import가 깨끗한 file로 옮겨 둘이 같이 쓴다. DOM kit과 섞여 있던 작은 helper(경과 시간, turn 실패 글, tool 본문 글, 질문 card 제목, 편집 diff)도 DOM 없는 file로 꺼내 둘이 같이 import한다. sidebar의 session 목록 규칙(무엇을 고르고 어떤 순서로 두는지, 상태 점)과 대화의 slash command 규칙도 desktop과 같은 file을 쓴다(아래 "목록").
- **목록.** sidebar의 workspace마다 session 줄은 desktop sidebar와 같은 규칙 file을 쓴다: 도는 중, 기다리는 중, 사람이 보지 않는 사이 turn이 끝난 session은 위에 만든 순으로 서고(상태가 바뀌어도 자리를 지킨다), 나머지는 접힌 Recent에 최근 7일 안에 움직인 것이 최근 순으로 선다. 상태 점의 뜻(기다림, 도는 중, 못 본 끝, 끝남)도 같다. 폰에는 탭이 없어 탭이 열려 있다는 이유로 위에 서는 줄은 없다. folder가 둘 이상인 project는 Files 위에 folder 고르기가 서고 검색 결과의 file은 그 folder에서 열린다.
- **폰이 두는 것.** 폰은 컴퓨터마다 마지막으로 읽은 앱 목록과 project 목록(id와 이름)과 그 아이콘을 폰 앱의 file로 둔다. 화면은 컴퓨터가 답하기 전에 이것으로 먼저 그리고 새 값을 받으면 바꾼다. 컴퓨터가 닿지 않는 동안에는 그 컴퓨터의 앱과 project를 흐리게 그대로 보인다. sidebar가 늘 떠 있으면서 지금 고른 컴퓨터의 앱·project·release가 바뀔 때(`StateChanged`)와 다시 붙을 때마다 다시 읽고, 컴퓨터가 뺀 앱은 아이콘도 지운다. 목록에서 빠진 컴퓨터는 그 file도 지운다. 대화 내용은 두지 않는다: 대화는 컴퓨터에 닿을 때만 보인다.
- **sample 컴퓨터.** dev build에서 환경 변수로 켜면 지어낸 data를 내는 컴퓨터가 목록에 든다. desktop gallery의 fake core를 같은 event client, store, hook으로 돌려 화면이 진짜 컴퓨터와 같은 모양을 받는다. 저장하지 않고 하는 일은 메모리만 바꾼다. 화면 모양은 sample로, 동작은 개발 core로 본다.
- **문구.** desktop과 같은 `@lophn/i18n` catalog다. desktop에 있는 문장은 그 key를 그대로 쓰고, 폰에만 있는 문장만 `mobile.`로 시작하는 key로 더한다. Hermes에는 `Intl.Segmenter`, `Intl.PluralRules`, `Intl.RelativeTimeFormat`이 없어 앱 시작 때 한 곳에서 영어 대체를 깐다(제목 한도의 글자 수를 code point로 세어 이모지 조합은 조금 길게 센다).
- **모양.** Appearance는 theme(시스템, light, dark)와 글 크기(small, default, large)를 이 폰의 보안 저장소에 둔다. 글 크기는 kit의 text scale 한 값으로 넘기고 화면마다 따로 고치지 않는다.
- **들어오기.** 처음 열면 Welcome이다. Scan the code는 camera로 초대장 QR을 읽고, "Paste the invite instead"는 초대장 글(QR에 든 JSON. desktop Settings › Remote의 [Invite a phone]이 보이는 "Show as text", `lophn remote invite phone`이 찍는 줄)을 붙여 넣는다(camera가 없거나 허락하지 않은 폰, emulator). 폰은 kind `phone` 초대장만 받고 컴퓨터용 초대장이면 그렇다고 말한다. Pairing 화면은 초대장의 컴퓨터에 붙어 초대장의 비밀로 서명한 자기 항목을 `join`으로 내밀고(새 폰이면 새 id, 다른 컴퓨터가 이미 들인 폰이면 명단의 그 id. 아래 "내 기기 명단"의 "들이기") 첫 연결이 열리기를 기다린다. Paired는 "Paired with <컴퓨터 이름>"이고, 이름 칸은 비어 있고 placeholder가 그 컴퓨터의 이름이다. 무엇을 쓰면 이 폰에서만 그 컴퓨터를 부르는 별명("Shown as")이 된다. 지났거나 이미 쓴 초대장은 Code expired, 닿지 않으면 Cannot reach 화면이다. 터미널 입력 허락은 사람이 초대장을 낼 때 정한다(기본 켬, `terminal-agent.md`). 기기 key 쌍, 폰의 이름, 컴퓨터 목록(주소 후보, port, host key, 서명 key, 기계 id, relay 주소, 명단의 이름, 별명)은 보안 저장소(이 기기에서만, 잠금이 풀렸을 때만)에, 든 명단(statement와 주소. 공개 key와 서명뿐이다)은 앱 file `roster.json`에 둔다. 무작위는 `expo-crypto`다(Hermes에는 전역 crypto가 없다).
- **명단에서 나가기와 빠지기.** Settings의 컴퓨터 상세 [Remove this phone from my devices]는 이 폰을 명단에서 뺀다: 붙어 있는 컴퓨터 하나에 `roster/leave`를 부르면 그 컴퓨터가 빼기에 서명해 모든 기계에 퍼뜨리고, 폰은 모든 컴퓨터, 든 명단, 기기 key를 잊고 Welcome으로 돌아간다. 붙은 컴퓨터가 없으면 폰만 잊고 명단에는 남는다(사람이 컴퓨터의 My devices에서 뺀다). 다시 쓰려면 새 초대장으로 새 기기(새 key, 새 id)로 든다. 컴퓨터 하나만 목록에서 지우는 길은 없다. 폰이 받은 명단(컴퓨터가 민 `roster`, `join` 거절의 `details.removal`)에서 자기 key가 빠진 것을 자기 root로 확인하면 같은 길로 다 잊는다. 확인하지 못한 거절은 그 컴퓨터를 `revoked`로 두고 앱이 다시 시작할 때까지 다시 붙지 않는다.
- **연결.** 저장한 direct 주소 후보(처음은 QR의 것)와 relay(QR에 있으면)를 같이 걸어 먼저 handshake가 된 것을 쓴다. relay 길은 바이트만 넘기므로 handshake와 그 뒤는 direct와 같다. relay를 더하기 전에 들어온 폰은 새 초대장으로 한 번 다시 들어와야 relay 주소를 안다(명단의 주소는 목록에 없던 컴퓨터를 더할 때만 쓴다). 폰은 그 컴퓨터의 기계 id를 알면 연결마다 hello에서 대조하고, 다른 id가 답하면 아무것도 보내지 않고 그 시도를 닿지 않은 것으로 끝낸다(목록에는 offline이다. 아래 "hello"). 저장한 기계 id를 대조한 연결에서는 core hello의 주소 후보로 저장한 목록을 바꾼다. 그 연결이 열린 direct 주소가 목록에 없으면 앞에 남긴다(컴퓨터는 자기가 닿는 주소를 다 알지 못한다. emulator의 host alias, 넘겨 준 port). 그래서 들어온 뒤에 생긴 주소(새 network, Tailscale)도 다시 들어오지 않고 다음 연결부터 건다. id를 아직 모르는 연결은 주소를 바꾸지 않는다: 같은 key를 가진 다른 기계가 기기를 다른 곳으로 이끌지 못하게 한다. port는 hello에 없어 `remote.port`를 바꾸면 다시 들어와야 한다. 붙을 때마다 첫 frame `join`(자기 key의 statement) 뒤에 든 명단(`roster`)과 마지막 `watch`(없으면 `[]`)를 보내고 core의 `ready`로 `ready`가 된다. 끊기면 1초에서 30초 backoff로 다시 붙는다. core가 protocol 오류로 연결을 닫은 뒤에도 다시 붙는다. 앱이 뒤로 가면 다시 붙기를 멈추고, 앞으로 오면 열린 연결에 `watch`를 다시 보내 3초 안에 `ready`가 없으면 버리고 바로 다시 붙는다. 틀린 조건(session id가 아닌 문자열 등)은 `watch`에 싣지 않는다. core가 그 조건을 이해하지 못하면 연결을 닫고, 새 연결이 마지막 `watch`를 다시 보내므로 폰이 영영 offline에 머문다. 컴퓨터 목록은 컴퓨터마다 상태(connecting, connected, offline, revoked)와 길(direct, relay), 그 컴퓨터 Inbox의 대기 수를 보인다.
- **hello.** Noise handshake 뒤 붙는 쪽이 먼저, core가 그 뒤에 hello를 보낸다. 붙는 쪽은 `{version, min_version, capabilities, name, phone?}`(name은 자기 이름 1~64자. capabilities는 폰이 답하는 `request` kind. phone은 폰의 화면 `{os, width, height, dpr}`이고 core가 이 컴퓨터에 처음 붙는 폰의 기기 행과 `shell.devices` 항목을 이것으로 만든다)이고 core는 `{version, min_version, capabilities, machine: {id, name, addresses}}`(지금 판과 하한은 둘 다 4, capabilities는 빈 목록)이다. `addresses`는 연결마다 다시 계산한 direct 주소 후보다: 설정 `remote.addresses`(사람이 적은 domain이나 IP. interface에 붙지 않는 VM의 공인 주소나 Tailscale 이름. 사람만 `lophn settings set`으로 바꾸고 Settings 화면의 칸은 없다)가 먼저, 그 뒤 loopback과 link-local을 뺀 interface 주소이고 16개까지다. 초대장의 주소 후보도 같은 목록이다. 이 칸 전의 core는 싣지 않아 붙는 쪽이 저장한 목록을 그대로 쓴다. 모르는 칸은 버려서 다음 판이 칸을 더해도 붙는다. Noise prologue(`lophn-remote/1`)는 판과 따로라 그대로다.
  - 판. 상대의 `version`이 내 `min_version`보다 낮거나 내 `version`이 상대의 `min_version`보다 낮으면 `conflict`로 닫는다. core는 붙는 쪽의 판이 범위 밖이어도 자기 hello를 먼저 보낸 뒤 닫아, 양쪽이 같은 두 hello로 같은 판정 `{code: conflict, details: {update: client | host}}`을 낸다. `client`는 붙는 쪽을, `host`는 그 컴퓨터의 lophn을 올려야 한다는 뜻이다. 붙는 쪽의 오류는 core hello의 `machine.name`을 `details.name`으로 같이 실어 어느 컴퓨터인지 말한다. core는 같은 값을 log에 남긴다. 붙는 쪽 연결(`@lophn/remote-client`)은 그 컴퓨터의 상태를 offline이 아니라 `update`(누가 올릴지와 함께)로 두고, 판이 맞아 붙을 때까지 같은 간격으로 다시 붙으며 그대로 둔다. 폰은 banner, 잠긴 입력 칸, Computers 줄에 "Update the lophn app on this phone to reach <이름>."(`client`)나 "<이름> runs an older lophn. Update lophn on <이름> to reach it from this phone."(`host`)를, desktop은 기계 고르기, My devices의 컴퓨터 줄, 그 기계 창의 gate에 같은 뜻("Update lophn on this computer" / "Update lophn on <이름>")을 보인다. 들어오는 중이면 폰의 실패 화면과 desktop의 [Join with an invite] 오류가 같은 뜻을 보이고, 초대장은 쓰이지 않아(`roster/join`은 저장하지 않는다) 올린 뒤 다시 쓸 수 있다. 올리는 일은 각 기계에서 사람이 한다(모든 기계를 올리는 단추와 updater는 없다).
  - 판 3은 명단이다(첫 frame이 `join`이고 `pair`가 없다). 판 4는 명단 규칙(쓰인 초대, key로만 세는 빼기, 모르는 서명자 상한)이다. 판 3과 같은 명단을 다르게 보므로 섞이지 않는다. 판 3 이하 build는 판 4 core와 범위가 겹치지 않아 hello 뒤 위 안내(`client`)를 받고 붙지 못한다. 판 1 옛 폰 build의 hello는 `min_version`과 `name`이 없어 core가 모양 밖 frame으로 보고 자기 hello 없이 닫는다. 옛 build는 붙지 못하고 다시 붙기를 되풀이하며 offline으로 보이고 누가 올려야 하는지 듣지 못한다. 그래서 폰 앱과 core를 같이 올린다.
  - 기계 확인. 붙는 쪽은 들어올 때 core hello의 기계 id를 저장하고, 저장한 것이 있으면 연결마다 hello의 id와 대조한 뒤에만 channel을 연다. 다르면 hello 말고 어떤 frame도 보내지 않고 닫는다(`conflict`, "a different computer answered"). 같은 key를 가진 복사된 data root가 답해도 `join`이나 call이 그쪽으로 가지 않는다. 판 2 전에 pairing한 폰은 첫 연결에서 id를 배우고 둘째 연결부터 대조한다. 폰은 같은 컴퓨터에 다시 들어오면 그 항목을 바꾸고 별명을 남긴다.
- **기기 kind.** 명단 항목의 kind는 `phone` 또는 `computer`다(폰 os는 `ios|android`, 컴퓨터는 `linux|macos|windows`이고 컴퓨터만 서명 key와 `machine`을 갖는다). 기기 자격은 kind와 상관없이 같다: 기기 route 목록 전체와 `app_sync/*`이고 다른 기계를 관리하는 길은 없다(`approval.md`). 컴퓨터마다의 ledger `devices` 표에는 그 컴퓨터에 붙은 폰의 local 행만 있다: 폰이 이 컴퓨터에 처음 붙을 때 hello의 화면으로 만들고 마지막 연결, 기준, push token, 화면 칸을 둔다. 폰이 명단에서 빠지면 같은 write에서 지운다. phone에만 걸리는 것이 이 행이다: 기준 기기(`devices/set_primary`), 설정 `shell.devices`의 preview 기기 항목, push token(`devices/set_push`), phone 탭이 다루는 preview view(`phone-screen.md`), presence의 폰 규칙(`attention.md`). 컴퓨터는 행이 없어 기준이 되지 못하고 push token을 두지 못한다.
- **이름.** 기기의 이름은 명단 항목에 하나이고 모든 기계에 같다. 어느 컴퓨터의 My devices에서나 `roster/rename`으로 바꾸면 그 컴퓨터가 서명한 새 rev가 퍼진다. 컴퓨터가 기기마다 붙이던 별명은 없다. 컴퓨터의 이름은 기계 이름(`machine.md`)과 한 값이다: 이 컴퓨터 줄은 "This computer"의 `machine/rename`으로 바꾸고 core가 바로 자기 항목을 새 rev로 서명하며(`roster/rename`으로 자기를 바꾸면 `invalid_input`), 다른 컴퓨터가 이 컴퓨터의 이름을 바꾼 rev를 받으면 그 이름을 기계 이름으로 삼는다. 폰의 이름은 폰이 연결마다 hello로 알리고, 컴퓨터는 폰이 알린 이름이 마지막으로 받은 것과 다를 때만 명단 이름을 새 rev로 서명한다(사람이 컴퓨터에서 바꾼 이름을 폰이 옛 이름으로 다시 덮지 않는다). `shell.devices`의 그 폰 항목도 명단 이름을 따른다(40자로 자른다).
- **이름(폰 쪽).** 폰 앱은 자기 이름(Settings › This phone, 기본은 기기 model, 40자)을 모든 hello에 싣는다. 이름을 바꾸면 열린 연결을 모두 닫고 다시 열어 컴퓨터가 바로 새 이름을 받는다. 폰은 컴퓨터마다 명단의 이름(`announced`)과 이 폰에서만 쓰는 별명(`name`, "Shown as")을 따로 두고 보이는 이름은 별명, 명단의 이름, 주소 차례다. 명단의 이름은 명단(없으면 hello)이 고치고 별명은 건드리지 않는다. 컴퓨터 상세의 "Shown as"는 보이는 이름이고 별명이 명단의 이름과 다르면 그 아래 "Calls itself <명단의 이름>"이 서며, sheet의 [Use the computer's name]이 별명을 지운다.
- **복사된 data root.** core는 기동마다 remote key 둘(host key, 서명 key)에 찍힌 기계 id(`machine`)를 지금 id와 대조한다. 다르거나 둘 가운데 하나만 읽히면 그 data root는 다른 기계에서 복사된 것으로 보고 key 둘을 먼저 지운 뒤 명단과 기기 행을 모두 버린다(`roster/forget_all`. 행마다 끊기와 같이 연결, 자격, `shell.devices` 항목을 거두고 push token도 사라진다). 다음에 remote를 열 때 지금 id를 찍은 새 key 둘과 새 자기 항목(새 id)을 만들고 relay에도 새 key로 붙는다. 옛 기계의 명단에 든 기기는 이 기계를 모르고, 이 기계는 명단의 컴퓨터에서 새로 초대받는다. key file이 없거나 둘 다 못 읽거나 id가 같으면 아무것도 하지 않는다. 이 판 전에 만든 host key에는 data step `remote.host-key.machine`이 key 값을 그대로 둔 채 지금 id를 찍고 `remote.signing-key`가 짝 서명 key를 더한다. Settings › Remote의 "This computer"는 복제로 새 기계가 되었으면 명단의 컴퓨터에서 다시 초대받으라고 알린다.
- **폰 route 목록.** 기기가 부를 수 있는 route는 `approval.md`가 정한다. 폰 화면을 지으며 session·대화 쪽에 Agents, Jobs와 그 실행 기록, workflow, 앱 실행 기록과 release, project의 file 목록과 글 file 읽기(`project_files/list`, `project_files/read`)가 더해졌고, 기기가 부르는 `jobs/update`는 `{job, enabled}`만 받는다. coding agent를 위해 `coding_sessions/list|switch_plan|switch|open`, `terminal_view/snapshot|watch|resize`, `terminals/open|input`이 더해졌다. agent의 browser page를 위해 `page_view/list|snapshot|watch|input|control|open`이 있다(`terminals/input`과 `page_view/input|control|open`은 목록에 있어도 이 기기의 터미널 입력 허락이 켜져 있을 때만 core가 받는다. 허락은 명단 항목의 칸이고 그것을 바꾸는 `roster/set_terminal_input`과 초대장을 내는 `roster/invite`는 목록에 없다). coding session의 대화를 위해 `acp/tool_body`, `acp/image_upload`, `acp/image_read`가 있다. 기기와 명단 route는 자기를 명단에서 빼는 `roster/leave`와 자기 push 설정을 두는 `devices/set_push` 둘이고, 알림을 위해 `presence/report`(지금 앞에 보이는지와 열린 session)도 목록에 있다. 사용자 앱의 폰 화면을 위해 `apps/phone_screens`, `apps/screen_file`, `app_views/open|call|close`가 있고 폰에서 도는 앱을 위해 `apps/phone_file`과 `app_sync/push|pull|snapshot|snapshot_file`이 있다(앱을 직접 부르는 `apps/call_tool`, grant, 화면 오류를 쓰는 `apps/log_view_error`는 없다). 홈 화면 위젯을 위해 `app_widgets/list`가 있다(`phone-home-screen.md`). 앱이 폰에 묻는 `app_phone.request`는 폰 gate에 없다. `devices/clear_push`와 `devices/push_targets`는 core 안 machine 자격만 부르고 폰은 부를 수 없다. 화면은 목록 밖 route를 부르는 단추를 보이지 않는다(Inbox에 job 거절이 없고 job 이름·때 고치기가 없다).
- **사람 route 목록.** 터미널 입력을 허락받은 기기에는 그 기계의 처음 설정이 열린다(`REMOTE_PERSON_ROUTES`, 내용과 확인 규칙은 `approval.md`의 "폰(기기) 자격"). 그래서 화면 없는 기계도 다른 컴퓨터의 창이나 폰에서 secret, provider 연결, 기본 model, 설정, agent, project 더하기를 처음부터 한다. 값은 그 기기와 그 기계 사이의 암호화된 연결로 그 기계의 core에만 간다(다른 컴퓨터의 창에서 넣은 값은 이 컴퓨터 core의 `machines/call` upload로 지나가고 이 컴퓨터의 secret 저장소, log, event, ledger에 닿지 않는다). 다른 기계의 창은 그 기계의 core만 쓰는 Settings 항목(General, Providers, Agents, Tools and skills, Shell rules, Diagnostics)과 project 등록(그 기계의 폴더 목록 `projects/browse`)을 열고, 이 컴퓨터에 붙은 항목은 한 줄로 알린다. 폰은 agent의 secret·sign_in 요청에 답하고 Settings › A computer › Providers에서 API key와 device code로 provider를 잇는다. 그 기계의 browser로 돌아와야 하는 로그인(ChatGPT, Claude, Antigravity, MCP·앱 OAuth)은 다른 기기에서 시작하지 않는다: 화면이 단추를 감추고, 기기 자격이 loopback 로그인을 시작하면 core가 거절한다.
- **컴퓨터가 폰에 묻는 길.** core가 폰에 일을 시키는 길은 하나다. remote channel에 frame 둘이 있다: core→폰 `request {id, kind, input, deadline_ms}`(deadline은 1~60초)와 폰→core `response {id, ok, value | error}`(`result`와 같이 ok로 가른다). `kind`는 폰이 하는 일의 이름이고 폰은 답할 kind를 handshake 뒤 `hello`의 `capabilities`에 적는다. core는 거기 없는 kind를 묻지 않으므로 옛 폰은 `request`를 받지 않고 `REMOTE_PROTOCOL_VERSION`은 그대로다. kind는 표 하나(`PHONE_KINDS`)에 입력 schema, 출력 schema, deadline과 같이 한 항목이고, 새 일은 그 항목 하나와 폰의 handler 하나로 더한다. frame은 바뀌지 않는다. 답의 bytes는 `value` 안의 `*_base64` 문자열에 base64로 싣고 원래 8 MiB 안에서 frame 상한(16 MiB)에 든다.
  - core의 `PhoneLink.call({device, kind, input, deadline_ms})`가 묻는다. 그 기기의 열린 연결에 `request`를 보내고(같은 기기의 연결이 여럿이면 마지막 것) 같은 연결에서 온 같은 `id`의 `response`, deadline, 연결 닫힘 가운데 먼저 온 것으로 끝낸다. 연결이 없거나 닫히면 `unavailable`(`phone_unreachable`), 폰이 그 kind를 `capabilities`에 적지 않았으면 `unavailable`(`unsupported`), deadline까지 답이 없으면 `unavailable`(`timeout`)이다. 모르는 `id`의 답, deadline 뒤의 답, 다른 연결(다른 기기)의 답은 버린다. 폰을 push로 깨우지 않는다. 입력과 출력이 kind에 맞는지는 묻는 쪽이 본다.
  - 폰의 handler는 앱이 앞에 있을 때만 답한다(아니면 `unavailable`, `phone_in_background`). 입력은 kind의 schema로 본다(틀리면 `invalid_input`). 답이 deadline 뒤에 올 일이면 보내지 않는다. kind는 handler가 있는 것만 `hello`에 적는다.
  - 첫 kind는 `location.get`이다. 입력 `{accuracy?: low|balanced|high, max_age_ms?: 0~300000}`(기본 balanced와 0, 기본은 폰이 적용한다), 출력 `{lat, lon, accuracy_m, at}`, deadline 20초다. 폰은 OS의 앞에 있을 때 위치 권한만 쓰고(background 권한은 manifest에 없다) 처음 쓸 때 한 번 OS에 묻고 거절하면 다시 묻지 않는다(`forbidden`과 `details.reason: "os_permission_denied"`. 사람이 시스템 설정에서 바꾼다). OS의 위치 서비스가 꺼져 있으면 `unavailable`(`location_off`)이고, `max_age_ms`가 있으면 그 안의 마지막 위치를 먼저 쓴다.
  - 앱의 길은 이 길 위의 하나다. 앱 backend가 SDK part `@lophn/cap-phone`의 `getLocation`을 부르면 앱 supervisor의 broker(`/_lophn/broker/phone/request`)가 live 자식인지, 지금 release의 선언 ∩ grant에 `phone.use {capability}`가 있는지를 요청마다 보고(없으면 `forbidden`이고 폰에는 묻지 않는다) core의 memory route `app_phone.request`(actor app)를 그 자식의 credential로 부른다. core는 앱이 active인지, 입력이 kind에 맞는지 본 뒤 사람의 기준 폰(`devices.is_primary`)에 묻고 폰의 답이 kind의 출력에 맞는지 보고 앱에 준다(안 맞으면 `unavailable`). 기준 폰이 없으면 `unavailable`(`no_phone`)이다. `app_phone.request`는 폰이 부르는 route가 아니다(폰 gate에 없다). 위치를 읽는 일은 lophn의 banner를 띄우지 않고 기록을 쓰지 않는다. 동의는 앱의 activation 동의 카드(`activation.md`)이고 읽는 것을 사람에게 보이는 것은 Android 자신의 위치 표시다.
  - drive(`drive.snapshot|act|screenshot|wait`, 단계 10). 컴퓨터의 agent가 연 phone 탭(`browser-tab.md`)의 `lophn browser` 호출을 core가 `drive.*`로 바꿔 그 앱의 preview view를 연 기기에 묻는다. preview만이다: core는 기기 owner의 preview view만 고르고, 폰은 자기가 연 preview view(그 컴퓨터를 위해 연 것)가 아닌 view에는 native module을 부르지 않고 `no_preview`로 답한다. 폰은 preview 화면이 열린 동안 화면을 켜 두지만 컴퓨터가 폰을 깨우거나 lophn 앱을 앞으로 부르지 못한다. 화면이 꺼졌으면 `screen_off`, 무언가가 preview를 덮었으면 `covered`, 사람이 take control했으면 act만 `conflict`다. 폰 앱의 화면과 native module은 `phone-screen.md`의 "drive".
- **알림.** 폰은 push token과 알림 설정을 붙는 모든 컴퓨터에 `devices/set_push`로 알린다(붙을 때마다, 바뀔 때마다). 컴퓨터는 이 값을 그 기기의 행에 둔다(token과 설정 칸 일곱, `devices/list`는 내지 않는다). 입력에 기기 id가 없어 부른 기기 자기 행만 고친다. `token: null`은 push를 끈 것이라 token만 지우고 설정은 둔다. 앱이 앞에 있는지와 열린 session은 `presence/report`로 알린다(앞뒤가 바뀔 때, session 화면이 열고 닫힐 때, 앞에 있는 동안 30초마다). 누구에게 언제 무엇을 보낼지는 core의 주의가 정한다(`attention.md`).
  - core 쪽. 기기의 마지막 연결이 닫히거나 기기가 끊기면 core가 그 기기의 presence를 잊는다. 죽은 token은 core가 `devices/clear_push`로 거둔다. push는 remote가 켜질 때 푸는 컴퓨터의 key에 기대므로 remote를 켠 적이 없거나 꺼져 있는 core는 push를 보내지 않는다(끄면 같은 core 실행 안에서 바로 멈춘다). `remote.push`가 비어 있어도 나가지 않는다.
  - 폰 앱 쪽. Paired가 알림을 한 번만 묻는다(`Turn on notifications`와 `Not now`. 다른 컴퓨터가 목록에 더해져도 다시 묻지 않는다). Settings › Notifications에서 나중에 켜고 스위치를 고른다: 일곱(`An agent needs me`, `Long work finishes`, `An app update waits`, `A job was missed`, `My apps notify me`, `Stay quiet while I am at the computer`, `Show session names`). 허락을 거절했으면 그 화면에 시스템 설정을 여는 단추가 선다. 알림 channel은 `needs-you`(high), `finished`, `apps` 셋이고 앱이 시작할 때 만든다(Android 13은 허락과 token을 부르기 전에 있어야 한다). 앱이 앞에 있으면 알림 배너를 그리지 않는다(core도 앞에 있는 폰에는 보내지 않는다).
  - 알림을 누르면. 알림의 `data`는 위젯과 홈 화면 아이콘이 쓰는 open target 해석 하나를 지난다(`phone-home-screen.md`). `data.host`가 가리키는 컴퓨터를 고르고 `session`(그 대화), `app`(그 앱의 폰 화면), `inbox`(Inbox)를 연다. 터미널 TUI session(`term:<탭>`)은 대화가 없어 Inbox로 간다(GUI 탭의 승인 대기는 알림이 아직 없다, 이슈 `push-misses-gui-tab-approvals`). 목록에 없는 session은 8초 기다린 뒤 Inbox를 연다. 이 폰의 목록에 없는 컴퓨터나 모양이 틀린 `data`는 아무것도 열지 않는다. 앱이 죽어 있다가 알림으로 열려도 같은 곳이 열린다.
  - 개발. EAS project id가 없는 build는 push token을 받을 수 없어 알림이 "쓸 수 없다"로 선다. dev build만 처음 쓸 때 만든 가짜 token을 `devices/set_push`로 보내고 개발 core의 fake push server가 그것으로 온 글을 받는다. 폰에 알림을 그리는 것은 Expo의 일이라 fake가 못 하고, Settings › Notifications 맨 아래(dev build만)의 `Send a test notification`이 같은 `data`의 local 알림을 띄워 누르기를 본다.
- **첨부.** 대화의 Add sheet는 Photos(Android 시스템 사진 선택기라 권한이 없다)와 Camera(권한을 묻고, 거절하면 이유와 설정으로 가는 길을 보인다)를 준다. 사진은 JPEG로 다시 인코딩해 보낸다. PNG, JPEG, GIF, WebP만이고 한 장 5 MiB까지다. 올릴 때는 desktop composer가 붙여 넣은 그림을 올리는 길 그대로 `message-images/upload`(바이트는 `call` 안 base64)를 부르고 받은 blob을 message의 image block에 싣는다. 사진만 있는 message도 보낼 수 있다. 컴퓨터가 offline이면 첨부를 잠근다. desktop은 컴퓨터의 path로 아무 file이나 붙이지만 폰의 file에는 컴퓨터의 path가 없어 그림만이다.
- **bytes.** frame은 JSON뿐이다. upload route는 `{input, base64}`로 보내고 file route의 답은 `{content_type, base64}`로 받는다. 한 file 8 MiB, frame 16 MiB 안이다.
- **폰 앱 package.** `mobile`은 root npm workspace 밖의 Expo project(SDK 58, dev build)다. Metro가 protocol, design(kit, i18n), desktop의 순수 logic file을 source로 읽고, 그 안의 bare import(zod, `@noble/*`)는 폰 앱의 `node_modules`에서 푼다. 연결(handshake, frame)은 좁은 입구 `@lophn/protocol/remote/client`로 쓴다. 명령과 개발 build는 그 package의 README에 있다.
- **연결 조각의 자리.** 연결(주소 경주, 재연결, dial, 자격 전 기계 id 확인), 명단으로 채우는 컴퓨터 목록 store, 초대장 글 읽기와 `join`, `roster/leave`는 폰과 core(다른 컴퓨터로 가는 link)가 같이 쓰는 package `remote-client`(`@lophn/remote-client`)에 있다. protocol과 base만 import하고 `node:`도 React Native도 import하지 않아 Metro와 core가 같은 source를 읽는다. key와 목록의 저장은 쓰는 쪽이 넣는다. 폰만의 것(컴퓨터의 `request`에 답하기, 보안 저장소, 화면 칸, sample 컴퓨터)은 폰에 남는다. 한 연결이 한 번에 여는 call은 8개까지이고 나머지는 앞의 답을 기다린다. 120초 안에 답이 없는 call은 `unavailable`로 끝내 자리를 비운다(가장 느린 route인 coding session 열기의 55초와 느린 폰 연결로 받는 큰 frame보다 길다). 답 하나를 잃어도 자리 하나를 영영 쥐지 않는다. core 쪽 read 줄은 caller마다 8개이고 넘는 read는 거절하지 않고 read 기한(2초)까지 잡아 두었다가 자리가 나면 줄에 넣는다(전체 64개 상한은 그대로다).
- **개발.** `npm run dev:remote`는 개발 core(`.dev-data`)의 remote를 켜고(port 47432, 사람의 lophn과 겹치지 않게, relay는 비운다) 폰 초대장 글(QR에 싣는 JSON)을 찍는다. 폰이나 emulator의 "Paste the invite instead" 칸에 붙여 넣는다. 초대장은 30분, 한 번이다. 컴퓨터 둘은 `npm run dev -- --viewer`의 두 번째 desktop에서 [Join with an invite]로 잇는다.

### desktop에서 다른 기계 보기

desktop 앱이 명단의 다른 컴퓨터의 session, 대화, 승인과 질문, Inbox, job 켜고 끄기를 그 기계의 창에서 본다. 받는 기계는 이 컴퓨터를 `device:<이 컴퓨터의 id>`인 기기로 보므로 권한은 폰과 같다. 다른 기계의 관리(설정, secret, provider)는 없고 각 기계의 처음 설정은 그 기계의 화면에서 한다. 명단의 관리(초대, 빼기, 이름, 터미널 입력)는 어느 컴퓨터에서나 이 컴퓨터 창의 Settings › Remote에서 한다(아래 "내 기기 명단").

```
이 컴퓨터의 창 ─┐
                ├─ shell main ── 이 컴퓨터의 core (사람 자격)
<기계> 창 ──────┘  (보낸 창으로     │ machines/call · watch · list
                   기계를 고른다)   └─ link ── <기계>의 core (기기 자격 device:<이 컴퓨터의 id>)
```

- **연결은 core가 든다.** renderer CSP는 `connect-src 'self'`라 창이 다른 기계에 직접 붙지 못하고, shell main도 다른 기계에 붙지 않는다(붙는 key와 code가 없다). 이 컴퓨터의 core가 명단의 다른 컴퓨터마다 link 하나를 든다(아래 "컴퓨터끼리의 연결"). shell main은 사람 자격으로 `machines/list`를 읽고(`StateChanged{remote_devices}`마다 다시) 다른 기계의 창에 `machines/call`·`machines/watch`로 지은 core 통로를 묶는다. 그 기계의 Gateway frame은 이 컴퓨터의 Gateway에 `MachineFrameReceived`로 와서 그 기계의 창에만 간다(`ready`면 창이 snapshot부터 다시 읽는다). shell main은 기계마다 마지막 watch를 들고 이 컴퓨터의 Gateway에 다시 붙을 때 다시 건다. 꺼진 기계는 core의 link가 backoff로 다시 붙으며 어느 창도 막지 않는다. 기계 사이의 session 목록 합치기는 없다.
- **기계 목록.** 목록은 명단의 다른 컴퓨터마다 이름(명단의 이름 하나), 상태(connecting, connected, offline, update와 누가 올릴지), 길(direct, relay), 마지막으로 본 때다. main이 통째로 밀고 renderer가 한 번에 바꾼다(`MachineList`). shell data에 남는 것은 시작 기계 `viewer/start.json`(`{machine, start, last, last_name}`, 0600, temp에 쓰고 rename)과 창 자리 `viewer/windows.json`(기계 id로 둔 자리와 크기)뿐이다. `machine`은 쓴 기계의 id이고 이 기계와 다르면(복사된 data root) 그 file을 쓰지 않는다. `last_name`은 목록이 오기 전에 마지막 기계의 창 제목이다. ledger 밖이라 recovery 복구본, 내보내기, 폴더 어디에도 실리지 않는다.
- **기계마다 창 하나.** 한 창은 사는 동안 한 기계만 본다. 기계를 고르면 그 기계의 창을 열거나 앞으로 가져온다. renderer가 창마다 core 하나를 module 수준에서 잡고 source를 그 위에 짓기 때문이다. 다른 기계의 창은 이 컴퓨터 창과 같은 desktop 주소를 여는데 따로 preload(core, 기계 목록, overlay, 창 단추, 단축키, 외부 링크만)를 받는다. 기계는 주소가 아니라 main이 창을 열 때 묶은 표가 정한다: 그 창이 보낸 `shell:core-call|core-watch|core-state-get`은 이 컴퓨터 core의 `machines/*`를 거쳐 그 기계로만 가고 이 컴퓨터의 core route에 닿지 않는다. 그 밖의 IPC는 모든 handler 앞의 guard 한 곳이 허락 목록(`shell:machines-list|open|this-window|visible|this-read|clone-here`, 창 단추, 외부 링크)만 넘기고 나머지를 `forbidden`으로 답한다. `this-read`와 `clone-here`는 이 컴퓨터의 core에 닿는 좁은 길이다: 이 컴퓨터의 project 목록·agent 목록·session 목록 읽기(`project.list`, `ListAgents`, `ListSessions`만)와 그 기계의 project를 이 컴퓨터에 clone하기(`project.clone`). 그 기계의 project 가운데 이 컴퓨터에도 있는 것을 보이는 데 쓴다(`project-identity.md`의 "다른 기계의 창"). renderer는 기계를 주장하지 못한다. OS 창 제목은 "<이름> — lophn"이다.
- **이 컴퓨터의 일은 이 컴퓨터의 창으로.** 다른 기계의 창은 이 컴퓨터의 창 목록에 들지 않아 이 컴퓨터의 알림, presence, surface, 전역 키, agent가 여는 창이 그 창을 보지 않는다. 이 컴퓨터의 알림을 누르면 이 컴퓨터의 창이 열리거나 앞으로 온다(다른 기계의 창만 열려 있어도). 다른 기계의 창에서 이 컴퓨터의 session을 누르면(`shell:machines-open`에 이 컴퓨터의 id와 session) 같은 길로 이 컴퓨터의 창이 그 session을 연다. 다른 기계의 창이 앞에 있거나 보이는 session이 바뀌면 shell main이 `machines/call`로 그 기계에 `presence/report`를 보낸다(`attention.md`).
- **다른 기계의 창의 화면.** renderer는 시작 때 이 창의 기계를 한 번 묻고(`thisWindow()`. 이 컴퓨터 창은 null), 다른 기계면 이 컴퓨터의 shell host가 필요하거나 기기가 부를 수 없는 source(Settings, provider, 빠른 실행의 core 쓰기, App details 관리, 편집기, 터미널, 로그인)를 짓지 않고 기계 context로 단추를 감춘다. 끄는 것: 터미널과 coding agent의 터미널·GUI, 편집기·file tree·file 열기, 지침·memory 편집, secret 창, browser·artifact 탭(그 기계의 browser page는 아래 Pages 탭으로 본다), agent가 여는 탭, 앱 화면·앱 panel·앱 창, detached 탭, Settings, provider 설정, agent·앱·project·job 만들기와 고치기, extension, thread bookmark, 그 기계의 OS 알림, session 지우기, 권한 mode. 탭 kind가 `thisComputerOnly`를 선언하고, 그런 탭이 저장된 링크, 검색 결과, 대화 안 file 링크로 열리면 본문 대신 "This opens only on <이름>"이 선다. Settings 자리는 "<이름>'s settings are changed on <이름>"과 [Open this computer]뿐이다. layout(탭, desk)은 창이 사는 동안 메모리에만 있어 다시 열면 Home이다(`workspace-layout.md`).
- **그 기계의 browser page.** 다른 기계의 창의 새 탭 menu에만 Pages가 있다. 그 기계의 core가 아는 browser 탭의 목록 탭(key `pages`)이 열리고, 줄을 고르면 그 page의 탭(key `page-view:<탭 id>`)이 열린다(`browser-tab.md` "멀리서 보기"). 탭은 보이는 동안 lease를 잡아 그림을 받고, 이 컴퓨터의 터미널 입력 허락이 그 명단 항목에 켜져 있으면 click·끌기·wheel, key, 쳐진 글(IME 포함)과 붙여 넣은 글, 주소·뒤로·다시 읽기, [Take control]·[Hand back]이 그 page에 간다. 꺼져 있으면 보기만 하고 허락을 켜는 곳을 한 줄로 보인다. 다른 기계의 창의 layout처럼 메모리에만 있다.
- **다른 기계의 앱 화면은 띄우지 않는다.** 앱 panel, 앱 창, 앱 view는 다른 기계의 창에 없다. 미룬 것이 아니라 하지 않는 것이다: 다른 기계에서 필요한 것은 session, 대화, 승인이고, 앱은 그 기계나 폰에서 쓰거나 sync 앱이면 이 기계의 사본을 쓴다.
- **기계 고르기와 gate.** title bar 왼쪽의 기계 고르기가 이 컴퓨터를 맨 위에, 명단의 다른 컴퓨터를 명단의 이름, 상태, 길이나 마지막으로 본 때와 함께 보인다. 다른 컴퓨터가 없으면 그리지 않아 한 대만 쓰는 사람의 화면은 그대로다. 한 번도 붙지 않은 창은 창 전체 gate("Connecting to <이름>…", "<이름> is offline"과 마지막으로 본 때, [Try again]·[This computer])이고, 한 번 붙은 뒤의 끊김은 마지막 화면 위의 한 줄이며 다시 붙으면 사라진다. 판이 어긋나면 gate가 누가 올릴지 말한다. 창의 기계가 명단에 없으면(빠졌거나, 이 컴퓨터가 빠져 새 명단으로 섰다) 어느 화면이든 removed gate("<이름> is not in your devices")다.
- **시작 기계.** 창이 하나도 없을 때 여는 길(시작, tray Open, 두 번째 실행)은 시작 기계를 연다: 고른 기계, 아니면 마지막에 쓴 기계(연결된 채 focus를 받은 마지막 창의 기계), 그것이 목록에 없으면 이 컴퓨터다. 시작 기계는 core를 기다리지 않고 `viewer/start.json`에서 고르고, 꺼져 있어도 그 창을 바로 연다(offline gate). 사람이 고른 기계를 명단에서 빼면 시작은 마지막에 쓴 기계로 돌아가고, 그 기계가 마지막에 쓴 기계였으면 이 컴퓨터가 마지막이 된다. 고르기는 Settings › Remote의 My devices 아래에 있다(다른 컴퓨터가 있을 때).
- **읽음은 host에.** 다 본 session의 표시(`unseen/list|dismiss`)는 기기 route다. 보는 것이 읽음을 만들고 읽음은 그 기계에 있어 어느 기기에서 봐도 같이 꺼진다. 폰도 같이 받는다.
- **두 기기가 한 session에 쓸 때.** 보내기는 그 화면이 아는 마지막 사람 메시지(`seen`)를 싣고, 그 뒤에 다른 사람 메시지가 있으면 core가 같은 transaction에서 거절한다(`acp.md`). 대화의 첫 snapshot을 받기 전에는 `seen`을 싣지 않아 이 검사를 하지 않는다. 꺼진 기계에 맡겨 두는 queue는 없다: 연결이 없으면 보내기는 `unavailable`이고 쓴 글은 입력칸에 남는다.

### 내 기기 명단

한 사람의 폰과 컴퓨터는 서명한 명단 하나를 같이 든다. 새 기기는 이미 든 컴퓨터 아무거나 하나의 초대장으로 들어오고, 명단이 나머지에 퍼져 모든 기계와 이어진다. 빼기도 어느 컴퓨터에서나 하고 소식이 닿는 대로 모든 기계가 끊는다. 컴퓨터끼리는 core가 명단으로 서로 붙는다. 계약(statement schema, 믿음 계산, frame, route)은 protocol의 remote 폴더에 있다.

#### 문제

- 믿음을 쌍마다, 방향마다 따로 두면 기기 id가 그 컴퓨터 안에서만 뜻이 있고, 폰 하나와 컴퓨터 셋이 서로 다 닿으려면 pairing이 아홉 번까지 든다.
- 빼기가 그 표를 가진 컴퓨터 하나에만 걸리면 잃은 폰을 컴퓨터마다 따로 빼야 한다.
- 컴퓨터는 늘 같이 켜져 있지 않다(dual boot, 집과 직장). 살아 있는 연결로만 들이고 퍼뜨리면 같이 켜질 수 없는 두 컴퓨터는 영영 못 잇는다.
- 화면 없는 기계도 같은 정체로 명단에 들고 다른 컴퓨터에 붙어야 한다. 붙는 쪽 key를 desktop shell이 들면 화면 없는 기계는 붙지 못하고, 컴퓨터 하나에 정체가 둘이 된다.
- 본보기가 없다. 조사한 제품은 쌍마다 잇기, 계정, 가운데 기계, 공유 비밀 하나 가운데 하나다.

#### 모델

명단은 서명한 statement의 집합이다. 폰과 폴더처럼 믿지 않는 곳을 거쳐도 서명이 가린다.

| statement | body | 서명하는 key |
|---|---|---|
| 항목 `{body, by, signature}` | `{type: entry, id, kind: computer\|phone, key, signing_key, machine, name, os, terminal_input, rev, invite}` | `by`(믿는 컴퓨터의 id)의 서명 key |
| 빼기 `{body, by, signature}` | `{type: removal, id, key, signing_key, at}` | 같다 |
| 초대장 `{body, signature}` | `{type: invite, key, by, kind, terminal_input, expires_at}` | 초대한 컴퓨터(`by`)의 서명 key. `key`는 한 번 쓸 Ed25519 key |
| 초대 서명 statement `{body, invite, signature}` | 항목 body | 초대장의 `key`(새 기기가 초대장의 비밀로 스스로 서명) |

- 기기를 가리키는 것은 `key`(Noise static key. 컴퓨터는 host key, 폰은 기기 key)다. `id`는 명단 전체에서 하나인 이름표이고 principal `device:<id>`도 이 값이다. 컴퓨터 항목만 `signing_key`(Ed25519)와 `machine`을 갖는다. 폰은 서명 key가 없어 누구도 들이지 못한다. `invite`는 그 기기가 들어온 초대 key다(컴퓨터의 자기 항목과 옮긴 항목은 null).
- 컴퓨터를 빼는 빼기는 `signing_key`에 그 서명 key를 싣는다(폰은 null). host key만 빼면 같은 서명 key로 새 host key의 항목을 만들어 돌아온다.
- 초대장의 `kind`는 사람이 고른 들일 기기의 종류다. 폰 초대장이 새어도 서명자(컴퓨터)는 들지 못한다.
- 서명하는 bytes는 `utf8("lophn-roster/1" + "\n" + canonical JSON(body))`다. body의 `type`이 달라 항목·빼기·초대장의 서명이 서로 바꿔 쓰이지 않는다.
- 주소(reach `{device, addresses, port, relay}`)는 서명하지 않고 snapshot에 따로 싣는다. 틀린 주소는 Noise가 key로 막아 못 닿을 뿐이다.
- 합치기는 합집합이다. canonical 글이 같은 statement는 하나이고 결과 배열은 canonical 글 순서다.

**믿음 계산(view).** 입력은 statement 집합과 root다. root는 믿음이 시작하는 컴퓨터의 **서명 key**다. host key(X25519)는 서명하지 못해 host key로 잡으면 누구나 "그 host key, 내 서명 key"인 항목을 스스로 서명해 root 행세를 한다. 컴퓨터의 root는 자기 서명 key 하나다. 폰의 root는 저장한 컴퓨터들의 서명 key이고, 초대장의 `issuer`, `join` 답의 `computer`, 명단에서 믿은 컴퓨터 항목에서 배운다.

1. root는 statement 안의 자기 서명 항목(`by`가 그 항목의 id이고 `signing_key`가 root이며 그 key로 서명이 맞는 것)으로 믿는다. 이 항목의 host key(root의 자기 key)에 다른 서명 key를 단 항목은 쓰지 않는다.
2. 믿는 컴퓨터가 서명한 statement(`by`의 id에 묶인 서명 key로 맞는 것)를 믿고, computer 항목이면 그 컴퓨터도 서명자가 된다. 더 늘지 않을 때까지 되풀이한다(T0).
3. T0가 믿는 빼기를 모은다(K0). 어느 빼기가 효력이 있는지는 공격 그래프의 grounded labelling(최소 고정점)으로 정한다. 마디는 K0의 빼기 statement(body, 서명자)이고, 빼기 r의 대상(key나 서명 key로 맞춘다)이 빼기 s의 서명자이면 r이 s를 공격한다. 모두 정해지지 않음에서 시작해 더 바뀌지 않을 때까지, 공격하는 빼기가 모두 OUT이면 IN(공격이 없으면 IN), 공격하는 빼기 하나라도 IN이면 OUT으로 정한다. 컴퓨터의 view에서는 그 컴퓨터 자신이 서명한 빼기가 처음부터 IN이다(자기 판단을 믿는다). 폰의 view에는 이것이 없다: 폰의 root(저장한 컴퓨터들) 가운데 도둑이 있으면 그 빼기가 처음부터 IN이 되어 폰이 도둑만 믿게 되므로, 폰은 grounded labelling만 따른다. IN인 빼기의 대상(빼기 body의 `key`와 `signing_key`)은 빠진다. body의 `id`는 서명자가 아무 값이나 달 수 있어 보지 않는다. 끝까지 정해지지 않은 빼기(시각 없이는 깰 수 없는 서로 물고 도는 빼기)의 대상도 빠지되(fail-closed), 컴퓨터의 view에서 그 컴퓨터 자신은 정해지지 않은 빼기로 빠지지 않는다(폰의 root는 빠진다: 폰은 엇갈리지 않은 컴퓨터만 믿는다). 대상을 빼는 빼기를 K라 한다.
4. K의 key와 서명 key를 뺀 채 1~2를 다시 한다. 빠진 것은 항목으로도, 서명자로도, root로도, 어느 항목의 `signing_key`로도 쓰이지 않는다.
5. 믿는 항목끼리 부딪는 key는 둘 다 뺀다(conflict). 한 host key에 서명 key 둘, 한 서명 key에 host key 둘(`signing_key`), 한 key의 kind·machine이 다름(`shape`), 다른 key가 같은 id(`id`), 한 초대 key로 다른 key 둘(`invite`. 지금 믿는 항목끼리만 센다: 빠진 컴퓨터가 남의 초대 key를 단 항목이 그 기기를 계속 빼지 못한다). root의 자기 key만은 빼지 않고 상대만 뺀다. 빼면 믿음이 줄므로 더 빠지는 것이 없을 때까지 4를 다시 한다.
6. key 하나에 항목이 여럿이면 rev가 큰 것, 같으면 `terminal_input`이 false인 것(허락을 거둔 쪽), 같으면 body canonical 글이 작은 것이 이긴다. 같은 key에 id가 여럿이면(컴퓨터마다 따로 만든 `dev_`) 가장 작은 id로 접는다.

- 초대 서명 statement는 믿음 계산에 들지 않는다. 닿은 컴퓨터가 확인하고 자기 key로 다시 서명한 항목이 퍼진다.
- 결과는 `devices`(이긴 body, 그 body 그대로에 서명한 컴퓨터, `pending`), `removed`(K. 뺀 key마다 body 하나, IN인 빼기면 `settled: true`이고 정해지지 않은 고리의 빼기는 false, `entry`는 그 key의 항목 가운데 지금 믿는 서명자가 서명한 것의 이긴 항목(id는 그 가운데 가장 작은 id), 그런 것이 없으면 그 기기가 자기 서명 key로 스스로 서명한 것, 그것도 없으면 null. 빠진 기기의 id와 이름은 여기서만 얻는다: 빠진 서명자가 다른 key의 항목에 단 id와 이름은 쓰지 않는다), `folded`, `conflicts`, `invites`, `keep`이다.
- **쓰인 초대**(`invites`)는 빼기 전 믿음으로 센다: T0 항목(어느 rev든) 가운데 지금 믿는 컴퓨터가 서명한 것의 (`invite`, key)와, 지금 믿는 컴퓨터가 낸 초대장으로 초대 key의 서명이 맞는 초대 서명 statement(초대 key마다 canonical 글이 앞선 하나)의 (초대 key, key)다. 그 기기가 빠졌는지 보지 않는다: 쓰인 초대장은 그것으로 든 기기를 빼도 쓰인 것이다.
- **pending.** 초대장으로 들었는데 다른 컴퓨터가 아직 받아들이지 않은 기기다: 초대 서명 statement뿐이거나, 믿는 항목이 모두 그 기기 자신의 서명뿐이고 초대로 든 표(이긴 항목의 `invite`나 남겨 둔 초대 서명 statement)가 있다(초대한 컴퓨터에 못 닿고 든 컴퓨터). 초대 없이 선 항목(혼자인 컴퓨터의 자기 항목, 옮긴 폰)은 기다리는 것이 없어 pending이 아니다. 판정은 protocol의 순수 함수 하나이고 `roster/list`가 기기마다 싣는다.
- **keep**은 저장하고 보낼 것이다. view는 keep에서 다시 계산한 것이고(keep이 더 줄지 않을 때까지 되풀이한다) keep만으로 다시 계산해도 같은 view다.
  - T0가 믿는 빼기 가운데 같은 서명자·같은 대상(key, 서명 key)마다 canonical 글이 앞선 하나(효력과 `removed`가 서명자와 대상으로만 정해진다). 지금 믿는 서명자의 것은 모두(OUT인 것도. 공격 그래프가 그것으로 정해진다), 지금 믿지 않는 서명자(빠졌거나 엇갈린 컴퓨터)의 것은 서명자와 대상이 둘 다 지금 믿는 컴퓨터가 서명한 항목에 든 key일 때만 상한 밖이다. 엇갈림을 정하는 데 들고, 수가 믿는 쪽이 보증한 기기 수로 묶인다.
  - T0가 믿는 항목 가운데 컴퓨터 항목 모두(빠진 컴퓨터도. 그 컴퓨터가 서명한 빼기를 다시 맞춰 보는 데 든다), 남은 기기·충돌한 key·빠진 key의 항목(빠진 기기의 `entry`와 쓰인 초대의 기록이다). 지금 믿지 않는 서명자가 서명한 것은 상한 안이다. 단 같은 서명자가 같은 key에 같은 id·초대·모양으로 더 앞선 항목에 서명했으면 뒤진 항목은 버린다. 그 서명자의 앞선 항목이 같은 믿음, 같은 id, 같은 쓰인 초대를 남기기 때문이다. 그래서 사슬 가운데 statement와 root의 자기 서명 항목이 남는다.
  - 초대 key의 서명이 맞는 초대 서명 statement. 지금 믿는 컴퓨터가 낸 초대장이면 초대 key마다 하나가 상한 밖이고 나머지는 상한 안이다. 기기가 든 뒤에도, 빠진 뒤에도 남긴다(쓰인 초대의 기록이고, 그 기기를 모르는 컴퓨터로 나른다).
  - 상한 안(capped): 지금 믿지 않는 서명자·초대장 서명자의 것(위에서 상한 밖으로 둔 빼기 말고)과 서명자를 아직 모르는 것(서명자도 대상도 빠지지 않은 것). 나중에 믿게 될 수 있어 남기되 `ROSTER_UNKNOWN_MAX`(512)개까지만 canonical 글 순서로 앞선 것을 남긴다. 받은 순서와 상관없이 모든 기계가 같은 것을 남기고, 밀려난 정직한 statement는 그 출처가 link나 폰으로 다시 보낸다. 지금 믿는 컴퓨터가 쓴 것은 이 셈에 들지 않고 밀려나지 않는다. 그래서 지금 믿지 않는 누구(붙은 기기, 빠진 컴퓨터, 새어 나간 초대장을 가진 쪽)도 저장소를 `ROSTER_STATEMENTS_MAX`(4096)까지 채우지 못하고, 믿는 컴퓨터의 빼기는 늘 저장된다(믿는 컴퓨터들이 스스로 그만큼 쓰지 않는 한).
  - 버리는 것: T0가 믿지 않은 statement 가운데 서명자 id가 T0의 서명자나 빠진 기기의 id인 것(위조나 빠진 기기를 사칭한 것)과 대상이 빠진 항목, 같은 서명자·같은 대상의 뒤진 빼기, 같은 무리의 뒤진 항목, 서명이 맞지 않는 초대 서명 statement. T0가 믿은 빠진 서명자의 statement는 버리지 않고 위 상한 안에 든다.
- 계산은 시각을 보지 않는다. 초대 서명 statement는 저장하는 쪽이 자기 시계로 거른다: 수명이 지났거나 지금부터 7일보다 먼 수명을 단 것을 버린다.

**컴퓨터의 key.** 컴퓨터의 정체는 core의 key 둘이다. host key(Noise static key, `remote/host-key.json`)는 받는 쪽(listener, relay)과 붙는 쪽(link) 둘 다에 쓰고, 서명 key(Ed25519, `remote/signing-key.json`)는 명단에 서명한다. 둘 다 0600이고 만든 기계의 id를 찍는다(`machine.md`). remote를 처음 켤 때 같이 만들고 같이 지운다: 표지가 이 기계와 다르거나 하나만 읽히면 둘 다 지우고 명단을 버린다. 서명은 core의 main thread가 하고 저장하는 쪽에는 서명한 statement만 간다.

**저장.** ledger 표 `roster_statements`(statement의 canonical 글 한 행)와 `roster_reach`(기기마다 주소 한 행)다. core 안 machine 자격 `roster/store`가 keep과 주소를 통째로 쓰고, 같은 write에서 접힌 id로 기기 행과 앱 sync log의 기기 칸을 고치며, view의 정해진 빼기가 뺀 key와 서명한 항목이 남지 않은 key의 기기 행(빠진 폰)과 그 push token을 지운다(keep이 빠진 기기의 항목도 남겨 statement만으로는 모른다. 엇갈림으로 빠진 폰의 행은 남아 풀리면 기준과 push token 그대로 돌아온다). view의 기기 이름을 그 행의 `alias`(이 컴퓨터가 보이는 이름)에 두어 기기 표 읽기와 `apps/phone_target`이 명단의 이름을 낸다. `shell.devices` 항목은 commit 뒤 main thread가 따라 고친다(이름, 접힌 id, 빠진 폰).

**컴퓨터가 명단을 고치는 순서.** core의 main thread 하나가 한다.

```
저장한 것 + 받은 것 ─merge─▶ view ─▶ 아직 이 컴퓨터가 서명하지 않은 devices의 body와 settled인 removed의 body에 서명
   ─▶ 서명을 더해 다시 view ─▶ keep·주소·folds를 저장(roster/store) ─▶ 붙은 연결마다 민다
```

- 컴퓨터는 view의 devices와 IN인(settled) 빼기에만 같이 서명한다(co-sign). 충돌로 뺀 항목, OUT이거나 정해지지 않은 빼기에는 서명하지 않는다: 정해지지 않은 빼기에 아무도 공격하지 않는 서명자(구경꾼)의 서명이 붙으면 그 statement가 IN이 되어 고리 밖으로 퍼진다. 컴퓨터 둘이 이어지면 서로의 항목에 서명하므로 두 명단이 합쳐진다.
- 접힌 id는 접힌 body(작은 id, 같은 rev)에 서명해 굳힌다. 같은 rev에서 body canonical 글은 id가 맨 앞이라 작은 id의 body가 이긴다. 접은 컴퓨터는 같은 write에서 큰 id를 쓰던 곳(앱 sync log의 기기)을 고치고, commit 뒤 `shell.devices[].device`를 고친다. folded는 큰 id의 항목이 keep에 남는 동안 저장마다 나오고, 저장은 기기 행이 이미 옮겨졌어도 접힌 쌍마다 `shell.devices`를 다시 고친다(바뀌지 않으면 쓰지 않는다). 그래서 commit과 설정 쓰기 사이에 죽어도 다음 저장이 고치고, 고치기는 다시 해도 같다.
- 연결과 자격을 거둘 때는 id만이 아니라 key로도 찾는다. 같은 id를 단 다른 key가 충돌로 빠져도 남은 쪽의 자격을 거두지 않고, 빠진 key의 연결은 id가 무엇이든 닫는다.

**옮기기.** 이 판 전의 data는 이렇게 이어진다.

- 기기 표의 phone 행은 그 컴퓨터가 서명한 항목이 된다(id, key, 이름, 허락 그대로, rev 1, 초대 없음). SQL은 서명하지 못하므로 schema step `remote.roster`는 표 둘을 만들고 kind desktop 행만 지운다. core는 key가 있는 기동과 remote를 켤 때 listener와 relay를 열기 전에 자기 항목과 함께 그 행들에 서명한다.
- 이 판 전의 host key에는 data step `remote.signing-key`가 짝 서명 key를 더한다. host key는 바뀌지 않는다.
- 다른 desktop에 붙던 key는 shell의 것이라 없어진다. data step `shell.viewer.roster`가 `shell/viewer/key.json`과 `machines.json`을 지우고 시작 기계(`start`, `last`와 그 기계의 이름)를 `viewer/start.json`으로 옮긴다. 표지가 이 기계와 다른 file은 옮기지 않고 지운다. 창 자리 `viewer/windows.json`은 그대로다. 컴퓨터끼리는 초대로 한 번 다시 잇는다.

**옮긴 폰.** 이 판 전에 pairing한 폰은 컴퓨터의 host key만 저장했다. 판 3으로 처음 붙을 때 `join`의 답 `computer.signing_key`를 받는다. 그 답은 저장한 host key로 확인한 Noise 연결에서 온 것이라, 폰은 그 컴퓨터의 서명 key를 root로 저장하고 답의 명단에 든 그 컴퓨터의 항목(host key와 서명 key가 같아야 한다)을 본다. 컴퓨터 쪽은 옮기는 step이 기기 표의 줄마다 그 컴퓨터가 서명한 항목을 만들어 두므로(id, key, 허락 그대로) 폰은 다시 pairing하지 않는다. 같은 폰을 여러 컴퓨터에 pairing했으면 컴퓨터마다 따로 배우고, 명단이 합쳐지면 id가 접힌다.

**들이기.**

- 든 컴퓨터가 초대장을 낸다(`roster/invite {kind, terminal_input, lifetime}`): 한 번 쓸 Ed25519 key를 만들어 초대장 body에 서명하고, 초대장, 그 비밀, 자기 서명 항목(`issuer`), 자기 주소를 글 하나(QR, CLI)로 보인다. 수명은 고른다: 기본 30분, 새 기기가 이 컴퓨터와 같은 때 켜질 수 없으면 7일. 새 기기 화면은 그 초대장의 만료 시각을 보인다(수명은 받는 컴퓨터의 시계로 본다).
- 새 기기는 자기 항목을 초대장의 비밀로 서명한다. 새 기기면 새 id, 이미 명단에 있는 폰이 다른 컴퓨터에 처음 붙으면 그 id다.
- 붙는 쪽의 첫 frame은 늘 `join {statements}`다. core는 그 key가 믿는 명단에 있으면 붙이고, 없으면 내민 statement를 본다: 믿는 컴퓨터가 서명한 그 key의 항목이면 같이 서명해 붙이고, 초대 서명 statement면 아래 확인을 하고 맞으면 자기 key로 서명해 붙인다. 빠진 key면 거절하고 그 빼기를 `details.removal`에 싣는다. 답은 `{device, computer: {id, signing_key}, roster}`다.
- 아직 누구인지 모르는 쪽이 저장소를 채우지 못하게 한다. 붙기 전 연결의 frame은 16 KiB, statement는 8개까지이고, statement는 모두 그 연결의 Noise key에 대한 것이어야 한다. 붙기 전 연결이 낸 초대 서명 statement는 확인이 맞을 때만 저장한다. 수명이 지났거나 7일보다 먼 것은 저장하지 않는다.
- 초대 서명 statement의 확인은 statement가 검증하는 컴퓨터에 닿을 때 한 번이고, 그 컴퓨터의 지금 view로 본다(`join`으로 왔든 명단에 실려 왔든 같다).
  - 초대장 서명자가 view의 컴퓨터가 아님(아직 모름 포함), 초대장 서명이 틀림, 항목이 초대 key로 서명되지 않음, 항목의 `invite`·`kind`·`terminal_input`이 초대장과 다름, 수명이 지금부터 7일보다 멂 → `unauthorized`, reason `untrusted`. statement는 keep에 남아 서명자를 믿게 되면 다시 본다.
  - key, id, 서명 key 가운데 하나가 빠짐 → `unauthorized`, reason `removed`. 수명보다 먼저 본다: 돌아온 기기가 "새 초대장"이 아니라 "key를 버려라"를 알게 한다.
  - view가 그 id를 다른 key로 든다(접힌 id, 충돌한 key 포함) → `conflict`, reason `id_taken`. 그 key가 다른 모양(kind, 서명 key, machine)으로 있거나 충돌로 빠졌음, 또는 그 서명 key를 다른 host key가 씀 → `conflict`, reason `key_taken`.
  - 검증하는 컴퓨터의 지금이 `expires_at` 뒤 → `unauthorized`, reason `expired`.
  - 같은 초대로 다른 key가 이미 들었음(view의 `invites`) → `conflict`, reason `used`. 같은 key가 다시 내면 받는다(다시 붙는 것이다).
- 이 컴퓨터가 다른 컴퓨터의 초대장으로 든다(`roster/join {text}`): `issuer` 자기 서명과 초대장 서명을 보고 issuer 항목에 서명한다(사람이 글을 넣은 것이 믿음의 근거다). 저장은 초대한 컴퓨터에 붙어 본 뒤다: 닿아 받아들여지면 저장하고 받은 명단을 합치고, 못 닿으면 저장하고 초대 서명 statement를 든 채 `pending: true`로 끝나고, 초대한 컴퓨터가 거절하면(`used`, `expired`, `removed` …) 아무것도 저장하지 않는다(믿지 않을 issuer와 죽은 statement를 남기지 않는다. 이미 믿는 컴퓨터가 서명한 빼기만 받는다). 자기가 낸 초대장이면 `conflict`(`this_computer`)다.

**나르기.**

- 붙은 뒤 붙는 쪽은 `roster {roster}`로 든 명단 전부를 보내고(`join` 뒤와 든 명단이 바뀔 때) core는 자기 명단을 답한다. core는 명단이 바뀔 때마다 붙은 연결에 `roster`를 민다. 폰은 받은 것(아직 믿지 못하는 statement와 초대 서명 statement 포함)을 다음에 붙는 컴퓨터에 넘기는 운반자다. 컴퓨터끼리는 core가 명단의 다른 컴퓨터마다 연결 하나를 유지하며 같은 frame을 주고받는다.
- dual boot(A와 B가 같이 켜지지 않는다): A에서 긴 컴퓨터 초대장 → B에서 `roster/join`(A에 못 닿아 pending. B는 A의 항목에 서명했다) → 사람이 B의 폰 초대장으로 폰을 B에도 들인다(폰은 A의 명단에만 있어 B를 모르고 B는 폰을 모른다. 이 한 번이 없으면 폰이 B에 붙을 길이 없다. 폰의 id는 그대로다) → 폰이 B의 statement(B의 초대 서명 statement 포함. B의 keep에 남아 있다)를 A에 나르면 A가 7일 안에 확인해 B에 서명하고, 폰이 A의 명단을 B에 나른다. B의 pending은 A의 서명이 닿을 때 풀린다.

**빠진 기기가 돌아오기.** 자기 key가 `removed`에 있는 것을 자기 root로 확인한 기기는 든 명단과 자기 key를 버린다. 컴퓨터는 복사된 data root와 같은 길이다: key 둘을 먼저 지우고 `roster/forget_all`로 명단과 기기 행을 버린 뒤, remote가 켜져 있으면 새 key와 새 자기 항목(새 id)으로 다시 선다. `roster/list`의 `removed_at`이 그때를 싣고(core 메모리에만 있다) Settings › Remote가 다른 컴퓨터가 이 컴퓨터를 뺐다고 알린다. 폰은 모든 컴퓨터, 든 명단, 기기 key를 잊고 Welcome으로 돌아간다. 그 뒤 초대장으로 새 기기(새 id, 새 key)로 든다. 뺀 key, 서명 key, id는 다시 들지 못한다.

**이름과 허락.** 이름은 항목에 하나이고 어느 컴퓨터에서나 바꾼다(`roster/rename`이 서명한 새 rev). 기기마다 붙이는 별명은 컴퓨터에 없다. 컴퓨터의 이름은 기계 이름과 한 값이다(위 "이름", `machine.md`). 터미널 입력 허락(`roster/set_terminal_input`)도 항목의 칸이라 모든 기계에 같다. 부를 수 있는 route 목록은 kind와 상관없이 하나다. 폰은 `roster/leave`로 자기만 뺀다. 컴퓨터가 부르면(연결된 컴퓨터의 화면이 넘긴 call) `forbidden`이다: 컴퓨터는 사람이 다른 컴퓨터에서 빼기로만 나간다.

**컴퓨터끼리의 연결.**

- remote가 켜진 컴퓨터의 core는 명단의 다른 컴퓨터마다 link 하나를 든다. 붙는 engine은 폰과 같은 `@lophn/remote-client`(주소 경주, 재연결, 기계 id 확인)이고, 받는 쪽은 그 컴퓨터의 listener가 폰과 같이 맡는다: 이 컴퓨터는 거기서 `device:<이 컴퓨터의 id>`인 기기다. 컴퓨터 둘은 서로에게 따로 link를 들어 한쪽만 닿는 network에서도 닿는 쪽 link로 명단이 오간다. 주소는 명단의 주소(reach)에서 오고 그 컴퓨터 hello의 주소 후보로 고친다. 조용히 끊긴 socket(잠든 노트북, 바뀐 network)은 ping으로 알아채 다시 붙는다.
- link는 붙을 때 이 컴퓨터 key의 statement(아직 받아들여지지 않은 초대 서명 statement 먼저, 그다음 컴퓨터들이 서명한 항목)를 `join`으로 내밀고, 그 뒤 든 명단 전부를 `roster`로 주고받는다. `join` 답의 `computer.signing_key`가 명단 항목의 서명 key와 다르면 link를 닫고 log를 남긴다. 그 컴퓨터가 이 컴퓨터를 거절하면 link는 멈추고 명단이 바뀌면 다시 연다. 거절에 실린 빼기는 이 컴퓨터의 root로 확인하고 맞으면 명단과 key를 버린다.
- `roster/join`은 초대한 컴퓨터에 20초까지 붙어 본다(WebSocket 열기와 handshake 한도). 넘으면 못 닿은 것과 같이 저장하고 pending이다. 판이 어긋나면 기다려도 끝나지 않으므로 저장하지 않고 어느 쪽을 올릴지 알린다(`conflict`, `details.update`).
- 이 기계의 화면은 다른 기계를 core의 route로만 부른다. `machines/call {machine, resource, method, body}`(와 `machines/watch`)는 shell main이 받은 capability가 있어야 한다(사람의 CLI token으로는 부르지 못한다). core가 그 기계와의 link로 `call` frame을 넘기고 답과 오류(code, message, details)를 그대로 돌려준다. link가 없거나 거절된 link면 `unavailable`, 명단에 없는 기계면 `not_found`, 이 컴퓨터 자신이면 `invalid_input`이다(이 컴퓨터의 route를 바로 부른다). 같은 `machine`을 든 key가 둘이면 그 기계를 든 첫 key로 간다. 복제된 key와 같은 열린 것이다(`machine.md`): 충돌 묶음으로 막으면 `roster/forget_all` 뒤 같은 기계가 새 key로 다시 들 때 옛 key가 아직 믿는 채이면 다시 든 컴퓨터가 빠진다. `machines/watch {machine, conditions}`는 그 기계의 Gateway 조건을 통째로 바꾸고(link를 새로 열어도 다시 건다), 그 기계의 frame(ready, event, closed)은 이 컴퓨터의 bus에 `MachineFrameReceived`(subject `machine:<mch_>`)로 실린다. 이 event는 기기 event 목록에 없어 다른 기계의 내용이 폰에 그대로 가지 않는다. `machines/list`는 명단의 다른 컴퓨터마다 이름, link 상태(connecting, connected, offline, update와 누가 올릴지), 길, 마지막으로 본 때다.
- 넘기는 것은 사람의 화면이 부른 것뿐이다. agent와 앱이 다른 기계를 부르는 길은 아직 없다(roadmap `multi-device`의 `remote-use`).

**화면과 CLI.**

- desktop Settings › Remote. 맨 위 "This computer"는 이 컴퓨터의 이름(`machine/rename`)과, 복사된 data root로 새 기계가 되었거나 다른 컴퓨터가 이 컴퓨터를 뺐다는 알림이다. My devices는 명단의 기기마다 이름, kind와 OS, 이 컴퓨터 표시, 컴퓨터면 link 상태, 폰이면 마지막 연결과 기준, 초대한 컴퓨터에 아직 닿지 않았으면 "Waiting", 터미널 입력 스위치, [Rename], 폰의 [Make primary], [Remove](확인을 받는다. 이 컴퓨터 줄에는 없다)다. 정해지지 않은 빼기로 빠진 기기(`roster/list`의 `disputed`)는 "Disputed"와 한 줄 설명, [Remove]만 선다(아래 "엇갈릴 때"). Add a device의 [Invite a phone]·[Invite a computer]는 초대장을 바로 내고 QR, "Show as text", 끝나는 때, [New invite]를 보인다. 새 기기의 터미널 입력(기본 켬)과, 컴퓨터면 긴 수명("이 컴퓨터와 같은 때 켜질 수 없다")을 같은 자리에서 바꾸면 새 초대장을 낸다. 초대장이 보이는 동안 명단에 새 기기가 서면 초대장을 닫는다. [Join with an invite]는 다른 컴퓨터가 보인 글을 붙여 `roster/join`을 부르고 거절 이유(`expired`, `used`, `untrusted`, `removed`, `this_computer`, `id_taken`, `key_taken`, 판 어긋남, remote 꺼짐)나 pending을 말한다. remote가 꺼져 있으면 목록 대신 켜라는 한 줄이다.
- 폰. 초대장 읽기는 위 "들어오기"다. 컴퓨터 목록은 명단이 채운다: 저장한 컴퓨터들의 서명 key를 root로 본 view가 믿는 컴퓨터 가운데 명단에 주소와 기계 id가 있는 것이 목록에 들고, view의 정해진 빼기가 뺀 컴퓨터는 빠진다(엇갈린 컴퓨터는 남되 붙지 않는다). 그래서 한 컴퓨터에 들어오면 나머지 컴퓨터가 목록에 뜬다.
- CLI `lophn remote on | invite <phone|computer> [--no-terminal-input] [--long] | join '<초대장>' | devices | remove <기기>`. 화면 없는 기계를 사람의 터미널에서 명단에 넣고 다룬다. `invite`는 초대장 한 줄을 찍고, `join`은 거절 이유를 `details.reason`으로 말하며 pending을 알린다. lophn agent의 `lophn` tool에 없고 agent의 shell에서 부르면 route의 actor(user)에서 막힌다. 명단을 바꾸는 `invite`·`join`·`remove`는 lophn의 터미널 탭 안(`LOPHN_SESSION_ID`가 `term:`으로 시작)에서 core에 붙기 전에 `forbidden`으로 끝난다: 탭의 shell은 사람 token을 받아 거기서 도는 coding agent와 사람을 가릴 수 없다. 읽는 `devices`와 `on`은 된다. 화면 없는 기계는 SSH의 터미널에서 한다. agent가 env를 지우면 지나가는 실수 막기다.

#### 엇갈릴 때

- **합치는 순서.** 합치기는 canonical 글로 줄 세운 합집합이고 view는 입력을 먼저 그렇게 정리하므로 같은 집합이면 같은 결과다. keep은 같은 서명자가 더 앞선 같은 모양의 항목에 서명한 것만 버리므로 keep만으로 다시 계산한 view가 같다. co-sign 때문에 기계마다 저장한 집합은 다르지만, 같은 statement를 다 만나면 같은 view로 모인다. 서로 믿고 어느 쪽도 빠지지 않은 두 컴퓨터는 T0와 K가 같아 같은 devices를 본다. 한쪽만 아는 빼기나 사슬이 있으면 그것이 닿을 때까지 둘의 명단은 다르다(한쪽만의 멤버십).
- **초대장이 새거나 다시 쓰일 때.** 초대장 글을 가진 누구나 수명 안에 그 kind의 기기로 든다. 같은 초대로 둘째 key가 들면, 첫 사용을 아는 컴퓨터는 `used`로 거절하고, 모르는 컴퓨터가 받았어도 두 항목이 만나는 곳에서 `invite` 충돌로 둘 다 빠진다(fail-closed. 사람이 새 초대장으로 다시 들인다). 초대 서명 statement를 다시 내는 것(replay)은 그 statement의 key만 들이고 그 key의 Noise 비밀이 없으면 붙지 못한다. 수명은 검증하는 컴퓨터의 시계로 보므로 시계가 틀린 컴퓨터는 수명을 다르게 본다.
- **빼기와 들이기가 엇갈릴 때.** 빼기를 모르는 컴퓨터가 뺀 기기의 새 rev나 그 key의 초대 서명 statement를 받아 서명해도 빼기와 만나는 순간 진다. 뺀(또는 훔친) 컴퓨터가 빼기 소식이 닿기 전에 들인 기기는, 그 사이 다른 컴퓨터가 같이 서명했으면 남는다. 사람이 목록에서 따로 뺀다. 빼기끼리는 grounded labelling이 정한다. 사람이 X에서 R을, Y에서 F(R이 빠지기 전에 들인 가짜 컴퓨터)를 뺀 뒤 도둑이 F로 X를, R로 Z를 빼면(Q2T), Y의 빼기는 공격이 없어 IN이고 F의 X 빼기가 OUT이 되어 X의 빼기가 IN, R의 Z 빼기가 OUT이다: 어느 root에서나 R과 F만 빠진다. R이 Y까지 빼면(Q1T) X와 Y는 자기 빼기를 처음부터 IN으로 두어 R과 F만 빼지만, 구경꾼 Z에서는 X→R→Y→F→X가 물고 돌아 아무것도 정해지지 않으므로 Z는 자기만 남기고 X, Y, R, F를 뺀다. 시각이 없어 "빠진 뒤"와 "엇갈림"을 가르지 못하므로 고리는 fail-closed다: 사람이 그 기계에서 믿지 않는 쪽을 다시 빼면 풀리지만(아래 "엇갈림 풀기") 남은 도둑은 되돌릴 수 없다. 서로 뺀 두 컴퓨터는 2-고리라 각자는 자기를 남기고 상대를 빼며 구경꾼은 둘 다 뺀다. 빼기 소식이 닿기 전의 도둑은 아직 믿는 컴퓨터라 아무나 뺄 수 있다(막을 길이 없다).
- **엇갈림 풀기.** 정해지지 않은 빼기로 빠진 기기는 그 컴퓨터의 My devices(`roster/list`의 `disputed: true`)와 `lophn remote devices`에 "Disputed"로 서고 `roster/remove {key}`(CLI `lophn remote remove <key>`)로 뺄 수 있다. 화면 없는 구경꾼은 CLI로만 푼다. 줄의 id와 이름은 지금 믿는 서명자가 서명한 항목에서(없으면 그 기기 자신의 서명에서) 오고, 빼기는 줄의 key로 고른다: 빠진 도둑이 자기 항목에 남의 id를 달면 그 id는 두 줄에 맞아 id로는 고르지 않는다(`conflict`). 도둑이 빠지기 전에 자기 이름을 다른 컴퓨터의 이름으로 바꿨고 그 rev에 다른 컴퓨터들이 같이 서명했으면 이름이 같은 두 줄이 선다. 규칙으로 가릴 수 없어 사람이 기계를 보고 고른다. 사람이 믿지 않는 쪽을 그 컴퓨터에서 다시 빼면 그 빼기는 그 컴퓨터가 서명한 것이라 그 view에서 처음부터 IN이고, 대상이 낸 빼기가 OUT이 되어 대상이 뺀 쪽이 돌아온다. 예: X가 R을 뺀 소식보다 "R이 X와 Y를 뺐다"가 먼저 Y에 닿으면 Y에서는 X와 R이 둘 다 빠진다(정해지지 않음). Y에서 R을 빼면 X가 돌아오고 모두 정해져, Y가 X의 빼기에 같이 서명해 퍼진다. 뺀 key를 다시 빼는 길은 사람의 화면과 CLI(actor user)뿐이라 빠진 컴퓨터가 쓰지 못한다.
- **폰과 엇갈림.** 폰은 자기 판단이 없어 엇갈린 컴퓨터를 믿지 않는다: 정해지지 않은 빼기에 걸린 저장한 컴퓨터는 목록에 남기되(잘린 것으로 보이고 붙지 않는다) 지우지 않고, 정해진 빼기로만 지운다. 엇갈리지 않은 컴퓨터 하나가 다시 빼면(또는 같이 서명하면) 폰도 그 결정을 따른다. 도둑이 폰이 저장한 컴퓨터를 모두 뺐으면 폰은 어느 쪽도 믿지 못한 채 남는다(아래 "열린 것").
- **명단의 컴퓨터는 서로 대등하다.** 어느 믿는 컴퓨터나 아무 항목의 새 rev에 서명하므로 컴퓨터의 터미널 입력 허락(초대장의 `--no-terminal-input` 포함)은 정직한 code에만 묶인다: 그 컴퓨터가 자기 항목을 허락한 rev로 서명할 수 있다. 명단의 컴퓨터 하나가 뚫리면 명단 전체가 뚫린 것으로 본다. 폰의 허락은 폰이 서명하지 못하므로 지켜진다.
- **주소는 서명하지 않는다.** reach는 서명 밖이라 붙은 기기 아무거나 다른 컴퓨터의 주소를 덮을 수 있다. 틀린 주소는 Noise가 key로 막아 다른 기계에 닿지 않지만, 잘못 도는 폰이 A의 B로 가는 link를 계속 못 붙게 할 수 있다.
- **복사된 data root.** 알아챈 복제는 새 기계 id를 받고 host key 표지가 어긋나 `roster/forget_all`이 명단, 자기 항목과 id, host key, 서명 key를 버린다. 복사본은 새 key와 새 id로 처음부터 초대받는다. 원래 기계의 key는 그대로다. 복사본이 옛 id를 새 key로 다시 쓰면 id 충돌로 둘 다 빠지므로(원래 기계는 자기 key라 자기 view에서 남는다) id도 버려야 한다. 알아채지 못한 복제(`machine.md`의 열린 것)는 같은 host key, 서명 key, id를 가진 두 설치라 명단도 하나로 본다(빼면 둘 다 빠진다). 알아챈 복제가 forget_all 전에 붙어 남긴 흔적(새 key의 항목)이 있으면 사람이 목록에서 뺀다. 폰의 기기 key는 그 기기에만 있는 보안 저장소라 복사되지 않는다.

## 지키는 것

1. 폰과 다른 기계의 창이 부르는 route는 모두 기기 route 목록 안이다. 화면이 목록 밖 route를 부르는 단추를 보이지 않는다(skip 바꾸기, session 지우기, 설정·secret 화면, job 만들기·고치기·거절).
2. desktop 화면의 동작과 모양은 폰 때문에 바뀌지 않는다. desktop 화면에 폰을 위한 분기(prop, host member)가 없고, 폰은 desktop의 DOM·Electron 화면 file을 import하지 않는다. 폰이 가져오는 것은 순수 logic뿐이다.
3. 화면은 연결과 key를 직접 만지지 않는다. data 층의 읽기 hook만 쓴다.
4. 기기 key는 폰의 보안 저장소에만 있다. 컴퓨터의 key 둘(host key, 서명 key)은 core data의 `remote/` 아래 0600 file에만 있고 shell과 renderer는 다른 기계에 붙는 key를 갖지 않는다. key file은 찍힌 기계 id가 이 기계와 다르거나 둘 가운데 하나만 읽히면 쓰지 않고 둘 다 지운다. 어느 내보내기에도 실리지 않는다.
5. 틀린 `watch` 조건은 보내지 않는다. 연결이 닫힌 뒤에는(사람이 끊은 것이 아니면) 다시 붙는다.
6. 폰이 명단에서 나가면 그 폰은 모든 컴퓨터, 든 명단, 기기 key를 잊는다. 컴퓨터에 닿으면 그 컴퓨터가 서명한 빼기가 모든 기계에 퍼지고, 닿지 않으면 명단에 남아 사람이 컴퓨터에서 뺀다. 다시 들려면 새 key로 새 초대장이다.
7. 폰 화면의 문구는 `@lophn/i18n`의 key다. 폰에만 있는 문장만 `mobile.`로 시작하는 새 key다.
8. relay는 증명하지 못한 control socket에 폰 연결을 잇지 않고, 폰 연결 둘의 message는 서로의 data socket으로 가지 않는다. relay는 내용을 보지 못한다(Noise는 폰과 core 사이에서 끝난다).
9. 폰은 자기 push token과 설정을 자기 기기 행에만 둔다. 다른 기기의 것을 고치는 입력이 없고, token과 설정은 `devices/list`로 나가지 않으며 `devices/clear_push`·`devices/push_targets`는 폰이 부를 수 없다.
10. 폰이 부르는 `coding_sessions/switch`는 `confirmed: true` 없이는 거절되고(화면이 sheet로 확인을 받은 뒤에만 보낸다) `terminals/input`은 core가 그 기기의 허락을 입력마다 본다. 폰 화면이 입력 칸을 그리는지는 안내일 뿐이다.
11. 폰은 컴퓨터의 앱을 띄우지 않는다. coding session과 터미널은 core가 가져 앱 없이 보고 열고 친다.
12. 알림을 눌러 무엇을 여는지는 폰이 `data`를 모양대로 읽을 때만이다. 모양이 틀리거나 모르는 컴퓨터면 아무것도 열지 않는다. 알림 글은 대화 내용을 싣지 않는다(`attention.md`).
13. 사용자 앱의 폰 화면은 guest 안에서만 돈다. guest는 폰 앱의 JS 전역, 보안 저장소, file system, network에 닿지 않고 그 오류가 폰 앱을 죽이지 않는다. 폰은 자기가 못 돌리는 화면(자기보다 새 kit·base, 옛 major, 모르는 module)을 열지 않고 받은 `phone.js`가 manifest의 크기와 sha256과 다르면 쓰지 않는다(`phone-screen.md`).
14. 폰이 연 view는 그 기기의 연결에 묶인다. 연결이 닫히면 core가 그 기기의 view를 지우고 폰이 다시 붙으면 같은 인자로 다시 연다. 폰은 view id로만 operation을 부르고 부를 수 있는 operation은 core가 view의 release 선언으로 정한다.
15. core의 `request`는 지정한 기기의 연결로만 가고, 그 기기가 `hello`의 `capabilities`에 적은 kind만 보낸다. 모르는 `id`, 다른 연결, deadline 뒤의 `response`는 버리고 기다리는 사이 연결이 닫히면 `unavailable`로 끝난다. 한 기기의 답이 다른 기기에 묻은 요청을 채우지 못한다.
16. 폰의 위치는 `phone.use {location.get}` grant가 있는 앱이 live일 때만 나가고 grant가 없으면 폰에 묻지도 않는다. 폰은 앱이 앞에 있고 OS 권한이 있을 때만 읽는다. background 위치를 읽지 않는다. 폰을 깨우지 않는다.
17. 폰에서 도는 앱의 data는 컴퓨터에 안 간 변경이 있는 동안 지우지 않는다(컴퓨터가 목록에서 빠져도 앱이 컴퓨터의 목록에서 빠져도 같다). standalone 앱의 data는 자동으로 지우지 않는다. 폰의 sync는 앱이 앞에 있고 컴퓨터에 닿은 동안만 돈다. `app_sync/push`와 `snapshot`은 짝지은 기기 자격만 받는다(`app-sync.md`).
18. 폰은 앱이 앞에 있을 때만 답하고 입력을 kind의 schema로 검사한다. `drive.*`는 그 폰이 연 preview view에만 닿고 live 화면, lophn 자신의 화면, 다른 앱에는 닿지 않는다.
19. 붙는 쪽은 저장한 기계 id와 core hello의 id가 다르면 hello 말고 어떤 frame도 보내지 않는다. 자격(`join`, call)이 다른 기계에 가지 않는다. 저장한 주소 후보도 기계 id를 대조한 연결의 hello로만 바꾼다.
20. 판 범위가 겹치지 않는 연결은 hello 뒤 어떤 frame도 오가지 않고 닫힌다. core는 붙는 쪽의 판이 범위 밖이어도 자기 hello를 먼저 보내 양쪽이 같은 `details.update`를 낸다.
21. kind로 가르는 것은 phone 장치(기준, `shell.devices`, push token, phone 탭의 preview view, presence의 폰 규칙)뿐이다. 컴퓨터는 다른 컴퓨터의 기기 표에 행이 없어 기준이 되지 못하고 push token을 두지 못하며, 그 밖의 권한은 폰과 같다.
22. 기기의 이름은 명단에 하나다. 폰의 연결은 폰이 알린 이름이 마지막으로 받은 것과 다를 때만 명단 이름을 고치고, 컴퓨터의 이름은 기계 이름과 한 값이다(`machine.md`). 폰이 컴퓨터에 붙인 별명은 그 폰 안에만 있고 연결이 고치지 않는다.
23. remote key 둘에 찍힌 기계 id가 지금 id와 다르거나 하나만 읽히면 그 key와 명단을 쓰지 않는다. key를 먼저 지우고 명단을 버리므로 중간에 죽어도 다음 기동이 key 없이 남은 명단을 보고 다시 버린다. 둘 다 못 읽는 key file은 덮지 않는다.
24. 다른 기계의 창이 보낸 IPC는 main이 그 창(webContents)으로 기계를 정한다. core 통로는 이 컴퓨터 core의 `machines/call`·`machines/watch`로 그 기계에만 가고, 허락 목록 밖의 channel은 어느 handler보다 먼저 `forbidden`이다. 이 컴퓨터의 core에 닿는 `shell:machines-this-read|clone-here`는 다른 기계의 창에서만 지나고 이 컴퓨터의 창에서 오면 `forbidden`이며, `this-read`는 `project.list`, `ListAgents`, `ListSessions`만 넘긴다. `shell:machines-open`이 싣는 session은 이 컴퓨터의 id에만 받는다. 이 컴퓨터의 알림, presence, 전역 키, agent가 여는 창은 다른 기계의 창을 쓰지 않는다.
25. 명단은 statement 집합의 함수다. 받은 순서, 받은 길, 받은 때와 무관하고, keep만으로 다시 계산해도 같다.
26. 빼기가 이긴다. 늦게 온 더 새 rev, 같은 key의 새 id, 같은 key의 초대 서명 statement, 같은 서명 key를 단 새 host key가 되살리지 못한다.
27. 뺀 key와 서명 key는 항목으로도, 서명자로도, root로도 돌아오지 않는다. 돌아오려면 새 key다. 빼기는 key와 서명 key로만 빼고 body의 `id`로는 아무것도 빼지 않는다.
28. 뺀 컴퓨터만 서명한 것은 쓰지 않는다: 그 컴퓨터가 빠지기 전에 다른 믿는 컴퓨터가 같이 서명한 항목만 남는다. 빠진 컴퓨터의 빼기는 그것을 공격하는 빼기(그 컴퓨터를 뺀 빼기)가 IN이면 효력이 없다.
29. 초대장은 statement가 검증하는 컴퓨터에 닿을 때 수명을 보고, 같은 초대로는 key 하나만 든다. 그 key를 빼도 그 초대장은 쓰인 것이다. 둘이 들었으면 둘 다 빠진다(빠진 쪽은 이미 빠져 있다). 초대장의 kind와 다른 기기는 들지 못한다.
30. 부딪는 key(id, 서명 key, 모양, 초대)는 둘 다 빠지고 컴퓨터는 거기 서명하지 않는다. root의 자기 key는 빠지지 않는다.
31. 폰은 누구도 들이지 못하고, 폰이나 폴더가 나른 것은 서명으로만 믿는다. root는 서명 key다.
32. 다른 기계로 넘긴 call은 받는 기계가 `device:<부른 컴퓨터의 id>`의 지금 route 목록으로 거른다. 넘기는 쪽은 범위를 넓히지 못한다.
33. 복사된 data root는 명단을 이어받지 않는다. 서명 key는 host key와 같은 기계 표지를 갖고 같이 지워진다(`machine.md`).
34. 같은 rev에서 터미널 입력 허락을 거둔 쪽이 이긴다.
35. host key와 서명 key는 늘 같이 새로 만든다. 서명 key만 잃거나 새로 만들면 다른 컴퓨터가 모두 `signing_key` 충돌로 보고 이 컴퓨터는 `key_taken`으로 다시 들지 못한다.
36. 컴퓨터는 정해진(settled) 빼기에만 같이 서명한다. 정해지지 않은 빼기에 서명하면 고리 밖으로 퍼진다.
37. agent 자격은 `roster/*`와 `machines/*`를 부르지 못한다(사람과 기기의 route는 actor user만, 저장 route는 core 안 machine 자격만 받는다). 다른 기계로 넘기는 call은 사람의 화면이 부른 것뿐이다.
38. 붙기 전 연결은 저장소를 채우지 못한다: `join`의 statement는 모두 그 연결의 key에 대한 것이어야 하고, 초대 서명 statement는 확인이 맞을 때만 남는다. 초대한 컴퓨터가 거절한 `roster/join`은 아무것도 저장하지 않는다.
39. 지금 믿지 않는 쪽(모르는 서명자, 빠지거나 엇갈린 컴퓨터, 믿지 않는 초대장)의 statement는 keep에 `ROSTER_UNKNOWN_MAX`개까지만 남고 믿는 컴퓨터의 statement와 빼기를 밀어내지 못한다. 엇갈린 줄의 id와 이름은 믿는 서명자(없으면 그 기기 자신)의 항목에서만 오고, 다시 빼기는 key로 고른다.

## 경계와 계약

- boundary `remote-protocol`: frame(hello 둘의 판 범위·기계·이름과 폰의 화면, 첫 frame `join`, `roster`, `call`·`result`, `request`·`response`, Gateway frame), 명단(statement와 초대장의 schema, 서명 bytes, 믿음 계산과 합치기, 초대 확인, pending), 기기 route 목록(`roster/leave`, `devices/set_push`, `presence/report`, `project_files/list|read` 포함), base64 bytes. protocol 판 4, 하한 4. 폰은 연결에 좁은 입구 `@lophn/protocol/remote/client`(연결, frame type, key, `REMOTE_PATH`, 초대장 schema, 명단 계산)를 쓰고, route 정의와 schema는 protocol source를 그대로 읽는다.
- 폰의 coding agent와 터미널: route `coding_sessions/*`, `terminal_view/*`, 기존 `acp/*`(coding session만의 `acp/tool_body|image_upload|image_read` 포함), event `AcpUpdated`·`StateChanged{coding_sessions}`·`TerminalScreenChanged`. 기기 허락 `terminal_input`은 명단 항목의 칸이고 `roster/invite {terminal_input}`이 초대장에 싣는다. 그 허락은 browser page를 다루는 것(`page_view/input|control|open`)도 덮는다.
- 폰과 다른 기계의 창의 browser page 보기: route `page_view/list|snapshot|watch|input|control|open`, event `PageViewChanged`·`StateChanged{browser_pages}`(계약은 `browser-tab.md` "경계와 계약").
- core가 폰에 묻는 길: frame `request`·`response`(protocol의 `phone` 폴더가 모양, kind 표, `unavailable` 이유를 정한다), `hello.capabilities`, core의 `PhoneLink`. 앱의 길은 memory route `app_phone.request`(actor app), broker `/_lophn/broker/phone/request`, SDK part `@lophn/cap-phone` 1.0.0, grant `phone.use {capability}`다. 이유 `details.reason`: `no_phone`, `phone_unreachable`, `unsupported`, `phone_in_background`, `location_off`, `timeout`(모두 `unavailable`)과 폰의 `forbidden`·`os_permission_denied`. drive(단계 10)는 `unavailable` 이유 `no_preview`, `screen_off`, `covered`, `conflict` 이유 `taken_over`, `stale_ref`, `off_screen`, agent에게 가는 문장 `PHONE_TAB_TEXT`를 더한다.
- 폰의 홈 화면: route `app_widgets/list`(폰 gate에 있다), `app_widget.set`(앱 자격), URL scheme `lophn`. 설계는 `phone-home-screen.md`다.
- boundary `mobile`: 폰 앱. boundary `design-native`: 폰 UI kit.
- 폰에서 도는 앱: route `apps/phone_file`, `app_sync/push|pull|snapshot|snapshot_file`, event `AppSyncChanged`. 계약은 `app-sync.md`다.
- 사용자 앱의 폰 화면: route `apps/phone_screens`, `apps/screen_file`, `app_views/open|call|close`, event `AppViewEvent`. 계약(manifest, host module 목록, host-guest 메시지)은 `phone-screen.md`다.
- 명단: route `roster/list|invite|join|remove|set_terminal_input|rename`(사람 자격), `roster/leave`(기기 자격. 부른 기기 자기만), core 안 machine 자격만 부르는 `roster/statements|store|forget_all`. `roster/invite {kind: phone|computer, terminal_input, lifetime: short|long}`은 초대장 글(`{invite, secret, issuer, reach}`, QR에 싣는 JSON)과 끝나는 때를 낸다(30분, 7일). `roster/join {text}`는 `{device, machine, pending}`이다. 거절 `details.reason`: `untrusted`, `removed`(`details.removal`에 그 빼기), `expired`, `used`, `id_taken`, `key_taken`, `this_computer`. ledger 표 `roster_statements`·`roster_reach`(schema step `remote.roster`). 바뀌면 `StateChanged{remote_devices}`.
- 컴퓨터끼리: link의 engine은 package `@lophn/remote-client`(boundary `remote-client`)다. route `machines/list|call|watch`(사람 자격), transient event `MachineFrameReceived`(subject `machine:<mch_>`, 기기 event 목록 밖).
- 폰의 기기 행: ledger 표 `devices`(이 컴퓨터에 붙은 폰의 local 행). route `devices/list`, `devices/set_primary`, `devices/set_push`(기기 자격), core 안 machine 자격만 부르는 `devices/connected {id, name, phone?}`, `devices/clear_push`, `devices/push_targets`.
- remote key: `<data root>/remote/host-key.json`과 `signing-key.json`, 칸 `machine`(만든 기계 id). data step `remote.host-key.machine`(이 판 전의 host key에 찍는다)과 `remote.signing-key`(짝 서명 key를 더한다)가 remote wiring에 있다.
- 폰의 보안 저장소: 기기 key, 컴퓨터 목록(`machine`, `signing_key`, `announced`(명단의 이름), `name`(별명)), 든 명단(statement와 주소), 폰 이름 `phone-name`.
- 다른 기계 보기: renderer가 읽는 `MachineList`(`{state: starting|ready, this, machines[{id, name, status: connecting|connected|offline|update, update: client|host|null, path, last_seen_at}], start: {mode: last} | {mode: machine, machine}, last}`, id는 모두 `mch_`), preload bridge `lophnMachines`와 IPC `shell:machines-list|changed|start|open|this-window|visible|this-read|clone-here`(`open { machine, session? }`, `this-read { route: "project.list" | "ListAgents" | "ListSessions", input }`, `clone-here { url, identity, title }`), 따로 preload `preload-remote`, shell data `viewer/start.json`·`viewer/windows.json`과 data step `shell.viewer.roster`. 기기 route `unseen/list|dismiss`.
- CLI `lophn remote on|invite|join|devices|remove`(사람의 터미널만).
- 앱 안의 길: place union 하나. 화면은 `open(place)`, `back()`, sidebar 열기, 컴퓨터 고르기만 부른다.

## 결정

- 폰 화면은 컴퓨터가 내려주는 web 화면이 아니라 폰 UI kit으로 쓴 React Native 화면이다. 이유: scroll, keyboard, gesture가 폰답고, 화면 내려주기(bundle, hash 확인 cache, WebView, bridge)가 없어 폰 앱이 단순하다. 비교한 폰 앱 다섯 가운데 셋이 RN native였다. 버린 안: 얇은 껍데기와 core가 내려주는 web 화면(계획 `phone-remote-web`과 `phone-shell`이 만들었고 이번에 지웠다). (사람, 2026-11-15)
- wireframe이 화면의 기준이다. 뼈대는 sidebar이고 아래 tab bar를 두지 않는다. 폭 600 이상에서는 sidebar가 늘 열려 있다. (사람, 2026-11-15)
- 화면 이동은 React Navigation(native stack과 drawer)이다. 이유: 넓은 화면의 고정 sidebar가 들어 있고 비교한 폰 앱이 쓰는 표준이다. (agent, 2026-11-15)
- 폰의 권한은 보기, 말하기, 답하기, 켜고 끄기, 지금 돌리기, 새 session이다. 만들기·고치기·지우기와 secret, provider, model 관리는 컴퓨터에서 한다. 폰에서 mode(skip)를 바꾸지 않는다: skip은 agent가 사람에게 묻지 않고 돌게 하는 권한 설정이라 desktop에서 정한다(`approval.md`). (사람, agent)
- 화면 문구는 desktop과 같은 `@lophn/i18n` catalog에서 온다. 이유: 같은 문장이 두 벌이 되지 않는다. (사람, 2026-11-15)
- 화면 아래의 로직은 desktop과 같은 TypeScript(event client, Inbox store, 대화 source)를 그대로 쓴다. 이유: 대화 해석이 한 벌이어야 한다. 대가: DOM에 묶인 desktop file의 순수 부분을 DOM 없는 file로 옮겨야 한다. 옮기지 못한 것은 폰이 베낀다. (agent)
- 폰의 대화 화면은 desktop 대화 화면(`AgentView`)을 폰 host로 쓰지 않고 폰 kit으로 새로 그린다. 이유: desktop 화면은 DOM이고 desktop만의 통로(터미널, file 열기, 끌어 놓기, preload)를 끌고 온다. 대화 해석(source)만 공유한다. (agent)
- 화면을 core 없이 보도록 dev build에 sample 컴퓨터를 둔다. 이유: 화면 worker와 사람이 컴퓨터 없이 모양을 본다. (agent)
- 폰의 [Remove]는 이 폰을 명단에서 뺀다(`roster/leave`). 컴퓨터 하나만 지우는 길은 없다. 이유: 명단에 든 폰은 명단의 모든 컴퓨터와 이어지므로 한 컴퓨터만 잊어도 명단이 다시 채운다. 닿는 컴퓨터가 없으면 폰만 잊고 사람이 컴퓨터에서 뺀다. 버린 안: 컴퓨터마다 자기 등록을 지우는 `devices/unpair`와 이미 아는 key의 `pair`로 옛 등록 바꾸기(앞의 판). (agent)
- 첨부는 사진(Photos, Camera)만이고 5 MiB, 그림 네 종류다. 이유: desktop과 같은 route와 message 모양을 쓰고, 폰의 file에는 컴퓨터의 path가 없다. 버린 안: 아무 file 첨부(file 고르기 module이 하나 더 들고 route가 없다). (agent)
- byte는 frame 종류를 늘리지 않고 `call` 안에 base64로 싣는다. 이유: 대화 이미지와 file은 작고, frame 종류를 늘리면 연결 계약이 커진다. (agent, 2026-11-15)
- 앞으로 온 앱은 열린 연결에 `watch`를 다시 보내 3초 안의 `ready`로 살아 있는지 본다. 이유: background에서 소리 없이 죽은 socket은 close event가 오지 않는다. 멀쩡한 연결은 `stale`로 깜빡이지 않는다. (agent, 2026-11-15)
- 폰 앱은 root workspace 밖의 `mobile`에 자기 `package.json`과 lock을 가진 Expo project로 둔다. 이유: React Native 의존 tree가 Electron 설치와 `npm run check`에 섞이지 않는다. protocol과 kit은 Metro가 source로 읽어 한 벌이다. 대가: 폰 앱의 type 검사와 test는 따로 돌린다(폰 앱 폴더의 `npm run typecheck && npm test`). (agent, 2026-11-15)
- 폰은 coding agent를 core가 가진 대화로 다루고 터미널은 화면 보기가 기본이다. 이유와 버린 안은 `harness-gui.md`(core의 handle, 바꾸기 확인, 열기·되살리기 범위)와 `terminal-agent.md`(터미널 보기). 폰 쪽의 정한 것: 터미널 화면은 먼저 React Native의 styled text row로 그린다(WebView terminal은 그 길이 못 쓸 때만. native module이 없이 되고 새 dev build가 필요 없다). 대화는 새로 그리지 않고 desktop의 harness GUI source에 폰의 feed를 끼운다. (agent)
- 터미널의 보이는 화면은 가리지 않고 폰에 보낸다. 입력은 기기마다의 허락이고 사람이 초대장을 낼 때 정한다(기본 켬). 명단 항목의 칸이라 모든 기계에 같고 어느 컴퓨터의 My devices에서나 기기마다 바꾼다. 이유와 대가는 `terminal-agent.md`의 결정. 폰의 입력 허락을 폰이 아니라 core가 입력마다 본다. (agent, 기본 켬은 사람)
- 터미널로 도는 coding session은 폰에서 그 터미널 화면으로 열고 `Switch to chat`은 그 화면의 menu에 둔다. 이유: 안내 화면을 거쳐 채팅으로 바꿔야만 쓸 수 있으면 도는 turn을 끊어야 했다. 터미널 화면에서 바로 치면 컴퓨터에서 쓰던 그대로 이어 간다. 버린 안: 안내 화면과 `View terminal` 단추(앞의 판). (사람이 방향, agent)
- 컴퓨터의 주소 후보는 hello마다 싣고 붙는 쪽은 기계 id를 대조한 연결에서만 저장한 목록을 바꾼다. 이유: pairing 뒤에 생긴 주소(새 network, Tailscale, VM)를 다시 pairing 없이 쓰게 하면서, 같은 key를 가진 복사된 data root가 기기를 다른 곳으로 이끌지 못하게 한다. interface에 붙지 않는 주소는 사람이 `remote.addresses`에 적는다. 버린 안: QR에서 받은 목록만 쓰기(앞의 판. 주소가 바뀌면 다시 pairing해야 했다). (agent)
- push는 Expo Push를 core가 직접 부르고 폰 쪽은 `expo-notifications`다. 알림 설정은 폰에 한 벌이고 폰이 붙는 모든 컴퓨터에 사본으로 둔다. 이유와 버린 안은 `attention.md`. 폰 쪽의 정한 것: Paired에서 한 번만 묻고 거절하거나 미루면 Settings에서 켠다. 이유: 처음 pairing하는 순간이 "알림이 왜 필요한지"를 가장 잘 말하고, 다른 컴퓨터를 더할 때마다 다시 묻는 것은 귀찮다. token을 받을 수 없는 build(EAS project id가 없는 build)는 가짜 token을 만들지 않고 "쓸 수 없다"로 둔다. 개발 build만 가짜 token을 쓴다. (agent)
- 사용자 앱의 폰 화면은 폰 앱 안의 guest runtime에서 돌고 react-native-web WebView로 그리지 않는다. desktop preview만 react-native-web이다. 이유와 버린 안은 `phone-screen.md`. (agent)
- core가 폰에 일을 시키는 길은 remote channel의 `request`·`response` frame 하나이고 `PhoneLink`가 묻는다. 칸 이름은 `capability`가 아니라 `kind`다. 이유: 폰이 하는 일은 한 갈래이고 위치 말고 폰 화면을 모는 일(단계 10)이 같은 길에 얹힌다. 그래서 frame은 그대로 두고 kind만 더한다. 앱 쪽 이름 `capability`(grant 범위, SDK)는 앱에 열어 준 kind만 가리킨다. 버린 안: desktop의 `/host-link`를 폰에 넓히기(loopback만이고 연결 하나이고 인증이 desktop의 Bearer다), 폰이 server가 되기(NAT 뒤), 기능마다 socket, event와 답 route로 주고받기(답을 이으려고 전달 보장을 다시 만든다). (agent)
- 폰은 답할 kind를 `hello.capabilities`에 적고 core는 적힌 kind만 묻는다. 이유: 옛 폰이 모르는 frame을 받아 연결이 끊기지 않고 판을 올리지 않는다. (agent)
- 폰을 push로 깨우지 않고 앞에 있을 때만 답한다. 이유: Android는 앞에 있는 앱의 foreground 위치만 허락하고 background 위치는 권한과 Google의 심사가 따로 든다. 위치를 읽으려고 사람의 폰을 push로 불러내는 것은 사람이 모르는 때에 읽는 길이다. 대가: 앱은 `unavailable`이 평소 일이다. (agent)
- 앱의 길만 열었다. agent가 폰 기능을 부르는 route와 CLI, 기기마다의 스위치는 쓰는 예가 생길 때 연다. 이유: 부르는 쪽이 없는 기능을 먼저 만들지 않는다. (agent)
- 위치 읽기에 lophn의 banner와 기록을 두지 않는다. 이유: 동의 카드가 앱마다 한 번의 동의이고 Android가 자기 위치 표시를 띄운다. (agent) 사람이 읽기를 보고 싶어 하면 그때 기록을 더한다.
- 앱의 `phone.use`는 기능마다 따로 묻고 거둔다(scope `{capability}`). 이유: 위치를 허락한 앱이 camera까지 얻지 않는다. `secret.use {name}`과 같은 모양이라 permission kind 하나로 기능을 늘린다. 버린 안: 기능마다 permission kind(더할 때마다 파일이 열 개 남짓 는다), 호출마다 묻기(위치는 조용하고 잦다). 사람은 두 번 묻는다: lophn의 동의 카드(이 앱이 폰의 위치를 써도 되나. 한 번)와 OS의 위치 권한(lophn이 위치를 읽어도 되나. 처음 쓸 때 한 번). (agent)
- 폰에서 도는 앱의 backend와 data는 폰이 가지고 컴퓨터가 hub다. 폰 gate에는 그 앱이 설치되고 맞추는 데 필요한 route(`apps/phone_file`, `app_sync/*`)와 event(`AppSyncChanged`)만 열고 앱을 직접 부르는 길은 계속 닫는다. 이유와 버린 안(relay가 변경을 맡기, 폰 둘을 직접 맞추기)은 `app-sync.md`. (planner)
- core가 폰에 묻는 길은 하나다(planner, 2026-11-15). remote channel에 `request`·`response` frame을 더하고 core에 `PhoneLink`를 둔다. 폰 기능(단계 8)과 폰 화면 다루기(단계 10)가 같이 쓴다. desktop의 `/host-link`와 같은 모양이고 폰은 두 번째 host다. 그래서 drive를 위한 `AppViewEvent` 갈래나 폰이 부르는 답 route(`app_views/drive_answer` 같은 것)는 없다. 버린 안: event로 요청을 보내고 route로 답 받기(두 길이 따로 기한과 짝을 맞춰야 한다).
- 공개 상태는 따로 열지 않고 Noise handshake 뒤의 hello에 싣는다. 붙는 쪽은 QR로 이미 key를 알아야 handshake를 하고 hello는 `join`이나 call보다 먼저 온다. 버린 안: 평문 HTTP 답(LAN의 누구에게나 이름과 id를 보인다). (planner)
- 붙는 쪽은 hello의 기계 id를 들어올 때 저장한 것과 비교한 뒤에만 frame을 보내고, 같은 id의 두 항목은 하나로 접는다(별명은 남긴다). 이유: 복사된 data root는 같은 key로 답한다. (planner)
- remote protocol 판은 올릴 때 하한도 같이 올린다(판 2: 판 범위, 기계 확인, 이름. 판 3: 명단. 판 4: 명단 규칙). 옛 폰 앱은 새 core에 붙지 못하므로 폰 앱과 core를 같이 올린다. hello는 모르는 칸을 버려 칸만 더할 때는 판을 올리지 않는다. 판 3은 옛 길(`pair` frame, 컴퓨터마다의 pairing code와 기기 등록 route)을 남기지 않는다. (planner, 판 3은 agent)
- 판이 어긋나면 core도 자기 hello를 먼저 보내고 닫고, 오류가 어느 쪽을 올릴지(`client`, `host`)와 그 컴퓨터의 이름(`name`)을 싣는다. 이유: 붙는 쪽이 "이 앱을 올려라"와 "<컴퓨터>의 lophn을 올려라"를 가를 수 있다. 고칠 수 있는 곳에서 고칠 것을 말한다. (planner, `machine-update`)
- lophn 판은 범위로 보고 제품 판 글은 보이기만 한다. 이유: 같은 build를 요구하면 한 기계를 올릴 때 나머지가 멈춘다. (사람·planner, `machine-update`)
- 기기 kind는 명단 항목의 `phone`과 `computer`다. phone에만 맞는 장치(기준, `shell.devices`, push token, phone preview view, presence의 폰 규칙)는 컴퓨터마다의 local 기기 행에 두고 컴퓨터는 그 행이 없다. 버린 안: kind `desktop`(shell main이 다른 기계에 붙던 기기, 앞의 판). (planner, `computer`는 agent)
- 컴퓨터 기기의 권한은 폰과 같다(보기, 말하기, 승인·질문 답, 앱 쓰기). 다른 기계의 관리는 없다. 그래서 기기 route 목록과 `app_sync/*`는 kind로 가르지 않는다. (planner)
- 기기 이름은 명단에 하나이고 어느 컴퓨터에서나 바꾼다. 컴퓨터의 이름은 기계 이름과 한 값이다: 다른 컴퓨터가 준 이름을 기계 이름으로 받고, 자기 이름을 바꾸면 바로 자기 항목을 다시 서명한다. 이유: 명단 하나를 모든 기계가 같이 들므로 기계마다 다른 별명은 같은 기기를 기계마다 다르게 부르게 하고, 두 값이면 다음 기동이 한쪽을 다른 쪽으로 되돌린다. 버린 안: 컴퓨터마다 알린 이름과 별명을 따로 두기(앞의 판, 사람 2026-11-16). 폰이 컴퓨터에 붙이는 별명("Shown as")은 폰 안에 남았다. (agent)
- 복사된 data root는 명단을 이어받지 않는다. remote key 둘에 만든 기계의 id를 찍고 기동 때 대조해 다르면 명단과 기기 행을 모두 버리고 key를 새로 만든다. 이유: 그 등록과 push token은 다른 기계가 pairing한 것이고, 같은 key 둘은 붙는 쪽을 헷갈리게 한다. 복제가 들고 온 provider key와 secret은 사람이 스스로 복사한 것이라 지우지 않는다. (planner)
- 폰을 깨우지 않는다(planner). 앱이 앞에 없으면 `unavailable`이고 문장이 agent에게 사람에게 부탁하라고 말한다. 이유: 폰 화면을 다루는 것은 사람이 폰을 들고 있을 때의 확인이고, 컴퓨터가 폰을 깨우거나 앞으로 부르면 사람이 모르는 사이에 폰이 움직인다.

- desktop이 다른 기계를 볼 때 이 컴퓨터는 그 기계의 기기(`device:<이 컴퓨터의 id>`)다. 기기 권한은 폰과 같고 컴퓨터 때문에 관리 route를 넣지 않는다. 더한 route는 `unseen/list|dismiss` 둘이다. (사람·planner, 2026-11-16)
- 다른 기계의 앱 화면은 띄우지 않는다. 미룬 것이 아니라 하지 않는 것이다. (사람, 2026-11-16)
- 한 창은 한 기계이고 기계마다 창이 하나다. 창은 지금의 `lophnCore` 통로를 그대로 쓰고 main이 보낸 창으로 기계를 가른다. 버린 안: 한 창에서 기계를 바꾸기(renderer가 창마다 core 하나를 module 수준에서 잡고 layout이 기계 안 id에 묶인다), renderer가 기계를 직접 부르기(CSP, key가 renderer에 온다). (planner)
- 다른 기계와의 연결은 core가 들고 화면은 `machines/call`·`machines/watch`로 부른다. 이유: 컴퓨터의 정체를 core의 key 하나로 두어 화면 없는 기계도 같은 정체로 붙고, 붙는 code와 key가 shell과 core에 두 벌이 되지 않는다. 버린 안: shell main이 기계마다 연결과 붙는 key(`viewer/key.json`, `viewer/machines.json`)를 들기(앞의 판). (agent)
- 다른 기계의 창은 따로 preload를 받고 main이 그 밖 IPC를 한 곳에서 거절한다. renderer는 bridge가 없을 때의 길로 기능을 감춘다. 이유: 거절이 handler마다 흩어지면 하나를 빠뜨린다. (planner)
- 다른 기계 창의 layout은 저장하지 않는다. 이유: layout file이 기계 안 id에 묶이고 detached 창까지 다른 기계에 묶는 일이 따라온다. (planner)
- 컴퓨터의 key 둘은 OS keyring이 아니라 core data의 0600 file에 기계 표지와 같이 둔다. 이유: keyring 없는 Linux와 화면 없는 기계에서 실패 갈래만 는다. (planner)
- 컴퓨터가 다른 컴퓨터의 명단에 드는 길은 초대장 글 붙여 넣기(Settings의 [Join with an invite], `lophn remote join`)뿐이다. 카메라 길은 없다. (planner)
- 연결 조각은 폰과 core(다른 컴퓨터로 가는 link)가 같이 쓰는 package에 있다. 이 package 밖에서 Noise 연결을 새로 짜지 않는다. protocol은 구현을 두지 않아서 따로 둔다. (planner)
- 한 연결의 call 수를 client가 8로 막는다. 이유: core의 read 줄이 caller마다 8이라 desktop 창이 workspace를 열 때의 묶음이 "Couldn't load"로 깨졌다. core도 줄이 찬 caller의 read를 거절하지 않고 read 기한(2초)까지 잡아 둔다(이 컴퓨터의 창에도 같은 묶음이 온다). 버린 안: core의 한도를 늘리기(한 caller가 reader를 더 오래 쥔다). (agent)
- client는 답 없는 call을 120초 뒤 `unavailable`로 끝내고, core는 frame 한도(16 MiB)를 넘어 보내지 못한 답을 `unavailable`("the reply is too large to send")로 대신 답한다. 이유: 답을 잃은 call이 8개 자리 하나를 앱이 도는 동안 쥐었다. 대가: 16 MiB를 넘는 snapshot을 가진 긴 coding session은 폰에서 열리지 않고 오류가 선다(이슈 `remote-reply-over-frame-limit-is-dropped`). (agent)

- 명단은 서명한 statement의 집합이고 믿음은 root에서 서명을 따라간다. 버린 안: 계정(lophn 서버가 기기 목록을 쥔다), 가운데 기계(없는 사람은 못 쓴다), 공유 비밀 하나(기기 하나만 뺄 수 없다), 지금의 쌍마다 pairing. (roadmap `multi-device`)
- 초대장 수명은 닿을 때 한 번 보고 view는 시각을 보지 않는다. 이유: 시각이 들면 같은 집합이 때에 따라 다른 명단이 된다. (agent)
- root는 host key가 아니라 서명 key다. 이유는 위 "믿음 계산". (agent, review가 확인)
- 같은 key의 여러 id는 가장 작은 id로 접는다. 이유: 같은 폰을 컴퓨터 둘에 pairing해 둔 사람은 옮긴 뒤 같은 key에 `dev_`가 둘이고, 순서와 무관한 규칙이 가장 작은 값이다. (agent)
- 빼기끼리는 공격 그래프의 grounded labelling으로 정하고, root가 서명한 빼기는 처음부터 IN, 정해지지 않은 고리는 대상을 빼되 그 view의 root는 남긴다. 버린 안: 서명자가 빠져도 빼기가 남기(빠진 도둑이 빠진 뒤에도 아무나 뺀다), 서로 뺐을 때만 예외로 두기(mutual 예외), K0의 대상으로 한 번 보기(빠진 도둑이 효력 없는 빼기 하나로 그 컴퓨터의 빼기를 막는다), 두 번 보기(첫 번과 둘째 번이 누가 빠졌는지를 뒤집어, 도둑이 신원 둘을 쥐면 Q2T에서 아무것도 하지 않은 Z가 빠지고 Q1T에서 다섯이 다 빠져 모든 컴퓨터가 스스로를 지운다), 고정점 없이 오가는 반복(서로 물고 도는 빼기에서 끝나지 않는다). (review, lead)
- 부딪는 것은 둘 다 뺀다(fail-closed). 어느 쪽이 맞는지 모르는 채 하나를 고르면 고른 쪽이 도둑일 수 있다. (review, lead)
- 옮긴 폰은 서명 key를 `join` 답으로 배운다. hello에 싣지 않는 것은 모든 연결의 첫 frame이 `join`이라 한 곳으로 충분하고, hello를 만드는 core 쪽 code를 이 계약에서 바꾸지 않아도 되기 때문이다. (agent)
- 새 기기는 이미 명단에 든 컴퓨터 하나가 들이고 명단이 나머지에 퍼진다(조사의 방식 1). 버린 안: 기기 하나(폰이나 첫 기기)가 모두에 서명하는 root, 공유 비밀 하나, 쌍마다 잇기를 두고 횟수만 줄이기. (사람)
- pairing code는 초대장이다. 든 컴퓨터가 한 번 쓸 key로 서명한 초대장을 내고 새 기기가 그 key로 자기 항목에 서명해 스스로 든다. 초대한 컴퓨터가 꺼져 있어도 된다(dual boot). 버린 안: 살아 있는 연결이 있어야만 들이기(같이 켜질 수 없는 두 OS는 영영 못 잇는다). (사람)
- 이미 pairing한 폰은 다시 pairing하지 않는다. 컴퓨터의 기기 표 줄은 그 컴퓨터가 서명한 명단 항목이 되고 host key는 그대로다. 컴퓨터끼리는 shell의 붙는 key가 없어지므로 초대로 한 번 다시 잇는다. 옛 key를 읽어 주는 호환 장치는 만들지 않는다. (사람)
- 초대장은 들일 기기의 kind를 싣고 다른 kind는 그 초대장으로 들지 못한다. 이유: 폰 초대장이 새어도 서명자(컴퓨터)가 들지 못한다. (agent, review)
- 초대장의 수명은 낼 때 고른다: 기본 30분, 새 기기가 초대한 컴퓨터와 같은 때 켜질 수 없으면 7일. 이유: 짧은 수명이 샌 초대장의 위험을 줄이고, 긴 것은 dual boot와 집·직장 컴퓨터를 잇는다. 그보다 먼 수명은 받지 않는다. (agent)
- 초대한 컴퓨터가 거절한 `roster/join`은 아무것도 저장하지 않는다(믿지 않을 issuer와 죽은 초대 서명 statement를 남기지 않는다. 이미 믿는 컴퓨터가 서명한 빼기만 받는다). 닿지 못했으면 저장하고 pending으로 끝난다. 판이 어긋나면 저장하지 않는다. (agent)

## 열린 것

폰의 preview 화면 다루기(drive)는 emulator의 release build와 개발 core(fake model)로만 보았다. 실제 폰, 실제 model의 agent turn, iOS는 보지 못했다(change-log `mobile-browser-use`).

사용자 앱의 폰 화면(`phone-screen.md`)은 emulator에서 개발 core에 손으로 지은 앱을 붙여 보았고 실제 agent가 만든 앱이나 실제 폰으로 보지 못했다. iOS는 짓지 않았다. 폰에서 도는 앱(`app-sync.md`)도 같다: emulator와 개발 core의 손으로 지은 앱 둘로만 보았고 실제 폰, 실제 agent가 만든 앱, 한 앱을 두 폰이 맞추는 것은 보지 못했다. 폰 화면의 알려진 빈틈은 `phone-screen.md`의 열린 것과 이슈 `phone-guest-*`, `phone-screen-*`, `phone-apps-menu-lacks-wireframe-rows`, `phone-open-url-blank-workspace`.

폰의 홈 화면(위젯, 아이콘)과 폰의 위치 읽기는 emulator에서 개발 core에 손으로 지은 앱을 붙여 보았다. 실제 폰, Electron desktop 앱의 동의 카드 줄과 앱 상세의 `phone.use` 줄, 실제 agent가 만든 앱, iOS는 보지 못했고 위치 정확도 `balanced`·`low`는 emulator에서 시간 초과였다(`high`만 됐다. emulator에는 network 위치가 없다). 설계와 알려진 빈틈은 `phone-home-screen.md`와 change-log `mobile-widgets`.

폰의 coding agent와 터미널은 실제 desktop 앱(Electron)에 붙여 보지 못했다. 폰 화면은 emulator에 붙인 개발 core로만 보았다: 지난 session을 실제로 되살리는 경우, 열기의 `conflict`·`unavailable` 거절, 실제 coding agent의 대화는 보지 못했고 실제 폰도 쓰지 않았다(change-log `mobile-coding-agents`). 폰이 PTY 크기를 잡고 desktop 탭이 다시 잡는 것, 폰이 연 터미널, 폭 2칸 글자 재기도 폰과 Electron에서 돌려 보지 않았다. 처음 받는 화면은 아직 컴퓨터 크기이고(폰이 크기를 잡은 뒤 다음 화면부터 폰 크기다), core를 다시 켜면 폰이 연 터미널을 잊어 그 화면을 다시 볼 수 없다. 터미널로 도는 session을 터미널 화면으로 여는 것, 새 session의 Terminal, 초대장의 터미널 입력 스위치, 펼칠 때 읽는 tool 본문, 폰이 붙이는 그림과 다시 연 대화의 그림도 폰과 Electron에서 돌려 보지 않았다. 주소 후보를 hello로 바꾸는 것은 test로만 보았고 실제 network가 바뀌는 경우(Tailscale, VM)는 보지 못했다. `remote.addresses`의 Settings 칸은 없다.

두 기기가 한 coding session이나 터미널을 같이 쓸 때의 빈틈: coding session에서는 폰이 lophn session에서 못 하는 입력(권한 mode, shell 실행)이 route로는 통한다(이슈 `coding-input-skips-device-scope`), 확인한 뒤에 다른 기기가 시작한 turn이 바꾸기로 말없이 끊긴다(`coding-switch-confirms-stale-plan`), 바뀔 때 폰에서 쓰던 글이 사라진다(`phone-draft-lost-on-view-swap`), 터미널 입력을 다시 보내면 두 번 쳐진다(`phone-terminal-input-retry-types-twice`), 기기 호출의 오류가 `details`를 잃어 "다른 기기에서 바뀌었다"를 보이지 못한다(`remote-call-errors-drop-details`). 긴 Claude Code session 하나가 폰에서 빈 대화로 열렸고 원인은 확인하지 못했다(`phone-coding-session-opens-empty`).

판 어긋남의 안내는 판 2 전 build에는 가지 않는다(판 1 옛 폰 build는 core가 모양 밖 frame으로 닫아 log에도 판 어긋남이 남지 않는다). 판이 실제로 다른 두 build로 보지 못했고(판이 하나뿐이다) test의 가짜 판으로만 보았다. desktop에서 한 번 붙은 기계의 창은 그 뒤 판이 범위 밖이 되면 마지막 화면 위의 한 줄이 누가 올려야 하는지 말한다. 저장한 기계 id와 다른 컴퓨터가 답하면 offline과 같아 보인다. 판 2 전에 pairing해 아직 기계 id가 없는 항목은 같은 컴퓨터에 다시 들어올 때까지 접히지 않는다. 

폰의 알림은 실제 FCM 배달을 확인하지 못했다. 사람의 Expo·Firebase 계정이 있어야 하고 지금까지는 fake push server로만 보았다(change-log `mobile-push`, `attention.md`). 폰에 아직 없는 것과 알려진 빈틈은 이슈와 change-log `mobile-app`에 있다: 대화의 수식과 mermaid는 code box로 보인다, fork와 rewind가 없다(글로 치면 컴퓨터에서 쓰라고 알린다. subagent 줄은 그 대화를 읽기 전용 sheet로 연다), Inbox의 History는 notice 목록이다, agent 줄의 model은 raw 이름이다.

다른 기계 보기와 명단(컴퓨터 둘과 폰 하나의 들이기, 빼기가 퍼지기, 옮긴 폰이 다시 pairing하지 않고 붙기, 컴퓨터끼리 다시 잇기)은 test와 한 컴퓨터의 개발 core 둘(`npm run dev`와 `npm run dev -- --viewer`, relay 없이)로만 보았다. 설치본 둘과 실제 폰, relay 길, dual boot, macOS·Windows의 key와 창은 보지 못했다(사람이 change-log `device-roster`의 checklist로 본다). `viewer/windows.json`에서 명단에서 빠진 기계의 창 자리 줄은 지우지 않고 남는다.

내 기기 명단의 남은 것:

- 같은 rev의 두 고치기(이름 바꾸기 둘)는 하나가 진다. 허락을 거둔 것만은 이긴다.
- 한쪽만 아는 빼기나 사슬이 있는 동안 두 기계의 명단이 다르다. 빼기는 그것이 닿는 대로 맞춰진다.
- 서로 뺀 두 컴퓨터는 각자 자기를 남기고 상대를 빼며 구경꾼은 둘 다 뺀다. 빼기가 물고 도는 고리는 구경꾼에서 고리의 컴퓨터를 모두 뺀다. 사람이 구경꾼에서 믿지 않는 쪽을 다시 빼면 풀린다(위 "엇갈림 풀기").
- 폰은 서명하지 못해 다른 컴퓨터가 같이 서명한 새 명단을 받을 때까지 접힌 id가 굳지 않는다.
- 초대장은 수명까지 받는다. 화면의 [New invite]는 앞의 초대장을 감출 뿐이고 쓰이지 않은 앞의 초대장도 수명 안에서는 들인다(초대한 컴퓨터는 한 번 쓸 key의 비밀을 저장하지 않아 거둘 목록이 없다).
- 폰이 컴퓨터에 붙이는 별명("Shown as")은 폰 안에 남았다. 컴퓨터 쪽 이름은 명단 하나다.
- 컴퓨터 하나만 폰의 목록에서 지우는 길은 없다. 폰의 [Remove]는 이 폰을 명단에서 뺀다.
- ledger `devices` 표에 명단이 대신 드는 옛 칸(`kind`, `terminal_input`)이 남는다. 표 다시 만들기를 이 판에 한 번 더 하지 않으려고 두었다. `alias`는 명단을 저장할 때 view의 이름을 두는 칸으로 쓴다.
- 도둑이 폰이 저장한 컴퓨터를 모두 뺐으면 폰은 모든 컴퓨터를 엇갈린 것으로 보고 어느 쪽도 믿지 못한다. 컴퓨터가 다시 빼도 풀리지 않는다(시각 없이 대칭이다). 폰이 믿을 컴퓨터를 사람이 폰에서 고르는 길이 있어야 풀린다.
