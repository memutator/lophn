# problems/feedback

사람의 [문제 알리기]에서 글과 당시 화면의 안전한 자료를 준비하고 사람이 보낼 자료를 선택하도록 하며, 첨부나 대상이 없어도 정직하게 제보를 접수하는 약속을 맡는다; 버튼의 배치와 앱 view 틀은 shell/app-frame이 맡는다.

## 요구

### 사람의 글과 대상

**[R1]** feedback은 인증된 shell에서 사람이 제출한 글만 받으며 글은 platform/redaction 뒤 공백 외 1~500 Unicode 문자로 제한한다.
- 이유: 앱과 agent의 주장을 사람의 경험으로 위조하지 않는다.
- 확인: 빈 글과 501자 글은 거절되고 app·agent가 대신 제출할 수 없으며 사람이 쓴 글은 해석과 별개로 보존된다.

**[R2]** 명세가 없거나 HTTP 200 응답을 받은 경우도 기대와 실제 결과가 다르면 feedback을 제출할 수 있다.
- 이유: 성공한 응답과 업무 정확성은 같은 사실이 아니다.
- 확인: 틀린 집계에 기대·실제·기간·시간대·source를 안전한 글로 남기고 명세가 없는 이유로 거절되지 않는다.

**[R3]** feedback은 알려진 표시 결과·invocation·automation·고정 문서나 데이터 판을 지목할 수 있지만 모르는 대상은 모른다고 표시한다.
- 이유: 마지막 요청을 무조건 제보 대상으로 확정하면 잘못된 수리를 유도한다.
- 확인: 비교 조회의 역순·늦은 응답과 늦은 제보에서도 실제 표시한 결과를 지목하며 연결을 모르면 임의 invocation이 붙지 않는다.

**[R4]** UI 입력 검사로 command가 시작되지 못한 feedback은 시작 전 실패로 설명하고 없는 invocation을 만들지 않는다.
- 이유: 실행하지 않은 일을 실행 실패로 남기지 않는다.
- 확인: 입력 검사로 버튼 동작을 막은 뒤 제보하면 실행 전이라고 보이고 가짜 invocation이 없다.

### 당시 화면과 선택

**[R5]** [문제 알리기]는 dialog를 열기 전에 버튼 시점의 app view만 캡처하고 보호 화면·lophn dialog가 떠 있거나 view가 가려진 동안 및 다른 창은 캡처하지 않는다.
- 이유: 제보 화면이나 보호된 결정·다른 앱의 비공개 자료가 섞이지 않아야 한다.
- 확인: 버튼 뒤 화면이 바뀌어도 당시 view 자료가 유지되고 보호 화면이 이미 떠 있거나 view가 숨겨졌으면 이미지 없이 이유를 보인다.

**[R6]** 제출 전 글과 안전한 화면 상태·redaction된 screenshot을 미리보고 각각 제외할 수 있으며 screenshot은 사람이 미리보기를 확인해 선택한 뒤에만 저장한다.
- 이유: 자동 준비와 자동 영구 저장을 구별해 민감한 화면을 보호한다.
- 확인: 안전한 화면 상태만 기본 선택되고 screenshot은 확인 전 선택되지 않으며 비공개 영역을 안전하게 redaction할 수 없으면 선택할 수 없다.

**[R7]** 자동 화면 상태는 화면 이름·선택 탭·URL path와 안전한 hash·입력 형태만 담고 URL query 값·업무 DB·command 입력 원문·read command 전체 결과를 자동 복사하지 않는다.
- 이유: 실제 표시 대상을 설명하면서 업무 값 전체의 자동 저장을 막는다.
- 확인: query 값과 민감한 표시 결과를 넣어 제보하면 원문 값이 빠지고 안전한 위치·형태와 제외 이유만 남는다.

### 자료 한도와 접수

**[R8]** 선택 screenshot은 PNG 머리를 검증하고 긴 변 1,600px 이하·2,097,152 bytes 이하로 제한한다.
- 이유: 기본 첨부 크기를 예측하고 위장 이미지나 과도한 자료를 받지 않는다.
- 확인: PNG 아닌 자료와 2MiB 초과 이미지는 거절되고 큰 정상 캡처는 긴 변 1,600px 이하로 준비된다.

**[R9]** 화면 상태는 redaction된 JSON 65,536 bytes 이하로 제한하고 feedback 전체 전송은 3,145,728 bytes 이하로 제한한다.
- 이유: 이미지와 상태를 함께 보내도 무제한 접수하지 않는다.
- 확인: 64KiB 초과 상태와 3MiB 초과 전송은 명시적으로 거절되며 글·이미지 개별 한도도 각각 확인한다.

**[R10]** 첨부 미선택·화면 없음·수집 꺼짐·수집 실패·redaction 제외·저장 실패는 각각 이유를 표시하고 첨부 없이도 글을 제출할 수 있다.
- 이유: 없는 screenshot 때문에 사람이 겪은 문제까지 잃어서는 안 된다.
- 확인: 각 실패를 주입해도 허용된 글이 접수되고 저장되지 않은 screenshot이 첨부됨으로 표시되지 않는다.

**[R11]** 미제출 초안·접수 대기·접수 완료를 구별하고 접수 실패에는 복사 가능한 글과 이유를 남기되 초안은 메모리에만 둔다.
- 이유: 로컬 입력을 영구 접수로 오해하거나 전송 실패로 글을 잃지 않게 한다.
- 확인: 접수를 막으면 완료 표시 없이 글 복사가 가능하고 임시 보존 실패도 보이며 shell 종료 후 초안 복구를 보장한다고 안내하지 않는다.

**[R12]** dialog 취소는 미제출 자료를 저장하지 않지만 이미 접수한 feedback은 dialog를 닫아도 삭제하지 않는다.
- 이유: 편집 취소와 발생 기록 삭제를 같은 동작으로 만들지 않는다.
- 확인: 제출 전 취소에는 보고가 없고 제출 완료 뒤 닫아도 같은 보고를 읽을 수 있다.

### 기존 문제와 후속 제보

**[R13]** feedback 제출 화면은 기존 문제 선택 여부를 명시적으로 보여 주고 제출한 뒤 problems/grouping의 묶기 결과로 돌아갈 수 있게 한다.
- 이유: 사람이 추가 제보를 어디에 남겼는지 확인할 수 있어야 한다.
- 확인: 선택한 기존 문제와 선택하지 않은 제출을 각각 보내면 problems/grouping이 정한 문제를 열 수 있다.

**[R14]** “직접 해 봤지만 안 됩니다”는 새 feedback으로 남기며 무시·오탐 판단과 수리 확인은 problems/closing의 사람 결정과 구별한다.
- 이유: 실패 경험을 닫힘이나 별도 자동 오탐 수리로 바꾸지 않는다.
- 확인: 직접 시도 실패 제보는 새 보고이고 무시·오탐 동작은 보호된 종료 사유를 남기며 자동 오탐 문제가 생기지 않는다.

## 열린 질문

- problems/feedback#Q1 자동 준비한 screenshot과 화면 상태의 기본 포함 범위를 유지할까.
- problems/feedback#Q2 feedback 원문·metadata·미완료 수 quota를 얼마로 제한할까.
- problems/feedback#Q3 최근 read command 8개·각 20행/16KiB 및 invocation 10개·오류 20개를 화면 상태에 자동 붙일까.
- problems/feedback#Q4 자동 캡처한 screenshot을 사람 선택 없이 첨부하던 규칙을 유지할까.

## 버린 것

- 오탐 버튼이 별도 자동 문제를 하나 만드는 규칙은 보호된 종료 사유로 충분하므로 버린다.
