## 문서끼리 어긋난 것

- `tmp/architecture/approval.md` 4장은 request에 `decided_by`(grant, human)를 두고 7장도 `decided_by`를 늘린다고 하지만, S2 11장 1은 `decided_by`를 두지 않는다고 확정했다. 머리 안내대로 S2를 따랐다. 같은 문서 3장은 data 손실을 "사본에서 잰다"고 하고 changes.md 4장 app-releases 줄도 "migration을 DB 사본에서 잰다"고 한다. S2 4장은 "처리는 S7"이라고만 한다. S2·S7을 따랐다.
- `tmp/architecture/approval.md` 5장은 rewind를 이 문서에 두고 changes.md 2장 approval 줄과 rewind 줄은 "core가 changeset을 남긴다"고 쓰지만, S2 11장 2와 S5가 SDK가 changeset을 뜨고 core가 보관·지휘한다고 정했다. S5를 따랐다.
- `tmp/changes-by-topic.md` 3장 shell/confirmation-window는 "별도 modal 창 → request 카드, toast, 대기 목록"이라 하는데, 이 창은 approval 말고도 문제 결정, 연결 회수, rewind, 비밀 입력(provider 연결, secret), 질문 선택지 action, 파일 삭제 같은 사람 결정에도 쓰인다. 새 문서(S1, S2, 요구)는 approval 쪽만 정하고 나머지 종류와 창이 어떻게 되는지는 어디에도 없다.
- S2 3·4장은 "lophn 쪽 설정(agent 정의, 지침, skill, Settings)을 고치는 것"을 agent grant의 대상으로 두고 req-1493·AGENT-ROLE도 그렇게 쓴다. 그런데 S4 11장 1은 "설정 고치기 tool은 지금 두지 않는다(보류)"이고, S2 5장 마지막은 file tool로 지침 파일을 쓰는 것만 설정 고치기로 본다고 한다. 지금 실제로 Gate에 걸리는 설정 고치기는 file tool의 지침 파일 쓰기 하나뿐이다.
- S2 5장은 "lophn agent의 file·shell·web tool은 Gate를 거치지 않는다"고 하고, 같은 문단에서 지침 파일 쓰기는 설정 고치기로 본다고 해서 file tool이 Gate를 거치는 경우가 생긴다. "지침 파일"이 정확히 어떤 경로인지(LOPHN.md, agent 정의 파일, skill 파일 등)는 S2, S4 어디에도 적혀 있지 않다.
- req-1495와 req-0315의 문장만 보면 turn 안 request와 보류 request의 수명이 섞여 읽힌다. S2 6장 표가 둘을 나눠 정했고(turn 안은 메모리·interrupted 때 cancelled, 보류는 표·더 새 release의 activation 시작 때 cancelled) 구현은 S2를 따른다. 요구 문장에는 이 구분이 드러나지 않는다.

## 확인 못함

- **confirmation handle 기반**: route의 `confirmation: "required"`와 core의 일회 handle 표(`server/identity/confirmation*.ts`, `protocol/base/confirmation-handle.ts`, writer의 예약·소비, main의 `confirmation_handle_register`)는 approval 말고도 12개 route가 쓴다(approval 허락·거절 둘, apps `grant.revoke`, coding agent 연결 회수, 파일 삭제, 문제 닫기, secret 둘, rewind, provider 둘, 질문 선택지 action). 새 문서에는 "사람 자격의 결정 command로만 결정한다(req-0303)"만 있고 이 handle을 둘지, 두면 창 없이 카드 클릭에서 어떻게 발급하는지 정한 곳이 없다. 추천: 사람 자격 증명 방법은 유지하고 창만 없앤다(handle은 카드 클릭에서 main이 발급). 이 영역은 approval 두 route와 `grant.revoke`만 센다.
- **비 approval 사람 결정 화면의 운명**: 문제 결정, 연결 회수, rewind, secret 입력(비밀번호처럼 가려야 하는 입력), provider 연결, 질문 선택지 action, 파일 삭제가 지금 확인 창을 쓴다. 새 설계에서 어디서 받는지 정한 문서를 못 찾았다. 특히 secret 입력은 원문이 renderer나 agent 대화에 보이면 안 되는 별도 필요가 있다. 이 영역은 approval 종류만 센다(`main/confirmation/kinds/approval.ts`·`apps.ts`·`app-decisions.ts`와 renderer 해당 화면).
- **agent grant의 저장 위치와 식별 단위**: S2 7장은 Grants가 주인이고 "지금 코드 `apps/permissions`"라고 하지만, 거는 쪽이 agent다. agent는 role 고정 agent(lophn 전체에 하나, Project Manager와 App Engineer는 place마다 하나)와 사람이 만드는 Operator 여럿이다. grant를 agent 정의 파일(frontmatter)에 둘지 표에 둘지, key를 agent ID로 할지 role+place로 할지 S4와 S2 어디에도 적혀 있지 않다.
- **app-api별 override의 저장**: "빼기"와 "묻는지 바꾸기"를 app-api key로 저장하는 구조, release가 바뀌어 app-api가 사라졌을 때 override를 어떻게 하는지는 문서에 없다.
- **보류 request의 종류 이름과 handler 등록 방식**: `activation`과 `reaction` 둘뿐이라는 것 외에 handler 계약(입력, 멱등 키, 적용 결과 칸)은 적혀 있지 않다.
- **`PermissionRequested`의 payload**: 대상, 정규화한 입력, 효과를 싣는 모양과 coding agent 표시(harness가 준 물음의 원문)의 모양은 S1이 이름만 정했다.
- **`RestartObservation`의 소비처**: `observeApprovals`를 지워도 되는지(`storage/migration`의 재시작 점검이 새 설계에서 남는지) 읽지 않았다.
- **`workspace/agent`·`agents-tab`이 권한을 보이는지**, 앱 상세에서 agent에게 앱을 할당하는 길이 있는지: 읽지 않았다. UI 고칠 것 마지막 줄과 "할당 화면" 항목의 위치가 이에 달려 있다.
- **test 규모**: 지울 test 파일의 정확한 개수와 줄 수는 세지 않았다(core/approvals 21개 test는 파일 이름으로 확인).
- **renderer의 toast 구조**: `overlay`와 `ask-agent-toast`가 지금 어떻게 toast를 띄우는지 자세히 읽지 않았다. 새 toast가 이 위에 올라가는지 S1 worker가 확인해야 한다.
