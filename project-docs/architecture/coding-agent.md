# coding-agent

coding agent 연결 장치는 사람이 쓰는 coding agent(`external-coding-agent`)와 lophn을 잇는 남은 부분이다. lophn CLI(`packages/cli/`), 제품 감지와 hook 설치와 공유 skill 사본(`packages/coding-agent/harnesses/`), 제품별 표(`packages/protocol/coding-agent/`)다. 사람이 연 터미널 탭에서 도는 coding agent의 상태, 탭 icon·점, 알림은 [terminal-agent.md](terminal-agent.md)다. lophn agent로 쓰는 harness(정의의 `runtime`이 `claude-code`, `codex`, `opencode`)는 아래 "harness agent" 절이다. 사람 터미널 탭에 coding agent를 띄워 일을 맡기던 길(coding session)은 없다.

## 흐름

```
Settings › Coding agents ─ shell main이 exec ─▶ lophn harness detect|refresh ─▶ 제품마다 감지 결과
Settings › Coding agents ─ shell main이 exec ─▶ lophn harness status ─▶ 제품마다 hook 상태(모두 dry_run, process 하나)
사람 터미널에서 harness를 처음 알아봄 ─▶ lophn harness install --dry_run ─▶ 없으면 lophn 창 dialog로 묻고 install
[Install hooks] ─────────────────────────▶ lophn harness install (누른 것이 허락)
[Uninstall hooks] ───────────────────────▶ lophn harness uninstall (우리 항목만 지운다, lophn이 쓴 skill 사본도)
shell main (core ready, 앱 activation, 설정 coding-agent.shared_apps 바뀜, hook 설치·삭제 뒤)
   ─ exec ─▶ lophn harness sync-skills ─ user token ─▶ core: settings.list, app.skills
   ─▶ hook이 놓인 harness의 skill_dir에 공유 skill 사본 (표시 file .lophn-shared)
harness ─ 전역 hook ─▶ lophn hook <harness> <event> ─▶ shell main hook socket ([terminal-agent.md](terminal-agent.md))
사람 ─▶ lophn agent run | <app> <command> | run … | workflow … | 그 밖의 명령 ─ user token ─▶ core
```

## 지키는 것

- **CLI 명령은 core를 부르는 명령과 `local` 명령 둘이다.** core를 부르는 명령의 표는 `packages/cli/commands/`의 `COMMANDS`이고 lophn agent의 `lophn` tool도 같은 표를 쓴다. `local` 명령은 `packages/coding-agent/local/`에 있고 binary 입구(`packages/cli/main.ts`)만 끼운다.
  - core를 부르는 명령(`agent run`, `<app> <command>`, `run wait|show|cancel`는 `architecture/run.md`, `workflow …`는 `architecture/workflow.md`, 그 밖의 명령은 lophn agent와 같은 표)은 `<data root>/run/user-token`(core가 켤 때 쓰는 user token, 0600)을 자격으로 쓴다. file이 없으면 lophn이 꺼진 것이라 `unavailable`로 끝난다(exit 5). CLI가 core를 띄우지 않는다.
  - `local` 명령(`hook`, `harness detect|refresh|install|status|uninstall`)은 core를 부르지 않는다. 예외는 `harness sync-skills` 하나다. 이 명령만 user token으로 core를 읽는다(binary가 `ctx.core()`로 끼우고, 자격 file이 없으면 `unavailable`).
  - `not_found`는 core가 준 글 그대로 돌려준다. user token은 출력에 남기지 않는다.
- **제품 감지는 shell main이 CLI를 exec해서 한다.** core는 사람의 PATH와 실행 파일을 모르고 감지 결과를 받지 않는다. Settings › Coding agents가 이 결과를 그린다(`packages/shell/main/desktop/coding-connection.ts`). 처음 읽기는 실행 파일 찾기만 하고, 제품을 실제로 실행하는 version probe는 사람이 다시 감지를 눌렀을 때만 돈다. 사람이 시키지 않았는데 제품을 띄우지 않는다.
- **앱의 source 폴더는 `app.create`가 commit된 뒤 core가 만든다.** writer 앞 처리(`packages/core/apps/registration/source-folder.ts`)가 내장 template을 `<data root>/apps/<app>/source`(`appDefaultSource`, `packages/protocol/apps/app-storage.ts`)에 깔고 첫 commit을 만든 뒤(사람의 전역 git 설정은 읽지 않고, 저장소 안에 `user.name`, `user.email`, `commit.gpgsign=false`를 남긴다) core 안 machine 자격으로 `app.connect_source`를 부른다. 폴더가 이미 있으면 덮지 않고, commit이 있을 때만 그대로 잇는다. 깔기나 잇기가 실패하면 앱은 `source_path: null`로 남는다. `app.connect_source`는 git 저장소의 맨 위이고 commit이 있는 폴더만 받는다.
- **hook은 harness의 사용자 전역 설정에 한 번 놓고, 놓기 전에 사람에게 묻는다.** 사람의 터미널에서 그 harness를 처음 알아봤을 때 shell main이 `lophn harness install`을 `dry_run`으로 불러 없는지만 보고, 없으면 놓을 file을 보여 주고 묻는다. 묻는 것은 OS 창이 아니라 lophn 창의 dialog다. shell main이 그 터미널을 고른 창에 push하고 그 창의 답을 기다리며(browser bridge와 같은 request id + ack), 답하기 전에 창이 닫히거나 reload되면 거절이다. headless나 창이 없으면 묻지 않고 놓지 않는다. dialog는 harness 이름, 하는 일 한 문장(상태를 보이고 turn 끝을 알린다), 쓸 file 목록이고 Codex는 `config.toml`에 hook trust도 같이 기록한다는 한 문장이 붙는다. Settings › Coding agents의 [Install hooks]는 누른 것이 허락이라 묻지 않는다. 허락하면 놓고, 성공은 toast 하나, 실패는 무엇이 왜 실패했는지와 file을 담은 dialog로 보인다. 거절은 기억하지 않고 다음에 다시 묻는다. 묻거나 놓기가 실패해도 터미널은 그대로 돈다(hook이 없어 상태가 unknown이다). `dry_run`은 event마다 우리 항목이 있으면 내용이 달라도 `unchanged`라 lophn이 업데이트돼도 다시 묻지 않는다. 표에 새로 더한 event에 우리 항목이 없거나, plugin file 본문이 지금 원문과 다르면(hook command만 다른 것은 같다고 본다. 2.x용으로 바뀌기 전의 OpenCode plugin도 여기 든다) `missing`이다. 개발 실행만 예외다. PATH의 `lophn`이 없거나 설치된 판이라, `npm run dev`가 만드는 launcher(`<저장소>/.cache/dev-cli/lophn`, 설치된 `/usr/bin/lophn`과 같은 본문에 경로만 저장소 소스와 그 저장소의 Electron으로 바꾼 것)를 `LOPHN_CLI`로 shell main에 주고, shell main이 그 경로를 hook command로 넘긴다. 그때의 `dry_run`은 우리 항목의 command가 다르면 놓을 것이 있다고 본다. launcher는 `.dev-data`가 아니라 저장소의 `.cache/`에 두어 schema가 바뀌어 `.dev-data`를 지워도 전역 hook이 가리키는 경로가 남고, 실행마다 다시 쓴다.
- **Codex hook은 trust까지 같이 기록한다.** Codex는 새로 놓이거나 바뀐 hook을 사람이 `/hooks`에서 trust하기 전까지 건너뛴다. 그래서 설치가 `~/.codex/config.toml`에 lophn 항목마다 `[hooks.state."<hooks.json 경로>:<event>:<group 번호>:<handler 번호>"] trusted_hash`를 쓴다. hash는 Codex `hook_hash`(rust-v0.164.0 `codex-rs/hooks/src/engine/discovery.rs`, `codex-rs/config/src/fingerprint.rs`)와 같은 계산이다(`packages/coding-agent/harnesses/codex-trust.ts`). 정규화한 handler 하나, matcher, event 이름을 key 정렬 compact JSON으로 sha256한다. lophn의 표만 고치거나 끝에 더하고 나머지 byte(주석, 다른 도구의 표)는 그대로 둔다. 파싱되지 않는 `config.toml`은 건드리지 않고 `failed`다. trust 기록이 없거나 hash가 다르면 `dry_run`이 `missing`이고 file 목록에 `config.toml`이 든다. 사람의 허락은 lophn dialog 한 번이다. Codex가 계산을 바꾸면 기록이 Modified가 되어 사람이 `/hooks`에서 trust하던 때로 돌아갈 뿐이다. orca도 같은 기록을 쓴다.
- **전역 설정은 사람의 다른 항목을 보존한다.** harness마다 통합 규칙(hook을 놓는 위치와 꼴, event → 신호, hook stdout, session id·session 이름 경로, resume 인자)은 `HARNESS_ADAPTERS[id]` 한 항목(`packages/protocol/coding-agent/harness-adapter.ts`)에 있다. 설치할 event는 그 항목의 `events` key다. 꼴은 Claude식 json settings(claude, qwen, qoder, codebuddy, command-code, droid, letta), JSONC(devin), 우리 전용 file(grok, copilot, kiro V3), flat json(cursor), 이름 붙은 hook object(antigravity), 표시한 TOML block(kimi), managed hooks file과 settings 칸(muse, `LPN_TERMINAL_HOOK`을 env 허용 목록에 더한다), 표시한 YAML block과 허용 목록 사전 기록(hermes), event마다 script file(cline), plugin·extension file(opencode·kilo·mimocode 공통 본문, pi, omp, amp)이다. prime-agent는 hook API가 없어 놓지 않는다. 어느 꼴이든 우리 항목만 바꾸고 나머지 byte(주석, 다른 도구의 항목)는 그대로 둔다. 파싱되지 않거나 고칠 수 없는 꼴이면 아무것도 쓰지 않고 `failed`다(muse에 다른 `managed_hooks_path`가 있으면 `conflict`). cline은 event마다 script 하나라 사람의 script가 이미 있으면 놓지 않는다. hook이 stdout에 정해진 JSON을 내야 하는 harness(antigravity, cursor)는 CLI와 launcher가 같은 표(`HARNESS_ADAPTERS[id].stdout`)에서 출력한다. lophn 밖에서 불려 바로 끝날 때도 같다.
- **Settings의 hook 상태는 CLI 한 번으로 읽는다.** `lophn harness status`가 모든 harness의 `install --dry_run`을 한 process에서 돌려 목록으로 낸다(`packages/coding-agent/local/harness-run.ts`). 화면이 열릴 때와 창이 focus를 다시 받을 때마다 읽으므로 harness마다 process를 띄우면 25개가 한꺼번에 뜬다(CPU 약 10초).
- **[Uninstall hooks]는 놓기의 거꾸로이고 우리 것만 지운다.** `lophn harness uninstall`(`packages/coding-agent/harnesses/uninstall.ts`)은 놓을 때와 같은 규칙으로 우리 항목을 알아본다(command가 `lophn hook <harness> `나 개발 경로로 시작, 표시 block, 우리 이름의 file). 사람이 우리 group에 더한 handler, 같은 이름의 사람 cline script, 다른 file을 가리키는 Muse 설정, 사람의 Hermes 승인은 남긴다. 글 형식(JSONC, TOML, YAML)은 우리 줄만 지워 놓기 전 byte로 돌아가고, JSON은 놓을 때처럼 다시 직렬화한다. 우리 것만 남았던 event key와 `hooks`, 우리 이름의 file(`lophn.json`, `lophn-hooks.json`, plugin file, cline script), 비게 된 file(`{}`, 빈 글)은 지운다. Codex는 우리 trust table을 지우고, 우리 group 뒤에 있던 다른 도구의 기록은 당겨진 위치의 key로 옮긴다(key가 바뀌면 Codex가 다시 trust하라고 한다). 사람의 handler가 섞인 Devin 항목처럼 offset으로 안전하게 고칠 수 없거나 파싱되지 않으면 아무것도 쓰지 않고 `failed`다. 누른 것이 허락이라 묻지 않고, 지운 뒤 이 실행에서는 터미널이 그 harness를 알아봐도 다시 묻지 않는다. 다음 실행에서는 거절처럼 다시 묻는다.
- **coding agent에게 가는 skill은 사람이 승인한 앱 공유의 public skill과, harness extension이 켜졌을 때의 내장 `lophn-agent` 하나다.** 사본은 `lophn harness sync-skills`(`packages/coding-agent/local/harness-run.ts`의 `runHarnessSyncSkills`)가 맞춘다. 읽는 것은 설정 `coding-agent.shared_apps`(앱 slug 목록. 앱 workspace의 agent가 청한 공유 요청을 사람이 coding agent까지 골라 승인할 때만 더해진다: `architecture/approval.md`)와 core read `app.skills`(`architecture/app-call.md`)다. 쓰는 곳은 hook이 놓인(`unchanged`) harness의 adapter `skill_dir`(사람 home 기준)이다: Claude Code `.claude/skills`, Codex·pi `.agents/skills`, OpenCode `.config/opencode/skills`. 다른 harness는 `skill_dir`이 null이라 사본이 없다. Codex와 pi는 폴더를 같이 쓰므로 하나라도 hook이 놓였으면 둔다. hook이 없는(`missing`) harness의 폴더에서는 lophn이 쓴 사본만 지우고, hook 상태를 못 읽은 폴더(`failed`)는 건드리지 않는다. 그 폴더를 쓸 수 없으면 `unavailable`이다.
- **사본에는 표시 file이 있고 lophn이 쓴 것만 덮고 지운다**(`packages/coding-agent/harnesses/skill-copies.ts`). skill 폴더마다 `.lophn-shared`(JSON `{app, release, files[]}`)를 두고, 표시가 있는 폴더만 덮고 지운다. 같은 이름의 폴더가 사람의 것이면(표시 없음) 건드리지 않고 건너뛰어 `skipped`로 알린다. 표시를 먼저 쓰므로 쓰다 멈춰도 다음에 우리 폴더로 알아본다. 지울 때는 표시 file에 적힌 file만 지우고(recursive가 아니다) 비게 된 폴더만 치워, 사람이 그 안에 넣은 file은 남는다. 폴더 이름은 `[A-Za-z0-9_][A-Za-z0-9_.-]*`, file 이름은 폴더 밖으로 못 나가는 것만 받는다(core가 준 값이라도 사람 home에 쓰는 일이라서다). 같은 이름을 두 앱이 내면 앞의 것(slug 순)만 쓴다. 내용이 같으면 다시 쓰지 않는다. `shared_apps`에서 slug가 빠지거나 앱의 active release가 그 skill을 public으로 내놓지 않으면 `app.skills`가 주지 않아 다음 sync가 사본을 지운다. `shared_apps`를 줄이는 화면은 없다.
- **사본은 core가 쓰지 않고 shell main이 CLI를 exec해서 맞춘다.** core는 data root 밖을 쓰지 않는다. shell main(`packages/shell/main/desktop/wiring/agent.ts`, `terminal/agent/skill-sync.ts`)이 부르는 때는 넷이다: core가 준비되었을 때 한 번(준비 신호를 받는 길이 없어 1초마다 상태를 보다가 starting을 벗어나 ready이면 부른다), 앱 view의 activation 신호(`AppViewChanged`의 reason `activation`. 앱을 가리지 않으므로 공유하지 않은 앱의 activation에도 돌지만 사본이 같으면 아무것도 쓰지 않는다), `SettingsChanged`의 keys에 `coding-agent.shared_apps`가 있을 때, hook을 놓거나 지운 뒤(사본이 hook이 놓인 harness를 따른다). 한 번에 하나만 돌고 도는 중에 온 요청은 끝난 뒤 한 번 더 돈다. 실패는 log만 남기고 부른 쪽을 막지 않는다. session 시작 hook은 core를 부르지 않으므로 쓰지 않는다.
- **`harness uninstall`은 lophn이 쓴 사본도 지운다.** 그 harness의 `skill_dir`에서 표시 있는 폴더를 치우고 지운 폴더를 출력 file 목록에 더한다. 같은 폴더를 쓰는 다른 harness의 hook이 남았으면 다음 sync가 다시 둔다.
- **설치는 전에 놓은 지운 skill의 얇은 사본도 지운다.** 지우는 이름은 상수 `RETIRED_SKILL_NAMES`(`lophn-build-app`, `lophn-repair`, `packages/coding-agent/harnesses/install.ts`)이고 패턴이나 목록 읽기로 고르지 않는다. 폴더에 `SKILL.md` 하나뿐이고, 그 글이 lophn이 쓰던 꼴과 byte까지 같고, `dry_run`이 아닐 때만 file 하나와 빈 폴더 하나를 지운다(recursive가 아니다). 사람이 고친 사본, 다른 file이 든 폴더, 다른 이름의 skill은 남긴다. 사람 home에 쓰는 일이라서다. 출력의 `skill` 칸은 이 지우기만 알린다. 옛 사본이 있는 사람은 `lophn harness install`을 한 번 돌려야 지워진다.
- **전역 hook은 lophn과 상관없는 harness 실행에서도 불린다.** lophn 터미널이 넣는 `LPN_TERMINAL_HOOK`이 없으면 launcher가 CLI를 띄우지 않고 끝나고, `lophn hook`도 stdin을 읽지 않고 아무것도 보내지 않은 채 성공한다. pi extension과 OpenCode plugin은 그 env가 없으면 hook을 등록하지 않는다. launcher는 CLI를 Electron의 Node로 띄운다(권한 flag 없음).

## harness agent

정의의 `runtime`이 harness 값인 agent는 lophn session을 갖되 run-loop가 돌리지 않는다. 입력(사람 메시지, call, run, step)은 shell main의 harness host가 그 harness의 headless CLI 명령으로 실행한다(`claude -p`, `codex exec`, `opencode run`). host는 extension `harness`(`packages/shell/main/extensions/bundled/harness/`)이고 `ExtensionContext`로만 lophn에 닿는다([extension.md](extension.md)).

```
Router ─ session.transport = harness ─▶ harness queue(core 메모리, run-loop queue와 따로)
extension harness(1초마다) ─ ctx.core, 사람 권한 ─▶ harness/take → start_turn
   ─ agents/read(permissions.deny), projects/get·apps/get(workspace 폴더) ─▶ 권한 flag, cwd
   ─ ctx.spawn(<harness headless 명령>, cwd = workspace 폴더, stdin 닫음) ─ 줄마다 parser ─▶ harness/record(글, harness_tool)
   ─ 1초마다 turns/read: core가 닫았으면(멈춤) process를 끈다 ─ process 끝 ─▶ finish_turn
                                          └▶ harness/set_external_id (harness의 session id, resume에 쓴다)
TurnEnded ─▶ result call이면 마지막 기록 메시지가 답(bare 자동 답과 같은 길, wiring/bare-reply.ts)
```

- **켜기는 설정 `extensions.harness.enabled`(Settings › System › Extensions, 기본 꺼짐)다.** 꺼져 있으면 extension을 load하지 않고, harness runtime session을 열지 않고(`unavailable`), 그 session으로 가는 메시지·call·step도 `unavailable`이며, 새 turn을 여는 host route(`take`, `start_turn`)도 `unavailable`이다. 기록·끝냄·외부 id route는 꺼져 있어도 받아, 끌 때 돌던 turn이 끝난다. 답·reaction·알림은 받아 열린 call이 닫힌다. 편집기의 runtime 고르기는 켜졌을 때만 harness 값을 내고, 이미 harness인 agent는 꺼져 있어도 그 값을 보인다.
- **session의 harness는 열 때 정해 바뀌지 않는다.** `sessions.harness`(trigger로 고정)와 외부 session id `sessions.harness_session`이 ledger step `lophn-agent.sessions.harness`다. 외부 id는 machine 전용 command `BindHarnessSession`만 쓰고, runtime이 harness가 아닌 session은 고치지 못한다(`packages/core/lophn-agent/session/harness_test.ts`).
- **host route는 사람 token(actor user)만, runtime이 harness인 session만 고친다**(`packages/protocol/lophn-agent/harness-host.ts`, `packages/core/main/daemon/wiring/harness.ts`). memory route라 renderer 통로에는 없다. 기록은 core 안 machine 자격으로 기존 command(StartTurn, RecordMessage, FinishTurn)에 남는다. turn은 시작 → 기록 → 끝 순서이고 `TurnEnded`는 한 번이다. 재시작하면 끝나지 않은 harness turn은 interrupted(restarted)로 끝나고 늦은 FinishTurn은 `conflict`다(`packages/core/lophn-agent/run-loop/harness-turn_test.ts`).
- **harness가 쓴 tool은 lophn이 실행한 것이 아니다.** 메시지 part `harness_tool {name, summary, status}`로만 남고 gate·rewind의 tool-call chain에 들지 않는다. 기록마다 `MessageRecorded`(`model_call: null`)를 내 대화가 바로 갱신된다.
- **headless 명령, parser, 권한 표는 harness마다 `HARNESS_ADAPTERS[id].headless` 한 항목이다**(`packages/protocol/coding-agent/headless/`). parser는 순수 함수이고 실제 녹화에서 만든 fixture로 본다(`headless_test.ts`, Claude Code 2.1.318, codex-cli 0.166.0, opencode 2.1.4).
  - Claude Code: `claude -p --output-format stream-json --verbose --permission-mode acceptEdits [--resume <id>] [--disallowed-tools …] -- <prompt>`. 편집은 묻지 않고 Bash는 거절된다. 정의의 deny `lophn(<slug> <command>)`는 `Bash(lophn <slug> <command>)`와 그 뒤 인자 꼴의 disallow다.
  - Codex: `codex exec --json --skip-git-repo-check -s workspace-write -- <prompt>`, 이어 가기는 `codex exec resume … -c sandbox_mode="workspace-write" -- <id> <prompt>`. stdin 끝을 기다리므로 host가 띄우자마자 닫는다.
  - opencode: `opencode run --standalone --format json [--session <id>] <prompt>`. 권한 flag가 없어 사람의 opencode 설정대로 돈다(사람, 2026-11-04). 끝 event가 없어 process의 exit code가 끝이다.
  - 전부 허락(`bypassPermissions`, `danger-full-access`)은 쓰지 않는다. deny를 옮길 수 없는 harness(Codex, opencode)는 정의에 deny가 있으면 띄우지 않고 그 turn을 `configuration_unavailable`로 끝낸다(대화에 이유 한 줄).
- **harness는 turn 자격으로 자기 shell에서 `lophn`을 부른다(사람, 2026-11-04: CLI를 쓰고 skill을 배포한다).** `harness/start_turn`이 그 session·그 turn에만 쓰이는 agent 자격을 내고(`packages/core/main/daemon/wiring/harness-credential.ts`, 기존 `CredentialRegistry`), host가 spawn env `LOPHN_AGENT_CREDENTIAL`(`packages/protocol/coding-agent/headless/env.ts`)에 넣는다. 범위는 그 workspace 종류의 `lophn` 명령 route뿐이고(`harnessOperations`, `workspaceOperations`의 부분, file·rewind·gate·ask route 없음) `TurnEnded`에 끝난다. CLI(`packages/cli/connection/client/token.ts`)는 그 env가 있으면 `run/user-token` 대신 쓴다. user token으로 `call.reply`·`call.send`는 지금처럼 `forbidden`이다(`harness-credential_test.ts`). host는 `LOPHN_CLI`가 절대 경로면 그 폴더를 PATH 앞에 두어 개발 launcher가 `lophn`이 되고, extension이 띄우는 process에는 shell main이 늘 `LOPHN_HOME`(그 shell의 data root)을 넣는다.
  - Claude Code는 `--allowed-tools "Bash(lophn *)"`로 `lophn`만 허락한다. 그 밖의 Bash는 거절이고 deny가 allow보다 앞선다.
  - Codex `workspace-write`는 loopback을 포함한 network를 막아(seccomp가 `connect`를 막는다) CLI가 core에 닿지 못하므로 `-c sandbox_workspace_write.network_access=true`를 넣는다. 쓰기는 workspace 안 그대로이고 Codex가 돌리는 명령이 인터넷에도 닿는다(사람, 2026-11-04). loopback만 여는 옵션은 없고, core의 unix socket 하나만 permission profile로 여는 길은 남겨 두었다.
  - opencode는 사람의 opencode 권한 설정이 `lophn`을 허락해야 부른다.
  - 쓰는 법은 내장 skill `lophn-agent`(`packages/coding-agent/skills/lophn-agent.ts`)다. 받은 call의 tag 읽기, `call reply`·`call send`·`call cancel`, `session list`·`agent card`를 적고 turn 자격이 있을 때만 쓰라고 한다. `lophn harness sync-skills`가 설정 `extensions.harness.enabled`가 켜졌으면 hook 상태와 상관없이(켜기가 사람의 허락이다) Claude Code·Codex·OpenCode의 `skill_dir`에 앱 공유 skill과 같은 표시 file로 두고, 꺼지면 그 사본만 지운다. shell main은 `SettingsChanged`의 keys에 그 설정이 있을 때도 sync를 부른다.
- **cwd는 session workspace의 폴더다.** project는 첫 폴더, 앱은 source 폴더(없으면 첫 폴더)다. 폴더가 없는 workspace(home, 폴더 없는 project·app)에서는 띄우지 않는다. 띄우는 env는 shell main의 것이고(harness가 자기 API key를 쓴다) lophn user token을 넣지 않는다.
- **끝은 parser의 끝 event나 exit code다.** 실패는 `model_error`, 시작하지 못하면 `target_unavailable`, 글 없이 끝나면 `no_answer`다. 사람이 멈추거나 core가 turn을 닫으면 host가 process를 끈다. 사람 메시지의 이미지는 `[image: <mime> not passed to the harness]` 글로 바뀐다.
- **run-loop는 harness 입력을 돌리지 않는다.** 닿으면 turn을 시작하지 않고 `target_unavailable`로 닫는다(`run-loop/prepare.ts`). 켤 때 접수만 된 사람 메시지는 harness wiring이 harness queue에 되돌린다.

## 왜 이 모양인가

- **harness는 shell host가 CLI 명령으로 돌린다(사람, 2026-11-04).** harness가 programmatic 실행을 공식으로 지원하므로 workflow와 job처럼 사람 없이 돌려도 된다. core는 사람의 PATH와 실행 파일을 모르므로 host는 shell main에 있고, core에는 route로만 붙는다. 이어 가기는 harness 자신의 session id라 TUI 열기와 다음 입력이 같은 대화를 resume한다.
- **coding session 층을 지웠다(사람, 2026-10-28).** lophn이 coding agent를 터미널에 띄우고 token·MCP endpoint·메시지 줄로 맡기던 층은 부르는 곳이 없었다. 앱 일은 그 앱 workspace의 lophn agent가 직접 지었고, 그 뒤 role이 없어져 맡길 쪽도 사라졌다. 지운 것: core apps module의 coding 폴더와 표 셋, coding token, `POST /mcp`, Router의 coding transport, shell의 coding 터미널 탭과 대기 목록 항목, CLI의 token 명령(`message send`, `app …`, `package …`). 다시 필요해지면 새로 설계한다. 사람이 연 터미널이 쓰는 hook, 감지, 설치는 남겼다(사람, 2026-10-26).
- **hook으로 상태를 안다.** herdr는 화면을 읽어 짐작하고 orca는 hook이 없으면 title 글리프로 짐작하지만 lophn은 짐작하지 않는다. 그 대가로 Claude Code를 Esc로 끊으면 `Stop`이 오지 않는다. 끊김 신호가 없는 harness에 한해 shell main의 터미널 상태는 사람이 친 단독 Esc·Ctrl-C를 보고 unknown으로 내린다. 끊김을 hook으로 알리는 harness(`interrupt_keys`가 빈 것)는 이 key를 보지 않는다([terminal-agent.md](terminal-agent.md)). turn 끝 신호가 있는 제품은 Claude Code `Stop`·`StopFailure`, Codex `Stop`·`Interrupt`(0.150 이상, interrupted), OpenCode `session.status` idle(전역 plugin이 root session의 event만 넘긴다. 뒤따르는 deprecated `session.idle`은 같은 끝이라 듣지 않는다. 2.x는 plugin이 `{id, setup}` default export로 event를 직접 구독하고 `session.execution.started`·`succeeded`·`failed`·`interrupted`가 `session.status` busy·idle로, `permission.asked`·`replied`는 그대로 1.x 모양으로 바뀌어 넘어가므로 shell main은 두 판을 구별하지 않는다. 2.x는 plugin을 공유 background service가 돌려 터미널 env가 닿지 않으므로 터미널이 `opencode --standalone`으로 띄운다), pi `agent_settled`다. pi는 `agent_end` 뒤에 retry와 compaction이 남을 수 있어 끝이 확정되는 쪽을 쓴다. plugin·extension 본문은 turn 끝 payload에 마지막 assistant 답(text block만)을 `lophn_message`로 싣는다. OpenCode 계열은 completed idle에서 1.x는 `client.session.messages`, 2.x는 `ctx.session.context`로 읽고(못 읽으면 뺀다), pi는 `agent_end`의 `messages`를 기억했다가 `agent_settled`에, omp·amp는 `agent_end`·`agent.end`의 `messages`에서 뽑는다.
- **coding agent에게는 사본을 두고 lophn agent에게는 두지 않는다(agent).** coding agent는 lophn 안에 정의가 없고 사람의 user token으로 부르므로 줄 것은 앎뿐이고, 자기 skill 폴더만 읽는다. lophn agent는 bundle을 바로 읽으면 되고(`architecture/agent-definition.md`) 사본은 동기화가 틀릴 길만 늘린다. 쓸 harness는 hook을 놓은 harness로 정해, 사람이 hook을 허락한 도구에만 lophn이 파일을 둔다.
- **hook을 앱 폴더가 아니라 전역에 한 번 놓는다.** 열 때마다 앱 폴더에 놓으면 앱 source에 harness 설정이 섞이고(release 제외 목록이 따라온다), 사람이 고친 file을 지키려고 hash 기록이 필요하다. 전역에 한 번 놓고 사람에게 묻는 쪽이 단순하다. 감지 표는 orca, emdash, herdr 가운데 둘 이상이 지원하는 25종이다(`HARNESS_IDS`). Gemini CLI는 Google이 Antigravity로 옮겨 지웠고 OpenClaw는 지원하는 곳이 없어 지웠다.
- **CLI 출력을 data fence로 감싸지 않는다.** 사용자 앱과 사람이 쓴 글은 공격자로 보지 않는다(AGENTS.md). 줄로 풀어 쓰고 `--json`이면 JSON 하나다.
