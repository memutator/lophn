# problems/grouping

운영 보고를 앱별 같은 문제로 모으고 열림·고치는 중·닫힘을 구별하며, 기간 제한 없는 같은 문제 참조와 App Engineer의 고정된 해석 연결을 유지한다.

## 요구

### 묶기 기준

**[R1]** 유효한 운영 보고가 최소 1개 있는 경우에만 문제를 만들고 같은 앱의 같은 선언 problem code는 release·업무 데이터 대상이 달라도 한 문제로 모은다.
- 이유: ticket이나 가설은 발생 사실이 아니며 같은 코드 수리를 행마다 나누지 않는다.
- 확인: ticket만 만들면 문제가 없고 서로 다른 release와 데이터 행의 같은 code 보고는 하나의 문제에서 읽힌다.
- 의도: problems#I3

**[R2]** 예외는 오류 이름과 당시 release source map으로 찾은 상위 최대 3개 앱 source frame의 상대 위치·함수로 만든 전체 SHA-256 지문으로 묶는다.
- 이유: 같은 예외를 코드 이동이나 업무 값에 따라 쪼개지 않는다.
- 확인: 같은 함수의 줄·열·업무 message만 바꾼 예외는 같은 문제이고 다른 상위 앱 위치의 오류는 다른 문제다.
- 의도: problems#I3

**[R3]** 예외 지문에서 줄·열·절대 경로·오류 message·업무 값·SDK와 runtime frame은 빼며 앱 frame이 없으면 발생마다 별도 문제로 남긴다.
- 이유: 오류 이름 하나만으로 관계없는 원인을 합치지 않는다.
- 확인: 앱 frame이 없는 같은 TypeError 2개가 자동 합쳐지지 않고 source map이 없으면 위치 불확실성이 보인다.
- 의도: problems#I3

**[R4]** 잘못된 앱 보고는 안전하게 남길 수 있는 잘못된 code별로 묶고 그 값을 안전하게 알 수 없으면 원래 발생별로 분리한다.
- 이유: 미선언 경로의 반복 문제를 찾되 안전하지 않은 code 원문을 grouping 근거로 저장하지 않는다.
- 확인: 같은 안전한 미선언 이름은 한 문제이고 redaction으로 구별 불가한 발생들은 자동 합쳐지지 않는다.
- 의도: problems#I3

**[R5]** 같은 code나 지문으로 묶였다는 사실은 분류일 뿐 같은 근본 원인이 증명됐다는 뜻으로 표시하지 않는다.
- 이유: 수리 가설이 관측 사실을 대신하지 않아야 한다.
- 확인: 문제 상세에서 보고와 원인 가설이 구별되고 지문 일치만으로 원인이 확정되지 않는다.
- 의도: problems#I3

### feedback과 비운영 보고

**[R6]** feedback은 사람이 같은 앱의 기존 문제를 명시적으로 선택한 경우만 덧붙이고 그 외에는 각각 별도 문제로 만든다.
- 이유: 같은 화면이나 비슷한 시각은 제보가 같은 결함이라는 증거가 아니다.
- 확인: 같은 앱·화면의 비슷한 글 2개는 별도 문제이며 명시적 선택 제보만 기존 문제에 연결된다.
- 의도: problems#I3

**[R7]** preview와 test의 진단은 운영 문제의 묶기·재발에서 제외한다.
- 이유: 의도적으로 실패를 재현하는 일이 운영 재발을 만들면 안 된다.
- 확인: preview·test 예외를 보고해도 운영 문제 상태는 바뀌지 않는다.
- 의도: problems#I3, problems#I5

### 진행과 재발

**[R8]** 문제 진행은 열림·고치는 중·닫힘 3가지만 제공하고 문제당 열린 repair ticket은 최대 1개만 연결한다.
- 이유: 작업 진행과 종료 근거를 여러 겹의 문제 상태로 복제하지 않는다.
- 확인: 문제 상세는 3가지 진행만 보이고 같은 문제에 열린 repair ticket 2개를 연결하려 하면 거절된다.
- 의도: problems#I3

**[R9]** 고치는 중은 열린 repair ticket의 유효한 claim이 있을 때만 표시하고 claim 해제·만료·완료 보고·취소 뒤 닫힘 근거가 없으면 열림으로 표시한다.
- 이유: ticket 없는 직접 수리와 완료 주장을 해결 또는 현재 담당으로 과장하지 않는다.
- 확인: ticket 생성·직접 고친 기록은 열림이고 유효 claim 뒤만 고치는 중이며 claim 종료와 검사 실패를 새 claim처럼 처리하지 않는다.
- 의도: problems#I3

**[R10]** 닫힌 문제도 기간 상한 없이 같은 묶기 기준과 문제 참조를 유지하고 재발 처리 자체는 problems/closing을 따른다.
- 이유: 14일이 지난 재발이 지난 수리와 단절되어서는 안 된다.
- 확인: 닫힌 지 15일 이후 같은 증상이 와도 기존 문제로 연결되고 이전 보고·고친 기록·닫힘 근거를 계속 읽을 수 있다.
- 의도: problems#I3, problems#I5

### 목록과 상세

**[R11]** 문제 목록은 앱·열림·고치는 중·닫힘으로 찾을 수 있고 기본으로 앱·증상·진행과 필요한 다음 행동만 보여 주며 최근 보고와 열린 ticket을 기준으로 한 탐색 및 발생 수·처음과 최근 시각·당시 release는 펼친 상세에서 읽을 수 있다.
- 이유: 현재 해야 할 일과 과거 관측을 함께 찾을 수 있어야 한다.
- 확인: 앱과 상태별로 필터한 목록에서 최근 발생을 찾고 문제를 선택하면 동일 보고에 기반한 수·시각·release를 읽을 수 있다.
- 의도: problems#I3, shell#I8

**[R12]** 앱 카드는 지금 필요한 문제 안내만 표시하고 문제 상세에는 진행·실제 담당·필요한 사람 조치를 먼저 보여 주며 문제 수와 당시 증거·현재 수리 작업은 펼친 상세에서 읽을 수 있고 ticket은 사람이 아는 en 작업 상태로 설명하되 claim·기한·연결 식별자는 사용자용 상세에도 노출하지 않는다.
- 이유: 앱의 문제가 몇 개인지와 실제 담당을 혼동 없이 알아야 한다.
- 확인: 직접 수리 중인 문제에 가짜 담당을 표시하지 않고 열린 수와 상세의 상태·ticket·조치가 일치한다.
- 의도: problems#I3, shell#I8

### 해석 연결

**[R13]** 담당 App Engineer는 사실과 원인 가설을 구별한 해석 문서의 고정 판·절을 문제에 연결하거나 해제할 수 있지만 문제 진행 상태는 바꾸지 못한다.
- 이유: 조사 내용을 발견할 수 있어야 하지만 해석은 닫힘 근거가 아니다.
- 확인: 읽을 수 있는 고정 판을 연결하면 같은 판으로 돌아가고 상태는 같으며 기존 연결은 lophn-agent/revert로 복원할 수 있다.
- 의도: problems#I3

**[R14]** 해석 변경과 ticket 상태 갱신은 읽은 문제 기준이 아직 같을 때만 적용하고 이전 해석 참조와 관측 이력을 보존한다.
- 이유: 동시 작업이 서로의 현재 연결을 덮어쓰지 않도록 한다.
- 확인: 서로 같은 이전 상태를 읽은 2개 변경 중 뒤의 낡은 변경은 충돌하고 이전 참조를 다시 찾을 수 있다.
- 의도: problems#I3

## 열린 질문

- problems/grouping#Q1 사람의 문제 병합·분리 기능을 추가할까.
- problems/grouping#Q2 앱 사이 공통 원인 관계를 사람에게 연결하게 할까.
- problems/grouping#Q3 feedback을 기존 문제로 묶는 방식은 사람의 명시적 선택으로 유지할까.

## 버린 것

- 대상 ID 128자·이름 60자·code당 50대상 이후 기타 대상 합치기는 업무 대상 없는 grouping 모델이므로 버린다.
- 업무 message를 200자로 정규화해 지문에 넣는 규칙은 message 자체를 지문에서 빼므로 버린다.
- 별도 Episode 및 앱·SDK·플랫폼·공유 자원 담당 이전 문제 모델은 앱 문제·보고·event와 platform/diagnostics 구분으로 충분하므로 버린다.
- App Engineer 해석 연결의 중복 요구는 이 문서의 같은 약속으로 대신하므로 별도 요구로 두지 않는다.
