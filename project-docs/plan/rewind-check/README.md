# rewind-check: app test의 rewind 검사를 실제로 성공한 write 호출로 증명한다

- 목표:
  - app test harness가 앱을 부르는 wire 회귀를 고친다. 지금 main에서 `rewind`·`examples` 검사가 모든 앱에서 깨져 있다.
  - `rewind` 검사가 만든 입력 대신 ticket `examples`가 실제로 성공시킨 write 호출의 changeset으로 되돌리기를 증명하게 한다. 증명하지 못한 write tool은 activation을 막지 않고 problem으로 알린다.
- 재료:
  - `project-docs/issues/activation.md`의 "write app-api의 rewind 검사가 fail로 나온다"(다시 정한 것: 사람, 2026-10-19)
  - `project-docs/architecture/app-call.md`(changeset, rewind), `project-docs/architecture/activation.md`, `project-docs/architecture/coding-agent.md`(ticket check, examples)
  - `project-docs/module-catalog.yaml`의 `packages/core/problems`
- 진단(lead, 2026-10-19):
  - template `add_item`의 rewind 실패는 입력 문제가 아니다. `packages/core/problems/tests/work/app-driver.ts`가 control socket 호출 셋(`rejectsInvalidInput`, `rewind`, `call`)에 계획 `domain-tools`가 process wire에서 지운 `context.project: null`을 아직 싣는다. 앱 runtime의 `parseProcessCall`(`packages/core/apps/runtime/entrypoint/wire.ts`)이 요청 전체를 400 `invalid_input "call request is invalid"`로 거절해 handler가 돌지 않는다. 같은 원인으로 `examples`의 모든 호출이 실패하고, `blueprint_handler_match`는 그 400을 handler 거절로 보아 공짜로 통과한다. 세 줄을 지운 사본에서 template 앱의 app test는 통과했다.
  - 검사 detail: coding token의 `detail:true`는 설계대로 막히지만 허락돼도 hash만 돌려준다. check별 이유가 든 observations blob은 `general_read:false`라 누구도 못 읽는다. user token은 `detail:false`도 `forbidden`이다(`packages/core/problems/tests/reads.ts`의 `sameApp`이 app target을 요구하는데 user token에는 없다).
  - 호출마다 changeset: 앱 자신의 test(`tests/*.ts`)는 harness 밖 in-process라 changeset이 없다. ticket `examples`는 앱 응답에 이미 write의 changeset이 실리고 `app-driver.ts`의 `call()`이 버릴 뿐이다.
- 정한 것(planner, 진단 뒤):
  - 증명 재료는 ticket `examples`의 write 호출 changeset이다. 앱 자신의 test는 쓰지 않는다.
  - app test의 `rewind`는 지금처럼 만든 입력으로 write tool을 부른다. 그 호출이 성공했는데 되돌리기가 틀리면 fail이다. 호출 자체가 실패하면 fail이 아니라 "증명 못 함"이고 activation을 막지 않는다.
  - examples run과 app test run은 따로 돈다. 판정을 합치지 않는다. examples의 되돌리기는 examples 검사 안에서 판정한다.
  - "증명 못 함"은 examples ticket일 때만 problem으로 알린다: examples run이 끝날 때 같은 (app, bundle_hash) app test의 `unproven` − 그 examples가 증명한 tool. examples가 아닌 ticket은 app test 증거와 pass 이유 한 줄로만 남긴다. activation 때 알리기는 이슈로 둔다(`project-docs/issues/activation.md`).
  - tool 선언에 fixture 칸은 두지 않는다.
  - user token의 `forbidden`(`sameApp`)은 이 계획에서 고친다(`rc-user-read`). observations blob을 아무도 못 읽는 것은 defect 이슈로 둔다.
- 범위 밖: 앱 자신의 test를 harness로 돌리기, observations blob 읽기 열기, e2e 돌리기.
- 단위와 순서: `tasks/*.md`가 정한다. task id는 `rc-`로 시작한다.
  - 모두 wave 1이다. 사람의 지시로 소유가 겹치지 않는 task를 최대한 동시에 돌린다. land는 merge될 때마다 한다.
