# app-call

앱은 선언에서 두 층을 내놓는다. 화면과 앱 자신이 쓰는 저수준 동작인 operation(`operations[]`)과, 앱이 골라 바깥에 내놓는 command(`commands[]`)다. operation을 부르는 길은 사람이 연 앱 화면과 그 앱 workspace session의 preview다. command를 부르는 길은 넷이다: agent의 명령 `lophn <app> <command>`(`<app>`은 앱 slug), 다른 앱, job이 연 tool run(program), flow instance가 연 tool run(flow). 어느 길이든 같은 판정(부른 쪽 확인, 막기)과 같은 기록(invocation)과 같은 직렬화(write는 앱마다 하나씩)를 거쳐야 한다. 그래야 "이 호출이 앱 data에 한 일"을 호출 단위로 알고, 사람이 고른 시점으로 앱 data를 되돌릴 수 있다(rewind). 그래서 모든 호출은 core를 지나고, write 동안의 앱 DB 변경은 changeset으로 떠서 invocation에 붙여 보관한다.

## 흐름

```
 person ── shell 앱 화면 (operation) ──┐
 agent  ── lophn <app> <command> ──────┼─ core-api(app.call_tool) ─▶ 호출 경로 (core/apps/calls)
 app    ── sdk ─ broker (command) ─────┤              1 부른 쪽 확인        (credential, 도는 turn·부모 invocation·job run·instance)
 program ── job run의 tool run ─────────┤   (core 안 run 연산만. route로는 못 연다)
 flow  ── instance의 tool run ──────────┘   (같다)
                                             2 막기               agent는 할당(judge), program은 통과(사람이 등록을 승인한 job), flow는 PM의 할당(unattended)과 비공개 거르기,
                                                                  앱은 active 앱 grant의 app.call. 묻지 않는다
                                             3 write·external이면 앱별 줄을 얻는다. read는 바로
                                             4 invocation 시작을 남긴다        ─▶ storage (ledger + changeset blob)
                                             5 보낸다
                                                │ child-supervision-protocol (supervisor가 길만 이어 준다)
                                                ▼
                                    앱 process (sdk runtime): handler 실행
                                    write·external 동안만 SQLite session ─▶ 결과와 changeset을 응답에 싣는다
                                                │
                                             6 invocation을 끝으로 남기고 changeset을 붙인다 ─▶ 부른 쪽에 결과

 rewind (사람만): 되돌릴 목록 ─▶ 앱 접수 닫기·drain ─▶ changeset을 최신부터 뒤집기(base)
                  ─▶ 앱 process가 한 transaction으로 적용(sdk) ─▶ 되돌림 표시, 접수 열기
 session rewind에서 사람이 앱을 고르면 같은 rewind로 간다 (workspace-session)
```

앱이 무엇을 했는지는 호출 기록(invocation)과 앱 log가 말해 준다. log는 앱마다 file 하나로 쌓고 supervisor 한 곳만 쓴다.

```
 앱 stdout·stderr (SDK reportProblem의 줄 포함, `[inv=<id>] ` 머리는 떼어 invocation 칸에) ─┐
 잡히지 않은 예외 (SDK가 frame 풀이 전의 stack을 broker로 보냄) ──────────────────────────┤
 앱 process의 비정상 종료 (supervisor가 관측) ───────────────────┤
 화면 오류 ── shell main ─ core(app.log_view_error) ─ supervisor ─┤
                                                                 ▼
                       app supervisor: 줄마다 redaction ─▶ 300자로 자름 ─▶ 줄 하나 ({ at, invocation, text })
                                                                 ▼
              <data root>/apps/<app>/logs/app.log  ── 8 MiB를 넘길 줄이면 app.log.1로 옮기고 새로 쓴다
 읽기: app.logs ─ core가 app.log.1, app.log를 직접 읽어 거르고 알려진 secret 값을 한 번 더 지운다 (supervisor가 없어도 읽힌다)
```

## 지키는 것

- 선언은 두 목록이다. operation은 `{name, title, effect}`이고 입력 schema가 없다(입력 검사는 앱 code의 일이다). command는 `{name, description, inputSchema, effect, public}`이다(`@lophn/declaration` 4.0.0). 두 목록을 합쳐 이름이 하나이고 handler는 이름 하나로 등록한다(`@lophn/cap-tool`의 `handle`). `effect`(`read`, `write`, `external`)는 program이 강제하고(write 줄, 기록), command의 `public`은 그 앱 workspace 밖에 보이는지다. 이름은 1~64자 `[A-Za-z0-9_.-]`이고 command schema의 root는 `object`다(인자가 없으면 `inputSchema: null`). agent wire 이름 `<slug>_<command>`의 64자와 겹침은 slug를 아는 `declaration.check`와 release 기록이 검사한다(SDK의 `defineApp`은 slug를 모른다).
- **선언의 `skills`는 앱이 내놓는 skill이다(`@lophn/declaration` 2.1.0, 없어도 되는 칸).** 항목은 `{name, public, commands}`다. `name`은 skill 폴더 이름 규칙(소문자·숫자·`-`, 64자까지)이고 겹치지 못하며, `commands`는 이 선언의 command 이름이다. `public`이 true인 skill은 다른 agent에게도 가므로 `commands`가 모두 public command여야 한다. 없는 command나 비공개 command를 쓰는 public skill은 선언 오류다. 칸이 없거나 비면 정본 json에 칸을 두지 않아 옛 선언의 hash가 그대로다. `domain` 칸을 지운 3.0.0(0.18.0) 뒤로는 옛 판으로 봉인한 bundle이 뜨지 않고 다시 release해야 한다. 판을 올린 `@lophn/app-ui`도 2.1.0이고, 옛 2.0.0 사본은 이미 쓰던 data root에만 남는다(새 data root에는 없다: `project-docs/issues/app-call.md`).
  - skill 본문은 앱 source의 commit 파일 `.lophn/skills/<name>/SKILL.md`다. template의 `.gitignore`는 SDK 설치 사본 `.lophn/sdk/`만 뺀다(옛 앱은 `.lophn/` 전체를 뺀 것을 앱 agent가 고친다).
  - release 준비는 선언한 skill마다(공개 여부와 관계없이) `.lophn/skills/<name>/SKILL.md`가 commit에 있는지 본다. 없으면 `failed`이고 이유에 `.gitignore`가 `.lophn/`을 통째로 빼면 `.lophn/sdk/`로 바꾸라고 싣는다.
  - 공개였던 skill을 지우거나 비공개로 바꾸는 release는 막지 않는다. `release.prepare`가 결과의 `removed_public_skills`에 그 skill을 싣는다(`removedPublicSkillsOf`, `packages/core/apps/releases/public-tools.ts`). skill이 부르는 command를 지우는 일은 `removed_public_tools`가 따로 싣는다.
- **공유되는 skill은 active release의 것이고 core read `app.skills`가 읽는다(`apps/skills`, actors user·machine).** 입력은 앱 slug 목록(64개까지)이고 slug마다 active release 선언의 `skills[].public`인 skill을 bundle 사본의 `.lophn/skills/<name>/`에서 읽는다. 선언에 없는 폴더는 열지 않는다. 없는 slug, 보관한 앱, active release가 없는 앱, 읽을 수 없는 skill(폴더 없음, 큼, 머리 틀림, 폴더 이름과 `name`이 다름, bundle 밖을 가리키는 symlink)은 오류 없이 뺀다. 결과는 skill마다 `{app, slug, release, name, description, skill_md, files}`이고 `skill_md`는 SKILL.md 전체, `files`는 옆에 딸린 `.md`다. 같은 이름을 두 앱이 내면 받는 쪽이 slug 순으로 정한다. 파일을 읽으므로 메인 스레드 read다(`appSkillsRead`, `packages/core/apps/routes.ts`). 읽는 쪽은 둘이다: 할당받은 agent(`architecture/agent-definition.md`)와 coding agent의 사본(`architecture/coding-agent.md`).
- **archived 앱은 agent에게 없는 앱이다(사람, 2026-11-07).** agent actor가 archived 앱을 읽거나 부르면 없는 앱과 같은 `not_found`이고, 목록은 그 앱을 뺀다. 되살리기가 사람의 화면에서 일어나므로 사람(user)은 계속 본다. 필터는 `authorizeApp`(`packages/core/apps/registration/model.ts`) 한 곳이다. 앱 read·command가 모두 이것을 거치므로 `app read|status|logs|invocations|tools`, release 목록·읽기, rewind가 한 번에 닫힌다. 이 밖의 길 셋만 따로 한다: `app.usage`의 앱 하나 읽기(`archivedToAgent`), release 준비와 `declaration.check`(`releaseGate`, `packages/core/apps/control.ts`), 앱 command 호출(`calls/service.ts`의 `app_archived`는 agent에게 `not_found`로 바뀌고 사람 화면에는 그대로 `denied`다). `app.tool_index`, `app.skills`, 공유 skill·command 목록은 처음부터 active만 읽는다. `lophn package read <name> --version`의 사용처는 active 앱의 지금 켜진 release만 센다(`loadUsages`). 지난 release와 archived 앱은 그 SDK 판으로 더 돌지 않아, 센다면 home lophn이 고칠 곳을 잘못 짚는다.
- **보관한 앱은 사람이 영구히 지울 수 있다(`app.delete`, 사람, 2026-11-07).** 보관 → 지움 두 걸음이고 active 앱은 `conflict`다. actor는 user뿐이다(agent는 `forbidden`). 지운 뒤에는 되돌릴 수 없다.
  - **한 Tx에서 ledger를 먼저 지운다**(`registration/delete.ts`의 `eraseApp`, 앱 workspace에 딸린 다른 module의 기록은 `appRemnantsEraser` port, 구현은 `core/main/daemon/wiring/apps-delete.ts`). 순서: blob 참조(복구본, changeset, annotation screenshot) → annotation → 앱 알림 → `activation_consents`·`activation_requests`·`app_data_records`·`invocations`·`app_rewinds`·`grants`·`releases`·`app_folders`·`app_icons`·`apps` 행. 앞의 다섯 표와 `apps`·`releases`·`grants`는 DELETE trigger가 평소 막으므로 새 schema step `apps.delete.erase-windows`가 trigger를 erase window 조건부로 바꿨다(session delete와 같은 장치, `storage/ledger/erase.ts`). 창은 이 command의 Tx 안에서만 열린다.
  - port 구현이 같은 Tx에서 지우는 것: 그 앱 workspace의 session 전부(`DeleteSession`을 `tx.call`로 불러 turn 닫기, 되돌리기 기록, blob 참조까지 session delete 그대로), 그 앱에 범위가 있는 agent 정의(`DeleteAgent`), 다른 agent의 할당(정의 파일 `apps`와 deny 규칙에서 이 앱을 뺀다), 그 앱을 부르는 job과 그 앱 workspace가 만든 job(`eraseJobsOfApp`), 열린 앱 공유 요청. 파일 할당 정리는 앱 행이 있을 때 해야 deny 규칙을 풀 수 있어 앱 행보다 먼저다.
  - **그 앱의 process가 지금 살아 있으면(멈추는 중 포함) `unavailable`이다.** 쓰기 앞 처리기가 보관한 앱에 대해 살아 있는 supervisor에 `observe`로 물어 process가 있을 때만 거절한다. ledger의 마지막 `AppStarted`는 보지 않는다: core가 꺼질 때는 `AppStopped`를 남기지 않아, 켜져 있다 꺼진 뒤 보관한 앱에 옛 사실이 영영 남기 때문이다. supervisor에 닿지 못하면 자식도 없는 것으로 본다. 살아 있는 preview는 먼저 멈춘다.
  - **commit 뒤 파일과 설정을 정리한다**(같은 처리기). `<data>/apps/<app>/`(source 저장소, bundle, data DB, log, preview)를 지우고(읽기 전용 폴더가 있어도), 지운 session의 `tool-results/<session>`과 되돌리기 저장소를 지우고, 설정에서 이 앱을 가리키는 것을 뺀다(`shell.quick_launch`의 고정, `shell.app_launch`의 `<app>:*`, `shell.sidebar_panels_off`·`shell.tray_off`, coding agent 공유 slug). `source_path`를 data root 밖 폴더로 이은 앱은 그 폴더를 지우지 않는다(사람의 폴더다). 끊기면 ledger는 이미 지워져 앱은 없고 남는 것은 이름 없는 폴더뿐이다(처리기가 실패를 log로 남긴다).
  - **shell은 남지 않는 event `AppRemoved`를 받아 정리한다.** main이 browser 저장소(`persist:app-<app>:live`와 `persist:app-<app>:preview-*` partition: 저장소를 비우고 폴더를 지운다), 그 앱 workspace의 layout 파일, 전역 float 목록의 그 앱 float을 지우고, 열린 창의 전역 float 층도 그 앱의 float을 닫는다. 다른 workspace의 탭, 앱 panel, 고정 단추는 지우지 않는다: 보관한 앱은 이미 "앱이 없다" 안내(`app-panel.notice.app-gone`)나 건너뜀으로 그려지고 지운 앱도 같다. tray 값은 읽을 때 걸러져 사라지고(`appStatus` null) sdk status는 앱 목록에서 계산해 남는 것이 없다.
  - **지우지 않는 것.** `events`(immutable이라 `AppCreated` 등과 새 `AppDeleted`가 남는다)와 `command_results`; program 알림(`notices.source='program'`, 기록이다. 읽는 쪽이 `apps`를 left join하므로 앱 이름이 빈 채로 읽힌다); 이 앱이 다른 앱 command를 부른 기록(그 다른 앱의 `invocations` 행이라 남고 caller에 지운 앱 id만 남는다); session의 되돌리기 결과(`rewind_apps`)와 `tool_calls`의 `app_tool`(다른 workspace의 기록); job run 기록, `runs`, `workflow_lines`(이력); 공개 SDK package(`packages.owner_app`은 지운 앱 id를 가리킬 수 있다); secret 값(이름은 전역이라 다른 앱이 같은 이름을 쓴다); 이미 쓴 credential(`ended`로 닫히고, 열려 있어도 앱 대상 판정이 `not_found`다).
- operation은 사람(화면)과 그 앱 workspace session의 preview만 부른다. agent·다른 앱·job·flow가 operation을 부르면 handler에 보내기 전에 `denied(gate_blocked)`다(`packages/core/apps/calls/service.ts`). 화면용 저수준 동작이 agent 계약(할당, 결과 크기)에 묶이지 않게 하려는 것이다.
- **선언의 화면은 `{key, label, path, places, params?, tray?}`이고 `places`가 그 화면이 열릴 수 있는 자리다**(`packages/protocol/apps/declaration/types.ts`, `Place = tab | panel | card | sidebar | tray`). `tab`은 앱 workspace 본문과 앱 전용 창(둘 다 `tab` 자리를 가진 첫 화면), `panel`은 project dock·desk float·전역 float, `card`는 대화의 앱 카드, `sidebar`는 오른쪽 sidebar, `tray`는 작업 표시줄 tray다. `places`는 비어 있거나 겹칠 수 없다(`protocol/apps/declaration/tools.ts`). `params`는 화면이 받는 인자의 `InputSchema`(root는 object)이고 없으면 그 화면은 인자를 받지 않는다. `tray`는 tray popup의 크기 `{width?, height?}`(px, `@lophn/declaration` 4.1.0. 4.2.0부터 각 쪽은 숫자(고정)나 `{min?, max?}`(내용에 맞춤))이고 `places`에 `tray`가 있을 때만 둔다. 없는 칸은 정본 json에 두지 않아 옛 선언의 hash가 그대로다. 옛 `sizes`(`full`)는 `places`(`tab`)가 됐다: 저장된 release 행의 선언은 ledger step `apps.releases.declaration-places`가 옮기고(`declaration_hash`는 준비 때 낸 값이라 그대로), `sizes`로 봉인한 bundle은 manifest hash가 묶여 있어 뜨지 않으며 앱을 다시 release해야 한다.
  - 화면이 열릴 때 자리·인자·workspace가 정해지고 열려 있는 동안 바뀌지 않는다(dock·float·전역 float는 모두 `panel`이라 자리가 바뀌는 경우가 없다). view 열기 입력(`packages/shell/ipc/app-frame.ts`의 `appViewOpenSchema`. `mode`로 가르는 union이라 live는 `release` string이 필수이고 preview만 null일 수 있어, 판 없이 live를 여는 호출은 compile error다. main `checkOpen`이 같은 규칙으로 거절한다)이 `place`와 선택 `params`, `workspace`(`{kind: project | home | app, id, folders}`)를 싣고, `card`는 `place`가 `card`일 때만 있다. main(`app-frame/registry.ts`)이 `params`를 그 release 선언의 그 화면 `params` schema로 다시 검사한다(`validateParams`는 protocol의 `validateInput`을 `desktop/wiring/app-views.ts`가 넘긴다. main tsc가 protocol을 읽지 못해서다). `params`를 받지 않는 화면에 인자를 주거나 schema에 맞지 않으면 `invalid_input`이다. 값은 화면의 주소 query(`appEntryUrl`의 `place`, `params`, `workspace`)로만 가고 core로 넘기지 않는다.
  - 화면은 preload의 `lophnApp.place`(`{place, params, workspace}`)를 읽고, SDK `@lophn/app-ui`(2.9.0)의 `usePlace()`가 그것을 감싼다. query가 없거나 틀리면 `place`가 null이고 `params`는 `{}`다. 전역 float는 workspace를 주지 않아 `workspace`가 null이다.
  - agent의 `visual.show {app, view, params?}`도 `params`를 받는다. `view`는 `card` 자리를 가진 화면이어야 하고(아니면 `not_found`) `params`는 그 화면의 schema로 검사해(`cardParams`) 맞지 않으면 `invalid_input`이다. 통과한 값은 message의 `app_card` part와 ACP의 `AcpCard`에 `params`로 실려 카드 view의 인자가 된다(`AcpCard.params?`는 `@lophn/agent` 1.2.0).
- **앱 화면은 자기 앱 workspace의 agent session과 ACP로 이야기한다(`lophnApp.agent`의 `open`, `snapshot`, `onUpdate`, `send`).** 앱 화면에서 보낸 것은 operation처럼 그 앱을 쓰는 사람의 메시지라, shell main(`packages/shell/main/app-frame/app-agent.ts`)이 sender view에서 앱을 정하고 사람 자격(`coreInternal`)으로 core에 넘긴다. 따로 허락 단계가 없다(사람, 2026-11-04).
  - `open({agent, title?})`의 `agent`는 agent의 handle이다. main이 그 앱 workspace에서 보이는 agent(`agents/list`에 workspace를 준 결과: 전역과 그 앱의 범위 agent) 가운데 handle로 `agt_` id를 풀고, 못 찾으면(없거나 다른 workspace의 범위 agent) `not_found`다. 늘 그 view의 앱 workspace(`{kind: app, id}`)에 `OpenSession`으로 새 session을 연다. 보통 lophn session이라 sidebar와 채팅 탭에도 보인다. 앱 code는 workspace를 고르지 못한다. `title`을 주면 연 직후 ACP `rename`을 보내 session 제목으로 한다(`OpenSession`에 제목 칸이 없다. 이름을 못 붙여도 session은 열린 채다). 주지 않으면 제목은 첫 prompt 글이다.
  - **`send`는 ACP 입력 `send`, `stop`, `answer`, `rename`만 넘기고 나머지(`decide`, `rewind`, `fork`, `run_shell` …)는 core에 닿기 전에 `forbidden`이다.** 앱 code는 AI가 만든 code일 수 있고, 승인은 사람이 채팅 탭에서만 한다(사람, 2026-11-07). 허용 목록이라 ACP에 입력이 늘어도 앱은 닿지 못한다.
  - `snapshot`·`send`는 먼저 `ReadSession`으로 session의 workspace가 그 앱인지 보고, 아니면(home, project, 다른 앱, 없는 session) `forbidden`이다. 확인한 session은 view마다 기억한다(session의 workspace는 바뀌지 않는다). 보내는 body의 상한과 입력 검사는 `AcpSend`의 것이고 bridge는 자르지 않는다.
  - `AcpUpdated`는 main이 type으로 구독해(`ctx.relay`) 그 session을 열었거나 확인한 view로만 보낸다. 그래서 앱이 기억해 둔 session에 다시 붙을 때는 `snapshot`부터 읽어야 갱신이 온다(SDK의 `session` 옵션이 그렇게 한다). view가 새로 열리면 기억도 비어 있다.
  - bridge의 type은 `LophnAppAgent<State, Update, Input>`(`packages/protocol/shell/app-bridge-types.ts`)이고 SDK가 ACP의 `AcpState`·`AcpUpdate`·`AcpInput`을 채운다. 이 portable entry가 `protocol/acp`를 import하면 shell main tsc가 base까지 읽어 깨지기 때문이다.
  - test는 경계 둘이다: 앱 view는 다른 앱·project·home의 session을 읽지도 보내지도 못하고, 열기는 늘 그 앱 workspace이며, 갱신은 그 앱 workspace의 것만 받는다. 허용 목록 밖의 입력(`decide`가 대표)은 core route를 부르지 않고 `forbidden`이다(`packages/shell/main/app-frame/app-agent_test.ts`).
  - **앱 화면이 연 session은 알림 규칙이 다르다**(`packages/shell/main/notice/rule.ts`). 앱이 turn마다 agent를 부려 쓰므로(오목의 수마다 한 turn) turn 끝(완료·실패)은 알리지 않고 못 본 점(Finished)도 찍지 않는다. 승인·질문은 사람이 가야 풀리므로 그대로 알리되, 그 session을 쥔 앱 view가 focus 창에 보이면 보고 있는 것으로 쳐서 알리지 않는다(`looking`). "앱 화면이 연 session"은 `app-agent.ts`가 연 것과 `snapshot`·`send`로 앱 workspace의 것임을 확인한 것을 기억한 집합이고(`isAppSession`, view가 사라져도 앱 process 수명 동안 남는다), "쥔 view"는 view별 `owned`(`viewsOf`)다. 앱 view가 보이는지는 `EmbeddedView`가 보이는 동안 `NOTICE_VISIBLE_CHANNEL`에 `{view_session, visible}`로 알린다(`useReportViewVisible`). 그 session을 채팅 탭으로 보고 있을 때의 규칙은 그대로다(`architecture/terminal-agent.md`의 "알림").
  - 앱 code는 bridge를 직접 부르지 않고 SDK `@lophn/agent`(`packages/sdk/agent/`, 1.3.0, template이 의존으로 싣는다)를 쓴다. `useAgentSession({agent, title?, session?})`는 `session`이 없으면 첫 `send`에서 `title`로 session을 연다. 화면을 연 것만으로 열면 sidebar에 빈 session이 쌓인다. `session`을 주면 그 앱 workspace의 기존 session에 다시 붙는다: 바로 snapshot을 읽고 `send`도 거기로 가므로, 화면이 다시 load돼도(workspace를 떠났다 돌아온 경우) 앱이 저장한 id로 진행 중 turn의 답을 이어 받는다. `agent`나 `session`이 바뀌면 session을 바꾼다. `rename(title)`은 ACP `rename`이고, `reset()`은 지금 session을 잊어 다음 `send`가 새 session을 열게 한다(`close()`는 구독만 푼다). 보내는 중이거나 turn이 도는 동안(`state.turn`이 `ended`가 아닐 때)은 SDK가 스스로 `lophnApp.setKeepAlive(true, <key>)`를 켜서 workspace를 떠나도 page를 살려 둔다(앱의 `useKeepAlive`와 key가 달라 서로 끄지 않는다. `architecture/workspace-layout.md`). 열자마자 snapshot을 읽고, 그동안 온 갱신은 모았다가 접고, `reread`가 서면 다시 읽는다. 앱 context는 `contextBlock({name, mimeType, text})`가 `resource` block(uri `app-context:<name>`)으로 싼다. prompt 조립은 앱 code의 몫이다.
  - 꼴이 있는 답은 `send(blocks, {reply: schema})`다. SDK가 꼴을 알리는 글 block을 덧붙이고, 그 turn이 끝나면 마지막 agent 메시지 글의 마지막 ```` ```json ```` 블록(없으면 글 전체)을 꺼내 schema의 `type`·`properties`·`required`·`items`·`enum`만 검사한다. 맞지 않으면 값이 아니라 오류(`{ok: false}`)이고, 멈추거나 실패한 turn도 오류다. core는 꼴을 모른다. test는 "꼴에 맞지 않는 답은 오류로 나온다"이다(`packages/sdk/agent/agent_test.ts`).
  - SDK가 보내는 입력은 `send`, `stop`, `answer`, `rename`뿐이다. 승인 결정과 줄 고치기는 lophn 채팅 탭에서 한다. 앞 session에 다시 붙으려면 앱이 그 session id를 저장해 두었다가 `session` option으로 넘긴다. 넘기지 않으면 화면이 열릴 때마다 첫 `send`에서 새 session이다.
- 모든 tool 호출은 core를 지난다. 화면에서 앱으로, 앱에서 앱으로 가는 직통 통로를 두지 않는다.
  - 막기, 기록, write 줄이 core 한 곳에 있어야 changeset이 빠지지 않는다.
- 부른 쪽은 호출 본문이 주장하는 대로 믿지 않고 core가 확인한다. credential의 종류와 caller 종류가 맞아야 하고, agent는 지금 도는 turn의 tool call이어야 하고, 앱은 활성 release이면서 부모 invocation이 지금 도는 호출이어야 하고, program은 본문의 job과 job run이, flow는 본문의 instance가 core가 만든 자격과 같아야 한다.
  - 끝난 turn이나 꺼진 판의 호출이 실수로 섞이면 막기와 기록이 틀린다. agent, 앱, program, flow는 늘 live 활성 release만 부른다.
- tool 호출은 부른 workspace를 싣지 않는다. 어느 workspace가 불렀는지는 부른 session의 workspace로 안다.
  - 앱 code가 호출자별로 data를 나누는 관례는 core가 지키지 못한다. 그래서 호출에 범위를 싣지 않는다.
- **비공개 command는 그 앱 workspace의 session만 본다.** 다른 workspace(home, project, 다른 앱)의 session은 `public` command만 본다. agent가 찾는 길(`packages/core/lophn-agent/tools/app-public.ts`의 `withPublicOnly`), `app.tool_index`(`packages/core/apps/declaration/reads.ts`), Grants 탭 후보(`packages/shell/renderer/workspace/agents/editor/grants-model.ts`)가 같은 규칙이다. flow instance가 연 tool run은 목록이 없어 부를 때 instance의 agent(`workflow.yaml`의 `agent`)가 놓인 workspace로 같은 규칙을 본다(`packages/core/apps/calls/gate.ts`). job이 연 tool run은 사람이 승인한 job이라 거르지 않는다. core의 할당 쓰기는 거르지 않으므로 agent에게 막는 곳은 이 거르기다.
- **사용 관계(`app.usage`)의 쓰는 쪽은 그 앱 command를 부른 agent session의 workspace다(`packages/core/apps/usage/`).** invocation 기록에서만 세고, home과 그 앱 자신의 workspace는 세지 않는다. 쓰는 곳이 있는 public command를 지우거나 비공개로 바꾸는 release는 막지 않고 `release.prepare`가 결과의 `removed_public_tools`에 그 command를 싣는다(`removedPublicToolsOf`).
- 호출 경로는 묻지 않고 막기만 한다. agent의 호출은 그 agent의 지금 할당을 `judge`로 보고(할당 안 된 앱, 뺀 tool이면 막는다), 앱의 호출은 부른 앱의 active grant 가운데 `app.call`이 그 대상 앱의 그 tool을 덮는지 본다. 막히면 `denied(gate_blocked)`다. 판정 자리는 write 줄 앞이다.
  - 사람에게 묻는 자리는 run-loop tool gate 하나다(`architecture/approval.md`). agent의 호출이 여기 닿았으면 물을 것은 이미 물었다. 앱이 앱을 부르는 것은 activation 때 사람이 grant로 허락한 것이라 묻지 않는다.
- program은 job이 연 tool run의 호출이다(`architecture/job.md`). 부른 쪽 사람이 없고 부른 turn도 없다. 자격(`CallAuth.program`: job, job run)은 route가 만들지 못하고 core 안 run 연산이 만든다(`packages/core/main/daemon/wiring/runs.ts`). caller 본문은 `{kind: program, job, job_run}`뿐이고 자격과 같아야 한다(`verifyCaller`).
  - 판정은 하지 않고 통과한다. 허락은 사람이 그 job의 등록을 승인한 것이다(`architecture/job.md` "승인"). scheduler는 승인한 job만 돌리고, 할 일(앱, tool, 입력)은 승인 뒤 바뀌지 않으며, program 자격은 core 안 run 연산만 만든다. 만든 agent의 할당과 비공개 규칙은 보지 않는다(`packages/core/apps/calls/gate.ts`의 `callAllowed`).
  - 그 밖의 줄, 기록, 직렬화는 다른 호출과 같다. invocation의 `caller_kind`에 `program`이 있다.
- flow는 workflow instance가 연 tool run의 호출이다(`architecture/workflow.md` "flow"). program과 같은 길이지만 판정이 있다. 자격(`CallAuth.flow`: instance, 그 project의 PM과 project workspace)은 core 안 run 연산만 만들고, caller 본문 `{kind: flow, instance}`의 instance가 자격과 같아야 한다. 판정은 PM의 지금 할당과 비공개 규칙(PM이 놓인 workspace)이다. code를 쓴 것이 PM이라 code로 PM의 할당을 넓히지 못한다. 사람이 PM에게 그 앱을 할당해야 flow가 그 tool을 쓴다. invocation의 `caller_kind`는 `flow`다.
- 앱 process의 caller parser(`packages/core/apps/runtime/entrypoint/wire.ts`)와 `packages/sdk/cap-tool/context.ts`, invocation의 `InvocationCaller`는 protocol schema의 손 사본이라(앱 process는 Zod를 싣지 않는다) caller 다섯 종류(person, agent, app, program, flow)를 protocol과 같이 받아야 한다. 하나라도 빠지면 그 caller의 호출이 앱에서 말없이 거절된다. invocation 표의 `caller_kind` CHECK는 protocol의 `appToolCallerSchema`에서 만든다(`packages/core/apps/invocations/schema.ts`).
- write와 external은 앱마다 한 번에 하나다. core의 줄과 앱 process 안의 mutex, 두 겹이다. read는 동시에 돈다.
  - SQLite session은 연결 단위라 두 write가 겹치면 한 changeset에 두 호출의 변경이 섞여 호출 단위로 되돌릴 수 없다. 줄을 쥔 호출이 돌아오지 않아도 줄이 영영 막히지 않게 abandon이 줄을 비운다.
- changeset은 앱 process(sdk)만 뜨고 적용한다. 앱 DB는 그 앱의 process만 열기 때문이다. core는 보관하고, 뒤집고, 지휘한다.
  - sdk migration으로 만드는 표는 PRIMARY KEY가 필수다. 없으면 SQLite session이 그 표의 변경을 기록하지 않아, 되돌릴 수 없는데 되돌린 것처럼 보인다.
  - read tool이 DB를 바꾸지 않는다는 선언은 믿고 검사하지 않는다. 틀린 선언이 rewind를 충돌시키면 통째로 취소되고 이유가 남는다.
- 보냈는데 응답을 못 받은 호출은 실패가 아니라 결과 모름(unknown)이다. 추정하지 않고 같은 일을 다시 부르지 않는다. 보내기 전에 막힌 것(앱이 멈춤, 연결 없음)은 unavailable로 구분한다. core가 다시 켜질 때 running으로 남은 invocation도 unknown으로 닫는다.
  - 쓰기가 일어났는지 모르는 채 성공이나 실패로 적으면 rewind와 재호출이 틀린다. 한 앱의 문제가 부른 쪽의 다른 일을 멈추지 않는다.
- invocation 기록은 지우지 않는다. 끝난 행은 되돌림 표시와 changeset 정리 말고는 바뀌지 않고(trigger), rewind 기록도 불변이다. 성공한 read는 남기지 않고, 실패한 read와 막힌 호출(denied)은 남긴다.
  - 감사와 session rewind 연결(session·turn별 write 목록)이 이 기록에서 나온다.
- rewind는 사람만 하고 시점 단위다. 고른 invocation부터 최신까지 live, 활성 release 안, 아직 되돌리지 않은 write·external을 모두 되돌린다. 누가 한 호출이든 같다.
  - 읽기 의존을 알 수 없어 호출 하나만 빼낼 수 없다. 그 앱을 쓴 모두의 변경이 함께 사라지므로 agent에게 rewind tool을 주지 않는다.
- rewind는 접수를 닫고 도는 호출을 drain한 뒤 적용한다(유예를 넘으면 취소). 어떤 길로 끝나도 접수를 다시 연다. 앱마다 applying rewind는 하나다.
  - changeset은 최신부터 뒤집어 한 transaction으로 적용하고, 충돌하면 통째로 취소한다. 반쯤 되돌아간 DB를 남기지 않는다.
  - 그래서 뒤집은 changeset 전부가 요청 하나로 간다. core는 control frame 한도를 넘을 수 있는 이 본문을 json 요청(`apps.apply`, payload는 `{ app }`) 뒤 같은 channel의 bytes frame과 `end`로 supervisor에 보낸다. 보내다 실패하거나 기한이 지나면 `abort`를 보내고 `unavailable`로 끝낸다. write 하나씩 나눠 보내면 중간 실패 때 일부만 되돌아간다.
- 결과 모름으로 닫혀 changeset이 없는 write가 범위에 있으면 rewind를 막는다. 얼마나 바뀌었는지 모르기 때문이다. 크기 한도로 changeset을 못 붙인 write는 막지 않고 "DB를 되돌리지 못함"으로 표시한다.
  - command 호출의 입력과 응답, operation 호출의 입력은 supervisor control frame 하나씩으로 오간다. operation의 응답이 frame 하나를 넘으면 supervisor가 같은 channel의 bytes frame과 `end`로 보내고(응답 payload `{stream: <channel>}`, `packages/core/apps/runtime/supervisor/control-link.ts`, `packages/core/apps/runtime/supervisor-link.ts`), 응답 상한은 shell과 같은 `CALL_RESULT_MAX_BYTES`(8 MiB, `packages/protocol/apps/calls/limits.ts`)다. 화면 목록 같은 큰 읽기를 전송 단위에 묶지 않으려는 것이다. command는 agent가 읽을 작은 결과가 맞아 frame 하나에 둔다. 응답이 상한을 넘으면 앱 process가 changeset만 빼고 `changeset_dropped: "too_large"`를 싣는다. 호출은 결과 모름이 아니라 성공·실패로 닫히고 요약에 `changeset_dropped`가 남는다. 빼지 않으면 frame에서 거절되어 결과 모름이 되고 rewind가 통째로 막힌다. 받다 끊기거나 기한이 지나면 결과 모름이다.
  - command의 결과 상한(`RESULT_MAX_BYTES`)은 그 frame 한도에서 결과 밖 칸 몫을 뺀 값이라, 상한 안의 결과는 changeset을 빼면 늘 frame에 든다. 입력 상한(`CALL_BODY_MAX_BYTES`)도 frame 한도 아래이고, 넘는 입력은 core가 보내기 전에 `invalid_input`으로 거절한다. 큰 값은 blob이나 file로 넘긴다. operation의 결과 상한은 `CALL_RESULT_MAX_BYTES`에서 1 KiB를 뺀 값이다.
- release를 넘는 rewind는 없다. activation이 끝나면 이전 release의 changeset을 지운다(invocation 기록은 남는다). 이전 release로 돌아가는 것은 activation의 일이다.
- preview는 따로 띄운 process와 일회용 DB로 돈다. invocation을 남기지 않고(응답의 `invocation`은 null) rewind 대상이 아니다. 운영 앱의 drain과 정지에도 걸리지 않는다.
  - preview 호출은 그 preview bundle의 선언으로 tool과 effect를 판정한다. 아직 release에 없는 새 앱과 새 tool도 부를 수 있다. ledger의 `release`는 비울 수 없어 release 없는 bundle의 호출은 기록할 자리도 없다.
  - preview를 부르는 쪽은 사람과 그 앱 workspace의 session(`preview.call`)이다. agent caller는 그 앱 workspace의 session일 때만 preview target을 부르고, 다른 workspace의 session은 `forbidden`이다(`verifyCaller`, `packages/core/apps/calls/caller.ts`). 앱 workspace의 session이 지은 release를 운영 data 없이 확인하는 길이다. agent의 live 호출 규칙(활성 release, `release` 없음)은 그대로다.
- 앱 호출 사슬은 같은 앱이 다시 나오면(call_loop) 또는 깊이 한도를 넘으면 handler에 가기 전에 막는다. 앱끼리 서로 부르다 줄이 영영 풀리지 않는 것을 막는다.
- 앱 log는 앱마다 `<data root>/apps/<app>/logs/app.log`와 돌린 앞 file `app.log.1` 둘이다(`appLogFile`, `packages/protocol/apps/app-storage.ts`). file 하나는 8 MiB까지이고 앱마다 합쳐 16 MiB다. 줄을 더해 8 MiB를 넘게 되면 `app.log`를 `app.log.1`로 옮기고(앞 `.1`은 버린다) 새 `app.log`에 쓴다. 모양은 `packages/protocol/apps/app-log.ts`가 정한다.
  - JSON Lines이고 줄마다 `{ at, invocation, text }`다. `invocation`은 아는 줄에만 있고 아니면 null이다. 앱 안에서 SDK가 invocation 문맥으로 찍는 줄(`reportProblem`, 잡히지 않은 예외)만 invocation을 싣고, 그 밖의 stdout·stderr 줄은 null이라 시각으로 찾는다.
  - 쓰는 쪽은 app supervisor 하나다. 앱 process에 log를 쓰게 하지 않고 supervisor가 `<data root>/apps`에 쓴다.
  - 줄의 출처는 다섯이고 `text`의 꼴이 다르다. 앱의 stdout·stderr 한 줄은 그대로(머리 `[inv=<id>] `만 떼어 `invocation`으로), SDK `reportProblem(name, message?, details?)`은 `error <name>[: <message>][ <details JSON>]`, 잡히지 않은 예외는 `exception <name>: <message>` 한 줄에 이어 봉인된 bundle의 source map으로 원래 source 줄로 푼 frame마다 `  at <path>:<line>:<column>`, 화면 오류는 `view_error <observation> <name>: <message>`, 앱 process의 비정상 종료는 `process_exit <근거>: <message>`다(근거는 `unexpected_exit`, `v8_oom`, `start_failed`, `ready_timeout`, `crash_loop`). 의도한 정지는 쓰지 않는다. preview 자식(release 준비의 handler 검사 포함)의 출력과 오류는 쓰지 않는다. 화면 오류도 live 화면의 것만 쓴다.
  - 줄마다 redaction을 하고 그 뒤에 300자로 자른다. 순서가 바뀌면 자른 줄에 secret 일부가 남는다. supervisor의 redaction은 credential pattern과, core에서 받아 앱에 건넨 secret 값(`apps.secret_value`)을 지운다. log가 disk에 남으므로 바깥 응답에 되돌아온 secret을 앱이 찍어도 file에 남지 않게 하려는 것이다.
  - 읽기는 core route `apps/logs`(`app.logs`)다. core가 두 file을 바로 읽어 `invocation`, `since`(포함), `until`(제외)로 거르고 가장 최근 `limit`줄(기본 200, 최대 1000)을 오래된 것부터 준다. supervisor를 거치지 않으므로 앱이 멈췄거나 crash loop여도 읽힌다. 읽을 때 알려진 secret 값으로 한 번 더 지우고, 안전하게 만들지 못한 줄이 있으면 읽기 전체가 `unavailable`이다.
  - actor는 user, agent, app이다. agent는 tool `app.logs`로 부른다. 앱 상태(`app.status`)와 호출 기록(`app.invocations`)도 같은 식으로 읽어, 앱을 진단하는 쪽은 이 셋을 본다.
- 앱 process는 권한을 막지 않는다(사람이 정했다). SDK 넷(`@lophn/cap-net`, `@lophn/cap-secret`, `@lophn/cap-fs`, `@lophn/cap-notify`)으로 나가는 일은 선언에 적고, net과 secret과 notify는 broker가 요청마다 선언 사실 ∩ 사람의 grant를 본다(notify는 `architecture/app-notice.md`). fs는 선언이 무엇에 닿는지 보이는 값일 뿐 막지 않는다.
  - net: SDK의 요청은 앱 supervisor의 broker(`net/fetch`)가 보낸다. broker가 요청마다 목적지(host·port)를 선언 사실 ∩ grant로 검사한다. 앱 process의 network는 막지 않으므로 이 검사는 이 client를 지나는 요청에만 걸린다. redirect는 한 단계마다 같은 검사를 다시 받고, 플랫폼 port는 grant가 있어도 막는다. 이 검사가 틀리면 supervisor가 아무 곳이나 간다.
  - loopback 목적지는 http, 그 밖은 https다. 사람이 켠 같은 컴퓨터의 서비스를 부르려는 것이고 기계 밖으로 나가지 않는다. https에서 http로 내려가는 redirect는 거절한다.
  - 앱은 요청에 본문(글 또는 bytes, 풀어 쓴 크기 10 MiB까지)과 header(32개까지)를 싣는다. `Authorization`·`Cookie`·`Host`·`Content-Length`·`Proxy-Authorization`은 schema(`brokerNetFetchInputSchema`)가 거절하고 `GET`·`HEAD`에는 본문이 없다. 인증은 앱이 아니라 secret 길이 붙인다. redirect가 301·302(GET·HEAD 아님)·303이면 `GET`으로 바꾸고 본문과 `content-type`을 버리며, 307·308은 method와 본문을 그대로 다시 보낸다. 앱 header는 처음 목적지와 같은 origin의 hop에만 실린다. 응답은 지금처럼 1 MiB 이하의 글·JSON이다.
  - secret: 앱의 `useSecret`은 이름과 목적지를 말할 뿐 값을 읽지 못한다. broker가 secret 이름 선언 사실 ∩ grant와 그 목적지의 `net.fetch` 허락을 검사하면, supervisor가 core route `apps.secret_value`로 값을 한 번 받는다. 이 route는 supervisor의 machine 자격만 부르고, 부른 supervisor가 지금 보는 live 자식과 맞을 때, core가 현재 선언 사실 ∩ active grant로 다시 판정해 통과할 때, 알려진 값 registry가 그 값을 알 때만 값을 준다. 모르는 값은 redaction이 지우지 못해서다.
  - supervisor는 받은 값을 같은 invocation의 같은 (host, port) 요청에만 `Authorization: Bearer`로 붙이고, 60초가 지나면 버린다. redirect로 목적지가 바뀌면 값을 다시 찾아 붙지 않는다. 앱의 응답과 오류에 값이 없고, 앱이 찍어도 log의 redaction이 지운다. Bearer 말고 다른 방식의 인증은 쓰는 앱이 생길 때 더한다.
  - OAuth secret: 선언의 `secret.use`에 `oauth`(authorize·token 끝점, scope, 추가 authorize parameter)가 있으면 그 이름의 값은 사람이 sign-in해 받은 access token이다. 사람이 앱 Access 탭에서 client id와 client secret(선택)을 넣고 [Sign in]을 누르면 core가 loopback callback을 열고 authorize URL(PKCE)을 만들고 shell이 OS browser로 연다. core가 background에서 callback을 받아 token으로 바꾸고 화면은 상태(`apps/oauth_state`)를 다시 읽는다. 끝점은 https이거나 loopback http다.
  - OAuth secret의 값은 `apps.secret_value`가 보내기 직전에 core가 refresh한다(남은 시간 5분 이하, 이름마다 한 번에 하나, 발급자 호출 대기열). 발급자가 400·401·`invalid_grant`로 거절하면 access·refresh·meta를 지우고 상태를 `failed`(`refresh_rejected`)로 두며 앱은 `conflict`("oauth sign-in required")를 받는다. 닿지 못하거나 5xx면 지금 token이 만료 전일 때 그 token을 보내고, 만료 뒤면 `unavailable`이다. client id나 선언의 끝점·scope·parameter가 바뀌면 옛 token을 쓰지 않는다(상태 `none`).
  - refresh token, meta, client id·secret은 `app-oauth.<이름>.refresh|.meta|.client_id|.client`에 두고 어느 호출로도 보내지 않는다(`core/secrets/file-attach.ts`). OAuth가 없는 secret의 값도 사람이 같은 탭에서 보호된 입력 창으로 넣는다.
  - 사람은 같은 탭에서 값을 지운다. plain secret의 [Remove value]는 `secrets/delete`이고, OAuth secret의 [Sign out]은 `apps.oauth_sign_out`이 진행 중인 시도를 버리고 access·refresh·meta를 지운다(client id·secret은 남는다). grant [Revoke]는 값을 지우지 않는다. 앱 secret 이름은 전역이라 같은 이름을 선언한 다른 앱도 그 값을 쓴다.
  - fs: `@lophn/cap-fs`는 OS가 허락하는 파일을 어디든 읽고 쓴다. 선언의 `fs.read`·`fs.write`(경로)는 앱이 무엇에 닿는지 보이는 값이고 `checkDeclaration`이 그것을 요구한다. 운영 bundle의 사본은 file 0444·폴더 0555다.
  - broker는 live 자식의 요청만 받는다. 준비 모드와 preview의 자식이 같은 통로를 부르면 거절한다(`liveOnly`). SDK의 stand-in이 그 자리를 채운다.

## 왜 이 모양인가

- **core 경유로 일원화했다.** 이전에는 부르는 쪽이 core가 서명한 연결로 앱 process socket을 직접 부르고 앱이 invocation을 나중에 알렸다. 판정, 기록, 줄 세우기가 흩어지고 신원 증명(proof) 장치가 따로 필요했다. 지금은 경로가 하나다.
- **앱이 되돌림 tool을 선언하게 하는 모델을 버렸다.** 앱마다 맞게 짜야 하고 틀려도 알 수 없다. SQLite session의 changeset은 앱 코드와 무관하게 DB 변경을 호출 단위로 잡는다.
- **뒤집기는 직접 구현했다.** node:sqlite에는 session과 apply는 있고 changeset을 뒤집는 함수(`sqlite3changeset_invert`)가 없다. changeset에는 UPDATE와 DELETE의 원래 값이 들어 있어, SQLite 문서의 changeset format을 읽는 순수 함수로 뒤집는다(base). patchset은 원래 값이 없어 뒤집지 못한다.
- **호출 단위가 아닌 시점 단위로 되돌린다.** write가 무엇을 읽고 썼는지 모르니, 호출 하나만 빼면 뒤 호출의 전제가 깨진다.
- **되돌린 invocation을 지우지 않고 표시한다.** 기록은 감사에 쓰이고, 반쯤 되돌아간 DB는 남기지 않는다. 되돌린 것을 다시 하기(redo)는 없다.
- **program caller를 따로 둔다.** 사람이 연 run의 호출은 사람의 호출이라 Gate를 거치지 않는다. job의 호출은 사람이 등록을 승인한 job의 호출이라 판정 없이 지나가지만, 기록에는 어느 job, 어느 차례가 불렀는지 남아야 한다. agent caller는 도는 turn과 tool call을 싣고 그것으로 확인하는데 job에는 그것이 없다. 그래서 job과 job run을 싣고 core가 만든 자격과 맞춰 본다. agent를 빌려 쓰면 없는 turn을 만들어야 한다.
- **job의 허락은 만든 agent의 할당이 아니라 사람의 등록 승인이다.** 할당으로 판정하면 job 하나를 돌리려고 만든 agent에게 그 앱 전체를 열어 줘야 하고(그 agent는 다른 session에서도 그 앱의 모든 tool을 부른다), job을 만든 agent는 그 tool을 직접 쓸 이유가 없을 때가 많다(앱 workspace에서 앱을 만든 agent가 그 앱의 수집 job을 만드는 경우). 할당이 없으면 job은 만들어지고 차례마다 말없이 막혔다. 사람이 job 하나(주기와 할 일)를 보고 승인하면 허락의 범위가 그 job의 할 일 하나로 맞는다.
- **flow caller를 program에서 가른다.** flow instance의 호출도 사람이 없지만 자격의 agent(`workflow.yaml`의 `agent`, 없으면 lophn)의 할당으로 판정한다. job이 없으니 본문과 자격이 맞춰 볼 것이 instance다. 같은 kind에 job과 instance를 nullable로 두면 parser 손 사본마다 둘 중 하나만 있는지를 다시 검사해야 한다.
- **공유 skill의 원본은 앱 source의 `.lophn/skills`이고 release와 같이 봉한다(agent).** lophn data 자리에 두면 command를 바꾸는 commit과 skill이 따로 움직인다. 앱 source에 두면 CLI를 바꾸는 commit에 skill이 같이 들어가고, 공유되는 판이 active release의 것이라 HEAD의 작업 중 판은 새지 않으며 activation이 곧 갱신이다. 앱 agent가 쓰는 자리와 공유 원본이 같아 따로 옮기는 단계도 없다. 비공개 skill은 그 앱 workspace의 `app` source로만 보인다.
- **agent는 앱 command를 명령으로 부른다(`lophn <app> <command>`, 사람 2026-11-01, 앱 단위는 2026-11-03).** 앱 command마다 provider tool을 만들면 tool 정의가 앱 수만큼 늘고 늦게 싣기 장치가 필요했다. 지금은 `lophn` tool이 부를 때 지금 할당, 활성 release의 command 선언, 비공개 규칙(그 앱 workspace면 전부, 아니면 public)으로 찾는다(`packages/core/lophn-agent/tools/lophn/resolve.ts`, `packages/core/lophn-agent/tools/app-tool/command.ts`). 기록 이름은 `<slug>.<command>`(argv 낱말은 `.`로 나누고 `_`는 `-`)이고 effect는 선언에서 온다. 앱 command는 session 시작 때 고정하지 않아 `tools_changed` notice가 없다. `lophn <slug> --help`가 description과 입력을 보인다. 사람은 binary의 `lophn <slug> <command>`로 run을 거쳐 부른다. 내장 명령 묶음 이름은 앱 slug로 쓰지 못하고 `app.create`가 `invalid_input`으로 거절한다(`RESERVED_APP_SLUGS`, `packages/protocol/apps/declaration/types.ts`). 정의의 deny 규칙은 `lophn(<slug> <낱말>)`이다(`denyRuleOf`). 처음에는 command가 앱 안의 domain에 속해 `lophn <domain> <command>`였다. domain을 지우며 앱으로 접었다. domain이 앱 하나뿐이던 앱은 이름 글자가 그대로다. 옮기기는 ledger step `apps.releases.declaration-no-domain`(저장된 선언의 `commands[].domain`을 지운다. `declaration_hash`는 그대로)과 data step `approvals.deny-rule-slug`(정의 파일의 `lophn(<domain> …)`을 그 domain을 가진 앱의 slug로. 못 찾은 규칙은 그대로)다. 같은 앱의 domain 둘이 같은 이름의 command를 냈으면 저장된 선언은 그대로 두고 다음 release 기록이 겹침으로 거절한다.
- **선언을 operation과 command 두 층으로 나눴다(사람, 2026-11-01).** 한 목록이던 때는 화면이 앱 process에 닿는 길이 tool뿐이라 화면용 저수준 동작이 모두 agent tool이 되었고, agent 계약의 결과 상한이 화면 기능을 깎았다(Mahas 세션 목록이 200행으로 줄었다). 앱 고유의 저수준 동작은 operation으로 화면과 앱이 쓰고, agent와 다른 앱에는 앱이 고른 의미 단위 command만 내놓는다. command handler는 앱 code의 같은 함수를 감싼다. 화면은 `window.lophnApp.callOperation`(`@lophn/app-ui`의 `useOperation`, `OperationButton`)으로 부른다. MCP 모양과 annotation은 바깥에 내놓는 MCP endpoint가 없어 지웠다.
- **session rewind가 앱 data를 저절로 되돌리지 않는다.** 시점 단위라 그 사이 다른 쪽의 변경도 함께 사라지기 때문이다. 사람이 앱을 골랐을 때만, 함께 되돌아갈 목록을 보인 뒤 같은 rewind로 간다(Claude Code의 rewind 메뉴가 코드와 대화를 따로 고르게 하는 것과 같다).
- **바깥 net의 목적지 검사는 broker가 요청마다 한다.** 앱 process의 OS 권한을 막지 않으므로(사람이 정했다) process 권한으로는 목적지를 가둘 수 없다. 그래서 SDK 요청마다 현재 선언 사실 ∩ grant를 읽는 쪽을 골랐다.
- **secret은 값을 앱에 주지 않고 전송 직전에 붙인다.** 앱이 값을 쥐면 응답, 오류, log로 새는 길을 앱 코드마다 막아야 한다. 앱은 쓰겠다는 요청만 내고, 값은 core가 supervisor에게 한 번 주어 붙인다.
- **OAuth access token은 선언한 secret 이름 그대로 둔다.** 그러면 broker의 판정, `apps.secret_value`, supervisor의 Bearer 붙이기가 OAuth를 몰라도 된다. OAuth가 더하는 것은 값을 보내기 직전의 refresh 하나다. 앱이 token을 받아 직접 refresh하면 refresh token이 앱 코드에 닿는다.
- **refresh 거절만 sign-in을 끝낸다.** 앱 OAuth와 MCP OAuth(같은 refresh 코드 `packages/core/lophn-agent/extensions/mcp-auth.ts`의 `refreshToken`), provider 구독 OAuth 모두 400·401·`invalid_grant`만 거절로 본다. 발급자의 일시 오류(5xx, 닿지 못함)에는 만료 전 token을 그대로 쓴다. 사람이 다시 sign-in해야 하는 일을 막으려는 것이다.
- **client는 사람이 그 서비스에 만든 것을 넣는다.** Google 같은 곳은 자동 등록이 없고, lophn이 자기 client를 들고 다니려면 서비스마다 심사를 받아야 한다. OAuth는 표준 authorization code와 PKCE로만 열고 서비스에 맞춘 것은 선언의 추가 parameter(`access_type=offline` 같은 것)뿐이다.
- **앱 log를 앱마다 file로 남기고 쓰는 쪽을 supervisor 하나로 했다.** 앱 안에서 쓰게 하면 앱 code가 log를 지우거나 고칠 수 있다. supervisor는 이미 앱의 stdout·stderr를 쥐고 있고 lophn의 코드라, 앱이 쓴 줄과 lophn이 아는 사실(비정상 종료, 화면 오류)을 같은 file에 같은 redaction으로 쌓는다. 메모리 buffer가 아니라 file인 것은 앱이 죽거나 supervisor가 다시 뜬 뒤에도 원인을 읽어야 해서다.
- **저장하는 problem 모델 대신 log를 primitive로 둔다.** 오류를 상태 machine(열림, 닫힘), 묶음, 보고 표로 올리면 계약과 tool이 앱 쪽 진단보다 무거워진다. lophn은 줄을 남기고 읽게만 하고, 무엇이 문제인지 읽고 판단하는 일은 agent가 한다.
- **예외 stack은 쓸 때 원래 source 줄로 푼다.** 봉인된 bundle 사본은 agent의 file 범위 밖이라 agent가 stack의 bundle 위치를 직접 풀 수 없다. 당시 release의 source map으로 supervisor가 풀어 읽을 수 있는 줄만 남긴다.
