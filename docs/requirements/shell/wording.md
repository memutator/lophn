# shell/wording

UI·안내·오류의 문체와 기본/상세 정보의 말, 같은 개념의 일관된 이름을 맡는다; 개발자가 쓰는 말을 그대로 쓰고 뜻을 옮긴 번역어를 만들지 않으며 표시할 실제 사실은 각 concern을 따른다.

## 요구

### 화면과 조작

**[R1]** 기본 UI는 한국어 합니다체의 1~2문장·사람이 지은 이름·사람 단위 숫자·다음 행동 하나를 먼저 보이며 사람을 사용자라고 부르지 않고 문장에 마침표를 붙이되 버튼·제목에는 붙이지 않는다.
- 이유: 기본 안내만 읽어도 영향과 다음 행동을 알 수 있게 한다.
- 확인: 오류·일정·결과 요약만으로 일과 다음 행동을 설명할 수 있다.

**[R2]** 꼭 알아야 하는 내부 개념도 개발자가 쓰는 영어·굳은 음차 이름을 그대로 사용하고 쉽게 설명하되 새 번역어로 대체하지 않는다.
- 이유: 개발 문서·agent·UI 사이의 개념 이름을 일치시킨다.
- 확인: release를 앱 버전, blueprint를 설계도, ledger를 장부라고 표시하지 않는다.

**[R3]** 한국어 조사는 이름의 받침과 읽는 소리에 맞춰 붙이고 을(를)·(이)가·(으)로 같은 병기를 쓰지 않는다.
- 이유: 이름에 붙는 조사가 자연스럽게 읽혀야 한다.
- 확인: 문서를·lophn 기획으로처럼 맞는 조사와 문장이 표시된다.

**[R4]** 사람이 정한 제목과 상태 라벨로 기본 대상을 설명하되 내부 slug·enum·ID를 이름처럼 그대로 표시하지 않고 개발 용어 자체를 억지로 번역하지 않는다.
- 이유: 사람이 정한 이름을 내부 저장값으로 대체하지 않는다.
- 확인: 기본 카드에는 이름과 영향이 보이고 기술 용어는 문서와 같은 이름이다.

**[R5]** 문제 안내는 합니다체 한 문장으로 원인 추측 대신 사람이 겪는 영향을 적는다.
- 이유: 확인하지 않은 원인을 사실처럼 말하지 않는다.
- 확인: 파싱 실패만 쓰지 않고 사용량 일부가 빠지고 있습니다처럼 관찰된 영향을 쓴다.

**[R6]** 고정 사용자 문구 검사는 snake_case·ID 접두사·영문 enum의 기본 안내 노출을 경고하되 개발 용어인 release·run·watch 등을 그 이유만으로 금지하지 않는다.
- 이유: 원시 값 노출은 막되 필요한 개발 용어까지 금지하지 않는다.
- 확인: 원시 상태값은 경고되고 공인된 개발 용어는 그대로 사용할 수 있다.

**[R7]** 고정 사용자 문구 검사는 조사 병기를 오류로 처리한다.
- 이유: 조사 병기를 사람이 읽는 문구로 채택하지 않는다.
- 확인: (이)가·을(를)가 포함된 문구가 채택되지 않는다.

**[R8]** 앱 사용자 화면의 기본 안내·접힌 상세·tooltip에는 code·check 식별·ID·원시 key·stack·log·원문 오류를 넣지 않고 문제 전달용 복사 문장의 문제 ID 및 별도 개발자 diagnostics만 예외로 둔다.
- 이유: 앱 안내가 원문 diagnostics로 변하지 않게 한다.
- 확인: 앱 오류 tooltip에도 stack이 없고 필요한 원문은 problems/reporting·platform/diagnostics로 이어진다.

**[R9]** shell은 problems/problem-codes가 확정하여 전달한 문구를 사용하고 자리표시자를 자체 해석하거나 앱 제목과 문구를 임의로 합치지 않는다.
- 이유: 소유 concern의 고정 문구 의미를 shell이 다시 해석하지 않는다.
- 확인: 같은 문제의 문구가 앱·shell에서 같고 추가 조사 치환으로 달라지지 않는다.

**[R10]** 안내·오류는 실패한 대상과 사람이 겪는 영향 및 가능한 다음 행동 하나를 먼저 적고 모르는 원인은 추측하지 않는다.
- 이유: 실패의 실제 영향과 가능한 복구 행동을 먼저 알려야 한다.
- 확인: 저장 충돌에는 어느 문서의 저장을 못 했는지와 비교해 보기, 연결 실패에는 어느 연결과 다시 연결하기를 보여 준다.

**[R11]** 화면·문서·agent 안내는 ledger·redaction·테스트·test result·snapshot·release·blueprint·invocation·automation·activation·run·세션·assignment·handoff·claim·provider·notification·approval request·confirmation window·acceptance check·watch·revert를 같은 이름으로 부른다.
- 이유: 같은 개념을 서로 다른 번역어로 부르지 않는다.
- 확인: 동일 대상을 세 경로에서 열어도 같은 단어이고 장부·가림·시험·설계도·넘김·맡음·배치·알림 같은 대체 번역어가 없다.

**[R12]** 내부 식별자·content hash·파일 경로·조건식·원시 오류는 기본 안내와 분리한 자세한 정보에 두되 shell/confirmation-window의 정확한 대상·경로 확인 및 앱 사용자 화면의 원문 금지 예외를 지킨다.
- 이유: 기본 안내와 정확한 기술 확인의 정보 밀도를 분리한다.
- 확인: 기본 안내가 원시 값으로 채워지지 않고 보호 화면에서는 정확한 경로를 확인한다.

### 개념 이름

**[R13]** 컨텍스트 관점은 기준·참고·watch, model 선택은 judgment model·organizing model로 부르고 agent 작업 제목은 run 또는 실행·앱 호출 제목은 invocation으로 구별한다.
- 이유: shell/wording이 watch와 사람 notification·agent run과 앱 invocation의 혼동을 없앤다.
- 확인: 관점·model·작업 기록 화면에서 이 이름을 그대로 찾는다.
