## 0. Design facts used for the verdicts

- approval: only `shell.run`, assigned app tools and MCP tools go through `judge`. `file.write` (including `LOPHN.md`), `operator.create`, `call` never ask. The only thing that asks in attended mode is a shell command that matches `PRODUCT_SHELL_RULES.ask` (`rm -r*`, `rm -fr*`, `rm -f -r*`, `git push*--force*`, `git push* -f*`, `git reset --hard*`, `curl * | sh *`, ...) or a user rule. Choices are `once | always | reject` (`turnRequestDecide`, snapshot `turn_requests`, events `TurnRequestOpened/Closed`). No fingerprint, no "session" choice, no `PermissionRequested`.
- assignment replaces grants: `agentAssignmentGet/Set` `{app, removed_tools}`. Agent-to-agent grants and reaction grants are gone. `call` is neither asked nor blocked (AGENT-ROLE T5/T6, `architecture/agent-call.md`).
- App Engineer builds the app itself: `release.prepare {app}` (agent-only route, actor `agent`, returns `prepared | failed{stage,reason}`) -> optional `preview.start/call/stop` -> `release.activate {release}` (agent-only; returns `waiting_consent` at once for first activation / widened declaration / `-- loss:` migration; otherwise waits up to 120 s for `active | failed | running`). The human answers with `activation.consent {release, choice: allow|reject}` + compare `{requested_at}`; pending list is `activations.consents`; events `ActivationConsentRequested/Closed` (transient). A newer release start closes older consent lines.
- Router rejects calls whose receiver resolves to `coding_agent` with `invalid_input` and writes no call row. Nothing calls `CodingTransport.start`, so a coding session / token cannot be created by any product path or by an e2e.
- `app.create` now installs the template into `<home>/apps/<app>/source`, commits, and connects it itself (machine principal). The source folder is the App Engineer place folder, so the agent runtime child is restarted (1 s polling) after `app.create` - `settle` is needed before opening an App Engineer session.
- no ticket, no test runner, no `ReleaseActivationFailed` reaction, no problems/reactions, no Reactor/domain events, no `/recap`, no `guide.read` (guides are skills `guide-*`), no `opening_context`/`event_seq`, no worker routes.
- app log is a file `<home>/apps/<app>/logs/app.log`; SDK `reportProblem(...)` returns `void` (no `.completion`).
- kind violations: transient `KindViolationFound {domain,count}` only (toast), dispatcher compares in memory, first sync after boot is baseline only, no session opens.

## 3. How e2e is run

- `deno task e2e` = `deno test --allow-all --no-check tests/e2e` (deno.json), file order, no `--parallel`, core per flow, budget 10 min (testing.md). `deno task e2e:deps` = `deno run --allow-all tests/support/coding/prepare-deps.ts` (downloads npm/jsr/esbuild into `.dev-data/e2e/deno-dir`, then proves `prepareFromSource` offline).
- `project-docs/plan/tools/lead/land.sh`: after `check:full`, `if [ -z "$LOPHN_LAND_SKIP_E2E" ] && ls tests/e2e/*_test.ts` -> `deno task e2e:deps` then `deno task e2e`. As long as stale e2e files exist and the skip variable is not set, every land STOPs with "e2e failed". The three open plans (headless-run, schedule-job, workflow) READMEs already say to land with `LOPHN_LAND_SKIP_E2E=1` (orchestrate skill: the human must say so in the lead session). Settings allow-list in `.claude/settings.local.json` has that exact command.
- `tests/eval/experiment/gate/mod.ts` has stages `check | e2e | dry-run`; `eval/experiment/variant/prepare.ts` runs `deno task e2e:deps`. So the eval experiment gate also needs a passing `deno task e2e` (or the eval plan must drop that stage).
- `tools/check.ts`: `NOT_CHECKED` is removed from type check, fmt/lint-source list (`sourceFiles`), and `deno test` discovery. `.claude/skills/write-test/SKILL.md` lines 88-89 and `architecture/testing.md` ("앱 길", `tests/support` table) describe the old ticket flow and the exclusion; update when the plan lands.

## 4. What the new support/app layer needs (for the rewrite)

- `startTestApp(core, fake, {name, slug, patch})`: `appCreate`; overlay sample + patch into `<home>/apps/<id>/source`, `git commit` (use `GIT_CONFIG_GLOBAL=/dev/null` like today); `settle` (runtime child restarts); open the App Engineer session.
- `aeLane(app)`: lane `match` = tool names include `release_prepare` AND body contains `App <id>:` (ticket_create no longer exists; keep per-app text marker).
- `deliverRelease(core, fake, app, {goal, preview?: boolean})`: script the AE lane `release_prepare {app}` -> (`preview_start {release}`, `preview_call`, `preview_stop` if asked) -> `release_activate {release: <id read from the prepare tool result>}` -> text; say `App <id>: <goal>`; wait the AE turn; return `{release, prepared|failed, activate}` parsed from tool results. `release.prepare` and `release.activate` are agent-only routes, so the test cannot call them directly: the fake-model AE lane is the only way (as in the product). Tool call ids must differ per hand-off (idempotency key).
- `approveActivation(core, app, "allow"|"reject")`: poll `activationConsents {app}` -> `activationConsent {release, choice}` with compare `{requested_at}`; `waitRunning` unchanged.
- optional `watch` of `ActivationConsentRequested/Closed` through `connectGateway`.
- Risk to check on the first run: `release.prepare` runs the build (esbuild) + migration check + preview start inside one agent tool call; old runs waited up to 300 s for preparation.
