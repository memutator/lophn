# 0.9.0

## agent 답이 쓰이는 대로 markdown으로 흐르고, reasoning·tool 제목·일한 시간이 보인다

```yaml
modules: [packages/base, packages/protocol, packages/core/lophn-agent, packages/core/main, packages/core/secrets, packages/core/storage, packages/core/apps, packages/design, packages/shell/main, packages/shell/renderer, tools]
checked: [architecture-approval, skill-ui-design, skill-wording, skill-write-test, agent-role, boundary-catalog, architecture-layers, architecture-testing, architecture-eval, architecture-activation, architecture-agent-call, architecture-app-call, architecture-place-session, architecture-agent-definition, architecture-browser-tab, architecture-artifact, architecture-workspace-layout, architecture-kinds, architecture-domain, tool-check, tool-worktree-prep, tool-e2e, tool-test-live, tool-eval, tool-check-deps, tool-dev, tests-support, tool-package-linux, tool-models-snapshot, tool-wording]
```

- 전:
  - agent 글은 plain text였고 tool call 없는 마지막 답만 저장했다. tool call과 같이 온 글("X를 확인하겠다")은 model 이력에만 들어가 사람은 끝내 보지 못했고, 마지막 답도 turn이 끝나야 보였다.
  - adapter가 읽을 수 있는 reasoning을 버렸다. tool 줄은 `file.read`, `shell (failed)`처럼 tool 이름뿐이었다.
  - "Worked for"는 이름과 달리 wall clock이라 승인을 기다린 시간이 들어갔고, 기다림 뒤 일하는 중 줄이 기다린 만큼 건너뛰었다. 60분이 넘으면 `75m`이었다.
  - 파일 읽기의 markdown link를 누르면 shell 창 전체가 그 web page로 넘어갔다.
- 후:
  - 글은 token streaming이다. adapter delta → run-loop가 50ms씩 묶은 날 글(감독 pipe `model_output`) → core가 쌓인 글 전체를 redaction하고 secret이 시작됐을 수 있는 끝을 붙잡아 agent event `ModelOutputStreamed`로 낸다. session snapshot이 쓰는 중인 글(`writing`)을 싣는다. 화면은 throttle해서 `ChatMarkdown`으로 그리고 닫히지 않은 code fence는 그릴 때만 닫는다.
  - model 응답 하나가 agent message 하나다(`MessageRecorded`). tool call과 같이 온 글도 그 응답의 tool call보다 먼저 저장한다. 마지막 응답은 글이 비어도 저장하고, run의 답은 빈 글이면 지금처럼 `no_answer`다. 사람이 멈추면 core가 `StopTurn` 앞에서 사람이 본 글을 저장한다(run·workflow의 멈춤도 같은 길). retry한 attempt의 글은 버린다.
  - agent 글은 markdown(design `Markdown` variant chat, artifact path link, 표 가로 scroll, task list checkbox 의미, code label은 fence info 첫 낱말)이고 사람 글은 plain이다. chat의 image는 불러오지 않고 alt 글의 link다.
  - code block은 Shiki(JS regex engine, 4.5.0)를 shell의 Worker에서 돌려 token을 span으로 칠한다. grammar는 언어마다 lazy chunk다(설치 약 +9 MB). CSP는 그대로다. design `CodeBlock`은 `HighlighterProvider`에서 highlighter를 받고 없으면 plain이다. 색 token `code.*`를 더했다.
  - reasoning: 세 adapter가 reasoning 글을 opaque 상태와 따로 모아 같은 delta 길로 흘리고 redaction을 거쳐 message part `{kind: "reasoning", text, duration_ms}`로 저장한다(batch 응답도). model 이력에는 가지 않는다. Anthropic adaptive thinking에 `display: "summarized"`, OpenAI Responses에 `reasoning.summary: "auto"`를 싣는다. 화면은 "Thinking" → "Thought for {d}" / "Thought"이고 펼치면 요약이다. Messages 보기에서는 숨긴다.
  - tool 제목: tool 정의마다 `display(input) → {category, title}`이 있다(`Read src/app.ts (10-80)`, `Search TODO in src`, `Fetch https://…`). `shell.run`에 선택 칸 `description`이 생겼고 비면 명령 첫 줄이다. shell 명령은 read/list/search/command로 가른다. core가 `ToolCallStarted`와 `ListToolCalls`를 낼 때 지금의 redaction으로 만들고 저장하지 않는다(`ListToolCalls`는 core API read로 옮겼고 `tool` filter가 생겼다). 이어진 탐색 call은 하나로 묶고("Read 2 files · Searched 1 time"), command·web도 묶는다. 묶음을 펼치면 call마다 제목과 시간, call을 펼치면 redaction된 입력 전체와 출력(64 KiB, 잘림 표시)이다. 승인 카드는 그대로다.
  - 시간: "Worked for"는 active(사람 기다림 제외)다. core가 turn이 끝난 순간까지 active를 마감해 `TurnEnded.active_ms`에 싣고, 마지막 사람 기다림이 닫히면 `TurnResumed`를 낸다. snapshot이 도는 turn의 `elapsed`를 싣는다. 일하는 중 줄은 기다림 뒤 건너뛰지 않고(`role="status"`), 기다린 시간은 완료 줄 tooltip이다. 60분 이상은 `1h 5m`이다. trace의 `wall_ms`는 진짜 wall이다.
  - shell 창의 main frame은 `lophn-shell://desktop` 밖으로 가지 않는다. `http`/`https` link는 OS browser로 열리고 새 창 요청은 막힌다.
  - 죽은 코드: `ProgressChip`, Tasks popover, `TaskView`, 화면 값의 `tasks`, `AgentHeader`의 `progress` 자리, 쓰지 않던 wireframe page `agent-chat`.

왜: agent가 markdown으로 답해도 사람은 기호를 그대로 봤고, 한 turn에서 agent가 무엇을 하는지(글, reasoning, 무슨 파일을 읽고 무슨 명령을 돌렸는지)와 일한 시간을 읽을 수 없었다. 비교한 harness(Claude, ChatGPT/Codex, Hermes, OpenCode, Gemini CLI, Cline 등)가 모인 정석에 맞췄다.

결정:
- 글은 token streaming으로 보인다. 정석이 답이고 지금 구현에서 옮기는 비용은 근거가 아니다. (사람, 2026-10-25)
- 고르는 기준은 정석과 맞는 의미다. 지금 구현에 맞추느라 고르지 않는다. (사람, 2026-10-25)
- tool call은 무엇을 했는지 semantic하게 보인다(Claude Code의 Bash `description`처럼). 펼치면 내용이 보인다. (사람, 2026-10-25)
- live 글의 redaction은 core가 하고 붙잡는 자리는 child에 알리지 않는다. child가 물을 수 있으면 secret 값을 한 자씩 알아낼 수 있다. 상수 길이로 붙잡지 않는다(긴 token의 앞부분이 나간다). (agent, planner)
- model 응답 하나가 agent message 하나이고, 한 model 호출의 message id는 `model_call`에서 정한다(`msg_` + ULID). (agent, planner·lead)
- 마지막 응답은 글이 비어도 저장하고 run은 빈 답을 `no_answer`로 본다. 중간 응답의 글이 run의 답이 되지 않게 한다. (agent, lead)
- 멈춘 답은 사람이 본 데까지 turn이 끝나기 전에 저장한다. provider가 끊어 retry하는 attempt의 글은 버린다. (agent, planner)
- markdown은 이미 있는 Lezer `Markdown`, highlight는 Shiki(JS engine, Worker, lazy grammar)다. 사람 글은 plain, chat image는 불러오지 않는다. (agent, planner)
- link는 renderer `onOpenLink`와 shell 창 navigation guard 둘 다로 막는다. (agent, planner)
- reasoning을 보이고 시간은 provider가 알린 reasoning block의 시작과 끝으로 잰다(읽을 글 없이 암호화만 와도 잰다). (agent, planner)
- "Worked for"는 active다. `TurnResumed`는 사람 기다림을 아는 core가 낸다. 멈춤·실패·끊김으로 끝나는 turn도 active를 끝난 순간까지 마감한다. (agent, planner)
- model이 쓰는 설명은 `shell.run`에만 두고 승인 카드에는 싣지 않는다(`architecture/approval.md`). 나머지 tool은 인자 template이다. 제목은 한 줄 120자, 저장하지 않고 읽을 때 지금의 redaction으로 만든다. 앱 tool 제목은 저장된 wire 이름이다. (agent, planner)
- 범위 밖: 수식·다이어그램, transcript 가상화와 `content-visibility`, turn마다 펼치기, 보기 select 저장, code wrap toggle, 한국어 catalog, agent todo list. (agent, planner)

## ChatGPT 로그인으로 부른 model이 "model error"로 끝나지 않는다

```yaml
modules: [packages/core/lophn-agent]
checked: []
```

- 전: transport는 content-type이 `text/event-stream`인 성공 응답만 stream으로 읽었다. ChatGPT 구독 token으로 부른 `api.openai.com/v1/responses`는 SSE 본문을 content-type 없이 보내서, lophn은 그것을 JSON으로 읽다 실패했고 모든 turn이 `unknown` → "model error"로 끝났다.
- 후: content-type이 없는 성공 응답도 SSE로 읽는다. content-type이 있고 SSE가 아니면 그대로 batch(JSON)다.

왜: 사람이 설치본에서 ChatGPT 로그인 후 `gpt-6.1-sol`로 보낸 첫 메시지가 실패했다. 실제 응답 한 번(2026-10-26, `x-oai-request-id: req_603ded9197b74c808d9b1f55bff7a526`)으로 header에 content-type이 없음을 확인했다.

결정:
- content-type이 없으면 SSE로 본다. 요청이 늘 `stream: true`이고 `accept: text/event-stream`이라서다. 버린 길: batch JSON parse가 실패하면 SSE로 다시 읽기(본문을 64 KiB 상한 안에서 한 번에 읽어 긴 답이 잘리고 글이 흐르지 않는다). (agent)

후속: 설치본은 다시 build해야 고쳐진다.

## 터미널에서 직접 띄운 coding agent의 icon, 상태 점, 알림이 탭에 보인다

```yaml
modules: [packages/protocol, packages/core/apps, packages/core/main, packages/coding-agent, packages/base, packages/design, packages/shell/main, packages/shell/renderer, tools]
checked: [architecture-coding-agent, architecture-terminal-agent, architecture-event, architecture-browser-tab, skill-wording, skill-ui-design, skill-write-test]
```

- 전:
  - 사람이 터미널 탭에서 `claude`를 띄워도 lophn은 몰랐다. hook launcher는 coding token이 없으면 바로 끝났고, hook은 core의 `coding.hook` route가 coding session 행으로만 받았다. 그 coding session을 여는 길은 막혀 있어 hook 상태 장치를 쓰는 곳이 없었다.
  - 탭 점은 이름 뒤에 따로 있었고 working도 멈춰 있었다. OS 알림은 없었다.
  - coding 탭 icon은 `vendorOf("claude")`가 없어 Claude에서 비었고 Gemini는 Google icon이었다.
  - 거절한 권한 물음에는 `PostToolUse`가 오지 않아 coding session이 waiting에 남고 줄이 막혔다. Codex `Interrupt`, Claude `PostToolUseFailure`를 받지 않았다. turn 끝 신호를 `TURN_END_SIGNALS`와 hook 표 두 곳에 따로 적었다.
- 후:
  - 터미널의 agent 층(`architecture/terminal-agent.md`): terminal-host가 1초마다 foreground process 이름을 읽어 무엇이 도는지 알고, hook이 상태(running, waiting, idle, unknown)를 알린다. 탭 icon은 harness vendor, 탭 점은 X 자리에서 working이면 숨 쉬고 마우스를 올리면 X로 바뀐다(lophn agent 탭도 같다). 사람이 안 보는 사이 turn이 끝나거나 권한을 물으면 finished 점, lophn 창이 모두 focus 밖이면 OS 알림이고 누르면 그 탭으로 간다. 단독 Esc·Ctrl-C는 unknown으로 내린다.
  - hook 길: `lophn hook`은 env `LPN_TERMINAL_HOOK`의 unix socket(shell main, 터미널마다 key)에 한 줄을 쓴다. core route `coding.hook`과 `HOOK_ROUTES`를 지웠다. coding 터미널의 hook은 shell main이 내부 route `coding_agent_terminals/hook`(`codingTerminalHook`)으로 넘긴다. launcher와 pi·OpenCode plugin은 그 env로 확인한다. launcher는 `hook`에만 그 env와 socket 경로 권한을 준다.
  - hook 설치: 사람 터미널에서 harness를 처음 알아보면 묻는다(실행마다 harness당 한 번). Settings › Coding agents에 Hooks 칸과 [Install hooks]가 생겼다. plugin file에 새 env 확인이 없으면 `dry_run`이 missing이다.
  - 그렇게 놓은 hook은 이미 도는 harness 실행에는 보이지 않는다(harness가 시작할 때 읽는다). 성공 알림이 그 harness를 다시 시작하라고 한다.
  - coding session: turn이 끝나면 남은 권한 물음을 `cancelled`로 닫는다. Codex `Interrupt`(0.150 이상)는 interrupted turn 끝, Claude `PostToolUseFailure`는 물음 닫힘이다. `canDeliverMessages`는 hook 표에서 계산한다.
  - 탭 icon은 harness id를 product icon으로 고른다(`harnessVendorOf`). 탭 점에 `finished`가 생겼다.

왜: 다른 harness 관리 도구(herdr, orca, emdash, paseo)는 터미널에서 띄운 agent의 icon, 상태, 알림을 보인다. 사람은 lophn 안 터미널에서 coding agent를 쓰고, 뒤에 lophn과 coding agent를 다시 이을 때 같은 층을 쓰려 한다.

결정:
- coding agent 연결의 hook, 감지, 설치는 남긴다. B와 B-lite는 하지 않는다(`products/roadmap/problem-ticket.md`). (사람, 2026-10-26)
- 사람이 연 터미널의 agent는 lophn session이 아니라 탭 상태다. (사람, 2026-10-26)
- 무엇이 도는지는 foreground process로도 안다. 상태는 hook만 쓴다. (사람, 2026-10-26)
- 알림은 turn 끝(완료, 실패)과 권한 물음이고, 보고 있으면 알리지 않으며, 사람이 멈춘 turn은 알리지 않는다. 창이 focus 밖이면 OS 알림, 안이면 탭 점이다. (사람, 2026-10-26)
- hook 설치는 처음 알아봤을 때 묻고 Settings에서도 놓는다. (사람, 2026-10-26)
- 작업 중인 agent의 점은 X 자리에서 pulse하고 hover하면 X다. lophn agent 탭도 같다. (사람, 2026-10-26)
- hook은 터미널을 가진 shell main이 받는다. core를 거치면 core가 사람 터미널을 알아야 한다. browser bridge와 같은 socket·key 꼴이다. (agent)
- 단독 Esc·Ctrl-C는 사람이 친 입력이라 짐작이 아니다. 멈췄다고 하지 않고 unknown으로 둔다(paseo와 같다). core의 coding session 상태에는 아직 넣지 않았다. (agent)
- launcher가 hook의 deno 권한을 sh에서 정한다. launch entry를 거치면 hook마다 deno가 두 번 뜬다. (agent)

- hook 설치는 OS 창이 아니라 lophn 창의 dialog로 묻는다. 그 터미널을 고른 창에 묻고 닫히거나 reload되면 거절이다. 앱 종료 확인만 OS 창이다. (사람, 2026-10-26)
- Codex hook은 설치가 `~/.codex/config.toml`에 trust 기록까지 쓴다. hash는 Codex `hook_hash`(rust-v0.164.0)와 같은 계산이고 사람 허락은 lophn dialog 한 번이다. orca와 같다. (사람, 2026-10-26)
개발 실행(`deno task dev`·`dev:mock`)은 저장소 `.cache/dev-cli/lophn`(설치된 launcher와 같은 본문)을 `LOPHN_CLI`로 준다. launcher는 `hook`에 socket 경로 읽기·쓰기·net(`unix:<경로>`)과 `LPN_TERMINAL_HOOK` env 읽기를 준다.

후속: macOS는 node로 도는 CLI를 hook이 올 때까지 알아보지 못하고, Windows는 이 층이 없다.

## 터미널에서 알아보는 coding agent가 25종이고, 공유 server를 쓰는 harness는 lophn 터미널에서 private server로 뜬다

```yaml
modules: [packages/protocol, packages/coding-agent, packages/shell/main, packages/shell/terminal-host, packages/shell/renderer, packages/design]
checked: [architecture-coding-agent, architecture-terminal-agent]
```

- 전: 알아보는 harness가 몇 종이었고 Gemini CLI와 OpenClaw가 있었다. Hermes는 hook 자리가 없었다. Codex 0.156 이상과 OpenCode 2.x는 공유 background server(Codex app-server daemon, `opencode serve --service`)에서 session을 돌려, hook이 그 server를 띄운 env로 돌고 lophn 터미널을 몰랐다(Codex README "per-client environment isolation is not provided").
- 후:
  - 25종: claude, codex, opencode, pi, omp, cursor, copilot, kimi, kiro, antigravity, grok, droid, amp, devin, qwen, qoder, hermes, muse, codebuddy, command-code, prime-agent, mimocode, cline, letta, kilo. Gemini CLI와 OpenClaw를 지웠다.
  - foreground 감지는 argv 규칙이다(`harnessOfProcess`: 이름, 판 붙은 이름, package 경로, python `-c` 안의 표지). 다른 harness의 hook은 받지 않는다(grok·devin·cursor가 Claude hook을 읽는다). 단독 Esc·Ctrl-C로 내리는 키는 harness마다다(grok은 Ctrl-C만).
  - hook 설치 꼴: Claude 꼴 JSON settings, JSONC, Kimi TOML block, Hermes YAML block과 shell-hook allowlist, plugin·extension file(OpenCode 계열, pi, omp, amp), event마다 script file(Cline). 사람의 설정과 다른 도구의 hook은 그대로 둔다. stdout을 요구하는 hook은 같은 글을 쓴다(antigravity Stop `{"decision":"stop"}`, cursor beforeSubmitPrompt `{"continue":true}`).
  - lophn 터미널의 shell function(bash `--init-file`, zsh `ZDOTDIR`, fish `--init-command`)이 `codex --no-daemon`, `opencode --standalone`, kilo `KILO_NO_DAEMON=1`, cline `CLINE_SESSION_BACKEND_MODE=local`로 띄운다. orca의 Codex shell function과 같은 꼴이다.
  - icon 25종(lobehub, emdash). Codex는 OpenAI 매듭이다.
  - 사람이 개발 앱에서 claude, codex, opencode, hermes, devin, cline, grok, agy를 띄워 icon, 상태 점, turn 끝을 확인했다. Hermes는 hook을 놓기 전에 떠 있던 실행이라 다시 시작해야 했다. 나머지는 이 컴퓨터에 없거나 띄워 보지 않았다.

왜: 사람이 orca·emdash·herdr가 지원하는 harness를 lophn에서도 알아보게 하고 싶었다. Gemini CLI는 Google이 Antigravity로 옮겼다.

결정:
- 범위는 orca, emdash, herdr 셋 가운데 둘 이상이 지원하는 harness다. 한 곳만 지원하는 것은 넣지 않는다. (사람, 2026-10-26)
- Gemini CLI는 지운다. 호환 장치를 남기지 않는다. (사람, 2026-10-26)
- OpenClaw는 지운다. 비교한 도구 어디도 지원하지 않는다. (agent)
- hook이 없는 harness(prime-agent)는 foreground 감지와 icon만 한다. (agent)
- 새 harness의 coding session 칸(`prompt`, `mcp`, `model_flag`)은 채우지 않는다. 그 길은 막혀 있다. (agent)
- 공유 server를 쓰는 harness는 lophn 터미널에서 private server 옵션으로 띄운다. app-server protocol로 붙는 길은 하지 않는다. (사람, 2026-10-26)

## 터미널에서 Claude Code 색이 나오고, 분할 칸 resize를 따르고, 바깥 agent session 표지를 물려받지 않는다

```yaml
modules: [packages/shell/renderer, packages/shell/main, packages/shell/terminal-host]
checked: [architecture-terminal-agent, architecture-browser-tab, skill-write-test]
```

- 전:
  - Claude Code가 터미널에서 흰색으로만 보였고 resize하다 보면 가끔 색이 돌아왔다. Claude Code는 색을 truecolor(`ESC[38;2;…m`)로만 낸다. xterm DOM renderer는 truecolor를 `setAttribute("style", "color:…")`로 붙이는데 shell CSP(`style-src 'self'`)가 선언을 막고, 같은 span에 곧바로 쓰는 CSSOM `letterSpacing`이 속성을 다시 직렬화해 남은 글까지 지웠다. 속성을 다시 적용하던 observer는 microtask라 늦었다. resize 뒤 `letterSpacing`을 쓰지 않는 크기가 되면 색이 살았다. Codex는 palette 색(class)이라 멀쩡했다.
  - 분할 화면에서 handle을 끌면 터미널이 따라 줄기도 하고 그냥 가려지기도 했다. renderer와 main 둘 다 "focus 칸의 고른 탭"일 때만 resize를 보내고 받아서, 다른 칸에 focus가 있으면 xterm만 새 폭이고 PTY는 옛 폭이라 TUI가 옛 폭으로 그려 잘렸다. input 검사를 그대로 옮긴 것으로 보인다(기록에 이유가 없다).
  - 탭이 다시 붙으면 버퍼를 처음부터 새 xterm에 다시 쓰면서 그 안의 옛 질의(DA1, focus 보고)에 xterm이 답했고, 그 답(`ESC[?1;2c`, `ESC[O`)이 PTY에 입력으로 갔다.
  - lophn을 agent session 안에서 띄우면 터미널이 `CLAUDECODE`, `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID` 같은 표지를 물려받아, 그 안의 Claude Code가 자식 session으로 돌았다("Transcript saving is off").
  - hook launcher가 Deno 2.9에서 unix socket 연결에 필요한 `--allow-net=unix:<경로>`를 주지 않아 hook이 조용히 아무것도 보내지 않았다.
  - 자기 바탕을 칠하는 full-screen TUI(OpenCode)의 둘레에 탭 바탕색 여백 띠가 보였다. 오른쪽은 xterm scrollbar 자리(14px)가 alternate buffer에서 늘 비어 더 넓었다.
- 후:
  - 셀은 xterm WebGL renderer(`@xterm/addon-webgl` 0.19.0)가 그린다. WebGL을 못 쓰거나 context를 잃으면 addon을 버리고 DOM renderer로 돌아간다(그때는 truecolor가 기본 글자색이다). `adoptInlineStyles`는 `<style>`만 constructable stylesheet로 옮긴다. CSP는 그대로다.
  - 보이는 터미널은 focus와 상관없이 칸 크기를 PTY에 보낸다. 사람의 키 입력과 restart만 focus 검사를 한다.
  - 다시 붙을 때 쓰는 옛 출력은 `replay`로 쓰고, 그 parse가 끝날 때까지 xterm의 답을 PTY에 보내지 않는다(write callback 경계). 그 몇 ms 사이에 친 키도 버려진다.
  - 터미널 env는 Claude Code와 Codex가 자식에 넣는 session 표지 16개를 지운다(`packages/shell/terminal-host/env.ts`). 사용자 설정(`CLAUDE_CODE_USE_BEDROCK` 등)은 남긴다.
  - 설치본과 개발 launcher가 `hook`에 `unix:<socket 경로>` net 권한을 준다.
  - scrollbar 자리를 왼쪽 여백과 같은 6px로 줄였다. alternate screen에서는 여백과 scrollbar 자리를 가장 가까운 cell의 바탕색으로 칠한다(Ghostty `window-padding-color = extend`). 왼쪽·오른쪽 띠는 줄마다, 위·아래 띠는 칸마다 칠해 OpenCode의 sidebar·header 색도 이어진다. 일반 화면은 그대로다.

왜: 사람이 개발 앱에서 쓰다 찾았다. 원인은 byte(실제 `claude` 2.1.310 시작 출력)와 headless Chrome 재현(같은 CSP)으로 확인했다.

결정:
- CSP를 풀거나(`style-src-attr 'unsafe-inline'`) `Element.prototype.setAttribute`를 창 전체에서 바꾸지 않고, inline style이 필요 없는 renderer로 바꾼다. 앞의 둘은 shell renderer 전체의 style 경계를 넓힌다. (agent)
- resize는 focus 검사 대상이 아니다. 치수만 바꾸고 PTY에 글을 넣지 않는다. (agent)
- 터미널 여백은 없애지 않고 색만 늘린다. 여백을 없애면 shell 글자가 칸 경계에 붙고, TUI일 때만 없애면 cols·rows가 바뀌어 resize가 일어난다. TUI 테마를 lophn에 맞추는 일은 사람이 harness에서 고른다. (사람, 2026-10-26)
- 여백 색은 alternate screen에서만 늘린다. 일반 화면의 prompt·powerline 줄은 늘리면 어색하고 Ghostty도 거기서는 거의 늘리지 않는다. (agent)

## agent 알림이 보고 있으면 없고, 창에 focus가 있으면 toast, 없으면 OS 알림이다

```yaml
modules: [packages/shell/main, packages/shell/ipc, packages/shell/preload, packages/shell/renderer, tools]
checked: [architecture-terminal-agent, architecture-event, architecture-approval]
```

- 전: 터미널 안 coding agent는 lophn 창이 하나도 focus가 아닐 때만 OS 알림을 냈고, focus일 때는 탭 점만 바뀌었다. lophn agent는 권한 물음·질문만 창마다 toast로 떴고(창 focus와 상관없이, 창이 여럿이면 여러 번) turn 끝은 아무것도 없었다. Agent 탭에는 안 본 turn 끝(finished) 점이 없었다.
- 후:
  - 두 종류가 같은 규칙을 쓰고 shell main 한 곳이 정한다(`packages/shell/main/notice/rule.ts` `routeNotice`). 그 탭이 focus를 가진 창에 보이면 알리지 않고, focus를 가진 lophn 창이 있으면 그 창 하나에 toast, 없으면 OS 알림이다. detached 창에 focus가 있으면 OS 알림이다. toast와 알림을 누르면 그 탭을 고른다.
  - 알리는 것은 completed·failed turn 끝과 권한 물음·질문이다. 사람이 끊은 turn, /clear, compact는 알리지 않는다.
  - Agent 탭도 못 본 turn 끝이면 finished 점이다. main이 못 본 session 목록을 갖고 창에 보낸다. 탭이 보이거나, 다음 turn이 시작하거나, session이 끝나면 지운다. Agent 탭은 mount된 동안 보인다고 main에 알린다.
  - renderer의 권한 물음·질문 toast(`waiting.toast-permission.*`, `waiting.toast-question.*`)를 지웠다. 앱 활성화 동의, 재시작 멈춤, kind 위반 toast는 그대로다.
  - 창 안 toast가 하나도 뜨지 않던 것을 고쳤다. toast(반응 층, hook 설치 성공, 앱 view 알림)는 anchor로 창 전체(y=0부터)를 줬는데 main은 anchor 전체가 본문(상단 bar 36px 아래) 안이어야 열어서 `invalid_input: anchor is outside window body`로 조용히 거절했다(개발 앱에서 같은 요청으로 확인). 같은 이유로 상단 bar의 최소화 칩에서 누른 터미널 닫기 확인 dialog도 열리지 않아 닫히지 않았다. 자리를 main이 정하는 표면은 모두 창 가운데 1px(`overlay/consumer.ts` `centerAnchor`)를 쓴다. 복사본 다섯이 하나가 됐다.

  - 창 단위 toast는 상단 가운데(상단 bar 바로 아래)에서 내려온다(reduced-motion이면 움직이지 않는다). 테두리(`--color-border-strong`)와 `--shadow-dialog`로 바탕과 갈리고, 행동 단추는 닫기 X와 같은 오른쪽 끝선의 따로 한 줄이다(design `Toast`, 탭 안 toast도 같다).
  - agent 알림은 앞에 아이콘(터미널 agent는 harness icon, lophn agent는 그 agent의 profile avatar)이 있고, 제목이 누가 어디서인지 말한다("Claude Code finished · 다운로드", "{agent}'s turn failed · {place}", "{agent} needs permission · {place}"; 어디인지 모르면 뒤를 뺀다). 본문은 마지막 응답의 앞부분(공백을 접고 160자), 권한 물음은 그 명령·도구·질문, 실패는 까닭이다. 줄 것이 없으면 본문이 없다(폴더 이름으로 채우지 않는다). OS 알림도 같은 글이다.
  - 마지막 응답은 harness가 turn 끝 hook payload에 주는 글이다: Claude 꼴(claude, qwen, qoder, codebuddy, kimi, muse, devin)·codex·droid·command-code·antigravity·grok·copilot은 `last_assistant_message`, kiro는 `assistant_response`. lophn이 쓰는 plugin·extension(opencode·kilo·mimocode, pi, omp, amp)은 마지막 응답을 `lophn_message`로 싣는다. transcript 파일은 읽지 않는다. cursor, hermes, cline, letta는 그런 칸이 없어 본문이 없다.
  - lophn agent의 이름·profile·대화 이름·마지막 응답은 main이 알릴 때 core에서 읽는다(`agent-definitions/read`, `sessions/read`, `messages/body`, 질문은 `ask/read`). 올린 그림 profile은 첫 글자 avatar로 보인다.
  - hook CLI는 stdin을 1 MiB까지 읽고 위쪽 글 칸을 4,096자로 자른 뒤 64 KiB를 잰다. 긴 마지막 응답 때문에 turn 끝 신호 전체가 버려지지 않는다.
  - plugin 본문이 바뀌어 이미 놓인 OpenCode·omp 등의 plugin은 다시 설치가 필요하다고 나온다.
  - 알림 단추 panel에 Finished 묶음이 있다. 안 본 사이 끝난 turn(터미널 agent와 lophn agent)이 쌓이고, 누르면 그 탭으로 가며, 그 탭을 보면 빠진다. 탭의 finished 점과 같은 값에서 계산하고 따로 기록을 두지 않는다. 개수 badge가 finished도 센다.

왜: 사람이 창을 보고 있을 때도 다른 탭의 agent가 끝난 것을 알고 싶다고 했다. 창이 여럿일 때 한 번만 알리려면 결정이 한 곳에 있어야 한다.

결정:
- focus면 toast, 아니면 OS 알림이다. 보고 있는 탭은 알리지 않는다. (사람, 2026-10-26)
- 터미널 쪽에서 이미 알리는 coding session은 lophn agent 쪽에서 다시 알리지 않는다. (agent)

## browser 탭 toolbar가 켜진다

```yaml
modules: [packages/shell/renderer]
checked: [architecture-browser-tab]
```

- 전: 일반 browser 탭(`<webview>` guest)의 뒤로·앞으로·새로고침·주소 칸·bookmark 단추가 늘 꺼져 있었고(마우스가 not-allowed), 주소와 제목도 탭에 반영되지 않았다. 2026-10-19 webview 그릇 도입부터다.
- 후: 그릇이 guest의 view session을 첫 `dom-ready`에서 얻는다. guest가 다시 붙어 id가 바뀌면 다시 알린다.

왜: Electron 44.5.1의 `getWebContentsId()`는 `did-attach` 때 "The WebView must be attached to the DOM and the dom-ready event emitted before this method can be called."를 던진다. 그 listener 안에서 session을 정하던 코드가 매번 조용히 끝나 session이 생기지 않았다. 개발 앱에서 숨긴 webview로 `did-attach`는 throw, `dom-ready`·`did-finish-load`는 id를 주는 것을 확인했다.

## lophn이 Deno 없이 Electron의 Node로 돌고, 앱과 flow는 권한 제한 없는 npm project다

```yaml
modules: [packages/base, packages/protocol, packages/core, packages/coding-agent, packages/design, packages/sdk, packages/shell/main, packages/shell/renderer, tools, tests]
checked: []
```

- 전: runtime이 Deno였다. module은 `deno.json`의 import와 workspace가 풀었고, check는 `deno check`·`deno test`였다. 앱과 flow는 Deno 권한 flag로 좁혀 돌았고 SDK를 `lophn-sdk:` import map으로 찾았으며, release 준비는 `deno cache`로 의존을 `vendor/`·`node_modules/`에 받았다. 설치본은 `/opt/lophn/deno`와 `DENO_DIR`을 싣고 launcher가 `deno run`을 불렀다.
- 후:
  - lophn의 모든 process(core와 자식, worker, 앱, flow, 선언 검사·추출, release 준비, CLI)는 Electron의 Node(`ELECTRON_RUN_AS_NODE=1`)로 뜬다. 개발과 test도 `node_modules/electron/dist/electron`이다. 자기를 다시 띄우는 곳은 `nodeCommand`(`packages/core/supervision/security/node-command.ts`) 하나다.
  - module은 root `package.json`의 npm workspaces와 lock 하나로 푼다. type check는 package마다 `tsc --noEmit -p`(옵션은 `tsconfig.base.json`), test는 Electron의 `--test`, 명령은 `npm run check`·`check:full`·`e2e`·`dev`다. `deno.json`과 `deno.lock`은 없다.
  - 앱 source는 npm project다. `package.json`은 정확한 판만 받고 SDK는 `file:.lophn/sdk/<이름>/<판>`이다. lophn이 설치 사본을 `.lophn/sdk`에 실제 file로 복사하고(`syncAppSdk`) npm이 `node_modules/@lophn/*`로 잇는다. 앱 명령은 `npm run check`, `npm test`, `npm run build`, `npm run wording`이다. platform이 npm 11.19.0을 싣고, agent shell의 PATH에는 `<data>/run/bin`의 `node`·`npm` shim이 있다. 그 `npm`은 의존을 까기 전에 SDK 사본을 맞춘다.
  - release bundle은 commit의 file, `.lophn/sdk`, `npm ci`(또는 `npm install`, install script 없이)가 만든 `node_modules`, esbuild로 지은 화면, `lophn-entry.ts`다. 앱 process는 그 사본 root에서 권한 flag 없이 뜬다.
  - flow는 `<data>/projects/node_modules/@lophn/flow` symlink로 SDK를 찾고, `workflow.check`는 platform의 `tsc`다.
  - 앱과 flow에는 권한 제한이 없다. Deno flag를 계산하던 code와 sandbox test를 지웠다.
  - 설치본은 Electron, platform source, production `node_modules`다. `deno` binary와 `DENO_DIR`은 없다.
  - eval: Deno 앱 source를 가진 재료 다섯(`calendar-app`, `calendar-app-bug`, `notify-app`, `calendar-data`, `date-range`)과 그것을 world로 쓰던 scenario 여덟을 지웠다.
- 같이 고친 bug:
  - 바쁜 기계에서 core가 멈추지 않았다. `node:http`의 `close`가 요청을 아직 보내지 않은 connection을 끝없이 기다렸다. 받은 요청이 끝나면 남은 connection을 닫는다(`packages/core/server/serve.ts`).
  - 앱을 만들 때 network가 없으면 npm이 몇 분씩 다시 시도해 `app.create`가 멈췄다. 2분에 끊는다.

왜: Deno의 권한 flag는 막는 것이 없었고(`shell.run`은 사용자 uid로 돈다, static import는 읽기 허락을 건너뛴다) 쓰기만 불편했다. 사람이 Deno를 떠나 Electron의 Node 하나로 가고, 앱과 flow의 권한을 막지 않기로 했다.

결정:
- Deno를 떠나 Electron의 Node로 간다. 앱과 flow는 network를 포함해 권한을 막지 않는다. OS sandbox는 두지 않는다. Deno 앱 source를 가진 eval 재료는 옮기지 않고 버린다. (사람)
- 개발과 test도 Electron의 Node다. production이 Electron이고, 이 기계의 `node` 24.20에는 `packages/core/jobs/schedule.ts`가 쓰는 `Temporal`이 없다. (agent)
- SDK 사본을 앱 폴더 안 `.lophn/sdk`에 실제 file로 두고 npm `file:` 의존으로 건다. Node는 `node_modules` 안의 `.ts`를 돌리지 않고, SDK의 npm 의존은 사본의 실제 경로에서 앱 `node_modules`로 올라가 풀려야 한다. (agent)
- release 준비의 npm은 install script를 돌리지 않는다. bundle에는 설치된 file만 필요하다. (agent)
- 펼친 `@types/node`는 Electron의 Node에 맞춰 24로 고정한다. Biome의 React rule은 꺼 둔 채다(`package.json`에 react가 오르면 저절로 켜진다). (agent)
- brief와 lead worktree 없이 주 session이 wave마다 worker를 띄웠다. wave 1 열다섯과 정리 하나, module 해석 하나, wave 2 여덟, wave 3 아홉, wave 4 넷. core 뒤집기와 wave 3 계약은 사람 요청으로 주 session이 직접 했다. (사람)

## lophn 자신의 자식 process가 모두 권한을 좁히지 않고 뜬다

```yaml
modules: [packages/core/supervision, packages/protocol, packages/core/apps, packages/core/main, packages/core/projects, packages/base, packages/coding-agent]
checked: []
```

- 전: apps supervisor, platform I/O child, kinds worker는 launch spec의 per-kind 권한 칸(`allow_read` … `net_any`)으로, 정비 자식, data job, release 준비 runner와 app-build 자식, `lophn` CLI launcher는 각자 짠 `--allow-*` 목록으로 Deno 권한을 좁혀 떴다. CLI는 `harness` 명령마다 권한 계획 entry(`launch-entry.ts`)를 한 번 더 띄웠다.
- 후: 모두 `--allow-all`로 뜬다(`--no-prompt`, `--cached-only --frozen`, `--config`는 그대로). launch spec은 kind, entry, policy, memory 한도뿐이고 `launchArgv`가 늘 `--allow-all`을 붙인다. CLI launcher는 `hook`의 빠른 길(`LPN_TERMINAL_HOOK`이 없으면 deno를 띄우지 않는다)만 남았다. AI가 쓴 코드를 돌리는 process(앱, preview, flow, 선언 검사·추출, release 준비의 선언 eval)의 flag는 그대로다.

왜: 좁힌 권한은 막는 것이 없었다(`shell.run`은 갇혀 있지 않다). Node로 옮기는 계획 `node-api`가 이 process들의 코드를 `node:*`로 바꾸면 Deno의 node 호환이 권한을 더 요구해(`node:child_process`가 env 권한을 요구했다) 좁힌 child만 깨진다(`project-docs/products/roadmap/node-runtime.md`).

결정:
- lophn 자신의 process는 권한 flag 없이 돈다. Node로 뒤집은 뒤에는 flag 자체가 없다. (agent)

왜: Deno를 떠나 Node 하나로 가기로 했다(사람, 2026-10-27). runtime을 뒤집기 전에 Deno 위에서 API와 도구를 먼저 옮겨, 옮기는 동안 `deno task check`와 e2e가 늘 통과하게 했다. 다음 계획 `node-flip`이 module 해석, runtime, 앱·flow sandbox, 설치본을 바꾼다.

결정:

- `Deno.errors` 대신 code를 비교한다. Deno API 오류와 `node:*` 오류가 같은 code를 실어 file마다 따로 옮겨도 판정이 맞는다. (agent)
- 자식 process는 `spawn`·`spawnSync`로 띄운다. Deno의 `execSync`는 `--allow-run`을 좁히면 실패한다. (agent)
- Biome 형식은 `deno fmt`에 맞췄고(2칸, 80자, 큰따옴표), 고칠 코드가 생기는 lint 규칙은 껐다. md·css·svg·html은 형식을 맞추지 않는다. (agent)

- coding agent 연결 장치의 coding session 층을 지운다. 사람이 연 터미널의 agent 층은 남긴다. (사람, 2026-10-28)

## Claude와 Google Antigravity 구독 계정으로 provider를 연결함

```yaml
modules: [packages/protocol, packages/core/lophn-agent, packages/shell/renderer]
checked: [boundary-catalog, architecture-layers, architecture-testing, tool-e2e, tool-test-live, tool-eval, tool-check-deps, architecture-terminal-agent, architecture-browser-tab, architecture-agent-chat, architecture-artifact, architecture-workspace-layout, architecture-appearance, tool-worktree-prep, tool-dev, tool-package-linux, skill-ui-design, tool-wireframes]
```

- 전:
  - 구독 OAuth는 ChatGPT와 SuperGrok뿐이었다. `anthropic` 정의는 API key만 받았고 Google은 API key의 OpenAI 호환 `google-gemini`뿐이었다.
  - protocol은 셋(`anthropic-messages`, `openai-responses`, `openai-chat-completions`)이었다.
  - callback listener는 127.0.0.1의 빈 port에서 path와 state를 보지 않고 첫 callback 하나를 받았다. 틀린 callback 하나가 로그인을 끝냈다.
  - refresh는 발급자의 답을 기다리는 사이 연결이 바뀌어도 그 token을 저장했고, 저장이 한 번 실패하면 받은 token을 버렸다.
- 후:
  - `OAuthDefinition`에 product 둘이 생겼다. claude `{client_id, authorization_endpoint, token_endpoint, account_endpoint, redirect_uri, scopes}`, antigravity `{client_id, client_secret, authorization_endpoint, token_endpoint, userinfo_endpoint, redirect_uri, scopes}`. `redirect_uri`는 port가 있는 loopback http다. 둘 다 flow `pkce_loopback`이다.
  - `anthropic`이 `oauth`(product `claude`)도 받는다. 새 내장 정의 `google-antigravity`는 `oauth`만 받고 protocol은 새 `cloud-code-assist`다. Antigravity의 client_secret은 공개 배포된 installed-app 값이라 정의 data에 둔다.
  - credential에 `account` 칸(`{id, email, organization_id, organization_name, project_id}`, OAuth만, 모르면 null)이 생겼다. ConnectProvider가 선택 칸 `account`를 받고 core의 로그인 처리기만 싣는다. schema: `provider_credentials.account`, `providers.protocol`이 `cloud-code-assist`를 받는다.
  - Claude 로그인: 고정 callback `localhost:54545/callback`(127.0.0.1과 ::1을 함께 쥔다), authorize에 `code=true`와 scope 여섯, JSON 교환(callback state를 싣는다). token 응답에 계정·조직이 빠지면 bootstrap으로 빈 칸만 채우고 실패해도 이어 간다. refresh는 JSON에 OAuth beta와 SDK User-Agent를 붙인다.
  - Antigravity 로그인: 고정 callback `127.0.0.1:51121/oauth-callback`, offline·consent, form 교환에 client pair. refresh token이 없으면 `unauthorized`(reauth_required)로 연결하지 않는다. userinfo로 email, `loadCodeAssist`로 project를 찾고 tier가 없으면 free-tier `onboardUser`를 보내 operation을 30초 안에서 1초마다 본다. 마지막 `loadCodeAssist`의 project만 저장하고 없으면 `unavailable`(project_missing)이다. free-tier 거절 이유는 `forbidden`(account_validation)과 https Google 주소일 때만 검증 주소로 낸다. refresh는 project를 다시 찾지 않고, project 없는 credential은 갱신하지 않는다.
  - 계정 model 목록: Antigravity는 연결 직후와 갱신 뒤에 `fetchAvailableModels`의 key(내부용·꺼진 줄 제외)를 `reported_models`에 둔다.
  - Claude 구독 호출은 Claude Code client profile로 보낸다(`providers/adapters/claude-code.ts`): `/v1/messages?beta=true`, Claude Code header 묶음, system 앞 billing·identity block, custom tool 이름 앞 `_`와 응답 이름 되돌리기, `metadata.user_id`, host가 만든 billing slot에만 쓰는 cch(XXH64, `adapters/xxh64.ts`). API key 호출은 그대로다.
  - Antigravity 호출(`providers/adapters/cloud-code.ts`): 이력을 contents/parts로 옮기고 envelope `{project, requestId, request, model, userAgent}`로 감싼다. tool 결과는 call 순서대로 user turn 하나, tool schema는 Cloud Code 부분집합, effort `low`·`medium`·`high`는 `thinkingLevel`이다. SSE는 `{"response": …}` frame이고 root error, prompt 차단, finishReason 없는 끝은 성공이 아니다. Google RPC status(`UNAVAILABLE`, `RESOURCE_EXHAUSTED` 등)를 stream 실패 분류에 더했다. output 상한은 보내지 않는다. project 없는 credential로는 turn을 시작하지 않는다.
  - callback listener(`openCallbackListener`)가 선택 칸 `{hosts, port, path, state}`를 받는다. 구독 로그인(ChatGPT 포함)은 path와 state를 넘겨, 맞지 않는 callback을 400으로 돌려보내고 기다림을 잇는다. 그 state의 `error`만 로그인을 끝낸다. 정한 port를 다른 프로그램이 쓰면 `conflict`(callback_port_in_use)다. MCP·앱 OAuth는 옵션을 넘기지 않아 그대로다.
  - refresh는 답을 받은 뒤 provider를 다시 읽어 `logged_in_at`이 바뀌었으면 늦은 token을 저장하지 않는다. 받은 token의 저장은 같은 값으로 세 번까지 다시 해 본다. 발급자 HTTP 공통 함수는 `providers/issuer-http.ts`로 옮겼다.
  - 화면: 단추 이름에 Claude와 Google Antigravity가 생겼다. 내장 정의의 연결 주소는 model 목록 주소의 마지막 칸을 뗀 것이다(`/models`가 아니어도 된다).

왜: 사람이 Claude와 Antigravity 구독으로 lophn의 model 호출을 하려 했다.

결정:
- Claude 구독 OAuth와 Antigravity를 provider로 넣는다. 0.2.0의 "Claude 구독 로그인은 두지 않는다"와 `roadmap/subscription-oauth.md`의 옛 추천(넣지 않는다)을 뒤집는다. Anthropic은 제3자 앱의 Claude.ai 로그인과 구독 credential 사용을 허락하지 않고 Cloud Code `v1internal`은 공개 API가 아니다. (사람, 2026-10-29)
- clean room으로 만든다. `research_notes/omp-subscription-oauth/`의 README와 구현자용 문서 넷(implementation-spec, claude-code, google-antigravity, fixtures)만 보고 원본 코드, 분석 문서, 웹은 보지 않았다. (사람, 2026-10-29)
- Claude Code client profile(header, system block, tool 이름, cch)을 명세 snapshot대로 넣는다. 서버가 어느 칸을 검증하는지 모르고, 빼면 구독 경로로 판단되지 않을 수 있다. 버린 길: profile 없이 Bearer만. (agent)
- Claude는 `anthropic` 정의에 OAuth를 더하고 Antigravity는 새 정의다. Claude 구독도 같은 Anthropic Messages endpoint이고, Antigravity는 endpoint·protocol·model 이름이 Gemini API와 다르다. (agent)
- 계정은 secret meta가 아니라 credential 칸에 둔다. model 호출(project, account uuid)이 runtime에서 읽어야 하고 비밀이 아니다. (agent)
- refresh lead는 지금의 5분 하나로 둔다. 명세의 snapshot은 응답 TTL에서 6분 앞을 갱신 시점으로 쓴다. (agent)
- 고정 port가 차 있으면 다른 port로 넘어가지 않고 `conflict`다. 발급자가 다른 port의 redirect를 받는지 확인하지 않았다. (agent)
- 첫 구현에서 뺀 것: subscription quota 조회, 401 뒤 한 번 다시 보내기, daily → sandbox failover, 사람이 code를 붙여 넣는 로그인, client version 자동 갱신, Antigravity roster의 model별 상한·thinking profile, thought signature 보존(대신 Gemini functionCall에 서명 검사 건너뛰기 표시). (agent)

후속:
- 실제 계정으로는 아무것도 확인하지 않았다. 남은 일은 `roadmap/subscription-oauth.md`에 있다.
- 개발 data(`.dev-data/`)는 지우고 새로 만든다(schema가 바뀌었다).

## 입력 예산을 실제 token에 가깝게 세고, 넘치면 turn 안 결과를 줄이고 다음 turn 전에 자동으로 Compact한다

```yaml
modules: [packages/core/lophn-agent, packages/core/main, packages/protocol]
checked: [architecture-place-session, architecture-run, architecture-agent-chat, architecture-layers]
```

- 전: 입력 예산은 wire JSON의 UTF-8 byte를 그대로 token으로 셌다. 영어·code는 byte가 token의 3~4배라 200k 창 model이 실제 약 5만 token에서 `context_limit`으로 막혔다. 넘치면 turn이 그대로 끝났고, turn 안 tool loop는 줄일 길이 없었다. Compact는 사람이 부를 때만 했고 요약 상한도 byte로 세어 약 1k token이었다.
- 후:
  - 입력 예산은 같은 turn 앞 call의 실제 prompt token(`input + cache_read + cache_write`)에 늘어난 byte를 더해 잰다. 앞 call이 없으면 byte/3이다. 이미지는 그대로 하나에 4096이다. compact 요약의 chunk와 본문 상한(`min(예산/10, 4000)`)도 같은 세기다.
  - 조립한 요청이 예산의 85%를 넘으면 turn 안 가장 오래된 tool 결과부터 본문을 고정 문장으로 바꿔 60% 아래로 내린다. 최근 결과 묶음 둘과 `skill.read` 결과는 그대로다. provider가 입력이 크다고 거절하면 같은 방식으로 줄여 다시 보낸다(turn마다 두 번까지).
  - turn의 첫 call이 예산의 절반보다 크고 이전 대화가 예산의 5분의 1 이상이면, 또는 turn이 `context_limit`으로 끝나면, 그 session의 다음 turn을 시작하기 전에 runtime이 Compact한다. `RequestSessionCompact`의 actor에 `machine`이 더해졌다. agent는 여전히 열 수 없다.
  - 요약 지시: 앞 요약이 있으면 갱신하고, 끝에 답을 기다리는 질문·요청은 그대로 남긴다. "token은 UTF-8 byte로 센다" 문장을 지웠다.

왜: 넘치는 곳은 거의 turn 안이다(앱 짓기 turn은 call 약 100번, tool 결과 하나 약 24 KiB). turn 사이 이력은 글뿐이라 turn 사이에 Compact하면 된다. OMP 분석(`research_notes/omp-cache-compaction-tool-loading/compaction.md`)의 threshold·prune·overflow 회복을 lophn 모양으로 줄였다.

결정:
- context가 넘칠 때 lophn이 사람 없이 줄인다: turn 안은 오래된 tool 결과 본문을 바꾸고, turn 사이는 자동 Compact한다. (사람, 2026-10-29)
- 실제 provider로 확인하는 일(cache, OAuth TTL, OpenAI tool search)은 보류한다. (사람, 2026-10-29)
- 앞 call이 없을 때 byte/3으로 센다. 영어·code와 한국어 모두 대개 실제보다 크게 센다. 낮게 센 경우는 provider overflow 회복이 받는다. (agent)
- 줄인 결과의 원문은 tool 호출 기록에 그대로 두고 model 입력에서만 바꾼다. model은 필요하면 tool을 다시 부른다. 버린 길: model로 turn 안 tool loop를 요약하기(호출이 하나 더 들고 요약이 틀릴 수 있다). (agent)
- 자동 Compact 판단은 runtime 메모리에 둔다. runtime이 다시 뜨면 잊고, 넘치는 turn이 다시 정한다. 저장하면 표나 칸이 하나 더 는다. (agent)
- 자동 Compact는 pump가 다음 turn을 시작하기 직전에 그 session에만 한다. 끝난 turn 뒤에 바로 요청을 열면 같은 순간 새 입력이 turn을 시작해 요청이 실패한다. (agent)

후속: `project-docs/plan/context-cache/`의 나머지(cache 표시 위치, OpenAI cache key, OAuth TTL, OpenAI tool 지연)는 그대로 남는다.

- 후:
  - 놓인 제품에 [Uninstall hooks]가 있다. CLI `lophn harness uninstall`(입력 `{harness}`, 출력 `{hook: removed|unchanged|not_supported|failed, files}`)이 우리 항목만 지운다. 규칙은 `architecture/coding-agent.md`다. IPC op `uninstall_hooks`, `CodingApi.uninstallHooks`가 생겼다.
  - CLI `lophn harness status`(입력 `{command?}`, 출력 harness마다 `{harness, skill, hook, files}`)가 모든 harness의 dry_run을 한 process에서 돈다. shell main의 hook 상태는 이 호출 한 번이다(약 0.25초).
  - 검색 칸과 표 사이, 표와 아래 안내 사이를 띄웠다.
  - Settings sidebar는 project 창 sidebar의 panel 꼴(`project-sidebar.module.css`)이다. 묶음(General, Agents, System)마다 제목과 항목 줄을 모두 놓는다. 위쪽 바의 단추로 접으면 항목 아이콘만 project 창의 `ActivityBar` 꼴로 남는다.

왜: 사람이 hook을 지우는 길을 요청했다. 화면에 들어갈 때 느린 원인은 harness마다 띄우던 process였다. sidebar는 사람이 shell sidebar 꼴로 바꾸되 묶음을 아이콘으로 나누지 말고 모두 줄지어 놓으라고 했다.

결정:
- 지우기는 놓을 때처럼 묻지 않는다. 누른 것이 허락이고 다시 놓을 수 있다. (agent)
- Codex에서 우리 group을 지우면 뒤 group의 trust 기록 key를 당겨진 위치로 옮긴다. 버린 길: 우리 기록만 지우기(다른 도구의 hook을 Codex가 조용히 건너뛴다). (agent)
- Settings sidebar는 묶음을 activity bar 아이콘으로 나누지 않고 panel에 모두 줄지어 놓는다. (사람, 2026-10-29)

후속: 없음.

## Explorer의 펼친 폴더가 저절로 닫히지 않고, sidebar scrollbar 위의 wheel과 끌기가 먹히지 않는다

```yaml
modules: [packages/shell/main, packages/shell/renderer]
checked: []
```

- 전:
  - 폴더를 열여섯 개쯤 넘게 펼치면 3초마다 몇 개씩 저절로 닫혔다. `useFileTree`는 펼친 폴더마다 `list`를 한꺼번에 보내고, shell main의 file adapter는 `list`마다 core `projects/list`를 불러 연결 폴더를 읽었다. core의 principal당 HTTP 동시 한도(16, queue 없음)를 넘은 호출이 `unavailable`이 되고, `useFileTree`는 이미 읽은 폴더의 실패를 이유와 상관없이 "폴더가 사라짐"으로 보고 펼침을 지웠다. 같은 순간의 renderer core 호출도 `unavailable`로 졌다.
  - Explorer scrollbar의 오른쪽 반(8px 중 3px)이 sidebar 폭 resizer 밑에 깔려, 그 위의 wheel은 scroll하지 않고 thumb을 끌면 scroll 대신 폭 끌기가 시작했다.
- 후:
  - file adapter는 같은 순간의 `list`들이 연결 폴더 읽기 한 번을 나눠 쓴다(`connectedFolders`). 펼친 폴더 200개를 다시 읽어도 core 호출은 한 번이다.
  - `useFileTree`는 `not_found`일 때만 펼친 하위 폴더를 닫는다. 다른 실패면 앞서 읽은 항목을 둔다.
  - sidebar 본문은 오른쪽에 resizer 안쪽 반만큼(4px) margin을 둔다. resizer 자리와 잡는 폭은 그대로다.

왜: 사람이 개발 앱에서 쓰다 찾았다. 원인은 worktree 앱(CDP)에서 재현해 확인했다. 동시 `list` 40개 중 20개 안팎이 `unavailable`, 펼친 폴더 20개가 6초 만에 9개로 줄었고, scrollbar 위 x=293~295에서 wheel이 듣지 않았다.

결정:
- 연결 폴더 목록을 cache하지 않고 동시에 도는 읽기만 합친다. 프로젝트 폴더를 고치면 다음 `list`가 바로 새 목록을 본다. (agent)
- core HTTP 한도는 그대로 둔다. 한도는 남이 core를 막지 못하게 하는 장치이고, 문제는 한 사람의 동작 하나가 core 호출 N개로 불어난 것이다. (agent)

후속: 칸 경계(`panes.module.css`의 `.grab`)와 floated 패널 오른쪽 손잡이(`float-panel.module.css`의 `.e`)도 왼쪽 칸·패널 본문 scrollbar를 덮는다(각 4px, 6px). sidebar처럼 본문을 비우는 것이 맞는지는 editor(CodeMirror)가 scroller를 직접 갖고 있어 따로 정한다.
