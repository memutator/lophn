## 4. OAuth (commit cd5c5e78d, Oct 17 2026)

- Flows: ChatGPT = PKCE S256 with 127.0.0.1 loopback callback `/auth/callback` (`providers/oauth.ts:3-8,140`), client registered as `dynamic_agent_client`, id_token verified via JWKS, requires scope `chatgpt.tokens.use.direct`; SuperGrok = RFC 8628 device code. Routes (actor user): `providers/login-begin` -> `{login, flow, interval_ms, expires_at, sign_in:{url, user_code}}`, `providers/login-complete` (poll; pending or connected provider), `providers/login-cancel` (`protocol/lophn-agent/providers.ts`, schemas `provider-inputs.ts:106-135`). The caller opens `sign_in.url` in a browser and polls `login-complete` at `interval_ms`; core then saves tokens and calls ConnectProvider itself (`providers/login.ts:90-130`), so tokens never pass the caller. After connect, the caller still sets `modelDefaultChange` (`fake-oauth/login.ts:56-62`).
- Storage: plain file `<data root>/secrets.json`, mode 0600, flat JSON name->string, atomic tmp+fsync+rename (`packages/core/secrets/file-store.ts:1-12`, `SECRET_FILE_NAME` in `protocol/secrets/secret-file.ts:14`). Names: `provider.<id>` (access), `provider.<id>.refresh`, `provider.<id>.meta` (`{client_id, subject}`), plus `provider-oauth.host-id` (per-install uuid for ChatGPT login) (`providers/oauth-secrets.ts`). Provider record (ledger `lophn.db`) holds credential state/`expires_at`. NO OS keychain, NO DBUS use, no env fallback ("환경 변수·다른 파일 fallback은 없다"). The only DBUS/XDG hit is `main/daemon/wiring/supervision.ts:96` forwarding `DBUS_SESSION_BUS_ADDRESS`/`XDG_RUNTIME_DIR` to app test (systemd-run), unrelated to secrets. => `bootCore`'s `clearEnv` + empty HOME does NOT break a logged-in data root; a root logged in once boots fine under bootCore.
- Refresh: `providers/oauth-refresh.ts`. Triggered lazily when the agent runtime asks for the secret `provider.<id>` (hook `providerOAuth: refresher.prepareToken`, `main/daemon/wiring/lophn-agent-runtime.ts:239`); if `expires_at - now <= leadMs` (5 min, `OAUTH_REFRESH_LEAD_MS`, `:194`) it sends `refresh_token` grant, saves the rotated refresh token FIRST then the access token, then records new `expires_at`. One refresh in flight per provider (`flights` map). Issuer 400/401/invalid_grant -> credential `refresh_revoked` and the token is withheld (turn fails `configuration_unavailable`); network/5xx errors -> falls back to current token if still valid. Refresh tokens rotate, so: (a) never copy/fork a logged-in data root (the copy and original would both hold a stale refresh token after either refreshes); (b) never run two cores on the same root (also blocked by the single-instance rule); (c) a root idle longer than the refresh token lifetime needs re-login (lifetime not documented in repo).
- `tests/support/fake-oauth/` (`mod.ts` ~250 lines, `login.ts` 62, `issuer_test.ts`): `startFakeIssuer()` loopback Deno.serve with `/device/code`, `/token` (authorization_code, device_code, refresh_token grants with required form fields), `/jwks`; scripted per-grant reply queues; `definition("chatgpt"|"supergrok")` returns a provider definition whose issuer URLs point at the fake (Anthropic-protocol, key "anthropic" so the fake model server can answer); 400 + journal mismatch on unscripted requests. `connectOAuthProvider(core, issuer, fake, {expires_in})` does loginBegin(supergrok) -> poll loginComplete -> modelDefaultChange. Used only by `tests/e2e/oauth_test.ts` (7 tests).
- `oauth-live` path needs: (1) a task (e.g. `deno task live:login`) that boots core on `.dev-data/live/home` via a hand-made `Run` (as in `tools/dev.ts:117-123`), reads the builtin definition, calls `login-begin`, prints `sign_in.url`/`user_code` for the human (ChatGPT: the loopback listener needs the browser on the same machine; headless/remote needs a port-forward), polls `login-complete`, sets the default model, stops core cleanly (`core.stop()`); (2) live/eval tasks that boot that root with `bootCore` (providers already connected; no connect step), verify with `providerList`/`providerRead` that `credential.state === "available"` and kind oauth else print "run live:login" and exit 0; (3) runtime caveat: the model call itself is made inside the agent runtime child, which gets the token through the core refresher hook, so nothing special in env; (4) cost kind will be `subscription`, not `reported/estimated` (`COST_KINDS`), so per-run USD cost is unknown for subscription roots; use tokens + call counts as the budget unit there.

## 10. Other facts worth knowing

- The key rule is satisfied naturally: the eval *runner* process may read `.env` (via `--env-file`), pass the key to `core.upload(...)` (stdin/body only, `Core.upload`), and `bootCore` keeps core env clean. Alternative: a one-time `live:login`-style task stores the API key in the live root's `secrets.json` too, so eval never needs `.env` at all (then only the first-time human step reads it).
- Secrets redaction: core redacts known secret values in blobs/log; eval artifacts (grading reports) should go through `scrub`-like handling if they include model transcripts.
- Egress: E2E core's agent runtime child can only reach connected provider hosts; real-network behavior for tools like web fetch is not part of E2E (rule 9: "인터넷은 막는다").
- Sandboxing of `run.remove()`: `removeDir` chmods before delete because core installs sdk copies read-only (`mod.ts:97-110`); a persistent live root must never be passed to `run.remove()`.
- Linux-only `/proc` scan means eval is Linux-only like E2E.
