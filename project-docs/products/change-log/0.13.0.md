# 0.13.0

## activation이 실패한 이유가 agent에게 간다, 앱 source와 겹치는 경로 규칙을 지웠다

```yaml
modules: [packages/core/apps, packages/core/router, packages/protocol]
checked: []
```

- 전:
  - 앱 grant를 만들 때 앱 source를 감싸거나 그 안인 `fs.read`·`fs.write` 경로를 `forbidden("path covers an app source")`로 거절했다. 이 검사는 activation의 마지막 commit(`activation.complete`)에서만 돌아서, 선언 검사와 사람의 동의, 새 앱 준비 확인을 다 지난 뒤에 떨어졌다. `~/.lophn`을 읽겠다는 선언은 그 안에 앱 source가 있다는 이유로 늘 거절됐다.
  - complete가 거절되면 실패 기록은 `commit_rejected: the new release was not adopted`뿐이었다. 거절 message는 버려졌다.
  - 동의가 필요한 activation은 `release.activate`가 `waiting_consent`를 돌려주면 끝이었다. 동의 뒤의 결과는 아무도 agent에게 알리지 않았다. 사람은 동의를 눌러도 대화에서 아무 말도 듣지 못했다.
- 후:
  - source와 겹치는 경로 규칙을 지웠다. `~/.lophn`을 지키는 장치는 사람의 동의 화면뿐이다.
  - complete가 거절되면 summary에 거절 message를 붙인다(`the new release was not adopted: <message>`).
  - `release.activate`가 기다리지 않은 시도(동의 뒤, 2분 기다림 상한 뒤, 재시작 뒤 이어받음)가 active나 failed로 끝나면 driver가 새 machine command `activation.report`를 부른다. 이 command는 release를 만든 agent session(`created_by`)에 새 notice 종류 `activation_finished`로 결과를 넣는다. 실패면 code, summary, 이전 release가 다시 도는지가 들어간다. Router의 `RouteInput`이 `notice`를 싣는다.

왜: mahas 앱의 release 6·7이 사람이 동의한 뒤에도 매번 `commit_rejected`로 떨어졌는데, 사람도 agent도 이유를 들을 길이 없었다.

결정:
- 앱 source와 겹치는 경로 규칙은 지운다. 사람이 정했다. 막아야 하는 것은 앱 code 쓰기와 data root(`secrets.json`, 다른 앱 data)인데 이 규칙은 그것을 정확히 막지 못하고, source가 마침 안에 있는 경로만 막았다. data root를 지키는 규칙은 아직 없다.
- 결과는 release를 만든 session에 알린다. 동의 표에는 부른 session이 없고, release를 만든 session과 activate를 부른 session은 보통 같다. 버린 길: 동의 표에 session을 더하기(schema migration이 필요하다). (agent)

후속: 없음.

## 화면 색·단추 일관성: Ink는 무채색, danger는 채운 빨강, 글자 단추에 행동 아이콘, 단추 묶음은 오른쪽

```yaml
modules: [packages/design, packages/shell/renderer, tools]
checked: []
```

- 전:
  - 기본 accent Ink에서 primary 단추는 검정·흰색인데 focus 테두리·고른 탭 강조선·selection·내 말 bubble은 파랑이라 primary 색이 둘로 보였다. 몇몇 강조선과 marker(tab strip, sidebar, tree, 진행 띠)는 `--color-text-*`나 `--color-focus`를 써서 accent를 바꿔도 따라오지 않았다.
  - `Button`의 `danger`는 빨간 글자 테두리 단추였다. 승인 카드의 Deny도 danger였고, 지우기 확인 중 몇은 primary였다.
  - 글자 단추 176개 중 142개가 아이콘이 없었다. 저장·취소 순서와 묶음 위치가 화면마다 달랐다(Save가 왼쪽, Settings 줄 단추가 칸 왼쪽).
- 후:
  - Ink preset의 `color.focus`·`color.selection`·`color.ink.soft`가 회색이다. 다른 accent는 그대로다. 주 행동·고른 것·켜진 것의 표시는 모두 `--color-ink-background`, `--color-focus`는 focus ring·입력칸 focus 테두리·drop 자리에만 쓴다.
  - 새 token `color.danger`(background·text·hover). `danger` 단추는 채운 빨강에 흰 글자다. 되돌릴 수 없는 일을 실제로 하는 단추(지우기 확인, Rewind, 연결 끊기, 값 지우기)에만 쓰고, Deny·Skip은 secondary다.
  - renderer `icons/action.ts`의 `actionIcons`로 같은 동사에 같은 아이콘을 붙인다. Cancel·Close 같은 닫기 단추만 글자뿐이다. `retryIcon`(chrome)을 지우고 `actionIcons.retry`로 합쳤다.
  - 단추 묶음은 오른쪽 끝, 닫기가 먼저고 주 단추가 오른쪽 끝이다.

왜: 사람이 Ink에서 파란 강조를 보고 accent가 blue라고 알았다. 색 역할과 단추 모양이 화면마다 달라 일관성이 떨어졌다.

결정:
- Ink에서는 focus도 무채색이다. 버린 길: focus만 파랑으로 남기기(화면에 accent가 둘로 남는다). (사람)
- bookmark 줄의 Remove는 바로 지우지만 secondary(휴지통 아이콘)다. 줄마다 채운 빨강이 서면 과하다. (agent)
- 탭 줄 resizer·칸 divider·drop 표시는 끌기 신호라 `--color-focus`로 둔다. (agent)
- 켠 토글(`aria-pressed`)은 `Button`·`IconButton`이 variant와 상관없이 selection 바탕에 accent 테두리로 그린다. effort 고르기와 도구 막대 토글이 같은 모양이다. (agent)
- design `Toast`의 action이 `icon`을 받는다. 파일 충돌 toast(Compare·Use disk·Keep mine)와 domain Undo에 붙였다. 앱이 준 label에는 붙이지 않는다. (agent)
- Workflow Stop은 instance를 `stopped`로 닫아 되돌릴 수 없으므로 danger다. (agent)
- `actionIcons.rewind`는 기록을 그 시점으로 되돌리기(History), `actionIcons.reset`은 기본값으로 되돌리기·Undo(Undo2)다. (agent)

후속: 없음.

## 앱 panel이 탭과 한 면으로 이어진다, 앱 icon, activity bar에 앱 panel 고정

```yaml
modules: [packages/shell/renderer/workspace, packages/shell/renderer/app-frame, packages/shell/main/workspace, packages/core/apps, packages/protocol/apps/declaration, packages/core/apps/packages/template]
checked: []
```

- 전:
  - project 창의 앱 panel 탭은 탭 줄 아래에 앱 이름·Live·연결 상태 줄(`ViewChrome`)이 늘 있었다. 그 줄과 앱 화면의 바탕이 달라 탭과 본문이 한 면으로 이어지지 않았다. 앱 template의 화면 바탕은 `base.css`·`AppShell`의 `--color-surface-floor`라 탭 본문(`--color-surface-base`)보다 어두웠다.
  - 앱에는 icon이 없었다. 앱 panel 탭은 늘 기본 아이콘, 런처와 place switcher는 첫 글자와 색이었다.
  - 앱 panel은 탭 줄의 + → App panel → 고르기로만 열었다.
- 후:
  - 앱 panel 탭은 화면이 멈추거나 crash했을 때, 앱이 멈췄을 때만 `ViewChrome`을 띄운다. 앱 template에 `src/surface.css`가 생겨 앱 바탕이 `--color-surface-base`다. 앱이 고치거나 지울 수 있다.
  - 앱 선언에 선택 칸 `icon`(bundle 안 경로, svg·png·webp)이 생겼다. release 준비는 그 파일이 commit에 있고 64 KiB 이하인지 본다. core read `apps.icon`이 active release의 icon을 base64로 준다. bundle 밖 경로·symlink, 큰 파일, 선언 없음은 `null`이다. 앱 panel 탭, activity bar의 고정 앱, 런처, place switcher가 그 icon을 쓴다.
  - activity bar 아래쪽(바로 가기와 Settings 사이)에 project마다 앱 panel을 고정한다. 앱 panel 탭의 탭 menu "Pin to activity bar"나 묶음 끝의 +로 더하고, right-click "Unpin from activity bar"로 뺀다. 누르면 같은 앱·화면 탭이 있으면 그 탭으로 가고 없으면 새로 연다.
  - layout 파일이 판 7이고 `rail_apps`가 있다. 판 5·6 파일은 읽을 때 판 7로 올린다.

왜: lophn은 탭과 본문의 바탕을 맞춰 한 면으로 보이게 하는데, 앱 panel만 그 사이에 다른 바탕의 줄과 더 어두운 화면이 끼었다. project마다 자주 쓰는 앱 화면을 매번 + 메뉴에서 고르는 것도 번거로웠다.

결정:
- 크롬 줄은 지우지 않고 문제가 있을 때만 띄운다. 멈춘 화면을 다시 여는 [Open again]이 그 줄에만 있다. (agent)
- 앱 바탕은 `@lophn/ui`가 아니라 template에서 맞춘다. 같은 판의 SDK byte를 바꾸면 기존 앱의 `npm ci`가 깨지고, 판을 올리면 `app-ui`·shell·template 고정이 같이 바뀐다. 사람이 강제하지 말라고 했다. 이미 만든 앱은 그대로다. (사람, agent)
- 고정 앱은 desk가 아니라 project 단위로 layout 파일에 둔다. 등록은 탭 menu와 + 둘 다, 누르면 있는 탭으로 간다. (사람)
- `icon`은 `@lophn/declaration` 판을 올리지 않는다. 선언 검증기 파일이 바뀌어도 판을 올리지 않던 앞선 변경을 따른다. 선언에 icon이 없으면 칸을 두지 않아 옛 선언의 hash가 그대로다. (agent)

## `/status` 창 점유가 Compact 뒤, model을 바꾼 뒤, call 사이에도 맞는다

```yaml
modules: [packages/core/lophn-agent, packages/protocol, packages/shell/renderer]
checked: []
```

- 전:
  - `ReadSessionStatus.context`는 마지막으로 끝난 판단 call의 `input + cache_read + cache_write`와 그 call의 `context_limit`이었다. Compact의 요약 call은 `organizing`이라 빠져서, Compact 뒤 다음 call까지 줄기 전 크기가 그대로 보였다. 그 call 뒤의 답, tool 결과, 새로 받은 메시지는 세지 않았다. model을 바꿔도 한도는 옛 model 것이었다.
  - footer와 panel의 입력 token 합에 `cache_write`가 빠졌다. Anthropic처럼 cache 쓰기를 따로 주는 provider에서 입력이 작게 보였다.
- 후:
  - 창 점유 = 그 call의 실제 prompt token + 그 call의 답 blob, 그 call의 tool 결과, 그 call 뒤에 받은 메시지 본문의 byte를 `BYTES_PER_TOKEN`으로 센 값(tool 결과 이미지는 `IMAGE_TOKENS`). session 자신의 답 메시지는 답 blob과 겹치므로 세지 않는다. omp의 `getContextBreakdown`(실제 prompt token + 그 뒤 꼬리 추정)과 같은 셈이다.
  - 그 call 뒤에 Compact가 이어졌거나 그 call의 turn 입력을 덮는 rewind가 적용됐으면 `context`는 다음 call까지 `null`이다.
  - 한도는 지금 session이 쓸 model의 것이다. 그 call과 model이 다르면 resolve와 같은 순서(사람이 적은 정보, catalog, 기본 한계 131072)로 읽는다. 기본 한계와 `withDefaultLimits`는 `models/user-entry.ts`로 옮겨 resolve와 status가 같이 쓴다.
  - footer의 입력과 panel의 입력 칸에 `cache_write`를 더한다. `StatusView`에 `cacheWriteTokens`가 생겼다.

왜: 사람이 lophn의 창 점유가 omp와 다르게 틀린다고 했다. 특히 Compact 직후 창이 여전히 찬 것처럼 보였다.

결정:
- Compact·rewind 뒤에는 추정하지 않고 모름으로 둔다. 요약과 남은 메시지로 다시 세면 system prompt와 tool 정의 크기를 따로 알아야 하는데 status read에는 그 값이 없다. 다음 call이 오면 실제 값이 된다. 버린 길: 요약 call의 token으로 추정하기(요약 call의 prompt는 접은 원문이라 창과 무관하다). (agent)
- system prompt·tool·skill이 그 call 뒤에 바뀐 양은 세지 않는다. omp는 세지만 lophn은 turn마다 prompt를 다시 조립하고 status read가 그 조립을 할 수 없다. (agent)

후속: 없음.
