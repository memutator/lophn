# documents/terms

context 하나에 속한 용어집을 맡는다. 용어집은 용어, 뜻, 그 뜻을 정한 쪽(사람 또는 Context Engineer)만 담는 agent용 자료이고, 그 context를 쓰는 agent의 prompt 자료로 들어간다. 사람은 Context 탭의 Glossary에서 보고 바꾼다. 용어 후보, 출현 근거, 문서 판 참조, 본문에서 용어를 찾아 검사하는 일은 없다.

## 요구

### 용어집의 모양

**[R1]** 용어집은 context 하나에 속하고 항목은 용어, 뜻, 그 뜻을 정한 쪽(사람 또는 Context Engineer), 정한 시각만 가진다.
- 이유: 용어집의 일은 agent가 사람 말을 같은 뜻으로 알아듣게 하는 것 하나다. 후보·근거 같은 군더더기는 agent prompt를 길게 하고 사람의 검수 몫만 늘린다.
- 확인: 항목 하나를 읽으면 용어, 뜻, 정한 쪽, 시각 네 가지만 나오고 후보 상태나 근거 필드가 없다.
- 의도: documents#I6

**[R2]** 용어집은 context마다 따로 있고 다른 context의 용어집에서 상속·번역·별칭·대응으로 가져오지 않는다.
- 이유: 같은 말이 다른 목적에서 같은 뜻이라는 보장은 없고, context 사이 연결은 Context Engineer가 계약의 경계로 설계할 일이다(documents/contexts).
- 확인: 두 context에 같은 용어를 서로 다른 뜻으로 둘 수 있고 한쪽을 고쳐도 다른 쪽이 바뀌지 않는다.
- 의도: documents#I6

**[R3]** 같은 용어집 안에서 용어는 앞뒤 공백을 자른 뒤 영문 대소문자를 구분하지 않고 비교해 유일하다.
- 이유: "Eating out"과 "eating out"이 따로 있으면 agent가 어느 뜻을 쓸지 헷갈린다.
- 확인: "Eating out"이 있을 때 "eating out"을 추가하면 새 항목이 아니라 중복으로 거절되고, 이름만 대소문자를 바꿔 고치는 것은 된다.
- 의도: documents#I6

**[R4]** 용어는 80자, 뜻은 1,000자 이하이고 한 context의 용어집은 항목 200개 이하이며 용어와 뜻은 비어 있거나 공백만 있을 수 없다.
- 이유: 용어집은 agent prompt에 들어가므로 크기에 상한이 있어야 하고, 긴 설명은 문서의 몫이다.
- 확인: 81자 용어, 1,001자 뜻, 201번째 항목, 빈 뜻은 각각 거절되고 80자·1,000자·200개는 받아진다.
- 의도: documents#I6, documents#I3

### 뜻을 정하는 사람

**[R5]** 사람과 Context Engineer는 둘 다 항목을 추가하고 뜻을 정할 수 있고, 사람은 어느 항목이든 고치거나 지울 수 있다.
- 이유: 말을 쓰는 사람이 뜻을 알고, Context Engineer는 자료를 읽어 용어 초안을 낼 수 있다. 용어집은 agent용 자료라 Context Engineer가 직접 정해도 사람의 계약이 깨지지 않는다.
- 확인: Context Engineer가 추가한 항목을 사람이 고치면 정한 쪽이 사람으로 바뀌고, 사람이 항목을 지우면 목록에서 사라진다.
- 의도: documents#I6

**[R6]** Context Engineer는 사람이 정한 항목을 고치거나 지우지 않는다.
- 이유: 용어집은 "내가 쓰는 말"을 agent가 알아듣게 하는 것이라 사람이 정한 뜻을 agent가 조용히 덮어쓰면 약속이 깨진다.
- 확인: 사람이 정한 항목에 대한 Context Engineer의 고치기·지우기는 거절되고, 사람이 그 항목을 고치면 다시 사람이 정한 것으로 남는다.
- 의도: documents#I6

**[R7]** 같은 항목을 사람과 Context Engineer가 동시에 고치면 나중 요청이 거절되고 읽은 뒤 바뀐 항목을 다시 읽어야 한다.
- 이유: 두 쪽 중 한쪽의 변경이 말없이 사라지면 안 된다.
- 확인: 같은 항목을 읽은 두 요청 중 먼저 온 것만 반영되고 나중 것은 충돌로 거절된다.
- 의도: documents#I6

### 기록

**[R8]** 항목을 추가·고치기·지울 때마다 누가(사람 또는 Context Engineer) 언제 했는지 lophn ledger에 남기고, 그 밖의 이전 뜻 이력은 보관하지 않는다.
- 이유: 누가 정했는지는 사람이 믿을 근거이지만, 뜻의 판 이력까지 두면 문서 판을 없앤 이유와 같은 무게가 다시 생긴다.
- 확인: 항목을 두 번 고치면 ledger에 고친 쪽과 시각이 두 번 남고, 용어집 읽기로는 마지막 뜻만 나오며 지운 항목은 목록에 남지 않는다.
- 의도: documents#I6

**[R9]** context를 보관해도 용어집 항목은 지워지지 않는다.
- 이유: 보관은 context를 쓰지 않는다는 뜻일 뿐 사람이 정한 말까지 버린다는 뜻이 아니다.
- 확인: context를 보관했다 해제하면 용어집이 그대로이다.
- 의도: documents#I6

### 읽기와 보기

**[R10]** 용어집은 용어 순서가 항상 같게 전부 한 번에 읽을 수 있고, 같은 내용이면 읽은 결과도 똑같다.
- 이유: 용어집은 agent prompt 자료에 들어가고 그 자료는 같은 내용이면 같은 바이트여야 한다. 실을 시점과 형식은 lophn-agent가 정한다.
- 확인: 항목이 같은 용어집을 두 번 읽으면 항목 순서와 값이 같고, 항목을 추가하면 용어 순서 자리에 끼어든다.
- 의도: documents#I6

**[R11]** 사람은 Context 탭의 Glossary에서 그 context의 용어집을 보고 항목을 추가하고 고치고 지울 수 있고, 각 항목은 누가 언제 정했는지도 보인다.
- 이유: 용어집은 agent용이지만 사람이 정한 말이 맞는지 보고 고칠 수 있어야 한다.
- 확인: Glossary에서 항목을 추가·수정·삭제하면 다음 읽기에 반영되고 각 항목에 정한 쪽과 시각이 보인다. 화면 모양은 shell이 맡는다.
- 의도: documents#I6

## 버린 것

- 용어 후보와 후보 상태: 용어집은 agent용이라 사람이 확정하기 전의 후보를 따로 둘 이유가 없다. Context Engineer가 직접 항목을 낸다.
- 용어의 출현 근거(문서 고정 판·section·줄 범위)와 근거 검증: 문서 판이 없어졌고 용어집은 뜻을 알려 주는 자료이지 본문 출현을 증명하는 자료가 아니다.
- 사람만 뜻을 확정하고 agent는 후보만 다룬다는 규칙: 용어집의 뜻은 Context Engineer와 사람이 함께 정한다(open-issues D33).
- 본문에서 용어 출현을 찾아 검사하는 일: 용어집은 검사 대상이 아니라 agent가 읽는 자료이다.
- 정의 목록 첫 페이지 30개와 cursor, 후보 목록 분리: 항목이 200개 이하이고 한 번에 읽는다.
- 용어 보관·보관 해제: 항목은 지우거나 두는 것만 있다. 지우면 되돌리는 이력이 없다.
- 앱 read command를 가진 context의 용어를 앱 설명의 읽을 근거로 제공하는 규칙: 용어집은 agent prompt 자료로만 쓰이고 앱 blueprint로 닿는 길이 없다.
- 별칭·번역·context 간 용어 대응·용어 상속: 정확한 용어와 뜻을 context마다 둔다(이전 결정 documents/terms#Q1·Q2 유지).
- 사람 답을 질문으로 받아 machine이 정의를 적용하는 경로: 사람이 Glossary에서 직접 고치므로 질문 답 적용이 필요 없다.
