# 0.2.0

## project-docs를 catalog, architecture, skill, check로 줄임

```yaml
modules: [tools]
checked: []
```

- 전: requirements, specs, dev 문서, task 기록이 약 4만 줄. 요구 ID 천 몇백 개를 사람이 검수하기 어렵고 코드와 30곳 넘게 어긋남.
- 후: `PRODUCT.md`, `boundary-catalog.yaml`, `module-catalog.yaml`, `architecture/<topic>.md`, `plan/`(skeleton, `weight.md`, `gaps.md`), `.claude/skills/` 넷. 약 2.2천 줄. architecture 문서는 지금 코드를 보고 다시 씀. `tools/check-source.ts`가 주석과 test 이름의 요구 ID, task 번호, 옛 말을 잡음.

왜: MVP 때 쌓인 명세가 코드보다 늦고 원자적이라 유지보수가 안 됨. 코드가 먼저이고 문서는 코드로 알 수 없는 것만 둔다.

결정:
- requirements, dev, tmp, 끝난 plan 내용을 지운다. 옛 내용은 tag `docs-before-trim`에 남긴다.
- requirements를 추상화한 `features.yaml`은 두지 않는다. 버린 이유: 또 하나의 동기화 비용.
- 무게 추적은 `plan/weight.md` 하나만. futures, metric, yaml 체계는 너무 무거워 버린다.
- 수평 관심사는 skill 넷(wording, write-test, orchestrate, ui-design)으로. module마다 AGENTS.md를 두지 않고 필요한 곳만.
- architecture 문서는 pull로 둔다. 사람이 필요할 때 넣어 준다.
- 전역 AGENTS.md에는 실천적이고 검증할 수 있는 지침만 둔다. 철학은 넣지 않는다. "스타트업처럼", "가장 단순한 구현", "방어 코드를 미리 만들지 않는다"는 효과가 있어 남긴다.

## core layer 규칙을 check로 강제

```yaml
modules: [tools]
checked: []
```

- 전: core module 사이의 import 방향을 보는 check가 없음. 바닥이 domain을, module이 `core/main`을 import하는 곳이 있음.
- 후: `tools/check-deps.ts`가 막음: module → `core/main`, 바닥 → lophn-agent·domain, lophn-agent → domain, domain끼리는 problems → apps만. 어긴 import는 type이나 함수를 쓰는 쪽으로 옮겨 고침. 동작은 같음.

왜: Deno는 실행 때 tree shaking을 하지 않아 import가 process와 Worker에 무엇이 실리는지를 정한다. 거꾸로 가는 import는 권한을 좁힌 process를 시작부터 죽이거나 순환 import를 만든다. 자세한 것은 `architecture/layers.md`.

결정:
- "domain끼리 import 금지"를 방향 규칙으로 완화한다. problems → apps는 자연스러운 한 방향 의존이다.
- 못 끊은 두 곳(projects → apps, lophn-agent → projects)은 check-deps에 이름으로 예외를 둔다. 버린 길: 다른 module의 표를 SQL로 직접 읽기. 의존이 check가 못 보는 곳으로 숨는다.
- "다른 module은 mod.ts로만 import"는 두지 않는다. barrel이 module 전체를 실어 오고, 막아 주는 깨짐은 type check가 잡는다.
- lophn-agent를 harness와 lophn domain으로 나누는 리팩터링을 다음 계획으로 한다. 예외 둘은 그때 다시 본다.

후속: 없음

## changelog와 버전, context-component-registry를 둠

```yaml
modules: [tools]
checked: []
```

- 전: 바뀐 것과 결정을 남기는 곳이 없음. 어떤 context 조각이 어떤 코드에 기대는지 적힌 곳이 없음.
- 후: `products/change-log/<version>.md`, `context-component-registry.yaml`. `boundary-catalog.yaml` 머리말을 다시 쓰고, `tools/check-modules.ts`에서 쓰지 않는 kind(guidance, bundle)와 참조 칸을 지움.

왜: plan → 구현 → changelog → context 유지보수의 흐름을 만들기 위해. catalog ID가 그 메타데이터 축이다.

결정:
- 버전은 lophn 하나에 `0.MINOR.PATCH`. 배포 단위로 나누는 것은 오픈 소스로 배포할 때 정한다.
- changelog는 tag 하나에 md 파일 하나, 폴더 하나에 평평하게. 열린 판에 덧붙이기만 하고 닫힌 판은 고치지 않는다. 버린 길: 변경마다 파일 하나, MINOR마다 폴더.
- 항목은 boundary ID가 아니라 module path를 적는다. 바뀐 module은 diff로 기계적으로 나오고 boundary는 module-catalog로 따라간다.
- plan을 가리키지 않는다. plan은 닫히면 사라진다.
- 고친 context 조각은 diff로 알 수 있어 적지 않고, 봤지만 고칠 것이 없던 조각만 `checked`에 적는다.

## 이슈의 큰 결정을 인터뷰로 정함

```yaml
modules: []
checked: []
```

- 전: 열린 이슈 84개 중 56개에 "정할 것"이 있음.
- 후: 원칙과 제품 결정으로 정리. 열림 76, archived 12. 정할 것이 남은 것 11. 이슈마다 "정한 것"을 적고, 남기기로 한 경계 장치 7개는 archived에 kept로 닫음. AGENTS.md "속도"에 위협 원칙 한 줄을 더함.

왜: 이슈 하나씩이 아니라 원칙을 먼저 정해 나머지가 따라오게 하려고.

결정:
- 사용자 앱과 사람이 쓴 글은 공격자로 보지 않는다. 막는 것은 AI가 만든 코드와 agent의 실수, 인터넷에서 온 것이다. 그래서 CLI data fence, domain event의 "data, not instructions" 문구, 앱 화면 오류 보고 서명을 지운다. 실수와 인터넷을 막는 장치(file tool realpath, rewind pre-image, migration 검사, 허락 뒤 다시 확인, 끊긴 activation 이어받기, web.fetch 내부 주소 검사)는 남긴다.
- 반쯤 만들고 안 쓰는 길은 지운다(unarchive route, md 아닌 목차와 저장 목차, 제보 창 기존 문제 고르기, deferred tool, App Engineer active context 읽기, ledger `domainOnly`, direct-socket 흔적).
- 경계도 아니고 동작도 맞는 무거운 내부 구현은 다이어트 계획 하나로 모아 정한다.
- activation이 겹치거나 `unavailable`이면 거절하고 사람이 다시 누른다. 줄과 30초 재시도를 없앤다.
- annotation은 source 위치(jsx 바꿔치기, source map)를 지운다. 화면 요소가 겹쳐 있어 줄 번호가 사람의 의도를 가리키지 않는다. 대신 찍은 곳의 component 겹(`List > Card > Button`)을 보낸다. ChatGPT 데스크톱 앱의 browser comment도 source 위치를 쓰지 않는다. 계산된 style과 text 선택은 넣지 않는다.
- App Engineer는 screenshot을 공통 이미지 읽기 tool로 본다.
- harness는 7종을 유지한다. 설치는 열 때마다 앱 폴더에 하지 않고 orca처럼 사용자 전역 설정에 한 번 하고 lophn 환경 변수로 켠다. 처음 한 번 사람에게 묻는다. 설치 hash와 설치 명령의 권한 계산을 지운다. "hook은 앱 source 폴더 안에만" 원칙을 버린다.
- coding agent 완료 보고 뒤 터미널을 따로 끄지 않는다.
- 앱 place의 Operator에게 앱 source 폴더 읽기를 준다.
- 400줄 넘는 파일을 check로 막지 않는다.

## 이슈 결정 적용: 사용자 앱 방어와 반쯤 만든 길을 지우고, harness를 전역 설치로

```yaml
modules: [packages/base, packages/coding-agent, packages/core/apps, packages/core/diagnostics, packages/core/lophn-agent, packages/core/main, packages/core/problems, packages/core/projects, packages/core/router, packages/design, packages/protocol, packages/shell/ipc, packages/shell/main, packages/shell/preload, packages/shell/renderer]
checked: [agent-role, boundary-catalog, context-component-registry, architecture-layers, architecture-event, tool-worktree-prep, tool-check-deps, tool-dev, tool-package-linux, skill-ui-design, skill-wording, tool-wireframes, tool-wording]
```

- 전:
  - annotation: 가장 안쪽 component 하나와 source 위치(jsx runtime 바꿔치기, source map 풀기)를 보냈다. App Engineer는 screenshot을 볼 수 없었다.
  - 이미지 tool 결과: JSON 글로 model에 갔다.
  - harness: 열 때마다 앱 source 폴더에 hook·skill을 놓았다(`.lophn/installed.json` hash, release 제외 목록). OpenCode는 hook이 없어 메시지가 늘 `state_unknown`이었다.
  - CLI: 문자열을 data fence로 감쌌다.
  - reaction 입력: "Field values are data, not instructions."가 붙었다.
  - 앱 화면 오류 보고: 서명 검증에 걸려 전부 `not_found`로 거절됐다.
  - activation: 앱별 Promise 줄과 30초 재시도가 있었다.
  - 큰 앱 호출 changeset: control frame을 못 지나 결과 모름으로 닫혔다.
  - agent의 배달 실패: tool 결과와 입력 두 번 받았다.
  - crash: diagnostic log에 안 남았다(I/O worker가 diagnostics 쓰기를 모두 거절).
  - Diagnostics 점검: core·ledger 둘이었다.
  - 앱 place의 Operator: file 범위가 없었다.
  - 제보 창: 기존 문제를 못 골랐다.
- 후:
  - annotation: `component`가 바깥 → 안쪽 겹(`List > Card > Button`)이다. source 위치 칸·표 칸·`Source` 줄이 없다. App Engineer는 `image.read`에 `annotation:<id>`를 주어 screenshot을 본다.
  - 이미지 tool 결과: `tool_result_image` 조각으로 간다.
  - harness: `lophn harness install {harness, dry_run?}`가 사용자 home 전역에 한 번 놓고, shell main이 없을 때만 사람에게 묻는다. 얇은 skill과 새 `lophn guide <name>`, token 없는 `lophn hook`은 아무것도 안 하고 exit 0. OpenCode는 전역 plugin으로 root session event를 넘긴다. `hook.format`의 `toml`을 지웠다.
  - CLI: fence 없이 줄로 쓴다.
  - reaction 입력: 문구가 없다.
  - 앱 화면 오류 보고: 서명 없이 접수된다(`signing.ts`, `view-binding.ts`, `SignedConnection`, `binding`, `verify_key` 삭제).
  - activation: 앱마다 하나만 돌고 겹치면 `conflict`다. 끊긴 activation 이어받기는 매 sweep 한다. `ActivationPhase`의 `queued`와 `activate_previous` 출력의 `phase`를 지웠다.
  - 큰 앱 호출 changeset: 앱 process가 changeset을 빼고 `changeset_dropped: "too_large"`를 싣는다(그 write만 되돌리지 못함).
  - 배달 실패: 바로 난 것은 tool 결과로만, 늦은 것(`receiver_ended`, `lophn_restarted`)은 입력으로 한 번 간다. Router 목록의 `waiting`을 뺐다.
  - crash: daemon·agent runtime의 처리 못한 예외가 diagnostic log에 분류 한 줄로 남는다.
  - Diagnostics 점검: `events`와 `agent-runtime`을 더했다.
  - 앱 place의 Operator: 앱 source 폴더를 읽기만 한다.
  - 제보 창: 그 앱의 열린 문제 20개에서 고른다.
  - 지운 반쯤 만든 길: deferred tool(`tool.search`), App Engineer active context 읽기, `unarchiveSession`, 저장 목차와 outline tool 셋, `outlineSourceSchema.format`, ledger `domainOnly`, `direct-socket.ts`(`CONTROL_PATHS`로), `app.agent_confirm_proof`·`invocation.accept_confirm`과 confirm proof schema.

왜: 앞 항목들에서 정한 것(사용자 앱과 사람이 쓴 글은 공격자로 보지 않는다, 반쯤 만들고 안 쓰는 길은 지운다)을 코드에 옮겼다. 세 bug(오류 보고 전부 거절, 이미지가 글로 감, diagnostics 쓰기 전부 거절)는 계획을 쓰며 찾아 같이 고쳤다.

결정:
- annotation source 위치를 지워도 `app.js.map`은 남긴다. problems가 앱 오류 stack을 풀 때 쓴다. (agent)
- App Engineer의 screenshot 읽기는 blob 일반 읽기를 열지 않고 `annotations.get`(App Engineer에게만, 자기 앱 것만)으로 파일 경로를 얻는다. 버린 길: blob `general_read`를 열기(owner scope 검사와 구간 읽기를 새로 맞춰야 한다). (agent)
- 전역 install CLI 권한은 지우지 않고 그 harness의 hook 설정 폴더와 skill 폴더로 좁혔다. `--no-prompt` CLI는 flag 없이 전역에 못 쓴다. 버린 길: 설치를 shell main(Node)으로 옮기기(coding-agent 코드를 shell bundle에 넣어야 한다). (agent)
- 등록 거절은 기억하지 않고 다음에 다시 묻는다. `dry_run`은 우리 항목이 있으면 내용이 달라도 `unchanged`라 lophn이 바뀌어도 다시 묻지 않는다. (agent)

후속:

## agent credential 상한을 tool 이름이 아니라 tool이 부르는 route 이름으로 만듦

```yaml

checked: [architecture-agent-definition, architecture-approval, roadmap]
```

- 전: tool 정의의 `contract`가 tool 이름(`ticket.create`)이라 agent credential의 operation 상한에 tool 이름이 들었다. core는 route 이름(`CreateTicket`)으로 대조하므로 이름이 다른 command tool이 `forbidden`이었다: App Engineer의 `ticket.create|update|verify|cancel`·`app.link_source`, PM의 `context.draft|submit`·`operator.create|update`, 모든 role의 `call`·`reply`·`cancel`, `visual.show`. core를 띄워 App Engineer의 `CreateTicket`이 403인 것을 확인했다. tool 정의의 `revision`은 builtin이 모두 상수 `"1"`이라 정의가 바뀌어도 tool 알림과 기록이 구별하지 못했다.

왜: harness와 domain을 나누는 계획의 첫 단계에서 registry가 조립 쪽이 넘긴 tool 목록을 받게 하면서 옛 칸을 지우다 찾았다.

결정:
- tool 정의가 부르는 route를 helper가 부르는 것까지 `routes`에 적는다. 빠지면 그 route가 command일 때 `forbidden`이다. 버린 길: 이름이 다른 tool만 route 이름을 더하는 작은 fix(정의와 상한이 따로 놀아 다음에 또 어긋난다). (agent)
- rewind route와 App Engineer의 `annotations.get`은 tool의 `routes`가 아니라 role 상한에 그대로 둔다(상한이 바뀌지 않게). (agent)

## provider를 API key로 연결하고, model catalog를 models.dev에서 받고, tool 결과 크기와 chip·coding agent 신호를 바로잡음

## 새 data root에서 앱 release까지 가는 길을 잇고, 앱 호출 frame·crash log·check의 구멍을 막음

  - core 기동(`main/daemon/wiring/sdk-install.ts`, `build`)이 `packages/sdk/*` 중 `deno.json`이 있는 것과 `@lophn/ui`·`@lophn/wording`을 `<dataRoot>/sdk/<이름 뒤쪽>/<판>`에, template을 `<dataRoot>/templates/app/`에 읽기 전용으로 깐다. 같은 byte면 그대로 두고 다르면 지우고 다시 쓴다. 판은 각 `deno.json`의 `version`이다(`packages/design`, `design/wording`에 `1.0.0`, `packages/sdk/cap-store/deno.json` 새로 만듦). blueprint·cap-store·cap-problem이 사본 밖 protocol을 가리키던 import는 사본 안 `vendor/`로 담는다. catalog 등록은 하지 않는다.

  - 화면마다 `screens/<key>/main.js.map`을 bundle에 넣고 `app.js.map`은 없다. problems는 stack이 가리킨 화면의 map으로 앱 source 위치를 푼다.
  - `apps.apply`는 json 요청(payload `{ app }`) 뒤 같은 channel의 bytes frame과 `end`로 본문을 보낸다(실패·기한 초과는 `abort`). 결과 상한 `RESULT_MAX_BYTES`와 입력 상한 `CALL_BODY_MAX_BYTES`는 control frame 한도 아래로 낮췄고, core는 넘는 입력을 보내기 전에 `invalid_input`으로 거절한다.
  - daemon crash handler는 diagnostics wiring의 `prepare`에서 걸린다. 앱 supervisor와 shell main은 crash 때 core에 진단 한 줄을 보내고 core가 component·location(`app-supervisor-crash`, `shell-main-crash`)을 정해 log에 쓴다. 앱 supervisor의 crash exit code는 1이다.

왜: 새 data root에서 template으로 만든 앱이 release 준비를 지나지 못했고, 앱 호출·rewind가 frame 한도에서 조용히 막혔으며, 사람이 원인을 모르는 crash가 있었다. 같은 문서 path 실수가 여러 번 났다.

결정:
- sdk 설치는 지워진 install 함수를 되살려 기동에 잇는다. 버린 길: release 준비가 repo의 `packages/`를 직접 읽기(release bundle에 굳힌 사본의 격리가 약해진다).
- 내장 sdk를 catalog에 등록하지 않는다. 같은 name·version의 byte가 바뀌면 등록이 `conflict`라 개발 중 sdk 소스를 고치고 다시 띄우면 기동이 막힌다. 그래서 `package show`가 내장 sdk guide를 주지 못하는 것은 이슈로 남겼다(agent).
- template은 고정 hash 없이 설치 때마다 repo 원본과 byte로 비교한다. template이 자주 바뀌어 손으로 고칠 hash가 짐이다(agent).
- file 수 상한을 올리지 않고 중복 복사를 없앤다.
- source map은 화면별로 둔다. 읽는 쪽이 sections를 풀지 않는다.
- rewind 적용은 write 하나씩 나누지 않고 bytes stream 하나로 보낸다. 나누면 중간 실패 때 일부만 되돌아간다.
- 앱 process에는 crash handler를 새로 걸지 않는다. 이미 `installCrashExit`, exception observer, supervisor의 crash 관측이 stderr와 problems에 남긴다(agent).
- shell main은 core를 import하지 못해 `installCrashHandler` 대신 작은 자체 handler를 둔다(agent).
- 문서 path check는 change-log, `issues/archived`, `plan/`, `products/roadmap/`을 보지 않는다. 앞으로 생길 path와 옛 path를 적는 곳이다(agent).

후속: 개발 data(`.dev-data`)를 지울 때는 sdk 사본이 읽기 전용이라 `chmod -R u+w`가 먼저 필요하다(lead 도구 `boot.sh`·`merge.sh`와 `deno task dev:mock`은 그렇게 한다). 옛 bundle 사본(중복 복사본, `app.js.map`)은 읽는 길이 없으니 개발 data를 지우고 앱을 다시 준비한다.

  - role과 ref·session 행의 변환(`placeOfAgentRef`, `agentRefOfColumns`, `agentIdentityOf`)은 `protocol/lophn-agent/places.ts`에 더했다.
  - `HARNESS_LEFTOVERS`에는 동적 app-api tool과 call·file tool 등 9개가 남았다.
  - agent가 보는 tool 목록, prompt, place 정보, 정의 file 자리는 같다. task마다 옮기기 전 값과 비교했다.

왜: role이나 place 규칙을 바꿀 때 harness를 같이 고치지 않게, 같은 규칙의 사본(정의 file 자리 셋, project data 자리 넷)을 하나로 모으려고.

결정:
- role↔ref 변환은 role 표가 아니라 protocol의 순수 함수로 둔다. 여러 harness file이 직접 쓰는데 표 인자를 끌고 다니지 않으려고, 그리고 protocol이 이미 role 정체성(`ROLE_PLACES`, `agentRefSchema`)을 가져서다. (agent)
- 지침 읽기의 "앱이 든 project"는 domain끼리 import하지 않도록 팀 file이 `appSourcePath`와 `innermostProjectOfPath`를 잇는다. (agent)
- 동적 app-api tool과 call·file tool의 domain 읽기는 옮기지 않는다(`project-docs/issues/layers.md`). (agent)

## MCP credential과 OAuth token을 `secrets.json`으로 옮기고 OS keychain 길을 지움

```yaml
modules: [packages/core/secrets, packages/core/lophn-agent, packages/core/main, packages/core/storage, packages/core/server, packages/protocol, packages/shell/renderer, packages/shell/main, packages/base]
checked: [architecture-agent-definition, boundary-catalog, skill-orchestrate, worker-prompt, tool-package-linux, architecture-layers, architecture-event]
```

- 전: secret 저장소가 둘이었다. provider API key는 `secrets.json`에, MCP credential은 설정의 `{secret}`이 `sec:<이름>`이 되어 ledger `secrets` 표와 OS keychain(Linux `secret-tool`)에, MCP OAuth token은 keychain에 바로 있었다. 설정 화면의 MCP credential 입력 창은 열리지 않았고, 화면은 옛 설정 꼴(`secret_ref`, `revision`, `classifications`)로 써서 인증이 있는 서버를 더하면 설정 schema가 거절했다. MCP 설정은 아무 secret 이름이나 받아 provider key나 다른 서버의 token을 MCP URL로 보낼 수 있었다. stdio env의 `{secret}`은 값이 한 번도 가지 않고 조용히 빠졌다.
- 후:
  - 저장소는 `secrets.json` 하나다. 이름 공간: `provider.<id>`, `mcp.<scope>.<server>`(사람이 넣은 MCP credential, scope는 `global`이나 project id), `mcp-oauth.<scope>.<server>.access`·`.refresh`·`.meta`(OAuth token과 만료·token endpoint·binding).
  - 설정 schema(`mcpServerSchema`)의 `{secret}`은 `mcp.` 이름만 받고 stdio env는 `{value}`만 받는다. `McpServerConfig`와 `sec:` 참조 꼴은 없다.
  - `createFileSecretAttach`가 이름의 앞머리로 용도를 정하고(앱 principal로 짐작하지 않는다) 그 밖의 이름은 보내지 않는다. 목적지는 `lophn-agent/secret-destinations.ts`가 이름 공간마다 찾는다: `mcp.`는 그 이름을 보내는 켜진 http 서버(전역과 project 층)의 URL origin, `mcp-oauth.<…>.access`는 meta `binding.server_url`의 origin이다. 갱신 token과 meta는 목적지가 없다. `providerSecretDestination`은 protocol의 `secretDestinationOf`가 되었다.
  - 감독 pipe의 `secret_send_request.use`는 `{name, destination}` 하나다. MCP 연결은 header·bearer·api_key·OAuth 접근 token을 이름으로 청하고, OAuth는 core가 보내기 전에 서버 설정과 대조하고 갱신한다(`McpAuthControl.prepareToken`). secret store의 put이 새 값을 먼저 알려진 값으로 올리므로 `syncSecrets`는 없다. `SecretStorePort`에 `get`·`delete`가 있다.
  - renderer는 서버를 `credential: {secret: "mcp.<scope>.<server>"}`로 쓰고 값을 `windowSecretInputOpener`·`enterSecret`(purpose `mcp`)로 받는다. 상태는 `secrets/status`로 읽는다. `ServerForm`이 `scope`를 받는다.
  - 지웠다: route `secrets/list`·`SetSecret`·`RemoveSecret`·`secrets/cleanup`·upload `secrets/input`, event `SecretSet`·`SecretRemoved`, main↔core `secret_comparison_request`·`_response`, `SecretUse`·`SecretRefSource`·`SecretPreparation*`, destination kind `mcp`, schema step `secrets`(`secrets`·`secret_preparations` 표), writer op `record-secret-preparation`, `CONTROL_OPERATIONS`의 `removeSecret`, keychain adapter와 옛 secret store, `CoreOptions.codingKeychain`, `platform-register.ts`(옛 list read뿐이었다), `extensions/secret-refs.ts`, .deb의 `libsecret-tools`, shell supervise `--allow-run`의 `secret-tool`.

왜: 사람이 token이 필요한 MCP 서버를 붙일 수 없었고, 저장소가 둘이면 어느 값이 어디로 가는지 두 번 따져야 했다. 이름 공간을 가르면 설정이 엉뚱한 이름을 가리켜도 값이 다른 목적지로 가지 않는다.

결정:
- keychain 길을 통째로 지운다. migration은 하지 않는다: 옛 `secrets` 표에는 제품 길로 값이 들어갈 수 없었고 keychain의 MCP OAuth token은 버린다. (사람)
- 이름 공간을 앞머리로 가르고 purpose 칸은 만들지 않는다. OAuth 접근·갱신 token은 각자 이름이고 meta는 같은 파일에 둔다. 이름이 고정이라 옛 vault의 새 항목·meta·옛 항목 rollback은 지운다. (agent)
- `mcp-oauth.`의 목적지는 접근 token만 갖는다. 갱신 token은 core만 쓰므로 보낼 곳이 없다. (agent)
- stdio env는 secret을 받지 않는다. 실행 파일을 대조할 계약이 없다. (agent)
- `windowSecretOpener`는 provider OAuth `signIn`이 아직 써서 남긴다(`issues/platform.md`의 provider OAuth 절). (agent)
- 단계 1~3(이름 공간, MCP credential, OAuth vault)은 한 commit이다. 감독 pipe의 `use`가 한 꼴이 되려면 셋이 같이 바뀌어야 하고, 나누면 버릴 중간 꼴이 생긴다. (agent)

후속: schema step `secrets`가 없어져 옛 개발 data는 기동하지 않는다. `chmod -R u+w .dev-data` 뒤 지우고 새로 만든다. MCP OAuth로 로그인한 서버는 다시 로그인한다. 화면이 부르지 않는 일반 설정 통로의 MCP 함수도 새 꼴로 고쳤다. 지우는 일은 `issues/shell.md`의 "일반 설정 통로의 MCP 함수" 절이다.
