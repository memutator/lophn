# coding-agent

coding agent 연결 장치는 사람이 쓰는 coding agent(`external-coding-agent`)와 lophn을 잇는 남은 부분이다. lophn CLI(`packages/coding-agent/cli/`), 제품 감지와 hook 설치(`packages/coding-agent/harnesses/`), 제품별 표(`packages/protocol/coding-agent/`)다. 사람이 연 터미널 탭에서 도는 coding agent의 상태, 탭 icon·점, 알림은 [terminal-agent.md](terminal-agent.md)다. lophn이 coding agent를 띄워 일을 맡기는 길(coding session)은 없다.

## 흐름

```
Settings › Coding agents ─ shell main이 exec ─▶ lophn harness detect|refresh ─▶ 제품마다 감지 결과
Settings › Coding agents ─ shell main이 exec ─▶ lophn harness status ─▶ 제품마다 hook 상태(모두 dry_run, process 하나)
사람 터미널에서 harness를 처음 알아봄 ─▶ lophn harness install --dry_run ─▶ 없으면 lophn 창 dialog로 묻고 install
[Install hooks] ─────────────────────────▶ lophn harness install (누른 것이 허락)
[Uninstall hooks] ───────────────────────▶ lophn harness uninstall (우리 항목만 지운다)
harness ─ 전역 hook ─▶ lophn hook <harness> <event> ─▶ shell main hook socket ([terminal-agent.md](terminal-agent.md))
사람 ─▶ lophn agent run | tool call | run … | workflow … ─ user token ─▶ core
```

## 지키는 것

- **CLI 명령의 `auth`는 `user`와 `local` 둘이다.** 명령 표는 `CODING_CLI_COMMANDS`(`packages/protocol/coding-agent/cli-commands.ts`)다.
  - `user` 명령(`agent run`, `tool call`, `run wait|show|cancel`는 `architecture/run.md`, `workflow start|report|stop|show`는 `architecture/workflow.md`)은 `<data root>/run/user-token`(core가 켤 때 쓰는 user token, 0600)을 자격으로 쓴다. file이 없으면 lophn이 꺼진 것이라 `unavailable`로 끝난다(exit 5). CLI가 core를 띄우지 않는다.
  - `local` 명령(`hook`, `harness detect|refresh|install|status|uninstall`)은 core를 부르지 않는다.
  - `not_found`는 core가 준 글 그대로 돌려준다. user token은 출력에 남기지 않는다.
- **제품 감지는 shell main이 CLI를 exec해서 한다.** core는 사람의 PATH와 실행 파일을 모르고 감지 결과를 받지 않는다. Settings › Coding agents가 이 결과를 그린다(`packages/shell/main/desktop/coding-connection.ts`). 처음 읽기는 실행 파일 찾기만 하고, 제품을 실제로 실행하는 version probe는 사람이 다시 감지를 눌렀을 때만 돈다. 사람이 시키지 않았는데 제품을 띄우지 않는다.
- **앱의 source 폴더는 `app.create`가 commit된 뒤 core가 만든다.** writer 앞 처리(`packages/core/apps/registration/source-folder.ts`)가 내장 template을 `<data root>/apps/<app>/source`(`appDefaultSource`, `packages/protocol/apps/app-storage.ts`)에 깔고 첫 commit을 만든 뒤(사람의 전역 git 설정은 읽지 않고, 저장소 안에 `user.name`, `user.email`, `commit.gpgsign=false`를 남긴다) core 안 machine 자격으로 `app.connect_source`를 부른다. 폴더가 이미 있으면 덮지 않고, commit이 있을 때만 그대로 잇는다. 깔기나 잇기가 실패하면 앱은 `source_path: null`로 남는다. `app.connect_source`는 git 저장소의 맨 위이고 commit이 있는 폴더만 받는다.
- **hook은 harness의 사용자 전역 설정에 한 번 놓고, 놓기 전에 사람에게 묻는다.** 사람의 터미널에서 그 harness를 처음 알아봤을 때 shell main이 `lophn harness install`을 `dry_run`으로 불러 없는지만 보고, 없으면 놓을 file을 보여 주고 묻는다. 묻는 것은 OS 창이 아니라 lophn 창의 dialog다. shell main이 그 터미널을 고른 창에 push하고 그 창의 답을 기다리며(browser bridge와 같은 request id + ack), 답하기 전에 창이 닫히거나 reload되면 거절이다. headless나 창이 없으면 묻지 않고 놓지 않는다. dialog는 harness 이름, 하는 일 한 문장(상태를 보이고 turn 끝을 알린다), 쓸 file 목록이고 Codex는 `config.toml`에 hook trust도 같이 기록한다는 한 문장이 붙는다. Settings › Coding agents의 [Install hooks]는 누른 것이 허락이라 묻지 않는다. 허락하면 놓고, 성공은 toast 하나, 실패는 무엇이 왜 실패했는지와 file을 담은 dialog로 보인다. 거절은 기억하지 않고 다음에 다시 묻는다. 묻거나 놓기가 실패해도 터미널은 그대로 돈다(hook이 없어 상태가 unknown이다). `dry_run`은 event마다 우리 항목이 있으면 내용이 달라도 `unchanged`라 lophn이 업데이트돼도 다시 묻지 않는다. 표에 새로 더한 event에 우리 항목이 없거나, plugin file 본문이 지금 원문과 다르면(hook command만 다른 것은 같다고 본다. 2.x용으로 바뀌기 전의 OpenCode plugin도 여기 든다) `missing`이다. 개발 실행만 예외다. PATH의 `lophn`이 없거나 설치된 판이라, `npm run dev`가 만드는 launcher(`<저장소>/.cache/dev-cli/lophn`, 설치된 `/usr/bin/lophn`과 같은 본문에 경로만 저장소 소스와 그 저장소의 Electron으로 바꾼 것)를 `LOPHN_CLI`로 shell main에 주고, shell main이 그 경로를 hook command로 넘긴다. 그때의 `dry_run`은 우리 항목의 command가 다르면 놓을 것이 있다고 본다. launcher는 `.dev-data`가 아니라 저장소의 `.cache/`에 두어 schema가 바뀌어 `.dev-data`를 지워도 전역 hook이 가리키는 경로가 남고, 실행마다 다시 쓴다.
- **Codex hook은 trust까지 같이 기록한다.** Codex는 새로 놓이거나 바뀐 hook을 사람이 `/hooks`에서 trust하기 전까지 건너뛴다. 그래서 설치가 `~/.codex/config.toml`에 lophn 항목마다 `[hooks.state."<hooks.json 경로>:<event>:<group 번호>:<handler 번호>"] trusted_hash`를 쓴다. hash는 Codex `hook_hash`(rust-v0.164.0 `codex-rs/hooks/src/engine/discovery.rs`, `codex-rs/config/src/fingerprint.rs`)와 같은 계산이다(`packages/coding-agent/harnesses/codex-trust.ts`). 정규화한 handler 하나, matcher, event 이름을 key 정렬 compact JSON으로 sha256한다. lophn의 표만 고치거나 끝에 더하고 나머지 byte(주석, 다른 도구의 표)는 그대로 둔다. 파싱되지 않는 `config.toml`은 건드리지 않고 `failed`다. trust 기록이 없거나 hash가 다르면 `dry_run`이 `missing`이고 file 목록에 `config.toml`이 든다. 사람의 허락은 lophn dialog 한 번이다. Codex가 계산을 바꾸면 기록이 Modified가 되어 사람이 `/hooks`에서 trust하던 때로 돌아갈 뿐이다. orca도 같은 기록을 쓴다.
- **전역 설정은 사람의 다른 항목을 보존한다.** harness마다 통합 규칙(hook을 놓는 위치와 꼴, event → 신호, hook stdout, session id·session 이름 경로, resume 인자)은 `HARNESS_ADAPTERS[id]` 한 항목(`packages/protocol/coding-agent/harness-adapter.ts`)에 있다. 설치할 event는 그 항목의 `events` key다. 꼴은 Claude식 json settings(claude, qwen, qoder, codebuddy, command-code, droid, letta), JSONC(devin), 우리 전용 file(grok, copilot, kiro V3), flat json(cursor), 이름 붙은 hook object(antigravity), 표시한 TOML block(kimi), managed hooks file과 settings 칸(muse, `LPN_TERMINAL_HOOK`을 env 허용 목록에 더한다), 표시한 YAML block과 허용 목록 사전 기록(hermes), event마다 script file(cline), plugin·extension file(opencode·kilo·mimocode 공통 본문, pi, omp, amp)이다. prime-agent는 hook API가 없어 놓지 않는다. 어느 꼴이든 우리 항목만 바꾸고 나머지 byte(주석, 다른 도구의 항목)는 그대로 둔다. 파싱되지 않거나 고칠 수 없는 꼴이면 아무것도 쓰지 않고 `failed`다(muse에 다른 `managed_hooks_path`가 있으면 `conflict`). cline은 event마다 script 하나라 사람의 script가 이미 있으면 놓지 않는다. hook이 stdout에 정해진 JSON을 내야 하는 harness(antigravity, cursor)는 CLI와 launcher가 같은 표(`HARNESS_ADAPTERS[id].stdout`)에서 출력한다. lophn 밖에서 불려 바로 끝날 때도 같다.
- **Settings의 hook 상태는 CLI 한 번으로 읽는다.** `lophn harness status`가 모든 harness의 `install --dry_run`을 한 process에서 돌려 목록으로 낸다(`packages/coding-agent/cli/commands/harness-run.ts`). 화면이 열릴 때와 창이 focus를 다시 받을 때마다 읽으므로 harness마다 process를 띄우면 25개가 한꺼번에 뜬다(CPU 약 10초).
- **[Uninstall hooks]는 놓기의 거꾸로이고 우리 것만 지운다.** `lophn harness uninstall`(`packages/coding-agent/harnesses/uninstall.ts`)은 놓을 때와 같은 규칙으로 우리 항목을 알아본다(command가 `lophn hook <harness> `나 개발 경로로 시작, 표시 block, 우리 이름의 file). 사람이 우리 group에 더한 handler, 같은 이름의 사람 cline script, 다른 file을 가리키는 Muse 설정, 사람의 Hermes 승인은 남긴다. 글 형식(JSONC, TOML, YAML)은 우리 줄만 지워 놓기 전 byte로 돌아가고, JSON은 놓을 때처럼 다시 직렬화한다. 우리 것만 남았던 event key와 `hooks`, 우리 이름의 file(`lophn.json`, `lophn-hooks.json`, plugin file, cline script), 비게 된 file(`{}`, 빈 글)은 지운다. Codex는 우리 trust table을 지우고, 우리 group 뒤에 있던 다른 도구의 기록은 당겨진 위치의 key로 옮긴다(key가 바뀌면 Codex가 다시 trust하라고 한다). 사람의 handler가 섞인 Devin 항목처럼 offset으로 안전하게 고칠 수 없거나 파싱되지 않으면 아무것도 쓰지 않고 `failed`다. 누른 것이 허락이라 묻지 않고, 지운 뒤 이 실행에서는 터미널이 그 harness를 알아봐도 다시 묻지 않는다. 다음 실행에서는 거절처럼 다시 묻는다.
- **coding agent에게 배포하는 skill은 없다. 설치는 lophn이 전에 놓은 지운 skill의 얇은 사본만 지운다.** 지우는 이름은 상수 `RETIRED_SKILL_NAMES`(`lophn-build-app`, `lophn-repair`, `packages/coding-agent/harnesses/install.ts`)이고 패턴이나 목록 읽기로 고르지 않는다. 폴더에 `SKILL.md` 하나뿐이고, 그 글이 lophn이 쓰던 꼴과 byte까지 같고, `dry_run`이 아닐 때만 file 하나와 빈 폴더 하나를 지운다(recursive가 아니다). 사람이 고친 사본, 다른 file이 든 폴더, 다른 이름의 skill은 남긴다. 사람 home에 쓰는 일이라서다. 출력의 `skill` 칸은 이 지우기만 알린다. 옛 사본이 있는 사람은 `lophn harness install`을 한 번 돌려야 지워진다.
- **전역 hook은 lophn과 상관없는 harness 실행에서도 불린다.** lophn 터미널이 넣는 `LPN_TERMINAL_HOOK`이 없으면 launcher가 CLI를 띄우지 않고 끝나고, `lophn hook`도 stdin을 읽지 않고 아무것도 보내지 않은 채 성공한다. pi extension과 OpenCode plugin은 그 env가 없으면 hook을 등록하지 않는다. launcher는 CLI를 Electron의 Node로 띄운다(권한 flag 없음).

## 왜 이 모양인가

- **coding session 층을 지웠다(사람, 2026-10-28).** lophn이 coding agent를 터미널에 띄우고 token·MCP endpoint·메시지 줄로 맡기던 층은 부르는 곳이 없었다. 앱 일은 그 앱 place의 lophn agent가 직접 지었고, 그 뒤 role이 없어져 맡길 쪽도 사라졌다. 지운 것: core apps module의 coding 폴더와 표 셋, coding token, `POST /mcp`, Router의 coding transport, shell의 coding 터미널 탭과 대기 목록 항목, CLI의 token 명령(`message send`, `app …`, `package …`). 다시 필요해지면 새로 설계한다. 사람이 연 터미널이 쓰는 hook, 감지, 설치는 남겼다(사람, 2026-10-26).
- **hook으로 상태를 안다.** herdr는 화면을 읽어 짐작하고 orca는 hook이 없으면 title 글리프로 짐작하지만 lophn은 짐작하지 않는다. 그 대가로 Claude Code를 Esc로 끊으면 `Stop`이 오지 않는다. 끊김 신호가 없는 harness에 한해 shell main의 터미널 상태는 사람이 친 단독 Esc·Ctrl-C를 보고 unknown으로 내린다. 끊김을 hook으로 알리는 harness(`interrupt_keys`가 빈 것)는 이 key를 보지 않는다([terminal-agent.md](terminal-agent.md)). turn 끝 신호가 있는 제품은 Claude Code `Stop`·`StopFailure`, Codex `Stop`·`Interrupt`(0.150 이상, interrupted), OpenCode `session.status` idle(전역 plugin이 root session의 event만 넘긴다. 뒤따르는 deprecated `session.idle`은 같은 끝이라 듣지 않는다. 2.x는 plugin이 `{id, setup}` default export로 event를 직접 구독하고 `session.execution.started`·`succeeded`·`failed`·`interrupted`가 `session.status` busy·idle로, `permission.asked`·`replied`는 그대로 1.x 모양으로 바뀌어 넘어가므로 shell main은 두 판을 구별하지 않는다. 2.x는 plugin을 공유 background service가 돌려 터미널 env가 닿지 않으므로 터미널이 `opencode --standalone`으로 띄운다), pi `agent_settled`다. pi는 `agent_end` 뒤에 retry와 compaction이 남을 수 있어 끝이 확정되는 쪽을 쓴다. plugin·extension 본문은 turn 끝 payload에 마지막 assistant 답(text block만)을 `lophn_message`로 싣는다. OpenCode 계열은 completed idle에서 1.x는 `client.session.messages`, 2.x는 `ctx.session.context`로 읽고(못 읽으면 뺀다), pi는 `agent_end`의 `messages`를 기억했다가 `agent_settled`에, omp·amp는 `agent_end`·`agent.end`의 `messages`에서 뽑는다.
- **hook을 앱 폴더가 아니라 전역에 한 번 놓는다.** 열 때마다 앱 폴더에 놓으면 앱 source에 harness 설정이 섞이고(release 제외 목록이 따라온다), 사람이 고친 file을 지키려고 hash 기록이 필요하다. 전역에 한 번 놓고 사람에게 묻는 쪽이 단순하다. 감지 표는 orca, emdash, herdr 가운데 둘 이상이 지원하는 25종이다(`HARNESS_IDS`). Gemini CLI는 Google이 Antigravity로 옮겨 지웠고 OpenClaw는 지원하는 곳이 없어 지웠다.
- **CLI 출력을 data fence로 감싸지 않는다.** 사용자 앱과 사람이 쓴 글은 공격자로 보지 않는다(AGENTS.md). 줄로 풀어 쓰고 `--json`이면 JSON 하나다.
