# agent-definition

lophn agent의 session 하나는 agent 정의(전역이거나 workspace 하나에 범위가 있다), session의 workspace, 설정 층으로 정의되고, turn마다 model 요청 하나로 조립된다. 이 조립에는 agent 정의, workspace 종류 지침, tool, 지침 파일, memory, skill, project·앱이 주는 workspace 정보가 모두 들어간다. 사람이 쓰는 agent 정의와, 그것이 model이 보는 prompt·tool 목록·결과로 바뀌는 길을 한 문서에서 다룬다. 이 길이 쓰는 model 호출 쪽(provider 연결, 구독 OAuth, model catalog, 입력 예산, compaction)도 같은 turn을 이루므로 함께 적는다.

## 문제

- 사람이 고친 지침이 며칠씩 열린 session에 닿아야 한다. 그러면서 prompt cache가 깨지지 않아야 한다. session 시작에 고정하면 수정이 안 닿고, 매 call 다시 조립하면 prefix가 흔들려 cache가 매번 깨진다.
- prompt에 들어오는 글(다른 agent, web, 문서)이 사람의 지시로 읽히면 안 된다.
- agent가 자기 정의나 권한을 스스로 넓히면 안 된다. 할당, 묻기 끄기, 외부 MCP server는 사람이 정한다.
- 한 turn에 model call이 백 번 가까이 되는 일(앱 하나를 짓는 turn)에서 대화 전체를 매번 새 입력으로 내면 비용과 context가 감당되지 않는다. 출력이 큰 tool 한 번이 context를 채워도 안 된다.
- 사람이 연결한 provider의 credential(API key, 구독 OAuth token)이 agent·앱·MCP 쪽으로 새거나 반대로 앱·MCP secret이 provider 쪽으로 새면 안 된다.

## 목표와 비목표

- 목표: agent 정의 하나가 어느 workspace에서 누구에게 보이고 무엇을 받는지 한 모양으로 정한다. turn의 prompt는 같은 재료에서 같은 bytes가 나오게 한다. 사람이 고친 것은 다음 turn에 닿고 cache miss는 한 번뿐이다. agent가 받는 tool과 권한은 workspace 종류와 사람의 할당이 정한다.
- 목표: model에 들어가는 글이 어디서 왔는지(사람, program, 다른 agent, 인터넷)를 `lophn-` tag와 고정 문장으로 밝힌다.
- 비목표: sandbox를 따로 두지 않는다. 경로 가두기, 환경 변수 허용 목록, Gate, 할당이 경계다(조사한 harness 여덟 가운데 경계를 기본으로 켜는 것은 Codex 하나였고, lophn agent는 coding agent보다 직접 하는 일이 적고 workspace가 범위를 정한다).
- 비목표: 사람이 tool 목록을 고치는 길(옛 preset과 tool 묶음)은 없다. 넓히는 길은 할당 하나다.
- 비목표: 앱과 MCP의 tool 결과를 감싸거나 의심하지 않는다. 사용자 앱은 공격자로 보지 않는다.
- 비목표: 일의 흐름을 tool로 만들지 않는다. 지침과 skill이 primitive를 엮는다.
- 비목표: memory의 자동 추출, 주기 정리, 검색은 하지 않는다.
- 비목표: tool 정의를 늦게 싣는(deferred) 장치는 두지 않는다.

## 모델

### agent 정의

agent 정의는 꼴이 하나다. 자리는 `<data>/agents/<id>.md`(올린 avatar는 그 옆)이고, 전역이거나 workspace 하나에 범위가 있다. 칸은 handle, name, workspace, profile, runtime, description, tools, skills, modality, model, skills_off, mcp_off, mcp_servers, extensions, apps, permissions, skip, 본문이다. 정의 file의 칸 목록은 고정이라 목록에 없는 칸은 저장 때 사라지고, 새 칸을 더하려면 저장 쪽도 함께 고친다. route는 `agents/*`다.

- **주소는 handle이다.** 만들 때 정하고 바뀌지 않는다(저장이 거절한다). 범위 있는 agent를 포함해 전역에 하나이고(대소문자·앞뒤 공백 무시), `lophn`은 예약이다. 새로 만드는 handle은 소문자·숫자·`-`·`_` 40자까지이고, 옛 정의의 handle은 옛 name을 그대로 옮긴 것이라 파일 schema는 공백 없는 비지 않은 글이면 받는다. `name`은 보이는 이름이라 바꿀 수 있고 겹쳐도 된다. 주소가 겹치면 받는 agent가 하나로 정해지지 않는다.
- **범위(`workspace`)**: `{kind: project|app, id}`이고 없으면 전역이다. 만들 때만 정한다. 범위 있는 agent는 그 workspace에서만 목록(`agents/list`)·명함·"Agents you can call"에 보이고 session도 거기서만 열린다(다른 곳이면 `not_found`). 다른 workspace는 `{agent, workspace}` call로만 닿고 call 정책(private 포함)이 그대로 걸린다. agent가 `agent.create`로 만들면 범위는 부른 session의 workspace로 정해진다(home session이면 전역, 다른 범위를 고르지 못한다). 앱 범위 agent는 자기 앱의 command(비공개 포함)를 할당 없이 부른다(`permissions.deny`는 그대로 적용). 다른 앱의 command는 사람의 할당이 있어야 한다.
- **내장 lophn은 workspace마다 하나의 객체이고 그 workspace의 범위 agent처럼 돈다.** id는 workspace에서 정해진다: Home `lophn_home`, project `lophn_<prj id>`, 앱 `lophn_<app id>`(`.`을 쓰지 않아 secret 이름 `mcp.<agent id>.<server>`, `mcp-oauth.<scope>.<server>.*`가 그대로 맞는다). 정의는 `<data>/agents/<id>.md`이고 file이 없으면 기본 정의다(처음 띄울 때 만들지 않는다. workspace가 없으면 그 lophn도 없다). 지우지 못하고 handle(`lophn`)과 profile을 바꾸지 못한다(profile은 `forbidden`, handle은 `invalid_input`). name, model, 본문, `mcp_servers`, `skills_off`, `mcp_off`, `extensions`, `apps`, `permissions`, `skip`은 그 workspace의 lophn 것이고, file에는 바꾼 name만 적히며 handle·profile·workspace는 적지 못한다. lophn끼리는 handle이 같아도 되고 `{agent: "lophn", workspace}` 짝으로 가린다. workspace를 빼면 부른 쪽 workspace의 lophn이다. 사람이 만든 agent만 `lophn`을 쓰지 못한다. Home lophn은 Home에서만 보이고 열린다. 앱을 지우면 그 앱 lophn의 정의 file도 같이 지워진다.
- **즐겨찾기 coding agent는 정의 file 없이 있는 전역 내장 agent다.** id `coding_<harness id>`(`coding_claude`, `coding_codex`, `coding_opencode`), handle은 harness id, name은 adapter label, runtime은 그 harness(`claude-code`, `codex`, `opencode`)다. `extensions.harness.enabled`가 켜지고 그 harness가 `shell.coding_agents.favorites`에 있을 때만 목록·명함·"Agents you can call"·handle 풀기에 선다. 사람의 새 session 메뉴(`+`, sidebar hover)의 lophn agents 묶음에는 없다: 사람은 Coding agents 줄로 같은 CLI를 TUI로 연다. id로 읽기는 늘 되어 열린 session과 harness host가 계속 돈다. file이 없으면 기본 정의이고 사람이 고치면 `<data>/agents/<id>.md`가 생긴다. 지우지 못하고 handle·runtime·workspace를 바꾸지 못한다. 세 handle은 예약이라 사람·agent가 새로 만들 때 `invalid_input`이다.
- **앱 삭제는 그 앱 범위 정의를 지운다.** 같은 transaction에서 앱 범위 정의 file(앱의 lophn 포함)을 지우고, 다른 agent의 `apps`가 그 앱을 가리키면 할당에서도 뺀다. project는 지우는 길이 없고 archive만 있어 그 범위 정의는 그대로 남는다. 등록(project, 앱)은 agent를 만들지 않는다.
- **runtime**은 `lophn | custom | claude-code | codex | opencode`이고 없으면 lophn이다(내장 lophn은 lophn 밖의 값을 거절한다). harness 값은 run-loop가 아니라 shell이 돌리고(`architecture/coding-agent.md`), resolve는 고른 tool·skill·MCP를 비운다.
- **description**은 한 줄 목적(줄바꿈 없음, 200자 이하)이다.
- **tools**는 custom이 고른 tool 이름(내장 tool, `mcp__<server>__<tool>`, `ext__<id>__<tool>`)이고 runtime이 custom일 때만 받는다(lophn에서 쓰면 `invalid_input`). lophn 명령(`call.reply`)과 앱 command(`<slug>.<command>`)는 이름으로 적지 않는다: custom이 `lophn` tool로 늘 받는다. 저장은 셋 중 어느 꼴도 아닌 이름(명령 이름과 `lophn` 포함)을 `invalid_input`으로 거절한다. 꼴만 보고 할당과 설정은 보지 않는다(나중에 바뀐다). 옛 정의의 명령 이름은 data step `agents.tools-no-commands`가 file에서 뺀다. **skills**는 custom이 고른 skill 이름이고 같은 규칙이다. custom이 skill을 하나라도 고르면 `skill.read`를 program이 더한다(목록을 읽을 tool이 없으면 목록이 소용없다).
- **modality**는 `{input?, output?}`이고 값은 `text`, `image`, `file`이다. 칸이나 값이 없으면 셋 다다.
- runtime, description, tools, skills, modality는 agent도 `agent.create`·`agent.update`로 쓴다. 상한(workspace 종류 목록, 할당, credential) 안에서 고르는 것이라 권한을 넓히지 않는다.
- **apps**는 할당한 앱의 slug 목록이다(slug는 앱을 만들 때 정해져 바뀌지 않는다). **permissions**는 지금 `deny` 하나이고 할당에서 뺀 command를 `lophn(<앱 slug> <command>)`로 적는다(`<command>`는 argv 낱말: `session usage`). 다른 규칙은 쓰지 않는다. 앱이나 command가 active 선언에 없으면 그 줄은 읽을 때 빠진다.
- **skills_off**는 받지 않을 skill 이름이다(아래 skill).
- **skip**은 그 agent 새 session의 skip 기본값이다.
- **profile**: 기본은 `{ kind: "character", shape, color }`다(shape 6종, color 8종은 protocol이 고정). 한 body path와 점 눈 두 개로 그리고 표정은 고정이라 형태·색으로 agent를 구별한다. sidebar, 대화, Agents 카드, 알림이 같은 Avatar를 쓴다. lophn은 고정 character를 쓰고 바꾸지 못한다. 사람이 만든 agent는 형태·색을 고르거나 이미지(`{ kind: "image", image: "avatar.<ext>" }`, png·jpg·webp만)를 올린다. SVG는 제품이 그리는 기본 character에만 쓴다. 올린 이미지 주소를 풀 수 없으면 이름 첫 글자를 쓴다.
- **명함**은 program이 정의와 할당에서 계산하고 저장하지 않는다.

### 설정 층과 할당

- 사람의 설정 층은 workspace마다 같다. Home 그릇 자리 `<data>/home/`, project `<data>/projects/<prj>/`, 앱 `<data>/apps/<app>/`에 지침 file, `extensions.json`(MCP server, skill 끄기), `skills/`, `memory.md`가 있고, workspace model 하나(ledger의 model 선택)를 따로 둔다. 전역 층(전역 `LOPHN.md`, 전역 설정, 전역 기본 model)이 그 위다.
- **할당은 agent id마다 정의 file의 `apps`와 `permissions.deny`다.** route `assignments/*`가 읽고 쓴다(저장 규칙은 `architecture/approval.md`). 정의가 전역이거나 범위가 있어도 할당은 workspace를 갖지 않는다(앱 범위 agent는 자기 앱이 더해져 읽힌다). 할당을 읽는 route는 agent 자격에 없다(사람과 machine만 읽는다).
- **session의 workspace 종류(home, project, app)가 tool 목록을 정한다.** 같은 종류면 agent가 누구든 같은 목록을 받는다(custom은 그 안에서 고른다).

### turn 조립

turn마다 run-loop가 한 번 읽어 그 turn의 판을 고정하고, I/O 없는 조립이 model 요청 하나를 만든다.

```
 입력   agent 정의 + session workspace + 설정 층 ─▶ resolved agent
        workspace 종류 층: 제품 고정 규칙 + workspace 종류 지침(home·project·app), 종류별 tool 이름 목록, 내장 skill
        tool: 조립이 넘긴 정의 중 그 종류 목록에 든 것 + 할당한 앱·extension의 tool + 설정한 층의 외부 MCP tool
        지침 파일: 전역 · home | project의 LOPHN.md(없으면 CLAUDE.md) | 앱 source의 AGENTS.md · agent 지침
        memory: global memory(Home memory) · workspace memory · agent memory
        skill: 내장 · 공유(할당한 앱의 public skill) · 전역 · project·app의 .lophn/skills · workspace-data
        workspace 정보: 같은 workspace의 agent, artifact 목록과 폴더, lophn은 project·앱 목록과 앱의 public command

 system  1 제품 고정 규칙 + workspace 종류 지침        ← cache 경계
         2 지침 층 (전역, home·project·앱 중 하나, agent)
         3 memory (지침 뒤)
         4 skill 목록 (이름과 설명)
         5 workspace 정보                          ← cache 경계
 tools[] 정렬된 정의 (내장 tool, 명령을 부르는 `lophn`, 외부 MCP tool, 할당한 extension의 tool)
 대화    Router 입력(tag로 출처 표시) ... 끝에 notice   ← 마지막 block과 그 앞 user message에 cache 경계
         └ 지난 turn이 본 판(seen)과 비교해 바뀐 층·목록만 notice로 끝에 덧붙인다.
           첫 turn과 compact 직후는 seen이 없어 notice가 없다.
         └ 날짜 notice(`date`)는 turn 이력 맨 앞(요청 바로 뒤)에 붙어 이력과 함께 남는다.

 custom runtime은 같은 길에서 고른 것만 싣는다:
 system  정의 본문 + `<lophn-untrusted>` 한 줄 + 자기 agent memory(global·workspace memory는 받지 않는다) + 고른 skill 목록 + workspace 정보   ← 본문 뒤와 workspace 정보 뒤에 cache 경계
 tools[] 고른 내장 tool ∩ workspace 종류 목록, `lophn`(lophn runtime과 같다: workspace 종류의 명령 전부, 할당한 앱 command는 부를 때 푼다), 고른 MCP tool, 할당한 extension 가운데 고른 tool
 대화    lophn과 같다. notice는 지침 층을 보지 않아 tool과 agent 목록(workspace 정보)이 바뀐 것만 간다
```

할당된 앱 command는 tools[]에 따로 싣지 않는다. model은 `lophn <slug> <command>`로 부르고 loop가 그 호출을 앱 command의 호출로 푼다.

### tool

- **lophn이 내놓는 일은 명령이고 model은 native tool `lophn` 하나로 부른다.** 명령 표는 binary `lophn`과 같은 표다. 입력은 `{args: string[]}`이고 호출 하나에 명령 하나다(pipe, `&&` 없음). tool 설명은 고정된 사용법과 그 workspace 종류가 부를 수 있는 명령(이름과 summary, 이름순)이다.
- tool 이름은 `<자원>.<동사>`이고 자원 하나에 동사 하나다.
- 명령은 `workspaces`를 갖고 그 종류가 부를 수 있는 명령만 목록에 든다.
- file tool(`file.read|grep|glob|write|edit`, `pdf.read`, `image.read`), `shell.run`, web tool, `skill.read`, `agent.create`·`agent.update`, `agent.memory`, 읽기 tool(`app.read`, `package.read`, `app.tools`)이 내장 tool이다.
- 이미지 결과는 JSON 글이 아니라 `tool_result_image` 조각으로 싣는다.

### 이력과 길이

- 이전 turn의 tool 이력은 다음 turn에 그대로 이어진다(요청 prefix가 앞 turn의 마지막 call과 바이트로 같다).
- 이력이 context 예산을 넘으면 오래된 tool 결과를 줄이고, 그래도 넘으면 turn 안 Compact로 요약한다. 이전 대화가 커지면 다음 turn 전에 Compact한다.

## 지키는 것

### cache와 판

1. **도는 turn은 시작 때 읽은 판을 끝까지 쓴다.** 지침, skill, workspace 정보가 도중에 바뀌면 다음 turn 시작에 system을 그 turn이 읽은 지금 판으로 다시 만들고, 바뀐 층·목록은 notice로 대화 끝에도 알린다(그 turn 요청에만 붙고 이력에 저장하지 않는다). 바뀐 turn에는 cache miss가 한 번 난다. tool 목록은 session 시작에 고정이라 system에 닿지 않고 notice로만 알린다.
2. **같은 재료는 같은 bytes다.** 정렬하고 시각·무작위에 기대지 않는다. 오늘 날짜는 system이 아니라 대화에 간다: 이력이 마지막으로 알린 날짜·time zone과 지금 날짜(host time zone)가 다를 때만(처음 포함) turn 첫 조립에서 `date` notice("Today's date is YYYY-MM-DD (time zone Z).")를 turn 이력 맨 앞에 둔다. turn 이력과 함께 저장되어 다음 turn에 같은 bytes로 이어지고, 이미 알린 날짜는 따로 저장하지 않고 이력에서 읽는다. 시·분은 싣지 않는다(매 turn 글이 붙는다. 필요하면 shell `date`). tag 목록도 코드로 끼우지 않고 고정 문장으로 둔다. notice는 program이 쓴 고정 문장만 쓰고 앱이 쓴 글(tool 설명)은 넣지 않는다. notice도 다음 turn부터는 이력의 prefix라, 앱 글이 들어가면 그 글이 바뀔 때마다 prefix가 달라져 cache가 깨진다. model에 보이는 tool 순서도 고정이다.
3. **cache 표시는 system 층 둘(workspace 종류, workspace 정보)과 대화 쪽 둘이다.** Anthropic 요청은 표시를 넷까지 받아 그 안에 든다. 대화 쪽 표시는 마지막 message와 그 앞 user message의 마지막 content block에 단다. 끝 block은 turn마다 새로 생긴 tool 결과나 사람 글이라 다음 call은 앞 call이 쓴 prefix를 읽는다. Anthropic은 표시마다 앞쪽 20 block까지만 찾으므로, 한 call에 block이 많이 늘어도 그 앞 user message 표시가 앞 call의 entry를 찾는다. 지침 층은 사람이 지침을 고칠 때만 바뀌어 따로 표시하지 않는다(바뀌면 workspace 정보 경계까지 다시 쓴다). tools는 system 앞이라 첫 system 층 표시가 함께 덮는다. 대화를 cache하지 않으면 앱 하나를 짓는 turn(model call 백 번 가까이)이 매 call 대화 전체를 새 입력으로 낸다.
4. **tool 목록은 session을 시작할 때 고정한다.** 도중에 activation이나 할당으로 앱 command, MCP tool이 더해지거나 빠져도 `tools[]`는 그대로 두고 대화 끝에 notice로 알린다. 빠진 tool은 목록에 남아도 부를 때 막힌다: 앱 command는 `lophn` 호출을 풀 때 지금 할당을 읽어 막고(Gate도 지금 할당을 읽는다), MCP tool은 연결 쪽 `call`이 지금 server 설정을 다시 읽는다(`architecture/approval.md`). 실행 쪽은 이번 요청의 `tools[]`가 아니라 session 고정 목록을 본다. 숨김은 model이 보는 것만 바꾼다.
5. **"tool 정의가 바뀌었나"는 정의에서 계산한다.** 이름, 설명, 입력 JSON schema, effect의 hash다. 따로 들고 다니는 판 번호를 두지 않는다. 정의가 같으면 release가 바뀌어도 알림이 나가지 않는 것이 맞다.
6. **workspace 정보에는 잘 안 바뀌는 목록만 넣는다.** 열린 session 목록과 앱 화면 상태는 넣지 않는다. 화면에서 본 것은 annotation이나 메시지로만 들어온다. 목록만 prompt에 두고 내용은 tool로 읽는다(목록이 없으면 model은 그것이 있는 줄 몰라 찾지 않는다). project workspace session에는 그 project의 `workflows/` 절대 경로 줄(`Workflows folder:`)이 실리고 workflow 목록과 instance 상태는 싣지 않는다(`architecture/workflow.md`). lophn의 workspace 정보에는 앱 지도(앱마다 slug, 이름, id, 활성 release의 public command의 낱말·effect·설명, 그 command를 쓰는 다른 앱·project "Used by")를 이름순으로 결정적으로 조립해 싣는다.

### 지침

7. **사람이 쓴 지침은 조용히 빼지 않는다.** 한 층이라도 못 읽거나 상한을 넘으면 turn을 시작하지 않는다. 빠진 채 일하면 사람이 모른다. 읽은 지침은 redaction을 거치고, 끝나지 않으면 역시 시작하지 않는다.
8. **지침 층은 덮지 않고 이어 붙인다.** 층은 `global → home | project | app → agent`이고 session의 workspace가 home·project·app 중 하나만 정한다. 읽기, 조립, 판 비교가 같은 층 목록을 쓴다. 다른 workspace의 일은 `call`로 그 workspace의 session에 넘기고 거기서 조립이 그 층을 싣는다. agent가 tool로 지침을 읽게 하지 않는다.
9. **지침 파일은 `LOPHN.md`이고 전역·Home·project 자리에서는 `LOPHN.md`가 없을 때 같은 자리의 `CLAUDE.md`를 읽는다.** `LOPHN.md`가 있으면 `CLAUDE.md`는 열지 않는다. `LOPHN.md`가 있는데 못 읽으면(폴더, 권한) `CLAUDE.md`로 넘어가지 않고 `unavailable`로 turn을 시작하지 않는다. 실제로 연 file 이름은 지침 읽기 결과의 `name`으로 오고 prompt 층 제목이 쓴다(`Project instructions (CLAUDE.md)`). `DOMAIN.md`는 그대로다. 앱 층만 앱 source의 `AGENTS.md`를 지침으로 읽는다(source가 이어지지 않은 앱은 그 층이 없다). 그 밖의 자리에서는 `AGENTS.md`를 지침으로 읽지 않는다. `LOPHN.md`를 옮기는 migration은 없다.
10. **지침이 시키는 말과 막는 것을 섞지 않는다.** Gate, sandbox, deny, 실행 목록은 prompt를 빼도 그대로다.

### 출처와 신뢰

11. **Router가 넣는 입력은 모두 user role이고 `lophn-` tag로 출처를 밝힌다.** 본문 속 `lophn-` tag는 escape하고 속성 값은 scrub한다. 사람의 steer만 `<lophn-steer>` 모양을 믿는다고 고정 본문에 적는다. 받은 메시지, 알림, tool 결과는 허락도 사람의 지시도 아니다. 받은 메시지는 뒤 turn의 이력에서도 받은 turn의 입력과 같은 bytes로 싼다(봉투가 답 방식, reaction event, 실패 이유를 저장한다. `architecture/agent-call.md`). result call의 답 방식 글은 runtime마다 다르고(lophn은 `lophn call reply`, custom과 harness는 "마지막 응답이 답이고 `lophn call reply`로 먼저 답했으면 그것이 답") 받은 turn과 이력 재생이 같은 runtime을 받아 같은 글을 만든다.
12. **감싸는 결과는 web 검색과 web 읽기뿐이다.** file, shell, 앱 tool, 외부 MCP 결과는 감싸지 않는다. 앱과 MCP는 사람이 할당하고 설정한 순간 믿는다는 철학이고 실행 때 의심을 더하지 않는다. "안전해 보이니 감싸자"로 되돌리지 않는다. 감싸는 글의 tag 처리는 한 곳이다.
13. **web 읽기는 redirect를 hop마다 검사하며 직접 따라간다.** 자동으로 따라가지 않고 최대 5번이다. hop마다 scheme과 host literal(localhost, 사설 IPv4, IPv6 loopback·ULA·link-local, 매핑 주소)을 검사해 인터넷 내용이 사람 PC의 내부 주소를 치지 못하게 한다. host 이름이 사설 주소로 풀리는 경우(DNS)는 보지 않는다.
14. **compact 요약 재료는 data 경계로 감싼다.** 요약할 대화 원문(web 결과가 섞여 있다)은 `~~~data` block으로 감싸고 제어 token과 동형 문자를 정리해 지시로 읽히지 않게 한다. tool 결과는 사람이 쓴 것이 아니라고 표시한다.
15. **shell은 환경 변수 허용 목록만 넘긴다.** lophn token과 secret은 이름으로 막는 것이 아니라 목록에 없어서 나갈 수 없다. 그 위에 `LOPHN_AGENT_SHELL=1`을 넣고, 그 shell 안의 `lophn` CLI는 이 표시를 보면 사람 자격을 받지도 core를 띄우지도 멈추지도 않고 `forbidden`으로 멈추며 `lophn` tool을 쓰라고 알린다. 앱 data는 앱 tool로만 다루고 앱 DB는 직접 열지 않는다(고정 본문).

### 권한과 경계

16. **agent credential의 operation 상한은 tool이 core에 부르는 route 이름이다.** core는 route 이름으로 대조하므로 tool 이름(`preview.start`)을 넣으면(route는 `previews.start`) command가 `forbidden`이다. tool 정의는 helper가 부르는 것까지 route를 적고, 상한은 그 workspace 종류 목록 tool의 route 합집합에 workspace 읽기, rewind, Gate 대기 같은 보조 operation을 더한 것이다. workspace 읽기에는 prompt의 "Agents you can call"을 채우는 agent 목록도 든다. 조건은 session workspace에서 나온다(app workspace면 그 앱 하나, project workspace면 그 project, home은 없다). custom이 고른 것은 상한을 좁히지도 넓히지도 않는다.
17. **tool 목록은 session의 workspace 종류로 고정하고 목록 밖 tool은 정의에도 실행에도 없다.** 같은 종류의 lophn runtime session은 agent가 누구든 같은 목록을 받고 사람은 목록을 넓히거나 좁히지 않는다. 넓히는 길은 할당 하나다. 공통 읽기와 `agent.create`·`agent.update`는 셋 모두에 준다. 명령은 이 목록이 아니라 명령의 `workspaces`가 정한다. 목록의 이름마다 정의가 있고 정의마다 어느 목록에 든다(어긋나면 agent가 그 tool을 말없이 못 본다). 편집 화면의 custom tool 고르기도 같은 목록을 쓴다.
18. **agent 정의를 만들고 고치는 tool은 할당을 주지 못한다.** `mcp_servers`, `skip`, `apps`, `permissions`(와 `extensions`)는 agent 자격의 입력에 있으면 `forbidden`이고, 고칠 때는 지금 file의 값과 같아야 한다. 할당을 넓히는 길은 사람의 `assignment.set`과 사람이 승인한 앱 공유 요청(`architecture/approval.md`) 둘뿐이다. agent가 자기 권한을 넓히거나 묻기를 끄는 길이 없어야 한다.
19. **agent 정의는 lophn data에 있어 file tool이 닿지 않는다.** agent가 자기 정의를 file tool로 고쳐 할당을 우회하지 못한다. 지침 file(`LOPHN.md`)과 그릇 자리의 `skills/`(Home 포함)·`artifacts/`는 그 범위의 agent가 묻지 않고 쓴다(rewind로 되돌린다).
20. **file tool은 workspace 폴더 안에 가둔다.** 경로는 realpath로 판정하고, 새 file이면 가장 가까운 상위 폴더의 realpath에 이름을 붙여 판정한다. 끊어진 symlink는 따라 쓰면 밖에 쓰게 되므로 거절한다. 읽기와 쓰기는 Gate를 거치지 않고 쓰기는 rewind로 되돌린다. `LOPHN.md` 쓰기도 묻지 않는다. shell은 shell 규칙으로 Gate를 거친다(`architecture/approval.md`). 이 판정이 사람 workspace 밖에 쓰는 실수를 막는 유일한 경계다.
21. **효과(read, write, external)는 model에 보이는 정의에 넣지 않는다.** registry만 안다. 효과는 기록과 재시도에 쓰이고, 판정은 할당과 shell 규칙이 한다.
22. **`lophn` 호출은 기록·effect 판단·Gate·retry 전에 명령의 호출로 풀린다.** 그래서 tool 호출 기록의 이름은 명령 이름(`job.create`)이고 effect·route·display는 명령의 것이며, idempotency key는 그 tool call id다. wrapper(read)로 판단하면 쓰기가 병렬로 돌거나 다시 실행된다. 이력의 tool_use는 model이 보낸 `lophn` 호출 그대로다. 명령으로 풀리지 않는 줄(help, 틀린 줄)은 help 글이나 `invalid_input`과 usage 한 줄로 답한다. workspace 종류가 부를 수 없는 명령은 session 목록에 없어 목록 밖 tool처럼 거절되고 credential 상한에도 그 route가 없다.
23. **앱 command는 `lophn <slug> <command>`로만 부른다.** 도움말(`lophn <slug> --help`)에 보이는 command는 지금 할당, 활성 release 선언, 비공개 규칙이 부를 때마다 정한다. 숨기거나 늦게 펼치는 장치는 없다. 앱의 비공개 command는 그 앱 workspace의 session만 보고 다른 workspace의 session은 `public`만 본다(`architecture/app-call.md`). 같은 규칙으로 할당한 앱의 command를 모으는 곳과 `app.tools` 결과가 걸러낸다.
24. **archived 앱에 묶인 agent 정의는 agent에게 없는 agent다.** agent actor의 `agent.list|read|card`는 그 정의를 빼거나 `not_found`로 답하고 그 앱 workspace를 준 read도 `not_found`다. 앱 read·call이 archived 앱을 가리는 규칙의 한 부분이다(`architecture/app-call.md`). 사람의 화면은 그대로 보고 앱을 되살리면 다시 보인다. 진단 명령(`app.status`, `app.logs`, `app.invocations`)도 archived 앱에는 `not_found`다.
25. **MCP server의 설정 층이 곧 할당이다.** 층은 전역, workspace(Home·project·앱 중 session의 것), agent 정의 순이고 끄기는 `mcp_off`다(`architecture/approval.md`). agent 정의 층의 MCP server는 그 agent의 turn과 MCP 목록에만 닿는다: turn 준비가 그 agent의 `mcp_servers`만 agent 층으로 넘기고, MCP tool 목록 요청도 agent id를 실어 같은 층을 더한다. 반면 `mcp.` secret의 목적지는 모든 agent 정의 층을 합친 목록을 본다(runtime child 하나가 모든 session의 MCP를 돌린다). 정의 층 server의 credential 이름은 `mcp.<agent id>.<서버>`라 다른 층·다른 agent와 겹치지 않는다. 이름 접두는 core가 강제하지 않고 편집 화면이 만든다. 정의 file을 쓰는 것은 사람뿐이다. MCP tool 이름이 wire 이름 규칙(영문, 숫자, `_`, `-`, 64자 이하)에 안 맞으면 안전하지 않은 글자를 `_`로 바꾸고 `[서버, 원래 이름]`의 해시 앞 8자를 붙여 줄인다(겹치면 등록을 거절한다).
26. **stdio MCP 서버의 env는 값만 받는다.** 실행 file은 대조할 목적지가 아니라서 secret을 넘기지 않는다. 설정 schema가 `{secret}`을 거절한다.
27. **agent 정의의 `skip`은 그 agent 새 session의 skip 기본값이다.** 켜 두면 새 session이 skip으로 시작해 shell `ask`를 묻지 않는다(deny 규칙은 막는다). `mcp_servers`처럼 사람만 쓴다. session의 skip은 사람이 대화 화면에서 켜고 끄고, fork한 session은 skip을 가져가지 않고 정의의 기본값으로 시작한다(`architecture/workspace-session.md`).
28. **shell extension의 tool은 사람만 쓰는 정의 칸 `extensions`(extension id 목록)로 할당한 agent에게만 싣는다.** 단위는 extension 하나(그 tool 전부)이고 custom은 그 가운데 `tools`로 고른다. model 이름은 `ext__<extension id>__<tool>`이다(내장의 `_` 하나, MCP의 `mcp__`와 겹치지 않는다). 정의는 core 메모리의 catalog(shell이 올린 manifest의 tool 가운데 켜진 extension의 것)에서 만든다. shell이 아직 올리지 않았으면 그 session은 extension tool 없이 시작하고 올린 뒤 `tools_changed`로 받는다. agent 자격의 `agent.create`·`agent.update`는 `extensions`를 받지 않는다(`forbidden`). 새 optional 칸이라 옛 정의 file은 그대로 읽힌다(`architecture/extension.md`).

### custom

29. **custom은 정의 본문, 고른 것, workspace 정보만 싣고 상한은 lophn과 같다.**
    - system은 정의 본문 한 block이고 workspace 종류 층 자리에 둬서 그 cache 표시가 tools까지 덮는다(system 표시는 하나). 제품 고정 규칙, workspace 종류 지침, 지침 층은 싣지 않는다(지침 층은 읽지도 않아 깨져도 turn이 시작한다). workspace 정보는 lophn과 같은 글을 같은 자리(맨 끝, cache 경계)에 싣는다: custom도 `lophn` tool을 늘 가지므로 자기 workspace, 폴더, 부를 수 있는 agent, 앱 command 이름을 알아야 명령을 쓴다. 자기 agent memory는 받고 global memory와 workspace memory는 받지 않는다. skill 목록은 정의 `skills`로 고른 것이 있을 때만 그것만 싣는다. 고른 skill은 turn마다 다시 읽고 바꾸면 다음 turn부터다. 본문이 비면 system이 없다.
    - 제품 고정 규칙과 같은 `<lophn-untrusted>` 한 줄을 본문 끝에 늘 붙인다(`lophn` tool의 browser 명령이 늘 있어서다). tag escape와 받은 메시지마다 붙는 고정 글은 runtime과 상관없이 같다.
    - 보이는 tool = 고른 이름 ∩ workspace 종류 목록(`lophn` 빼고) + `lophn`(늘 선다. 설명과 `lophn help`에 싣는 명령은 lophn runtime과 같다: 그 workspace 종류의 명령 전부(명령의 `workspaces`)이고 할당한 앱 command는 `lophn <slug> <command>`로 부를 때 푼다) + `mcp__<server>__<tool>`로 고른 MCP tool + 할당한 extension 가운데 고른 tool. 목록 밖 이름은 말없이 빠진다.
    - 실행 목록은 그 session 고정 목록 중 지금 정의가 고른 tool과 그 workspace 종류의 명령·할당한 앱 command 전부다. 정의에서 뺀 tool은 바로 못 부르고 더한 tool은 새 session부터다(lophn의 tool 목록 고정과 같은 때). 명령과 앱 command의 상한은 lophn과 같은 workspace 종류, 할당, Gate다(custom이 좁히지도 넓히지도 않는다).
    - 브라우저(`tab.open`, `browser.*`) 같은 명령은 고르지 않고 `lophn` tool로 쓴다. 그래서 브라우저만 쓰는 좁은 agent는 내장 tool을 하나도 고르지 않아도 된다.
    - notice는 tool 목록이 바뀐 것만 간다. 지침과 agent 목록은 싣지 않으니 판 비교에서도 뺀다.

### 명령과 tool 결과

30. **model에 보이는 schema와 실행 검증은 구분한다.** 기본은 입력에서 JSON Schema를 만들고 tool API에서 쓰지 않는 생성기의 `$schema` 표시는 뺀다. 명시한 schema는 그대로 보낸다. description은 tool 선택과 호출에 필요한 의미·예외를 남기고 schema와 중복되는 문구를 줄인다.
31. **틀린 입력에는 어디가 왜 틀렸는지 알린다.** 실행기의 입력 검사가 거절하면 첫 문제의 자리와 이유를 싣는다(`at count: Too big: expected number to be <=5`, 모르는 key는 `unknown key extra`). handler가 `invalid_input`을 돌려주면 그 문장을 붙인다. `not_found`·`forbidden` 등 다른 code는 code별 고정 문장이다. handler 문장은 범위 밖 대상의 이름·존재를 담을 수 있으므로, handler의 `invalid_input` 문장에는 범위 밖 대상의 정보를 넣지 않는다. 실패한 대상이 model이 보낸 입력뿐인 tool(지금 `skill.read` 하나)은 handler 문장을 그대로 싣는다: 그 이름은 prompt의 skill 목록에 이미 실려 가릴 것이 없고, 가리면 원인을 못 가려 같은 입력으로 되풀이한다.
32. **목록과 하나는 `<자원>.read` 하나로 읽는다(`app.read {app?}`, `package.read {name?, version?}`).** 대상을 생략하면 목록, 주면 그 하나의 상세다. 기존 core route를 그대로 부르므로 읽기 범위(app workspace session은 그 앱 하나)와 오류는 route의 것이다. 지정한 대상이 없거나 범위 밖이면 그 오류이고 목록으로 바꾸지 않는다. 결과는 원래 목록·상세의 꼴 그대로다. `package.read`의 `version`과 `offset_bytes`는 `name`과 함께만 쓰고 `name` 없이 주면 `invalid_input`이다. `action` enum이나 중첩 union은 두지 않는다.
33. **모든 앱의 tool 목록을 읽는 tool(`app.tools`)은 home과 app 목록에만 있다.** 새 앱을 청받았을 때 이미 있는 기능을 찾고, app workspace의 agent가 선언의 `app_connections`에 정확한 tool key를 적으려는 것이다. 읽기 전용 route `app.tool_index`가 active 앱의 이름·설명과 tool(name, title, description, effect, public)만 주고 앱 하나를 지정하면 `inputSchema`와 선언된 `outputSchema`도 준다. 이 route는 앱 범위 판정을 하지 않는다. app workspace session의 자격이 그 앱 하나로 묶여 있어 기존 `app.list`·`app.get`의 검사는 그대로 두고, 돌려주는 칸을 이것으로 한정해 다른 앱의 source, ticket은 열리지 않게 했다.
34. **내장 SDK(`@lophn/*`)는 package tool이 설치 사본에서 읽는다.** `package.read`의 목록은 catalog의 앱 package 뒤에 `builtin` 칸을 싣고, `@lophn/` 이름을 주면 설치 사본(`<data root>/sdk`)의 판과 `guide.md`를 읽는다. 내장 SDK는 catalog에 등록하지 않고 설치 사본이 정본이다. 어느 role도 그 폴더를 file tool로 읽지 못하므로 tool이 대신 읽어 준다. guide가 tool 결과 상한보다 길면 상한 안의 창을 돌려주고 `continuation.read_next`에 다음 창의 `offset_bytes`를 싣는다(잘라 버리지 않는다).
35. **앱을 진단하는 읽기 명령(`app.status`, `app.logs`, `app.invocations`)은 home과 app workspace의 agent만 부른다.** 앱이 돌고 있는지, 앱 log에 무엇이 쌓였는지, 어느 호출이 어떻게 끝났는지를 원래 기록 그대로 읽고 판단하는 쪽이 agent의 몫이다(problem 같은 가공된 보고를 거치지 않는다). app workspace session의 자격은 그 앱 하나로 묶여 있다. log의 줄 꼴과 redaction은 `architecture/app-call.md`다.
36. **tool 결과는 model에 약 24 KiB까지만 싣는다.** shell은 stream마다 앞 12 KiB와 뒤 12 KiB만 남기고 가운데는 생략 표시로 바꾼다. 오류는 끝에 나오므로 뒤를 버리지 않는다. 출력 많은 명령 한 번이 context를 채우지 않게 한다.
37. **결과를 줄이는 것은 runtime의 일이고 명령 결과는 버리지 않는다.** 내장 명령과 앱 command의 handler는 전체 결과를 돌려준다. runtime이 크기를 재고 24 KiB를 넘으면 전체를 pretty JSON으로 `<data root>/tool-results/<session>/<tool call>.json`에 쓰고, model에는 그 안의 앞부분(배열이 있으면 배열 뒤쪽을 덜어 낸 것, 없으면 pretty JSON 머리)과 "전체(N bytes)는 그 경로에 있다, file.read·file.grep으로 읽어라" 한 줄을 준다. 기록되는 결과는 앞부분이라 다음 model 호출에도 같은 bytes다(cache). 쓰기에 실패하면 경로 없이 앞부분만 준다. 스스로 창을 나누는 tool(file.read, file.grep, web, shell, pdf)은 이 길을 타지 않는다(넘친 file.read를 다시 file로 쓰는 고리를 막는다). session을 지우면 rewind 기록과 같이 그 session의 결과 폴더를 지운다(보관은 남긴다). 그 session의 file tool은 자기 결과 폴더를 읽기로만 연다. 작업 폴더와는 따로라 cwd가 되지 않고 다른 session의 폴더와 data root의 나머지는 계속 막힌다. `lophn` binary는 이 길을 타지 않고 전체를 찍는다.
38. **사람 메시지와 받은 call·답의 이미지는 image part로 model에 바로 간다.** `image.read`를 거치지 않는다. 받은 이미지는 뒤 turn의 이력에도 그대로 실린다(받은 turn과 같은 bytes, `architecture/agent-call.md`). 넷 packer가 각자의 꼴로 싣는다: Anthropic은 user content의 `image` block, Responses·Codex는 `input_image`, Chat Completions는 이미지가 있을 때만 user content 배열, Cloud Code는 `inlineData`다. 이미지를 못 받는 model에는 tool 결과 이미지와 같은 `IMAGE_OMITTED` 글이 간다. 이미지에는 redaction을 하지 않는다. 자동 제목, 검색, Compact 요약 재료에는 이미지 자리에 고정 글 `[image]`가 간다. 앱 workspace의 session은 `image.read`로 annotation screenshot(`annotation:<id>`)도 연다.
39. **model 요청에 싣는 이미지는 최신 것부터 base64 합이 12 MiB 안인 것뿐이다.** tool 결과 이미지와 사람·받은 이미지를 같이 센다. 오래된 tool 이미지는 조각을 빼고 짝 tool 결과 글 끝에 `[image omitted]`를 붙인다. 오래된 사람·받은 이미지는 그 자리에서 `[image]` 글이 되어 part 순서가 바뀌지 않는다. 요청 body 전체를 blob으로 저장하고 그 상한이 16 MiB라 이미지가 쌓이면 model call을 보내지 못한다. 예전 규칙은 "최신 둘"이었는데 사람 메시지 하나에 작은 screenshot 여럿이 들어오면 개수 규칙이 볼 이미지를 뺀다. 상한을 넘을 때만 그 자리의 prefix가 바뀌어 cache가 한 번 깨진다. 입력 예산은 이미지를 base64 byte가 아니라 이미지당 고정 4096 token으로 센다(byte로 세면 screenshot 하나로 `context_limit`이 난다).
40. **입력 예산은 같은 turn 앞 call의 실제 prompt token에 늘어난 byte를 더해 잰다.** 앞 call의 token은 provider가 보고한 `input + cache_read + cache_write`다. 늘어난 byte는 그대로 token으로 세고 줄어든 byte는 3 byte를 한 token으로 뺀다. 앞 call이 없거나(turn의 첫 call) token을 모르면 이미지를 뺀 byte를 3으로 나눠 센다. 영어·code는 약 3.5~4, 한국어는 약 3~4.5 byte가 token 하나라 대개 실제보다 크다(byte를 그대로 token으로 세면 200k 창 model이 실제 약 5만 token에서 막혔다). compact 요약의 chunk와 본문 상한도 같은 세기다. 낮게 센 경우는 provider가 거절하고 아래처럼 줄인다.
41. **turn 안 이력은 context에 맞게 줄인다.** 조립한 요청이 예산의 85%를 넘거나 넘쳐 막히면 그 turn 안 가장 오래된 tool 결과부터 본문을 고정 문장 하나로 바꿔 60% 아래로 내린 뒤 다시 조립한다. 가장 최근 tool 결과 묶음 둘과 `skill.read` 결과는 바꾸지 않고, 50 token보다 적게 줄어드는 결과도 그대로 둔다. tool_use와 결과의 짝, 이미지·참조 조각은 남는다. 한 번 바꾼 결과는 그 turn이 끝날 때까지 바뀐 채라 그 뒤 prefix는 다시 같다(줄일 때마다 cache miss는 한 번). 원문은 tool 호출 기록에 그대로 있고 model은 필요하면 tool을 다시 부른다. provider가 입력이 크다고 거절하면(`context_exceeded`) 보낸 크기의 60% 아래로 줄여 다시 보낸다(turn마다 두 번까지). 줄일 것이 없으면 turn은 `context_limit`으로 끝난다.
42. **앞 turn의 tool 이력은 다음 turn에 그대로 이어진다.** turn은 tool 묶음이 끝날 때마다, 그리고 끝내기 직전에 turn 안 이력(답 글, tool_use, tool 결과, 반영한 steering, 마지막 답)을 blob으로 checkpoint한다(참조는 마지막 하나). 보낸 것과 같은 모양이다: 줄인 tool 결과는 줄인 채, 오래된 이미지는 뺀 채다. 다음 turn은 그 turn의 요청 메시지 뒤에 이 이력을 그대로 잇고 이력이 맡은 그 turn의 답·steering 메시지는 따로 넣지 않는다. 앞 turn이 마지막 call에 보낸 prefix와 바이트가 같아 다음 turn의 첫 call이 그 prompt cache를 읽고 model은 앞 turn에서 tool로 본 것을 잊지 않는다. 이력은 그 turn의 마지막 메시지 seq 자리에 놓여 Compact·숨김·접힘이 turn 끝과 같이 덮는다. 이력이 없는 turn(이 판 이전 turn, 남기지 못한 turn)은 메시지로만 읽는다. Compact 요약 재료로는 이력 message를 조각마다 나눠 tool 결과가 사람의 말이 아니라고 적는다. 이미지 상한은 앞 turn 이력까지 합쳐 센다.
43. **compact는 사람이 부르거나 이전 대화가 커지면 다음 turn을 시작하기 전에 runtime이 한다.** 같은 model이 요약하고 요약 대상 원문은 data 경계로 감싸 지시로 읽히지 않게 한다.
    - turn의 첫 call이 예산의 70%보다 크고 그 가운데 이전 대화가 예산의 5분의 1 이상이면, 또는 turn이 `context_limit`으로 끝나면, 그 session의 다음 입력이 골라질 때 runtime(machine 자격)이 Compact 요청을 열고 요약한다. 다음 입력이 오지 않는 session은 요약하지 않는다(Codex·opencode·Claude Code처럼 다음 요청 직전에 lazy하게 한다). 요약하는 동안 그 session은 도는 중으로 잡혀 turn이 요약이 끝난 뒤 시작하고(입력은 queue에 남는다) 다른 session의 turn 시작은 기다리지 않는다. 사람이 부른 Compact와 "Summarize from here"도 turn을 시작하는 pump를 기다리게 하지 않고 따로 하나씩 돈다. Compact는 대화 prefix cache를 깨므로 창이 꽤 찰 때까지 미룬다.
    - turn 안에서 조립 추정이 예산의 85%를 넘거나 provider가 입력이 크다고 거절하면 그 turn이 자기 session을 Compact한다(turn 안 Compact). 재료는 이전 대화(최근 사람 메시지 몇 개는 남김)와 이 turn의 진행(agent 응답과 tool 결과)이고 요약 지시에 작업이 진행 중이며 요약 뒤 같은 작업을 이어 간다는 뜻을 더한다. 끝나면 turn 메모리의 이력을 비우고 session 대화를 다시 읽어 같은 turn을 이어 간다. turn당 두 번까지이고 요약이 실패하거나 할 것이 없으면 가장 오래된 tool 결과부터 본문을 고정 문장으로 바꿔 60% 아래로 줄인다. core는 turn이 도는 동안 그 turn 자신(machine 자격, 입력의 `turn`이 도는 turn)의 Compact 요청과 확정만 받는다. 요청과 event(`CompactStarted`, `CompactEnded`)는 사람의 Compact와 같고 `CompactStarted`의 `turn`이 그 turn이다. 요약할 것이 없으면 요청을 열지 않는다. 실패해도 session은 풀리고 그 turn은 그대로 시작한다. 이 판단은 runtime 메모리에 있어 runtime이 다시 뜨면 잊고 그 뒤 넘치는 turn이 다시 정한다. agent는 Compact를 열지 못한다. 요약은 앞 요약이 있으면 그것을 갱신하고, 끝에 답을 기다리는 질문이나 요청이 있으면 그대로 남긴다.
44. **사람에게 묻는 중 사람이 그 session에 메시지를 보내면 기다림을 끝내고 그 메시지를 tool 결과로 넘긴다.** 그것이 답인지는 LLM이 읽는다. harness가 뜻을 가리지 않는다.

### skill

45. **skill은 목록(이름과 설명)만 prompt에 넣고 본문은 tool로 읽는다.** 꺼진 skill은 목록에서 빼고 읽기도 막는다. 도는 turn은 시작 때 읽은 판을 쓴다. `skill.read`는 `path`를 빼면 본문이고 `path: "SKILL.md"`(과 `./SKILL.md`)도 같은 본문이다. `path`는 SKILL.md 옆에 딸린 `.md` file 하나이고, 없으면 `not_found` 문장에 그 skill의 딸린 file 이름을 싣는다(없으면 `no bundled files`). model이 본문을 읽으려고 `path`를 채워 보내는 것이 실제 호출의 다수라 `SKILL.md`를 실패시키면 읽을 길이 없다.
46. **`SKILL.md`의 머리는 YAML로 읽고 YAML이 못 읽는 머리만 옛 줄 단위로 읽는다.** `name`과 `description`을 YAML(core schema)에서 읽어 `description: >`나 `|` 같은 block scalar도 받고 다른 key는 지우지 않고 무시한다. 따옴표 없는 값에 `: `가 있어 YAML이 못 읽는 옛 skill은 `key: 단순 값` 줄만 받는 줄 단위 읽기로 되돌려 전에 읽히던 skill이 사라지지 않게 한다(block·flow 표기와 중복 key는 이 길에서 거절). 닫히지 않은 fence, map이 아닌 머리, name·description 규칙 위반은 고치지 않고 제외 사유로 남는다.
47. **skill 층은 내장 < 공유 < 전역 < project·app < workspace-data이고 같은 이름은 마지막 층이 덮는다.** 단 내장 skill은 모두 끌 수 없고 사람 skill이 같은 이름으로 덮지 못한다(role이 일하는 데 필요한 skill이 사라지면 lophn 동작이 막힌다). 덮지 못해 제외된 사람 skill은 사유를 남겨 왜 안 보이는지 알린다. 전역은 등록 폴더와 개인 보관소(`~/.lophn/skills`)다. project·app 층은 그 workspace 폴더(project의 첫 등록 폴더, 앱의 source)의 `.lophn/skills`이고(Home은 폴더가 없어 이 층이 없다) repo에 commit되어 사람들과 같이 다닌다. 앱 workspace에서는 그 source의 skill이 public이 아닌 것까지 모두 `app` source로 보인다. 폴더가 없으면 그 층은 없다. workspace-data 층은 그 session 그릇의 data 자리 `<data>/home/skills/`, `<data>/projects/<prj>/skills/`, `<data>/apps/<app>/skills/`이고 사람의 폴더가 없는 project도 받는다. 그릇 session은 이 폴더를 file tool로 쓴다. `.agents/skills`나 다른 harness의 보관소는 읽지 않는다. 끄기는 이름 단위이고 전역 설정, workspace(Home·project·앱)의 `extensions.json`, agent 정의의 `skills_off` 세 곳이다. 층의 자리와 내장 skill 폴더는 workspace 종류 층이 정하고 harness는 받아 쓴다. 읽기 허락과 skill 발견이 같은 값을 써야 허락 밖 폴더를 찾다 막히지 않는다.
48. **agent 정의의 `skills_off`는 받지 않을 skill을 고른다.** 후보는 환경이 준 skill(내장, 공유, 전역, project·app, workspace-data) 전부이고 `skills_off`에 적힌 이름만 받지 않는다. 비면 전부 받는다. 끌 수 없는 내장 skill은 적어도 늘 받는다. 이름이 끈 것이라 어느 workspace에서 편집해도 뜻이 같다(받을 이름을 고르던 옛 `skills`는 한 workspace에서 보이는 목록으로 저장해 다른 workspace의 skill을 말없이 뺐다). prompt의 skill 목록, `skill.read`, `/` 메뉴가 같은 규칙을 쓴다. 내장 skill은 선언한 workspace 종류에서만 발견된다. prompt 목록, `skill.read`, `/` 메뉴, Agents 탭의 skill 수가 같은 발견을 쓰고 사람 화면(`ReadSkills`)만 workspace 종류 없이 모두 본다. 모든 agent 정의(lophn 포함)가 이 칸을 쓰고 전역과 workspace 층의 끄기 설정은 그대로 층마다 있다.
49. **할당한 앱의 public skill은 목록, `skill.read`, `/` 메뉴, Agents 탭 개수에 같은 규칙으로 실린다.** 정의의 `apps`가 가리키는 앱의 active release bundle에서 선언 `skills[].public`이 true인 것만 읽는다. 비공개 skill과 선언에 없는 폴더는 열지 않는다. prompt 목록과 `skill.read`는 core read `app.skills`(`architecture/app-call.md`)가 읽어 준 본문을 쓰고 동기 read인 `/` 메뉴와 Agents 탭 개수는 같은 규칙의 동기 읽기를 쓴다. 같은 이름은 slug가 앞선 앱의 것이 이기고 앱 자기 workspace에서는 `app` 층으로 이미 보이므로 공유로 싣지 않는다. 읽을 수 없는 skill(폴더 없음, 큼, 머리 틀림, 폴더 이름과 `name`이 다름, bundle 밖을 가리키는 symlink)은 오류 없이 뺀다: 다른 agent에게 주는 덤이라 하나가 틀려도 나머지는 가야 한다. `app.skills`를 읽지 못해도 공유 skill이 없는 것으로 보고 turn은 시작한다. `skills_off`로 끌 수 있다. 공유받은 skill을 적는 칸은 따로 없다: 할당이 곧 받기다. bundle의 값이 그대로 쓰이므로 활성 release가 바뀌면 다음 turn부터 달라진다.
50. **모든 workspace 종류에 같은 말은 제품 고정 규칙 한 곳에 둔다.** workspace 종류 지침(home·project·app)에는 그 종류에만 맞는 말만 두고 agent 이름을 말하지 않는다. 같은 종류의 lophn runtime session은 agent가 누구든 같은 지침을 받는다(custom은 싣지 않는다). 이름은 workspace 정보와 정의 본문이 준다. tool이나 skill이 일부 종류에만 있는 말은 고정 규칙에 "If you have …" 꼴로 둔다. `agent.create`는 세 종류 모두에 있어 그냥 쓴다. 넘기는 곳은 agent 이름과 workspace로 적는다(`to: {agent: "lophn", workspace: {app: "<name>"}}`).
51. **일의 절차와 쓰는 법은 내장 skill이다.** 사람이 부르는 `new-app`·`repair-app`(home), `write-workflow`(project), `write-artifact`(project, app), 설계 절차 `design-app`(app), package 내기·쓰기 절차 `publish-package`(app)가 있다. app 지침은 짓기 전에 `design-app`을 읽으라고만 하고 `DESIGN.md`의 절, kit 찾기, 화면 원칙은 그 skill이 갖는다. lophn 사용법을 설명하는 skill은 없다. 내장 skill의 선언은 이름, workspace 종류, `can_disable: false`, `menu`이고 설명은 SKILL.md frontmatter 하나에 있다. 설명은 "읽을지"를 고르는 재료라 무엇을 하는 skill인지만 말하고 절과 규칙은 본문에만 있다. 필요할 때 읽는 길은 `skill.read` 하나다. 설정의 뜻은 `settings.get`이 읽는다.
52. **`/` 명령은 session 조작 built-in 여덟(new, rename, archive, compact, fork, mcp, skills, permissions)과 skill뿐이다.** 메뉴 항목은 `{name, title, description, source: builtin | skill}`이고 묶음은 Commands와 Skills 둘이다. `/이름 글`은 `Use the "<skill>" skill for this request.` 뒤에 빈 줄과 사람이 친 글을 이어 그 session의 다음 turn 사람 메시지로 접수한다. 내장 skill은 `menu: true`인 것만 메뉴에 뜨고 내장이 아닌 skill(전역, project·app, workspace-data, 공유)은 늘 뜬다. built-in 이름과 같은 skill은 메뉴에서 빠진다(읽기는 된다). model 없이 tool을 바로 부르는 명령은 없다.

### memory

53. **memory는 셋이고 memory tool 하나로만 쓴다.** global memory는 Home의 workspace memory 파일(`<data>/home/memory.md`) 그것이다. 새 파일이 아니고, Home lophn이 쓰며 모든 workspace의 lophn과 사람이 만든 agent가 prompt로 받는다(Home session은 같은 파일이라 `global memory`로 한 번만 싣는다). project·앱 lophn은 Home lophn을 부를 수 없어(`agent-call.md`) 쓰지 못하고 읽기만 한다. workspace memory는 그 workspace 그릇 자리의 `memory.md`(Home `<data>/home/memory.md`, project `<data>/projects/<prj>/memory.md`, 앱 `<data>/apps/<app>/memory.md`)이고 그 workspace의 lophn만 쓰며 그 workspace의 모든 agent가 prompt로 받는다. lophn은 따로 agent memory가 없다. agent memory는 사람이 만든 agent마다 `<data>/agent-memory/<agt id>.md`이고 그 agent만 쓰고 받는다. file이 없으면 빈 memory다.
    - 쓰는 길은 `agent.memory` 하나다. 입력은 `new_string`과 선택 `old_string`뿐이다: `old_string`이 없으면 덧붙이고 있으면 정확히 한 번 나오는 글을 바꾼다(빈 `new_string`은 지운다). 자리 입력이 없고 어느 file인지는 부른 session의 agent id만이 정한다(lophn이면 그 id가 가리키는 workspace의 workspace memory, `agt_` agent면 자기 agent memory, 그 밖은 쓰지 못한다). 사람이 만든 agent는 workspace memory와 다른 agent의 memory를 쓰지 못하고 lophn은 다른 workspace의 memory를 쓰지 못한다. 모든 workspace 종류 목록에 있고(Home lophn도 file 쓰기 tool은 없지만 memory는 쓴다) custom은 골라야 받는다. effect는 `write`이고 Gate는 없다.
    - file tool은 memory file에 닿지 않는다. file tool 범위에는 memory 폴더가 없다. 대신 rewind의 쓰기 폴더에만 그 session의 memory 폴더(lophn은 workspace의 그릇 자리, 사람이 만든 agent는 `<data>/agent-memory`)를 더해 memory 쓰기도 file tool과 같은 pre-image를 남기고 rewind가 쓰기 전 내용으로 되돌린다.
    - memory는 앱·project·사람이 만든 agent를 이름과 id로 적는다(`Mahas (app_…)`). 이름은 바뀌고 지운 앱의 이름과 slug는 새 앱이 다시 쓰지만 id는 그대로다. 그래서 workspace 정보는 지금 workspace, Home의 앱·project 목록, 부를 수 있는 agent(lophn 밖) 줄마다 id를 싣는다. 싣는 때 memory 글에 나온 id마다 지금 이름(앱은 이름과 slug, project는 title과 name, agent는 이름과 handle, 보관 표시)이나 `deleted`를 푼 줄을 memory block 끝에 더한다. agent는 그 지금 이름으로 사람에게 말하고 call에는 slug를 쓰며 지운 것의 note를 지운다. 읽지 못한 id(not_found 밖의 오류)는 줄을 내지 않는다. 지운 것으로 잘못 알리면 agent가 사람이 정한 note를 지운다. memory file은 고치지 않는다(`agent.memory`의 `old_string`은 file 그대로의 글과 대조한다).
    - 사람이 만든 agent를 지우면 그 agent memory file도 지운다. 앱을 지우면 앱 폴더의 workspace memory가 함께 지워지고, 그 앱에 범위가 있는 agent의 agent memory도 agent 삭제를 따라 지워진다.
    - 주입: 지침 block 뒤에 `memory` system block으로 싣는다. 글은 `~~~data` 경계 안에 출처 줄(`global memory`, `workspace memory`, `agent memory`) 순으로 놓는다. cache 표시는 달지 않고 판 비교에 넣지 않아 notice도 없다. custom은 global·workspace memory를 받지 않는다.
    - session 첫 turn에 읽어 고정한다. session마다 첫 turn에 읽은 글을 쥐고 이후 turn에 같은 bytes를 싣는다. session 중에 쓴 memory는 다음 session부터 보인다(tool 결과가 그렇게 말한다). daemon이 다시 뜨거나 Compact로 compaction 경계가 바뀌면 다시 읽는다(tool 목록, 이전 turn의 판이 사라지는 때와 같다).
    - 파일마다 8 KiB이고 넘치는 쓰기는 거절한다(`invalid_input`, 거절 문장에 지금 크기를 싣는다). 줄이는 일은 agent의 몫이다. 자동 추출, 주기 정리, 검색은 하지 않는다.
    - 무엇을 담나는 내장 prompt가 말한다. Home memory는 모든 workspace가 읽으므로 workspace를 건너는 사실(사람의 계정·선호, workspace 지도, 앱에 대한 사람의 결정 가운데 program이 기록하지 않는 것)만 담고, login 목록은 계산되므로(`lophn login list`) 옮기지 않으며 "이 일에는 이 login"이라는 선택만 적는다. 사람이 정한 것, 계산할 수 없는 의도, "무엇을 누구에게 물으면 되나" pointer만 담는다. 정의·할당·명함처럼 계산할 수 있는 것과 다른 workspace의 내용은 담지 않는다. 경계를 넘는 길은 call뿐이다. 진행 상태(앱이 어느 판까지 옮겼나, home이 어느 판까지 검토하고 무엇을 정했나, 맡긴 기능이 끝났나)는 program이 ledger에 적고 돌려주므로(`architecture/ui-kit.md`의 "SDK 결정과 맡기기") global·workspace 어느 memory에도 담지 않는다. `update-apps`는 memory를 보지도 쓰지도 않고, `migrate-sdk`는 사람이 그 앱에서 고른 세부(임계값, 단축키)만 memory에 적고 묻기 전에 본다.

### 명함

54. **명함은 program이 계산하고 저장하지 않는다.** 읽기 route `agents/card`(명령 `agent.card`, `lophn agent card <handle>`)이고 모든 workspace 종류에서 부른다. 입력은 handle과 선택 `workspace`다: handle `lophn`은 workspace마다 하나라 workspace로 가리키고, agent session이 workspace 없이 읽으면 자기 workspace의 lophn이다(사람이 workspace 없이 읽으면 좁히지 않아 Home lophn이 먼저 걸린다). 칸은 handle, name, workspace, description, runtime, model, modality(없으면 셋 다), 답 방식(`replies`), 기본 lophn agent와의 차이(`diff.plus`, `diff.minus`), notes다. `model`은 정의 → workspace → 전역 순으로 정해진 model의 provider 이름, model 이름과 가격(USD, 1000000 token당 input·output, catalog의 `price_basis` 첫 요율이고 모르면 `price: null`)이다. model 층이 없거나 provider가 없거나 harness runtime(자기 model을 쓴다)이면 칸이 없다. 사람 화면과 `agent.card`를 읽는 agent가 같은 값을 본다(agent가 model과 가격을 보고 맡길 agent를 고를 수 있다). 차이는 그 agent의 정의로 계산한다(lophn이면 그 workspace의 lophn 정의). lophn은 plus가 할당한 앱의 public command에서 deny로 뺀 것을 제외한 것, `skills_off`에 없는 할당 앱의 public skill, 정의 층 MCP server 이름이고 minus가 `skills_off`다. custom은 plus가 고른 `tools`(내장·MCP·extension tool)를 적힌 그대로와 고른 skill(`skill: <name>`), minus가 `lophn built-ins`다. prompt 원문은 싣지 않는다. 답 방식은 칸 없이 정한다: 모든 runtime이 none, result, conversation이다(custom도 `lophn` tool로 `call.reply`를 늘 가진다). `modality.input`에 image가 있는데 고른 model의 catalog `input_media`에 image가 없으면 notes에 적는다(거절하지 않는다). 비공개 command와 deny로 뺀 command가 차이에 보이면 부르는 agent가 못 부르는 것을 보고 고르게 되므로 차이에서 뺀다. Router가 쓰는 동기 조회는 없는 handle과 틀린 정의 file이면 null이고 그 workspace에서 보이는 agent만 찾는다. agent session이 읽으면 범위 agent는 그 session의 workspace에서만 찾아지고 명함에 `callable: {home, here}`가 붙는다: 부르는 session이 그 agent를 home에서(workspace를 빼고 부를 때), 자기 workspace에서 부를 수 있는지(call 정책, `architecture/agent-call.md`). 그 밖의 workspace로 보낼 수 있는지는 보낼 때 Router가 정한다. 사람이 읽는 명함에는 없다.
55. **model에는 명함이 두 자리로 간다.** workspace 정보의 "Agents you can call"은 `- <handle>: <description>`(name이 handle과 다르면 `<handle> (<name>)`, 범위 agent면 `[this workspace only]`, description이 없으면 그 앞까지만) 한 줄씩이고 차이와 modality는 싣지 않는다(system prompt가 길어지고 할당이 바뀔 때마다 cache가 깨진다). 전체 명함은 agent가 `lophn agent card <handle>`으로 읽는다. 목록 줄과 notice 기준(seen의 agents)은 같은 줄 만들기를 써서 description이 바뀌면 system 글과 함께 `agents_changed` notice가 간다. description은 앱이 쓴 글이 아니라 정의의 글이라 notice에 실린다.

### 화면

56. **사람 화면(agent 목록 카드, 편집기)도 같은 `agents/card`를 읽어 보이고 renderer는 다시 계산하지 않는다.** 편집기의 명함은 저장된 정의를 따른다. 편집기에서 modality를 고르고 한쪽 셋을 다 고르면 그쪽 칸은 file에서 빠진다. 명함 runtime 줄은 정의의 runtime 값을 그대로 보인다(custom은 `Custom`). model 줄은 `model`이 있을 때만 보이고 가격이 없으면 가격 없이 이름만 보인다.
57. **Agents 탭은 Home, project, 앱 어디서나 열리고 그 workspace의 층을 보이고 고친다.** 여는 길은 탭 줄 + menu의 Agents 항목이고 대화의 권한 view의 Edit도 같은 탭을 연다(탭은 workspace에 하나). 지침(project·Home은 `LOPHN.md`, 앱은 source 폴더의 `AGENTS.md`이고 source를 잇지 않은 앱은 빈 칸이 잠긴 채 보인다), workspace memory, workspace model 하나, skill 켜고 끄기, MCP server다. Home 층 MCP server의 로그인 owner는 `{kind: "home"}`이다. memory 칸은 8 KiB 대비 크기를 보이고 사람이 고친 글은 다음 session부터 보인다는 안내가 있다. 사람은 지침과 같은 길로 memory를 고친다. agent 편집기에는 사람이 만든 agent의 agent memory 칸이 있다(lophn은 workspace memory를 쓰므로 없고 저장 전의 새 agent도 없다). Home Agents 탭의 memory 안내는 이 memory가 global memory로 모든 workspace에 가는 것을 말한다. 편집기는 탭으로 나뉜다: General(profile, name, handle, 범위, 설명, 받고 내는 것, 명함, Skip permissions, Delete), Runtime(runtime과 model), Instructions, Skills, Memory, Tools(custom이 고르는 tool, MCP server, shell extension), Grants. harness runtime에는 Skills·Memory·Tools가 없고 lophn에는 Memory가 없으며 저장 전의 agent는 Grants를 열 수 없다. [Cancel]·[Save]는 어느 탭에서나 보이고 거절된 항목이 숨은 탭에 있으면 그 탭에 표시가 뜬다. [Open]은 같은 탭을 그 agent의 편집기로 바꾸고(탭 이름과 아이콘도 그 agent다) 왼쪽 위 ←·→(마우스 뒤로·앞으로, Alt+←·→)가 그 탭에서 연 목록과 agent 사이를 오간다. 이동 기록은 메모리에만 있다. 편집기는 읽거나 저장한 정의와 다른 값을 쥐면 탭 줄에 문서 탭과 같은 저장 안 됨 표시를 띄우고(다른 탭에 다녀와도 편집이 남는다) Ctrl+S로 저장하며, 편집이 남은 채 이동하거나 탭을 닫으면 문서 탭과 같은 질문을 한다. 저장은 편집기에 머문다(새 agent는 만든 agent로 이어진다). project·앱의 Agents 탭 목록은 그 workspace의 lophn(첫 줄)과 전역 agent, 그 workspace 범위 agent만 보인다(다른 workspace의 lophn과 범위 agent는 목록에 두지 않는다). Home의 Agents 탭은 모든 agent를 보인다: Home lophn, 전역 agent, 모든 project·앱의 범위 agent(다른 workspace의 lophn은 뺀다). 사람은 workspace를 열지 않고 어느 agent든 한 곳에서 보고 고친다. 범위 agent의 카드는 범위(`<name> · project`·`<name> · app`)를 보이고, 열면 같은 editor가 그 agent 자신의 workspace로 열려 지침·skill·MCP 층이 그 workspace의 것이다. Home에서 만드는 새 agent는 그대로 전역이다. 목록은 `agents/list`를 workspace 없이 불러 읽는다(사람은 전부 받는다). lophn 편집기는 handle·profile을 잠그고 name을 바꾸게 하며 범위 칸은 id에서 나온 workspace를 읽기 전용으로 보이고 Delete가 없다. 저장·할당 panel·MCP server의 credential 이름(`mcp.<scope>.<server>`)은 그 lophn id를 쓴다. Settings › Agents에는 lophn card와 편집이 없다(전역 기본 model, 전역 `LOPHN.md`, call policy만 있다). call policy의 agent 쌍 목록에서 lophn은 이름이 같아 `lophn · <workspace 이름>`으로 가른다. session·job·알림이 agent 이름을 보일 때는 그 session의 lophn id로 name을 읽는다. 카드·명함·편집기에 범위를 `All of lophn`(전역 agent) / `Home`(Home lophn) / `<name> · project` / `<name> · app`으로 보인다. 새 agent의 범위는 편집기의 Workspace 칸에서 고른다: 기본은 화면을 연 workspace이고 전역으로 바꿀 수 있으며, Home이나 Settings에서 열면 전역뿐이다. 고른 값은 만들 때 `definition.workspace`로 보낸다. 저장된 agent의 범위는 읽기 전용이다(core가 바꾸는 저장을 거절하므로 바꾸는 길을 화면에 두지 않는다).
58. **dev:mock도 편집 화면과 대화가 같은 AgentsSource를 쓴다.** 대화 기록만 장면별 fake이고 이름·profile은 요청한 agent의 정의에서 읽는다. 정의나 grant를 저장하면 열린 대화의 `changed` 구독에도 알려 다시 읽는다.

### model 호출과 credential

59. **provider credential(API key, 구독 OAuth access token)은 `secrets.json`의 이름 `provider.<id>`로만 가리킨다.** ConnectProvider는 그 provider 몫의 이름만 받는다. 값은 core가 전송 직전에 그 이름을 가진 회수되지 않은 provider의 endpoint origin과 요청 목적지가 같을 때만 읽어 agent runtime의 전송 callback 하나에 준다. 값은 ledger, event, log, 오류, model 입력에 없다. 다른 이름을 가리킬 수 있으면 앱·MCP secret이 provider endpoint로 나간다.
60. **secret 저장소는 `secrets.json` 하나이고 이름의 앞머리가 이름 공간이다.**
    - `provider.`는 provider credential이다(구독 OAuth는 옆에 `provider.<id>.refresh`·`.meta`를 둔다. 둘은 어떤 provider의 secret_name과도 같지 않아 core 밖으로 안 나간다). `mcp.`(`mcp.<global 또는 agent의 agt id>.<서버>`)는 사람이 넣은 MCP credential이고, `mcp-oauth.<scope>.<서버>.access`·`.refresh`·`.meta`는 MCP OAuth token이다. `app-oauth.<이름>.refresh`·`.meta`·`.client_id`·`.client`는 앱 OAuth의 갱신 token, meta, 사람이 넣은 client이고 access token은 앱이 선언한 이름 그대로 둔다(`architecture/app-call.md`). `provider-oauth.`는 provider 로그인이 쓰는 core 안의 이름이다. `login.<lgn id>.password`·`.totp`(TOTP seed)는 사람이 넣은 site login 값이고 metadata(label, origin, username, note)는 `<data>/logins.json`(0600)에 따로 둔다(`architecture/browser-tab.md` "site login").
    - 전송 부착은 앞머리로 용도를 정한다. `app-oauth.`, `provider-oauth.`, `login.`은 누가 불러도 보내지 않는다. `login.` 값이 core를 나가는 길은 shell main이 shell capability로 부르는 `logins/release` 하나다. 앞머리가 없는 이름은 앱 secret이고 앱을 대신하는 호출(`conditions.app`)만 보낸다(앱 호출이 앞의 셋을 가리키거나 그 밖의 호출이 앱 secret을 가리키면 거절한다). 앱 secret의 목적지는 이름 공간이 아니라 현재 선언 ∩ active grant가 정한다.
    - provider와 MCP 이름의 목적지는 이름 공간마다 따로 찾는다: `mcp.` 값은 그 이름을 header나 bearer·api_key로 보내는 켜진 http 서버(전역, project 층, 모든 agent의 정의 층)의 URL origin으로만, `mcp-oauth.` 접근 token은 그 meta가 묶인 서버 URL origin으로만 간다. 갱신 token과 meta는 core 밖으로 나가지 않는다. MCP 설정 schema는 `mcp.` 이름만 받으므로 설정(사람 실수나 agent가 고친 project 설정)이 provider key나 다른 서버의 token을 가리켜 MCP URL로 보내지 못한다.
    - 값을 넣는 것은 사람뿐이고 보호 입력 창으로만 들어온다(`secrets/put`은 사람 자격). agent는 값이 필요한 자리를 가리켜 요청만 한다: `lophn ask secret`(`input_request/ask`)이 `ask`와 같은 session 대기열에 서서 대화에 card로 뜨고, 사람이 card를 눌러야 shell main이 창을 연다(site login 요청과 같은 요청 모델이다, `architecture/browser-tab.md`). agent는 secret 이름을 넘기지 못하고 자리만 넘기며 자리는 CLI flag로 그대로 옮겨 적을 수 있는 평평한 모양이다. 이름, 대상 이름, card에 보이는 목적지, 로그인 target은 core가 정의·grant·설정에서 읽는다. 자리는 넷이다. (1) provider: 내장 정의 key(API key와 로그인을 둘 다 가진 정의는 기본이 API key이고 `sign_in`을 줘야 로그인, 로그인뿐인 정의는 로그인)나 custom provider(`display_name`·`base_url`·`protocol`: Settings의 Custom 연결과 같은 규칙으로 https 주소만 key와 함께 받고 이름은 `display_name`에서 core가 만들며 card가 host를 크게 보인다). provider 자리는 home session만 청한다. 같은 정의의 provider가 이미 있으면 key를 바꾸고(다른 방식으로 연결돼 있으면 `conflict`), 없으면 값을 저장한 뒤 shell main이 `providers/connect`까지 보내며 연결이 실패하면 넣은 값을 지운다. (2) 앱 secret: app id와 그 앱의 active grant에 있는 `secret.use` 이름이고 그 앱의 session과 home session만 청한다. OAuth를 선언했으면 로그인이다(client id가 아직 없으면 `conflict`). (3) MCP server: 설정에 이미 있는 server 이름. core가 이 session이 닿는 층에서 찾는다: home은 전역·Home 층·자기 agent 정의 층, project·앱 session은 자기 agent 정의 층과 자기 workspace 층(다른 workspace에는 닿지 않는다). 같은 이름이면 agent > workspace > 전역이 이긴다. http server가 가리키는 `mcp.` 이름(header, bearer·api_key credential, oauth2 client credential)이 값 자리이고 oauth2는 로그인도 자리다. 청할 것이 여럿이면 `part`(`credential`, `client`, `sign_in`, `header:<이름>`)로 고르게 하고, 청할 것이 없는 server(stdio 포함)와 닿지 않는 server는 `not_found`다. (4) 로그인(`sign_in` 요청): 구독 provider, 앱 OAuth, MCP OAuth는 넣을 값이 없어 card의 [Sign in]이 Settings·앱 상세와 같은 로그인 흐름을 돌린다. 무엇에 로그인하는지(provider 연결 입력, 앱과 이름, MCP begin 입력)는 core가 요청 view에 싣고 card는 그 target만 쓴다. 끝나면 card가 `input_request/done`으로 `signed_in`이나 오류를 알린다(sign_in 요청은 그 두 가지만 받는다). agent가 받는 것은 `stored`, `signed_in`, `cancelled`, `unattended`나 값이 없는 오류뿐이다. 요청은 grant를 주지 않는다.
61. **MCP OAuth의 접근 token과 갱신 token은 각자 이름이다.** 알려진 값 registry가 값 전체로 맞추므로 JSON 하나로 합치면 token 하나를 redaction할 수 없다. 만료가 가까우면 core가 보내기 전에 갱신하고 secret store의 put이 새 값을 먼저 알려진 값으로 올린다. 발급자가 갱신을 400·401·`invalid_grant`로 거절하면 세 이름을 지우고 사람이 다시 로그인한다. 그 밖의 실패(5xx, 닿지 못함)에는 만료 전 token을 그대로 쓴다.
62. **MCP OAuth sign-in은 server의 소유자로 연다.** 소유자는 전역(workspace·agent 둘 다 null), Home 층(workspace `{kind: "home"}`), project·앱 층(workspace), agent 정의 층(agent id) 중 하나이고 `agent-mcp-auth/*`가 `workspace`와 `agent`를 받는다(둘 다 있으면 `invalid_input`). token 이름도 소유자로 정한다: `mcp-oauth.<global, home, workspace id, 또는 agent id>.<server>.*`(전역 `global`과 Home 층 `home`은 다른 소유자다). 같은 이름의 server가 층마다 있어도 token이 섞이지 않는다. 사람이 server form에서 OAuth 2.1(issuer, client ID, scopes)을 고르고 client secret은 더한 뒤 보호 입력으로 `mcp.<scope>.<server>.client`에 넣는다(넣지 않으면 public client). core는 그 값을 token 교환과 refresh 본문에만 싣는다. 시작할 때 `${issuer}/.well-known/oauth-authorization-server`를 먼저 읽어 https 끝점을 쓰고 없거나 맞지 않으면 `${issuer}/authorize|token`이다. dynamic client registration은 없다. agent 정의 층 server는 저장된 정의 file에서 찾으므로 저장하기 전에는 sign-in하지 못한다.
63. **구독 provider 로그인(ChatGPT, SuperGrok, Claude, Google Antigravity)은 token을 core만 만진다.** core가 writer queue 앞에서 `BeginProviderLogin`·`CompleteProviderLogin`·`CancelProviderLogin`을 받는다. SuperGrok은 device code다. ChatGPT(`openai` 정의의 product `chatgpt`), Claude(`anthropic` 정의의 product `claude`), Antigravity(`google-antigravity` 정의)는 PKCE와 정의의 `redirect_uri`에 고정된 callback이다(ChatGPT `localhost:1455/auth/callback`, Claude `localhost:54545/callback`, Antigravity `127.0.0.1:51121/oauth-callback`). ChatGPT는 Codex CLI의 공개 client(`app_EMoamEEZ73f0CkXaXp7hrann`)로 로그인하고 교환은 form이다. 계정 id(`chatgpt_account_id`)와 email·plan은 token claim에서 읽고 계정 id가 없으면 연결하지 않는다. browser를 열기 전에 그 port로 듣고(`localhost`면 127.0.0.1과 ::1을 함께 쥔다) 다른 프로그램이 쓰고 있으면 `conflict`다. listener는 path와 이 시도의 state가 맞는 callback 하나만 받고 다른 요청은 400으로 돌려보낸 채 기다림을 잇는다. Claude 교환은 JSON이고 token 응답에 계정·조직이 빠지면 bootstrap으로 빈 칸만 채운다. Antigravity 교환은 form에 installed-app client pair를 싣고 refresh token이 없으면 연결하지 않는다. 그 뒤 userinfo로 email을, `loadCodeAssist`(tier가 없으면 free-tier `onboardUser`와 30초 안의 operation poll)로 Cloud Code project를 정한다. 마지막 `loadCodeAssist`가 준 project만 저장하고 없으면 연결하지 않는다. 로그인이 확정한 계정(id, email, 조직, project)은 비밀이 아니라서 credential의 `account` 칸에 둔다. Complete는 기다리지 않고 한 번 보고 pending이나 연결된 provider를 낸다. 끝나면 core가 token 셋을 저장하고 사람의 context로 ConnectProvider를 부른다. token은 renderer와 ledger·event·log를 지나지 않는다. 발급자 주소와 client 값은 provider 정의 data라서 fake 발급자는 정의만 바꿔 돈다.
64. **구독 OAuth access token은 runtime에 건네기 직전에 갱신한다.** agent runtime이 `provider.<id>`를 달라고 하면 core가 만료까지 5분 미만일 때 provider마다 한 번에 하나만 refresh grant를 보낸다. token을 바꾸는 곳은 이 하나다(model 호출과 model 목록이 따로 갱신하지 않는다). grant 꼴은 product가 정한다: ChatGPT·SuperGrok·Antigravity는 form(Antigravity는 client pair를 싣는다), Claude는 JSON에 OAuth beta와 SDK User-Agent를 붙인다. Antigravity는 저장된 project가 없으면 보내지 않고 project를 다시 찾지도 않는다. 발급자의 답을 받으면 provider를 다시 읽고 그사이 Disconnect했거나 다시 로그인했으면(`logged_in_at`이 다르면) 늦은 token을 저장하지 않는다. refresh token은 회전할 수 있으므로 새 refresh를 먼저 저장하고(오지 않으면 지금 것을 그대로 쓴다) access를 저장한 뒤 `RefreshProviderCredential`로 만료를 올린다. 저장이 실패하면 받은 같은 값으로 다시 쓰고 이미 쓴 옛 refresh token을 다시 보내지 않는다. 발급자가 grant를 거절하면 credential이 `revoked`가 되고 token을 건네지 않는다. 그 밖의 실패는 지금 token이 살아 있으면 그대로 건넨다. 같은 refresh token을 두 곳에서 쓰면 발급자가 둘 다 폐기할 수 있기 때문이다.
65. **구독 OAuth provider의 계정 model 목록만 계정의 허락 목록이다.** ChatGPT와 Antigravity provider는 연결 직후와 갱신 직후, 그리고 목록이 아직 없을 때 token을 건넨 뒤에 같은 Bearer로 계정 model 목록(ChatGPT Codex backend `GET /models?client_version=…`의 `models[].slug`, Antigravity 그 project의 `fetchAvailableModels`에서 내부용·꺼진 줄을 뺀 key)을 읽어 `credential.reported_models`에 둔다(`RecordProviderModels`). 읽는 일은 token을 기다리게 하지 않고 실패하면 앞서 저장한 목록을 남긴다. model을 고르는 화면과 turn의 resolver는 목록 밖 이름을 쓰지 않는다(`null`이면 거르지 않는다).
66. **ChatGPT 구독 호출은 Codex backend로 보낸다.** 연결의 provider endpoint는 정의의 `oauth.inference_endpoint`(`https://chatgpt.com/backend-api/codex`)다. packer가 만든 Responses body를 보내기 직전에 `/responses`로 바꿔 보낸다: `max_output_tokens`를 빼고(backend가 거절한다) `include`에 `reasoning.encrypted_content`를 늘 넣고, session에서 만든 같은 값을 본문 `prompt_cache_key`와 `session_id`·`conversation_id`·`session-id` header에 싣는다. backend는 이 값으로 cache를 가진 machine을 고르므로 빠지면 앞부분이 같은 요청도 cache를 거의 못 읽는다. `chatgpt-account-id`·`originator`·`version`(Codex client 판, model 목록도 이 판으로 거른다) header를 붙인다. 값은 Codex client profile이고 OpenAI가 제3자에게 공개 보장한 계약이 아니다. plan 한도 code `usage_limit_reached`는 `credential_unavailable`·`quota`로, `usage_not_included`는 `plan_access`로 읽는다.
67. **Claude 구독 호출은 Claude Code client profile로 보낸다.** packer가 만든 Messages body를 보내기 직전에 다시 만든다: `/v1/messages?beta=true`, Claude Code header 묶음(`anthropic-beta`에 option의 beta를 합친다), system 앞의 billing block과 identity block, custom tool 이름 앞 `_`(응답의 tool 이름은 그 요청의 표로 원래 이름으로 되돌린다), `metadata.user_id`(provider와 계정에서 만든 device id, session에서 만든 session id), 마지막 byte의 cch(placeholder를 넣어 직렬화한 byte의 XXH64를 host가 만든 billing slot 다섯 byte에만 쓴다). 모든 cache 표시의 수명은 1시간(`ttl: "1h"`)이다: Claude Code도 plan 안의 대화에 1시간을 쓰고, 5분이면 tool 실행이나 사람을 기다리는 사이에 cache가 사라진다. 표시를 모두 같은 수명으로 두어 "긴 수명이 짧은 것보다 앞" 규칙에 걸리지 않는다. 같은 `anthropic` 정의의 API key 호출은 이 profile을 쓰지 않는다.
68. **Antigravity 호출은 protocol `cloud-code-assist`다.** Claude model도 Anthropic wire가 아니라 Google contents/parts로 간다. packer가 이력을 contents로 옮기고(tool 결과는 call ID로 잇고 그 assistant turn의 call 순서대로 user turn 하나에 모은다, tool schema는 Cloud Code가 받는 부분집합으로 줄인다) 보내기 직전에 `{project, requestId, request, model, userAgent}` envelope로 감싼다. conversation 값(cascade·trajectory·`sessionId`)은 session에서 만들어 요청마다 같다. 응답은 `{"response": …}` frame이고 root error, prompt 차단, finishReason 없는 끝은 성공이 아니다. Gemini가 functionCall에 붙인 thought signature는 tool call에 실려 그 turn의 이력(`tool_use.signature`)을 따라가고 같은 turn의 다음 요청에 그대로 돌려보낸다(서명 없이 먼저 온 조각의 서명은 다음 functionCall에 붙인다). 서명은 turn 이력에 함께 남아 뒤 turn에도 그대로 가고, 서명이 없는 functionCall(이력을 남기지 않은 옛 turn)에는 서명 검사를 건너뛰는 표시를 싣는다. output 상한은 보내지 않는다. 계정 project가 없는 credential로는 turn을 시작하지 않는다.
69. **OAuth 발급자 호출(MCP, provider, 앱 OAuth)은 대기열 하나로 runtime이 대신 보낸다.** core module graph에는 외부 fetch가 없다. core가 요청(https이거나 loopback http, GET·POST)을 대기열에 놓고 agent runtime이 machine 입구(`TakeIssuerRequest`·`FinishIssuerRequest`)로 가져가 보낸 뒤 답한다. 요청과 응답 본문은 작업 메모리에만 있다. 계정 model 목록 GET(Bearer)도 이 대기열이 나른다.
70. **custom provider가 알려 주는 model 목록은 찾기 위한 것이다.** custom provider는 연결 form에서 API(Chat Completions, Responses, Anthropic Messages)를 고르고 그 값이 정의의 `protocols`와 provider의 `protocol`이 된다. 요청 경로와 인증 header는 내장 provider와 같다(Anthropic Messages는 `x-api-key`). 내장 정의가 아니고 OAuth도 아닌 provider는 연결 직후와 사람의 `RefreshProviderModels` 때 core가 `GET {endpoint}/models`(OpenAI 호환 `data[].id`)를 같은 발급자 대기열로 읽어 `credential.reported_models`에 둔다. 정의의 `models_endpoint`는 https만 담으므로 주소는 provider의 endpoint에서 만든다(local http 주소도 같다). `api_key`면 `provider.<id>` 값을 endpoint와 같은 origin에만 Bearer로 붙인다. 실패하면 저장하지 않아 앞 목록이 남고 명령은 `unavailable`이다. 내장 provider와 OAuth provider에는 `invalid_input`이다: 내장 provider의 `/models`에는 embedding 같은 model이 섞여 고를 목록을 망친다. 이 목록은 고를 것을 보여 줄 뿐 목록 밖 이름을 막지 않는다. 연결 직후 화면이 목록을 한 번 다시 읽어 찾았으면 도착한 창에 찾은 수를 한 줄로 보이고 없으면(실패나 빈 목록) Manage models의 그 provider 묶음과 model 정보 form을 바로 연다. 기본 model 고르기는 그 뒤다. 이 읽기는 Bearer만 붙이므로 Anthropic Messages 주소에서는 대개 실패해 form으로 간다.
71. **model catalog는 동봉 snapshot 위에 models.dev 갱신을 덮고 사람이 적은 custom model 정보가 맨 위 user 층이다.** snapshot은 판을 낼 때 만들고 실행 때 갱신(2시간에 한 번 공개 GET, 설정 `lophn-agent.model.catalog_auto_update`로 끈다)이 같은 변환을 쓴다. catalog는 고를 수 있는지를 정하지 않고 정보(한도, option 축, 입력·출력 형식, 가격)만 준다. 고를 목록은 provider가 알려 준 목록이 있으면 그것, 없으면 그 정의의 catalog 항목이고, 어느 쪽이든 사람이 정보를 적은 그 정의의 model을 더한다. 다른 정의의 catalog 항목은 이름이 같아도 빌리지 않는다(같은 이름도 provider마다 한도가 다르다). 사람이 적은 정보(`SaveUserModelInfo`·`RemoveUserModelInfo`·`ReadUserModelInfo`, compare `seq`)는 custom 정의에만 받고(내장·OAuth 정의 key는 `invalid_input`) ledger에 둔다. 파생 `catalog.json`은 깨지면 snapshot으로 다시 만들어 사람이 적은 것을 잃기 때문이다. catalog를 읽는 세 곳(`ReadModelCatalog`, turn resolver, 저장 검사·session model)이 모두 그 정보를 `source: "user"` 항목으로 만들어 같은 열쇠의 catalog 항목 위에 둔다. 사람이 안 적은 한도는 turn이 칸마다 기본 한계로 채운다. core는 어느 provider에서나 목록 밖 model 이름을 받는다(화면에서 이름을 적는 길은 Manage models의 custom provider [Add model]뿐이다). catalog에 없는 이름은 option 축 없이 기본 한계(context 131072, output 4096, tool 지원)로 돌고 호출 기록의 basis에 `model_listed: unknown`으로 남는다. 이름이 틀리면 provider 호출이 거절해 기존 실패 길(`model_unavailable`)로 드러난다. 거절하는 것은 구독 OAuth 계정의 허락 목록 밖 이름뿐이고 저장 검사는 목록을 보지 않는다.
    - **agent의 model 선택 정보는 `lophn agent models`로 읽는다.** 사람이 켠 목록과 현재 provider에서 고를 수 있는 목록의 교집합을 화면 picker와 같은 규칙으로 계산한다. provider ID·이름과 model 이름, 지원 옵션 축·값·기본값, token 한도, 입력·출력 media, 가격을 함께 돌려준다. 계정·credential·접속 metadata와 옵션의 전송 wire는 싣지 않는다. catalog에서 확인하지 못한 정보는 null이고 options가 null이면 option_values는 빈 객체만 쓴다. 빈 options 배열은 옵션이 없다고 확인된 것이다. 이 목록을 prompt에 주입하지 않고 설정 전에 agent가 조회한다. 저장된 정보만 읽고 model provider를 호출하거나 사람이 켠 목록을 바꾸지 않는다.
72. **한 호출의 output은 `min(32000, output_limit, context_limit / 4)`이다.** OpenAI 계열이 보내는 `max_tokens`와 입력 예산이 남기는 output 몫(turn 준비, compact)이 같은 값이다. vLLM 계열은 입력과 `max_tokens`의 합이 context를 넘으면 거절한다. context의 4분의 1로도 묶어 작은 context model이 창 대부분을 입력에 쓴다. Anthropic은 `min(output_limit, 32000 + thinking 예산)`이다. Cloud Code Assist는 상한을 요청에 싣지 않고(계정 model의 상한을 모른다) 입력 예산만 같은 몫을 남긴다. Chat Completions의 effort `maximum`은 `"max"`로 보내고 Responses에는 그 값이 없다.
73. **call의 추정 비용은 겹치지 않는 token 구간 × 그 call의 `price_basis` 요율이다.** 새 입력, cache read, cache write, output을 각자 요율로 곱한다. cache 요율이 없으면 input 요율로 센다. 저장된 `input`은 adapter가 이미 cache를 뺀 새 입력이라 다시 빼지 않는다(`cache_in_input`은 provider가 원래 어떻게 세는지를 적은 표시다). provider는 금액을 주지 않아(OpenAI·Anthropic·b.ai 응답의 `usage`는 token 수뿐) 금액은 늘 `estimated`이고 가격이 없으면 `unknown`이다. 계산한 비용을 보이는 화면은 없다(`ReadAgentUsage`로 읽는다).
74. **model을 고르는 세 자리(대화의 picker, Settings → Agents의 Default model, agent·project 정의의 Model 칸)는 같은 picker이고 고르기만 한다.**
    - 붙인 provider의 model 가운데 켠 것만 provider별로 보이고 지금 고른 model은 꺼져 있어도 보인다. 지금 model이 어느 층(이 대화 > agent 정의 > workspace > 전역 기본값)에서 왔는지 한 줄로 보인다. workspace 층은 Home, project, 앱이 각자 갖는다(ledger `model_choices`의 scope가 `home`, project id, 앱 id이고 `ReadWorkspaceModel`·`ChangeWorkspaceModel`이 `{workspace: "home" | prj id | app id}`로 읽고 고친다). 정의 읽기의 `effective.model.source`는 agent가 고르지 않았고 그 workspace 층에 model이 있으면 `project`다(출처 이름은 workspace 층을 가리킨다. 공개 SDK type에 실려 있어 이름은 그대로 둔다).
    - 맨 아래 "Manage models" 줄이 Manage models 창을 연다. 그 창에서 provider마다, model마다 켜고 끄고 "+ Connect provider"로 연결 창을 연다. 붙이면 그 provider 묶음이 맨 위에 온다. model 행에는 입력 형식 icon과 context가 보인다. custom provider 묶음에는 목록 다시 읽기와 [Add model]이 있고 model 행마다 [Edit]이 있다. 둘 다 model 정보 form을 연다. 저장한 정보는 user 층이라 다시 읽기가 목록을 provider 것으로 바꿔도 그 model이 남는다. 켠 model은 전역 목록 하나(`ReadShownModels`·`ChangeShownModels`, 칸 `provider`·`model_name`)에 적는다. 기본이 끔이라 새 provider와 새 model은 꺼져 나오고 사람이 Manage models에서 켠다.
    - 사람이 model을 고르면(전역 기본, project, session 저장) core가 같은 transaction에서 그 model을 켠 목록에 더한다. 고른 model이 picker에 보여야 하기 때문이다. 전역 기본 model이 없을 때 session이나 project의 model을 처음 고르면 그 선택이 전역 기본으로도 저장된다(다음 대화가 model 없이 실패하지 않게 한다). 전역 기본 model이 없을 때 provider를 붙이면 기본 model 고르기 창이 뜬다. 켠 model이 아직 없으므로 그 창의 picker는 켠 목록과 상관없이 고를 수 있는 model 전부를 보이고(`showAll`) Manage models 줄이 없다.

## 경계와 계약

- boundary: `agents`(정의, 명함, 할당), `agent-workspaces`(workspace 종류 층), `agent-tools`, `run-loop`, `core-api`. 코드 module과의 대응은 `project-docs/module-catalog.yaml`이다.
- **route(사람과 machine)**: `agents/list|read|create|change|delete|card`, `assignments/*`(할당 읽기·쓰기), `agent-mcp-tools/list`(MCP tool 이름·설명·effect, agent id를 실어 정의 층을 더한다), `agent-mcp-auth/*`(MCP OAuth, `workspace`와 `agent` 둘 중 하나), 지침 읽기(층 `global | home | project | app | agent`), skill 읽기(`skills/read`, 입력 `{workspace?: "home" | prj id | app id}`), workspace 설정(`workspaceExtensionSettingsRead|Change`, `workspaceModelRead|Change`, 입력 `{workspace: "home" | prj id | app id}`), provider 연결(`ConnectProvider`, `BeginProviderLogin`·`CompleteProviderLogin`·`CancelProviderLogin`, `RefreshProviderCredential`, `RefreshProviderModels`, `RecordProviderModels`), model 정보(`SaveUserModelInfo`·`RemoveUserModelInfo`·`ReadUserModelInfo`, `ReadModelCatalog`, `ReadShownModels`·`ChangeShownModels`), 사용량(`ReadAgentUsage`), Compact(`CompactStarted`·`CompactEnded` event).
- **agent actor가 부르는 읽기**: `agent.list|read|card`, `app.read`, `package.read`, `app.tools`(route `app.tool_index`), 진단 명령 `app.status|logs|invocations`, `skill.read`. agent 자격의 `agent.create`·`agent.update`는 `mcp_servers`·`skip`·`apps`·`permissions`·`extensions`를 받지 않는다(`forbidden`).
- **tool 이름 공간**: 내장 `<자원>.<동사>`, 외부 MCP `mcp__<server>__<tool>`, shell extension `ext__<extension id>__<tool>`, 앱 command는 tool이 아니라 `lophn <slug> <command>`. `lophn` tool 입력은 `{args: string[]}`.
- **prompt 계약**: 입력 tag `lophn-` 접두(`<lophn-steer>`, `<lophn-reaction>`, `<lophn-untrusted>`), notice 종류(`agents_changed`, `tools_changed` 등 바뀐 층·목록, 날짜 `date`), `Workflows folder:` 줄, "Agents you can call" 줄 꼴.
- **저장 모양**: agent 정의 `<data>/agents/<id>.md`(frontmatter + 본문, avatar는 `<data>/agents/<id>/avatar.<ext>`), 지침 `LOPHN.md`(없으면 `CLAUDE.md`)와 앱 source의 `AGENTS.md`, workspace memory `memory.md`와 agent memory `<data>/agent-memory/<agt id>.md`(폴더를 `agents/`와 나눈 것은 `<data>/agents/*.md`를 훑는 옛 data step과 섞이지 않게 하려는 것이다), 설정 층 `extensions.json`, workspace-data `skills/`, 큰 tool 결과 `<data root>/tool-results/<session>/<tool call>.json`, secret `secrets.json`(이름 공간은 위 60), 설치된 SDK `<data root>/sdk`, 파생 catalog `derived/lophn-agent/catalog.json`과 `catalog-state.json`.
- **오류 코드**: 경계에서는 공통 일곱(`invalid_input`, `not_found`, `forbidden`, `unauthorized`, `conflict`, `unavailable`, `internal`)만 쓴다. turn 실패 이유는 `context_limit`, `context_exceeded`, `configuration_unavailable`, `model_unavailable`, `credential_unavailable`, `quota`, `plan_access` 같은 이름이다.
- **data step(옛 data를 새 모양으로)**: `agents.handle`(handle에 옛 name을 채운다, 정의를 schema로 읽는 다른 step보다 먼저), `agents.skills-off`(옛 `skills` → `skills_off`), `agents.drop-domains`(`domains` 칸 삭제), `domains.workspace-data`(domain 폴더 → 그릇 `skills/`), ledger·data step `lophn.split-per-workspace`(전역 `agents/lophn.md`를 Home과 모든 project·앱의 lophn 정의로 복사하고 옛 `lophn` id를 가진 session·job·run·call·settings·secret 이름·layout 탭을 workspace의 lophn id로 옮긴다).

## 결정

- **지침 반영은 대화 끝에 덧붙이기다.** 이유: 조사한 harness는 세 갈래다. session 시작에 고정(Claude Code, Hermes)은 며칠 열린 session에서 `LOPHN.md` 수정이 안 닿고, 매 call 다시 조립(Goose)은 call마다 prefix가 흔들린다. 바뀐 것을 대화 끝에 notice로 알리는 Codex와 OpenCode를 따르되 system은 turn 시작마다 지금 지침으로 만든다. 지침은 거의 안 바뀌어 편집 뒤 첫 turn의 cache miss 한 번이 싸고, notice를 session 기록에 저장해 prefix를 고정하는 쪽은 비용이 크다. 버린 안: 매 model call 직전에 다시 읽기(Goose 쪽). 바뀐 층의 전문을 통째로 notice에 싣고 Added/Removed diff를 없애는 안은 notice가 길어져 그대로 두었다(목록 종류를 더 늘릴 때 다시 본다).
- **cache 표시를 system 둘, 대화 둘로 나눈다.** 이유: 층마다 바뀌는 빈도가 다르고(workspace 종류는 고정, workspace 정보는 자주) 하나로 줄이면 층 하나만 바뀌어도 그 뒤 전체가 miss다. 대화 쪽이 하나면 한 번에 20 block 넘게 늘어난 요청이 앞 cache를 찾지 못한다. 앱 하나를 짓는 turn은 model call이 백 번 가까이라 대화를 cache하지 않으면 매 call 대화 전체가 새 입력이다.
- **sandbox를 따로 두지 않는다.** 이유: 조사한 harness 여덟 가운데 경계를 기본으로 켜는 것은 Codex 하나다. lophn agent는 coding agent보다 직접 하는 일이 적고 workspace가 범위를 정한다. 대신 경로 가두기와 환경 변수 목록을 둔다.
- **MCP와 앱 tool 결과를 감싸지 않는다.** 이유: 일곱 harness 가운데 다섯이 그대로 넣고 server 신뢰 표시로 결과 처리를 바꾸는 곳은 없다. 감싸는 것은 아무도 배정하지 않은 web 결과뿐이다.
- **tool은 자원 하나에 동사 하나(`<자원>.<동사>`)다.** 이유: 효과, 쓸 수 있는 workspace 종류, 상태 전이의 전제, 결과 모양 가운데 하나라도 다르면 나눈다. Gate, rewind, workspace 종류 목록이 모두 tool 단위이기 때문이다. 거르기와 범위만 다르면 인자로 합친다.
- **일의 흐름은 tool로 만들지 않는다.** 버린 안: `app.plan` 같은 흐름 tool. 지침과 skill이 primitive를 엮게 했다. 예: 앱 오류를 고치는 일은 `app.logs`로 읽은 줄을 근거로 앱 workspace의 session이 코드를 고치고 `release.prepare`로 이어 간다.
- **`document.*`를 file tool로 대신한다.** 이유: 문서는 디스크의 file이다. pdf와 이미지만 model에 보이는 모양이 달라 따로 읽는다.
- **workspace 종류 고정 목록과 할당이 옛 preset과 tool 묶음을 대신한다.** 사람이 tool 목록을 고치는 길을 없애고 권한을 바꾸는 길을 할당 하나로 모았다.
- **고정 규칙은 영어 고정 본문 하나다.** 이유: tag의 뜻을 입력마다 반복하지 않고 prefix에 한 번 둔다. 입력에는 값만 싣는다. reaction(`<lophn-reaction>`)은 lophn program이 알리는 사실이고 본문은 고정 문구다. 사용자 앱을 공격자로 보지 않으므로 "data, not instructions"를 붙이지 않는다.
- **command는 사람이 이름으로 부르는 skill이다.** 새 개념을 두지 않았다. role 명령은 같은 이름의 내장 skill이 됐고, core route가 없던 `/recap`과 만드는 곳이 없던 command의 `tool` 갈래는 지웠다. 사람이 tool을 바로 누르는 곳은 앱 화면이다.
- **model이 읽는 내장 skill(`write-*`, `design-app`)은 `/` 메뉴에 띄우지 않는다.** 이유: 사람이 부를 일이 아니고 띄우면 메뉴에 끌 수 없는 줄만 는다.
- **lophn 사용법을 설명하는 skill(옛 `guide-*` 여덟 편)을 두지 않는다.** 0.10.1에서 사람이 지웠다. 설정의 뜻은 `settings.get`이 public 정의에서 읽는다. (사람)
- **skill 발견은 동기 구현 하나다.** 이유: core의 read handler(`ReadSkills`, `ListCommands`, agents read)가 동기라 비동기 발견을 부를 수 없다. turn 준비는 비동기 함수 안에서 동기 함수를 그대로 부른다. file IO는 port로 받아 core module graph에 동기 file API가 없다.
- **공유 skill은 사본을 만들지 않고 active release bundle을 바로 읽는다.** 이유: 사본은 동기화가 틀릴 길만 늘린다. 원본은 앱 source의 `.lophn/skills`이고 release와 같이 봉해서 CLI를 바꾸는 commit에 skill이 같이 들어가고 HEAD의 작업 중 판은 새지 않는다. lophn agent는 bundle을 참조하고 coding agent에게만 사본을 둔다(`architecture/coding-agent.md`). (agent)
- **공유 skill을 정의의 따로 둔 칸에 적지 않고 할당에 붙인다.** 이유: 따로 두면 아는 것(skill)과 부를 수 있는 것(command)이 두 칸으로 갈라져 어긋난다. (사람, 2026-11-02)
- **지침 file은 `LOPHN.md`이고 `CLAUDE.md`를 fallback으로 읽는다. `AGENTS.md`는 앱 층만 읽는다.** 이유: lophn은 본질적으로 coding agent가 아니다. coding agent와 같이 쓰는 `AGENTS.md`를 모든 자리에서 읽으면 다른 도구의 지침이 섞여 사람이 무엇이 prompt에 들어가는지 모른다. 앱 source의 `AGENTS.md`는 앱 template에서 오고 앱 agent가 이미 그 지침 역할로 읽던 file이라 앱 층에 한해 지침으로 읽는다. (사람, 2026-11-02 / 앱 층 2026-11-09)
- **tool 정의를 늦게 싣는 대신 명령으로 묶었다.** 이유: 늦게 싣기(`tool.load`, Anthropic `defer_loading`)는 provider마다 길이 갈렸고 숨길 tool이 늘수록 장치가 커졌다. lophn이 내놓는 일을 명령 표 하나로 두면 lophn agent는 `lophn` tool 하나로, coding agent는 같은 표의 binary로 같은 명령을 쓴다. 두 번 만들지 않고 `tools[]`는 workspace 종류마다 작은 고정 집합이 된다(`project-docs/products/roadmap/command-surface.md`). (사람, 2026-11-01)
- **정의에 일할 범위를 고르는 칸이 없다.** 이유: 예전에는 `domains`가 그릇 안의 domain을 골라 `DOMAIN.md`, domain skill, 비공개 command를 좁혔다. domain을 지우며 칸도 지웠고 칸이 차 있던 agent는 그릇 전체로 넓어졌다. 같은 때 domain 폴더의 `skills/`는 그릇의 `skills/`로 옮기고(이름이 겹치면 뒤 domain의 skill이 `<name>-<domain 이름>`이 된다) `DOMAIN.md`·`kinds.yaml`은 지웠다. 보관 폴더는 만들지 않는다. (agent, 2026-11-03)
- **custom은 정의 본문과 고른 것만 싣고 상한은 lophn과 같다.** 이유: 앱 안 코치나 짧은 일 agent는 lophn 제품 규칙과 내장 tool 전부가 필요 없고 그 bytes가 매 turn 든다. 고르는 칸은 `tools` 하나이고 custom에서만 쓴다(lophn runtime에는 항목별 끄기를 두지 않는다). 고른 것은 workspace 종류 목록, 할당, 설정한 MCP 안에서만 보이고 돈다. credential 상한은 고른 것과 상관없이 workspace 종류로 정한다. system cache 표시는 본문 block 하나에 단다(tools까지 덮는다). 정의에서 뺀 이름은 바로 못 부르고 더한 이름은 새 session부터다. 편집 화면의 내장 tool 목록은 core와 같은 protocol 목록을 쓴다. reply 명령을 모르는 runtime이 result call에 답하지 않아 부른 쪽이 멈추는 일은 자동 답으로 막는다(runtime 쪽이나 transaction 안이 아니라 core가 turn 끝 event를 보고 답하므로 멈춘 turn에 답이 나가지 않는다). custom이 받은 call의 경계는 tag 이름과 메시지마다 붙는 고정 글이 알리고 인터넷에서 온 것만 `<lophn-untrusted>` 한 줄로 알린다. (agent, 2026-11-04) 다 덜어진 상태에서 사람이 skill도 더한다. (사람, 2026-11-04) 그 뒤 lophn 명령과 앱 command는 고르지 않고 `lophn` tool로 늘 받는다: 명령을 이름으로 적게 하니 편집 화면에서 어떤 명령이 있는지 보이지 않아 브라우저를 쓰는 custom agent를 만들 길이 없었다. 명령은 workspace 종류와 할당·Gate가 이미 상한이라 custom이 고르게 둘 이유가 없다. 내장 tool, MCP, extension tool과 skill은 그대로 고른 것만이다. (사람, 2026-11-10) custom이 받은 result call의 답 방식 글은 harness와 같다: 마지막 응답이 답이고 `lophn call reply`로 먼저 답했으면 그것이 답이다. core의 자동 답은 call이 아직 accepted일 때만 보내므로 둘이 겹치지 않는다. (agent, 2026-11-10) `lophn` tool을 늘 주면서 workspace 정보도 싣는다: 명령이 있어도 자기 workspace와 앱 command 이름, 부를 agent를 모르면 쓰지 못한다. 처음에 뺀 이유(작은 agent의 bytes)는 잘 안 바뀌는 목록이라 cache되어 작다. (사람, 2026-11-10) shell.run과 ACP terminal의 자식에는 자격이 없어 그 안의 `lophn` CLI가 사람 자격을 받거나 core를 새로 띄우려 했고 "core가 준비되지 않았다"로 엉뚱하게 실패했다. core가 그 shell env에 `LOPHN_AGENT_SHELL=1`을 넣고 CLI는 agent 자격 없이 그 표시를 보면 바로 `forbidden`으로 멈추고 `lophn` tool을 쓰라고 알린다. (agent, 2026-11-10)
- **명함은 program이 정의와 할당에서 계산하고 저장하지 않는다.** 이유: 사람이 agent가 서로를 고를 명함을 원했고 workspace마다 agent가 열리면 agent 쌍을 하나하나 고르기엔 경우가 너무 많아 call 정책을 크게 정한다. 답 방식은 칸 없이 program이 정한다. custom이 skill을 고르면 `skill.read`를 program이 더한다. (agent, 2026-11-04)
- **큰 명령 결과는 버리지 않고 file로 쓰고 model에는 앞부분을 준다.** 이유: 앱이 질문에 맞는 결과를 내는 것을 model의 한도가 깎지 않게 하려는 것이다. 버린 안: 명령 handler가 결과를 줄이는 것(줄이기는 runtime의 일이다). (사람, 2026-11-02)
- **archived 앱에 묶인 agent 정의는 agent에게 숨긴다.** 이유: 앱 read·call이 archived 앱을 가리는 규칙의 일부다. 사람의 화면은 그대로 본다. (사람, 2026-11-07)
- **memory는 file tool이 아니라 tool 하나로 쓰고 session 첫 turn에 고정해 싣는다.** 이유: file tool로 열면 agent가 다른 agent나 workspace의 memory 경로를 골라 쓸 수 있고 어느 file이 memory인지도 흐려진다. 자리를 입력에서 빼고 부른 agent가 정하게 하면 경계가 한 곳에 있다. 중간에 싣는 글이 바뀌면 prefix cache가 매 turn 깨지고 지침처럼 바뀐 것을 notice로 알리면 agent가 자기가 쓴 글을 되받는 notice가 쌓인다. 그래서 다음 session부터 보이게 하고 notice를 내지 않는다. 8 KiB 상한은 hermes처럼 작게 두어 항상 읽히는 글로 남기려는 것이다. (사람, 2026-11-08, 11-09)
- **memory는 앱·project·agent를 id로 적고 싣는 때 지금 이름을 푼다.** 이유: memory가 이름으로 적은 앱 결정이 이름을 바꾸거나 지운 뒤 같은 이름·slug로 만든 새 앱에 붙어, 업데이트 질문을 건너뛰는 일이 조용히 났다. 버린 안: 앱을 지울 때 프로그램이 memory 줄을 지우기(자유 글이라 정확히 찾을 수 없고 사람의 글을 프로그램이 지운다), 지울 때 Home lophn에게 정리를 시키기(지울 때마다 model 호출이 들고 사람이 모르는 사이 memory가 바뀐다), memory 글을 싣는 때 이름으로 바꿔 쓰기(`old_string` 대조가 깨진다). (사람, 2026-11-10)
- **agent는 secret 값이 필요한 자리를 가리켜 사람에게 요청하고, 이름과 목적지는 core가 읽는다.** 이유: 설정은 agent가 바꿀 수 있어도 secret이 걸린 일(provider 연결, 앱의 API key)은 "Settings에 가서 넣으세요"라는 글로 끝났고, 앱을 짓는 agent가 여기서 가장 자주 막혔다. 값이 보호 창으로만 들어오는 것과 창을 사람이 여는 것은 그대로 둔다. agent가 이름을 정하면 다른 자리의 값을 덮어쓰게 하거나 자기가 고른 목적지로 나가는 이름에 값을 넣게 할 수 있어 자리만 받는다. provider 자리를 home에만 연 것은 모든 workspace의 model 선택과 비용에 걸리기 때문이다. 명령 이름이 `secret request`가 아니라 `ask secret`인 것은 새 명령 묶음 이름이 앱 slug 예약(SDK 판을 올린다)을 요구해서다. `ask`는 이미 예약돼 있다. 대화의 대기 항목에 요청 전용 칸을 두지 않고 질문 내용이 없는 항목을 card가 읽어 가르는 것은 그 칸이 ACP 상태(SDK가 내놓는 type)라서다. (사람이 방향, 2026-11-11 / 나머지 agent)
- **MCP server와 로그인, custom provider도 같은 요청이다. MCP는 session의 자기 workspace 층도 청한다.** 이유: 로드맵은 project·앱 agent에게 자기 정의 층만 열었지만, project나 앱 workspace 층(`extensions.json`)의 server는 그 workspace의 agent가 이미 쓰는 것이고 다른 workspace에는 닿지 않아 사람이 보는 card가 같다. 한 server가 secret 이름을 여럿 가질 수 있어 agent는 이름이 아니라 역할(`part`)만 고른다. 로그인은 값이 없어 card의 [Sign in]이 지금 화면의 흐름을 renderer에서 그대로 돌리고(흐름을 따로 만들지 않고 Settings·앱 상세·card가 같이 쓰는 한 곳에 둔다) 결과만 core에 알린다. 버린 길: shell main이 로그인을 돌리기(device code를 card에 보일 수 없고 흐름이 둘이 된다). custom provider에서 이 컴퓨터의 http 주소는 key가 없어 값을 넣는 자리가 없으므로 요청하지 않는다(사람이 Settings에서 연결한다).
- **memory는 global·workspace·agent 셋이고 lophn은 따로 agent memory가 없다. global memory는 새 파일이 아니라 Home memory다.** 이유: 모든 workspace가 아는 사실이 있어야 하는데(사람의 계정·선호, workspace 지도) 새 파일·새 tool은 쓰는 길과 경계를 하나 더 만든다. 쓰는 쪽을 Home lophn으로 두면 project·앱에서 속은 agent가 모든 prompt에 글을 넣는 길이 생기지 않는다. (agent)
- **memory는 workspace memory와 agent memory 둘이고 lophn은 따로 agent memory가 없다.** 이유: agent memory 폴더를 `agents/`와 나눈 것은 `<data>/agents/*.md`를 훑는 옛 data step과 섞이지 않게 하려는 것이다. (agent)
- **memory tool 이름은 자원 `agent`를 쓴 `agent.memory`다.** 이유: 내장 tool의 자원 이름은 앱 slug로 예약돼야 하는데(앱 slug 예약 목록) 그 목록은 `@lophn/declaration`에 사본으로 들어가 새 예약은 SDK 판을 올리게 한다. `agent`는 이미 예약돼 있다. 앱 agent 지침의 memory 습관은 `@lophn/agent` 1.6.0(minor) 메모로 알린다. (agent)
- **내장 lophn은 workspace마다 하나의 객체다.** 이유: 전역 lophn 하나의 name·model·MCP·끄기·할당이 모든 workspace에 같이 걸렸고 Home과 앱은 사람 설정 층이 없었다. 이제 lophn은 그 workspace의 범위 agent처럼 목록·명함·call 정책·할당·MCP secret이 agent id로 나뉜다. Settings의 전역 lophn 편집은 없애고 전역 `LOPHN.md` 편집은 남긴다. Home 층의 MCP OAuth owner 열쇠는 전역(`global`)과 다른 `home`이다. 전역 lophn의 MCP OAuth refresh token이 lophn마다 복사되어 서로 무효로 만들 수 있다는 문제는 그대로 두기로 닫았다. (agent)
- **model catalog는 OpenCode 꼴이다.** 이유: OpenCode와 Codex는 catalog snapshot을 넣고 실행 때 받는다. 손으로 쓴 목록은 새 model이 나와도 판을 올리기 전에는 쓸 수 없다. models.dev 항목의 `limit.input`이 없으면 context 한도를 입력 한계로 두고 출력 예약은 입력 예산이 따로 뺀다. (사람)
- **오래된 이미지만 빼고 기록은 그대로 둔다.** 이유: tool 호출 기록과 그 출력 blob에는 이미지 base64가 남는다. 기록에서 빼는 길은 model call이 막히지 않으니 실제로 막힐 때 한다.
- **ChatGPT, Claude, Antigravity 구독 연결은 각 제품의 client profile을 따른다.** 이유: ChatGPT는 OpenAI 공식 Sign in with ChatGPT가 아니라 Codex CLI의 공개 client로 로그인한다(공식 token은 `api.openai.com/v1`만 받고 `prompt_cache_key` routing을 줄 수 없어 cache가 거의 맞지 않았다). Anthropic은 제3자 앱의 Claude.ai 로그인과 구독 credential 사용을 허락하지 않고 ChatGPT가 쓰는 Codex backend와 Antigravity가 쓰는 Cloud Code `v1internal`도 공개 API가 아니다. header와 값은 2026-10 조사 snapshot이고 제공자가 보장한 계약이 아니다. 사람이 그 위험을 알고 고른 연결이다. (사람)
- **web 읽기의 redirect hop 검사와 DNS 해석 검사.** 남긴다. 이유: 인터넷 내용이 사람 PC 내부 주소를 치지 못하게 막는 권한 경계이고 줄일 이유가 약하다. DNS 해석 검사는 더하지 않는다.
- **compact 요약 재료의 data 경계와 제어 token·동형 문자 정리를 남긴다.** 이유: 대화에 web 결과가 섞여 있어 이것은 인터넷 방어이고, 지워서 줄어드는 것은 정규식 몇 줄이다.
- **끌 수 없는 내장 skill과 같은 이름의 사람 skill을 제외 사유와 함께 남긴다.** 이유: 이것이 없으면 사람이 만든 skill이 왜 안 보이는지 알 수 없다.
- **MCP tool 이름 변환을 남긴다.** 이유: wire 규칙 때문에 길거나 이상한 MCP tool 이름은 어차피 바꿔야 한다.
- **tool 목록에서 빠진 tool은 이유를 구별하지 않고 `not_found` "tool is not available" 하나다.** 이유: 이유를 구별하는 길은 쓰이지 않았다. 반쯤 만들고 안 쓰는 길은 지우고 필요해지면 다시 만든다.

## 열린 것

- 파일 읽기가 pdf와 이미지 말고 docx 같은 형식을 못 읽는다. 필요해지는 형식 하나씩만 더한다(이슈 `file-read-lacks-docx`).
- provider 실패의 응답 본문은 남기지 않아 본문이 HTML 오류 page인지 다른 꼴의 SSE인지 같은 내용 갈래를 모른다. `unknown`일 때만 본문 앞부분을 redaction을 거쳐 남길지는 secret 경계의 규칙을 바꾸는 것이라 사람이 정한다(이슈 `provider-failure-body-not-kept`).
- Home memory의 workspace 지도를 채우는 길이 없다. project·앱 prompt에 Home에 알리라는 말이 없다. 추천은 project·앱 prompt에 알리기를 더하는 것이다(앱 agent가 읽는 prompt라 SDK 메모 판단이 필요하다)(이슈 `home-memory-workspace-map-empty`).
- 이미 있는 provider id로 연결하면 `conflict`로 끝나는데 값은 이미 덮어쓴 뒤라 그 provider의 key·token이 새 값으로 바뀐다. 끊기에서 secret 값 정리는 best-effort라 누락될 수 있다. 값을 쓰기 전에 그 id가 있는지 보거나, 연결이 성공한 뒤에 옮기는 안이 있다(이슈 `provider-id-overwrite`).
- web 읽기의 DNS 재바인딩은 검사하지 않는다.
- tool 결과의 이미지 base64는 tool 호출 기록과 출력 blob에 그대로 쌓인다. 실제로 막힐 때 줄인다.
- 입력 token 추정은 byte 기반이라 대개 실제보다 크게 센다(낮게 센 경우만 provider 거절로 줄인다).
- catalog를 즉시 새로 받는 route와 화면은 없다. 자동 갱신 설정은 다음 기동부터 적용된다.
