# 환경마다의 길: 붙는 길과 앱 data가 가는 길

상태: 로드맵. 2026-11-17 사람이 원칙을 내고 planner가 정리했다. 붙는 길의 첫 걸음(직접 주소를 pairing 뒤에도 새로 받기, 사람이 적는 주소)은 계획 `issue-sweep`이 한다. 나머지는 아직 계획으로 열지 않았다.
배경 문서: `project-docs/architecture/remote.md`, `project-docs/architecture/folder-sync.md`, `project-docs/architecture/app-sync.md`, `project-docs/architecture/machine.md`, `project-docs/products/roadmap/multi-machine.md`.

## 사람의 말 (원문)

> 중심 기계를 둔다/아니다 와 간단한 문제가 아니라니까? 사용자 환경이 다 다른데 어떻게 해. 그에 맞춰서 우리가 길을 준비해놔야하는거라고. vm 없으면 file에다 google drive 붙여서 쓸 수 있게, tailscale 없으면 한계를 감안하고 우리 relay 서버, vm이 있으면 사용자의 선택의 폭이 가장 높아지는거고

> 근데 사실상 폰을 hub로 쓸 수도 있게 하는 선택지도 제공할 수 있는 거 아니야? 어짜피 예를 들어서 calendar data 같은 것들은 엄청 작을텐데? 큰 데이터는 WIFI 연결 되었을 때만 보내기 이런 설정 같은 걸 할 수 있게끔하고

## 원칙

- lophn은 사용자의 환경을 요구하지 않는다. 사용자가 가진 것에 맞는 길을 준비해 두고, 환경이 좋을수록 더 좋은 길을 쓴다.
- 길은 lophn이 환경을 보고 스스로 고른다. 사람에게는 지금 어느 길인지를 보이고, 길을 고르게 하지 않는다.
- 중심 기계를 "둔다, 안 둔다"를 정하지 않는다. 늘 켜 둔 기계가 있으면 쓰고 없으면 다른 길로 간다.
- 길이 달라도 주고받는 것의 꼴은 같다(`folder-sync.md`의 file 꼴). 길은 운반 수단이다.

## 붙는 길

폰이나 다른 기계의 desktop이 한 컴퓨터에 닿는 길이다.

| 사용자 환경 | 길 | 한계 | 지금 |
|---|---|---|---|
| 아무것도 없음 | lophn relay | 속도와 크기 한도, relay를 한 번 거친다 | 된다 |
| 같은 network | 직접 | 밖에서는 안 된다 | 된다 |
| Tailscale | 직접(어디서나) | 양쪽에 깔아야 한다 | pairing할 때 켜져 있었으면 된다 |
| 공인 주소가 있는 VM | 직접(어디서나) | 사람이 주소를 적어야 한다 | 안 된다 |

할 것:
- 직접 주소를 pairing 뒤에도 새로 받는다. 사람이 적는 주소를 둔다(계획 `issue-sweep`, 이슈 `phone-direct-addresses-fixed-at-pairing`).
- 사람이 적는 주소의 설정 화면(Settings › Remote).
- Tailscale을 켠 실제 두 기기로 직접 붙는지 확인한다(사람).
- 인터넷에 port를 연 기계의 방어(접속 시도 제한). VM에서 필요해진다.

## 앱 data가 가는 길

여러 기계의 앱 data를 맞추는 길이다. 아래로 갈수록 환경이 좋고 빠르다.

| 사용자 환경 | 길 | 사람이 할 설정 | 늦는 정도 | 지금 |
|---|---|---|---|---|
| 컴퓨터 한 대와 폰 | 폰이 그 컴퓨터를 거친다 | 없음 | 컴퓨터가 켜져 있으면 바로 | 된다 |
| 컴퓨터 여러 대와 폰 | 폰이 나른다 | 없음 | 폰 앱을 열 때 | 없다 |
| 폴더 도구(Google Drive, Syncthing) | 폴더 | 도구 설정 | 분 단위 | 된다(설정 화면 없음, 실제 도구로 확인 안 함) |
| 늘 켜 둔 미니 PC | 그 기계를 거친다(연결로) | 기계 하나를 켜 둔다 | 바로 | 폴더로만 된다 |
| 빌린 VM | 그 기계를 거친다, 주소가 고정이다 | VM 설정 | 바로 | 안 된다 |

### 폰이 나른다

- 폰은 사람이 늘 들고 다니고 집과 회사의 컴퓨터에 다 닿는 기기다. 폴더 도구도 늘 켜 둔 기계도 없는 사람의 기본 길이 된다.
- 폰은 기준이 아니라 운반 수단이다. 한 컴퓨터가 낸 변경 묶음을 받아 두었다가 다른 컴퓨터에 붙었을 때 넘긴다. 합치는 것은 받는 컴퓨터가 지금 규칙(덮지 않고 합친다)으로 한다. 폰을 잃어도 못 전한 묶음이 늦어질 뿐이다.
- 폰에 화면이 없는 앱의 data도 내용을 모르고 나른다. 전하고 나면 지운다.
- 크기 규칙: 작은 묶음은 언제든 보내고, 큰 묶음(기준 크기는 설정)은 Wi-Fi일 때만 보낸다.
- 지금은 폰이 컴퓨터마다 앱 사본을 따로 가지고 서로 넘기지 않는다(`app-sync.md`).
- 한계: 폰 앱이 뒤로 가면 연결이 끊기므로 사람이 앱을 열 때 움직인다. 뒤에서 나르려면 OS의 background 작업이 든다.

### 늘 켜 둔 기계를 거친다

- 컴퓨터끼리도 remote 연결로 앱 data를 맞춘다. 지금은 폰만 이렇게 하고 컴퓨터끼리는 연결이 있어도 보기에만 쓴다.
- 늘 켜 둔 기계가 맡아 두는 곳이 된다. 꺼져 있던 기계는 켜지는 대로 그 기계와 맞춘다.
- 그 기계가 꺼지면 이 길은 멈춘다. 그때는 다른 길(폰, 폴더)이 있으면 그 길로 간다.

### 화면 없는 VM

- 화면 없이 처음 설정하는 길(provider, key, remote 켜기)이 없다(`multi-machine.md`의 "하지 않는 것").
- 터미널과 coding agent의 GUI가 desktop 앱 쪽에 있어, 화면 없는 기계에서는 폰이 coding agent 터미널을 열 수 없다(`headless-schedule.md`, `standalone-core.md`).

## 사람이 정할 것

- 순서. planner의 추천: 붙는 길 다듬기 → 폴더 길의 설정 화면과 실제 도구 확인 → 폰이 나른다 → 늘 켜 둔 기계를 거친다 → 화면 없는 VM. 사람이 VM을 곧 쓸 계획이면 뒤의 둘을 당긴다.
- 한 앱의 data가 두 길로 같이 갈 수 있는가(폰과 폴더). 받는 쪽이 같은 묶음을 두 번 받아도 한 번만 적용하면 되므로 planner의 추천은 "된다"다.
- 대화(session)는 옮기지 않는다는 지금 결정을 그대로 둘지. planner의 추천은 그대로 둔다(그 기계에 붙어서 본다).

## 하지 않는 것

- lophn의 relay나 서버가 사용자 data를 맡아 두기(`multi-machine.md`).
- 길을 사람이 손으로 고르는 설정. 예외는 큰 묶음의 Wi-Fi 규칙처럼 비용에 걸린 것이다.
